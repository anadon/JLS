# Issue #795: TASK-C585-2: in-app help computes its "open in browser" URL from the topic id, and the hosted site gets the same link strictness plus working search
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of the ask

Part of FEAT-C35-2 (#585), split into TASK-C585-1 (#794, publishing/versioning) and this task (#795): compute the in-app "open in browser" link from the topic id + running version (AC-1/AC-2), extend CI link-integrity checking to the hosted site (AC-3), and ship client-side search plus no-JS degradation (AC-4).

## Findings, most severe first

### 1. [High] AC-2's version-fallback check requires either a network probe or an unspecified bundled manifest, and the parent issue itself already flagged this exact risk as unresolved

AC-2: "falls back to `latest` only when the running version has no published site — reporting the fallback rather than doing it silently." Determining "has no published site" for the *running* version means either (a) an HTTP probe from the desktop app at click time, or (b) a list of published versions baked into the jar at build time and kept in sync with every future release. Neither is named. Option (a) contradicts the project's own recorded decision: ARCHITECTURE.md's "Help delivery" section states help "must work offline" and the in-jar viewer is deliberately self-contained; README nowhere describes JLS phoning home. This is not a hypothetical concern I'm inventing — the parent issue #585's own boundary-note comment names it directly: "Offline parity stays #584's and this issue may not erode it... AC-3's computed links are exactly where that invariant would leak" (referring to #585's AC-3, which is this task's AC-1/AC-2 territory). #795 restates the acceptance criteria but does not restate or discharge that risk; a reviewer reading only #795 would not know the fallback mechanism was already called out as unresolved by a sibling document. **Recommendation:** name the mechanism explicitly (bundled version manifest generated at release time, no runtime network call) and state that a network probe is out of scope, closing the loop #585's comment opened.

### 2. [Medium] AC-1's "documented rule" cannot actually be authored yet — the URL structure it documents is decided by a still-open, still-unimplemented prerequisite

AC-1 requires "a documented rule" mapping in-jar topic id to hosted URL. But the hosted site's shape (source format, whether `.html` extensions survive, directory-style vs flat URLs) is the explicit subject of TASK-C584-1 (#791, "the help source format is chosen and recorded") and TASK-C584-3 (#793, "the same source emits the static site target") — both open, both unimplemented, both upstream of this task's own declared dependency chain (#795 → #794 → #793 → #791/#792). Writing and testing a "documented rule" today is premature: the rule can't be pinned until #791/#793 land. This isn't fatal — the `ordering_after: [TASK-C585-1]` chain does transitively sequence after #793 — but it means this task's 0.5-1 mw estimate was made before the shape of the thing it maps *to* exists, and #585's own comment separately warns that a topic-id rename during #584's migration "breaks every computed 'open in browser' link here" — a risk #795 depends on but does not itself guard against with an AC (e.g., no criterion here asserts topic-id stability is a tested precondition before this task starts). **Recommendation:** add an explicit precondition/AC that topic-id stability (from #584/#793) is verified before this task's rule is authored, not merely assumed.

### 3. [Medium] AC-3's CI scope is ambiguous between a hermetic local build and the live deployed site, with real cost implications either way

"CI checks link integrity across the hosted site with the strictness the in-jar tree gets; a dead cross-link fails the build" — but the *strictness* precedent, `HelpTopicsTest` (test/jls/HelpTopicsTest.java, per its own doc comment "every Map.jhm url must exist as a bundled resource... every bundled help file must be reachable"), is a hermetic classpath check with zero network I/O. If AC-3 means "crawl the actually-published hosted site," that's a network-dependent CI step (flaky, slow, and per #794's AC-3 there will eventually be multiple live *older* versions — is CI expected to re-crawl every previously published version on every push, forever?). If it instead means "build the site artifact locally in CI and link-check that," it's hermetic and cheap but doesn't verify what AC-2 depends on (that a version's *deployed* URL actually resolves). The issue doesn't say which, and the two readings have very different cost/feasibility profiles. **Recommendation:** state explicitly that AC-3 checks the CI-built site artifact (hermetic, matching the in-jar precedent), and that live-deployment verification (if wanted) is a separate, explicitly-scoped smoke test with its own failure-handling story for third-party outages.

### 4. [Medium] AC-4 bundles two independently-falsifiable claims into one criterion, and "search" is unspecified enough to be gameable

AC-4 = "search returns the expected page for a committed spot-check fixture set" AND "the site degrades to a usable static browse with scripting disabled." These are unrelated mechanisms (a search index vs. a no-JS navigation fallback) with independent pass/fail conditions, forced into one AC — the same anti-pattern flagged in the sibling review of #587 (issue-reviews/issue-0587.adversarial.md, finding 5) for this same documentation cluster. As written, "search returns the expected page for a fixture set" can be satisfied by a hand-coded lookup table of fixture terms → pages with no real search engine behind it — technically passing while the stated goal ("working search," per the issue title) is not met for any query outside the fixture. No search technology is named (client-side index size, build-time generation, e.g. Lunr/Pagefind-class tooling), which also means no one has checked its license fits a GPLv3 project the way this codebase normally vets dependencies (FlatLaf's license/footprint is audited in docs/flatlaf-evaluation-2026-07.md; ELK's EPL-2.0 was deliberately kept out-of-process per ARCHITECTURE.md's #222 section) — a hosted-site-only JS library is very likely fine since it never links into the Java binary, but this issue is silent on it where the project's own precedent is not. **Recommendation:** split into two ACs, name a candidate search implementation and its license, and require the fixture set to exercise the real index (not a lookup shim) — e.g. via a query the fixture term does not appear in verbatim.

### 5. [Low] "reporting the fallback rather than doing it silently" (AC-2) has no specified surface, so it's satisfiable in a way a user never sees

No UI mechanism is named — a debug-level log line technically "reports" the fallback without any student or instructor ever seeing it, which defeats the stated purpose (avoiding silent staleness). **Recommendation:** name the surface (status text near the link, a tooltip, whatever fits the Swing help viewer) so the criterion is testable against something a human actually encounters.

## What's solid

- The task decomposition itself (publishing/versioning in #794 vs. link-computation/search/CI in #795) is a reasonable split of #585, and the `ordering_after` chain, while not spelling out every transitive hop, does correctly sequence behind the site-generation prerequisites when followed through #794.
- AC-1's core mechanism — deriving the link from a rule "asserted over the whole topic set" rather than hand-maintained per-page — is the right shape and mirrors the project's existing completeness-ratchet pattern (`HelpTopicsTest`'s topic/page reachability checks).
- The distinction the parent issue draws between this task's AC-3 (link integrity: dead link) and #587's AC-1 (claim accuracy: live but wrong link) is correctly non-overlapping and well-documented in #585's comment thread, so there's no double-counted work here.

## Net assessment

The task is well-placed in the dependency graph and its core idea (computed, asserted links) is sound, but three of its four acceptance criteria have real gaps: AC-2 revives an offline-erosion risk the parent issue already flagged and never closes, AC-3's CI target (hermetic build vs. live site) is unstated with materially different cost profiles, and AC-4 conflates two mechanisms behind one gameable fixture check. Worth a rework pass on the acceptance criteria before estimation or implementation starts.
