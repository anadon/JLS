# Issue #689: TASK-C532-2: "why did this change?" renders the ancestor chain of a selected transition, each hop naming its element and its consumed delay
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

A GUI rendering task that presumes a working, well-specified "retained relation" and "accessor" from its prerequisite (TASK-C532-1, #688) and a well-defined "selected transition" input from its other prerequisite (TASK-C529-1, #684) — neither of which is itself settled, per the sibling adversarial reviews on file (`issue-reviews/issue-0532.adversarial.md`, `issue-reviews/issue-0529.adversarial.md`) and per direct inspection of the current codebase. On top of that inherited risk, #689 introduces its own gaps: no acceptance criterion in this issue names a concrete test (a sharp break from the family's own pattern), AC-1's "chain" framing implicitly assumes linearity that the underlying event model cannot guarantee before reconvergent-fan-in support (TASK-C532-3, #691) exists, and AC-4's "is not constructed at all" claim is unfalsifiable as worded.

## Findings, most severe first

### 1. HIGH — the issue builds a rendering surface on a producer/consumer relation that does not exist in the current event model, and does not flag this as a risk to itself
The Outcome text says the inspector "walks TASK-C532-1's retained relation backwards." Checked against the actual event model:
- `SimEvent.PinChanged` is a zero-field record (`src/jls/sim/SimEvent.java:30-31`): `public record PinChanged() implements Payload {}` — no producer, pin, or wire reference.
- `WireNet.propagate` computes the winning driver during tri-state resolution and then discards it (`docs/capability-roadmap/lf-03-causal-debug.md:15-29`, quoting `src/jls/elem/WireNet.java:484`: `value = actual; // :484 — the driver identity is dropped`), for what that same document says is 82.3% of all events fired.
- `Reacts.react(long now, Simulator sim, SimEvent.Payload todo)` gives the reacting element no per-pin identity at all.

`issue-reviews/issue-0532.adversarial.md` finding 1 already flags this against #532/#688: a "producer-to-consumer relation" must be *synthesized*, not retained, and per-hop attribution for reconvergent inputs is not something the current event keying can ground. #689 inherits that problem wholesale — AC-1's "ancestor chain hop by hop, each hop naming the element" is exactly the rendering of the relation #688 has not been shown able to produce — yet #689 treats #688's accessor as a settled black box ("The inspector reads only TASK-C532-1's accessor") and raises no contingency for the case where that accessor cannot resolve a unique producer per hop.
**Recommendation:** Do not treat #688 as a stable, resolved dependency. Add an explicit note that #689 is blocked on #688's causal-attribution mechanism being designed (not merely "landed"), and state what #689 does if the accessor can only offer element-level, not per-pin, attribution at a reconvergence point.

### 2. HIGH — no acceptance criterion in this issue names a verification test, breaking the family's own testing discipline
Every sibling in this family names a concrete test: #532 (parent feature) names `CauseChainCompletenessTest`; #691 (TASK-C532-3) names the same test plus explicit two-directional-failure demonstration; #529/#684 name `HazardDiagnosisWalkthroughTest` and `ChronogramClosedCostTest`; #688 uses `ChronogramClosedCostTest`. #689's four ACs are all prose: "renders its ancestor chain hop by hop… with a running accumulated total" (AC-1), "the chain terminates explicitly… says so rather than presenting a partial chain as complete" (AC-2), "no synthetic granularity… is introduced" (AC-3), "is not constructed at all in headless/batch runs" (AC-4) — none cites a test class or method. This is also a direct conflict with `test/jls/ui/package-info.java`'s stated discipline ("every helper assertion in this package is itself pinned by at least one deliberately-failing test… so the harness cannot silently pass on an empty circuit") and with ARCHITECTURE.md's Layer 1/2/3 UI-verification model, neither of which #689 references even though it is squarely a rendering feature (`area:gui`, `area:sim`). As written, a PR could add the inspector panel, eyeball it once, and claim all four ACs "addressed" with no CI gate blocking a regression.
**Recommendation:** Name a test for each AC (e.g., a Layer-1 `CircuitAssert`-style check that the rendered chain's elements/delays/total match a fixture's known ancestor set for AC-1; an explicit truncation-fixture test for AC-2; a headless-build class-loading/construction-count assertion for AC-4), specifying which harness layer each belongs to.

### 3. MEDIUM — AC-1's "chain" framing assumes linearity the event model cannot promise before #691 lands, and nothing requires the inspector to say so
AC-1: "the inspector renders its ancestor chain hop by hop, each hop naming the element and its consumed delay, with a running accumulated total." AC-2 reinforces the linear framing: "The chain terminates explicitly — at a primary input, a clock, or the retention window's edge." Reconvergent fan-in — an element whose output event has more than one plausible producer among its inputs — is real and is explicitly the subject of the sibling task #691 ("A transition with reconvergent fan-in renders as distinct paths… TASK-C532-3, ordering_after: [TASK-C532-2]"), i.e. #691 is scheduled to land *after* #689 and to add multi-path rendering. That means #689, taken as shippable on its own (it is `tier:task`, independently completable per the project's own "task" granularity), must render *something* for a reconvergent hop before #691 exists to handle it properly. Nothing in #689 specifies what that something is: pick one producer arbitrarily and call it "the" ancestor? Refuse to render past that hop? Both are plausible readings of "hop by hop… accumulated total," and the wrong one — silently picking one of two unequal-delay paths and presenting it as *the* cause — is precisely the misleading behavior the parent capstone (#504) exists to prevent ("hazards stop being an instructor's assertion and become something the tool can point at"). AC-1/AC-2 as worded would be satisfied by a PR that always follows, say, the first input pin at every hop, silently wrong for glitches, and no test in this issue would catch it (see finding 2).
**Recommendation:** Add an explicit AC for the single-producer-ambiguous case: either the inspector must render an explicit "multiple candidate ancestors, see TASK-C532-3" marker rather than picking one silently, or #689 must state it is out of scope for any circuit exhibiting reconvergent fan-in on the selected transition's own dependency chain (with a test asserting the marker/refusal, not just the happy path).

### 4. MEDIUM — AC-3's citation of "CAP-23 Open Question 1's recommended default" treats a filing-blocking open question as pre-resolved without a recorded decision
CAP-23 (#504) lists Open Question 1 verbatim: "Cause-chain granularity: per-net or per-element-port events? Recommended default: whatever the scheduler already keys on, exposed honestly — no synthetic granularity the engine does not have. **Blocks PF-3's filing.**" The "Blocks PF-3's filing" annotation is the capstone author's own gate: it says this question must be *decided*, not merely defaulted, before PF-3 (which #532, #688, #689, #691 are all decomposed from) is filed. #689 (like #532 before it, per that issue's own review) cites the "recommended default" language as if it were an adopted decision, but no REPLAN comment or decision record resolving Open Question 1 appears on #504 (the issue's only comment, dated 2026-08-04T03:12:12Z, discusses a different topic — the #508 ratchet conflict — not this open question). #689 was filed 2026-08-04T15:21:01Z, roughly 12 hours after PF-3 (#532) itself, with the gating question still nominally open on its parent capstone.
**Recommendation:** Get an explicit decision comment on #504 closing Open Question 1 (even if it simply ratifies the recommended default), and cite that comment from #689 rather than re-citing the open question's own recommended-default text as though citing it were the same as resolving it.

### 5. LOW — AC-4's "is not constructed at all in headless/batch runs" is a reasonable design goal but unfalsifiable as an acceptance criterion
Compare to the family's actual pattern for this exact class of claim: `ChronogramClosedCostTest` (used by #527/#529/#688) measures *cost* with the panel closed but the class still loaded/constructible; `HeadlessCoreRatchetTest` (ARCHITECTURE.md, `jls.sim`) enforces *no AWT/Swing imports* in `Simulator`/`BatchSimulator` at the package level. AC-4's claim is a third, stronger thing — the inspector class must never be instantiated at all in batch mode — but names no analogous ratchet test (e.g., a batch-mode smoke test with class-load/instantiation counters, or a package-import-boundary check placing the inspector under a GUI-only package `HeadlessCoreRatchetTest`-style enforcement could reach). Without one, "not constructed at all" reduces to a code-review judgment call that can silently regress the next time someone wires the inspector into a shared code path for convenience.
**Recommendation:** Either point AC-4 at an extension of `HeadlessCoreRatchetTest`'s pattern (package-boundary enforcement) or add a dedicated construction-counter test exercised under `-b` batch mode.

## What's solid
- Ordering after both #688 (the data source) and #684 (the selection input) is the correct dependency shape in principle — the inspector genuinely cannot exist meaningfully before either lands, so the ordering itself is not wrong, only optimistic about what "landed" will mean (finding 1).
- AC-2's requirement that a window-truncated chain say so explicitly, rather than silently presenting a partial chain as complete, is a good instinct and directly forecloses one obvious way this feature could be quietly wrong.
- Scoping the inspector to read only #688's accessor (AC-4) rather than the concrete retention buffer is consistent with #504's stated seam requirement ("a stable seam over the event structures, not the concrete queues") and with the project's general seam discipline (`docs/extension-points.md`).
- The task is appropriately small in ambition relative to its sibling #691 — deferring reconvergent-path rendering to a separate task is a sound decomposition in principle (see finding 3 for the gap in how #689 alone should behave in the meantime).

## Verdict rationale
The task inherits an unresolved, evidence-backed foundational problem from its own prerequisite (finding 1) without acknowledging it, specifies zero testable verification for any of its four acceptance criteria against a project culture that otherwise insists on invariant-checked tests everywhere in this exact feature family (finding 2), and leaves undefined exactly the ambiguous-ancestor case that a "why did this change?" tool must get right to be trustworthy rather than actively misleading (finding 3). None of this makes the concept unsound, but none of it should be discovered mid-implementation either — needs-rework.
