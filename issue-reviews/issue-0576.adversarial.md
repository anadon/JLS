## Findings

### 1. [Critical] The issue body is self-contradictory, and the project's own fix lives only in a comment, not in the body
The machine block still reads:
```yaml
ordering_after: ["#300 CAP-06 verdict slice / #369 FEAT-053 (the verdict and report this consumes)"]
```
while AC-5 says the opposite: *"if the CAP-06 verdict slice slips, this ships against today's three-exit-status contract — degraded but real."* One field defers the feature indefinitely behind an entire capstone (#300 is `tier:capstone`); the other explicitly licenses starting today. The 2026-08-08 round-2 comment on this very issue calls this out in detail ("A scheduler reading the machine block defers this feature indefinitely; a scheduler reading AC-5 starts it today") and prescribes a fix (`ordering_after: []`, a per-criterion table pointing AC-2/AC-3 at `#466` instead of `#300/#369`). That correction is real and well-reasoned, but as of this review **it has not been applied to the issue body** — it exists only as comment `#issuecomment-5227455669`. Any tool or reader that consumes the body (the machine block, the AC list) rather than the full comment thread still sees the contradiction. Recommendation: edit the issue body itself to replace the `ordering_after` block and cross-reference the correction, not just leave it as a comment trailing a stale body.

### 2. [High] AC-2/AC-3 have a gameable escape hatch that outlives the round-2 fix
AC-2 requires verdicts "consuming CAP-06's report slice" (i.e. #466's engine, per the comment's own table). AC-5 permits shipping without it, "degraded but real," against today's plain 0/1/2 exit contract. Fine as stated for AC-2. But AC-3 requires the CI walk to catch a planted failure and "attribute it to the right student," and the Outcome paragraph and sibling task #757 both promise verdicts "with counterexamples." Pre-#466, there *is no counterexample* to attribute — only a bare nonzero exit code. AC-3 carries no explicit degraded-mode carve-out the way AC-2/AC-5 do. That leaves two readings: (a) AC-3 is satisfied by "which student's exit code went nonzero," a much weaker claim than "verdicts with counterexamples," or (b) AC-3 implicitly requires #466 and AC-5's "degraded" ship can't actually close AC-3. The issue doesn't say which, so an implementation could pass a CI test that greps a failing student's name out of a plain exit-status run and call AC-3 done, while the "why did this student fail" promise in the Outcome section (and #757's own criterion) goes unmet. Recommendation: state explicitly whether AC-3's degraded form is bare pass/fail attribution or requires a counterexample, and if the latter, make AC-3 (like AC-2) conditionally deferred rather than silently assumed continuous.

### 3. [High] The issue claims a parent/child relationship to #755/#757 that GitHub's own structure does not show
The round-2 comment refers to "this issue and its child #755," and #755/#757 both carry `part_of_feature: 576` in their bodies. But `issue_read get_sub_issues` on #576 returns an empty list, and #755's own `get` reports `has_parent: false`. There is no formal GitHub sub-issue link tying #576 to the two tasks the comment says now own AC-1 (#755) and AC-2/AC-3 (#757). Meanwhile #576's own body still lists all five ACs undifferentiated, as if #576 itself must deliver all of them — it has not been edited to say "AC-1 is now #755, AC-2/AC-3 are now #757." A reader relying on GitHub's hierarchy view (or an automated closer that walks sub-issues) will not discover #755/#757 from #576, and closing #576 without a structural link leaves no traceable proof the decomposed work actually covers the original ACs. Recommendation: use the actual sub-issue relationship (or explicitly restate in the body which ACs moved where), not prose alone.

### 4. [Medium] Estimate reconciliation is invisible
#576 itself is banded `2-3` (mw). Its two spun-off tasks are banded separately: #755 at `0.5` and #757 at `1-1.5`, covering AC-1 and AC-2/AC-3 respectively — that's 1.5–2 mw for three of the five ACs, with AC-4/AC-5 (robustness, degraded-mode documentation) apparently left to #576 proper. Nothing in #576 states whether its 2-3 mw figure is inclusive of the children's estimates (i.e., #576 now just tracks AC-4/AC-5, closer to 0.5-1mw) or additive on top of them. As filed, the estimate double-counts or under-counts depending on interpretation — a scheduler can't tell which without inference.

### 5. [Medium] AC-4's "named per-student result" doesn't anchor to the codebase's existing structured-error convention
`ARCHITECTURE.md` documents a deliberate, tested `LoadError` taxonomy (`IO_ERROR`, `NOT_A_CIRCUIT`, `MALFORMED`, `NEWER_FORMAT`, `UNKNOWN_ELEMENT`, `ELEMENT_ERROR`, `LIMIT_EXCEEDED`, issue #58) as the project's one way to report structured failures across every front end. #576's AC-4 ("malformed, missing and renamed submissions produce a named per-student result") never says whether that result routes through `LoadError`-style categories or invents a parallel, cohort-grading-specific vocabulary. Given the project visibly cares about not growing parallel error taxonomies (see #466's careful gating of a *new* exit status 3, and its explicit "a broken grader scores every submission as wrong" failure-mode discipline), leaving this open invites an implementation that reinvents the taxonomy instead of reusing it.

### 6. [Low] AC-3 and AC-4 are never required to be exercised together
AC-3's CI walk plants exactly *one* mutated submission; AC-4 separately demands correct handling of malformed/missing/renamed submissions. Nothing requires the single CI walk to include a mix of a clean pass, the planted-failure student, and a malformed/missing/renamed submission all in the same cohort run. An implementation can satisfy AC-3 with an all-well-formed cohort and satisfy AC-4 with a disjoint, narrower unit test — never proving that per-student attribution still works correctly when the cohort is a *mix* of failure classes, which is the realistic case (a real class submission directory will have some late/misnamed/corrupt entries alongside real failures).
