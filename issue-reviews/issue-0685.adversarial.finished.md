# Issue #685: TASK-C529-2: clicking a wire lands on its chronogram lane, creating the lane if the signal was never displayed — and the round trip is a scripted offline test
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

The canvas-wire → chronogram-lane half of cross-probing, split out of #529 (FEAT-C23-2) as the second of two tasks (#684 = TASK-C529-1 is the first). The individual acceptance criteria for the wire-click direction are reasonable and build on hit-testing that already exists. But AC-3's central verification claim contradicts the parent capstone's (#504) own written definition of the test it cites, the same test has real prerequisite features that neither #685 nor its declared dependency chain reaches, and AC-4's "same identity seam" claim papers over a granularity mismatch that the repository's own simulation code makes concrete.

## Findings, most severe first

**1. (HIGH) AC-3's test-step sequence contradicts CAP-23's (#504) own canonical definition of that same test.**
#685's Outcome states the "scripted, fully offline `HazardDiagnosisWalkthroughTest` leg runs trigger → capture → edge click → element flash → wire click → lane focus without a human," and AC-3 says this test "runs the full round trip ... and fails if either direction stops resolving." But #504 (CAP-23) defines this exact test's gate as: "**AC-1** (`HazardDiagnosisWalkthroughTest`). The full §1 steps 1–2 walk (trigger, capture, edge click, cause chain naming both unequal-delay paths) passes as a scripted GUI test, entirely offline. Spans PF-5+PF-1+PF-2+PF-3." The canonical walk ends in a **cause-chain** step (PF-3, #532) — there is no wire-click-to-lane step anywhere in #504's §1 or its AC-1 definition, and #685's six-step description drops the cause-chain step entirely. Either #685 is silently redefining a test whose canonical scope is owned by #504 (no `REPLAN:` comment on #504 records this), or an implementer satisfies #685's literal AC-3 wording with a class that isn't actually the CAP-23 AC-1 gate despite sharing its name — in which case "fails if either direction stops resolving" is an unverifiable claim about a test that, per #504, doesn't test that direction at all.
**Recommendation:** either name a distinct test for the wire→lane leg and stop invoking `HazardDiagnosisWalkthroughTest`/CAP-23-AC-1 for it, or post a `REPLAN:` comment on #504 that amends AC-1's defined step sequence to include (or explains how it coexists with) the wire-click leg, and reconcile the missing cause-chain step.

**2. (HIGH) AC-3's cited test has undeclared prerequisites #685 cannot reach through its own dependency chain.**
`HazardDiagnosisWalkthroughTest`'s "trigger → capture" opening (also asserted in #685's own Outcome text) is FEAT-C23-5 (#534, open), whose own AC-2 states: "firing on the shipped hazard-demo's runt pulse opens the chronogram centered on the capture (**CAP-23 AC-1 leg**)." #685's `ordering_after: [TASK-C529-1]` (#684) chains to `[TASK-C527-2]` (#680) chains to `[TASK-C527-1]` (#678) — a complete, self-consistent path to the chronogram tap and panel, but it never reaches #534. No matter how correct #685's own code is, the test it cites as its acceptance gate cannot run to completion until a feature outside its declared dependency graph also lands. (The same gap was independently found against sibling #529 at the FEAT level; it recurs here, unresolved, at the TASK level that would actually be implemented.)
**Recommendation:** add `#534` to `ordering_after` (or explicitly scope AC-3 to a test double / pre-armed capture fixture that doesn't require the live analyzer element), and state which of #504's AC-1 prerequisites this task's test build actually assumes are present versus stubbed.

**3. (MED-HIGH) AC-4's "single resolution path" claim conflates two different identity domains, one of which is proven lossy in this codebase.**
AC-4: "Both directions resolve through the same identity seam TASK-C529-1 uses — a single resolution path, not two that can disagree." TASK-C529-1 (#684, AC-2) resolves an **event → the element that emitted it**. #685 resolves a **clicked wire → the chronogram lane for that signal** — a `Wire`/`WireNet` → net-identity lookup (`src/jls/elem/Wire.java:16`, `src/jls/elem/WireNet.java:16`), not an event-to-emitting-element lookup. For multi-driver/tri-state nets, `WireNet.propagate` computes the winning driver and then discards it: `value = actual; // src/jls/elem/WireNet.java:484`, and the event actually posted, `SimEvent.PinChanged` (`src/jls/sim/SimEvent.java:26-30`), is a zero-field record carrying no producer reference. TASK-C529-1's direction depends on recovering that discarded identity for such nets; #685's direction does not need to (a clicked `Wire` already carries its `WireNet` directly, no event lookup required). Declaring both "the same seam" is either (a) vacuously true if it just means "both consult a shared element/net registry," in which case it asserts nothing useful, or (b) literally forces the wire→lane direction through the same event-based resolution proven unreliable for multi-driver nets elsewhere in this feature family, which would be a self-inflicted regression on the one direction that didn't need it.
**Recommendation:** state explicitly what "the same seam" means at the type level (a shared `Element`/`WireNet` identity registry both directions consult) and confirm the wire→lane direction is keyed on `WireNet`/`Wire` identity directly rather than routed through TASK-C529-1's event-resolution path.

**4. (MED) "The same grouping and radix defaults a manually added lane gets" (AC-2) depends on a UX action that is not actually defined anywhere in the cited dependency chain.**
Neither #680 (TASK-C527-2, the panel/grouping/radix task) nor #527 (FEAT-C23-1) describes a manual "add a lane for a signal not yet probed" action — #680's AC-1 says only "opening the panel shows live lanes for **probed** signals," and its AC-2/AC-3 describe grouping and radix for lanes that already exist. The closest existing precedent in the codebase is the current trace window's watch/probe mechanism (`InteractiveSimulator.java:997` — `watchable.isWatched()` — and `:981` for wire probes), which has no stored "default radix" anywhere (`grep radix JLSInfo.java` — no hits). #685's AC-2 assumes "manually added lane" defaults are a settled, reusable concept by the time this task lands, but that concept is not actually specified by any issue in the chain it depends on.
**Recommendation:** either have #680 explicitly define the manual add-lane action and its defaults (radix, grouping placement) before #685 can cite them, or specify the defaults directly in #685 (e.g., "bin for 1-bit, hex for >1-bit, ungrouped") rather than deferring to an action that doesn't yet exist on paper.

**5. (LOW-MED) "Focuses that signal's lane" is unspecified when the target lane is inside an existing named group.**
#680's AC-2 establishes that "lanes can be grouped into named groups" — a real feature this task must coexist with, since #685 ships after #680 in the chain. AC-1/AC-2 here say clicking a wire "focuses that signal's lane, scrolling the lane list to it," but say nothing about a lane that already exists inside a collapsed/named group: does focusing expand the group, scroll to the group header, or fail silently if the group is collapsed? This is exactly the kind of case a scripted walkthrough test can skip (single ungrouped lane) while leaving the stated behavior unverified for the grouped case a real chronogram session will produce.
**Recommendation:** add an explicit note on grouped-lane focus behavior (auto-expand vs. scroll-to-group), and require the test fixture to include at least one grouped lane.
