# Issue #569: FEAT-C30-4: the extension API is published with a stability statement — the plugin story Digital never offered, backed by a jar built outside the repo
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what's being asked

Publish `docs/extension-points.md` (#223) and the external-element-jar mechanism (originally attributed to #399, since closed as a duplicate of #212) as a public-facing doc with a per-seam stability statement (frozen/evolving/internal) and a deprecation policy, and demonstrate (AC-4) that a non-maintainer can follow it to a loadable jar. It is PF-4 of the CAP-30 "developer recruitment" capstone (#514).

## Findings, most severe first

**1. AC-3/AC-4 require a mechanism (#212) that is explicitly demand-gated and not yet built, and the issue's own comment trail concedes this without resolving it.** #212's body states plainly: "all execution-gated on demonstrated demand (milestone M4): this issue is the design record until a real external-provider request arrives," and its Open Questions section reaffirms "**Build now or hold for demand?** Recommended default … **hold**." Its three implementation tasks are listed as `planned_tasks` (unfiled) with status "Unfiled — demand-gated." I verified this against the working tree: `grep -rn ServiceLoader src/ test/` returns only the design-comment hit in `src/jls/JLS.java:15`; `src/jls/elem/ElementProvider.java`, `src/jls/module/ServiceLoaderDiscovery.java`, and `src/jls/elem/ForeignElement.java` do not exist. #569's own second comment (2026-08-08) says "A publication layer cannot precede the thing it publishes" and correctly re-points `ordering_after` at #212 — but nowhere does #569, or the comment correcting it, address the contradiction that #212 is on record as *should not be built speculatively*. Filing/prioritizing #569 (CAP-30 costs PF-4 at "2-3 mw") creates exactly the speculative-build pressure #212 was designed to resist. This needs an explicit REPLAN on #212 lifting or reframing the demand gate before #569 can be sequenced at all — as written, #569 is ordered after a feature its own upstream issue says must not be executed yet.

**2. AC-4 makes completion contingent on an external human's voluntary action, which is not a deliverable engineering can schedule or force.** "AC-4: … one external element jar built from the published docs by someone other than the maintainer loads and runs" (verbatim, also CAP-30 AC-6). By construction the maintainer cannot satisfy this alone. CAP-30 (#514) itself treats the underlying premise as falsifiable: "KC-30-2: If two quarters pass post-PF-1..4 with zero external PRs, the outreach premise is falsified." So the parent capstone already anticipates the scenario where AC-4 simply never fires through no engineering fault. #569 has no analogous kill/fallback clause of its own — it should either (a) inherit KC-30-2's escape hatch explicitly, or (b) split AC-4 into an engineering-controllable proxy (e.g., a maintainer-run walkthrough rehearsal, timed, with the doc as the only input) plus a separate, openly time-boxed adoption metric that can go unmet without blocking issue closure.

**3. AC-1 as literally written is gameable in a way the issue's own second comment warns against.** AC-1: "A published document … enumerates the supported extension points from the #223 catalog with their types and an example each." The catalog (`docs/extension-points.md`, read from the repo) has 4 "typed now" rows and 3 "pending" rows (`hdl.importer`, `app.command`, `gui.theme`). #569's second comment explicitly flags the hazard: "A row still `pending` in #223's catalog is not a supported extension point and must not appear in AC-1's published set as though it were... publish only the typed-now rows and mark the rest as unpublished rather than as 'evolving.'" That is the correct call — but it lives in a comment, not in the AC text itself. As written, AC-1 would be satisfied by a document that lists all seven rows (including three with no shipped contract) as "supported," which is precisely the misrepresentation the comment says must not happen. The AC text needs to be edited to say "typed-now seams only," not left to a superseding comment a future implementer may not read.

**4. Cost band (`band_mw: "2-3"`) does not describe the true critical path and the issue doesn't flag the gap.** The Notes section insists "this issue owns only the publication and stability-guarantee layer" and that framing is what justifies 2-3 person-weeks. But AC-3/AC-4 cannot be satisfied until #212's full mechanism ships, and #212's design record (via the now-closed #399, whose ~14-item implementation checklist covered a new sealed-hierarchy class, `ServiceLoader` discovery wired into boot, a `-providers` CLI flag, a security-ratchet update, and a full P1–P10 test battery) is a multi-week engineering effort in its own right, not a documentation task. If band_mw is meant to cover only the writing/publishing work assuming #212 ships elsewhere, the issue should say so explicitly and make the dependency's cost visible in `serves_capstones`/CAP-30's own MW rollup rather than implying the whole PF-4 line item is 2-3 mw. As it stands the estimate will read as "this is nearly free" to anyone scheduling off the issue title alone.

**5. The issue body is stale at the moment of review, and the fix lives only in a comment.** The machine block still reads `ordering_after: ["#223 …", "#399 (TASK-0107 external element jar)"]` and Notes still says "the single in-tree loading class stays in #399" — but #399 was closed as `duplicate` of #212 on 2026-08-08, the same day the correcting comment was posted. This is a process/hygiene issue rather than a logic one (the comment does correctly patch it), but it means anyone reading only the issue body (not both comments) will chase a closed issue number. Recommend editing the body directly rather than relying on a comment stack to be read in full, especially since this is now the *second* round of drift (comment 1 already corrected a #330/#212/#223 boundary question; comment 2 corrects a second, independent staleness).

## What's solid

- The scope boundary is genuinely well-drawn and durable: "the catalog mechanics stay in #223; the single in-tree loading class stays in #212; the ServiceLoader element-provider mechanism stays in #212" cleanly separates *mechanism* from *publication*, and the issue's first comment shows real adversarial work was already done distinguishing this from #212/#223/#330 (the "separating tests" argument for AC-2/AC-4 being inexpressible in #212's or #223's own terms is correct and non-obvious).
- AC-2 (frozen/evolving/internal + deprecation policy) is correctly identified, in the issue's own second comment, as the one piece of scope no other issue owns — that's an accurate and useful finding, not scope creep.
- The ordering rationale ("a stability statement over a catalog that is still moving is not a statement") is sound engineering logic, independent of the demand-gate problem above.

## Recommendation

Do not schedule #569 until: (a) #212's demand gate is explicitly and separately resolved (a REPLAN on #212 itself, naming a real requester, per its own Re-planning Protocol) or the gate's implications for #569's ordering are addressed head-on rather than papered over by an `ordering_after` pointer swap; (b) AC-4 gets an explicit fallback/kill condition consistent with CAP-30's KC-30-2; (c) AC-1's text is edited (not just commented) to restrict "supported extension points" to typed-now rows; and (d) the machine block and Notes are edited in place to drop the closed #399 reference. None of this invalidates the feature's premise — the publication/stability-statement work is real and worth doing once #212 exists — but as currently ordered and worded the issue can be "completed" on paper (doc merged, AC-1/AC-2 satisfied against a doc listing pending rows as evolving) while the actual goal (a working, published, externally-buildable plugin story) remains unreachable behind a gate this issue does not control.
