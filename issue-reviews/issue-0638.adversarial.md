# Issue #638: TASK-C598-1: an unassigned port and a wrong-direction binding each name themselves and their fix — and a design with several reports all of them in one failure
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what's actually being asked

Five ACs on `jls.hdl.board`: (1) unassigned-port diagnostic naming the port+fix, (2) wrong-direction-binding diagnostic naming the pin+the board as authority, (3) aggregation of all offenders in one failure in a stable order, (4) nothing written to disk on any refusal, (5) one diagnostic-text vocabulary reusable verbatim by the GUI (`TASK-C598-3`, #643). Parent feature #598 and completed feature #264 give real grounding; `PcfEmitter`/`PinBindings` genuinely exist at `src/jls/hdl/board/`.

## Findings, most severe first

**1. [High] AC2 assumes a per-pin direction data model that does not exist anywhere in the codebase, and the issue neither adds it nor flags it as required new scope.** `Board` (`src/jls/hdl/board/Board.java:26-27`) is `record Board(String name, String fpga, Format format, Map<String, String> pins)` — pins are `name -> physical location string`, nothing else. `Boards.ICESTICK` (`src/jls/hdl/board/Boards.java:34-78`) stores 33 pins with zero direction metadata. AC2 says a wrong-direction binding must be refused "with the board definition cited as the authority for what the pin is" — but today the board definition carries no opinion on pin direction at all. This is not a wiring gap on top of existing data (unlike AC1, which reuses `PcfEmitter`'s existing walk); it requires a schema change to `Board`/`Boards` plus classifying every existing pin, none of which is mentioned in the task body, the `ordering_after: [264]` dependency, or the cited line ranges. `ordering_after` should name whatever issue/decision produces that schema (or #638 itself should absorb and scope that design work), but as written a reader would reasonably believe AC2 is "add one more check next to the existing ones."

**2. [High] Even granting a direction field, most of the iCEstick's own pins have no real fixed direction, and the issue gives no guidance on how to classify them — leaving AC2 either under-specified or trivially gameable.** Of the 33 `ICESTICK` pins, only a minority have a genuinely fixed direction from the vendor docs cited in `Boards.java`'s own comments: `CLK` (oscillator → FPGA, input-only), `LED1..LED5` (FPGA → LED, output-only), `UART_RX`/`UART_TX` (fixed by the FTDI wiring). The 24 `PMOD*`/`J1_*`/`J3_*` header pins are generic GPIO — bidirectional by nature, direction determined entirely by what the student wires externally, not by the board. AC2's own framing ("an output port bound to an input-only pin **or the reverse**") presumes a clean binary input/output partition that doesn't hold for most of this board's pins. Nothing in the issue says whether header pins should be exempted (bidirectional), and if they are, a compliant implementation can pass AC2's letter by writing a test against `CLK` or an `LED` pin alone while leaving the other 24 pins unchecked — "wrong-direction bindings are refused" would hold for 3 named pins and be silently absent for the rest of the table. That gap is exactly the kind of untested surface #598 exists to eliminate (it cites Logisim-Evolution's #91-class silent failure as the anti-pattern to avoid) — #638 risks reproducing a narrower version of that same failure mode for the un-classified pins.

**3. [Medium] AC3's "stable order... pinned by a test" is not actually demonstrated by the precedent this issue points to.** The issue frames aggregation as "matching the discipline that already exists," citing `PcfEmitter.java:116-120`. The existing regression test for the multi-offender case, `everyProblemIsReportedInOneMessage` (`test/jls/hdl/board/UnbindablePortsTest.java:128-140`), only asserts `message.contains(...)` for each offender — it never asserts their relative order. So the precedent this task is told to imitate does not itself pin order, despite AC3 explicitly demanding a test that does. The issue doesn't say what "stable" means operationally (file line order? port-declaration order? something else) — without that, "stable order, pinned by a test" can be satisfied by a test that never actually checks ordering, same failure mode as finding 2.

**4. [Medium] AC5 cannot be verified within this task's own boundary, even though the issue's ACs are otherwise framed as independently testable.** AC5 requires the diagnostic vocabulary to be "renderable verbatim" by a GUI that doesn't exist yet — #643 (`TASK-C598-3`) is the sibling task building that surface, and #598's own text says "the diagnostics themselves are testable headlessly and can land ahead of it [the GUI]." A one-sided "vocabulary discipline" (e.g., message text lives in named constants/format methods rather than being assembled ad hoc inline) is something #638 can adopt, but "pinned by a test" — as the sibling ACs are — isn't actually possible for cross-surface reuse until #643 exists to consume it. As written, AC5 reads as a testable acceptance criterion on par with AC1-4 when it is really a design constraint whose verification is deferred to a different, not-yet-landed issue. Recommend either dropping the "pinned by a test" framing for AC5 in #638, or making explicit that #638's obligation is only to expose the strings through a reusable API (e.g., a shared formatter/record) that #643 can later test against.

**5. [Low] The issue undersells how much of AC1/AC3/AC4 is already implemented and tested at HEAD, which risks distorting scope/effort estimates.** `PcfEmitter.emit` already produces the exact "port \"X\" ... has no pin binding; add a line ..." diagnostic (`PcfEmitter.java:82-86`), already aggregates every offender into one `errors` list before throwing (`PcfEmitter.java:69,111-119`), and the CLI wiring already computes constraint text before any file write and aborts cleanly on `HdlExportException` (`src/jls/JLSStart.java:414-433`). `UnbindablePortsTest` already exercises and asserts on the exact diagnostic text for the missing-binding case (`aMissingBindingNamesThePortAndTheRepair`, lines 50-57) and the multi-offender case (`everyProblemIsReportedInOneMessage`, lines 128-140). The issue's "Outcome" section ("closed headlessly so they can land ahead of any GUI") reads as if AC1/AC3/AC4 are net-new work; in reality the only genuinely new deliverable is AC2 (plus, per finding 4, a vocabulary contract for AC5). An implementer or estimator reading only the issue body would overestimate remaining work on three of five criteria and could easily underestimate the one (AC2) that actually requires new design.

**6. [Low] Soft dependency on #264 is imprecise about what's actually needed.** `ordering_after: [264]` points at a feature-tracking issue that is still open, with most of its own definition-of-done unchecked (real-toolchain P&R evidence, manual hardware flash, Stage-2 ECP5 board — none done). Only the already-landed sub-slice of #264 (PR #242's `PcfEmitter`/`PinBindings`, per #264's own roster table) is actually what #638 depends on. As stated, a reader has to go read #264 in full to figure out that the dependency is already satisfied and #638 isn't blocked on #264's open items — the issue would be clearer citing the specific landed commit/PR rather than the whole feature issue.

## What's solid

- AC1 and AC4 are concretely grounded in real, existing code with a working, tested pattern to imitate (`PcfEmitter.java`, `UnbindablePortsTest.java`); a "specific diagnostic text, not merely an exception" bar is exactly what's already enforced there. One line each, no further comment needed.
- The "reuse, don't rebuild" framing matches #598's explicit boundary notes ("#264 owns... extend and surface them, do not rebuild them") — no contradiction with the parent feature.
- The all-or-nothing / nothing-written-on-refusal contract (AC4) is real and already verified end-to-end at the CLI layer (`JLSStart.java:414-444`), not just inside `PcfEmitter`.

## Verdict rationale

The issue is well-grounded for 3 of its 5 acceptance criteria (they're already implemented and merely need a modest extension/reuse), but AC2 — the criterion that gives this task its title and half its "Outcome" claim — rests on a data model that doesn't exist and that the issue never scopes, and the physical reality of the board (mostly bidirectional headers) makes "wrong-direction binding" ill-defined without additional design decisions the issue doesn't make. AC3 and AC5 both have "pinned by a test" language that isn't actually achievable as literally stated given current precedent (AC3) or current sibling-issue state (AC5). This needs rework: scope the direction-data-model question explicitly (even if the answer is "classify only CLK/LED/UART/IR pins as fixed-direction, leave headers unchecked, and say so"), and tighten AC3/AC5 to criteria that are actually verifiable inside this task.
