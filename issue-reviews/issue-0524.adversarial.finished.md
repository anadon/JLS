# Issue #524: FEAT-C21-1: the headless CLI stops being observed behavior and becomes a frozen, versioned promise — invocation, exit codes including status 3, artifact paths and xUnit schema, held by a conformance suite and a compatibility ratchet
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

The outcome is coherent and well-bounded on paper: freeze invocation, exit statuses, artifact paths and the xUnit schema behind a conformance test and a semver ratchet, without re-owning verdict *content*. The three child tasks (#686 TASK-C524-1, #687 TASK-C524-2, #690 TASK-C524-3) decompose it cleanly and their bands (1-1.5 + 0.5-1 + 0.5 mw) sum exactly to this issue's own `band_mw: 2-3` — unlike sibling issue #369, whose band doesn't match its row sum. The problem is that this issue's own comment thread has already run two adversarial passes on it, found real defects, and declared them fixed — but the fixes were only ever written into comments, never into the issue body. As filed, the machine-readable block a scheduler or implementer would actually parse still carries the defects both prior passes identified.

## Findings, most severe first

### 1. `ordering_after` still names #369, five hours after a same-thread comment concluded it shouldn't — verified live, not fixed

The body's machine block reads `ordering_after: [369, 466]`. The most recent comment (`issuecomment-5227296462`, 2026-08-08T17:33:49Z — the same timestamp as the issue's own `updated_at`, so this is the latest activity) argues at length that naming #369 imports #369's own `blocked_by: [316, 321, 347]` — the `SimpleEditor` decomposition (#316), the Yosys JSON writer (#321), and the parity harness (#347) — none of which the CLI-contract freeze needs, and concludes: **"Correction: `ordering_after: [466]`."** It further states this correction was **"Mirrored on #369, #466 and on this issue's child #686."**

I fetched #524 and #686 directly (not cached): both still read `ordering_after: [369, 466]` verbatim. GitHub comments cannot edit another issue's YAML block, and no edit to #524's body is visible in the fetched content. So the claimed mirror did not happen, and the defect the review found is still live in the artifact a scheduler would read. Cross-checked against #369's own body (`blocked_by: [316, 321, 347]`, confirmed): the import is real, not merely a hypothetical the comment raised. **As currently filed, this issue tells a scheduler that a headless-CLI-contract freeze cannot start until a Swing editor refactor and an HDL netlist exporter land — the exact defect the project's own review process already caught and considered closed.** Recommend: maintainer edits the body's machine block directly; a comment is not sufficient for a field tooling parses structurally.

### 2. AC-1's checkbox is worded as a present-tense claim about HEAD, and it is false at the commit reviewed

AC-1: *"the contract document specifies invocation, every exit status (including status 3), artifact paths, and the xUnit schema, and each clause is exercised by a conformance test (`CliContractConformanceTest` passes at HEAD)."* Verified against the tree: `grep -n '"check"\|"report"' src/jls/JLSStart.java` returns nothing, the `FLAGS` table holds 10 entries (h, b, i, s, t, d, p, v, r, vcd — no `-check`/`-report`), no `CliContractConformanceTest` exists under `test/`, and `docs/batch-interface.md:36-40` documents exactly three exit statuses, not four. Comment 2 (`issuecomment-5227296462`, §3) already caught this and wrote: *"Read as a completion criterion this is fine; read as a statement about the codebase it is false. **Intended reading: 'passes at the commit where this feature closes.'**"* — but that disambiguation lives only in the comment. The checkbox itself is unedited and still reads as a present-tense assertion. This is a textbook gameable-acceptance-criteria shape: nothing in the visible AC text distinguishes "must become true at close" from "is already true", so a careless closer could point to the checkbox's literal wording and a same-day green CI run without checking whether the test was ever seeded to actually catch a violation. Recommend the checkbox be reworded in the body (`... passes at the commit where this issue closes`) rather than left for a reader to reinterpret via a buried comment.

### 3. AC-2 still reads as if this issue alone owns the ordering guarantee, contradicting the split the same comment thread already negotiated

Comment 1 (pass 2) found AC-2 here and #531's AC-3 are the same criterion written twice, both citing "CAP-21 AC-2," and declined to merge them, escalating instead. Comment 2 then resolves the escalation: *"#524 (this issue) owns the artefact [...] the recorded falsification transcript [...] It does **not** require any adapter lane to exist. #531 owns the ordering guarantee. That in the assembled four-way fixture, the contract-conformance check is evaluated before any adapter lane executes."* That is a sensible split. But the issue's actual AC-2 text was never edited to match it — it still reads: *"A seeded contract violation (e.g. a changed exit code) on a scratch branch fails CI before any adapter test runs; the falsification transcript is recorded (CAP-21 AC-2)."* The phrase **"before any adapter test runs"** is precisely the ordering-guarantee clause the same comment just assigned to #531, not to this issue. Left as-is, two readings survive: (a) #524 must itself prove an adapter-lane ordering property it has no adapters to test against, which is infeasible for an issue whose own boundary note says verdict/adapter work is out of scope; or (b) #524 can close on the transcript alone while quietly implying (via unedited wording) that the ordering guarantee is also discharged here, which risks #531 closing later on "the transcript already exists" without producing its own ordering assertion — the exact double-close hazard comment 1 flagged. Recommend AC-2's text be edited to drop "before any adapter test runs" (or rephrase to "the transcript records that clause X was violated and detected", with the *ordering* explicitly deferred to #531) so the split the maintainer already agreed to is enforceable from the checkbox alone.

### 4. The contract's most novel clause (status 3) is frozen before its own design is settled, and the escape hatch (AC-3) has no test named

Status 3 does not exist anywhere in the tree today (confirmed: zero `System.exit(3)` call sites in `src/jls/JLSStart.java`; `docs/batch-interface.md` and `ARCHITECTURE.md`'s CLI-contract section both document only 0/1/2). Its meaning is entirely #466's to design, and #466 is itself open, under active revision (its own adversarial review, `issue-0466.adversarial.md`, verdict `needs-rework`, found #466's body and its own "REVISION" comment give contradictory Definitions of Done). #524 proposes to "freeze" a contract clause whose upstream design isn't settled yet. AC-3 is the only mitigation ("The ratchet encodes a written versioning policy... such that FEAT-053-lineage verdict evolution remains possible without breaking the freeze") but, unlike AC-1/AC-2/AC-5, it names no conformance test — it's prose describing a property the ratchet must have, not a checkable clause. Child task #687 (TASK-C524-2) does name a concrete AC for this ("The policy is shown to admit at least one concrete planned verdict evolution from #369/#466 without a major bump") — but that AC lives on the child, not on #524 itself, so #524's own DoD is unfalsifiable on this point in isolation. Recommend #524's AC-3 either point explicitly at #687's admits-one-evolution test as its discharge mechanism, or be dropped from #524's own checklist as redundant with the child task.

### 5. AC-4's determinism claim names no test and doesn't cite the mechanism that actually makes it achievable

AC-4: *"The byte-identical-goldens discipline extends to the artifact envelope: no timestamps, ordering, or locale nondeterminism in verdict output across container boundaries."* Comment 2 notes, almost in passing, that this is achievable specifically because #466's xUnit report "carries no `timestamp`, `hostname` or `time` attribute" and recommends "that dependency on a specific design decision... should be named in the ratchet's regression test" — but that recommendation targets the ratchet (#687), not this AC. As worded in #524's own body, AC-4 is a restatement of an existing discipline with no new test named (contrast AC-1's `CliContractConformanceTest` and AC-2's falsification transcript), so it is easy to claim satisfaction by citing pre-existing golden tests (`BatchSimulationGoldenTest`, `VcdExportGoldenTest`) that were never scoped to the artifact envelope specifically. Recommend naming the concrete assertion (e.g., "the xUnit writer emits no `timestamp`/`hostname`/`time` attribute, asserted by test X") the way AC-1 and AC-2 do.

### 6. Minor: the feature/task hierarchy is prose-only, not GitHub-native

#524 (`has_parent: false, has_children: false` per the API) claims three children via body text alone (`part_of_feature: 524` in #686/#687/#690) and one parent via `serves_capstones: [502]` in its own body — none of these are registered as GitHub sub-issues. A consumer using `get_sub_issues`/`get_parent` on #524 would see no relationships at all, despite the prose graph being load-bearing for scheduling. ## Verdict rationale

The design is sound and the project's own review process has already found and correctly diagnosed the issue's real defects (stale `ordering_after`, an unfalsifiable-as-worded AC-1, an unresolved AC-2/#531 overlap). None of those fixes made it from comment into body. An implementer who reads the issue body today — the artifact of record — inherits a false blocking dependency, a checkbox that is already false as literally worded, and an AC-2 that still claims an ordering guarantee the maintainer's own resolution assigned elsewhere. This is fixable with body edits, not a redesign, but it is not currently safe to hand to an implementer as-is. **needs-rework.**
