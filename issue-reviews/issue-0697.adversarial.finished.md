# Issue #697: TASK-C525-2: GradescopeCorpusTest grades all 300 fixture submissions inside a declared wall-time budget, with two runs identical
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what's being asked

`GradescopeCorpusTest` should run the in-tree Gradescope containerized template over a 300-submission fixture corpus, assert a wall-time budget, assert byte-identical output across two runs, and emit a score vector in the form #719 (`CrossPlatformScoreParityTest`) consumes. Nothing this issue depends on exists yet: at HEAD there is no Gradescope template anywhere in the tree (confirmed — `grep -rli "gradescope" .` returns nothing; the closest artifact is `examples/autograde/autograde.py`, a stdout-line grepper), no 300-submission corpus, and no golden score vectors. This is a pure downstream-of-vaporware task.

## Findings, most severe first

**1. The issue's own dependency declaration is admitted-wrong by the maintainer, in a comment, and left unfixed in the issue body itself.**
The YAML front matter states `ordering_after: ["TASK-C525-1", 531]`. The issue's single comment (posted by the OWNER, 2026-08-08, four days after filing) says outright: *"`ordering_after: ["TASK-C525-1", 531]` is wrong in both entries, and the second is an inversion"* — because feature #531's own task #719 (`CrossPlatformScoreParityTest`) *consumes* this task's output, so ordering behind the whole of #531 is a cycle at feature granularity, and `"TASK-C525-1"` is an unresolved string rather than the actual issue number (#694). The comment also points out the declared ordering never mentions #717 (`TASK-C531-1`, the task that actually builds the 300-submission corpus this test needs) at all — a missing dependency, not just a malformed one. The corrected reading the comment proposes — `ordering_after: [717, 694]`, `blocks: [719]` — has not been written back into the issue body or its YAML block. Anyone implementing straight from the visible acceptance criteria and front matter (without reading the comment thread) will order work against a cycle and miss the corpus dependency entirely. **Recommendation:** edit the issue body's YAML to the corrected form before this is picked up; don't leave a self-correction stranded in a comment on a still-wrong issue.

**2. Hard dependency on two unbuilt artifacts, both currently hypothetical, one of them gated by a policy that doesn't exist.**
This task needs the Gradescope template + adapter from #694 (TASK-C525-1, open, unimplemented) and the fixture corpus + golden vectors from #717 (TASK-C531-1, open, unimplemented). #717's own AC-4 requires "the large-fixture policy in force for the repo" to be applied to the corpus before it lands — I grepped `docs/` for any such policy and found none; it doesn't exist in this repository today. #717's comment thread itself flags this: *"if [the large-fixture] policy shrinks the corpus, this budget is re-derived rather than inherited."* So #697's AC-2 (the wall-time budget) is asserted against a corpus whose size is not yet fixed, gated by a policy that is not yet written. There is no way to responsibly set the budget number today; any number picked now is provisional and likely to be thrown away. **Recommendation:** either mark AC-2's specific budget value as TBD-pending-#717/large-fixture-policy explicitly, or fold "declare and justify the budget" into this task's own scope rather than pretending it's independently specifiable now.

**3. "Two consecutive full-corpus runs produce identical output, byte for byte" is underspecified enough to be gamed.**
The criterion doesn't say what "output" is scoped to. A results.json for 300 students plausibly contains timestamps, container/host identifiers, or ordering that is naturally non-deterministic; the easy way to pass this test is to strip or normalize those fields inside the adapter before comparison — which is exactly the loophole AC-4 tries to close for a *different* seam ("without per-adapter normalization applied after the fact"). AC-4's wording implies normalization *before* the fact (baked into the adapter's own construction) is fine, which is a distinction without an enforced difference: nothing in the acceptance criteria stops an implementer from quietly engineering the adapter to only ever emit deterministic-by-construction fields and calling that "no normalization applied after the fact." **Recommendation:** name the exact artifact and byte range under test (e.g., "the emitted `results.json` byte stream, unmodified") and require the determinism assertion to run against the adapter's actual first-class output artifact, not a derived/normalized copy.

**4. The wall-time budget criterion has no stated method, tolerance, or reference hardware — a build-time flake magnet.**
"A wall-time budget for the full corpus is declared in tree and enforced by the test" names no unit, no measurement method (wall clock on which runner?), and no slack for CI runner variance. Performance-budget assertions on shared CI hardware are a classic source of intermittent red builds; without a stated tolerance or a runner-class pin, this test will either need a padding so generous it stops meaningfully guarding against regressions, or it will flake and get skipped/ignored in practice — silently defeating the stated purpose ("a performance regression... surfaces as a red lane rather than as a Gradescope timeout"). **Recommendation:** specify measurement basis (e.g., median of N runs, or CI-runner-class-relative budget with documented margin) as part of this task's own acceptance criteria, not left to the implementer's judgment.

**5. Scope-inflation risk in the Outcome text versus what's actually tested.**
The Outcome claims the adapter is "proved at cohort scale rather than on one submission," but the Boundary and AC text make clear this only runs the *local containerized template* against a fixture corpus — it never touches real Gradescope infrastructure. That's a reasonable and explicitly stated scope limit (Gradescope is proprietary; #525's own Boundary says "documented spec only"), but the Outcome's phrasing ("proved... rather than on one submission") reads as a stronger platform-compatibility claim than the AC actually delivers. A reader skimming the Outcome could reasonably believe this validates against the real Gradescope grading pipeline; it does not, and CAP-21's own risk register (KC-21-3) explicitly anticipates the documented spec drifting from reality. **Recommendation:** tighten the Outcome sentence to state plainly that this proves the containerized template's own self-consistency at scale, not compatibility with live Gradescope infrastructure.

**6. `band_mw: 0.5-1` looks optimistic given the actual shape of the work.**
Once #694 and #717 land, this task still needs: wiring a 300-submission batch run through a Docker container twice, collecting/parsing 300 results.json score entries into the shared vector form, and standing up a wall-time-budget assertion with acceptable CI stability (see finding 4). That's a nontrivial CI-integration task, and the 0.5–1 mw band undercounts the budget-tuning and flake-proofing work in particular. Not a blocker, but worth a sanity check before this is estimated into a sprint.

## What's solid

- The Boundary section is genuinely disciplined: it correctly declines to re-own the four-way parity assertion (that's #719's job) and correctly declines to re-own corpus construction (that's #717's job) — good adherence to the single-producer-per-artifact discipline this issue graph is trying to enforce elsewhere.
- AC-4's core idea — the emitted vector must be in the shared form #719 consumes, without after-the-fact per-adapter normalization — is the right constraint in spirit; it's only the boundary case in finding 3 that's exploitable.
- The issue correctly cites CAP-21 AC-3 as its parent acceptance criterion and doesn't silently expand or contradict it.

## Verdict rationale

The technical shape of the task is reasonable, but the issue as filed carries a live, maintainer-acknowledged-but-uncorrected dependency error (finding 1) that would misroute an implementer today, plus two genuinely gameable acceptance criteria (findings 3 and 4) that need tightening before this is worth picking up. Fix the YAML front matter and tighten the two criteria; the underlying task doesn't need to be re-planned from scratch.
