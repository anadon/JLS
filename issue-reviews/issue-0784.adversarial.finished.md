# Issue #784: TASK-C553-2: "coming from CircuitVerse" and "coming from Falstad", each with a marked importer slot no page may fill before the importer exists
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what's being asked

Two new "coming from X" one-pagers (CircuitVerse, Falstad) plus a build-time
check that applies to all four "coming from" pages (these two, plus the two
from the sibling task TASK-C553-1 / #782: Logisim-Evolution, Digital),
verifying no page's importer-link slot claims an importer that isn't actually
shipped. Part of FEAT-C27-6 (#553), itself serving CAP-27 (#511), evidenced by
the #510 niche survey.

## Findings, most severe first

**1. [High] AC-3's "check" is underspecified to the point of being gameable, and the issue's own cited evidence shows exactly how.** The issue says a check must fail "when a page's importer slot is filled with a link to an importer that is not present in the build." "Present in the build" is never defined. #510 (this issue's own evidentiary source), footnote 2, records precisely the ambiguity this leaves open: `jls.hdl.imp.NetlistImporter` (Yosys-JSON netlist import, #61) exists at `src/jls/hdl/imp/NetlistImporter.java` with a full test suite (`test/jls/hdl/imp/NetlistImporterTest.java`), "but are wired to no CLI flag or menu, hence unreachable by users." A check that tests "does the class exist / does it compile" would pass for a page linking that importer while the importer remains completely unusable by a reader who follows the link — which is exactly the "page that implies an importer exists before it does" failure mode the issue's own framing ("worse than a page that says nothing") is written to prevent. As written, the acceptance criterion can pass while the real goal (never mislead a switcher) fails. **Recommendation:** define "present" operationally — reachable from the CLI/menu with a passing end-to-end smoke test, not merely class-present-on-classpath — before any check is built.

**2. [High] AC-1's "linking shipped examples" has an undeclared, unmet dependency.** The repository currently ships zero discoverable example circuits: `resources/samples/` (the mechanism #548 and #73/#381 assume already exists) is absent from the tree; the only `.jls` files under version control are three files under `test/fixtures/` and the unsurfaced `riscv/gui/cpu.jls` — precisely the state #510 describes ("no example circuits ship where a user can find them (all .jls files are test fixtures or the unsurfaced RV32I showcase)"). #548 (the Examples-menu feature that would create shippable, linkable examples) is open and unstarted. #784's own `ordering_after` frontmatter lists only `[TASK-C553-1]` — it does not list #548, yet AC-1 cannot be satisfied honestly without something to link. The sibling task #782 (TASK-C553-1) is explicit about this same dependency for its own two pages ("links at least one shipped example (#548)"); #784 drops that explicit tie while keeping the same requirement in prose. **Recommendation:** add #548 to `ordering_after`, or narrow AC-1 to permit linking `test/fixtures/*` circuits explicitly (noting the licensing caveat below) until #548 lands.

**3. [Medium] Scope reaches into deliverables this issue does not own.** AC-3 requires the check to validate all four pages, but two of them (Logisim-Evolution, Digital) are owned and authored by #782 (TASK-C553-1), which is itself still open with no pages yet written. #784 is thus required to either (a) build validation infrastructure against page content that doesn't exist yet and whose eventual shape #784 doesn't control, or (b) retroactively impose a page format/slot convention on #782's deliverables from outside that issue. Either way, #784 is doing design work that belongs to — or must be renegotiated with — #782. There is also a second collision: CAP-29 (#513) plans its own "PF-1 — Shared import-report infrastructure" for a related but distinct purpose (reporting *what's lost on import*, not *whether an importer exists*). Two independently motivated "does importer X exist/what can it do" mechanisms invite drift. **Recommendation:** either fold the check into #782 (or a new shared task both depend on) and have #784 consume it, or explicitly scope #784's check to only the two pages #784 authors, deferring the other two to #782.

**4. [Medium] AC-3 is likely to be untestable-by-exercise for a long time, i.e. vacuously true.** CAP-29 (#513), which owns the actual CircuitVerse/Falstad importers, is unstarted, estimated at 13-20 mw, and itself `ordering_after` CAP-16/#311 (also unstarted). That means for the foreseeable future both pages' importer slots will always read "not yet available" — there is no positive case (a real importer landing) to exercise the check against, and CI can't distinguish "the check correctly found no violation" from "the check is a no-op / broken and would never catch a real violation." Nothing in the AC asks for a negative-path test (e.g., a fixture page with a deliberately bogus importer link that the check must reject). Without that, "a check exists" can be satisfied by code that never actually fires. **Recommendation:** add an explicit AC requiring a mutation-style negative test fixture that proves the check fails on a bad slot.

**5. [Medium] Predecessor task not landed — building ahead of an unset template.** `ordering_after: [TASK-C553-1]` signals #784 should follow #782, but #782 is open with zero pages written, and the shared comparison-table content it and #784 both point to (#545, "the comparison-table content overlaps FEAT-C27-1 (#545); write it once and reference it from both surfaces") is also open and unwritten. #784 has nothing concrete to structurally match — page layout, slot markup convention, and comparison-table linking pattern would need to be invented by whichever of #782/#784 lands first, with real risk the second diverges from the first's ad hoc choices. **Recommendation:** either sequence #784 strictly after #782 merges (so the page template and slot convention are fixed artifacts to copy), or make the two-vs-two split into one PR/one task to guarantee consistency.

**6. [Low] AC-1 is a compound, hard-to-fail criterion.** It bundles four independently-testable properties — discoverable from README, readable in under five minutes, maps concepts/gestures, links shipped examples — into one bullet. Contrast with the parent feature #553, which splits the same requirements into AC-1/AC-2 separately. A reviewer checking "AC-1: done" could be waving through a page that satisfies three of the four properties. **Recommendation:** split into separate criteria as #553 does.

**7. [Low] "Readable in under five minutes" has no defined measurement.** No word-count ceiling, reading-level target, or timing method is specified (inherited unchanged from #553/#782, not introduced here, but still a gap in this issue's own acceptance bar). **Recommendation:** pick a proxy (e.g. word count ≤ N, checked by a simple test) rather than leaving it to reviewer judgment.

**8. [Low] Fixture-linking risk if AC-1 is worked around via test fixtures.** #73's 2026-07-17 decision (referenced by #548's boundary notes) establishes "samples are authored clean for licensing; test fixtures are reused only where one already fits" — a deliberate licensing/provenance guard on what circuits get surfaced to end users. If #784's authors route around finding #4/#2 above by linking `test/fixtures/*.jls` directly from a public-facing page, that guard is exactly what would need re-litigating; the issue doesn't mention it. **Recommendation:** if fixtures are used as a stopgap, get an explicit licensing sign-off consistent with #73's decision rather than assuming test fixtures are safe to publish.

## What's solid

- AC-4's grounding in `docs/hdl-support-research.md` and the #510 teardowns is concrete and verifiable — the cited files and the survey's per-competitor "loudest pains" tables are real and specific enough to write honest "what JLS doesn't do" sections from.
- The core principle — no page may claim an importer that isn't shippable — is a genuinely good norm and directly answers a real problem (#510's observation that JLS's on-ramp materials currently overclaim/underdeliver versus competitors).
- The four-pages-total structure (splitting Logisim/Digital into #782 and CircuitVerse/Falstad into #784) is a reasonable size-based split and matches the two tasks' comparable band_mw estimates.
