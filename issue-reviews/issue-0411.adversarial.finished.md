## Findings

**1. (High) The armed-preflight fix as scoped will not produce the exit code §7.11 requires — P6 is satisfiable while the real goal fails.** §7.11 and O7 require that a missing `compare` be classified as environment (exit 2), calling this the "single most damaging outcome" to get backwards. But `scripts/wayland-rig.sh` has no `die_env()`-style helper at all: its `die()` (`scripts/wayland-rig.sh:53`) is hardcoded `exit 1` for every call site, and the script's only `exit 2` is one literal at `scripts/wayland-rig.sh:294`, reserved for "control frame never mapped." §8's checklist item is just "Add `compare` to the rig's tool preflight ([`scripts/wayland-rig.sh` L66])" — which is satisfied by adding the string `compare` to the existing `for tool in ...; do ... die "$tool is not installed"; done` loop. Doing exactly that, and nothing more, makes a missing-`compare` failure exit **1** (JLS-side) via the unmodified `die()`, not exit 2 — the opposite of what O7/§7.11 demand, and P6's literal check ("grep the preflight; observe `compare` present") passes regardless. Contrast `scripts/x11-rig.sh`, which already has `die_env()` (`x11-rig.sh:84`, `exit 2`) precisely so its preflight loop (`x11-rig.sh:103`) gets the classification right. **Recommendation:** state explicitly in §8 that `wayland-rig.sh` needs a new `die_env()`-equivalent (mirroring `x11-rig.sh`) before `compare` is added to the preflight loop, and change P6 to assert the exit code of a simulated missing-`compare` run, not just grep-presence of the string.

**2. (Medium-High) The X11 twin has the identical preflight gap, but is excluded from the task's own scope — the issue repeats the exact mistake O2 flags.** `scripts/x11-rig.sh:103` (`for tool in Xvfb xdotool xwininfo import identify; do`) also omits `compare`, and its late runtime fallback (`x11-rig.sh:399-400`) also only fires after the pixel-diff step is reached. Since this very task arms `PIXEL_DIFF_MIN` on **both** `ci.yml:386` and `ci.yml:513` (O2's whole correction), O7's "arming the gate makes ImageMagick a hard requirement" applies equally to `gui-x11` — yet §8's checklist and §14's Definition of Done name only `scripts/wayland-rig.sh L66`, never `scripts/x11-rig.sh`. This is the same class of omission O2 exists to correct ("the planning corpus treats PIXEL_DIFF_MIN as one placeholder... there are two"), reintroduced one layer down. **Recommendation:** add a matching `x11-rig.sh` preflight line item to §8 and §14, or explicitly state (with a reason) why only the Wayland lane needs it.

**3. (Medium) The calibration instruction is ambiguous about whether one AE value or two independently-measured values feed the two `PIXEL_DIFF_MIN` sites.** §8 says: "Read the AE from the most recent green run's `pixel-diff.txt` artifact. Set `PIXEL_DIFF_MIN` per §7.10's formula, **at both L386 and L513** ... and record the observed AE and the date in the comment beside each." "The AE" (singular) is read once, then applied "at both" sites — but `gui-wayland` (headless sway + pixman software rendering + `grim`) and `gui-x11` (Xvfb + `import`/`identify`) are different rendering pipelines with their own `pixel-diff.txt` artifacts, and nothing in the wording forces the executor to pull two separate numbers from two separate lanes' artifacts rather than reusing one lane's AE (most likely the Wayland lane's, since it's the one with a nightly record) for both. A miscalibrated X11 threshold from an unrelated renderer's baseline would either be vacuous or flaky the first week, which is exactly the risk H2's own falsification criterion is written to catch — but only if someone notices the wrong number was used. **Recommendation:** make §8 say explicitly "one AE per lane, from that lane's own green-run artifact — do not reuse the Wayland AE for the X11 line or vice versa."

**4. (Medium) Definition of Done contains an item no contributor PR can unilaterally satisfy, without saying how a PR is allowed to close.** §14 lists "Both GUI job names registered as required branch-protection checks, recorded in the commit message (P7)" as an unconditional checkbox, while §6 separately concedes "**Repository settings access** for P7 ... this is the one deliverable a contributor without admin rights cannot complete." Open Question 1 discusses *who* registers the checks but never states whether a PR that ships everything else and defers only P7 is "done" (with the standard `WAIVED:` comment rule 10 elsewhere requires), or whether merge is blocked until the maintainer performs the settings change in the same window. As written, an executing agent following §14 literally cannot check every box without maintainer participation, and the issue doesn't say that's acceptable. **Recommendation:** state plainly that P7 gets a `WAIVED: pending maintainer registration` note rather than treating it as a blocking checkbox equal to the code items.

**5. (Low) Self-test parity is real work, not boilerplate, and is undercosted by one line in §8.** `scripts/wayland-rig-selftest.sh`'s stub toolchain (`STUB_BIN`: `sway`, `swaymsg`, `grim`, `java`) has no `compare` stub and no `STUB_AE` plumbing at all, unlike `scripts/x11-rig-selftest.sh`, which already has both (`p2-pass`/`p2-fail` cases at lines 175/177, `STUB_AE` support). So the P4 case ("Run the rig self-test with a stub whose AE is below `PIXEL_DIFF_MIN`; observe exit code 1") requires *building* AE-stubbing machinery for the Wayland self-test from scratch, not just adding a test case to existing plumbing the way the X11 twin already has it. §8's single bullet ("Extend `scripts/wayland-rig-selftest.sh` ... with the P3, P4 and P5 cases") reads as one unit of work; P4 here is materially larger than P3/P5. Not wrong, just worth flagging for anyone estimating the task at "a day."

## Net assessment

The technical grounding is exceptionally strong — nearly every citable claim reproduces against HEAD. The gaps are all in the *completeness of the fix's scope*: the preflight/exit-code fix as literally scoped can satisfy its own acceptance test (P6) while leaving the classification bug it's meant to close (finding 1), the X11 twin is quietly left out of a fix its own reasoning applies to (finding 2), and the calibration instruction has room to silently cross-contaminate two unrelated rendering pipelines (finding 3). None of these invalidate the task, but each would let a literal-minded implementation pass every stated checkpoint while missing part of the stated goal — worth tightening before work starts.
