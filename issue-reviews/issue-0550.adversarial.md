# Issue #550: FEAT-C27-3: first launch lands somewhere — a starter circuit or welcome pane replaces the empty tab pane, and never regressing that is a per-commit gate
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: sound-with-concerns

## Summary of the ask

#550 wants two things layered on top of #381 (TASK-0030, the empty-state panel builder): (1) upgrade "first run offers a next move" from polish to a per-commit CI gate (AC-1), (2) record a starter-circuit-vs-welcome-pane decision (AC-4), (3) wire the panel's Open Example action to #548's future examples set (AC-2), and (4) add a per-commit startup-time regression check (AC-3). Verified against the checked-out tree: `grep -rin 'welcome|firstRun' src/jls` returns nothing, `resources/samples/` does not exist — the empty-tab-pane problem the issue describes is real and current, matching #381's own O3 finding.

## Findings, most severe first

**1. AC-1's "per-commit gate, not a review item" framing conflicts with how the display-tagged suite is actually wired in CI (evidence-backed, high severity).**
AC-1 says the regression check is "asserted by a display-tagged test that fails if the launch path regresses (CAP-27 AC-4 as a gate, not a review item)." But `.github/workflows/ci.yml:69-73` documents the xvfb install step as explicitly **best-effort**: *"Best-effort so a transient apt failure doesn't block the build - each affected suite skips itself when its tool is missing."* And the `@Tag("display")` tests additionally self-skip under `assumeFalse(GraphicsEnvironment.isHeadless())` (ci.yml:125). So the exact mechanism this issue proposes to promote to "gate, not review item" has a documented silent-skip path baked into the CI it would run on — a flaky apt-get failure (or any environment where xvfb isn't present) makes the "gate" pass by not running, not by verifying anything. #381 itself already flags the adjacent risk in its own Threats to Validity: *"A new display test that only passes on the retry is a flake, not a pass."* AC-1 needs an explicit clause for what happens when the display substrate is unavailable (fail loud vs. skip loud vs. accept skip) — as written, "never regressing" is not actually guaranteed by the referenced test tag.
Recommendation: either require the launch-path test to fail (not skip) when the display substrate can't be provisioned in the required CI job, or state plainly that the guarantee is "regresses undetected only if xvfb is unavailable" and accept that as a residual risk.

**2. AC-3 bundles a machine-checkable claim with a claim nothing in this codebase can check (high severity, feasibility/testability).**
AC-3: "A per-commit startup-time regression check exists and holds the KC-27-1 line: default palette, startup time and first-year conceptual load unchanged." Grepping the repo for any startup-time measurement harness (`StartupTime`, `startup_time`, timing assertions) returns nothing in `src/` or `test/` — this infrastructure does not exist and the issue doesn't scope building it (no threshold, no tolerance, no methodology: cold JVM launch? time-to-first-paint? on which of the CI runners, which are shared and noisy?). Worse, "first-year conceptual load unchanged" is not a property any per-commit check can evaluate — it is exactly the kind of judgment #381 itself (Falsification Criteria, Threats to Validity) treats as a **PR-narrative** obligation ("K9 ... stated and justified in the PR"), not a JUnit assertion. AC-3 as literally worded asks for one check to hold three different kinds of claims, only one of which (palette) already has a test (`ThemeTest`), one of which (startup time) needs new infrastructure this issue doesn't budget for, and one of which (conceptual load) cannot be automated at all.
Recommendation: split AC-3 into (a) an automatable startup-time regression test with a stated methodology and tolerance band appropriate to noisy CI, and (b) a PR-narrative conceptual-load justification requirement, matching the precedent #381 already set. Don't imply a single per-commit check covers all three.

**3. AC-4's "decision" is not actually open — the dependency it must consume has already made it, creating an internal contradiction (medium-high severity).**
AC-4 asks for "the starter-circuit-vs-welcome-pane decision ... recorded on this issue with the K9/D9 rationale; whichever loses is explicitly not built." But the Boundary section of the same issue says #550 "**consumes, does not duplicate**" #381 TASK-0030, whose own predictions (P2, P9) and Method steps already commit to building "the empty-state panel with the four actions taken as constructor arguments" — i.e., the welcome-pane path is already the specified, in-flight implementation of the very dependency #550 is forbidden from re-specifying or duplicating. Building a starter circuit instead would directly violate #550's own "consumes, does not duplicate" boundary and conflict with #381's already-written interface contract (§7.4: "The empty-state panel class, constructed by SimpleEditor..."). So AC-4 either (a) is busywork — rubber-stamp "welcome pane wins" with no real deliberation possible — or (b) if taken literally as an open decision, contradicts the issue's own consumption boundary. The Outcome paragraph even hints the answer is preordained ("a starter-circuit option is decided against the welcome-pane default"), which reads as already assuming the welcome-pane outcome while AC-4 dresses it up as still-to-be-decided.
Recommendation: either drop AC-4 as a decision criterion and just state "welcome-pane is the answer, inherited from #381's already-specified panel, recorded here for traceability" — or, if the decision is genuinely meant to be open, explicitly carve out that reopening it requires renegotiating #381's scope via the #73/#355 REPLAN protocol the issue itself cites, so an implementer doesn't quietly violate that boundary.

**4. Hard unstated prerequisite: the dependency this issue "consumes" has zero lines of code today (medium severity, feasibility).**
The issue text presents #381 as an owner already assigned to build the panel ("the implementation already has an owner"), but `resources/samples/` doesn't exist and no welcome/first-run symbol exists anywhere in `src/jls` (confirmed by grep). #381 is itself a large task (2-week band per #355, 14-step Method, a 96-to-126-call-site color-literal sweep as a hard prerequisite to its dark-theme half, five open decisions still unresolved). #550's `ordering_after: [381]` correctly encodes the sequencing dependency, but nothing in the issue signals to a reader scanning the backlog that this is not "near-term, 1-2 mw" work in practice — it is gated behind a multi-week task that has not started. Labeling it `band_mw: "1-2"` without a visible caveat about #381's readiness risks under-planning.
Recommendation: add a one-line status note on #550 itself (or keep it current via comment) pointing at #381's actual progress before anyone budgets #550's "1-2 mw" as calendar time from today.

**5. AC-2's dependency on #548 is real but untracked in the machine-readable ordering field (medium severity, scope/gaming risk).**
AC-2: "Open Example binds to the FEAT-C27-2 (#548) examples set once it exists." This is a genuine functional dependency, but `ordering_after: [381]` omits 548. Nothing says whether #550 may close before #548 lands (wired instead to #381's 3-5 placeholder samples) or must wait, and no follow-up task/issue is named to force the rebind once #548 ships. As written, an implementer can satisfy AC-2 by wiring "Open Example" to whatever #381 shipped, close #550, and the "binds ... once it exists" clause becomes an orphaned promise with no owner.
Recommendation: either add 548 to `ordering_after` (accepting the longer critical path) or file the rebinding as an explicit tracked follow-up with an issue number, rather than leaving it as a parenthetical aside.

**6. Inherited, currently-unresolved planning inconsistency across #73/#355/#381 (medium severity, process risk).**
The issue's own comment (by the maintainer/tooling) flags two escalations against #73: its `planned_tasks` are still unfiled while #381, #545, #548, #550 and #552 all declare they consume them, and #73's `serves_capstones: []` is stale now that CAP-27 builds directly on it. The comment explicitly states "No merge, no close, no body edited" — meaning these escalations are still open as of the latest comment. #550 rests its entire "consumes, does not duplicate" framing on #381's scope being stable and correctly attributed to #73's roster, but that attribution itself is flagged as needing a maintainer `REPLAN` that hasn't happened. If #73 is later replanned in a way that reassigns or splits #381's scope, #550's boundary section goes stale without any mechanism in #550 itself to catch that.
Recommendation: block #550 (or at least flag it) until the #73 REPLAN the maintainer's own comment calls for actually lands, so #550 isn't built against a graph edge that's known-inconsistent at filing time.

## What's solid (brief)

- The boundary discipline is good: #550 correctly refuses to re-spec the panel itself, correctly defers "Open recent" to #76 exactly as #73 §6 already decided, and correctly cites the maintainer's own dedup ruling rather than re-litigating it.
- AC-1's core claim (first launch must never show an empty `JTabbedPane`) is verifiably true today as a defect — confirmed by reading `JLSStart.java` (uses `JTabbedPane` with no empty-state fallback) and by #381's own O3 grep — so the underlying problem statement is not manufactured.
- The `#511`/CAP-27 lineage is coherent: #550's AC-1 and AC-4 map cleanly onto CAP-27's AC-4 and KC-27-1 without adding scope CAP-27 didn't already ask for.

## Verdict rationale

Not "needs-rework" outright — the core outcome is legitimate, narrowly scoped, and the maintainer's own comment already did real dedup work. But AC-1's gate claim is contradicted by the CI's own documented self-skip behavior, AC-3 mixes a checkable and an unmeasurable claim into one criterion, AC-4 is either vacuous or self-contradictory given the consumption boundary, and the issue sits on a graph edge (#73's roster attribution) the maintainer has already flagged as needing a REPLAN that hasn't landed. These are all fixable by tightening the acceptance criteria and waiting on the upstream REPLAN, not by rewriting the feature — hence sound-with-concerns.
