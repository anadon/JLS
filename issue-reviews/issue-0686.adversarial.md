# Issue #686: TASK-C524-1: the headless CLI contract is written down and made executable — invocation, every exit status, artifact paths and the xUnit schema, each clause held by a conformance test
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

The issue asks for `docs/batch-interface.md` to become a fully-tested, clause-by-clause contract, with a new `CliContractConformanceTest`. The instinct is sound and the target document already exists and is already declared "normative, and a stability contract" (`docs/batch-interface.md:3`). But the issue as written asks the document to pin things — exit status 3, the xUnit report schema, the `-check`/`-report` artifact paths — that do not exist anywhere in the tree yet, and it orders itself behind unrelated work while failing to depend cleanly on the one issue that actually builds what it's supposed to freeze. Notably, the issue already carries one comment (2026-08-08, same author, self-labeled adversarial review) that found real defects here; as of this review the issue body is unchanged and those defects are still live. This review confirms that prior comment's core findings independently against the current tree and adds several the comment did not cover.

## Findings, most severe first

### 1. [High] The contract can't honestly specify "every exit status including status 3" because status 3 doesn't exist in the code

The Outcome text requires the document to specify "every exit status including status 3." I grepped `src/jls/JLSStart.java` for every exit call: there are ~70 `System.exit(1)` sites, two `System.exit(0)`, one `System.exit(2)` (line 1146) — and zero `System.exit(3)`. `docs/batch-interface.md`'s own exit table (`:36-40`) lists exactly three rows: 0, 1, 2. I also confirmed `src/jls/sim/` has no `Expectations.java`, `TestVectorRunner.java`, or `GradeReport.java` — the classes that #466 (TASK-0111, still open) would introduce to make status 3 reachable at all. The Boundary paragraph frames this task as "freezing the surface, not designing it," as if the surface being frozen already exists; it does not. You cannot write a conformance test for a status code, artifact path, or schema that has no implementation to test against.

The issue's own review comment (2026-08-08) partially caught this in point 2 ("this task cannot specify status 3 before #466 defines it — and should not try") but stopped at recommending an ordering fix; it did not flag that, as currently scoped, AC-1's literal text ("every exit status ... including status 3") is unsatisfiable until #466 lands the mechanism. **Recommendation:** either gate this task's status-3/schema clauses explicitly on #466 shipping (not just reorder `ordering_after`, see #2 below), or rescope AC-1 to say the document records status 3 as *reserved, pending #466* and the conformance test covers only statuses 0–2 until then.

### 2. [High] `ordering_after: [369, 466]` is unfixed despite the issue's own review comment recommending the fix a day before this review

Issue #369 (FEAT-053) carries `blocked_by: [316, 321, 347]` — the `SimpleEditor` decomposition, the Yosys JSON netlist writer, and the retirement-indexed parity harness (verified by reading #369 directly). None of those three gates a document-and-test task about CLI exit codes and an xUnit schema. What #686 actually needs from #369's lineage is narrower: the verdict channel (status 3, the report schema, artifact paths), which is entirely #466's payload. I re-verified #466 directly: its `blocked_by` is `[]` (the panel-half prerequisite, TASK-0021, is noted as needed but not yet recorded as a machine edge). So `ordering_after: [466]` alone would terminate cleanly; `ordering_after: [369, 466]` needlessly chains this task behind unrelated Swing/HDL work.

The issue's own 2026-08-08 comment makes exactly this argument and proposes `ordering_after: [466]`. As of this review the issue body's machine block still reads `ordering_after: [369, 466]` — the fix has not been applied, and there's no acknowledgment in the thread that it was rejected. An open, self-identified defect sitting unresolved in an otherwise-ready-looking issue is itself a process finding: someone triaging this issue by reading only the top of the body (as most reviewers will) will inherit the wrong ordering. **Recommendation:** apply the comment's fix (drop 369) before this issue is picked up.

### 3. [Medium] AC-3's schema pin conflicts with #466's own determinism requirement, and the issue doesn't say so

AC-3 says "the xUnit schema is pinned as a schema artifact, not described in prose alone, so a report can be validated mechanically." I read #466 in full: its H5/P7 require the emitted report to contain **no** `timestamp`, `hostname`, or `time` attributes, because those three are exactly what break byte-determinism (needed for `grade.py` to diff a student's run against an instructor's, and for parallel grading). A stock xUnit XSD treats at least some of these as expected/typed attributes on `<testsuite>`/`<testcase>`. If whoever executes #686 pins an off-the-shelf xUnit XSD as "the schema artifact" (the natural reading of AC-3 in isolation), JLS's own byte-deterministic golden reports would fail validation against the very schema meant to certify them. The issue text is silent on this; the prior review comment flags it in passing (point 4) but doesn't frame it as a design trap for whoever writes the schema. **Recommendation:** AC-3 should say explicitly that the pinned artifact is a JLS-specific xUnit *profile* (a restricted/extended XSD or equivalent) that permits omission of those three attributes, not a generic xUnit schema.

### 4. [Medium] "Each clause tagged to the conformance test that exercises it" has no falsifier and is gameable exactly the way AC-4 was already shown to be gameable

The Outcome's central mechanism — "each clause is exercised by a conformance test... a clause nobody can test is a clause that does not belong in the contract" — sounds rigorous but as written admits a trivial satisfaction: a "conformance test" tagged to a clause can assert something true-by-construction (e.g., a hardcoded string literal equals itself, or a constant equals itself) without ever invoking the CLI or checking real behavior, and the checkbox "each clause tagged to the conformance test that exercises it" would read as done. The issue's own comment supplies exactly the right falsifier for AC-4's exclusion list — "a test that would still pass if that behaviour changed" — but doesn't generalize that mutation-style falsifier to the primary clause-coverage AC (AC-1/AC-2), which is the one that matters most since it's the whole point of the task. **Recommendation:** require, for every tagged clause, a demonstrated red/green pair (test fails against a deliberately mutated doc or implementation, passes against the real one), not just a tag pointing at a test method.

### 5. [Medium] The Boundary's "freezing, not designing" framing collides with #466's still-open, execution-blocking decisions

I read #466's "Open Questions & Decisions Needed" section: at least two items are marked "Blocks execution" — OQ1 (what `after` means for the first expectation when there's no prior `at`/`after` to anchor it) and OQ3 (which format `-report` defaults to for an unrecognized extension). Both are exactly the kind of clause #686 would need to pin in the contract document (they determine artifact/timing semantics). If #466 lands with those decided differently than whatever #686's author assumes while drafting ahead of #466, the resulting contract document needs a rewrite, not an extension — which contradicts "freezing the surface, not designing it." **Recommendation:** state plainly in #686 that drafting the status-3/schema clauses must wait until #466's execution-blocking Open Questions are resolved, not merely until #466 "lands" in some partial form.

### 6. [Low] The `part_of_feature: 524` claim has no GitHub-native backing, and its sibling tasks (TASK-C524-2, TASK-C524-3) have no issue numbers

The issue's YAML block declares `part_of_feature: 524`, and the Boundary text assigns the ratchet/versioning policy to "TASK-C524-2" and the queryable version to "TASK-C524-3" — but I checked via the issue-hierarchy API: `get_parent` on #686 returns `null`, and `get_sub_issues` on #524 returns an empty list. The decomposition exists only as prose inside issue bodies. Concretely, this means: (a) nothing enforces that #524's other acceptance criteria (seeded-violation-fails-CI, the semver/deprecation ratchet, the queryable version) actually get filed and tracked once #686 closes; (b) a reader relying on GitHub's own sub-issue UI will not discover this relationship at all. This mirrors the "TASK-0021 not yet filed" pattern already visible in #466/#369, so it's a repo-wide habit rather than unique to #686, but it's still a real risk that "the ratchet and versioning policy" quietly never gets filed once the more concrete #686 ships and closes out visible progress on #524. **Recommendation:** either use GitHub's sub-issue linkage for #524↔#686, or explicitly file placeholder tracking issues for TASK-C524-2/-3 now.

## What's solid

- Treating `docs/batch-interface.md` as "starting material, not the artifact" matches how ARCHITECTURE.md already describes it (a normative companion document, `ARCHITECTURE.md:6-9`), so the premise that this doc already carries weight is correct.
- AC-4 (state plainly what's *not* part of the contract) is the right kind of criterion for a stability promise, and the existing review comment already strengthened it with two concrete, verifiable candidates (the `-t` stdout-vs-stderr deviation, `displayOutcome`'s four frozen strings) rather than leaving it abstract.
- Anchoring every clause to a named test is the correct general shape for turning "observed behavior" into "a contract" — the design principle in finding #4 is about tightening the falsifier, not rejecting the approach.

## Bottom line

The issue is well-intentioned and partly self-corrected already (its own 2026-08-08 comment found real defects), but that correction hasn't been applied to the issue body, and independent verification against the current tree surfaces a harder problem the comment only partially named: this task's core deliverables (status 3, the xUnit schema, `-check`/`-report` artifact paths) don't exist yet anywhere in the code, so "freeze the surface" is premature until #466 lands the surface itself, with its execution-blocking decisions resolved. Needs rework before it's actionable: fix the ordering, make the status-3/schema clauses explicitly conditional on #466, and tighten AC-1/AC-2's test-coverage criterion with the same falsifiability standard already applied to AC-4.
