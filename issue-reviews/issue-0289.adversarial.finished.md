# Issue #289: Dark mode: FlatDarkLaf plus a dark Theme variant, currently impossible because ~113 draw sites hardcode black foregrounds
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: sound-with-concerns

## Summary

Verified independently against HEAD (5311625, 2026-08-09): `Theme` (`src/jls/Theme.java`, 10-field record, no `foreground` role yet), `UserPrefs.THEME_KEY` (`UserPrefs.java:32`), the FlatLaf `-Djls.laf` seam (`JLSStart.java:937-1006`), `ThemeTest`'s 25.0 delta-E bar (`test/jls/ThemeTest.java:33`), and the grep counts are all real and match the issue's claims. The infrastructure-reuse story is sound. But the acceptance criteria have a real gap (the test that would catch the actual failure mode — an illegible dark foreground — doesn't exist and isn't required), the P1 grep gate is worded in a way that cannot be literally satisfied, and one "if" in §7.1 is actually already true at HEAD, which the issue should say plainly rather than hedge.

## Findings (most severe first)

### 1. HIGH — No acceptance test gates foreground-vs-background legibility, the issue's own stated defect

The abstract's failure mode is explicit: hardcoded black draws "on a dark background they would be illegible." But every gate in §9/§14 is (a) the grep count, (b) `ThemeTest`'s delta-E matrix, or (c) a persistence round-trip. I read `test/jls/ThemeTest.java:1-80` directly: `DISTINGUISHABLE = 25.0` gates pairwise distances among wire-state roles (`touch`, `highlight`, `watch`, `nonZero`, `initialState`, `wireOff`, `wireZero` — see the `@param` list at `Theme.java:34-43`); it says nothing about a new `foreground` role's contrast against `background`, because that role doesn't exist yet and isn't named in the test. A `Theme.DARK` with `foreground = Color.black` and `background = Color.darkGray` would pass every stated gate (P1 grep ~0, P2 wire-state deltas unaffected since `foreground` isn't in that matrix, P3 persistence, P4 light unchanged) while every element label and outline is invisible — exactly the bug in the title. The second comment (2026-08-08) adds prose ("adequate contrast against a dark background… report the conflict") but names no test and sets no numeric bar, and that prose isn't reflected in the issue body's own §5/§9/§14. **Recommendation:** add an explicit `foreground`-vs-`background` contrast requirement (extend the same delta-E machinery, or a WCAG-style contrast-ratio check) as a named, gating test in §5/§9/§14 before implementation starts.

### 2. HIGH — The P1 grep gate ("113 → ~0") cannot be literally satisfied against the issue's own P4

Re-running `grep -rn "Color\.black\b\|Color\.BLACK\b" src/jls --include=*.java | wc -l` reproduces 113 exactly. But 2 of those hits are `Theme.java:65` and `Theme.java:81` — the `wireZero` field of `DEFAULT` and `CLASSIC` themselves, verified in the source (`Color.black, // wireZero` in both records). `ThemeTest.classicReproducesTheLegacyPalette` (line 42) asserts `assertEquals(Color.black, t.wireZero(), "wireZero")` — a correct, permanent constraint. So the grep can never hit ~0 while P4 ("CLASSIC and DEFAULT light rendering byte-identical") holds; only `src/jls/edit` (110, independently confirmed by direct grep) is the real sweep target. The issue's own P1 wording is internally inconsistent with its own P4. The stated fallback, "residual literals annotated," has no enforcement mechanism in §14 — nothing requires a test that fails on an un-annotated or unbounded allowlist (the second comment quotes exactly this failure mode from #381 — "an allowlist that has grown to cover everything is the failure mode" — as material to carry in, but that anti-vacuity test is not in the Completion Criteria checklist). **Recommendation:** scope the P1 gate to `src/jls/edit` (110) explicitly, or exclude `Theme.java`'s two palette-definition lines by name; promote the anti-vacuity allowlist test from "material worth carrying in" prose to an actual §14 checkbox.

### 3. MEDIUM — The 113 figure silently includes one literal that should probably *not* be swept, and the issue doesn't say so

Breakdown, independently verified: 110 in `src/jls/edit/*.java` (the real draw-site bugs), 2 in `Theme.java` (deliberate palette constants, see Finding 2), and 1 in `src/jls/BatchTracePrinter.java:176` (`gg.setColor(Color.black)`), which is on the batch trace-printing path. §7.1 itself says "exports and printing must pin the light/classic palette" — under that same logic, `BatchTracePrinter`'s literal is arguably *correct as shipped* and should be left alone, not mechanically swept into a theme-following `foreground` role. Neither the second comment's "110 (`src/jls/edit/`)" figure nor the issue body's undifferentiated "113" flags this one file as a case requiring a decision rather than a mechanical edit. **Recommendation:** state the three-way breakdown in Observations (110 sweep targets / 2 palette constants excluded / 1 print-path literal requiring an explicit keep-or-sweep decision), matching the more careful count the maintainer's own comments already did piecemeal.

### 4. MEDIUM — §7.1's "if export paths read the active theme" is not hypothetical; it is true today, independently confirmed

I traced the actual call path: `CircuitRenderer.exportImage` (`src/jls/edit/CircuitRenderer.java:301-382`, both the raster and `.svg` branches) and `CircuitRenderer.print` (`:186`) both call `draw()`/`ElementRenderers.draw`, the same method the interactive canvas uses. That shared path reads `JLSInfo.Palette.touchColor`, `.highlightColor`, `.wireOffColor`, `.nonZeroColor`, `.wireZeroColor`, `.watchColor`, `.initialStateColor` — confirmed directly in `WireRenderer.java:64-76`, `WireEndRenderer.java:34-62`, `StateRenderer.java:61-163`, `RegisterRenderer.java:47`, `PinRenderer.java:76`, `MemoryRenderer.java:43`, `JumpStartRenderer.java:65` — and those statics are exactly what `Theme.apply()` rewrites (`Theme.java` javadoc: "every consumer follows the active theme without being edited"). Only the export/print *background* is hardcoded white (`CircuitRenderer.java:323,372`); every element/wire color is not. So switching to CLASSIC today and exporting a PNG or printing already bakes CLASSIC's red/green/cyan/blue into the output — this is a live bug that predates #289, not a risk contingent on DARK shipping. Writing §7.1 as "if" invites an implementer to treat it as optional dark-mode-specific polish. **Recommendation:** reword §7.1 as a confirmed finding with the cited call sites; separately decide whether the existing CLASSIC-leaks-into-exports bug is in scope for a "dark mode" task or deserves its own tracking issue (it will get strictly worse once a low-key-value DARK `wireZero`/`foreground` exists, but it is not new).

### 5. MEDIUM — §7.4 locks in a single `foreground` role while the issue's own second comment argues against exactly that shape

§7.4 states definitively: "`Theme.foreground()` role (name final at implementation)." The second comment (2026-08-08), presented as material worth carrying into execution, says the opposite: "A colour with no matching `Theme` role must fail the sweep, not acquire an allowlist entry silently — and the fix is a role named for what it means semantically, never a twelfth role called 'black.'" Taken literally, that means distinct call-site categories (element outlines, state-machine text, wire-zero strokes are already a separate role, memory-cell borders, etc.) may need distinct semantic roles, not one catch-all — a materially larger design than a single find-replace. The issue body never resolves this tension: §7.4 (normative contract) and the inbound comment (guidance for execution) point in different directions, and nothing in §8/§14 flags it as an open decision. **Recommendation:** decide before implementation whether `foreground` is one role or several and update §7.4 accordingly; if it turns out to be several, the "mechanical, no new helpers expected" cost estimate in §7.5 no longer holds and should be revised.

### 6. LOW/MEDIUM — The `blocked_by: [286]` dependency is explicitly waivable, undermining the issue's own Research Question

§3 asks for "canvas, chrome, and L&F flipping together." `blocked_by: [286]` exists because, per this issue's own text, "chrome must follow Theme roles before any dark palette can restyle it." I confirmed #286 is open, unstarted (1 comment, no PR referenced) via `issue_read`. Yet §14 offers an explicit out: "Blocker #286 landed (or dependency waived per rule 10)." If #286 stalls and #289 proceeds via the waiver, the shipped result is a themed canvas next to #286's own documented hardcoded chrome (`Color.CYAN`/`yellow`/`WHITE` at `SimpleEditor.java:408,411,3946-3975,2334,2404`, per #286's Observations) on a dark background — worse UX than no dark mode, and not what §3 promised. **Recommendation:** either make the #286 dependency hard for the "chrome" portion of the Definition of Done (no waiver), or scope §3's Research Question down to "canvas dark mode" if the waiver path is taken, so a waived landing isn't measured against a promise it didn't keep.

### 7. LOW — §7.4's "through the existing `installLookAndFeel` seam" undersells the amount of new runtime-swap code needed

`JLSStart.installLookAndFeel()` (`JLSStart.java:994-1016`, confirmed by direct read) is a one-shot, boot-time static call with no notion of live theme switching — it picks a L&F once at startup based on `-Djls.laf`. The live flip described in §7.9 (`SwingUtilities.updateComponentTreeUI` on theme change, presumably triggered from the Color-scheme menu while the app is running) is new machinery layered beside that seam, not reuse of it. This is a framing nit — §10's Falsification Criteria already correctly anticipates the real risk ("restrict L&F choice to next-launch" if live swap destabilizes dialogs) — but it means the "mechanical … no new helpers expected" framing in §7.5/§8 doesn't actually cover H2's live-swap requirement. **Recommendation:** note explicitly in §7.4 that H2 is new code, not seam reuse.

### 8. LOW — No chunking plan for a ~110-site, cross-file mechanical sweep

§2 and §8 call the sweep "mechanical, reviewed in chunks" but no chunk boundary is proposed (per file? per renderer category? one PR?). Given P4 requires provably byte-identical light rendering across the entire sweep, one large PR is exactly the shape most likely to hide the "semantic mistake" the second comment itself warns a "110-site mechanical diff hides… easily." Process/cost risk, not correctness. **Recommendation:** commit to a chunking scheme (e.g., one PR per renderer file, each gated by the #24 pixel-baseline suite) in §8.

## What's solid (no attack needed)

- Infra-reuse claims check out on direct inspection: `UserPrefs.THEME_KEY` persistence (`UserPrefs.java:32,83,125`) needs no new code; FlatLaf (`pom.xml`) already bundles `FlatDarkLaf` in the same jar per #153's own decision record in `ARCHITECTURE.md`, so H2 needs no new dependency.
- `ThemeTest`'s CIE76/Vienot delta-E harness is real, currently green, and mechanically extendable to a third theme — a good regression net for the wire-state part of the problem (see Finding 1 for what it doesn't cover).
- P4 (CLASSIC/DEFAULT rendering byte-identical post-sweep) is a well-chosen regression guard against exactly the "mechanical diff hides a semantic mistake" risk the maintainer separately names in the second comment.
- The dependency/duplication bookkeeping against #381 and #570 (first comment) is unusually careful for a task-tier issue — the "who owns dark mode" question is resolved with cited evidence rather than left ambiguous, which is more than most trackers manage.
