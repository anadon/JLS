# Issue #574: FEAT-C32-3: every shop-window surface — README and example gallery — carries a "Try it in your browser" link that lands on a running demo circuit
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

#574 is the last link in a three-deep chain (CAP-32 #516 → FEAT-C32-1 #572 → FEAT-C32-2 #573 → FEAT-C32-3 #574): it wires README and gallery links to a browser demo that does not exist yet and whose implementation mechanism has not even been chosen. Confirmed against the checkout: there is no GitHub Pages workflow (`.github/workflows/` has only `ci.yml`, `codeql.yml`, `mutation.yml`, `release.yml`, `repro-installers.yml`, `scorecard.yml` — no `pages`/`gh-pages` job), no gallery page, and no `Try it` string anywhere in `README.md` or `docs/`. The issue's own scoping (in its one comment) is careful and largely defensible; the acceptance criteria themselves have real gaps.

## Findings, most severe first

**1. AC-4 assigns this issue accountability for content it explicitly disclaims owning.**
AC-4 reads: "The landing flow preserves the funnel: demo page states what the full tool adds and links the installers (capstone AC-4)." But the Boundary notes say: "Integration only: this feature adds links and gallery wiring; the demo mechanism **and pages** are FEAT-C32-1/-2's scope." A criterion about what the *demo page* states cannot be verified by anything #574 actually changes (README/gallery links) — it can only be verified by inspecting #573's output. As written, #574 can be "done" (links added, pointing at a page that violates AC-4) while its own AC-4 checkbox is ambiguous: is it #574's failure or #573's? Recommend either dropping AC-4 from #574 (it's already #573 AC-5 verbatim) or rewriting it as something #574 actually controls, e.g. "the link text/label itself sets the expectation that the desktop tool is the full product" plus a cross-reference check that #573's page satisfies its own AC-5 before #574's links go live.

**2. AC-3's "operated or account-gated" line is inherited, not tightened, and is not testable as written.**
Quoted: "AC-3: Links resolve to static pages only — no redirect through anything operated or account-gated (capstone AC-3)." Nobody defines "operated." GitHub Pages — the obvious host (see #551: "published via the repository or GitHub Pages") — is itself infrastructure GitHub operates; it is publicly viewable without an account but authoring/redeploying it requires the maintainer's GitHub account. If that counts as "operated," AC-3 is already violated by the most likely hosting choice; if it doesn't count, the criterion needs to say so explicitly (e.g. "static hosting under this project's own domain/Pages site is fine; third-party demo SaaS is not"). There is no test named anywhere (unlike, e.g., #545 AC-4's drift check or #551 AC-2's CI regen) that could catch a future PR silently adding a redirect through a gated service. Recommend a concrete, automatable rule ("link host must be one of: github.io project pages, this repo's raw content — nothing else") plus a link-checker test, analogous to the existing `HelpTopicsTest` link checker cited in ARCHITECTURE.md.

**3. The mechanism this issue's links will point to may itself violate the "nothing operated" property it asserts, and #574 never checks.**
#572 (the feasibility spike this whole chain rests on) picks CheerpJ as the primary candidate: "CheerpJ-wrapped jar running the Swing GUI." CheerpJ's standard deployment loads its runtime loader from Leaning Technologies' own CDN (`cheerpjloader.js` from a leaningtech-operated origin) unless self-hosted — an external, third-party-operated dependency at *page-load* time, not just at build time. That is exactly the kind of "operated" dependency capstone AC-3 ("nothing to operate, nothing that can die and take user data with it") and #574's own AC-3 are trying to rule out. #574 takes AC-3 as a given constraint on the pages it links to but has no mechanism to verify the winning implementation actually satisfies it — it just assumes #573 got it right. Given #572/#573 are both still open and no go/no-go has been recorded, this is a live risk this issue inherits blindly. Recommend #574 not be started (or at least not closed) until #572's go/no-go comment confirms the chosen mechanism is self-hosted/CDN-free, since that determines whether #574's AC-3 is even achievable.

**4. Title and AC-1 presuppose an interactive outcome that the cited kill-criteria explicitly allow to not happen.**
Title: "...lands on a running demo circuit." AC-1: "lands on a running FEAT-C32-2 demo page." But #516 KC-32-1 and #572 AC-4 name two fallback mechanisms if CheerpJ fails: "(a) headless-rendered interactive SVG with a JS signal player" (still arguably "running") and, critically, "**(b) recorded video walkthroughs**" — which is not a running demo circuit by any reading, it's a video. If PF-1's spike lands on fallback (b), #574's title and AC-1 become false on arrival: the linked page would show a passive recording, not something a user "pokes." Nothing in #574 flags this contingency or says what happens to its own title/AC wording if PF-2 ships as fallback (b). Recommend #574 either be filed with wording robust to any of the three PF-1 outcomes ("lands on the FEAT-C32-2 demo page, whatever form it takes") or explicitly blocked from being worded/closed until PF-1's go/no-go is known.

**5. AC-2's "demo-enabled example" is undefined, making the criterion gameable.**
"AC-2: The published example gallery (#551) links each demo-enabled example to its corresponding demo page." Neither #574, #573, nor #572 defines what makes an example "demo-enabled." #572's spike is scoped to "the three biggest example circuits" only; #573 claims to serve "the CAP-27 curated example set" (implied: all of it) "with captions." If the CheerpJ/SVG-player subset only ever covers a handful of examples (element-subset gaps are a known risk pattern in this project — see the closed #500's PF-2 "unsupported-element report" language for the sibling HTML-export capstone), AC-2 is satisfied whether 1 example or 20 examples get links, and there's no lower bound. A gallery that links exactly one trivial demo example still "passes" AC-2 literally. Recommend AC-2 name a concrete completeness bar (e.g., "every example #573 ships a demo page for, no fewer, verified by a scripted cross-check between the gallery's example list and #573's page manifest").

**6. No drift/link-rot enforcement is specified, unlike sibling issues in the same cluster.**
#551 AC-2 requires gallery regeneration "by one scripted command in CI... so renders cannot silently drift." #545 AC-4 requires a build-time drift check for README image paths. #574 has no analogous requirement for the links it adds — nothing says a CI job asserts the "Try it" URLs actually 200 and land on content, so link rot (demo page moved, #573's static host renamed, GH Pages path changed) would go undetected indefinitely. Given the project already has a working pattern for this (`HelpTopicsTest`, per ARCHITECTURE.md's Test layout section), the omission here looks like an oversight rather than a deliberate scope cut. Recommend adding an AC modeled on the siblings' drift checks.

**7. "Prominent" (AC-1) is unfalsifiable as written.**
"AC-1: The README carries a prominent 'Try it in your browser' link..." — no placement, styling, or above-the-fold requirement is given (contrast #545 AC-1's explicit "above the fold" language for screenshots). Any single link anywhere in the README technically satisfies AC-1 as literally worded. Low severity since a human reviewer will catch an obviously buried link at PR time, but it is still a criterion that could be gamed by a minimal-effort implementation. Recommend borrowing #545's "above the fold" concreteness.

## What's solid

- The de-duplication comment (2026-08-04) is a genuinely good piece of process hygiene: it correctly identifies and forecloses the tempting-but-wrong absorption of this issue's AC-2 into #551 and AC-1 into #545, with a concrete reason for each ("would make #551 unshippable until #572's go/no-go resolves"). This is the kind of boundary work that prevents scope creep, and it's already done here — no adversarial finding needed.
- `ordering_after` on both #573 and #551 is the right dependency shape, and the comment correctly notes the failure mode is graceful (#551 ships with these links simply unfilled if #573 stalls) rather than blocking.
- `band_mw: "0.5-1"` is a plausible estimate for "add some links" scoped as described, assuming the upstream demo mechanism exists — the cost estimate is not the problem, the premise is.
- Explicitly re-citing KC-32-2 (no in-browser editor) as an inherited scope cliff rather than silently assuming it is good practice and keeps this issue from quietly growing into editor-adjacent scope.

## Recommendation

Do not schedule implementation work on #574 until #572's feasibility spike has produced its go/no-go and #573 has a concrete page to link to — the issue is currently unimplementable and several of its ACs (2, 3, 4) cannot be meaningfully verified against a target that doesn't exist. Before that, tighten AC-2/AC-3/AC-4 per findings 1, 2, 3, 5 above so the criteria are actually checkable once the upstream lands, and hedge the title/AC-1 wording per finding 4 against the recorded possibility that PF-1 resolves to the "recorded video" fallback rather than a running demo.
