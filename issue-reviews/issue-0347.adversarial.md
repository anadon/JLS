Every one of §§1–7's most load-bearing claims (the record's negative field contract, the exclusion-set mechanism, the sync-point digest, §5.3's "deliberately-failing null test", §8.3's ratification block) is sourced to this phantom document. An implementer who follows "do not restate it; implement it" has nothing to implement against. This is the same defect independently found in the fleet's review of issue #359 (`issue-reviews/issue-0359.adversarial.md`, finding 2) and is visible in the body this reviewer already quoted from issue #326's own text, so it is not a one-off transcription slip — it recurs across the planning corpus this issue belongs to. Recommendation: before filing any of TASK-0069/0070/0072/0073, either commit `docs/parity-contract.md` for real or strip every "already specified" claim and re-derive the record/comparator/exclusion-set design from scratch in this issue.

**4. [High] Acceptance criterion IC-1 (the null test) is underspecified enough to be gameable, and Open Question 5 admits it.**
Criterion 6 / IC-1 requires "a knowingly wrong implementation… ships beside it and the harness must reject it." But Open Question 5 asks "What is the knowingly wrong implementation, concretely? A single injected bug is easy to pass around… (a) a small family of injected faults… (b) one" and leaves it unresolved, merely recommending (a) as a default. As written, IC-1's Do/Observe pair ("run the harness against the knowingly wrong implementation… Observe: FAIL, at a named retirement index and field") is satisfiable by a single trivially-detected fault (e.g., always-return-zero for one register), which would make the harness look validated while leaving whole classes of subtler divergence (off-by-one retirement counting, an excluded bit that shouldn't be, a sync-point digest that never fires) completely unexercised. Nothing in §4's invariants or the DoD requires the fault family to be adversarially chosen against the comparator's actual mechanisms (retirement-index alignment, exclusion-set masking, digest sync points) rather than against the reference machine's ISA semantics. Recommendation: pin Open Question 5 to option (a) now, and additionally require at least one fault per comparator mechanism (a mis-retired instruction, an excluded-bit leak, a state divergence invisible at retirement but caught at a sync point) so IC-1 cannot be satisfied by one easy fault.

**5. [Medium] The verdict lattice's UNKNOWN case is defined by exclusion ("otherwise") and never operationalized — nothing says when it actually fires.**
§3's formula gives PASS and FAIL($k^*,f^*$) precise conditions, then assigns UNKNOWN to "otherwise" with no worked case. §4 invariant 4 says "the verdict lattice never collapses UNKNOWN into PASS" and IC lists nothing that exercises UNKNOWN. A harness whose third lattice value is only ever asserted never to equal PASS, but is never shown occurring, risks being implemented as effectively binary (PASS/FAIL) with an UNKNOWN branch that is dead code — satisfying invariant 4 vacuously because it's never reached. Recommendation: add an integration criterion that manufactures an UNKNOWN condition (e.g., truncate one trace, or omit a sync point) and asserts the verdict is UNKNOWN, not PASS and not FAIL.

**6. [Medium] Scope-boundary tension between invariant 1 ("`jls.sim` is not modified. Not one line.") and criterion 7 ("Host input is logged in retirement index and replays deterministically").**
Retirement-indexed input logging requires knowing, at input-injection time, which retirement index is "current" — but the four consumed hooks (`beforeEvent`, `beforeReact`, `afterEvent`, `probeSample`) are all *reactive* (fired after/around an event), and the issue never states which hook, or what combination, derives a monotonic retirement counter without the simulator itself exposing one. If retirement counting turns out to require a new counter field or a new hook in `jls.sim`, invariant 1 and criterion 7 are in direct conflict, and the re-planning protocol only covers "TASK-0072 is refuted" (a different task) — it does not name this specific tension. This is exactly the class of risk §7 says it wants surfaced ("never an unreviewed [seam]"), but the issue does not surface it here. Recommendation: state explicitly, before filing TASK-0069, whether retirement counting is derivable purely from `afterEvent`/`probeSample` call order in the *existing* code, with a concrete pointer to how (which JLS elements' `react()` calls constitute a "retirement" is not obvious from `Simulator.java` alone — retirement is an ISA-level concept the simulator has no notion of).

`ARCHITECTURE.md`'s own module layout confirms `Simulator`/`BatchSimulator` "import no AWT, Swing, or `jls.edit`" and cites `HeadlessCoreRatchetTest` as the enforcing test (issue #77) — this part of the issue is grounded in something real and checkable, unlike findings 1–2 above.
