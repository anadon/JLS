## Findings, most severe first

### 1. The exclusion boundary against #277 is self-contradicting for the one file that matters most (P3)

**Evidence.** Completion Criteria: *"No file named in §2 O3 is touched — those four dispatch sites are #277's"* — and O3 names `src/jls/edit/SimpleEditor.java:2312-2321` as one of the four (the toolbar/palette builder). Separately, P3 requires: *"Register an op observer and perform a gesture; observe the observer sees every submitted mutation, including the multi-op gestures the op sink collapses."* I read the actual mutation choke point this has to hook into: `src/jls/edit/SimpleEditor.java:5547-5571`, the anonymous `OpSink` whose javadoc literally says *"The single mutation entry point (issue #167, collab Stage 0b)... The collaboration layer (issue #163) will observe this same entry point."* That is the only place in the codebase every `submit`/`submitAll` call passes through, collapsed multi-op gestures included (`submitAll` at line 5563-5570 does the collapse the issue is talking about). There is no other choke point to hang a fan-out on without touching this file.

So: satisfying P3 requires editing `SimpleEditor.java` — a file literally named in O3 — at a location ~3200 lines away from the excluded line range. The completion-criteria bullet says "no file," O3's own line-range framing says only specific lines are off-limits. Both readings are present in the same document and they conflict on the one deliverable (P3) that is central to this task's value proposition. Whoever picks this up will either (a) violate the "no file" bullet to deliver P3, or (b) refuse to touch `SimpleEditor.java` and cannot deliver P3 at all. Neither is a good default to leave to executor discretion.

**Recommendation.** Before work starts, restate the completion criterion at the correct granularity: "no code at `SimpleEditor.java:2312-2321` (or the equivalent post-drift range) is touched" — not "no file." Explicitly name the `opSink` definition (~line 5547) as in-scope for this task.

### 2. The determinism apparatus (P4/H3) is close to tautological at the current contributor topology, but is sold as the single most important thing in the issue

**Evidence.** §7.12 / §11: *"the determinism apparatus lands in this change, not later... P4's tests must exist before #277 lands, or there is a window in which a contribution-order bug is undetectable... the single most important sequencing fact here."* I read `ModuleResolver.java` (the thing the determinism claim rests on): its own javadoc already states *"The order is Kahn's topological sort with an id-sorted tie-break, so it is a pure function of the manifest set — independent of input, discovery, or iteration order."* That guarantee is already shipped (#220, closed) and is presumably already covered by `ModuleResolverTest`/`ModuleRuntimeTest` if they exist.

More importantly, I read the four modules' `register()` methods: `CoreModule` contributes only to `elem.element-provider`, `GuiModule` only to `gui.palette-contributor`, `HdlModule` only to `hdl.exporter`, `CollabModule` contributes nothing. **No two modules contribute to the same extension point today.** A "contribution-order bug" (two contributors to one point folding in a different order) is structurally impossible to construct at this scope — there is nothing for declaration-order permutation to perturb. P4's three-way golden comparison (same order twice, then permuted) will pass trivially and for the wrong reason: not because determinism was verified, but because there is exactly one contributor per point to reorder against nothing. The urgency framing in §11 ("easy to get backwards," "single most important... fact") overstates the risk this test actually retires.

**Recommendation.** Either (a) demote this to a smaller, honestly-scoped test that documents the *current* single-contributor invariant rather than claiming to guard against order bugs that cannot yet occur, or (b) if the real intent is to pin `ModuleResolver`'s existing tie-break guarantee against regression, say that plainly instead of implying this task discovers a new risk.

### 4. P6 checks a coarser property than H5 claims to establish

**Evidence.** H5: *"Nothing this task adds reaches the simulation inner loop, assertable structurally rather than by review... Refuted by any registry or capability lookup reachable per event."* P6 / the Method checklist: implement this "in the shipped `test/jls/ArchitectureRulesTest.java` idiom." I read that file: every existing rule is a *package-level bytecode dependency* check (ArchUnit `noClasses().that().resideInAPackage(...).should().dependOnClassesThat().resideInAPackage(...)`), e.g. `onlyTheKnownDebtInSimDependsOnEdit`. That idiom proves "no compile-time type from package X is referenced from package Y" — it does not prove "no call reachable per event," which is the actual claim in H5. A capability lookup smuggled in through an already-permitted type (e.g., a `Consumer`/`Runnable` callback object constructed outside `jls.sim` and merely invoked inside it, or a lookup hidden behind an interface `jls.sim` is already allowed to depend on) would satisfy a package-dependency rule while still doing exactly what H5 forbids. This is a real gap between the falsification criterion's language and what the named idiom can actually check — not fatal (the existing idiom is a reasonable proxy and cheap to add), but the issue should not claim P6 gives structural proof of H5's stronger claim.

**Recommendation.** Either narrow H5's wording to match what a package-dependency rule can prove, or accept that P6 is a strong but incomplete proxy and say so.
