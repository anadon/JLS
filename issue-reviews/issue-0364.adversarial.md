## Findings, by severity

### 1. [High] The issue's own "done" gate is already broken by an un-reconciled machine block
The Definition of Done requires: *"Machine block, roster table, and mermaid graph agree with reality at close."* But the single comment on this issue (2026-08-04) states `#326` — the target of this issue's `blocks: [326]` edge and the `F36 --> F38` mermaid arrow — was closed as a duplicate, and the real edge is now `blocks: [202]`. The comment says the edge target changed; **the issue body's YAML machine block and mermaid diagram were not edited to match** — only a comment was appended pointing at the discrepancy. Any tooling or reviewer that parses the machine block programmatically (which the corpus's own "Link pass" methodology implies happens) will read a stale `blocks: [326]` today, 5 days after the correction was known. Recommendation: edit the issue body's YAML block and mermaid diagram in place (or require this class of correction to always edit the body, never just comment), since the stated completion criterion demands the body reflect reality and it currently does not.

### 2. [High] TASK-0013 ownership is a mutual-deferral hazard, not a resolved shared dependency
TASK-0013 (byte budget + copy-on-write init) is claimed by *both* this issue and #354 (FEAT-006), and each issue's Re-planning Protocol explicitly permits re-homing it to the other: this issue says *"TASK-0013 re-homed to FEAT-006 (#354): allowed — it is shared and either feature may own it"*, and #354 says the symmetric thing (*"TASK-0013 re-homed to FEAT-036"*). Neither issue names a tie-breaker or a default owner if both agents/executors independently assume the other will file it. Since `planned_tasks` requires each entry to resolve to "a filed issue or descoped" before either feature can close, this is a concrete way both features stall waiting on each other, or the task gets filed twice by two independent executors working the two feature issues in parallel (equally bad — duplicate work, potentially divergent designs for the same `newWordStore`/`initSim` code). Recommendation: pick one issue as the actual filer of TASK-0013 now (the issue text itself observes the number is "shared... at the task level," but sharing bookkeeping is not the same as assigning who acts).

### 3. [Medium] The Memory.java conflict-surface analysis in §6 undercounts who touches `setValue`/`save`
§6 states: *"the only shared file is `src/jls/elem/Memory.java` — where the mask work is in `init`/`react`/`setValue`/`save` and the budget work is in `newWordStore`/`initSim`, so the conflict surface is small."* This only accounts for two of the three planned tasks. TASK-0034 (bulk section) also modifies `Memory.java`'s `setValue`/`save`: §3 states the element gains *"one saved string attribute naming a bulk section"* and that a block declaring more than one image form (text / RLE / bulk) *"is a load diagnostic, not a last-writer-wins"* — logic that has to live in the same `setValue`/`save` methods the mask task is editing. So `setValue`/`save` are actually a three-way hot spot (mask attribute, mutual-exclusion diagnostic, section reference), not the two-way split the sequencing section describes when it hands "budget and section" to one agent and "mask" to another as if their edits land in disjoint methods. Recommendation: name `setValue`/`save` explicitly as the contested region across all three tasks and sequence edits there specifically, rather than asserting file-level parallelism is safe.

### 4. [Medium] Integration criterion 6 doesn't cover the case most likely to be drawn wrong
Criterion 6 (*"mask's absence means all-ones, not zero"*) and the arithmetic in §3 test two states: mode off (no port), and mode on with every mask bit explicitly set to 1. Neither tests mode on with the mask input **present but left unconnected** — the state a student is most likely to produce by accident when wiring a new port. JLS's simulation model is two-state-plus-HiZ (per `ARCHITECTURE.md`'s citation of `docs/simulation-semantics.md` §2/§9), so a floating mask input reads as HiZ, not as a defined 0 or 1 bit, and $M(m)$ in the masked-write formula is undefined for $m \notin \{0,1\}^\ell$. The issue specifies "absent" (attribute/port doesn't exist) but never specifies "present-and-floating," which is a different and more common failure mode once the port exists. This is a real gap an implementation could pass the stated criterion 6 while still being silently wrong (e.g. treating floating mask bits as 0 and quietly write-protecting bytes a student expected to update). Recommendation: add a floating-mask fixture to the golden/integration plan and state its required behavior (e.g. reject, or treat HiZ lanes as unwritten with a diagnostic) in §3 rather than leaving it undiscovered.

### 5. [Medium] The "three capabilities, one issue" framing overstates what a WAIVED close actually delivers
The Abstract states *"No single child delivers this: the mask without the budget cannot address a real image, and the budget without the bulk section cannot carry one through the file"* — i.e., all three are needed together. But §7's Re-planning Protocol then says if TASK-0034 stays blocked by #319 indefinitely, *"the honest answer is that they can [ship without it]... criterion 2 is then WAIVED"* — meaning the issue can close DONE with only two of the three capabilities landed, directly contradicting the Abstract's "no single child / none alone" claim. This isn't a fatal flaw (the WAIVED path is explicit and honest about the disposition), but it means the CAP-08 audience ("anyone importing a published core... a real core's memory does sub-word writes and its image is a byte budget, not a word count") is oversold in the Impact section relative to what a WAIVED closure actually ships: a real, guest-scale image still would not be representable, since #319's own multi-week frame (with its own unresolved Open Question 1: text-grammar-vs-multi-member-container) is a hard prerequisite with no committed timeline. Recommendation: state the WAIVED-outcome capability set explicitly in the Impact section, not only in §7.

### 6. [Low] Open Question 1 ($B_{max}$) is a shared unknown gating acceptance, with no owner named for who answers it first
Open Question 1 (the byte budget number and its headroom) is stated as *"shared verbatim with #354 and must be answered once, not twice,"* and blocks TASK-0013's acceptance threshold in both issues. Like finding 2, this is a genuine shared unknown with no stated resolution mechanism (which issue's discussion is authoritative, or is it decided in a third venue?). Low severity because it's explicitly flagged as an open question rather than silently assumed, but it compounds finding 2: the same two issues that can't agree on who *files* TASK-0013 also haven't agreed on who *decides* the number that task's acceptance criteria depend on.
