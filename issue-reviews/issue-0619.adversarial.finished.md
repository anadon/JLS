# Issue #619: TASK-C558-5: one real published .dig circuit imports as a single undoable operation with zero unexplained losses
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

#619 (TASK-C558-5) is the closing acceptance task for FEAT-C29-2 (#558, the
`.dig` importer): it asks for one real published `.dig` circuit to import
atomically, undoably, with zero unexplained losses reported through #556's
shared schema. It sits at the bottom of an entirely unstarted dependency
chain — TASK-C558-1..4 (#612, #614, #615, #617) and TASK-C556-1/2 (#608,
#610), themselves resting on #323/#451/#314 — and none of that
infrastructure exists in the tree today (`grep -rli "digital|\.dig\b|xstream"
src/ docs/` returns nothing but a stray `docs/capability-roadmap` mention).
The task's citations check out in part (the no-partial-circuit half of
AC-2) but AC-2's "undoable operation" half cites a discipline that has no
precedent anywhere in the codebase, and AC-1/AC-4 inherit the same
single-file gameability this fleet already flagged on the parent issue.

## Findings, most severe first

**1. [HIGH] AC-2 bundles a real, verified precedent with one that does not exist, under a single "inherits" citation.** AC-2: *"Import is a single undoable operation; undo restores the workspace exactly, and a failure part-way through leaves no partial circuit behind (the `NetlistImporter` discipline #323 inherits; CAP-29 AC-4)."* The **no-partial-circuit** half is real: `NetlistImporter.importNetlist` (`src/jls/hdl/imp/NetlistImporter.java:70-114`) collects every problem and throws `ImportException` before any save text is emitted — confirmed by reading the code, and independently confirmed correct by this fleet's own #323 review ("the no-partial-circuit inheritance from `NetlistImporter.java:46-47`... checks out exactly"). The **undo** half has zero precedent. `NetlistImporter` has no editor integration at all — it is a pure text-emitting function consumed only by tests (`ImportPipelineTest`, `NetlistImporterTest`); a `grep` for `[Ii]mport` across `src/jls/edit/*.java` finds no File→Import menu item anywhere, and the only "import" concept that does exist in the editor (`Editor.java:187`, `:320-328`, `Circuit.isImported()`) is the unrelated subcircuit-reuse feature, not file-format import. `ARCHITECTURE.md`'s undo model (`CircuitSnapshot`, snapshot-before-each-mutating-gesture) is a plausible mechanism to reuse, but nothing today wires an importer into it. #323, the issue AC-2 says already "inherits" this discipline, is itself unstarted — its own report machinery (TASK-0054) is recorded elsewhere in this review fleet as absent/not-filed. So AC-2 cites an established lineage (`NetlistImporter` → #323 → #619) for a requirement that, for its undo half, has never been built once, anywhere, in this codebase. **Recommendation:** split AC-2 into the verified inheritance (no-partial-circuit) and the genuinely novel work (wiring any importer into the editor's undo stack for the first time), and price/scope the latter as new design work rather than inherited discipline.

**2. [HIGH] AC-1's single-file bar is the same gameable criterion this fleet already flagged on the parent issue — and #619 is the task that actually executes it.** AC-1: *"One real published `.dig` circuit imports with zero unexplained losses... (CAP-29 AC-1)."* This verbatim-copies CAP-29 AC-1 ("one real published circuit per format") without addressing the #558 review's finding 1, which contrasts this exact phrasing against CAP-16/#311's own sibling capstone: a ≥30-file, ≥3-repository corpus with a published per-construct coverage table and a measured >50% re-cost trigger (KC-16-1). #619 is not a restatement of that concern one level up — it is *the task where the single file gets chosen and committed*. As written, an implementer can satisfy AC-1 and AC-4 together by hand-picking one trivial `.dig` file with only basic gates, producing a CI fixture that never exercises the mapping table's harder cases (parameterized circuits, mux/adder mappings, the report's `mapped-with-caveat`/`refused` dispositions). The verification could pass while the outcome text's actual claim — "something an instructor can trust" — remains untested for anything beyond the easiest case. **Recommendation:** require the chosen fixture to exercise at least one instance of each disposition value in #608's closed vocabulary (`mapped`, `mapped-with-caveat`, `refused`, `dropped-by-design`), or require a small corpus (N≥3) rather than one file.

**3. [HIGH] The dependency depth is real but undisclosed in the issue's own risk framing.** `ordering_after` names three direct predecessors (TASK-C558-3 `#615`, TASK-C558-4 `#617`, TASK-C556-2 `#610`), but the actual chain underneath is: `#610` is blocked on `#608` (TASK-C556-1) plus `#323`/`#451`; `#615`/`#617` are blocked on `#614`/`#612`; `#614`/`#612` are the parse/map stages of #558 itself. That is **eight open, unstarted issues** beneath #619, several of which this same review fleet has already independently marked `needs-rework` for their own AC/scope problems (#556, #558, #562). Nothing in #619's "Boundary notes" flags that closing this single task requires the entire upstream stack to land cleanly first, several links of which are not yet even internally consistent. A reader of #619 alone has no way to see this. **Recommendation:** either link the full transitive chain (or a pointer to CAP-29's DAG) in Boundary notes, or add a note that this task cannot be estimated independently of its upstream siblings' outstanding rework.

**4. [MED] KC-29-1's ambiguity is carried forward unresolved.** Boundary notes restate CAP-29's kill criterion verbatim: *"at 1.5× #558's 4-6 mw band the format downgrades to a documented external-conversion recipe."* 1.5× of the 4mw floor (6mw) or the 6mw ceiling (9mw)? This exact ambiguity was already flagged on #558 (finding 7) with the same fix suggested (a measured trigger, as CAP-16's KC-16-1 has). #619 had the opportunity to resolve it when restating the criterion and did not. **Recommendation:** state the edge explicitly here, or point to wherever it was resolved upstream.

**5. [MED] AC-4's fixture requirement is silent on licensing/provenance, a risk this same capstone family has already flagged twice.** AC-4 requires the real `.dig` circuit be "a committed CI fixture" — i.e., checked into a GPLv3 repository. #323 (FEAT-025, the sibling `.circ` importer) devotes an entire Open Question to exactly this ("the licence question must be settled before absorbing any source... blocks filing children"), and #562's review flags the identical gap for Digital test-case fixtures. #619 is the third task in this capstone family to require committing someone else's published circuit without raising consent, attribution, or license compatibility. **Recommendation:** add a licensing/provenance check to the acceptance criteria or boundary notes, mirroring #323's Open Question 2.

**6. [LOW] `band_mw: "1"` has no stated derivation, and finding 1 suggests it undercounts.** If AC-2's undo integration really is novel work (finding 1) rather than inherited discipline, sourcing/vetting a licensable real-world fixture (finding 5), building a corpus/coverage argument (finding 2), and wiring end-to-end CI around all of it is plausibly more than 1 maintainer-week — the same "band copied forward without a task-level reconciliation" pattern this fleet flagged on #556 and #558. **Recommendation:** show a short cost breakdown, or explicitly note the 1mw figure assumes AC-2's undo work already exists (and is therefore contingent on finding 1 being wrong).

**7. [LOW] AC-4's "committed CI fixture" is a good mechanism undercut by the same single-file gap as finding 2.** The idea — a real fixture regression-tests the mapping table so a later change "turns the build red" — is sound engineering, but its value is bounded by what the one committed file happens to exercise. If AC-1's fixture is the same trivial file discussed in finding 2, the regression net it buys is correspondingly thin.

## What's solid

- **The no-partial-circuit half of AC-2** correctly and verifiably inherits real code discipline from `NetlistImporter` (`src/jls/hdl/imp/NetlistImporter.java:70-114`) — confirmed by direct reading, not just citation.
- **AC-5's `mapped-with-caveat` vocabulary** matches #608 (TASK-C556-1) AC-1's actual defined closed vocabulary (`mapped` / `mapped-with-caveat` / `refused` / `dropped-by-design`) exactly — a real, checkable cross-reference rather than invented terminology, and AC-3's "no `.dig`-specific report dialect" is consistent with that shared schema existing as designed (contingent on #608/#610 landing first, per finding 3).
- **The boundary note scoping out embedded test-case translation to #562** ("Embedded test-case translation is #562, not this task; this task only guarantees the test sections reached the model intact") matches #562's own stated scope split verbatim — a genuinely careful, non-duplicated boundary.
- **Explicitly restating and applying KC-29-1** rather than silently dropping the capstone's kill criterion is the right discipline, even though the criterion's own wording remains ambiguous (finding 4).
