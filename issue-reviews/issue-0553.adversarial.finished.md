# Issue #553: FEAT-C27-6: a switcher from Logisim-Evolution, Digital, CircuitVerse or Falstad gets a one-page map from the tool they know to JLS
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of the issue
Four "coming from X" one-pagers (Logisim-Evolution, Digital, CircuitVerse, Falstad) mapping each tool's concepts/gestures onto JLS, linking shipped examples, with honest gap statements and a placeholder importer-link slot. Declares `ordering_after: []` ("startable now"). Serves CAP-27 (#511) PF-6.

## Findings, most severe first

**1. Contradicts CAP-29 (#513) about what these four pages actually contain.** #513's own PF-6 reads: *"Migration documentation (0.5–1 mw): per-format 'what survives, what doesn't' pages (joint with CAP-27 PF-6)"* — i.e. CAP-29 is treating #553's four pages as the deliverable for **per-import loss reporting** (what a `.dig`/`.cv`/Falstad-text import drops or approximates). But #553's own body scopes these pages as general concept/gesture onboarding ("naming honestly what JLS does better and what it does not do") and explicitly forbids importer content: *"This feature must not specify or start importer work."* A page that is startable today, before any of CAP-29's importers (PF-2–PF-5, none merged) exist, cannot simultaneously be the "what survives, what doesn't" per-construct import-loss document CAP-29 is counting on — that content is definitionally post-import. Either #553's boundary note is wrong (it does need importer-loss content and should not be startable now), or #513's PF-6 cross-reference is wrong (it should file its own instrument). As written, one of the two capstones will find its PF-6 unsatisfied and nobody currently owns closing that gap. **Recommendation:** resolve before starting — either #553 explicitly excludes "what survives/doesn't survive an import" content and #513 files a distinct PF-6, or #553 is re-scoped/re-ordered to follow the importers so the loss content is real.

**2. `ordering_after: []` ("startable now") is false on the issue's own terms for two of four ACs.** AC-2 requires linking "at least one shipped example (FEAT-C27-2, #548) per major concept" — but #548 is open and unimplemented; confirmed against the repo: no `resources/samples/` directory and no example-circuit fixtures exist outside `test/fixtures/` (test-only, not user-facing). The issue's own comment (2026-08-04, pass-2 dedup) concedes this: *"AC-2's per-concept example links depend on #548's curated set existing... the example links are the part that waits."* Separately, the body itself says *"The comparison-table content overlaps FEAT-C27-1 (#545); write it once and reference it from both surfaces"* — but #545 is also open and unimplemented (grepped README.md for a Logisim-Evolution/Digital/CircuitVerse/Falstad table: none found). So the pages cannot be completed to their own acceptance criteria without two other open, unstarted issues landing first, despite `ordering_after: []` implying the opposite for anyone scheduling off that field mechanically. **Recommendation:** set `ordering_after: [545, 548]` (or split "prose can start now" from "AC-2/table references block completion") so the metadata matches the real dependency the issue's own text and comment already admit.

**3. AC-1 ("readable in under five minutes") is unverifiable and gameable.** No word/line budget, no reading-time methodology, no test. Contrast with sibling issues in the same batch: #545 AC-4 specifies a concrete `ReadmeOnboardingTest`-shaped drift check; #548 AC-3 specifies `SampleCircuitsTest`-shaped verification. #553 defines zero automated checks for any of its four ACs — nothing catches a page that balloons past five minutes, an example link that 404s after #548 refactors its sample set, or a claim that goes stale when #510 (a living survey, itself still open and being amended — comments through 2026-08-08) is corrected later. **Recommendation:** add a concrete gate, e.g. a word-count/line-count ceiling asserted by a test analogous to `ReadmeOnboardingTest`, plus a link-existence check for the example and importer-slot references (mirroring #545 AC-4's drift check).

**4. AC-2's "per major concept" is undefined, so the linking requirement is gameable.** "Major concept" has no enumeration or minimum count anywhere in the issue (contrast #548 AC-2's explicit category list: combinational/sequential/FSM/datapath/RV32I). A page could declare one trivial "major concept" and satisfy AC-2 with a single link while leaving the actual concept map (hierarchy, delay model, tri-state/HiZ, multi-driver resolution — the things #510 says JLS is genuinely differentiated or genuinely behind on) unlinked and unexamined. **Recommendation:** either enumerate the required concept set per tool (can borrow #510 §1's dimension list) or require a minimum link count with named categories, as #548 does.

**5. Feasibility/cost risk: four "honest," gesture-accurate comparisons at 1-2 mw is thin for the honesty bar AC-3 sets.** AC-3 requires claims honest per `docs/hdl-support-research.md` and the #510 teardowns. The #510 survey (verified above) is deep on tracker-mined *complaints* and scored *dimensions*, but thin-to-absent on the concrete UI *gestures* (click-to-wire, rotate shortcuts, subcircuit-drill mechanics) a migration one-pager needs to map accurately — that requires hands-on familiarity with four separate external tools, which the cited sources don't obviously supply. Getting this wrong is exactly the kind of thing that erodes trust with the switcher audience the page exists to keep. **Recommendation:** either fence "gesture-level" claims out of scope (map concepts only, not click-by-click UI) or budget time for verifying gesture claims against each tool directly, not just against #510's complaint-mining.

**6. `docs/hdl-support-research.md` is a narrow honesty source for a broad four-tool comparison.** That document (confirmed by reading it) is scoped to HDL export/import/simulation feasibility — relevant mainly to the Logisim-Evolution FPGA-export axis of #510's rubric, not to the bulk of what a "concepts and gestures" page for CircuitVerse or Falstad would cover (delay model, hierarchy, testing). Citing it as *the* other honesty anchor (alongside #510) overstates its coverage; a reader checking AC-3 compliance against that doc alone would find it silent on most of the page content. **Recommendation:** cite it only for the HDL/export claims it actually supports; lean on #510 (and, ideally, direct tool inspection) for the rest.

**7. README real-estate/scope-creep risk, acknowledged but not resolved.** The issue's own comment flags that #545 (comparison table / product pitch), #574 (browser-demo link) and #553 (four migration links) all write to the README's shop-window section, and asserts "fine as long as each owns distinct content" — but #553 gives no structural guidance (e.g., "one line + link per page in a dedicated section," vs. inlining full page content) for how four new pages get discovered from an already 369-line README without visually competing with #545's screenshots/GIF/table. Low risk of outright conflict (comment already adjudicated ownership), moderate risk of an unreviewed README layout scramble when three features land near-simultaneously. **Recommendation:** state explicitly that discovery is a single short linked section (not inlined content), to bound the README diff.

## What's solid
- The importer-link fencing (AC-4, boundary note) is clear and internally consistent: no page may imply an importer exists before it does, and ownership of `.circ`/`.dig`/`.cv`/Falstad-text importers is correctly deferred to #311/#513.
- The dedup against #545 (shared comparison-table content, authored once) is a sound instinct even though its scheduling implication (finding 2) isn't reflected in the metadata.
- Scope is otherwise appropriately narrow — docs-only, no code/test surface touched, low blast radius if the content itself is wrong (unlike an importer bug, a bad claim on a doc page is cheaply fixed).
