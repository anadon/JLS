## Findings, most severe first

**1. AC-2's cited honesty source barely covers two of the four named competitors, and not on the axis the table needs.** `docs/hdl-support-research.md` is scoped to HDL export/import/simulation feasibility (its own title: "HDL Support for JLS: VHDL, Verilog/SystemVerilog, and SystemC — Research Report"). Grepping it for the four comparison targets: Logisim-Evolution and Digital appear repeatedly but only in the HDL-export/FPGA-flow context (lines 14, 27, 104-134, 151-193, 295-316); **CircuitVerse and Falstad are never mentioned anywhere in the document's 579 lines.** AC-2 says the table must be "honest per `docs/hdl-support-research.md`" — for half the row set there is nothing in the cited document to be honest *against*. A reviewer checking AC-2 compliance literally cannot use the named source for two of the four rows, so either the claims about CircuitVerse/Falstad are unsourced (contradicting "honest per X") or the criterion is unenforceable as written. This is independently corroborated by the sibling review of #553 (`issue-reviews/issue-0553.adversarial.md`, finding 6), which flags the exact same document for the exact same reason on a related task — two different reviewers, same gap, same citation. **Recommendation:** name the actual evidentiary source per row (e.g. #510's niche-survey teardowns, which per #511's `evidence:` field are the real per-tool competitive research) and reserve `docs/hdl-support-research.md` for the HDL-export axis only, where it actually applies.

**2. AC-2's second honesty clause is a category mismatch: it cannot be tested the way it's phrased.** AC-2 continues: "no claim a fresh clone cannot reproduce (#73 §4 invariant)." #73 §4's actual text is "README claims nothing a fresh clone cannot reproduce" — a verifiability bar for claims *about JLS*, checkable by building the fresh clone and confirming the behavior. A comparison-table row about Falstad's or CircuitVerse's feature set is a claim about a different project's software; "reproduce it from a fresh clone of JLS" is not a coherent test for that claim (a fresh JLS clone reproduces nothing about a competitor). The invariant is being imported wholesale from a context where it makes sense (self-claims) into one where it doesn't (third-party claims), leaving AC-2 with no defined verification method at all — contrast AC-1 and AC-4, which both cite a concrete automatable check. **Recommendation:** split AC-2 into two testable halves: claims about JLS itself (checked against the invariant as originally scoped) and claims about competitors (checked against a named, dated source per row, with a "last verified" note since competitor feature sets drift).

**3. Internal contradiction between the boundary note and AC-1 over who owns the screenshots.** The boundary note states plainly: "#73's planned 'README onboarding pass' task... and #381 TASK-0030's README items are the baseline. This feature owns only the shop-window delta on top: the animated GIF, the comparison table, badge curation, and the gallery link" — i.e. screenshots are explicitly *not* this issue's item. Yet AC-1, the first acceptance criterion, requires "at least two screenshots plus an animated GIF... all checked in." If #545 is implemented before #381 lands (nothing blocks that — `ordering_after: [381]` is declared "convention, not necessity" in both #545's yaml comment and the dedup comment), AC-1 forces #545 to author the same two screenshots #381's Method §8 already plans to add ("Add two README screenshots... add `test/jls/ReadmeOnboardingTest.java` (P4)"). That is not a delta; it is the same deliverable claimed by two open issues, with no adjudication comment addressing the #545↔#381 (or #545↔#73) overlap the way the same-day comment addresses #545↔#551/#553/#574. Whichever lands second either duplicates work or discovers its AC/task item was already satisfied by the other, silently. **Recommendation:** add an explicit boundary comment resolving #545 vs. #381/#73 the same way the existing comment resolves #545 vs. #551/#553/#574 — either #545 hard-depends on #381's screenshots landing first (and `ordering_after` should say so, not merely "convention"), or AC-1 is rephrased to require screenshots *exist* (satisfied by either issue) rather than requiring #545 to add them.

**4. AC-4 names a test class that doesn't exist yet, owned ambiguously.** "`ReadmeOnboardingTest` shape #381 §8 already plans" — confirmed: `test/jls/ReadmeOnboardingTest.java` is not present in the repo (`find test -iname '*Readme*'` returns nothing under `test/jls`), and #381's own Method checklist (§8, second-to-last bullet) is the one that actually schedules writing it, as P4's verification. #545 does not list #381 as a blocker (`blocked_by`/`ordering_after` treat it as soft), so #545 may need to write this test itself to satisfy its own AC-4, then #381 writes "the same" test again per its own checklist — same class name, same purpose, two authors, no filed coordination. This is the same root cause as finding 3, surfacing again on the test surface rather than the asset surface. **Recommendation:** same fix as finding 3 — pick one owner for the test file and have the other issue's AC/task reference it rather than re-plan it.

**5. AC-3 ("badges are curated... decorative badges are removed") describes a problem that doesn't exist in the current README.** `grep -n '!\[' README.md` returns exactly one image reference: the OpenSSF Scorecard badge (line 3), and it is unambiguously informational (security posture), not decorative. There is no badge clutter to curate today — #73's own O4 observation (cited by #381) independently confirms the README's only image is that same badge. As written, AC-3 is trivially satisfiable by doing nothing (there is nothing to remove) or is silently redefined to mean "don't add decorative badges while adding others for CI/build/license status" — a materially different, unstated task. **Recommendation:** rewrite AC-3 as a forward-looking constraint ("badges added by this change are limited to X, Y, Z; none purely decorative") rather than an audit-and-remove criterion that has nothing to act on.

**6. Feasibility/cost risk: `band_mw: "1-2"` looks light for the actual scope once the dependency tangle is priced in.** In scope: capturing 2+ screenshots and an animated GIF (no GIF-capture tooling exists anywhere in the repo — `scripts/` has `grim`-based static screenshot rigs (`wayland-rig.sh`, `x11-rig.sh`) but nothing that records/encodes an animated sequence; this has to be built or done by hand outside CI, and #519 (CAP-35), which is explicitly named as owning "screenshot-generation-from-source infrastructure," is not required to land first — "hand-captured images here are acceptable until that lands"), authoring a 4-tool comparison table honest per findings 1-2 above, curating badges, wiring the #551 gallery link, and resolving the #381/#73 overlap in findings 3-4. Sibling capstone #511 bands the *whole* PF-1 slice at "1-2 mw" too, so this isn't a #545-specific padding error, but the unresolved dependency risk (finding 3) means the actual work could silently double if #381 hasn't landed first. **Recommendation:** price the GIF-capture step explicitly (tooling to build or manual-and-documented-as-manual, per the pattern #381 §9 already uses for its own screenshot matrix) and flag the estimate as contingent on #381's landing order.

**7. No repository-size or asset-hygiene bound on the checked-in GIF/screenshots.** AC-1 requires the assets be "checked in," full stop — no size cap, no compression requirement, no format guidance (a naive uncompressed screen-recording GIF of "drawing-and-simulating" can easily run into tens of MB). Checked-in binary assets are permanent in git history; an oversized or poorly-optimized GIF becomes a standing clone-size tax with no test catching it (AC-4's drift check only asserts the path exists, not that the asset is reasonably sized). **Recommendation:** add an explicit size ceiling (e.g. "<2 MB GIF, <500 KB per screenshot") and note the compression approach (many maintainers convert to a looping WebP or an MP4-with-poster instead of raw GIF for exactly this reason).

- AC-4's core mechanism (a drift check that fails the build on a dangling README image path) is concrete, automatable, and consistent with the project's existing test-backed-contract style (`FormatHeaderTest`, `LookAndFeelPolicyTest`, etc.) — the right shape even though its ownership vs. #381 is unresolved (finding 4).
- Scope is appropriately docs-only: no `.jls` format, CLI, or simulation-core surface is touched, so blast radius on a wrong or incomplete landing is low and cheaply correctable.
- Deferring screenshot-generation infrastructure to #519 rather than blocking on it is a reasonable, explicitly-stated scope cut.
