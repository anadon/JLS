# Issue #823: TASK-C568-2: fifteen genuinely-first-issue items are labelled and each one names the files and tests it touches, so picking one requires no conversation
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: sound-with-concerns

## Summary of the issue

A curation-only task (no new code): label ≥15 open issues `good first issue`, each verified one-PR-sized, each carrying named entry-point files/tests (in-body or a curation comment), none requiring `SimpleEditor` internals without an explicit warning, each with a locally-checkable acceptance signal, and the pass recorded on parent #568. `band_mw: 0.5-1`, no `ordering_after`.

## Findings, most severe first

**1. No sequencing gate on #822 (fork CI) — the shelf can promise a green/red verdict that does not yet exist.**
#568 (the parent feature this task serves) frames the whole point as: "they pick one, push to their fork, and CI on the fork gives them a green/red verdict with zero maintainer action" (AC-3 there is fork-runnable CI, filed separately as #822, `TASK-C568-1`, still open). #823 declares `ordering_after: []` and its own AC list never requires #822 to be done first. If #823 lands before #822, a first-time contributor picks a freshly labelled "good first issue," pushes to their fork, and — per #822's own body — "can sit waiting on approval, which turns a five-minute feedback loop into a day." That is exactly the failure #568 exists to prevent, and #823 is the piece that puts a shelf in front of newcomers before the safety net (#822) is confirmed in place. Recommendation: add `ordering_after: ["TASK-C568-1"]`, or at minimum make AC-1 conditional on #822's fork-CI verification (its own AC-4) having landed.

**2. "Verified to be one-PR-sized against the current tree — not merely small-sounding" (AC-1) has no operational definition.**
There is no LOC/file-count/hour bound, no rubric, nothing distinguishing "small-sounding" from "verified." This is the exact criterion AC-1 exists to police, and it is unfalsifiable as written — a curator can satisfy it by assertion ("I checked, it's small") with no way for anyone else to audit the claim after the fact. Sampled candidates from the open `tier:task` pool vary wildly under an identical `band_mw` scale: #861 (a download-count collector script + idempotency + fixture test, `band_mw: 0.25-0.5`) reads as genuinely first-PR-sized; #316-adjacent tasks in the same tier run to `12-20` maintainer-weeks for the feature they belong to. Nothing in #823 requires citing the chosen band_mw, a diff-size estimate, or any other checkable proxy. Recommendation: require each curation comment to state a concrete bound (e.g. "touches N files, no new public API, estimated <1 day") so AC-1 is auditable rather than asserted.

**3. Stale entry-point references are a known, repo-documented failure mode this task does nothing to guard against.**
#316 (the very issue #823 cites for the SimpleEditor carve-out) records: *"`SimpleEditor.java` moves again before pickup: every line number here is trustworthy only at `2d0ca9d` — the file has five recorded re-baselines in July 2026 and grew 4,119 → 4,477 → 5,155 → 5,651 → 5,712 → 5,852. Re-derive before acting."* That instability is not unique to `SimpleEditor` in this tracker's style — many open `tier:task` bodies cite specific line numbers as evidence. #823's AC-2 requires naming entry-point files/tests at labelling time but has no re-verification trigger for when the cited lines drift before a newcomer picks the issue up (weeks or months later, per #568's "quarter" cadence in its sibling #824). A newcomer following a stale line reference into a 5,852-line file is the opposite of "picking one requires no conversation." Recommendation: either pin curation comments to a commit hash the way #316 does, or add a lightweight freshness check to the restocking rule (#824) that re-verifies cited files/lines still exist before a labelled issue is shown as current.

**4. Style/density mismatch between "good first issue" and the actual backlog is not addressed by labelling alone.**
The open `tier:task` pool (401 issues at time of review) is uniformly written in this project's dense formal-tracker style: YAML frontmatter (`task_id`, `part_of_feature`, `band_mw`, `ordering_after`), aphoristic titles, acceptance criteria that sometimes include mathematical notation and DAG-walk prose (see #316 for the extreme case, though that one is `tier:feature` not `tier:task`). By contrast, the four issues that *have* historically carried `good first issue` (#10, #12, #13, #27 — all closed) predate this convention and read as plain, short asks ("remove tracked CVS/ metadata," "expand README"). #823's acceptance criteria (AC-1 through AC-4) check scope and pointers but never check *readability* — an issue can be genuinely one-PR-sized and still be gated behind a body a newcomer cannot parse without first learning the tracker's vocabulary (`band_mw`, `ordering_after`, `part_of_feature`, tier semantics). AC-4's "acceptance signal a contributor can check locally" doesn't cover "can a contributor understand what's being asked without cross-referencing three other issues." Recommendation: add a criterion that the curation comment restates the ask in plain language, independent of the YAML header and tracker jargon.

**5. `band_mw` itself is undefined anywhere in the checked-out tree.**
`grep -r "band_mw"` across `README.md`, `ARCHITECTURE.md`, and `docs/*.md` returns nothing; the unit ("maintainer-week," presumably) and how it should be read against "one-PR-sized" is never spelled out in-repo. This isn't #823-specific, but #823 leans on the task tier's cost data ("drawn from the existing open task tier") as if it's a reliable filter, and there's no written definition a curator (or this reviewer) can check it against. Minor, but worth a one-line pointer to wherever `band_mw` actually is defined (if anywhere), so curation isn't guessing at what the numbers mean.

## What's solid

- The `SimpleEditor` carve-out (AC-3) is accurate and correctly deferred: #316 does own that decomposition, is genuinely blocked (`blocked_by: [317, 337]`), and is the wrong place to point a newcomer — the issue gets this right and cites the correct issue number.
- Correctly avoids re-litigating the restocking rule (#824) or the fork-CI mechanics (#822); scope stays to curation only, matching #568's own task breakdown.
- AC-2's "or a curation comment" concession is consistent with the tracker's stated convention ("bodies are not rewritten in this tracker") rather than inventing a new rule.
- The empty-shelf premise is factually verified: a live search confirms the `good first issue` label exists in the repo but currently zero *open* issues carry it — the outcome statement's framing ("stocked shelf... at least fifteen") is not solving an already-solved problem.
- Band (0.5-1 mw) and no-new-code framing are appropriately light for pure labelling/annotation work, modulo the actual research cost in finding legitimately small items (see Finding 2).
