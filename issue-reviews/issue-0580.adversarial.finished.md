# Issue #580: FEAT-C34-2: `winget install jls` works, and every release bumps the manifest without anyone remembering to
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Findings

### 1. (Critical) The Outcome's central claim is false against the current codebase, and the fix lives only in an unincorporated comment
The Outcome states: *"gets the same MSI the Releases page publishes — **the signed one**, matching the attested checksum."* AC-1 repeats it: *"installed MSI checksum matches the attested release asset."* But no signed msi exists on this repo today. Verified directly:
- `.github/workflows/release.yml:303` and `:307` still mark both Windows legs (`windows-latest`, `windows-11-arm`) `experimental: true`, so a broken Windows leg still ships silently (per #443's own analysis of the same lines).
- Issue #134 (Authenticode signing via SignPath) is open and blocked on a maintainer custody action (SignPath enrollment, unset `SIGNPATH_API_TOKEN`/`SIGNPATH_ORGANIZATION_ID`); its own text states "no signed msi exists anywhere."
- README.md:31-33 already asserts signing in the present tense while it is false — a defect #134 itself tracks.

The issue's own 2026-08-08 comment (posted after filing) admits this: *"The measured state on master... no Authenticode-signed msi exists anywhere. README already states in the present tense that the Windows installers are signed."* It proposes a "degraded mode" (ship against the unsigned msi, never assert "signed" anywhere in the manifest/listing). That is a reasonable fix, but it **rewrites AC-1's substance via a comment** rather than editing the issue body — the Outcome section and the literal AC-1 text an executor reads first still promise a signed installer. Any executor working from the machine-readable `ordering_after: []` block (unedited, still reads `[]`) rather than scrolling to the corrective comment starts unblocked and could ship a manifest whose surrounding prose repeats the false "signed" claim.
**Recommendation:** edit the issue body itself — reword the Outcome and AC-1 to drop "the signed one," add the degraded-mode language and the "must not describe the artifact as signed" constraint inline, and add an explicit `ordering_after_by_criterion` or `blocked_by`-style note so it survives a first read, not just a comment archaeology exercise.

### 2. (High) AC-2's "verified once end to end" doesn't define success against a process this project doesn't control
AC-2: *"A tagged release produces a manifest PR against `microsoft/winget-pkgs` with no manual steps beyond approval, verified once end to end."* "Verified" is undefined: does it require the PR to actually be **merged** by Microsoft's winget-pkgs moderators/validation pipeline, or merely opened? Opening a PR is fully within this project's control and automatable; merging is not — winget-pkgs runs its own automated validation (including installer execution and, for many manifests, checks tied to code-signing status) plus human moderator review, on a timeline this project cannot set. As written, an executor could open one PR, watch CI post it, call AC-2 "verified," and close the issue while the manifest is still sitting in Microsoft's review queue or has been rejected — meaning `winget install jls` (AC-1, the actual user-facing outcome) never works, yet the acceptance criterion reads satisfied.
**Recommendation:** state explicitly that AC-2 requires the PR to be **merged and the package installable via `winget install`**, and give a decision rule for what happens if Microsoft's review stalls or rejects the manifest (e.g., unsigned-installer policy — see Finding 3).

### 3. (High) Feasibility risk: winget-pkgs validation may itself flag or reject an unsigned MSI
Compounding Finding 1: `microsoft/winget-pkgs`' automated validation pipeline performs installer execution/analysis and can flag manifests over authenticity signals for unsigned Windows binaries; community moderators have in the past pushed back on unsigned installers for exactly the SmartScreen-reputation reason README.md already documents. The issue nowhere addresses the possibility that submitting against the *currently unsigned* msi could be rejected or delayed by winget-pkgs' own review — a real risk that directly threatens AC-2's "verified once end to end," and is a stronger reason than the issue credits for `ordering_after` to at least *soft*-depend on #134 landing before the first real submission attempt (the round-2 comment's "degraded mode" argues the opposite; that tradeoff isn't argued against the actual winget-pkgs review policy, just asserted).
**Recommendation:** research winget-pkgs' actual policy on unsigned installers before scoping AC-2's timeline; if rejection risk is material, either sequence the first live submission after #134, or record the risk explicitly as the issue's Boundary section does for the msi-signing gap generally (it currently only names the *SmartScreen UX* risk, not the *submission-acceptance* risk).

### 4. (Medium) AC-5 is unfalsifiable / gameable as worded
AC-5: *"The per-release cost of the winget submission-and-review cycle is recorded against KC-34-1's 0.5 mw threshold."* No methodology is specified: what counts as "cost" — maintainer keyboard-time only, or elapsed wall-clock time waiting on Microsoft's async review (which per Finding 2/3 is outside this project's control and could span days)? "Recorded" has no correctness bar — writing down any number, however unmeasured, satisfies the letter of the criterion. Since KC-34-1 (in the parent capstone #518) is a kill criterion that can cause the whole channel to be dropped, an inaccurate or cherry-picked cost figure has outsized downstream consequences.
**Recommendation:** define the unit (maintainer-minutes of active work vs. elapsed calendar time to merge) and require at least one real release cycle's data, not a projection, before AC-5 is marked done.

### 5. (Medium) Undeclared supply-chain surface: no mechanism named for the winget-pkgs submission itself
"Release-workflow automation" is the entire specification for how a manifest PR gets opened against a third-party repo. It does not name the tool (e.g., a community GitHub Action like `vedantmgoyal2009/winget-releaser`, or `wingetcreate`/`komac` invoked directly), nor the credential that authorizes pushing/opening PRs against `microsoft/winget-pkgs` on the project's behalf — a new external-write credential this single-maintainer project doesn't currently hold for any other channel. This repo's existing CI is disciplined about pinning third-party actions by SHA (per #134's evidence for the SignPath action) and about GPLv3/EPL linking hazards (per ARCHITECTURE.md's plugin-trust section); this issue's Boundary section is silent on both the tool choice and whatever token/identity will hold write access to a Microsoft-owned repo.
**Recommendation:** name the tool and pin it (SHA, not a floating tag/major-version), and state explicitly whose PAT or bot identity is used and its scope, consistent with the project's existing supply-chain posture elsewhere in the release pipeline.

### 6. (Low) AC-4's dependency on #511 is real scope creep undeclared in the issue body
AC-4 requires "the project description and short blurb shared with CAP-27 (#511)." The round-2 comment correctly identifies that #511 doesn't yet exist as shippable content, and that #579 makes an identical claim on the same not-yet-produced artifact — two consumers of an asset neither #511 nor anything else is on record as committing to produce for this purpose. The original issue body states `ordering_after: []` with no mention of this dependency at all; a reader of the body alone would reasonably believe AC-4 is self-contained.
**Recommendation:** keep the corrected `ordering_after_by_criterion: {AC-4: [511]}` from the comment, but fold it into the issue body rather than leaving the base `ordering_after: []` line uncorrected and technically still claiming "startable now" at full scope.

## What's solid
- Explicitly excluding Chocolatey with a one-line maintenance-arithmetic rationale (KC-34-1) is a clean, non-scope-creeping boundary call.
- AC-3 ("InstallerSha256 read from `SHA256SUMS-installers-*`, never hand-copied") is concrete, testable, and correctly targets exactly the kind of manual-drift failure mode the parent capstone (#518) was filed to prevent.
- The Boundary section correctly declines to duplicate #443/#338's installer-promotion work rather than re-scoping it here — good separation of concerns between "produce a signed/required msi" and "publish a manifest pointing at whatever msi exists."
