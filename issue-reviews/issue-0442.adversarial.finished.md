# Issue #442: TASK-0026: a simulation regression becomes a build failure — an exact event-count equality, two ceiling-only bands, and one gate over every golden
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

The mechanical parts this issue proposes are real and mostly verified against HEAD: the `afterEvent` seam exists unchanged (`src/jls/sim/Simulator.java:269-270`, overridden at `src/jls/sim/BatchSimulator.java:139-145`), `BatchSimulator.runSim()` runs synchronously on the calling thread (no dedicated thread, `src/jls/sim/BatchSimulator.java:112-131`) so the single-thread `getThreadAllocatedBytes` assumption holds, the `SpatialIndexTest.java:218-244` ratio-timing precedent is quoted accurately, and the "8 discoverable `*GoldenTest` classes vs. corpus's 6" claim (O3) reproduces exactly at HEAD. But the issue's entire quantitative basis lives in documents that do not exist in this checkout, it is hard-blocked by three large, unstarted tasks, and its acceptance criteria contain several pre-authorized escape hatches that let the gate go green while the thing it claims to protect quietly erodes.

## Findings, most severe first

**1. The evidentiary foundation this issue argues from is not present in the repository — a severe internal contradiction.**
The issue's numbers (245.5 / 121.5 / 243.1 / 388.4 events/cycle, the "ceiling with generous headroom" rationale, §7.3's warm-up discipline, O6's clocking-regime rule) are all sourced from `docs/machine-calibration.md` and `docs/plan/evidence/BRIEF.md`, cited at commit `2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7`. Verified against the actual checkout:
```
$ git cat-file -t 2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7
fatal: git cat-file: could not get object info
$ find docs/plan -maxdepth 2
find: 'docs/plan': No such file or directory
$ ls docs/machine-calibration.md
ls: cannot access 'docs/machine-calibration.md': No such file or directory
```
Neither `docs/plan/` nor `docs/machine-calibration.md` exists anywhere in this tree, and the evidence commit itself is not an ancestor of HEAD. The issue's own second comment (posted the same day, 2026-08-08) independently found the identical problem — "`git ls-tree -r origin/master` returns zero paths under `docs/plan/`" and "the commits `2d0ca9d` and `3a81a4a` are not present in the repository at all" — and re-homed some (not all) of the cited figures to `docs/capability-roadmap/keystone-c-performance.md`. That comment is a correction to the issue body, not a fix; the issue body as filed still cites a nonexistent evidence trail as though it were load-bearing. **Recommendation:** before this task is assigned, the issue body should be edited (or a supersede comment posted) pointing every cited number at its master-branch home, or explicitly marked "unverifiable at filing, see comment."

**2. The task is hard-blocked by three open, unstarted, large tasks — it cannot be started today, and the issue's own first Method step admits it.**
`blocked_by: [377, 379, 413]`. All three are open with `state: "open"` and none shows evidence of being in progress: #377 (build a two-cycle CPU fixture using a not-yet-existent `RegisterFile`-based datapath, extend a counting simulator, resolve a 3.2x events/cycle discrepancy), #379 (add a new `LogicElement` subclass to a `sealed` hierarchy, re-run a levelized harness at CPU scale), #413 (regenerate an untracked/missing anchor fixture, delete the entire `riscv/` directory, re-home six documents). The issue's own §8 Method starts with "Confirm #377, #379 and #413 have landed and read their measured values; a band invented rather than measured ratchets against nothing" — i.e., by the issue's own logic, no work here can begin, and the properties file's numeric contents (the deliverable) cannot be populated. **Recommendation:** do not schedule this task until its blockers land; if it must be filed now, mark it explicitly `status: blocked, not ready for pickup` rather than leaving it looking actionable.

**3. The ns/event ceiling has a pre-authorized escape hatch that can silently stop it from gating the one thing FEAT-030 (#362) cares about.**
Falsification criterion H2: "if the ns/event ceiling fails on an unrelated PR, H2 is wrong. Next move: demote the timing assertion to a **reported** number... leaving the equality and the allocation band as the gates." This is written into the issue as a pre-approved response to the *first* observed false failure ("Rides along, but the demotion trigger must be written into the test's comment" — Open Question 3). Combined with O4's own measured 4.2x same-JVM spread, a noisy CI runner make an early false failure close to guaranteed. The net effect: the strongest performance signal in the gate (the one FEAT-030's "engine constant-factor program" most needs) is designed to be demoted to advisory-only the first time it is inconvenient, and that demotion counts as *compliance* with this issue's own falsification criteria rather than as a weakening of it. **Recommendation:** either commit to a specific ceiling headroom multiple up front (e.g., "3x the measured max") so H2's trigger condition is meaningfully harder to hit, or acknowledge in the Definition of Done that the timing gate is expected to become advisory-only shortly after landing.

**4. The event-count equality has a matching escape hatch: a real regression can be laundered as "nondeterminism."**
H1's falsification path: "if any fixture's event count varies across reps, JDKs or platforms, H1 is wrong **for that fixture**. Next move: ... exclude that fixture from the equality with the variance recorded... **Do not weaken the equality into a band**." The instruction not to weaken into a band is good, but there is no adjudication step distinguishing "this fixture is nondeterministic" from "this PR introduced nondeterminism as a side effect of a real bug" — both produce the identical observable (a red equality test that varies across reps), and the prescribed remedy for both is the same: exclude the fixture. A contributor under deadline pressure has every incentive to reach for the exclusion path. **Recommendation:** require that any new exclusion be accompanied by a separate filed issue investigating the nondeterminism (the issue already says this for H1 in prose — "investigate the source of nondeterminism as a separate issue" — but this is not in the Completion Criteria checklist, so it is not actually enforced).

**5. "Ceiling only, generous headroom" is never given a number in this issue, so P4/P5 are satisfiable by an arbitrarily loose ceiling.**
Open Question 3's recommended default is "gate it initially with generous headroom above the measured maximum" — but "generous" is not quantified anywhere in this issue; the actual numeric ceiling is deferred entirely to #377/#379's measurements (not yet taken, per Finding 2). Nothing in the Definition of Done pins how tight the ceiling must be relative to the measured maximum, only that it must be a ceiling (checked by "reading the diff", P4) and that it exists. A ceiling set at, say, 100x the measured max would satisfy every literal completion criterion in this issue while gating nothing. **Recommendation:** state the headroom multiple as part of this issue (e.g., "ceiling = 2x observed max across reps") rather than leaving it to be invented at implementation time with no review anchor.

**6. The `ThreadMXBean` degrade-to-skip path can silently disable the allocation gate with no durable record.**
§7.11: "The JVM lacks `com.sun.management.ThreadMXBean`. The allocation band skips **with a stated reason recorded in the test output**." Test output (stdout/JUnit report) is ephemeral CI log content, not a reviewed, committed artifact — unlike the properties-file re-baseline mechanism the issue elsewhere insists on precisely because it wants re-baselines to be "a one-file diff with a stated reason" that a human reviews. A JVM/vendor change in the CI image (a plausible, unannounced event) could disable this whole band with nothing appearing in any PR diff, and nobody would notice until asking why a regression wasn't caught. **Recommendation:** make the skip fail loudly (e.g., require a tracked `.properties` flag or environment variable to be set explicitly to accept the skip) rather than degrade silently via println.

**7. Scope creep risk baked into a dependency, not this issue's own text — worth flagging anyway.**
This issue's stated scope ("adds four assertions... no production Java changed") is narrow and appropriately bounded, and §12/§13 explicitly disclaim engine changes, CI-lane policy, and #232's representation work. That discipline is good. But because #413 — one of its hard blockers — includes deleting the entire `riscv/` directory (26 files) and re-homing six documents' citations, and #379 requires modifying a `sealed` class's `permits` clause (real production code), the *practical* lead time and blast radius behind this issue before it can even start is large. This is not a defect in #442's own text, but a reviewer approving "just #442" without reading its blockers would badly underestimate what has to happen first.

**8. Line-number citations have already begun to drift, exactly as the issue itself warns.**
O2 cites `src/jls/sim/Simulator.java:265-270` for the `afterEvent` hook; at HEAD the method body is at lines 269-270 (javadoc starts a few lines earlier). Minor, and the issue's own Threats to Validity section (O11 equivalent) anticipates this ("Stale line numbers... Re-derive before trusting"), so this is a solid, self-aware caveat rather than an oversight — noted only so the executor re-derives rather than trusting the exact ranges.

## What is solid

- The `afterEvent` seam (O2) is real, `protected`, already overridden by `BatchSimulator`, and requires zero changes to `jls.sim` — verified directly.
- O3's "8 discoverable `*GoldenTest` classes vs. the corpus's stated 6" is exactly reproducible at HEAD; this is a genuine, well-evidenced defect in a document this issue references, correctly caught rather than propagated.
- The single-threaded synchronous execution model for `BatchSimulator.runSim()` is accurate, which makes the `getThreadAllocatedBytes`-on-the-sim-thread design sound in principle.
- The explicit anti-vacuity guard (P6, "at least two fixtures, minimum") and the "no floor on queue depth or dup-suppression counts" invariant (P9) are well-reasoned defenses against the gate defeating its own stated purpose (protecting FEAT-030's legitimate targets) — genuinely good design instincts, even where other parts of the acceptance criteria are gameable.
- The `SpatialIndexTest.java:218-244` precedent is quoted accurately and is a reasonable existing-code analog for the "assert the exact thing, report the noisy thing" pattern.

## Verdict rationale

**needs-rework.** The mechanical design (seam reuse, golden discovery mismatch, anti-vacuity guard) is sound and low-risk. But the issue cannot be picked up today (Finding 2), argues from a partly-nonexistent evidence trail that it does not itself correct (Finding 1), and its acceptance criteria contain multiple author-sanctioned paths by which the gate can go green without protecting what it claims to protect (Findings 3-6). These are fixable without discarding the design, but they need to be fixed in the issue text — pin the ceiling headroom, require a durable (not println) record for skipped bands, and require a companion issue on any equality exclusion — before this is safe to hand to an implementer as a self-contained unit of work.
