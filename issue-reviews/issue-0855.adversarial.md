# Issue #855: TASK-C580-1: an in-tree winget manifest validates, and its InstallerSha256 is read from the published checksums asset rather than typed by a human
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what's being asked

A committed generator produces a three-part winget manifest (version/installer/locale) for a release, reads `InstallerSha256` from that release's `SHA256SUMS-installers-*` asset, and `winget validate` passes in CI. Nothing about actual submission to `microsoft/winget-pkgs` is in scope here — that is left to a sibling task under #580. No `winget`-related file, script, or workflow step exists anywhere in the repo today (`grep -ril winget` returns only issue-review markdown), so this is greenfield work with no existing pattern to conflict with.

## Findings, most severe first

**1. [High] The parent feature's stated precondition is false, and #855 silently inherits it.** #580's machine block reads `ordering_after: []  # the signed MSI already ships; #443 TASK-0027 strengthens but does not gate`, and #580's outcome text promises winget delivers "the same MSI the Releases page publishes — **the signed one**, matching the attested checksum." But #134 (open, last updated the same day as this issue) documents the opposite as current fact: "Latest release tag predates the signing merge and no release followed it... no signed msi exists anywhere," and lists SignPath enrollment, secret-setting, and a proof run as still-outstanding maintainer-only steps. #134 even flags README's present-tense signing claim as a "live documentation defect" for the exact same reason. #855 copies #580's "consumes, does not own, the MSI" framing but never states the actual (unsigned) status the winget manifest will point at today, and AC-5 only carves out risk language for the msi leg being "advisory" (a CI-gating concept), not for the msi being unsigned (a trust concept). A generated winget package that installs an unsigned msi under Windows Package Manager is a materially different, worse outcome than the one #580 describes, and #855's acceptance criteria don't require noticing the gap.
   - Recommendation: add an AC (or an explicit stated-risk note, mirroring the msi-advisory carve-out) that the manifest's trust story is unsigned-until-#134-lands, and decide whether the generator should refuse to produce a manifest at all while unsigned, or must simply document the caveat.

**2. [High] AC-4 depends on content that does not exist yet, despite `ordering_after: []`.** AC-4 requires listing metadata (description, blurb, tags, licence, homepage) to "come from the shared CAP-27 (#511) text rather than being written fresh here." But #511's own machine block lists `planned_features: [PF-1 unfiled, PF-2 unfiled, PF-3 unfiled, PF-4 unfiled, PF-5 unfiled, PF-6 unfiled]` — none of CAP-27's features, including the README/shop-window PF-1 most likely to contain such copy, have been filed, let alone written. #855 declares `ordering_after: []`, i.e., nothing blocks it, yet one of its five acceptance criteria cannot be literally satisfied until unfiled work in a different capstone lands. This is exactly the kind of "half-edge" #338 warns against elsewhere in this same issue family.
   - Recommendation: either add #511 (or a specific PF) as a real `ordering_after` dependency, or narrow AC-4 to "reuse #511's text once it exists; write a placeholder now and file a follow-up to swap it in" — as written, an executor is stuck choosing between violating AC-4 and inventing the "shared" text this AC exists to prevent.

**3. [Medium] AC-2's checksum-asset dependency is coupled to a currently-flaky, currently-experimental leg, and the coupling isn't spelled out.** Per #443 (open, unlanded), the Windows msi leg runs under `continue-on-error: true`/`experimental: true`, and #338/#443 explicitly document the failure mode: "a failed leg used to leave the run green with that installer silently absent from the release." If a given release's Windows leg fails, `SHA256SUMS-installers-windows-*` for that release simply won't exist, and per AC-2 "a missing asset fails the generator loudly" — meaning winget manifest generation (and by extension #580's "version bump is a workflow output rather than a maintainer chore" promise) breaks on exactly the releases where the experimental leg misbehaves. AC-5 acknowledges "if the msi leg is still advisory... that is a stated risk on #580" but that language is about CI-gating status, not about this specific downstream failure mode on #855's own automation.
   - Recommendation: name this coupling explicitly as a stated risk on #855 (not just #580), and consider whether the generator should degrade gracefully (e.g., skip-and-alert) rather than hard-fail the whole release pipeline on a missing Windows asset.

**4. [Medium] AC-3 is schema-only validation and is gameable relative to the real goal.** `winget validate` checks manifest schema conformance; it does not verify the installer URL 404s or resolves correctly, does not check `InstallerSwitches`/silent-install correctness for the per-user msi described in README ("per-user install, no admin rights needed"), and does not simulate `microsoft/winget-pkgs`' actual moderation/CI bot. A generator could produce a schema-valid manifest with a wrong-but-well-formed `InstallerSha256`, a stale `InstallerUrl`, or missing `Scope: user` and still satisfy AC-3 in full. Contrast with this repo's own testing culture (README/ARCHITECTURE cite `InstallerMatrixPolicyTest`, `FormatHeaderTest`, `SaveTagsTest`, golden tests everywhere) — #855 asks for no generator-level unit/golden test at all, only a CI-tool pass/fail.
   - Recommendation: add an AC for a generator unit test with a fixed fake release fixture (golden-manifest comparison), and consider an AC that resolves `InstallerUrl` (HEAD request) as part of CI, not just schema shape.

**5. [Medium] AC-1 omits the two winget/msi fields that are the actual pain points, ProductCode and UpgradeCode.** "Version, installer URL, and locale metadata filled from release data" reads as if everything winget needs comes from release metadata, but winget's upgrade detection for MSI packages keys on a stable `ProductCode`/`UpgradeCode`, which `jpackage` must be configured to keep stable across versions or every `winget upgrade` silently fails to detect the new version (or worse, produces a side-by-side install). Nothing in `scripts/build-installer.sh` (per #338/#443's own line-cited audits) is described as pinning these GUIDs. This is a routine, well-known winget/MSI failure mode that the issue doesn't mention at all.
   - Recommendation: add an explicit AC (or a stated risk) confirming `ProductCode`/`UpgradeCode` stability across releases before or alongside this task, since a generator that "just works" against `winget validate` can still ship a package that never upgrades cleanly.

**6. [Low] AC-2's "a mismatch... fails the generator loudly" is ambiguous and untested.** It's unclear what the checksum is being compared against for a "mismatch" (presumably: download the installer bytes and recompute sha256 against the value read from the SHA256SUMS asset) — the AC never says so, and unlike sibling tasks in this family (#443's Method section requires new tests to "fail before the change, pass after"), #855 has no requirement that the missing-asset and mismatch failure paths be exercised by a test rather than merely coded and assumed to work.
   - Recommendation: state the comparison explicitly and require a test that injects a deliberately wrong checksum/missing asset and asserts the generator fails (mirroring #338 IC-5's "null test" discipline).

## What's solid

- The boundary carve-outs (msi building/signing stays with #338/#134; leg promotion stays with #443; Chocolatey explicitly out of scope per #580) are correctly respected and avoid scope creep — #855 doesn't try to re-litigate work owned elsewhere.
- AC-2's core principle — sourcing `InstallerSha256` programmatically instead of hand-transcribing it — closes a real, well-understood error class and is a genuinely good design constraint for a manifest generator.
- Scoping this as "smallest, most scriptable channel... proven on the cheapest one" before Homebrew/Flathub is a reasonable de-risking sequence, assuming the false-premise and dependency issues above are fixed first.
