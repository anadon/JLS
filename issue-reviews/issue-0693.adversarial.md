# Issue #693: TASK-C533-1: the interactive simulator advances by exactly one event, or one wavefront, on demand — with simulated time shown and the event order unchanged
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Findings

### 1. [Critical] AC2's fixture and its "existing goldens" do not exist in the repository

AC2 says: *"Stepping through the shipped hazard-demo circuit produces the same final
state and the same event sequence as a free-running simulation of the same circuit,
**pinned against the existing goldens**."* This is written as if the circuit and its
goldens already exist and this task only needs to add a regression assertion.

They do not. `grep -rli hazard /home/user/JLS` (excluding this session's own
issue-review output) returns nothing under `src/`, `test/`, `docs/`, or `riscv/`.
`test/fixtures/` holds exactly `riscv-sum1to10.jls`, `fork-4.6-shiftregister.jls`,
`headless-canary-gate.jls`, and the `legacy-4.1/` set — no hazard circuit. There is no
`examples/` directory of demo circuits either. `test/jls/BatchSimulationGoldenTest.java`
and `test/jls/SequentialGoldenTest.java` — the "existing goldens" AC2 presumably means —
carry no hazard-circuit fixture or golden output for one.

The phrase traces back to the parent capstone #504 (CAP-23), whose §1 walkthrough step 1
reads "Open the shipped hazard-demo circuit (a classic static-1 hazard)" — also present
tense, also describing something that is not in the "Background — scope already shipped"
section of that same issue. The gap was already flagged at the feature level in this
repo's own `issue-0533.adversarial.md` review. It is not resolved here: #693's own scope
(four ACs, all about the stepping control and time readout) includes no line item to
design, author, and check in a `.jls` static-hazard fixture plus an expected golden
event trace, yet AC2 makes that fixture's existence a precondition of the task's own
verification. `ordering_after: []` names no prerequisite that would create it either.

**Recommendation:** either (a) fold "author `test/fixtures/hazard-demo.jls` (or similar)
and its golden event/output trace" into this task's explicit scope and AC list, or (b)
file that fixture as its own small task, make #693 `ordering_after` it, and reword AC2 to
name the fixture task by number instead of asserting it already ships.

### 2. [High] "One wavefront" is not well-defined given zero-delay elements — and the ambiguity has a real failure mode

AC1: *"a step advancing... by one wavefront (every event at the current timestamp),
[advances] exactly that much and no more."* `docs/simulation-semantics.md:229-232` is
explicit that six element kinds — `Splitter`, `Binder`, `InputPin`, `OutputPin`,
`SubCircuit`, `Constant` — react with **zero delay** and "propagate within the same
timestamp, so an arbitrarily deep chain of wiring elements adds zero time." That means
processing one event at timestamp T can itself post further events at timestamp T,
which were not in the queue when "the current wavefront" was first observed.

The issue never says whether "one wavefront" means (a) drain exactly the events that
were queued at T at the moment stepping was requested, or (b) drain events at T until no
more remain, including ones generated by processing earlier same-T events. These are
different, both textually defensible under "every event at the current timestamp," and
they produce observably different stopping points on any circuit with a same-timestamp
chain (which the codebase already has six element types capable of building). Worse:
`docs/capability-roadmap/lf-03-causal-debug.md:411-412` states plainly that "JLS has no
loop detection at all today." Reading (b) — drain until the timestamp truly advances —
has no defined terminus on a same-timestamp combinational loop; a student's own circuit
could turn "step one wavefront" into a UI hang, which directly contradicts AC1's promise
of advancing "exactly that much and no more."

**Recommendation:** state the intended semantics explicitly (most likely: snapshot the
queue's at-T entries before processing and drain exactly that set, so newly-posted
same-T events become the *next* wavefront) and add an acceptance criterion — not just an
implementation note — covering the zero-delay-chain case, ideally with a same-timestamp
combinational-loop fixture as a bounded-hang regression test.

### 3. [Medium-High] AC3's "event sequence" is not a thing the codebase currently exposes for comparison

AC3: *"a test asserts the stepped sequence equals the free-run sequence element for
element."* `SimEvent` (`src/jls/sim/SimEvent.java:96-102`) keeps `time`, `seq`,
`callBack`, and `todo` all `private`, with no accessor surface built for this kind of
comparison. `SimEvent.PinChanged` is a zero-field record — per the causal-debug
roadmap doc, 82.3% of all events fired carry no payload information beyond "something
upstream moved." The existing recording surfaces (`TraceSample`, `Trace.Change`) are
per-signal value histories that **dedupe on value equality**
(`BatchSimulator.java:173-178`, `Trace.java:186-191`), which means two different event
sequences that happen to produce the same final value history would look identical
through those surfaces even though the per-event ordering differed.

As written, AC3 can be satisfied by a test that compares only recorded trace/watched
output between stepped and free-run modes — which is what the existing test
infrastructure makes cheap — while the literal claim ("event sequence... element for
element") goes unverified. That is a real gap between what the acceptance criterion says
and what an implementer can cheaply make pass.

**Recommendation:** name the concrete comparison surface AC3 requires (e.g., a
test-only hook or package-private accessor exposing `(time, callback identity, payload
kind)` per fired event) before work starts, so "equals element for element" has an
actual meaning to implement against.

### 4. [Medium] No acknowledgment of the pre-existing Step/Animate control this task must interact with

`InteractiveSimulator.java` already ships a `Step` button and `Animate` button
(`src/jls/edit/InteractiveSimulator.java:324-430`) driven by a user-entered `stepAmount`
(a **time duration**, not an event count) and a `stepEnd`/`beforeEvent` mechanism
(`:37`, `:774-805`) that pauses the run once the next queued event's time exceeds the
target. This is a real, already-shipped "stepping mode," just at time-duration
granularity rather than event/wavefront granularity. The issue's "two controls exist —
step-one-event and step-one-wavefront" says nothing about whether these are new buttons
alongside the existing `Step`/`stepField`/`Animate` trio, a replacement for them, or a
different mode entirely — and doesn't touch the fact that the clock-display update path
(`SwingUtilities.invokeLater` writing `showClock` in `beforeEvent`, `:786-801`) is
already wired to the existing mechanism and would need to be shared or duplicated.

**Recommendation:** state explicitly whether the new controls extend, replace, or sit
beside the existing Step/Animate UI, and whether `stepEnd`'s existing pause logic is
reused for the new granularities or is separate machinery.

### 5. [Medium] Undeclared interface gap with dependent sibling task #695

TASK-C533-2 (#695, `ordering_after: [TASK-C533-1]`) animates "the affected wire(s)... the
producing element and each consuming element" per step — data #695 can only get from
whatever #693 exposes about *what just fired*. But #693's own AC list promises only "the
current simulated time is displayed and updated" (AC1); nothing in its four ACs commits
to surfacing which element(s)/wire(s) were touched by a given step. If #693 is
implemented to satisfy only its own stated ACs, #695 has no data contract to build on
and will need to reopen or amend #693's implementation. This should be named as a
cross-task interface requirement now, not discovered during #695.

**Recommendation:** add an AC (or an explicit non-goal note) to #693 committing to
exposing the per-step affected element/wire set, even if #693 itself does nothing
visual with it.

### 6. [Low] AC4 is close to tautological given the codebase's existing headless boundary

`Simulator`/`BatchSimulator` are already enforced AWT/Swing-free
(`HeadlessCoreRatchetTest`, `ARCHITECTURE.md`'s "Headless by construction (issue #77)"
note), and stepping is explicitly GUI-only per this issue's own framing. Any
implementation that respects that existing boundary satisfies "batch and headless
behaviour... byte-identical" close to automatically — the AC doesn't discriminate a
correct implementation from an incorrect one so much as re-assert an invariant the
codebase already ratchets elsewhere. Keeping it as a regression test is still worthwhile
(cheap insurance), but it should not be counted as meaningful independent verification of
this task's actual new behavior.

  `band_mw: 2-3` — the cost estimates are internally consistent across the task split,
  no padding or double-counting found there.
