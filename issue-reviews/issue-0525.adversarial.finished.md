# Issue #525: FEAT-C21-2: an instructor copies the in-tree Gradescope template and a JLS lab grades in the platform's native UI — per-test scores, visible/hidden split, bounded output
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what's being proposed

An in-tree Gradescope autograder template (Dockerfile pinning a headless-JRE JLS build, `setup.sh`/`run_autograder`, and an adapter converting xUnit verdicts to Gradescope's `results.json`) that turns a CAP-06 lab-as-data submission into per-test scores in Gradescope's UI. Serves CAP-21 (#502) PF-2, ordered after FEAT-C21-1 (#524, the frozen CLI contract), transitively behind #369/#466.

## Findings, most severe first

### 1. (High) AC-1's grading target — "the CAP-21 fixture class (300 submissions)" — is owned by a sibling issue this one doesn't declare a dependency on

AC-1 requires the built autograder to grade "every submission of the CAP-21 fixture class (300 submissions)... (CAP-21 §1 step 1)." But the 300-submission corpus and its golden score vectors are the explicit deliverable of #531 (FEAT-C21-6, CAP-21 PF-6): *"a 300-submission fixture corpus, and golden per-student score vectors."* #525's `ordering_after` is `["FEAT-C21-1"]` only — it does not list #531. #531's own `ordering_after` is likewise `["FEAT-C21-1"]` only and does not list #525. Each issue instead treats the other as its *consumer/comparator*, not its prerequisite: #531 says adapters "feed" it, #525 says it grades "the CAP-21 fixture class" as if that fixture already exists to be graded. Concretely, whoever builds #525 first has no corpus to run AC-1 against (it has to invent a placeholder), and whoever builds #531 first has no adapters to validate against — a documented pattern already flagged as an unaddressed gap on the sibling adapter issue #526 (finding 1 there), and it applies to #525 identically, with the identical fix needed: either #525 drops the 300-submission grading claim to "supplies xUnit input in the documented shape" and defers full-corpus grading to #531/CAP-21 AC-3, or the `ordering_after` edges are added on both issues.
**Recommendation:** add the `#531 blocks #525` edge (or the reverse, explicitly) before implementation starts, and clarify which issue owns the corpus's existence versus its use.

### 2. (High) "Valid results.json" and "identical output across two runs" are gameable in a codebase that has already demonstrated this exact failure mode

`docs/capability-roadmap/lf-04-formal-and-grading.md` documents, as the measure of the current gap, that the repo's own shipped example (`examples/autograde/autograde.py`) grades by hard-coding `EXPECTED_STDOUT_LINES` — literal expected bytes, not a real comparison — and calls this out explicitly: *"A submission that is wrong on 254 of the 256 possible inputs and right on that one passes."* AC-1 ("emitting valid results.json with per-test scores...") and AC-3/CAP-21-AC-3 ("identical output across two runs") are both satisfiable by an adapter that, given #531's golden score vectors are shipped in-tree as fixtures, special-cases the fixture corpus and emits the known-correct scores directly rather than deriving them from a live xUnit run per submission — trivially deterministic, trivially "valid," and disconnected from whether the adapter actually parses xUnit or invokes JLS at all. Given the tree's own documented precedent for exactly this shortcut, "valid schema + reproducible bytes" is not sufficient evidence the adapter grades correctly; nothing in the acceptance criteria requires the golden vectors to be *held out* from the adapter's build/test inputs, or requires a mutation/tamper test (e.g., a submission perturbed after fixture-freeze) that a hard-coded-answer adapter would fail.
**Recommendation:** add an acceptance criterion that the adapter is exercised against at least one submission not present in the fixture corpus at authoring time (or a corpus subset held out until CI run time), so schema validity and byte-determinism can't be satisfied by table-lookup against known answers.

### 3. (Medium-High) "A results.json schema mismatch or spec drift surfaces as a named error... not in a live course" has no mechanism to detect drift it doesn't already know about

The boundary notes correctly rule out scraping ("documented spec only — no scraping, no undocumented endpoints"), so the CI lane can only validate against a schema/spec checked into this repo. But nothing in the issue says who re-fetches Gradescope's published spec, how often, or what triggers a re-check — the CI lane will pass indefinitely on a pinned, stale copy of the schema even after Gradescope changes it, and will only "surface a named error" for drift someone has already noticed and encoded a fixture for. The promise "never a silent misgrade... if the spec moves" is not actually backed by a live-detection mechanism; it degrades to "we will not silently misgrade for spec changes we happen to catch by other means" — which is a materially weaker claim than the one being made in the outcome text.
**Recommendation:** either name the update/monitoring cadence for the pinned spec copy (a recurring maintenance task, a link-check against Gradescope's docs page, etc.) or soften the claim to state plainly that drift detection is bounded by how current the pinned schema is.

### 4. (Medium) The declared dependency chain understates real cost by the same margin flagged on sibling issue #526

#525 correctly notes it is "transitively behind #369/#466" via #524, but #524 itself (fetched directly) records `ordering_after: [369, 466]` and both of those are non-trivial: #369 (FEAT-053) carries its own 9–15 mw band with unfiled sub-tasks and open prerequisites per the #526 review, and #466 (TASK-0111) — the issue that actually builds the xUnit-report/verdict machinery #525's adapter consumes — is itself in a **self-contradictory state** as of this pass: its body and its own "REVISION" comment give conflicting Definitions of Done (a `TestPanel` and worked-lab fixture the revision comment says do not belong in that issue), and a load-bearing dependency claim in its body was already stale at filing. #525's declared `band_mw: 2-3` is real only for the adapter shim itself; the actual unblocked-to-ship cost includes landing #466 in a form stable enough to consume, which is not currently true. This mirrors #526 finding 4 almost exactly and applies with the same force here, since #525 and #526 sit at the identical point in the dependency graph.
**Recommendation:** not a defect unique to #525's own scope, but the issue (or #524, which both siblings point to) should carry a pointer that #466 needs its own consolidation pass before FEAT-C21-1 can be considered a stable target to build against.

### 5. (Medium) "Wall-time budget" and "bounded output" are both undefined numbers, and Gradescope enforces its own hard limits independent of whatever JLS declares

AC-2/CAP-21-AC-3 requires grading "within a declared wall-time budget," and the outcome text requires "bounded output" — but no figure appears anywhere in the issue for either. Gradescope autograders have platform-side execution-time and log-size ceilings that are not under this project's control; a "declared" budget that is simply set generously enough to always pass (e.g., "under 24 hours") technically satisfies the letter of AC-2 while leaving the adapter unusable on the actual platform it targets, and the issue gives no cross-check against Gradescope's real limits. Likewise "bounded output" needs an actual byte or line count to be a testable criterion rather than a description.
**Recommendation:** state the specific budget numbers (and cite Gradescope's documented per-assignment execution-time and output-size limits so the declared budget is checked against something external, not self-selected).

### 6. (Low-Medium) "The adapter never opens an interactive session" restates an already-true structural property rather than adding a new engineering constraint

`ARCHITECTURE.md` states plainly that "Batch mode never leaves the main thread and never touches Swing (headless-safe...)" — this has been true of `BatchSimulator` since before this issue was filed, and `Simulator`/`BatchSimulator` are enforced headless-only by `HeadlessCoreRatchetTest` per `ARCHITECTURE.md`'s module-layout section. An adapter built on top of the documented batch CLI cannot open an interactive session even if it tried, absent new code specifically added to do so. Citing #498 §7.2 here is not wrong, but presenting it as an acceptance criterion this feature must achieve slightly overstates what work item it actually is (a non-regression statement, not new scope).

## What's solid

- Scoping the adapter to Gradescope's documented `setup.sh`/`run_autograder`/`results.json` contract, with an explicit "no scraping, no undocumented endpoints" boundary, is the correct posture for a proprietary platform and matches the project's own stated delegation stance (`ARCHITECTURE.md`'s subprocess-boundary discussion).
- "The adapter lives in a dedicated CI lane, not the core matrix" correctly reflects CAP-21 risk 1 and keeps a flaky/slow platform-integration test out of the main build gate — sound engineering hygiene.
- "No LTI tool... files-only kit" is an accurate, narrow exclusion that matches #498 §8 exclusion 7 as quoted, and avoids scope creep into operating a service.
- Grounding the Docker image in a "headless-JRE JLS build" is realistic: `ghcr.io/anadon/jls` is a real, already-shipped, multi-arch, signed container image built for exactly this batch/CI use case (per `README.md`), so this is not a green-field integration on that front.

## Verdict rationale

The two high-severity findings are structural, not cosmetic: the issue's central acceptance criterion (grade the 300-submission fixture) depends on a sibling issue with no declared ordering edge in either direction, and the codebase has a documented, on-the-record precedent (`autograde.py`'s hard-coded expected lines) for exactly the kind of gaming that "valid results.json, byte-identical across runs" fails to rule out. Combined with an unverifiable "spec drift" detection promise and undefined wall-time/output bounds, a team picking this up today could ship something that passes every stated acceptance criterion while never having graded a real, previously-unseen submission correctly. Nothing here suggests killing the feature — the platform scoping, exclusions, and container grounding are sound — but the acceptance criteria need tightening before implementation starts.
