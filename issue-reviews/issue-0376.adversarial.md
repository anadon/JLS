## Findings

**1. (High) The issue's central evidence citation is already a dead link on the default branch.** The body states: *"the allocation finding is `docs/plan/evidence/BRIEF.md` §13 CORRECTIONS, which landed in `3a81a4a...`"* and quotes it as load-bearing motivation. `docs/plan/evidence/BRIEF.md` was added at `3a81a4a` (2026-08-02) and then **deleted** by commit `742da74` ("docs: remove the planning corpus now that it is encoded in issues"), which is on `master`'s current tip lineage (`c5cee1b`, 2026-08-05) — confirmed: `git show c5cee1b:docs/plan/evidence/BRIEF.md` returns "does not exist". Issue #376 itself lists as a Completion Criterion: *"Every cited evidence document and permalink resolves on the default branch at close."* That criterion is unsatisfiable as the citation is written today — it names a repo-relative path, not a commit-pinned permalink, so there is nothing to resolve. Recommendation: repoint the citation to a permalink at `3a81a4a` (the way #353 and #468 already do it — e.g. `https://github.com/anadon/JLS/blob/3a81a4a.../docs/plan/evidence/BRIEF.md`), or drop the citation since none of O1-O9's code claims actually depend on it (they're independently pinned at `2d0ca9d` and re-verified above).

**2. (Medium) H3's acceptance path is gameable — no fixture exercises the "last-wins" contract it exists to protect.** §7.4/§10 promise the new `Map`-based signal resolution "reproduces last-wins exactly" and H3 is "refuted if any existing test's behaviour changes on duplicate pin names." But grepping `test/` finds **no existing fixture with two `InputPin`s sharing a name** feeding `SigSim.initSim` — I searched for `duplicate`, `last-wins`, and pin-name-collision patterns and found nothing. The Method checklist (§8) only adds a scaling fixture (`stimulusParseIsLinearInInputSize`, `signalResolutionDoesNotScaleWithCircuitSize`) and the P4 put-attachment fixture — neither exercises H3's correctness claim at all. A naive `Map` rewrite that silently becomes first-wins (the far more natural implementation of a name→pin map) would pass P5/P6 unregenerated, pass the scaling tests, and still be wrong, because nothing in the required test set can observe the difference. Recommendation: add a duplicate-name fixture and a positive assertion (`Map` resolves to the *last* declared pin) as its own Method step, not just a prose promise.

**3. (Medium) Parent-feature bookkeeping is out of sync with this issue's own existence.** #376 declares `part_of_feature: 353`. #353 (FEAT-005)'s own decomposition table still lists *"planned — TASK-0009 (1.5 wk) | ... | Not filed"* as of its `updated_at: 2026-08-04T07:09:38Z` — a day **after** #376 was created (`2026-08-03T14:13:18Z`). Either #353 was updated for an unrelated reason without reconciling its child roster (a process gap this corpus's own machinery is supposed to prevent — see #353's "Re-planning Protocol" and its own Completion Criteria item "Machine block, roster table, and mermaid graph agree with reality at close"), or the ownership `#376` claims was never accepted upstream. A reviewer picking this up should not trust `part_of_feature: 353` at face value without checking #353 first.

**4. (Low) Baseline reuse across two different CLI shapes.** O2 nets out a 233 ms baseline measured (implicitly) from a bare `-b tiny.jls -t <empty> -d 1` invocation; O3 nets out the *same* 233 ms figure against a `-b $f.jls -savetext ${f}out.jls` invocation — a different code path (no `-t` parse, but adds a full file write). The two experiments' internal doubling ratios are self-consistent and don't depend on the shared baseline, but the "Materials & Apparatus" section never asks for a `-savetext`-specific baseline measurement, so the O3 absolute "net of baseline" numbers rest on an assumption not stated in §11 Threats to Validity (which flags "JVM startup is 233 ms of every figure above" as if it's the same 233 ms everywhere).

**5. (Low) "Halfway" is imprecise.** Open Question 1 recommends `t(4N) < 8*t(N)` as "halfway between linear (4x) and quadratic (16x)". 8 is the *geometric* mean of 4 and 16, not the midpoint (which is 10) — the number chosen is reasonable, but the justification as stated is inexact and could confuse a reviewer checking the arithmetic.

**6. (Cost/process, informational) Ceremony-to-diff ratio is large.** The actual fix is a `StringBuilder` swap, a pre-built `HashMap`, an order-preserving worklist, and moving one `if` block out of a `for` loop — plausibly under 100 changed lines across three files. The issue mandates a new `test/resources/perf/` fixture generator, two new scaling-test classes, ratio-ordering coordination with two sibling tasks' bookkeeping (#468, #405), and reconciliation with a parent feature (#353) whose own roster is stale (Finding 3). None of this is wrong, but a reviewer should budget for the process overhead, not just the code change, when estimating this "task."
