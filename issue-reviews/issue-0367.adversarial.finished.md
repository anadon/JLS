# Issue #367: FEAT-047: a circuit can declare what one tick means in physical time, once, and everything that reports time reports it in that unit — declaring nothing keeps today's behaviour exactly
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: sound-with-concerns

## Summary of what's being attacked

FEAT-047 declares an optional per-circuit `TimeBase` (magnitude 1/10/100 × decimal exponent), wired through the file format (new `TIMEBASE` record, `FORMAT_VERSION` 2→3), the VCD `$timescale` line, and eventually the analog solver step and audio sample rate. The core evidence (dimensionless-time clause in `docs/simulation-semantics.md:26-30`, the hardcoded `$timescale 1 ns $end` at `src/jls/sim/BatchSimulator.java:423`, `Circuit.FORMAT_VERSION = 2` at `src/jls/Circuit.java:102`, the token loop at `src/jls/Circuit.java:886-901` that fails `MALFORMED` on any unrecognized token, `formatVersionNeeded()` at `src/jls/Circuit.java:1580-1587`, and the `subElement != null` suppression at `:1479-1483`) all check out against the current tree. This is one of the better-grounded issues in the tracker. The findings below are about scope, process, and testability, not about the code evidence being wrong.

## Findings, most severe first

### 1. The issue is not actually the unit of work — #882 is, and the two documents now disagree on what "this issue" means
The body's own Definition of Done still reads `requires_tasks` / `planned_tasks: TASK-0101` — a task (#431) that was absorbed and closed as a duplicate back into this issue on 2026-08-04, then un-stranded by filing #882 on 2026-08-08 (comment `5227537026`). The issue body itself was **never edited** to reflect this: `planned_tasks` in the machine block still names the closed TASK-0101, not #882. A reviewer or executor who reads only the issue body (as this assignment instructed) will build a plan around a dead task id and only discover the real child by reading to the bottom of a six-comment thread. **Recommendation:** the issue body's machine block must be edited to reference #882, not left for tribal knowledge in a comment. This is a process defect this exact review methodology (issue-body-first) would have missed if the comments hadn't been pulled.

### 2. `serves_capstones` in the machine block is stale and the issue's own comment thread admits it without fixing it
Comment `5227091040` states `#303 (CAP-11) is closed as a duplicate of #308 (CAP-10)` as of 2026-08-03, one day before the issue's own evidence commit `2d0ca9d`. Yet the machine block still lists `serves_capstones: [308, 303, 305, 309, 313]` and the flowchart still draws `F47 --> C303`. The same comment says this is "not acted on in this pass" and leaves it as an unactioned `REPLAN:` obligation on five separate sibling issues. An automated or human executor trusting the machine block (which rule A of the DoD says must "agree with reality at close") is currently working from a graph with a dead node in it, and nothing in this issue enforces the correction before this issue itself closes. **Recommendation:** either fix the block now or make "prune closed serves_capstones entries" an explicit, checked completion-criterion line rather than a comment aside.

### 3. The "one conversion, tree-wide" criterion (§5 criterion 5) is gameable as written
"Checkable by grep over the tick-to-seconds arithmetic" is not a specification of what the grep matches, and multiplication by a magnitude/exponent pair can be spelled many ways (`* 1e-9`, `/ 1_000_000_000L`, a locally-inlined `ticks * mult * Math.pow(10, exp)`, a second `record` with the identical shape but a different name). A grep for a literal string is trivially satisfied by renaming, and a grep with no defined pattern cannot be reproduced by a second reviewer. Contrast this with the issue's own criterion 3 (exactness assertion) and criterion 2 (recompute-vs-accumulate), both of which state the exact test name and exact assertion. Criterion 5 has neither. **Recommendation:** pin the grep expression (or better, a SpotBugs/Error Prone custom check, or a `TimeBase`-only visibility restriction) in the acceptance criteria the way #882's AC-2 pins the no-accumulation test.

### 4. Two features are independently and mutably targeting the same file-format version counter, and the issue's own mitigation is an honor system
§6 and the carried-forward comment (`5181525358`) are explicit that if #367/#882 lands first, `FORMAT_VERSION` becomes 3, and FEAT-013 (#319) — which is a **from-scratch rearchitecture of the versioning mechanism itself**, `blocked_by: [334]`, currently unblocked-but-not-started — "must adopt the attribute rather than leave two version mechanisms in the tree forever." There is no code-level enforcement of this; it is a documentation obligation on a *different, independently-scheduled* open issue. If #319 lands first instead, the issue says its own version-policy step "shrinks to nothing" — but doesn't specify what that reduced step actually emits, only that it "rides its per-section must-understand flag instead." Neither direction has a test or a CI check that would catch the tree ending up with two version mechanisms; it is caught only if a human remembers the `REPLAN:` obligation months later. **Recommendation:** at minimum, add a tracking test/comment convention (e.g., a single well-known constant or a code comment at both `Circuit.FORMAT_VERSION` and wherever #319's mechanism eventually lands) that fails loudly if both mechanisms exist simultaneously, rather than relying on cross-issue memory.

### 5. The picosecond-default recommendation is asserted with confident arithmetic but never validated against the actual consumers it's for
Open Question 1 recommends picosecond "for mixed-signal work," with the range math (~107 days of 64-bit tick space, ~2.5h before losing double-exactness) reproduced three times across the issue and its comments. But the two cited beneficiaries — FEAT-046 analog solver (#351) and FEAT-045 host audio (#346) — are both explicitly *not yet built* ("consumers that do not exist yet"). No evidence is offered that a 2.5-hour double-exactness ceiling is actually adequate for whatever the eventual analog solver's longest run needs to be, or that picosecond (vs. femtosecond, which the grammar also allows) is the right default for RF/transmission-line work (CAP-18, #313, propagation delay over "a physical length"). The number is picked because it is defensible in the abstract, not because it was checked against a concrete downstream requirement. **Recommendation:** before locking the default, get at least one worked example from #351 or #313 (e.g., "a 345.6ps `Td` transmission line simulated for N ticks needs precision X") rather than a generic mixed-signal justification.

### 6. Quantization and exactness are both framed as "documented, not fixed" — that's a legitimate design choice but it is easy to under-scope in review
Criterion 7 and AC in #882 require the 44.1kHz quantization figure (11.6ppm @ 1ns, 1.7ppb @ 1ps) to be "the documented figure" checked by a unit test (`theQuantizationOfFortyFourPointOneKilohertzIsTheDocumentedFigure`). That's good — it's a testable claim. But nothing in the issue requires that figure be re-derived if the *default* precision (Open Question 1) changes later; the test as named is hardcoded to one specific base. If a future change picks femtosecond as default (or a different base per-consumer), this test's asserted ppb figure silently becomes irrelevant documentation rather than a living contract. Minor, but worth flagging since the issue is unusually rigorous everywhere else about exactly this kind of drift.

### 7. Cost estimate (§ "Cost reconciliation") explicitly does not sum to the stated band, and the gap is hand-waved to a residual with no size estimate
The issue states outright: "The rows do not sum to the band; the band exceeds the row sum by 1.33x at the low end and 2x at the high end," attributing the gap to the unfiled residual (carrying the unit through consumers that don't exist yet). This is honest, but it means the 2-3 maintainer-week band is **not derived from any actual estimate of the residual's size** — it's asserted, then the gap between the one estimated task (1.5wk) and the asserted band is explained after the fact rather than the band being built up from parts. A planner using this issue to schedule work has no way to sanity-check the 2-3mw figure independently. **Recommendation:** either size the residual (even roughly, e.g., "waveform axis label change: X, delay dialog: Y") or state the band is a placeholder pending #351/#346 existing.

## What's solid (no rework needed)

- **The absent-by-default contract (invariant 1-2, AC-4) is well-specified and testable**: byte-identical goldens over the whole fixture corpus, unchanged `FORMAT`, is a strong, falsifiable claim with a named failure mode ("fix the condition, never the golden").
- **The no-accumulation contract (AC-2) is unusually rigorous**: it requires the test to demonstrate the failure mode it guards against (`sum != recompute` at some scale) rather than merely asserting the recompute path, which prevents a vacuously-passing test.
- **The version-refusal design is correctly diagnosed against the real code**: the observation that a version-2 reader hits `MALFORMED` (not `NEWER_FORMAT`) on an unrecognized `TIMEBASE` token, verified directly against `Circuit.java:886-901`, is accurate and the fix (bump version, category `NEWER_FORMAT`) is the right one.
- **The scope boundary against structured element delays and against FEAT-013/046/045 is clearly and repeatedly drawn**, with an explicit rejected-alternatives list (§2) — this is not a feature quietly annexing adjacent work.
- **The residual acknowledgment (no task id, "cannot be a task now without pre-committing to their shapes") is honest about what isn't actually planned**, rather than papering over it with a fake task row.

## Verdict rationale

The technical core (the type, its grammar, the version bump, the absent-by-default proof) is well-evidenced against the actual repository and has already been executed into a concrete, testable child (#882). The concerns above are about issue-tracker hygiene (stale machine-block fields, dead task references left in the body) and about acceptance criteria that are rigorous in most places but gameable or under-specified in a couple of spots (§5 criterion 5's unpinned grep; the un-validated precision default). None of these block the work from proceeding — #882 already carries a tighter, largely self-consistent contract — but the issue body itself, if used as the source of truth by an executor who doesn't read all six comments, would misdirect effort toward a closed task id and an overpopulated capstone list. Hence sound-with-concerns rather than a plain sound.
