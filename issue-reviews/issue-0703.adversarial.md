# Issue #703: TASK-C526-2: a failing test annotates the exact circuit file it failed on, so a student sees the problem where the problem is
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

TASK-C526-2 asks for GitHub check annotations on the specific `.jls` file a failing hidden test belongs to, sourced from "the batch artifact's own file references through the frozen contract." Traced against the actual dependency chain (#526 → #524 "frozen CLI contract" → #369/#466 "the verdict machinery"), none of which has landed, the issue both inherits unresolved defects from its own prerequisites and adds two of its own: it asks for hidden-test counterexamples to be written into a check annotation the graded student can read on their own commit, and it writes a testable acceptance criterion (multi-file attribution) that no upstream design document supports.

## Findings, most severe first

### 1. (Critical) AC-1 puts the hidden-vector counterexample directly in front of the student being graded — an unaddressed leak, not a new one

AC-1: *"A failing test on a fixture submission produces a check annotation attached to the circuit file that failed, with the test name **and the counterexample** in the annotation body."* The counterexample is exactly the expected/observed value pair `GradeReport` (#466 §7.6) writes into a failing `testcase`: *"failure elements carrying the expected and observed values and the time."* A GitHub check annotation on a pushed commit is rendered directly in that commit's own Checks tab and PR diff view — visible to the person who pushed it, i.e. the student being graded on "the lab's hidden vectors" (#526's own phrase). Push, read the expected value off the annotation, hardcode it, push again, repeat per vector: the "hidden" suite is fully exposed one failing push at a time. This is not a new observation in this review chain — the parent issue #526's own adversarial review (`issue-0526.adversarial.md` finding 2) already flagged this exact leakage path for the Classroom Action generally and recommended redacting expected/observed values from any student-visible surface. #703 is the issue that actually builds the annotation body, and it restates the leak as a requirement ("the counterexample in the annotation body") without qualification, redaction, or even a cross-reference to #526's finding. **Recommendation:** AC-1 must specify what "counterexample" means on the annotation surface — pass/fail plus which watched element and vector index, never the expected value, unless the vector is marked visible (mirroring #525 Gradescope's visible/hidden split).

### 2. (High) AC-3's premise — one submission spanning multiple circuit files with independently attributable failures — has no support anywhere in the traced dependency chain

AC-3: *"A submission with failures in two different circuit files produces two annotations, each on its own file."* Every document upstream of this issue describes grading as operating on exactly one circuit file per run:
- `docs/batch-interface.md:19-22`: `jls -b [...] circuit.jls` — "takes one circuit file operand" (singular, ARCHITECTURE.md's own words: `jls -b` "takes one circuit file operand").
- #466 (TASK-0111, the task that designs the verdict artifact this issue consumes) §7.3's data table: *"a directory of submissions | `grade.py` | one `.jls` per student"* — one file per student, not several.
- #369 (FEAT-053, the owning feature) never once describes a multi-file submission; its whole verdict model (§3, the $\mathrm{verdict}(v_i)$ definition) is scoped to a single circuit $C$.
- CAP-21 (#502) PF-3's own line item says only *"check annotations on circuit files"* — no plural scenario, no multi-file submission model.
Nothing in this chain defines what "a submission" containing multiple `.jls` files even means (one lab with several sub-problems? one repo with several labs graded together?), nor how a single verdict artifact would carry failures scoped to two different source files when the batch engine's own invocation contract is one file in, one report out. If the Action is expected to loop `jls -b` once per file in a multi-circuit assignment, then file attribution is already known to the Action from its own invocation loop and AC-1/AC-2's "derive it from the artifact" instruction becomes moot for this scenario (see finding 3) — and if it isn't a loop, no mechanism exists to produce it. Either way this AC cannot currently be implemented against real upstream design. **Recommendation:** either cite the (currently nonexistent) upstream issue that defines multi-file submissions, or rewrite AC-3 against the model that actually exists: one `.jls` per grading invocation, N invocations per submission, attribution owned by the invocation loop.

### 3. (High) AC-2's core mechanism — "attribution derived from the batch artifact's own file references" — is not just undesigned but plausibly the wrong mechanism, given how the batch interface actually works

AC-2: *"Attribution is derived from the batch artifact's own file references through the frozen contract; the Action does not guess a file by name matching."* This presupposes the xUnit artifact carries a file-path field. It does not, in the only design that exists for it: #466 §7.6 ("Data provided (structure)") specifies the report as "one `testcase` per expectation" carrying expected/observed/time, explicitly *excluding* timestamp/hostname/duration for determinism — and names no file-path or file-reference field at all. Since `jls -b` grades exactly one circuit-file operand per invocation (finding 2), the file a report describes is not observed *from* the report — it is the CLI argument the Action itself already passed in. Deriving attribution "from the artifact's own file references" is asking for information that would have to be manufactured redundantly (the invoking process already has it) and that no upstream issue proposes adding to the frozen xUnit schema. The AC sets up a false choice — "artifact's own reference" vs. "guessing by name matching" — when the actual correct answer (the file is a constructor parameter of the invocation, known with certainty, not guessed and not derived post hoc) is neither option offered. Left as worded, an implementer is nudged toward proposing a new field on #524's still-open "frozen contract," expanding a surface #524 itself hasn't finished defining (see finding 4). **Recommendation:** rewrite AC-2 to state the actual mechanism — the Action's own invocation loop is the source of truth for file identity — or, if a genuine multi-file-per-invocation batch mode is intended (finding 2), name the issue that adds it and the field it would add to the report schema.

### 4. (Medium) The "frozen contract's artifact-path clause" this issue calls "a real test of" is itself unsettled, and a parallel review already found it unstable

The outcome text frames this task as testing "the frozen contract's artifact-path clause" — i.e. #524 (FEAT-C21-1). #524 is open, and its own adversarial review (`issue-0524.adversarial.md`, verdict `needs-rework`) found: a stale `ordering_after` the maintainer's own comment already retracted but never fixed in the body; AC-1 worded as a present-tense claim that is false at HEAD; and status 3 (the mechanism #703 would depend on to know a run "failed" rather than merely "ran") frozen before its own upstream design (#466) is complete. Separately, `issue-0524.visionary.md` characterizes #524's "artifact paths" clause as "close to vacuous." #703 treats this clause as settled enough to build a feature against ("a real test of the frozen contract's artifact-path clause, not a cosmetic feature") while the clause's own owning issue has not converged on what it contains. **Recommendation:** either #703 should be ordered explicitly behind #524's own close (not just #526's transitive note), or the outcome text should stop asserting the clause is exercised as if it already has stable content to test against.

### 5. (Medium) All four acceptance criteria are presence checks with no named test and no correctness assertion — gameable as literally worded

Compare to sibling issues in the same program (#524's AC-1 names `CliContractConformanceTest`; #466's predictions are each a numbered, falsifiable P-item with a concrete assertion). #703's four checkboxes are prose descriptions of desired behavior with no test name attached: "produces a check annotation," "attribution is derived... not guess[ed]," "produces two annotations," "produces a repo-level annotation." A literal-minded implementation could satisfy AC-1 by emitting exactly one hardcoded annotation string containing the words "test name" and a placeholder value whenever any test in the run fails, regardless of which watched element or vector actually diverged — nothing in the AC text requires the annotation's *content* to be checked against the actual failing expectation, only that an annotation with *a* test name and *a* counterexample exists. **Recommendation:** name a conformance test for each AC (e.g., `AnnotationAttributionTest`) that asserts content correctness — the annotation names the actual failing watched element and vector index — not merely annotation presence.

### 6. (Low) AC-4's "cannot be attributed to a specific file" case has no defined trigger given the current single-file batch model

AC-4: *"A test whose failure cannot be attributed to a specific file produces a repo-level annotation that says so."* Given finding 2 (one circuit file per `jls -b` invocation), every test in a report is trivially attributable — it's the operand the Action passed. The only failure modes that don't name a specific circuit file are run-level failures (a `LoadError`, a runtime failure, exit status 1/2) that aren't per-test failures at all; those aren't "a test whose failure cannot be attributed," they're a run that never produced a verdict. As worded, AC-4 describes a case that either can't occur under the current architecture or needs its own precise definition (e.g., what happens when the expectations file names a watched element that doesn't resolve in a subcircuit? that's a parse-time usage error today per #466 §7.11, exit 2, not a per-test attribution failure). **Recommendation:** replace "cannot be attributed to a specific file" with the concrete failure mode intended (run-level failure vs. per-vector failure) so the criterion has an actual trigger to test.

### 7. (Low) Prose-only hierarchy: `part_of_feature: 526` is not a GitHub sub-issue relationship

`get_parent` on #703 returns `null`, and #526's own `get_sub_issues`/children would not surface #703 either — the `part_of_feature`/`ordering_after` graph this whole task-tier program relies on lives entirely in YAML frontmatter text, not in GitHub's native issue-relationship API. This is a repo-wide convention (already noted in `issue-0524.adversarial.md` finding 6), not unique to #703, so it's recorded for completeness rather than counted heavily against this issue.

## What's solid

- **The Boundary note is accurate and appropriately narrow.** "Presentation of an existing verdict; verdict content and counterexample generation are CAP-06's" correctly defers to #300/#369/#466 rather than re-scoping the verdict engine — consistent with how #369 and #466 themselves describe the ownership split.
- **The core UX motivation is sound and well-stated.** Annotating the failing file directly (versus a log dump a student must correlate by hand) is a real usability improvement over the status quo (`examples/autograde/autograde.py`'s string-diff grading), and nothing here disputes that goal.
- **`ordering_after: ["TASK-C526-1"]` is a real and correctly-identified prerequisite** — #701 (TASK-C526-1) is indeed the task that builds the Action's own run/report step this one attaches annotations to; the sequencing is not backwards.

## Verdict rationale

The issue's central idea is reasonable, but it sits on an unfinished, actively-revised dependency chain (#524 flagged `needs-rework` independently) and adds a genuine new hazard of its own: putting hidden-vector counterexamples into a check annotation the graded student reads on their own commit, with no redaction criterion, echoing a leak the parent issue's own review already named and that #703 does not address. AC-3's multi-file scenario has no upstream design support at all, and AC-2's "derive attribution from the artifact" instruction is likely solving the wrong layer given the batch interface's actual one-file-per-invocation shape. None of this requires killing the task, but it should not be picked up as filed. **needs-rework.**
