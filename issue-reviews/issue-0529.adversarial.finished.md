# Issue #529: FEAT-C23-2: clicking a waveform edge flashes the gate that emitted it on the canvas, and clicking a canvas wire lands on its chronogram lane — identity by click, not by matching names by eye
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

A small, plausible two-way UI linkage (waveform edge ↔ canvas element) whose acceptance criteria overstate what they actually verify. AC-3 asserts "both directions" are covered by a single named test, but that test — by the wording of #529 itself and by the parent capstone's (#504) own definition of it — only ever exercises one direction. The identity claim underpinning AC-1 ("resolves identity through the same seam the chronogram tap uses") is contradicted for a real, non-trivial case (multi-driver/tri-state nets) by the repository's own engineering analysis of this exact code path. And the issue's only stated dependency (`ordering_after: [FEAT-C23-1]`, #527) omits at least two other planned features that its own named verification test structurally requires.

## Findings, most severe first

**1. (HIGH) AC-3 claims bidirectional test coverage from a test leg it itself describes as one-directional, and AC-2 has no named test at all.**
AC-3 reads: "Both directions work inside the scripted, fully offline `HazardDiagnosisWalkthroughTest` (CAP-23 AC-1) leg that runs trigger -> capture -> edge click -> element flash." The enumerated steps of that leg — trigger, capture, edge click, element flash — are exactly AC-1's direction (waveform → canvas); no step corresponds to AC-2 (canvas wire click → chronogram lane, "creating the lane if the signal is not yet displayed"). This matches the issue's own "Boundary / reference notes": "The CAP-23 demo slice includes only the one-way half (edge -> element flash); the canvas -> lane direction completes here" — i.e. the issue itself documents that the shared test predates and does not cover the direction #529 is supposed to add. Cross-checking #504 (CAP-23) directly confirms it: AC-1 there is defined as "the full §1 steps 1–2 walk (trigger, capture, edge click, cause chain naming both unequal-delay paths)... Spans PF-5+PF-1+PF-2+PF-3" — canvas-to-lane focusing is absent from that enumeration too. As written, an implementer can satisfy AC-3's literal test requirement while AC-2 (half the feature's stated Outcome) ships with zero automated verification.
**Recommendation:** name a distinct test (or a distinct `@Test` method) for the canvas→lane direction, and stop citing `HazardDiagnosisWalkthroughTest` as proof of "both directions" — cite it only for the direction it actually walks.

**2. (HIGH) AC-3's named test has real prerequisites this issue does not declare.** `HazardDiagnosisWalkthroughTest` is CAP-23's own AC-1 gate, and per #504 it "Spans PF-5+PF-1+PF-2+PF-3" — i.e. it requires the triggering logic-analyzer element (PF-5, filed as #534, open), the chronogram (PF-1, #527, open), cross-probing (PF-2, this issue), and the cause-chain inspector (PF-3, filed as #532, open, whose own `ordering_after` is `[FEAT-C23-2]`, i.e. #529). #529's machine block lists only `ordering_after: [FEAT-C23-1]` (#527). If the "trigger -> capture" half of the leg needs #534 and the same test class also carries #532's cause-chain assertions (per #504's definition, not a separately named test), then #529 cannot actually pass AC-3 in isolation no matter how well its own code is written — the test it points to won't compile/pass until siblings that are not its declared dependency also land. That is either a missing `ordering_after` entry or evidence that AC-3 is pointing at the wrong (not-yet-writable) test.
**Recommendation:** either add `#534` (and clarify the #532 relationship, given #532 depends on #529 rather than the reverse) to `ordering_after`/blocking notes, or replace AC-3 with a scoped test that only requires what #529 itself provides plus #527.

**3. (MED-HIGH) The identity claim in AC-4 is contradicted, for a real case, by the repo's own analysis of the exact propagation code path.** AC-4 says cross-probing "resolves identity through the same seam the chronogram tap uses" as if a well-defined "emitting element" is always available from that seam. `docs/capability-roadmap/lf-03-causal-debug.md` (lines 15–30) documents the opposite for multi-driver nets: `WireNet.propagate` (`src/jls/elem/WireNet.java:454-485`) computes the winning driver during tri-state resolution and then discards it — `value = actual; // :484 — the driver identity is dropped` — and the event actually posted, `SimEvent.PinChanged` (`src/jls/sim/SimEvent.java:30-31`), is a zero-field record carrying no producer reference; per the same doc it is "82.3% of all events fired." For a lane bound directly to one watched element's own output (the existing `Trace` class already stores `private Element element;`, `src/jls/edit/Trace.java:57`), identity is trivial and the issue's claim holds. For a bus/net lane with more than one candidate driver — exactly the "hazard diagnosis" scenario CAP-23 is built around (reconvergent paths, conflicting drivers) — "the element that emitted that event" is information the current propagation path actively throws away, and no amount of "the same seam" phrasing conjures it back. The issue never scopes AC-1 to single-driver signals only.
**Recommendation:** either explicitly scope AC-1/AC-4 to elements with a single static driver (deferring multi-driver identity to #532's cause-chain/journal work, which is designed to carry provenance) and say so in the issue, or add the minimal driver-identity retention this needs and note the added cost against AC-4's "no additional per-event cost" claim.

**4. (MED) "Flash" is unspecified and can be satisfied by never un-highlighting.** AC-1 says an edge click "visibly flashes/highlights the emitting element" (either/or wording). The only highlight primitive in the codebase is a persistent boolean — `Element.java:41-42` (`protected boolean highlight = false;`), `:571-589` (`setHighlight`/`isHighlighted`), rendered via `ElementRenderSupport.drawHighlight` — with no timed/transient state and no distinction from ordinary selection-highlighting. A literal reading of AC-1 is satisfied by calling `setHighlight(true)` once and never reverting, which is indistinguishable from "select this element" and would visually collide with whatever the user has actually selected on the canvas. No duration, no un-highlight trigger (next click? timer? next edge?), and no interaction rule with concurrent user selection is specified.
**Recommendation:** specify the flash as a distinct, time-bounded visual state (or explicitly define it as reusing selection state with revert-on-next-action), and say what happens if the emitting element is already selected or already flashing from a prior click.

**5. (MED) Cross-subcircuit navigation is unaddressed.** "Scrolling it into view if off-screen" (AC-1) presumes the emitting element is on the currently open canvas. JLS's circuits are hierarchical (`src/jls/elem/SubCircuit.java`, `src/jls/edit/SubCircuitDialog.java`, `SubCircuitRenderer.java`); a probed/traced signal can originate inside a subcircuit instance that is not the currently open editor view. The issue says nothing about what "flash the emitting element" means when that element lives behind an unopened subcircuit boundary — does the editor auto-descend into the subcircuit, open a new window, or silently no-op?
**Recommendation:** add an explicit acceptance note (or an explicit out-of-scope statement with a follow-up issue) for the subcircuit case, since "the student diagnosing a bad edge" scenario this issue targets is exactly where nested designs get used.

**6. (LOW-MED) AC-4's "no additional per-event cost" claim rides on a ratchet test that predates this feature and was not written to detect this feature's cost.** `ChronogramClosedCostTest` is #527's (FEAT-C23-1's) AC-5/K9 gate, guarding the chronogram's own event-stream tap. #529 asserts its cross-probing "accrues" no additional per-event cost and cites "AC-5 tolerance unaffected" as if that existing test already covers it. But #529 potentially adds its own machinery (e.g., a click-time or event-time lookup structure mapping signals/nets to elements for AC-1, or listener registration for AC-2) that #527's test was authored before #529 existed and therefore was not designed to catch a regression in.
**Recommendation:** either explicitly re-run/extend `ChronogramClosedCostTest` (or an equivalent) after #529's code lands and record the result, or add a note that this criterion is inherited/unverified-by-a-new-test and should not be treated as self-certifying.

## What's solid (no rework needed)

- The maintainer's own boundary-note comment (2026-08-04) already resolved the #529 vs #532 duplicate-conflation risk with a clear, evidence-based non-merge rationale (depth: one vs. depth: N) — no rework needed there.
- Canvas-side wire click handling and hit-testing already exist (`SpatialIndex`, `instanceof Wire` branches throughout `SimpleEditor.java`, e.g. lines 901, 954, 1006, 2625), so AC-2's "clicking a wire on the canvas" is not new mechanism, just a new consumer of it.
- Scroll-into-view precedent already exists via `JViewport` ancestor lookups used elsewhere in the editor (`SimpleEditor.java:2119,2150,2212,2991,3510,5404`; `InteractiveSimulator.java:1254-1279`), so AC-1's "scrolling it into view" is feasible with existing patterns (modulo finding 5's subcircuit gap).
- Treating TASK-0008 (#373, synthesized-net naming stability) as "consumed if present, not required" is correctly hedged — cross-probing keying on element/event identity rather than display names sidesteps that task's actual scope (HDL export names), which is unrelated to GUI wire identity.
