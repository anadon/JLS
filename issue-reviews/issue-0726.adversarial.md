# Issue #726: TASK-C554-1: one documented command runs the benchmark suite and emits events/s and cycles/s per fixture, with each fixture's clocking regime recorded
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what's being proposed

Promote the ad-hoc measurement in `riscv/bench_kernel.py` into a committed, one-command, in-tree benchmark harness that emits events/s and cycles/s per fixture with a recorded clocking regime, built without touching `riscv/` (D5), with run-to-run figures reported against a stated tolerance. Ordered after #413 (TASK-0025). Fixtures are explicitly out of scope (#728) and the machine-readable contract is explicitly out of scope (#730).

## Findings, most severe first

**1. The issue's own acceptance criteria are already stated to be wrong by the maintainer's own later comment, and the body was never updated to match.** A 2026-08-08 comment on the parent (#554#issuecomment-5227413660) reads, addressed to this exact issue: *"#726 says 'one documented command runs the benchmark suite and emits events/s and cycles/s per fixture, with each fixture's clock…'. That is necessary and not sufficient."* It names two concrete additions — phase-split timing (`initSimulation` vs `runEventLoop`, a ~43% swing on `k2000`: 0.568s vs 0.742s per `docs/capability-roadmap/keystone-c-performance.md:121`) and the full event census (fired/posted/dup-suppressed/max-queue-depth) — and states plainly: *"#442's events-per-clock-cycle equality is asserted against these integers... Without them, #442 has a gate and no way to feed it."* #726's Acceptance Criteria section still reads only "emits events/s and cycles/s per fixture at stated node counts" plus a clocking-regime clause; nothing about phase-split timing or the event census. The issue's own `created_at`/`updated_at` (both 2026-08-04) predate the comment (2026-08-08) and the body has not been revised since. An implementer who satisfies the literal text produces a harness that passes its own review while leaving #442 — the one other consumer this issue names in its Boundary section — unfed. **Recommendation:** fold the comment's two additions into the Acceptance Criteria verbatim (phase-split timing as two separately-reported numbers, full event census as machine-readable fields) before work starts.

**2. The Outcome sentence misdescribes what `riscv/bench_kernel.py` actually measures, and the real instruments behind the numbers this project has already published don't exist in the tree at all.** Read directly (`riscv/bench_kernel.py:59-64`): the script wraps one `subprocess.run(["java","-jar",...])` call end-to-end in `time.time()` — JVM boot, circuit load, and the whole simulation folded into one wall-clock number (`jlsrun.py:27-43` confirms `run_circuit` shells to the jar and returns only stdout/rc, no phase timing, no event counts). That is the noisy **CLI-inclusive** figure `keystone-c-performance.md` itself calls out as "≈1,100–1,450 cycles/s end-to-end from the CLI" (`keystone-c-performance.md:140-141`) — a different and much worse number than the "8,090 cycles/s" warm-loop figure the same document headlines, which comes from **in-process** instrumentation (`jls.sim.KernelProbe2`, `KernelProbe`, `Census`, `NoDedup`) that is explicitly described in that doc's own §12 as living "under `/tmp/.../scratchpad/bench/`... re-runnable against the tree at HEAD" — i.e. never committed. Verified independently: `grep -rn "class KernelProbe\|class Census\|class NoDedup" src test` returns nothing. So the issue's claim that the harness "becomes a committed, in-tree benchmark harness" that "lives in `riscv/bench_kernel.py`" is not a promotion of existing measurement code — it is new instrumentation work (an in-process phase-timing and event-counting harness) that must be built essentially from scratch, and the issue's framing understates that. **Recommendation:** state explicitly that this is new in-process instrumentation, not a port of `bench_kernel.py`'s subprocess-timing approach, and size the task accordingly (the `band_mw: 0.5-1` estimate looks light against this).

**3. The stated single prerequisite (`ordering_after: [413]`) is real but unlanded, and confirmed absent from this checkout.** #413 (TASK-0025) is open, itself `blocked_by: [377, 379]`. Checked directly: `test/fixtures/` contains exactly four files (`fork-4.6-shiftregister.jls`, `headless-canary-gate.jls`, `legacy-4.1/README.md`, `riscv-sum1to10.jls`) — no CPU-scale fixture, no `k2000`-equivalent — and neither `CalibrationFixtureTest` nor `NoRiscvDirectoryReferencesTest` (the tests #413 is supposed to add) exist anywhere under `test/`. So today there is no in-tree CPU-scale circuit for this harness to run against, and no in-tree, riscv/-free way to generate one either: `riscv/build_cpu.py` (the only circuit generator that exists) is exactly what D5 and this issue's own boundary forbid depending on. The only tracked fixture available right now, `riscv-sum1to10.jls`, is the one #442's own O5 finding already flags as useless for this purpose: "retires 194 events at final time 15... exercises elaboration, not the queue." A harness stood up today can only be validated against a workload too small to produce a meaningful events/s or cycles/s figure. **Recommendation:** treat #413 as a hard blocker in practice, not just in the frontmatter — do not start implementation (beyond scaffolding/design) until #413's fixture lands, and say so in the issue.

**4. "the harness refuses to report a figure whose regime it cannot state" has no defined taxonomy, so it is satisfiable by a no-op.** Nothing in #726 (or in #730, which owns the output schema) enumerates what a "clocking regime" is. `docs/machine-calibration.md` and #442 O6 establish that this is not decorative: two element-for-element identical circuits produced events-per-cycle figures of 121.5 under an internal clock and 388.4 under a TestGen/`-t` vector — a 3.2x spread from drive method alone. As written, an implementer can satisfy this AC by hardcoding the literal string `"regime: default"` on every fixture and technically never fail to "state" one, while never actually distinguishing internal-clock from `-t`-vector drive — defeating the entire reason the criterion exists. **Recommendation:** enumerate the regime values this harness must recognize (at minimum: internal-clock vs `-t`/TestGen-vector, per #442 O6's own vocabulary) as part of AC-2, not left for #730 to invent after the fact.

**5. The run-to-run tolerance criterion is gameable and conflicts with measured reality unless a discipline is specified.** AC-4 asks for "figures within a stated run-to-run tolerance, and that tolerance is reported alongside the numbers" — but states no methodology. #442's own measurement (O4, same repo, same machine, three fresh reps in one JVM, zero code change): ns/event spanning 432,915.5 → 103,917.5, a **4.17x** spread. `docs/machine-calibration.md` §7.3 (cited by keystone-c-performance.md §8.1) prescribes a specific discipline — best-of-N with warm-up reps discarded — precisely because a naive tolerance would have to be enormous to not immediately self-violate. #726 requires none of that: an implementer can satisfy the letter of AC-4 either by (a) declaring a tolerance wide enough to be meaningless (e.g. ±500%) and technically "reporting" it, or (b) silently applying an undocumented warm-up/best-of-N scheme, producing a number nobody else can reproduce the derivation of. Either way "within a stated tolerance" passes review while telling a reader nothing. **Recommendation:** require the harness to follow (or explicitly cite and reuse) `docs/machine-calibration.md` §7.3's warm-up/best-of-N convention rather than inventing its own, and require the tolerance to be derived from an observed spread, not asserted.

**6. Scope/ownership seam with #442 is named but not enforced.** The Boundary section correctly disclaims building "a second gate" — #442 owns ceiling bands. But AC-4's ad hoc tolerance-and-report mechanism is functionally the same kind of noise-handling #442's ceiling bands already formalize (`test/fixtures/simulation-budget.properties`, best-of-N, ceiling-only). Without an explicit instruction to reuse #442's convention (see finding 5), the two issues are likely to land two different noise-handling methodologies for what should be the same underlying event-loop measurements, which is exactly the "two issues own the same measurement" failure mode the parent capstone (#512 CAP-28) is on record as trying to avoid (per #554#issuecomment-5176145586). **Recommendation:** add a line to the Boundary section: "tolerance/warm-up methodology follows #442's `docs/machine-calibration.md` §7.3 convention; do not invent a second one."

**7. No implementation language is specified, and the existing code being displaced is exactly the kind of tooling the project has decided against.** `riscv/bench_kernel.py` and its dependencies (`riscv_ref.py`, `build_cpu.py`, `jlsrun.py`) are Python, out-of-tree by D5's own definition even before deletion. #726 says the new harness "runs from the in-tree build" but never states it must be Java/Maven-native (e.g., a tagged JUnit `longrun` test, matching the `#335`/TASK-0016 precedent for long-run lanes) rather than, say, a new committed Python script that itself becomes a future re-homing problem identical to the one #413 is currently paying down. **Recommendation:** state explicitly that the harness is Java/Maven-native per D5's own wording ("a first-class, in-tree, tested JLS mechanism"), not merely "not `riscv/`".

## What's solid

- The producer/consumer boundary — this suite reports numbers, #442 owns the gate, #728 owns fixtures, #730 owns the machine-readable contract — is clean and, per the parent capstone's own dedup pass, not in dispute.
- Requiring the clocking regime to accompany every figure at all (rather than leaving it implicit) is directionally correct and anchored in a real, measured hazard (#442 O6's 3.2x regime-dependent spread).
- Explicitly declining to build a second gate over #442's territory is the right call and avoids an obvious duplication trap.

## Bottom line

The framing is sound but the acceptance criteria as literally written are stale relative to the maintainer's own follow-up comment on the parent issue (phase-split timing and the event census are missing though named as required), understate the scope of new instrumentation actually needed (this is not a "promotion" of `bench_kernel.py`, whose wall-clock method is the noisy CLI-inclusive figure the project already distinguishes from the number that matters), rest on a prerequisite (#413) that is confirmed absent from the tree today, and leave two of four acceptance criteria (the clocking-regime taxonomy, the run-to-run tolerance) loose enough to be satisfied by a no-op implementation. This needs a body rewrite — absorb the maintainer's comment, name a regime taxonomy, cite #442's warm-up discipline, and state Java/Maven-native explicitly — before it is ready to execute against.
