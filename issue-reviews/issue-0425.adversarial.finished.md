# Issue #425: TASK-0080: the guest-visible byte stream is written to its own file handle and compared byte for byte, and changing the clock period changes no output byte
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

The issue is open (confirmed via `issue_read`) and internally disciplined — it is honest about its own red state (O1–O6 are real, reproduced against this checkout: `machines/` does not exist, no `timeout-minutes` anywhere in `.github/workflows/`, `docs/batch-interface.md:33-48`'s stdout/stderr table matches verbatim, `JLSStart.FLAGS` really has 14 rows and none of them is `--transcript`/`--clock-period`/`-console`). The falsification-first methodology (P3 must be written first and shown red) is sound engineering discipline. But the task's own dependency graph, once traced, shows it sits at the far end of a chain that is far deeper and less certain than `blocked_by: [395, 392, 378]` states, its declared parent feature does not actually track it, and at least one Prediction (P8) depends on a mechanism the issue never defines.

## Findings, most severe first

**1. The declared parent does not track this task — the re-home is not actually wired up.** Comment #2 on this issue (2026-08-08) says the parent moved `326 → 202` after #326 was closed as a duplicate. I fetched #202: its `requires_tasks` is `[278]` only, it has one open sub-issue (not this one), and its body — Capability Statement, Decomposition table, Completion Criteria — never mentions `machines/`, `TASK-0080`, a boot run, or a Linux guest at all; #202 is scoped to the existing single-cycle `riscv/` CPU (fib/memtest goldens, an HDL-export oracle, a sample circuit). The comment itself concedes this isn't done: *"A later roster/relabel pass should resolve this task into #202's `requires_tasks`."* Until that pass happens, this task's Definition of Done item *"Landing reported on #326 with a `STATUS:` comment"* points at a **closed** issue, and no open feature's Completion Criteria or Integration Criteria actually gates on this task landing. Recommendation: block execution until the roster pass lands, not just the maintainer comment.

**2. The true critical path is far deeper than `blocked_by` states, and part of it is unfileable.** The YAML declares three blockers (#395, #392, #378), but the prose itself names two more hard prerequisites — TASK-0069 (transcript capture/replay/console pane) and TASK-0012 (`-d 0`) — that "cannot yet be filed as an edge" because they have no issue numbers. Following the chain one level further: #392 is itself only landable after three *more* unfiled tasks (TASK-0038, TASK-0070, TASK-0076); #395 is gated by an Open Question that "blocks execution absolutely" pending a maintainer ratification of a previously-recorded "no committed guest images" policy; #378 is blocked by #374 (TASK-0015), unlanded, plus a conventional (unfiled) TASK-0017. So the actual precondition set for #425 to even *start* is on the order of six-plus large tasks, at least two of them not yet expressible as GitHub issues. Treating this as a three-item `blocked_by` list understates the programme by a wide margin.

**3. `blocked_by: [392]` does not mean what it implies — landing #392 does not produce a bootable machine.** #392's own scope statement is explicit: *"This task establishes the method rather than the whole machine ... two boundaries actually green — `alu` and `regfile`."* Decode, load/store (itself additionally gated on an unfiled write-mask task), CSR, CLINT, the CPU composition, and the `rv32-soc.jls` top level (UART, DTB, console) are **not delivered by #392** and, per #392's own text, are deliberately "not re-decomposed into task ids" — they are undifferentiated future labor inside a stated 12–26 maintainer-week band for the *whole* feature. #425's Method step says "Confirm ... #392 ... [has] landed" as if that clears the way to run `machines/cpu-rv32/rv32-soc.jls`; in fact the file this task needs to run against has no tracked path to existing at all. This is a hidden assumption that should be surfaced as its own blocking dependency (or this task should not claim `machines/cpu-rv32/rv32-soc.jls` as an input until a task actually owns building it end to end).

**4. P8's method is internally contradictory and its mechanism is undefined.** P8 and the Conclusion both describe the structural expedition as *"the same file with the CPU boundary flipped to `structural`, the same `boot.itlog`, the same golden."* If a `SubCircuit` instance's fidelity attribute (#389/#325) changes from `behavioral` to `structural`, the `.jls` save text differs — it is not "the same file" in the byte-identical sense this task is otherwise fastidious about (`cmp`, golden, exclusion set). Worse: §7.1 ("External interfaces modified") adds exactly two new surfaces, `--transcript` and `--clock-period` — there is no CLI flag, no documented file-variant convention, and no cited mechanism for *how* an operator flips the boundary. #421 (TASK-0066, "a subcircuit instance's implementation can be switched mid-run") is the obvious candidate but is listed only as `related`, not `blocked_by`, and its abstract is about *mid-run* switching, not selecting an initial per-run binding. P8 is explicitly "recorded, not automated," but even a manually recorded procedure needs a defined mechanism, and none exists in this issue or its cited blockers.

**5. `--clock-period`'s coverage guarantee is undefined at a fidelity boundary.** Open Question 5 requires the multiplier to apply to "every `Clock` element in the elaborated design," and §11 says "the multiplier's coverage must be asserted, not assumed." But a boundary running in `behavioral` fidelity is backed by an external reference model (`jls.mach`, per #392 O5–O7 and #389/#325), not by drawn `Clock` elements. Nothing in §5 or §7 says whether or how `--clock-period` is expected to affect timing inside a behavioral-mode boundary, and H1 ("no output byte moves under a 10x clock period") is not obviously even well-typed when part of the simulated system isn't running through JLS's `Clock`/event-queue machinery at all. This is exactly the kind of "coverage asserted for the wrong reason" failure mode §11 warns about for the drawn side, but the issue never extends that warning to the mixed-fidelity case its own P2/P8 commands run.

**6. The load-bearing test's design is admittedly gameable, and that risk is marked non-blocking.** Open Question 4 states plainly: *"a single integer multiple can pass by coincidence on a design whose timing happens to scale"* and recommends 10x plus a fractional multiplier — but files this under "Rides along," not "Blocks execution." P3 is simultaneously called "the load-bearing half," "the cheapest test in the programme," and the thing that "gates everything built on the stream regime." A falsification guard whose author has already identified a concrete way it can pass for the wrong reason should not be shippable with that gap unresolved and non-blocking.

**7. The normative documents this task cites do not exist in this repository's history, and the pinned evidence commit is not a valid object here.** `git log --all -- docs/parity-contract.md` and `docs/virtual-hardware-parity.md` return nothing, and `git cat-file -t 2d0ca9d` fails ("not a valid object name") against this checkout's history (HEAD `bd54461`). Sibling issue #423 quotes specific line-numbered text as living at `docs/parity-contract.md:229-252` at that same pinned commit. Whatever produced this discrepancy, an implementer picking up #425 "at the executor's checkout" (Method step 1's own instruction) has no way to verify §1's citations of `docs/parity-contract.md` §2.4/§2.5/§3.3/§3.6/§5.4 or `docs/virtual-hardware-parity.md` §1.3/§1.5, which this task treats as authoritative and explicitly declines to restate.

**8. Two independently-designed "exclusion set" mechanisms are heading for the same programme without reconciliation.** P4 here creates `test/fixtures/c2/exclusions.txt`, a free-text file with "a reason per entry" and a count ratchet, owned entirely by this task. #423 (listed only as `related`) builds `jls.parity.ExclusionSet`, a fixed four-entry enum (`mcycle`, `minstret`, `mtime`, `mtimecmp`) ratcheted bidirectionally against `docs/parity-contract.md` §2.5. Both are called "the exclusion set" for the same overall parity claim, at different granularities (transcript-line text vs. typed retirement-record fields), and #425 never states whether `exclusions.txt` is meant to be a strict subset, a superset, or an unrelated mechanism relative to #423's `ExclusionSet`. Left unreconciled, this is exactly the kind of drift the H2/H3 falsification criteria in both issues warn against.

## What's solid

- The refusal to write a per-instruction comparison (§7.10, "do not let a reviewer ask for one") correctly cites and defers to #347/#423's documented reason (`docs/parity-contract.md` §3.6) rather than re-litigating it here.
- O4's insistence on a **second** scheduled job sharing the `nightly` concurrency group, rather than widening the existing cron, is correct and matches `ci.yml`'s actual header comment and concurrency block as checked out.
- The "cannot be automated" carve-out for live interaction (§6, §9) is honest about what a replay-based test can and cannot prove.

## Recommendation

Do not schedule execution. First: (a) land the roster/relabel pass so an open feature actually tracks this task; (b) either fold TASK-0069/TASK-0012 into filed, numbered issues or explicitly waive them per this repo's own rule 10; (c) get a written answer for how P8's boundary-flip is performed and whether `--clock-period` is well-defined across a mixed-fidelity run, before `--clock-period` ships as the "load-bearing" guard; (d) reconcile this task's `exclusions.txt` against #423's `ExclusionSet` before either lands.
