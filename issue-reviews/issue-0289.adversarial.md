# Issue #289: Dark mode: FlatDarkLaf plus a dark Theme variant, currently impossible because ~113 draw sites hardcode black foregrounds
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: sound-with-concerns

## Summary

The infrastructure claims check out against HEAD (29afb26): `Theme` (`src/jls/Theme.java`), `UserPrefs.THEME_KEY` (`UserPrefs.java:32`), the Color-scheme menu (`JLSStart.java:1941-1963`), the `-Djls.laf` seam (`JLSStart.java:937-1016`), and `flatlaf:3.7.2` in `pom.xml:80-83` are all real and as described. But the issue's headline evidence (the "113" count) conflates three different populations, its P1 acceptance gate cannot be literally satisfied, its own delta-E test does not gate the defect the issue exists to fix, and one of its stated risks (§7.1 export/print theme-leak) is understated as hypothetical when the source shows it is already true today. These are fixable in the issue text before work starts, hence "sound-with-concerns" rather than "needs-rework."

## Findings (most severe first)

### 1. HIGH — The acceptance criteria never test the actual defect (illegible foreground on dark background)

The abstract's failure mode is explicit: "on a dark background they would be illegible." But every gating check in §9/§14 is either (a) a grep count, (b) `ThemeTest`'s delta-E matrix, or (c) a persistence round-trip. `ThemeTest` (`test/jls/ThemeTest.java:1-60` and its `DISTINGUISHABLE = 25.0` bar) validates **pairwise distances among the wire-state roles** (`touch`, `highlight`, `wireOff`, `nonZero`, `wireZero`, …) — it says nothing about the new `foreground` role's contrast against `background`. A `Theme.DARK` that sets `foreground = Color.black` on a `background = Color.darkGray` would pass P1 (grep ~0), pass P2 (wire-state deltas unaffected, since foreground isn't in that matrix), pass P3 (persistence), and pass P4 (light rendering untouched) — while every element label and body outline is invisible, exactly the bug the issue exists to fix. The second comment adds prose about "adequate contrast against a dark background" but stops at "report the conflict," with no delta-E-style numeric bar and no test named. **Recommendation:** add a concrete foreground-vs-background contrast requirement (e.g., extend `ThemeTest`'s delta-E machinery to check `foreground` against `background` for every shipped theme) to §5/§9/§14 before implementation starts, not as a soft aspiration in a comment.

### 2. HIGH — The P1 grep gate ("returns 113 → ~0") cannot be literally satisfied, and its escape hatch is unenforced

Re-running the cited grep (`grep -rn "Color\.black\b\|Color\.BLACK\b" src/jls --include=*.java`) reproduces 113, but two of those hits are in `Theme.java:65` and `Theme.java:81` themselves — the `wireZero` field of `DEFAULT` and `CLASSIC`, i.e. the palette's own deliberate value, not a hardcoded-foreground bug. `ThemeTest.classicReproducesTheLegacyPalette` (`test/jls/ThemeTest.java:42`) asserts `Color.black == t.wireZero()` and is a permanent, correct constraint — so grep will **never** hit ~0 in `src/jls`, only in `src/jls/edit` (the 110 figure the second comment separately re-derives). The issue's own P1 wording ("Observation-2 grep returns 113 … post-change it returns ~0") is therefore internally inconsistent with its own P4 requirement (CLASSIC/DEFAULT must stay byte-identical, which requires keeping those two literals). The stated fallback — "residual literals annotated" — has no enforcement: nothing in §14's checklist requires a test that fails on an un-annotated or unbounded allowlist. (The second comment quotes exactly this failure mode from #381 — "an allowlist that has grown to cover everything is the failure mode" — as material to carry in, but it is not yet in the issue body's Completion Criteria.) **Recommendation:** scope the grep gate to `src/jls/edit` (110, not 113) or explicitly exclude `Theme.java`'s palette-definition lines and `BatchTracePrinter.java`; add the anti-vacuity allowlist test from the second comment to §14 as a hard requirement, not carried-forward prose.

### 3. MEDIUM — The 113 figure conflates draw-site bugs with a legitimate palette constant and an export-path literal that should NOT be swept

Breaking down the 113: 110 are genuine draw-site literals under `src/jls/edit/*.java` (the real sweep target); 2 are `Theme.java`'s own `wireZero = Color.black` definitions (deliberate palette values, not bugs — see Finding 2); 1 is `BatchTracePrinter.java:176` (`gg.setColor(Color.black)`), which is on the batch/trace **printing** path — per the issue's own §7.1 contract ("exports and printing must pin the light/classic palette"), this literal is arguably *correct as-is* and should be left alone or explicitly justified, not swept into a theme-following `foreground` role. An implementer mechanically "fixing all 113" per the title/Observation-2 risks two opposite mistakes: breaking `ThemeTest.classicReproducesTheLegacyPalette` by touching `Theme.java`, or making batch trace-printing theme-dependent by touching `BatchTracePrinter.java`, which is the exact leak §7.1 warns against for other export paths. **Recommendation:** state the breakdown (110 draw sites / 2 palette constants / 1 print-path literal, explicitly excluded) in Observations rather than a single undifferentiated "113," matching the more careful accounting the maintainer's own second comment already did.

### 4. MEDIUM — §7.1's export/print theme-leak is written as a hypothetical when the source shows it is already true

§7.1 reads: "if export paths read the active theme, dark canvases could leak into printouts." This is not conditional at HEAD: `Theme.apply()` rewrites the mutable `JLSInfo.Palette` statics (per `Theme.java`'s own javadoc, "every consumer follows the active theme without being edited"), and the raster/SVG image-export path (`CircuitRenderer.exportImage`, `src/jls/edit/CircuitRenderer.java:301`) explicitly reuses "the same element paint path that fills a bitmap" (comment at line ~311) — and that paint path (`WireRenderer.java:64-76`, `RegisterRenderer.java:47`, etc.) reads `JLSInfo.Palette.touchColor`/`wireOffColor`/`watchColor`/etc. directly. Only the export **background** is hardcoded (`svg.setColor(Color.white)` at `CircuitRenderer.java` near line 313); wire/element colors are not. So today, switching to a theme with non-default wire colors (e.g. `CLASSIC`) and exporting an image *already* bakes that theme's colors into the PNG/SVG — confirming the risk is live, not speculative, and it will get worse once a `DARK` theme with a dark-adjacent `wireZero`/`foreground` exists. Writing this as "if" invites an implementer to treat §7.1 as optional polish rather than a pre-existing gap this task must also close for the *existing* CLASSIC/DEFAULT choice, let alone the new DARK one. **Recommendation:** reword §7.1 as a confirmed finding with the cited call sites, not a conditional; consider whether the export-pinning fix is really in scope for a "task" issue whose title is about dark mode, or whether it's really an existing latent bug that predates this issue (in which case it may deserve its own tracking issue rather than being folded in here as an afterthought).

### 5. MEDIUM — Internal conflict between the issue body's single `foreground` role and the maintainer's own inbound guidance

§7.4 commits definitively to one new role: "`Theme.foreground()` role (name final at implementation)." The second comment, presented as material "worth carrying into this issue's execution," warns against exactly this shape: "A colour with no matching `Theme` role must fail the sweep, not acquire an allowlist entry silently — and the fix is a role named for what it means semantically, never a twelfth role called 'black.'" Taken at face value, that guidance implies distinct call sites (element body outlines, state-machine borders, text labels, wire zero/off strokes) may need distinct semantic roles rather than one catch-all `foreground`, which is a materially different, larger design than what §7.4/§8 describe (a single mechanical find-replace). The issue as filed does not resolve this tension — it locks in "one role" in the normative Interface Contract section while the "material to carry forward" comment argues against exactly that pattern. **Recommendation:** decide before implementation whether `foreground` is one role or several, and update §7.4/§8 accordingly; a mid-implementation redesign here would invalidate the "mechanical, no new helpers expected" cost estimate in §7.5.

### 6. LOW/MEDIUM — `blocked_by: [286]` is waivable, which lets "dark mode" ship without themed chrome despite the Research Question promising both

§3's Research Question asks for "canvas, chrome, and L&F flipping together," and `blocked_by: [286]` exists specifically because "chrome must follow Theme roles before any dark palette can restyle it." But #286 is itself open, unstarted (1 comment, no linked PR, confirmed via `issue_read`), and §14's own checklist offers an out: "Blocker #286 landed (**or dependency waived per rule 10**)." If #286 stalls and #289 is waived through, the shipped result is a themed canvas next to hardcoded `Color.CYAN`/`yellow`/`WHITE` chrome (`SimpleEditor.java` per #286's Observations) on a dark background — a materially worse UX than "no dark mode," and not what the Research Question promised. **Recommendation:** either make the #286 dependency hard (no waiver) for the "chrome" part of the definition of done, or explicitly scope down the Research Question/title to "canvas dark mode" if the waiver path is taken, so a waived landing isn't reported against a promise it didn't keep.

### 7. LOW — §7.4's "through the existing `installLookAndFeel` seam" undersells the runtime-swap risk already flagged in §10

`JLSStart.installLookAndFeel()` (`JLSStart.java:994-1016`) is a one-shot, boot-time static call, invoked once around `JLSStart.java:1222`; it has no notion of live theme switching. The runtime flip described in §7.9 (`SwingUtilities.updateComponentTreeUI` on theme change) is new machinery layered beside that seam, not a reuse of it — the existing seam only decides what to install *at launch*. This is a framing nit, not fatal: §10's own Falsification Criteria already correctly anticipates the real risk ("If theme-switch L&F swap destabilizes open dialogs … restrict L&F choice to next-launch"). But §7.4's language undersells the amount of new code this needs relative to the "mechanical … no new helpers expected" framing applied to the rest of the task. **Recommendation:** note in §7.4 that H2's live-swap path is new code, not seam reuse, so the "no new helpers" cost estimate in §7.5 is understood to apply only to the sweep, not to H2.

### 8. LOW — No chunking/milestone plan for a ~110-site, ~25-file mechanical change

§2 Observation 1 (the source javadoc) and §8 both call the sweep "mechanical, reviewed in chunks," but no chunking boundary is proposed (per-file? per-element-category? one PR?). Given P4 requires provably byte-identical light rendering across the whole sweep, a single giant PR is exactly the shape most likely to hide the "semantic mistake" the second comment warns a "110-site mechanical diff hides... easily." This is a process/cost risk, not a correctness one. **Recommendation:** commit to a chunking scheme (e.g., by renderer file, gated by the #24 pixel-baseline suite per chunk) in §8 rather than leaving it to the implementer's discretion.

## What's solid (no attack needed)

- The infra-reuse claims are verified true: `UserPrefs.THEME_KEY` persistence (`UserPrefs.java:32,83,125`) needs no new code; `flatlaf:3.7.2` (`pom.xml:80-83`) already bundles `FlatDarkLaf` in the same jar, so H2 needs no new dependency.
- `ThemeTest`'s CIE76/Vienot delta-E harness (`test/jls/ThemeTest.java`) is real, already green, and mechanically extendable to a third theme — a good regression net for the wire-state part of the problem (see Finding 1 for what it doesn't cover).
- P4 (CLASSIC/DEFAULT rendering byte-identical post-sweep) is a well-chosen regression guard against exactly the "mechanical diff hides a semantic mistake" risk the maintainer separately names.
- The dependency structure and boundary comments (vs. #381, #570, #787) are unusually well-documented for a task-tier issue — the ownership question is resolved cleanly, which is more than most trackers manage.
