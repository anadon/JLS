# Issue #512: CAP-28: every public performance claim is a published, reproducible measurement — and JLS's simulation speed has a number a competitor comparison can cite
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: sound-with-concerns

## Summary

This capstone's Outcome, its five acceptance criteria, and KC-28-1 are well-formed and I did not find grounds to reject them. The problems are all upstream and downstream of that solid core: the machine-readable frontmatter is already stale and self-contradicted by the issue's own second comment, the "gap is publishing, not measuring" framing that justified PF-1's original scope is false and independently verifiable as false, the demo-slice critical path is longer than the `band_mw` implies once its transitive `blocked_by` chain is walked, and two of the acceptance criteria (AC-2's "tolerance," AC-5's "flagship workload") are underspecified enough to be satisfied on paper without closing the real gap.

## Findings, most severe first

### 1. [HIGH] The frontmatter is machine-readable and already wrong, and nothing edits it back

The issue's opening YAML block states `related: [... "#476 TASK-0063 / #475 TASK-0056 (engine stack that will move the numbers)" ...]`. I fetched #475 directly: `"state":"closed","state_reason":"duplicate"`, closed 2026-08-08 — the same day the issue's own comment #2 flagged this. Comment #2 says to "read that clause as #476 / #879" but does not edit the body, and GitHub issue bodies aren't self-updating. Any tooling, agent, or future reader that parses the `related:` block programmatically (which this filing's own style — `filed_by:`, `cap_id:`, machine-block YAML — clearly anticipates) will silently pick up a closed/superseded issue number. **Recommendation:** edit the issue body's `related:` line, not just comment on it; a correction that lives only in a comment thread does not survive the next automated pass over open issues the way this project's own tooling (see the "coverage pass" comment #1) clearly expects to run.

### 2. [HIGH] The originating premise ("the gap is publishing, not measuring") is false, and the issue's own PF-1 scope was written against the false version

The `evidence:` line reads: *"baseline check: harness exists at riscv/bench_kernel.py — the gap is publishing, not measuring."* I verified this directly:

- `riscv/bench_kernel.py:4-9` self-describes: *"Not part of the verification suite... It produced the kernel measurements in docs/capability-roadmap/keystone-c-performance.md; re-run it before and after any such change rather than trusting those numbers."* It builds the *fixture*, not the number.
- `docs/capability-roadmap/keystone-c-performance.md` §12 lists the actual instruments that produced the headline number (`jls.sim.KernelProbe`, `KernelProbe2`, `Census`, etc.) as living under a scratchpad path outside the repo.
- `git grep -l "KernelProbe\|class Census\|NoDedup" -- src test riscv` returns **zero matches** — I ran this myself and confirmed it independently of the issue's own comment #2.

So the actual state is not "we publish nothing despite having a harness" but "the number that would be published exists once, was measured off-tree, and its instrument was never committed." PF-1 as originally written — *"promote `riscv/bench_kernel.py`'s measurement into a committed, documented benchmark"* — undershoots this: `bench_kernel.py` only builds the workload, not the timing/event-count probes that produce AC-1's actual numbers. Comment #2 catches this and says PF-1's scope "should therefore be read as: commit the instrument, not just formalize the fixture generator" — but, same issue as Finding 1, this correction lives in a comment and the PF-1 bullet in the body is unedited. A contributor reading only the body (or an agent doing a shallow pass) will scope #554 too narrowly and produce something that satisfies the *stale* PF-1 text while leaving AC-2 unreproducible. **Recommendation:** edit PF-1's body text to say "commit the instrument" explicitly, and make sure #554 (already filed against the old text) is checked against the corrected scope before it's considered to satisfy PF-1.

### 3. [HIGH] The demo-slice critical path is longer than `band_mw: "3-6"` suggests, and the issue doesn't surface it

`ordering_after: ["#413 TASK-0025"]` is real and load-bearing (I read #413 in full: `riscv/build/k2000.jls` is untracked, ungenerated on disk, and is the anchor six documents divide by — confirmed via #413's own `git ls-files --error-unmatch` probe). But #413 is itself `blocked_by: [377, 379]` — both open tasks (TASK-0022, TASK-0023) that #413 says must land first "because deleting the generator before the measurements exist destroys the ability to characterize the fixture that replaces it." So the chain a reader has to walk to get from "capstone filed" to "PF-1 can even start" is #512 → #413 → {#377, #379}, three additional open issues, none of which #512's body mentions by number. The capstone states `demo_slice: "PF-1+PF-2 first published number with methodology, 1-2 mw"` as if PF-1 is close to shovel-ready; it is gated behind at minimum three other unlanded tasks with their own multi-week specs. This isn't fatal (the ordering is honestly stated as a hard dependency), but the `band_mw` estimate reads as if it prices PF-1's own labor, not the wait for its prerequisites, and nothing in the capstone flags that distinction for whoever schedules it. **Recommendation:** either fold the transitive dependency chain into the capstone's ordering notes, or explicitly state that `band_mw` prices execution time only and excludes prerequisite wait time.

### 4. [MEDIUM] AC-4 / PF-3's "do not build twice" boundary with #442 assumes #442 is a small, landed thing; it is neither

PF-3 says the CI perf lane is "joint with TASK-0026 #442's bands ... do not build twice." I read #442 in full: it is a 14-section task with its own five open questions (discovery-pattern ambiguity already found a real bug — 8 discoverable `*GoldenTest` classes vs. 6 the spec assumed — a ceiling-vs-floor debate, and a documented 4.17x same-JVM timing variance that #442 itself says forces its bands to be one-sided). #442 has not landed (no `simulation-budget.properties`, no `SimulationBudgetRatchetTest` exist in the tree today — I did not find them via Glob/Grep). PF-3 is therefore not "joint work with a peer task," it is **fully blocked** on #442's much larger and still-undecided scope landing first, and #442 is itself `blocked_by` #377/#379/#413 — the same chain as Finding 3. AC-4 ("a regression beyond the band turns a scheduled lane red before the published number is a lie") cannot be satisfied at all until that whole chain clears.

### 5. [MEDIUM] AC-2's "stated tolerance" and AC-5's "flagship workload" are both gameable as written

- **AC-2**: *"An independent party can reproduce the number within a stated tolerance from the doc alone."* No tolerance is specified anywhere in #512, which is defensible for a capstone that defers detail to its features — except the issue's own evidence chain (via #442's O4, which I read) measured a **4.17x** spread in ns/event across three reps in one JVM with no code change. A tolerance wide enough to swallow that variance would make AC-2 trivially satisfiable while still being useless for catching a real regression; nothing in #512 forecloses that outcome, and nothing hands PF-2 a floor on how tight "stated tolerance" has to be.
- **AC-5**: *"The head-to-head is published with the harness, including at least one workload where a competitor wins."* Good instinct (forecloses cherry-picking a workload where JLS always wins), but "flagship workload" is never pinned to a specific tracked fixture the way #413 insists the CPU-scale anchor must be. PF-4 could satisfy AC-5's letter by choosing a trivially small "competitor wins" workload while comparing JLS's best case against Digital's worst case on the actual headline ("flagship") comparison, and no acceptance criterion here would catch that asymmetry. KC-28-1 partially guards against the worst form of this (it forecloses hiding a bad flagship result), but only if "flagship workload" is fixed *before* the numbers come in — which AC-5 doesn't require.

**Recommendation for both:** name the tolerance mechanism (e.g., "ceiling only, best-of-N, per the discipline #442 is already establishing") and name or require a committed definition of "flagship workload" (e.g., the same `k2000`-scale fixture #413 tracks) before PF-4 executes, not after.

### 6. [LOW] Unaddressed licensing/redistribution question for PF-4

AC-5 requires a "published harness" for the head-to-head against Digital and Logisim-Evolution. Logisim-Evolution is GPLv3 (compatible with JLS's own GPLv3 per `pop_GPLv3.pdf`/`LICENSE` at repo root); Digital's license terms aren't addressed anywhere in #512. If PF-4's harness needs to vendor or redistribute either tool's binary/source to be "reproducible... from the doc alone" (AC-2's own bar), that's a licensing question nobody in this issue has asked. Low severity because the obvious mitigation (link to the competitor's own repo/release, don't vendor it) is standard practice and likely what's intended, but the issue doesn't say so.

### 7. [LOW] The 120 kHz vs. cycles/s comparison that motivates the whole capstone is asserted, not audited

The `evidence:` line frames the deficit as "Digital teardown (published 120 kHz processor claim vs JLS's zero published numbers)". `docs/capability-roadmap/keystone-c-performance.md` (which I read in full) measures JLS at ~8,090 simulated CPU cycles/s in-loop, ~1,100–1,450 cycles/s end-to-end from the CLI — genuinely an order of magnitude or more below Digital's cited 120 kHz, and possibly comparing different things (simulated clock frequency vs. cycles/s achieved on a synthetic sum-loop workload; different CPUs, different toolchains). #512 doesn't ask whether the two numbers are unit-comparable before citing the gap as the capstone's motivating fact, and PF-4 is the feature that would actually settle this — meaning the capstone's own justification is presently unverified by its own criteria. Not a blocker (KC-28-1 already commits to publishing whatever the honest number turns out to be), but worth flagging that the "we lose every performance conversation by default" framing is doing motivational work here without having been checked against apples-to-apples methodology yet.

## What's solid (one line each)

- **Outcome and AC-1 through AC-5** are clear, testable, and internally consistent with each other.
- **KC-28-1** (publish even if >5x behind Digital) is the single strongest piece of this issue — it explicitly forecloses the most likely failure mode (quiet suppression of an unflattering number) and correctly treats honesty as the deliverable rather than the score.
- **`ordering_after: #413`** is a real, well-justified, hard dependency — I independently confirmed #413's own observation that the CPU-scale anchor is neither tracked nor present on disk today.
- **The issue's own comment #2** is a genuinely good adversarial pass (I re-verified its central claims: the closed #475, the missing `KernelProbe*` harnesses, `bench_kernel.py`'s self-description) — my main complaint about it is structural (Finding 1/2), not substantive.
- **Filed sub-issues #554/#555/#557/#560** exist and are scoped to reference rather than duplicate the relations named in the capstone body, per comment #1's own coverage table, which I spot-checked against #554 directly.
