# Issue #554: FEAT-C28-1: the measurement behind every public number is a committed, documented benchmark suite — with fixtures below CPU scale, tracked in-tree, that outlives the deletion of `riscv/`
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what's being proposed

Promote `riscv/bench_kernel.py`'s ad-hoc measurement into a committed, documented benchmark command (AC-1), add 2-3 sub-CPU-scale fixtures (AC-3), keep every fixture tracked outside `riscv/` so deleting that directory leaves the suite green (AC-2), and emit output the downstream doc/lane features can consume without hand-editing (AC-4). Ordered after #413 (TASK-0025), which is supposed to re-home the CPU-scale calibration fixture before `riscv/` is deleted. Three child tasks (#726, #728, #730) already exist splitting this exact scope.

## Findings, most severe first

**1. The issue's own AC-1/AC-4 are already stated to be wrong by the maintainer's own later comment, and the issue body was never corrected.** The 2026-08-08 comment on this issue says plainly: *"AC-1] is necessary and not sufficient"* — the command must also separate `initSimulation` from `runEventLoop` timing (a ~43% swing on `k2000`) and emit the full event census (fired/posted/dup-suppressed/max-queue-depth) because *"#442's events-per-clock-cycle equality is asserted against these integers... Without them, #442 has a gate and no way to feed it."* Yet the Acceptance Criteria section of the issue body still reads only *"emits events/s and cycles/s per fixture at stated node counts."* An implementer who satisfies the literal AC-1/AC-4 text — and #726's identically narrow AC list — produces a suite that passes review while leaving #442 (TASK-0026, already `blocked_by: [413]` and needing exactly this census) unfed. This is the textbook "acceptance criteria that can pass while the real goal fails" pattern, and it is self-diagnosed in-thread but not fixed in the spec. **Recommendation:** fold the comment's two additions (phase-split timing, full event census as machine-readable fields) into AC-1/AC-4 verbatim before work starts, and update #726/#730 to match.

**2. The dependency chain is deeper than the one edge the issue declares, and none of it has landed.** `ordering_after` names only `#413 TASK-0025`. But #413 itself is `blocked_by: [377, 379]` (TASK-0022/TASK-0023, measuring α/CPI/k and behavioral binding), and per #335's own roster all six FEAT-009 tasks — including #413 — are status "not filed" as of this writing. Verified independently: `test/fixtures/` contains exactly four `.jls` files (`fork-4.6-shiftregister.jls`, `headless-canary-gate.jls`, `legacy-4.1/README.md`, `riscv-sum1to10.jls`) — no CPU-scale anchor — and `test/fixtures/simulation-budget.properties` (which #442 needs and which this suite's numbers should feed) does not exist. So "orders after #413" understates the real prerequisite: this feature cannot produce a meaningful AC-1 number until at least three unlanded tasks (#377, #379, #413) land in sequence first. **Recommendation:** either state the full transitive dependency in `ordering_after`, or explicitly note (as #413 already does for its own blockers) that this is a real, not preferential, ordering constraint.

**3. `docs/capability-roadmap/keystone-c-performance.md` cites numbers from instrumentation that is not in the repository, and this issue inherits that fixture/harness gap without addressing it.** The doc's §12 recipe compiles `jls/sim/KernelProbe.java`, `KernelProbe2.java`, `Census.java`, and `NoDedup.java` "from a scratchpad outside the tree" and calls `riscv/bench_kernel.py` itself *"a scratch harness, not part of the verification suite, and can be deleted"* (`docs/capability-roadmap/keystone-c-performance.md:815`, confirmed by direct read). Verified: `git grep -l "class KernelProbe\|class Census\|class NoDedup" -- src test` returns nothing — none of these four classes exist anywhere in the tree today. So "promote the measurement that today lives in `riscv/bench_kernel.py`" (the issue's own Outcome sentence) is imprecise: the actual instruments behind the one number this repo has ever published live nowhere at all, not even in `riscv/`. The issue should say so explicitly (it is new-build work, not literally "promotion" of existing code) rather than implying the harness merely needs re-homing.

**4. The GitHub issue hierarchy does not reflect the YAML-declared task decomposition, which is a real coordination hazard for a fleet of agents/reviewers.** #726, #728 and #730 each declare `part_of_feature: 554` in their frontmatter, but `issue_read get_sub_issues` on #554 returns an empty list (`has_children: false`). Any tooling or reviewer that walks GitHub's actual parent/child graph — rather than grepping issue bodies for YAML — will miss all three child tasks and could duplicate or contradict their scope. This is exactly the kind of drift the project's own `REPLAN:`/`STATUS:` conventions elsewhere are designed to catch, and it isn't caught here. **Recommendation:** use GitHub's native sub-issue linking (`sub_issue_write`) for #726/#728/#730, not just prose frontmatter.

**5. AC-2 ("deleting `riscv/` leaves the suite green") has no enforcement mechanism specified, unlike its sibling tasks.** #413 ships `NoRiscvDirectoryReferencesTest` (a ratchet with a non-empty allowlist) precisely because prose claims about `riscv/`-independence rot silently (per #413 O5, doclint-invisible `{@code}` citations already rotted once). #554/#726/#728 specify no analogous ratchet test — AC-2 is checked once, presumably by eyeballing, and nothing prevents a later PR from quietly reintroducing a `riscv/`-relative path into the suite's fixture list or generator. **Recommendation:** add an explicit acceptance criterion requiring a CI-enforced check (a ratchet test or a CI step that runs the suite with `riscv/` absent), not just a stated intent.

**6. AC-3's "smaller standard circuits" has no size floor, so it is gameable in the way #442's own O5 already documents happening once.** #442's O5 finding is that `riscv-sum1to10.jls` (194 events, final time 15) "exercises elaboration, not the queue," making a gate built on it alone useless for catching a queue-level regression. AC-3 here asks only for fixtures "below CPU scale" with no minimum node count or behavior (e.g., must exercise the event queue under sustained clocking) — a trivially small 2-gate counter satisfies the letter of AC-3 while reproducing the exact failure mode #442 already flagged as a threat to validity. **Recommendation:** borrow #442's own language and require that at least one sub-CPU-scale fixture be clock-driven over enough cycles to exercise queue/dedup machinery, not just settle once.

**7. No implementation language/runtime is specified, which matters given what is being replaced.** The suite it replaces (`riscv/bench_kernel.py` and its Python dependencies `riscv_ref.py`, `build_cpu.py`, `jlsrun.py`) is exactly the kind of out-of-tree, non-Java tooling the project's D5 decision and ARCHITECTURE.md's Java-only, headless discipline are moving away from. Neither #554 nor #726 states that the new "committed command" must be Java/Maven-native (e.g., a JUnit-tagged `longrun` test per #335's TASK-0016 precedent) rather than a new Python script that itself becomes a future re-homing problem. **Recommendation:** state explicitly that the harness is a first-class in-tree JLS mechanism per D5's own wording ("Whatever replaces them must be a first-class, in-tree, tested JLS mechanism"), not merely "not `riscv/`".

## What's solid

- The producer/consumer boundary against #555/#557/#560/#442/#335 is unusually well drawn (comment 1) and is not itself in dispute — no merge-direction ambiguity found.
- The `ordering_after: #413` edge is directionally correct: #413 genuinely must land first since it is the only path to a tracked CPU-scale fixture (confirmed: no such fixture exists in `test/fixtures/` today).
- Explicitly disclaiming a second gate (leaving ceiling bands to #442) avoids the "two issues own the same measurement" duplication risk the maintainer flags as the one thing that would break the whole CAP-28 chain.

## Bottom line

The boundary-setting and dependency direction are sound, but the acceptance criteria as literally written in the issue body are stale relative to the maintainer's own follow-up analysis, understate the real (three-task-deep) dependency chain, omit any ratchet-style enforcement for the deletion-survival claim that is the feature's namesake property, and leave AC-3's "below CPU scale" fixtures unbounded enough to reproduce a gaming pattern the project has already caught once (#442 O5). This needs a body rewrite (fold in comment 2's additions, tighten AC-2/AC-3, fix the sub-issue linkage) before it's ready to execute against.
