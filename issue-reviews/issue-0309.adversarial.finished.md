# Issue #309: CAP-14: JLS's own analog answer and real ngspice's agree to a declared 3.16e-3 envelope nightly, so "the solver is correct" stops resting on JLS's own tests
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of the issue

A `tier:capstone` proposal: JLS emits a SPICE deck real `ngspice` can run, JLS's own (to-be-built) analog solver and ngspice's are compared on a fixture corpus within a derived 3.16e-3 relative tolerance, on a nightly non-gating CI lane, with an anti-cheat lower bound and a solver-statistics ratchet so an in-envelope regression still fails. It requires seven already-filed feature issues (#351, #331, #367, #368, #336, #317, #315) and carries an extensive machine-readable dependency block, a mermaid DAG, and four follow-up "REPLAN"/adjudication comments auditing that graph's internal consistency.

Verification note: I spot-checked the issue's most load-bearing repository citations against the actual checked-out tree (not the issue's `evidence_commit`, which does not exist here — see Finding 1) and they held up: `grep -rli spice src/` and the analog/nodal/newton/adc/dac pattern both return nothing; `grep -rl ProcessBuilder src/` returns nothing while `test/` returns 15 files; `grep -rn timeout-minutes .github/workflows/` returns nothing against 23 `runs-on:` jobs (14+5+1+1+1+1); `src/jls/elem/Element.java:18` really is `permits DisplayElement, LogicElement, Wire`; the `HdlExporter` net-walk, `ElementRegistryTest`, and `HdlPolicyTest` line citations match (adjusted for the line-number drift the issue's own re-pin comment already documents); `VerilogEmitter`/`VhdlEmitter`/`PcfEmitter` line counts match exactly (752/1149/199). Issue #317's `blocked_by: [353, 354]` and its own "UNOWNED at 3-6 maintainer-weeks" self-assessment are confirmed by fetching #317 directly. This is a well-fact-checked issue where it cites live source — which makes the gaps below more notable, not less.

## Findings, most severe first

**1. [High] The core numeric claim rests on evidence that is not, and may never be, in this tree.** The issue's `evidence_commit: 2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7` does not exist in this repository at all (`git cat-file -t 2d0ca9d...` → `fatal: bad object`); the issue's own pinned comment (2026-08-03) confirms it "exists only on a branch that will not be merged and will be deleted." More importantly, several documents §3/§4/§5/the DoD cite as sources for the load-bearing arithmetic are simply absent from the tree I reviewed: `docs/parity-contract.md`, `docs/machine-calibration.md`, `docs/virtual-hardware-parity.md`, and the entire `docs/plan/capstones/` directory (including `CAP-14-ngspice-interoperation-parity.md` itself) — all confirmed missing via direct filesystem check. The headline number this issue exists to fix — the 3.16e-3 envelope, replacing a flawed 1e-4 figure — is derived from measurements the issue says live in `11-analog-determination.md §1.2, §4.2, §4.3, §5.1`, an out-of-tree planning document. AC-8 exists precisely because the issue's own author recognizes this ("cannot be met by that citation... requires them re-run and committed"), but until AC-8 runs, no reviewer today can independently verify the 5.38e-4 drift figure or the 1e-3 RELTOL floor the whole envelope is built on. **Recommendation:** do not treat §4's arithmetic as settled until AC-8 lands; gate any dependent work (e.g. promoting AC-2 to required for a device family) on the in-tree re-measurement actually existing, not on the out-of-tree citation.

**2. [High] Scope and cost are wildly disproportionate to this project's stated mission and its own recent precedent, and the issue never argues the disproportion away.** Standalone cost is quoted as 50.5-79 maintainer-weeks (over a year of full-time single-maintainer effort) to add a from-scratch nonlinear circuit solver, device models, a physical time base, and mixed-signal bridges to a tool README.md describes as "an educational digital logic circuit editor and simulator." ARCHITECTURE.md's own "Recorded decisions" section shows this project declining i18n and a dark theme — both far cheaper — explicitly because "single-maintainer... is a large, ongoing tax." This issue's only justification for its own much larger ask is "Priority 14 of 18," asserted without argument, and a `D8`/`D10` process citation that a want is "a path and a cost, not a policy question" — which sidesteps rather than answers whether analog SPICE parity belongs in a *digital logic* teaching tool's roadmap at all. **Recommendation:** the priority ranking and the fit-for-mission question deserve an explicit paragraph here, not a bare number.

**3. [Medium-High] A concrete promotion gate in the acceptance criteria is left unstated.** AC-2: "promoted to required per device family only after a stated number of green runs" — no number appears anywhere in the issue body, the machine block, the Open Questions, or the Completion Criteria. As written this cannot be executed: whoever closes this issue must invent a threshold with no stated criterion for what counts as sufficient (2 runs and 50 runs both satisfy the literal text). This is exactly the kind of gap the adversarial lens exists to catch — an acceptance criterion that reads as rigorous but is silently unfalsifiable at the one number that decides when the nightly, non-gating oracle starts mattering. **Recommendation:** state the number (or the rule that derives it) before this issue is treated as ready to execute against.

**4. [Medium] AC-5's cross-platform bit-identical determinism claim for a Newton-Raphson adaptive-step solver is asserted, not engineered.** AC-5 calls determinism "the property no external floating-point simulator can supply and which the whole claim rests on," but nowhere does the issue discuss how Java guarantees it across the platform matrix README.md documents (Linux/macOS/Windows on amd64/arm64, plus a RISC-V jar target) once transcendental math (`exp`, `pow`, `log` — inescapable in diode/BJT device models) and adaptive step control enter the picture. JLS's existing digital `Simulator` is a discrete-event interpreter with no floating-point iteration to speak of (`src/jls/sim/Simulator.java:36`, `protected long now = 0;` — an integer tick counter); porting that determinism story to a nonlinear analog solver is a materially different and harder problem that FEAT-046 is assumed, not shown, to solve. **Recommendation:** either point to FEAT-046's own determinism design (I did not review #351 in depth) or flag this as an open risk in #309 rather than presenting it as settled.

**5. [Medium] Licensing due diligence on "porting numerics from ngspice" is one sentence, on a project that is otherwise careful about licensing.** OQ-1 recommends "porting with attribution" from ngspice (mixed BSD-3-clause and legacy UC Berkeley/SPICE3 attribution-clause code) into GPL-3.0-or-later JLS, calling it "a cost-and-specialism judgement, not a policy." No license text is cited, no per-file attribution/notice plan is described, and there is no cross-reference to `SECURITY.md` or a legal review — a conspicuous gap given ARCHITECTURE.md's #222 decision explicitly avoids EPL-2.0 (ELK) linking hazards and README.md documents provenance-attestation and Authenticode-signing discipline in detail. **Recommendation:** name the actual ngspice license(s) in scope and the attribution mechanism before FEAT-046/FEAT-049 start porting code, not after.

**6. [Medium] The issue's own numbers show the acceptance window is thin, and the fallback is to delete the entire nightly lane rather than adapt it.** §3 states plainly: "the whole window is one decade" and, against the two-sided `2·RELTOL` bound, "the declared envelope retains... 1.58x margin... which is positive but thin." KC-14-1 commits to deleting the comparator lane outright if the envelope must widen past 1e-2 rather than weakening it. That is a defensible anti-goodharting stance, but it means a large chunk of the claimed 10-16 mw marginal investment (comparator, ASCII parser, nightly wiring, golden headers) is disposable on a margin the filer already calls thin — a real execution risk worth surfacing to whoever prioritizes this against #317's already-noted lack of an owner.

**7. [Low-Medium] The issue is overwhelmingly process/governance content, not engineering content, and that ratio is worth naming.** Roughly 90% of the body (and all four comments) is DAG bookkeeping — roster-to-issue-number resolution, edge mirroring/withdrawal, evidence re-pinning, feature-coverage verification — generated and cross-checked by an automated process ("Generated by Claude Code" on every comment). Real technical design (comparator algorithm, deck grammar, fixture selection methodology, ASCII-output parser) is deferred entirely to the seven required feature issues, several of which (per #317's own text) are themselves unowned. This is acceptable for a capstone-tier tracking issue, but four rounds of self-audit before any solver code exists is a meaningful process cost on a project that is, by its own account, single-maintainer.

**8. Solid, briefly:**
- The re-derivation of the 3.16e-3 envelope (replacing a 1e-4 figure that the issue shows sat *below* its own measured noise floor) is genuinely well-reasoned arithmetic, not hand-waving, and the disjoint AC-2/AC-4 band check is a legitimate anti-cheat design.
- The DAG-no-cycle argument (§ machine block, cross-checked against #317's actual `blocked_by`) holds up under independent verification.
- D8's "never link/subprocess ngspice from `src/`" constraint is concretely measurable today (`grep -rl ProcessBuilder src/` → 0) and the issue correctly treats it as a hard boundary rather than an aspiration.
- The technical repository citations I checked (line numbers, grep counts, file sizes) were consistently accurate against the live tree.

## Bottom line

The dependency graph and internal cross-checking are unusually rigorous, and several individual numbers are honestly derived. But the issue asks a single-maintainer digital-logic teaching tool to commit over a year of effort to a SPICE-parity capstone whose central tolerance figure cites evidence that is not in the tree, whose promotion gate has an unstated threshold, and whose cross-platform determinism and licensing questions are asserted rather than engineered. These are fixable, not fatal — hence "needs-rework" rather than "should-not-proceed" — but none of the seven required features should be treated as executing against settled acceptance criteria until findings 1 and 3 are closed.
