## 3. [High] The alphabet premise assumes a four-state per-bit model that does not exist in the codebase or the accepted spec

§1 and §7.10 build the plane-count arithmetic (`planes(r) = ceil(log2(r+3))`) on "a radix-$r$ alphabet with full X/Z/U" and state "the four-state work itself uses five" code points (`0 1 X Z U`) at radix 2. But `docs/simulation-semantics.md` §2 — the current, normative spec — reads: **"Value domain: two states plus HiZ ... There is no unknown/X state anywhere ... HiZ is all-or-nothing per signal ... There is no per-bit HiZ."** Per-bit X and per-bit Z is not what JLS has today, and it is not yet a landed design: the `FourState` permit (IEEE 1364 aval/bval plane pair, per-bit X/Z) exists only as a sketch carried in #232's comment thread for the still-open #881, not as accepted, built semantics. #422 treats "the four-state work" as an established fact the plane-count arithmetic can safely assume, when it is itself unbuilt, undecided design belonging to a different open issue. If #881 lands with a different plane layout than the aval/bval sketch, §1's "fourth-plane cliff is at radix 6" arithmetic (H2, P3) may need to be re-derived before this task can even start.

## 4. [Medium] Open Question 2 ("does `diminish` saturate or wrap?") is marked "Blocks execution" but nothing in §5 tests it

The issue's own Open Questions section says the diminish boundary "Blocks execution — an unfixed boundary is two implementations waiting to happen," and recommends saturate. But no prediction in §5 (P1–P10) asserts diminish's behavior at the boundary (`diminish(0)` at any radix). ## 5. [Medium] P2's differential test has no committed PRNG, unlike its sibling P4

P4 requires "the seed is committed so a failure is reproducible," and Open Question 4 goes further, flagging that even a committed seed needs "a named, version-stable generator ... not `java.util.Random`'s defaults." P2 — the test that proves "radix 2 is free" (H1, the entire justification for the binary fast path costing nothing) — runs "10,000 random operand pairs at widths 1, 8, 32 and 64" with no seed or generator requirement at all. A flaky P2 (irreproducible on re-run) would leave H1 essentially untested despite being the load-bearing hypothesis of the whole task ("Stop. The collapse is the entire justification for radix 2 costing nothing"). **Recommendation:** apply the same seed/generator discipline Open Question 4 demands for P4 to P2 as well.

## 6. [Medium] Feasibility risk on H5's hardware requirement, with no fallback if the hardware can't be obtained

Materials & Apparatus lists as required: "Hardware exhibiting the microcoded `PEXT`/`PDEP` path — AMD Zen 1, Zen+, Zen 2, Hygon Dhyana." §11 itself calls out this is a **bus-factor-1, single-maintainer** project. Open Question 1 marks the shift/mask-vs-intrinsic decision as "Blocks execution," but the issue never says what happens if the assignee has no access to that specific silicon (unlikely to be available in CI or on a typical dev machine). Without a stated fallback (e.g., a documented default choice if the hardware is unreachable within some effort budget), this is a plausible stall point that could block the whole task on a hardware acquisition problem rather than a design problem.
