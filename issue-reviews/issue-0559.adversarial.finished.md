# Issue #559: FEAT-C29-3: a CircuitVerse .cv project opens in JLS with its subcircuits intact, and every construct that only looks preserved — starting with queue-priority delay — is named in the report
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what's being proposed

A `.cv` (CircuitVerse project JSON) importer: subcircuits map to JLS `SubCircuit`s with hierarchy preserved, the queue-priority "delay" attribute is imported but flagged as not semantics-preserving, JSON parsing is hardened as untrusted input, and import is undoable with no partial circuit ever emitted. Sibling of #558 (.dig) and #561 (Falstad text) under CAP-29 (#513), sharing a report contract with #556 (FEAT-C29-1). A same-day maintainer comment on this issue already investigated and rejected the "these four are duplicates" hypothesis with a concrete comparison table — that housekeeping is solid and I don't re-litigate it.

## Findings, most severe first

**1. (High) No JSON parsing capability exists anywhere in the codebase, and the issue neither prices nor acknowledges acquiring one.** `pom.xml` has no JSON dependency (only `org.tukaani:xz`, `org.jfree.svg`, `flatlaf`, `jspecify`, plus test deps — confirmed by grepping every `artifactId`). The only JSON the tree touches today is Yosys netlist output consumed by an *external subprocess* (`docs/hdl-support-research.md`), never parsed in-process. AC-4 says "hardened as untrusted input per the #38 standard," but #38's actual fixes (`FileAbstractor.readZip` entry-size cap, `Memory.decodeInitRLE` run-length cap, try-with-resources on `readXZ`) are container/RLE-specific to the `.jls` format — there is no existing depth/size-bound idiom for JSON in this project to reuse. Whoever picks this up must first choose and vet a JSON library (or hand-roll a bounded streaming parser), which given this project's SBOM/attestation/license discipline (README "License and provenance," the CycloneDX BOM, #349's provenance-audit requirements for absorbed data) is itself nontrivial work. This is unpriced and unmentioned in a 3-5 mw band.

**2. (High) AC-1 and AC-2 are gameable relative to the sibling importer's own established bar.** The CAP-29 sibling this issue is modeled on, #323 (FEAT-025, `.circ`), requires a *corpus* of public files with a mechanical net-count/net-membership equality assertion ($P(\mathrm{imp}(f)) \cong P_{\mathrm{src}}(f)$, criterion I1) and a committed accept/reject table (I6) before the estimate is trusted. #559's AC-1 asks only for "one real published `.cv` project" with "zero unexplained losses," and AC-2 ("subcircuits map... with hierarchy preserved") carries no analogous measurable predicate at all — no net-partition equality, no corpus. As written, an implementer can satisfy both by picking a single trivial project with no nested subcircuits, no tri-state buses, and no fan-out edge cases, and calling AC-1/AC-2 done. Given CAP-29 AC-1 ("One real published circuit **per format**... zero unexplained losses") uses the same wording for all three siblings, this weakness is inherited, not unique to 559, but it lands here uncorrected.

**3. (Medium-High) The entire prerequisite chain this issue depends on is unlanded, and the issue presents itself as schedulable regardless.** `ordering_after` names #556 and #314. #556 is itself `ordering_after` #323, which is `blocked_by` #314 and #349 — both open. Verified: `src/jls/imp/` does not exist, no `docs/registry-keyed-tables.md`, and the only importer precedent in the tree is `src/jls/hdl/imp/NetlistImporter.java` — a different subsystem (Yosys HDL netlist, not a foreign-CAD-tool migration importer) whose builder is explicitly `private` and must be promoted before reuse (per #323 Open Question 4, itself unresolved). The 3-5 mw band implicitly assumes the shared report contract and loud-loader discipline already exist; today none of it does, and none of #556/#323/#314/#349 is close to landing. The issue is honest about ordering in its YAML header but doesn't surface that the whole chain is presently empty scaffolding — a reader skimming Outcome/AC could reasonably think this is buildable now.

**4. (Medium) AC-3 (the delay-honesty criterion) has no independently testable pass condition.** The underlying claim is well-sourced — #510 §3 cites CircuitVerse's own tracker issue #1412 for "delay is queue-priority, timing untrustworthy," so this isn't invented. But AC-3 only requires the flag to be "documented... in the migration report, imported but flagged, never presented as equivalent" — prose, not a predicate. Compare #323's report-totality test, an *equality* ($C_{\mathrm{src}}(f)\setminus C_{\mathrm{out}}(f) = R(f)$) enforced by a golden test. #559 relies entirely on #556 to supply that machinery (architecturally fine, per the boundary note), but as written *this issue alone* has no golden fixture, no named test, and no way to distinguish "documented" from "documented so vaguely instructors miss it."

**5. (Medium) Two acceptance criteria are in latent tension and the issue doesn't resolve it: faithful reproduction vs. never-silently-rewriting.** #510's evidence table records that CircuitVerse's own subcircuit nodes have a known bug ("subcircuit nodes silently disconnect," CircuitVerse's own tracker item cited alongside #1412). A real published `.cv` project may therefore encode a subcircuit whose *source-tool* connectivity is itself broken. AC-2 asks for hierarchy "preserved"; AC-5 forbids the importer from "silently rewrit[ing] semantics." Nothing in the issue says whether the importer should reproduce a known CircuitVerse connectivity bug bug-for-bug (arguably correct fidelity, arguably importing a defect JLS shouldn't perpetuate) or normalize it (which is itself a semantic rewrite AC-5 disallows unless it's named as a loss). The issue also never states which CircuitVerse schema version(s) it targets, despite the format having changed shape over the tool's multi-year GSoC-driven history (#510 §3) — a real underspecification for "plain JSON" that isn't actually one static schema.

**6. (Low-Medium) No licensing/provenance discussion for reproducing CircuitVerse-specific semantics, where the sibling issue treats this carefully.** #323 (`.circ`/Logisim-Evolution) spends an entire Open Question on whether replicating a competitor's exact geometric/connectivity rules from having read its source is a clean-room hazard, and recommends documented compliance over clean-room reimplementation specifically because clean-room-from-read-source is legally *worse*. #559 says nothing about the equivalent question for CircuitVerse (whose semantics — including the exact delay/queue-priority behavior this issue asks to be replicated and flagged — presumably requires reading CircuitVerse source or its own bug reports to get right). Given how deliberately the rest of this plan handles that question for the other two formats, its total absence here reads as an oversight rather than a considered non-issue.

**7. Solid, no rework needed:**
- AC-4's hostile-input criterion ("no code paths from document content to filesystem or network, one test per attack vector") is concrete and directly mirrors #323's proven I3 pattern — a good criterion, just missing the tooling (finding 1).
- AC-5 correctly reuses the existing no-partial-circuit discipline documented at `NetlistImporter.java:46-47` rather than inventing a new one.
- The boundary section's disclaimer against #311/#323 (`.circ` is CAP-16's, this is CAP-29's) is correct and consistent with both parent issues (#513, #556) on inspection.
- The `AC-4`/`AC-5` cross-references to CAP-29 AC-5/AC-4 are internally consistent — I checked both directions against #513's text and they match; no citation drift.

## Verdict rationale

The core idea is legitimate, well-bounded against its siblings, and the delay-honesty motivation is real (grounded in CircuitVerse's own bug tracker, not invented). But this issue as written could be "completed" against a single toy project with a hand-picked JSON library and pass every stated AC while leaving the two things that actually matter — correctness on real course material and honest hardening — unverified. Combined with an entirely unbuilt prerequisite chain and an unaddressed fidelity-vs-no-rewrite conflict on subcircuit connectivity, this needs another pass before implementation: tighten AC-1/AC-2 to a corpus-and-equality standard like #323's, name a JSON dependency (or hardening approach) and its license/SBOM handling, pin a target CircuitVerse schema version, and state the policy on reproducing a known-buggy source construct.
