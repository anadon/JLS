# Issue #775: TASK-C551-2: the gallery is a published page linked from the README and linking back to install, readable in both browser themes
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

#775 is TASK-C551-2, the publication half of FEAT-C27-4 (#551): take TASK-C551-1's (#773) scripted SVG renders and captions and publish them as a linked, install-adjacent gallery page. The task decomposition and scope fencing (vs CAP-35/#519's hosted-manual scope) are genuinely clean. But two of its four acceptance criteria have real specification gaps once checked against the codebase: the dark-theme requirement (AC-3) is only partially achievable at this task's layer because the upstream render mechanism bakes an unthemed white background into the SVG bytes themselves, and the dead-link check (AC-2) has no design decision behind it and no analog anywhere in this project's existing (static, hermetic) test suite. There is also an unflagged overlap with #545 over who edits the README's link section.

## Findings, most severe first

**1. AC-3's "renders acceptably in both light and dark browser themes" assumes a property the upstream render mechanism does not provide, and #775 does not control that mechanism.**
Quoted: "3. The page renders acceptably in both light and dark browser themes, or ships a single theme deliberately and says so on the page." Confirmed in `src/jls/edit/CircuitRenderer.java` lines 314-324: SVG export explicitly fills an opaque white background into the document itself — `svg.setColor(Color.white); svg.fill(rect);` — before drawing circuit elements, with no theme parameter or alternate palette anywhere in the export path (`SvgExportTest.java` pins this as the export's exact behavior). That background is baked into the SVG bytes TASK-C551-1 (#773) hands off unmodified (per #773's own scope, and #775's `ordering_after` takes #773's output as a given, not something #775 can change). So "dark theme" support is achievable only for the page chrome around each tile, never for the tiles themselves — every circuit will always render as a light rectangle regardless of page theme. The AC's escape hatch ("or ships a single theme... and says so") makes this gameable: the actual, only-available outcome (light SVGs on a themed page, or a light-only page with one disclaimer sentence) trivially satisfies the AC as literally worded, while a naive reader would expect the AC to mean the *gallery experience* is dark-theme-native, which it structurally cannot be without #773/#551 changing the renderer — a change neither issue proposes. Recommend: reword AC-3 to state the real, achievable target explicitly (e.g., "each SVG tile sits on a light card; the surrounding page chrome supports both themes") rather than a blanket claim that invites either false compliance or scope creep into CircuitRenderer.

**2. AC-2's dead-link check has no design decision behind it and no precedent in this project's test suite.**
Quoted: "2. The README links to the gallery and the gallery links back to install instructions; a check fails when either link is dead." The Outcome section leaves the publish target open ("published via the repository or GitHub Pages"). `test/jls/HelpTopicsTest.java` (line 42: "Issue #70 extended this into a full link checker") is this project's only existing link-checking discipline, and it resolves links statically against files on the classpath inside the jar — it has no mechanism for, and no precedent for, checking a link into a page hosted outside the repository (GitHub Pages) or checking a live external URL from CI. If the gallery ends up on GitHub Pages, "a check fails when either link is dead" means either a new network-dependent CI job (unprecedented in an otherwise fully hermetic, headless-safe test suite per `ARCHITECTURE.md`'s threading/CI notes) or the AC silently gets satisfied by a weaker static check that doesn't actually verify the published, live link. Recommend: pick the publish target now (in-repo static file keeps the check a same-repo relative-path test, consistent with the `HelpTopicsTest`/README-drift-check pattern the project already uses) rather than leaving "repository or GitHub Pages" open with a check requirement that only works cleanly for one of the two options.

**3. Undeclared overlap with #545 (FEAT-C27-1) over who edits the README's gallery link.**
#775 AC-2 states flatly "The README links to the gallery," implying #775 performs that edit. But #545 (the README shop-window feature) says in its boundary notes: "links to the FEAT-C27-4 gallery page when it exists" — describing the same README edit as part of its own scope. Neither issue's `ordering_after` cites the other (#775 cites only `TASK-C551-1`), so there is no declared sequencing for which issue actually owns the README change, risking duplicate edits or a merge conflict when both land. Recommend #775 either add `ordering_after: [545]` (or vice versa) or explicitly narrow AC-2 to "the gallery links back to install instructions" and let #545 own the inbound README link, since #545 is the issue whose whole purpose is curating the README.

**4. The dependency chain #775 rests on does not exist in the codebase yet, so AC-1 is unverifiable today and the 0.5–1 mw estimate is contingent on an unscoped upstream contract.**
`grep -ri caption src/` finds no caption-metadata concept, and there is no `resources/samples/` directory — confirming #548 (curated Examples set + captions, still open) and #773/TASK-C551-1 (the render+caption generator, still open) have not landed. #775 AC-1 ("shows the SVG render and caption for every circuit in the Examples set, generated from TASK-C551-1's output rather than hand-assembled") cannot be checked against anything real yet, and the band_mw estimate assumes a stable, already-known output shape from #773 that has not been built. This is normal for staged backlog work and the `ordering_after` sequencing is correct, but it means #775 cannot be estimated with real confidence until #773 actually ships and its output format is known — worth a note rather than a blocker.

**5. AC-4's forward reference to CAP-32 (#516) creates an implicit future-maintenance obligation with no owning follow-up issue.**
Quoted: "When CAP-32 (#516) lands a browser runner, entries link to it; until then no entry implies one exists." #516 is a capstone (band_mw 3-6) whose own feasibility spike is unresolved — the companion review of #573 in this same repo notes "#572 is still open, no go/no-go comment exists." Nothing in #775, #551, or #516 files a task for "revisit the gallery and add browser-runner links once #516 ships." Low severity since it's easy to pick up later, but it is a gap in the otherwise careful `task_id`/`ordering_after` traceability this project practices elsewhere (e.g., #773, #545, #548 all cite concrete prerequisite issue numbers).

## What's solid

- The CAP-35 scope fence ("must not grow into the hosted-manual scope CAP-35 owns") is accurate and consistent with #519's own boundary note that CAP-27/gallery-type work owns "first ten minutes" surfaces while CAP-35 owns the documentation system.
- `ordering_after: [TASK-C551-1]` is the one prerequisite that actually matters for this task and is correctly identified — #775 does not try to duplicate #773's rendering or caption work.
- The technical foundation is real: `-i out.svg` batch export exists and is tested (`src/jls/JLSStart.java` lines 765, 821, 1038; `test/jls/SvgExportTest.java`, `test/jls/CliImageExportTest.java`), so the premise that a gallery can be built from shipped export machinery is accurate, not aspirational.
- Scope is appropriately narrow ("a single page") and the issue does not try to re-litigate #773's generation concerns or #516's browser-runner concerns — good discipline about staying in its own lane.

## Recommendation

Before scheduling: (a) reword AC-3 to name the achievable dark-theme target given CircuitRenderer's hardcoded white SVG background, rather than a blanket "acceptable in both themes" claim; (b) pick the publish target (in-repo vs GitHub Pages) so AC-2's link check is actually implementable with a mechanism consistent with `HelpTopicsTest`'s static-check pattern; (c) resolve the README-edit ownership overlap with #545 via explicit sequencing or a narrower AC-2.
