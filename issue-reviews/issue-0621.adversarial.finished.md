# Issue #621: TASK-C559-1: a .cv project parses as untrusted JSON into an in-memory CircuitVerse model, bounded in depth and size
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what's being proposed

The first of five tasks under FEAT-C29-3 (#559, CircuitVerse `.cv` importer): parse a `.cv` project's plain JSON into an in-memory model, treating it as hostile input from byte one — bounded depth/size, no filesystem/network reachability from document content, loud rejection on malformed/truncated input, no partial model ever escapes. Element mapping (#622), hierarchy rebuild (#624), delay-honesty (#626) and atomic-import acceptance (#628) are explicitly deferred to sibling tasks. `band_mw: "1"` (one week).

## Findings, most severe first

**1. (High) The one-week budget doesn't price acquiring a JSON-parsing capability, and this is a known gap, not a new one.** `pom.xml` has no JSON dependency — confirmed by grep, only `org.tukaani:xz`, `org.jfree.svg`, flatlaf, jspecify, plus test deps. The sibling review at `issue-reviews/issue-0559.adversarial.md` (finding 1) already flagged this for the parent feature and it was never addressed here: whoever picks up #621 must first choose a JSON library (or hand-roll a bounded streaming parser) and, given this project's SBOM/attestation/CycloneDX discipline (README "License and provenance"), get it through license and provenance review. That alone is plausibly most of a week before any CircuitVerse-specific parsing logic is written. AC-1 through AC-3 are stated as if the parsing substrate already exists.

**2. (High) "Duplicate keys" as a required attack-vector test presupposes parser behavior most JSON libraries don't provide by default.** AC-1: "one test per attack vector — deep nesting, oversized document, duplicate keys, unexpected types." Standard JSON parsing (Jackson `JsonNode`, Gson `JsonObject`, `org.json`) silently last-value-wins on duplicate object keys unless a non-default strict mode is explicitly enabled (e.g. Jackson's `DeserializationFeature.FAIL_ON_READING_DUP_TREE_KEY`, not on by default) or a custom streaming parser is written. The issue treats duplicate-key rejection as a given test to write, not a design decision with library-selection consequences — it silently constrains finding 1's unmade library choice to one that supports (or can be coerced into) duplicate-key detection, without saying so.

**3. (High) AC-1's bounds are unquantified, making the criterion gameable in both directions.** "Depth and size bounds are enforced with a named limit in the diagnostic" names no numbers. An implementer can satisfy the letter of AC-1 with arbitrarily conservative bounds (e.g. depth 10, 1 MB) that pass every self-authored attack-vector test while rejecting real course-scale CircuitVerse projects with legitimately nested subcircuits — and nothing in #621 or #559 requires calibrating against a real corpus the way #323 (`.circ`, cited as this capstone's own precedent) requires a corpus-based net-count equality check before the estimate is trusted. Conversely, bounds calibrated loosely enough to admit a real project could still admit a crafted bomb. Nothing here pins the limits to measured real-world `.cv` sizes/depths.

**4. (Medium-High) AC-4 makes a forward promise this task cannot itself verify.** "The parsed model preserves CircuitVerse's per-circuit structure and inter-circuit references, so TASK-C559-3 has a hierarchy to rebuild" — but #621's own acceptance criteria contain no test asserting the model's hierarchy/reference shape is queryable or structurally correct; "preserves" is asserted, not pinned by anything in this issue. #624 (TASK-C559-3) is the one that will discover, after the fact, whether the model #621 shipped is actually adequate. A parser that stuffs everything into a generic `Map<String,Object>` tree technically "preserves" the data and could pass AC-1–AC-3 while leaving #624 to redesign the model from scratch — the coupling is real but untested on this side of the boundary.

**5. (Medium) The entry point for `.cv` files is unspecified, which matters for a one-week estimate.** ARCHITECTURE.md's load pipeline (`FileAbstractor.openCircuit` → XZ/zip/plain-text sniffing → `Circuit.load`) is `.jls`-specific; nothing in #621 says whether `.cv` parsing is wired into the editor's Open dialog, a new CLI flag, or is purely a library-level class exercised only by tests until #622/#628 land. "Reads as hostile input from the first byte" implies a real ingestion path exists, but the issue never names it, and the existing `LoadError` taxonomy (`src/jls/LoadError.java:38-66`: `IO_ERROR`, `NOT_A_CIRCUIT`, `MALFORMED`, `LIMIT_EXCEEDED`, …) is never mentioned as the target for AC-3's "refuses loudly," so it's unclear whether this task reuses that machinery or invents a parallel one.

**6. (Medium) `ordering_after: [314]` looks inherited rather than derived for this specific task.** #314 (FEAT-002) is open and makes the *`.jls` attribute-dispatch loader* loud on unmatched attributes — a different code path (`Element.setValue`, `Circuit.java`'s five loader arms) than a from-scratch JSON parser. AC-1's "named limit in the diagnostic" need is already satisfiable today via the existing `LoadError` category/detail/hint fields (ARCHITECTURE.md "Error-reporting contracts"), which predate and don't depend on #314. If #621 doesn't actually need #314 to land first, the ordering dependency blocks scheduling for no real reason; if it does need it, the issue doesn't say why.

**7. Solid, no rework needed:**
- AC-2 ("no code path from document content reaches the filesystem or the network; a fixture containing path-like and URL-like strings proves it") is concrete, falsifiable, and mirrors the proven #38/#323 hostile-input pattern.
- AC-3's "malformed or truncated `.cv` refuses loudly and returns no partial model" is a clean, testable no-partial-state discipline consistent with the rest of the codebase's load contract.
- The boundary notes cleanly hand off element mapping, hierarchy, delay-honesty and atomic-import to #622/#624/#626/#628 — I checked all four against #621's text and the scope split is consistent and non-overlapping.
- Scoping this task to "parsing only" (no element semantics, no filesystem writes) is the right cut for a one-week task in isolation from finding 4's concern about verifying the cut is *sufficient*.

## Verdict rationale

The scope boundary against its sibling tasks is clean, and AC-2/AC-3 are genuinely well-formed. But the one-week estimate assumes a JSON-parsing capability, a duplicate-key-detection strategy, and a defined ingestion entry point that none of #621, #559, or `pom.xml` currently provide or price, and AC-1's bounds are unquantified enough to be satisfied by numbers with no relationship to real CircuitVerse projects. Needs another pass: name the JSON library (and its license/SBOM path), state numeric-or-corpus-derived depth/size bounds, confirm duplicate-key detection is achievable with the chosen library, name the file-open entry point and whether it reuses `LoadError`, and verify `ordering_after: [314]` is actually load-bearing for this task rather than copied from the parent feature.
