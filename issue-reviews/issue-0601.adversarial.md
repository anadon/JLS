# Issue #601: TASK-C332-2: loading a part set holds one part resident at a time, and the peak-memory bound is a recorded measurement rather than a claim
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what's being asked

Rewrite `Circuit.finishLoad` (`src/jls/Circuit.java:1300-1422`) so that, given a part-file set produced by TASK-C332-1 (#600), only one part is resident at a time, with peak resident memory bounded by `max_i M(D_i) + M(B) + c`, measured and recorded rather than asserted; a single-file design must still round-trip byte-identically; and the `O(n)` `LinkedList.remove` at line 1369 must not reappear on the new path.

## What checks out

- **Line anchors are accurate.** `finishLoad` runs 1300-1422 as claimed; the wire-end list is declared at 1345 (`LinkedList<WireEnd> ends`); the partition `while` loop starts at 1355 (issue cites 1354-1355, the comment+loop pair); `ends.remove(vend)` is exactly at 1369. Verified by direct read, not by trusting the issue.
- **AC-3 and AC-4 are concrete and testable as stated**: byte-identical single-file save/load is a mechanical regression check, and "grep/measure that this specific `LinkedList.remove` pattern doesn't reappear" is a clean, unambiguous guard.
- **Scope discipline is good.** The task doesn't reach into net-identity naming (#602), the uncuttable-cycle refusal (#604), or the equivalence harness (#606) — those stay in their own filed siblings. No creep observed.
- **The task is honest about its own dependency**: it states plainly it needs #600 for something to stream and #353 for the quadratic fixup to already be fixed, rather than silently assuming either.

## Findings, most severe first

**1. (High) The memory bound conflates transient load-time peak with steady-state simulation memory, and the issue never reconciles the two — the AC could be satisfied while the actual capability goal is not achieved.**
`finishLoad` today permanently populates `Circuit.elements` (lines 1341, 1350) with every element from every part, because that list is what `jls.sim.Simulator` iterates for the life of the circuit (ARCHITECTURE.md: "Circuit — the circuit model: element list..."; simulation is a single-thread, single-process event-queue interpreter per the recorded decision on #221, and cross-partition execution is explicitly deferred to #333/FEAT-056, which this issue's own boundary notes exclude: "Concurrency across parts is FEAT-056 (#333). Elaboration here is sequential over parts."). Given that, after streaming load finishes, either (a) the assembled `Circuit` still holds all N parts' elements in memory for simulation to work at all — in which case the "peak resident bytes... bounded by the largest part + B + c" claim is true only for a transient window inside `finishLoad` and buys nothing for the actual reason #332 wants this ("a design too large for one machine" — abstract of #332), since the steady state a moment after load is still O(sum of parts); or (b) the assembled circuit genuinely does *not* retain the full element set, in which case local single-process simulation of the whole design is no longer possible with the current `Simulator`, and the issue has silently taken on part of #333's scope without saying so. Either reading is a real problem, and #601 picks neither explicitly. *Recommendation*: AC-1 should state whether the bound is claimed only for the `finishLoad` call's transient peak (and, if so, say plainly that steady-state memory after load is *not* bounded, so reviewers don't over-read the capability), or else scope in what post-load representation is kept and how it interacts with `Simulator`.

**2. (High) `M(B)` is unconstrained, which is a hole a gameable implementation can drive through.**
AC-2 bars "a convenience index... over the whole design," and cites #332 invariant 3 verbatim: the specific failure mode is a structure whose size is `Θ(Σ_i |D_i|)`. But the bound in AC-1 already budgets an unbounded, unmeasured `M(B)` (the boundary description) as a flat additive term. Nothing in AC-1 or AC-2 requires `M(B)` itself to be bounded independent of `N`. A real partitioned design's boundary net count plausibly grows with the number of cuts (e.g., a shared bus or clock net touched by every part), so an implementation could push whatever indexing it needs into the boundary description — which is not literally "proportional to the sum of all part sizes" and so would not trip AC-2's stated test — while still reintroducing `O(N)`-ish growth in practice. *Recommendation*: either give `M(B)` its own declared bound (e.g., proportional to boundary-net count, not to `N` × anything), or have the test sweep `N` while holding boundary topology fixed and assert peak memory is flat, closing the loophole regardless of where the offending structure is hidden.

**3. (Medium) AC-1's measurement methodology and thresholds are entirely unspecified, unlike the sibling feature this one leans on.** "Measured by an instrumented load test whose recorded number goes in the PR" names no instrument (heap histogram, `-Xss`/RSS sampling, `Instrumentation.getObjectSize`, JMH), no part count or part-size fixture, and no numeric value for the constant `c`. Contrast #353 (FEAT-005), which this issue's own boundary notes depend on, which commits to a concrete "50,000-cycle run... within a declared wall-clock and peak-heap budget." Without a fixture and a tolerance, "measured, not asserted" is satisfiable by picking a fixture small enough that JVM/GC noise swamps any real difference between streaming and non-streaming code, and the PR reviewer has no baseline to catch it. *Recommendation*: pin `N`, `M(D_i)`, and `M(B)` in a committed fixture, specify the measurement tool, and require the test to fail on the *current* (fully materializing) code, the same discipline #332's own "ABSENT at 2d0ca9d" evidence entries use elsewhere.

**4. (Medium) The deepest real dependency is unfiled and not surfaced here.** #600 (TASK-C332-1)'s own AC-4 requires the part-set container to be "section-framed and carr[y] must-understand semantics from #319" (FEAT-013). #319 is itself a large open feature whose three child tasks (TASK-0033/0034/0071) are all "not filed," and #319 is `blocked_by: [334]`. So the artifact format #601 streams over does not yet exist even in design, several links up the chain, and none of that shows up in #601's "Boundary notes" (which name only #600 and #353). This isn't a contradiction inside #601, but it is a materially incomplete picture of readiness: starting #601's implementation design before #319/#600 settle the on-disk part-set shape risks rework. *Recommendation*: note the transitive dependency on #319 explicitly, even if only as a "rides along" caveat, so a scheduler doesn't treat #601 as ready-to-start once #600 alone lands.

**5. (Low) AC-2's verification instruction — "the test checks for it rather than trusting review" — doesn't say what the test actually asserts beyond a scaling curve.** Reliable assertions about `Θ(·)` growth from a JUnit-style heap measurement are inherently GC/JIT-sensitive and a common source of CI flakiness; ARCHITECTURE.md's headless, `mvn verify`-green discipline gives no precedent for this kind of test. Worth a stated tolerance/retry policy up front rather than discovering it as CI flakes.

## Verdict rationale

The issue is well-anchored in the actual codebase and consistent with its parent (#332) and sibling (#600, #353) issues — no internal contradictions, no scope creep, accurate citations. But finding 1 (the load-time-vs-steady-state ambiguity) goes to whether the acceptance criterion, as literally written, measures anything that matters for the stated goal, and finding 2 (unbounded `M(B)`) is a concrete way to pass AC-1/AC-2 while reintroducing the exact defect #332 invariant 3 forbids. Both should be resolved in the issue text before implementation starts, hence **needs-rework** rather than sound-with-concerns.
