# Issue #624: TASK-C559-3: CircuitVerse subcircuits arrive as JLS subcircuits with hierarchy intact, and an unmappable one refuses instead of flattening
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what's being asked

Task 3 of 5 under FEAT-C29-3 (#559, CircuitVerse `.cv` importer, itself CAP-29's third pillar). Given a parsed CircuitVerse model (TASK-C559-1, #621) and an element-mapping table (TASK-C559-2, #622), this task rebuilds subcircuit hierarchy as nested JLS `SubCircuit` elements: preserve nesting (AC-1), preserve port order/direction or refuse (AC-2), refuse by name rather than flatten on an unmappable construct (AC-3), and dedupe instances to one shared definition rather than one copy per instance (AC-4).

## Findings, most severe first

**1. AC-4 requires a data model that does not exist and is not in this task's declared dependency chain — and its own escape hatch collides with a sibling task's acceptance criterion.** AC-4 reads: "Instances of the same source subcircuit reference one imported definition, not one copy per instance." I read `src/jls/elem/SubCircuit.java:26`: `private @Nullable Circuit subCircuit;` — each `SubCircuit` element owns a private, independently-deep-copied `Circuit`. `copy()` (`SubCircuit.java:332-338`) builds a **fresh** `Circuit` object graph per instance, and `save()` (`SubCircuit.java:282-289`, specifically line 287 `getSubCircuit().save(output)`) writes the full definition body once *per instance*. This is exactly the gap #357 (FEAT-017, "one subcircuit definition, N instances that reference it") exists to close — and #357 is **open, blocked_by three other open features (#318, #319, #340), none of which have landed**, with its own author estimating the true cost at 25-36 maintainer-weeks against a 4-week task sum. #624's own "Boundary notes" acknowledges this directly: "the definition/instance model JLS needs is #357 ... this task consumes it rather than rebuilding it, and refuses by name where #357 has not landed." That is a reasonable-sounding escape hatch in isolation, but it is not reasonable against sibling task TASK-C559-5 (#628), whose AC-1 demands "one real published `.cv` project imports with **zero unexplained losses**" and whose AC-2 demands a whole-project-or-nothing atomic import — no allowance for "refuses because #357 hasn't landed." Any real, non-trivial CircuitVerse project that reuses one subcircuit more than once (an extremely common pattern — a ripple-carry adder built from N instances of one full-adder subcircuit is closer to the median CircuitVerse project than the exception) will hit AC-4's refusal path under #624's own stated fallback, which then makes #628 unsatisfiable by any such project. **Recommendation:** either (a) add #357 to `ordering_after` as a hard blocking dependency and accept that this task cannot close before a 25-36 mw feature does, or (b) rewrite AC-4 now to something achievable without #357 — e.g. "repeated instances import as independent copies (JLS's current model); this is a named, reported limitation, not a refusal" — and drop the refuse-on-#357-absence framing so it stops contradicting #628.

**2. The whole task is downstream of two other unlanded, unfiled-consequence tasks, and one of *those* leans on a third large unrelated feature.** `ordering_after` names only TASK-C559-2 (#622), itself open with zero implementation. #622 in turn is `ordering_after: [TASK-C559-1, 323]` — #621 (also open, no parser exists: `grep -rn "CircuitVerse" src/` and `grep -rln "\.cv\b" src/` both return nothing in this checkout) and #323 (FEAT-025, the *Logisim-Evolution* `.circ` importer — an entirely different competitor format, itself blocked_by #314/#349, neither landed, estimated 6-12 mw against a 4-week task sum in its own words). None of TASK-C559-1, TASK-C559-2, or FEAT-025 exist in `src/` today. This task is being reviewed three layers above bedrock that hasn't been poured. That alone isn't disqualifying (tasks are routinely filed ahead of their prerequisites in this tracker, as the #625 review from this same fleet already noted for a different issue), but it means nothing here can be built or meaningfully tested yet, and the "written table" TASK-C559-2 promises (which AC-1's "level by level" comparison and AC-3's refusal-by-name both implicitly assume exists) is speculative. **Recommendation:** label this blocked/not-yet-actionable, or state explicitly that reviewing it now is planning-only.

**3. "Unmappable subcircuit construct" is never defined, here or in either parent.** AC-3 says refusal happens "by name" for "a subcircuit construct JLS cannot express," but no concrete example is given — not in #624, not in #559 (FEAT-C29-3), not in #621/#622. CircuitVerse subcircuits can carry parametrized bit-widths, "quick" ad hoc combinational subcircuits, and — per TASK-C559-4's own title — queue-priority delay semantics that are subcircuit-adjacent. Without a concrete list, "a fixture proves the refusal path is live" (part of AC-3) can be satisfied by inventing *any* trivially-refusable dummy construct (e.g., a subcircuit referencing a nonexistent element ID) that never corresponds to anything a real CircuitVerse export produces — passing the letter of AC-3 while leaving the actual unmappable constructs instructors will hit unhandled and unreported. **Recommendation:** name at least the constructs TASK-C559-2's forthcoming element table is expected to reject, and require the refusal fixture to be drawn from that set, not an arbitrary invented one.

**4. No cycle/self-reference guard is named, and none exists in the current codebase to inherit.** AC-1 talks about "multi-level" nesting but not about malformed or adversarial nesting — a subcircuit graph where A instantiates B which (directly or transitively) instantiates A. I checked for existing cycle handling: `grep -n "ecursi|ycle|ircular" src/jls/elem/SubCircuit.java src/jls/Circuit.java` finds only unrelated hits (tri-state propagation recursion guard, an unrelated recursive save call) — there is no subcircuit-hierarchy cycle detector to inherit. TASK-C559-1's AC-1 bounds *JSON nesting depth* as an attack vector, but a cyclic subcircuit-ID reference graph can be JSON-flat (a list of circuit definitions cross-referencing each other by ID) and still recurse without bound when TASK-C559-3 walks it to rebuild `SubCircuit` objects — `SubCircuit.copy()`'s "build a fresh object graph" pattern (finding 1) is exactly the kind of code that would stack-overflow on such input. Given #38's untrusted-input standard is explicitly invoked elsewhere in this task family (#621 AC-1/AC-2), a `.cv` file is adversary-controllable content and this is a real, unaddressed attack surface for *this* task specifically (hierarchy reconstruction), not just the parser. **Recommendation:** add an explicit AC (or amend AC-3) requiring cycle detection in the subcircuit reference graph with a named diagnostic and a fixture, distinct from TASK-C559-1's JSON-depth bound.

**5. AC-2's "same order" is asserted against a representation that doesn't obviously preserve order.** `SubCircuit` stores its port correspondence as `Map<Input,InputPin> inmap` and `Map<OutputPin,Output> outmap` (`SubCircuit.java:32-35`) — `HashMap`, not a `LinkedHashMap` or list — so nothing in the type itself guarantees or records a port order; whatever "order" AC-2 means to compare presumably comes from the pins' visual/positional order on the subcircuit boundary, not from these maps. The issue doesn't say where "order" is sourced from on either the CircuitVerse side or the JLS side, so the comparison AC-2 demands ("in the same order and direction") isn't grounded in a concrete, checkable representation. **Recommendation:** state which ordering is authoritative on each side (e.g., CircuitVerse's port-array index vs. JLS's pin y-coordinate) before this is buildable.

**6. Cost band absent from this task; feasibility rests entirely on the parent's 3-5 mw estimate for all five tasks combined.** Given findings 1 and 2 — a genuine (if partial) dependency on a 25-36 mw feature, plus two unlanded upstream tasks — the parent feature's kill criterion (KC-29-1, 1.5× the 3-5 mw band) reads optimistic for this specific task once AC-4 is taken at face value rather than deflated by the refusal escape hatch.

## What's solid

- **AC-3's fixture requirement** ("a fixture proves the refusal path is live") is good discipline in principle — it guards against a refusal path that exists in name only, never exercised. It just needs grounding in a real construct (finding 3).
- **The "boundary notes" pointer to #357 as the owning feature for the definition/instance model** is the right instinct — not trying to re-solve #357 inside this task — even though the specific fallback it proposes creates the conflict in finding 1.
- **AC-1's cross-reference to FEAT-C29-3 AC-2** for the level-by-level hierarchy comparison is a real, traceable link (verified against #559's body) rather than a dangling citation.

## Bottom line

The task's structure is sound — it correctly scopes hierarchy reconstruction as distinct from element mapping (#622) and delay-semantics honesty (#626) — but AC-4 commits to a capability (shared subcircuit definitions) that today's codebase and dependency graph cannot deliver, papers over that with a refusal fallback that directly undercuts sibling task #628's "zero unexplained losses on a real project" bar, and leaves both "unmappable construct" and "port order" undefined against concrete representations. Needs AC-4 reconciled with #357's actual state (or #357 added as a hard blocker) and a named example set before this is buildable.
