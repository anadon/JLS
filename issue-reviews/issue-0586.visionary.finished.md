# Issue #586: FEAT-C35-3: every screenshot in the docs is a build product — the headless-sway rig captures them per release, so no image can outlive the UI it claims to show
- Lens: visionary
- Date: 2026-08-08
- Reviewer: Claude Opus 5
- Verdict: endorse-with-reframing

## What this issue is really for

The end is not "screenshots are build products." The end is **no image in JLS's
documentation can make a false claim about the program**. Regeneration-per-release
is one mechanism for that; the issue has fused the goal to that single mechanism
and then inherited a display apparatus, a fail-open CI lane, a pinned JBR
download, and a pixel-tolerance calibration problem as the price. The goal is
right and is squarely CAP-35's best trait (#519's own framing: JLS's *content*
discipline is already strong — `HelpTopicsTest`, `HotkeysHelpAccuracyTest`,
`MenuAcceleratorPolicyTest`, `ElementRegistryTest` — while its *delivery* lags).
The route cuts along the wrong seam.

## Ground truth: what the corpus actually is today

I enumerated every image the docs reference:

- **README.md: zero screenshots.** One badge (`api.scorecard.dev`).
- **`docs/**.md`: zero screenshots.** Two badge references in
  `docs/standards-adoption/02-openssf-badge.md`.
- **In-jar help (`resources/help/`, 95 files): exactly one screenshot** —
  `resources/help/elements/keypad.jpg`. Every other `<img>` (10 of them) is a
  **toolbar icon** (`const.gif`, `bind.gif`, `up.gif`, …) — the *same asset file
  the toolbar loads*, not a picture of the UI.
- **The hosted manual does not exist** (CAP-35 PF-2, unfiled).

So AC-2's check ("no screenshot referenced by README, the hosted manual or the
in-jar help is a hand-committed file") governs a present corpus of **one JPEG**,
plus a future corpus that PF-1/PF-2 have not created yet. Worse, applied
literally it fails the build on `resources/help/images/const.gif` — a toolbar
icon that can never have a manifest entry, because it is not a screenshot at all.
The missing concept in this issue is a **taxonomy of images**, and once you have
that taxonomy most of the apparatus evaporates.

## Alternative framing A: classify by *what makes the image rot*, then pick the
cheapest non-rotting representation per class

**Class 1 — circuit content** (a drawn circuit, a trace, an element in context).
This is the bulk of what a logic simulator's docs, README and store listings
actually show. JLS **already renders this headlessly and deterministically**:
`jls -i out.svg circuit.jls` → `src/jls/edit/CircuitRenderer.java:314-358`
(JFreeSVG path), pinned by `test/jls/SvgExportTest.java:78`
(`assertArrayEquals` on two consecutive exports — **byte-identical**) and
`test/jls/ElementDrawSmokeTest` (`everyElementDrawsOnTheSvgExportPath`). No
compositor, no JBR, no `grim`, no ImageMagick, no tolerance number. The output is
text, so it **diffs in git** and a stale render is visible in review. README
already sells this format as "the right format for slides, lab reports and hosted
docs" (README.md:134-136). Fixtures already exist —
`test/fixtures/riscv-sum1to10.jls`, `riscv/gui/cpu.jls`.
For this class, "the image cannot outlive the UI" is true **by construction**:
the image *is* the program's renderer output, regenerated by a Maven-reachable
loop of maybe thirty lines.

**Class 2 — UI assets** (toolbar gifs). Already non-rotting for the same reason,
and already link-checked by `test/jls/HelpTopicsTest.java` (issue #70: every
inline `href`/`src` must resolve case-sensitively against the jar's real entry
names). Zero work. It needs *naming* as a class purely so AC-2 does not try to
govern it.

**Class 3 — chrome screenshots** (a full window: menus, palette, trace pane).
The only class that genuinely needs a live toolkit on a compositor. Its real
consumers are the three store listings (#579/#580/#581 AC-4: "at least three
screenshots") and one or two README hero shots. That is **roughly 3–6 images**,
not "every screenshot in the docs."

**Class 4 — motion.** #545 AC-1 requires "an animated GIF of drawing-and-
simulating." A boot-and-screenshot rig cannot produce this at all; it needs #91's
`wtype` interaction scripting plus a recorder (`wf-recorder`), neither of which
this issue names. AC-5 promises to satisfy #545 "by name" and, as written,
**cannot**.

The prize: the expensive apparatus shrinks to Class 3, and the largest class
becomes a deterministic build step the project has already shipped and tested.

## Alternative framing B: make the *alarm* the deliverable, not the *pipeline*

Even for Class 3, "regenerate per release" is the wrong primitive for the stated
fear. The fear is an image *silently* outliving its UI. The cheap, exact answer
is a **staleness fingerprint**: each chrome screenshot's manifest entry records
the enumerable UI surfaces it depicts — palette entry set (`src/jls/edit/Palette.java`,
`PaletteEntry.java`), menu accelerator table (`MenuAcceleratorPolicyTest`), hotkey
table (`HotkeysHelpAccuracyTest`), element registry (`ElementRegistryTest`),
`JLSStart.FLAGS`. CI hashes those model surfaces and fails when a fingerprint
moves without a recapture. This gives AC-3's exact semantics — "a manifest entry
naming a window, pane or circuit that no longer exists fails loudly" — as a
**headless model assertion that needs no rig at all**, and it runs on every push
rather than once per release. The capture itself then becomes an ordinary release
chore behind `scripts/`, and CI never depends on the JBR download or the
compositor to keep documentation honest.

This is also the *same discipline CAP-35 PF-4 is already committed to*
(docu-tests asserting docs against the registry). Framing B makes #586 a
contributor to that ratchet rather than a fourth, differently-shaped apparatus.

## Where AC-4 is a category error

AC-4 asks for a pixel tolerance "in the idiom #101 uses for `PIXEL_DIFF_MIN`."
That idiom does not transfer. Reading `scripts/wayland-rig.sh:342-362`,
`PIXEL_DIFF_MIN` is a **liveness** statistic — *how many pixels differ from an
empty desktop* — answering "did anything render at all?" #586 needs a
**stability** statistic — *how many pixels differ between two runs of the same
input* — answering "is the capture reproducible?" Different question, different
derivation, different failure direction (liveness wants a floor; stability wants a
ceiling). Borrowing the idiom would produce a number that looks calibrated and
gates nothing.

More fundamentally: a pixel tolerance is a fudge factor covering nondeterminism
you have chosen not to eliminate — fontconfig package drift, JBR build drift,
pixman rasterization. The project has **already proved** where determinism lives:
the drawing path is byte-identical (`SvgExportTest`), the compositing path is not.
I am **explicitly disregarding AC-4 as written**. The replacement: Class 1 images
are asserted byte-identical with *no tolerance*; Class 3 images are not gated on
pixels at all — they are gated on the Framing-B model fingerprint, plus a
non-blank floor reused from #101 so a blank frame cannot pass.

## Alignment with the project's arc

**Sequencing pulls against CAP-35.** `ordering_after: []` claims independence,
but AC-2 names "the hosted manual" as a governed consumer and AC-5 names CAP-27
surfaces. The hosted manual is PF-2, unbuilt; the single-source pipeline is PF-1,
unbuilt; #545 explicitly states "hand-captured images here are acceptable until
CAP-35 lands." So #586 would build governance for images that do not exist, over
targets that do not exist, while #545 is licensed to hand-commit in the interim —
guaranteeing a period where the check either fails or has nothing to check.

**Base rate argues against per-release automation.** JLS's editor
(`SimpleEditor`, ~4k lines) has been visually stable for a decade; the one
scheduled event that will invalidate every raster shot at once is the dark-mode /
hardcoded-color work (#76, ~126 audited call sites per ARCHITECTURE.md:284).
Per-release capture automation for a once-in-years event is over-engineering; a
loud staleness alarm for exactly that event is precisely right — which is
Framing B again.

## What I would keep

- The outcome sentence, verbatim. It is correct and worth owning.
- An in-tree manifest — but for **Class 3 only** (3–6 chrome shots), plus a
  declared Class-1 fixture list.
- Reuse of #101's rig as a *consumer*, and the refusal to inherit its two
  weaknesses. Both boundary notes are right and should survive any reframing.
- AC-3, upgraded: it becomes cheaper *and* stronger as a model assertion.

## Restated acceptance criteria (proposed)

- AC-1′: one `mvn`-reachable command regenerates all **Class 1** images from
  committed `.jls` fixtures as SVG; the release procedure additionally runs the
  Class-3 capture script.
- AC-2′: every image referenced by README, the in-jar help and (when it exists)
  the hosted manual is classified — generated / UI asset / captured-chrome — and
  an unclassified image fails. Extend `HelpTopicsTest`, do not build a second
  checker.
- AC-3′: a manifest entry naming a pane, palette entry, menu, hotkey or circuit
  fixture that no longer exists fails a **headless** test on every push.
- AC-4′: Class 1 is byte-identical across runs (no tolerance). Class 3 is gated
  on the AC-3′ fingerprint plus a non-blank floor; **no pixel-tolerance number is
  invented**, and the #101 `PIXEL_DIFF_MIN` and fail-open close-outs remain
  blockers only for the Class-3 lane.
- AC-5′: consumers named — #545's *still* images and #579/#580/#581 store
  listings draw from this set. #545's animated GIF is **out of scope and blocked
  on #91**; say so rather than implying coverage.

## Verdict

**endorse-with-reframing.** The goal is one of the most defensible in the
capstone set. The design cuts along the display stack when it should cut along
image provenance, and in doing so ignores that JLS already ships the
deterministic, headless, byte-identical rendering path that solves the majority
case outright. Reframed, this feature gets smaller, lands sooner, gates on every
push instead of every release, and stops depending on two known-broken things in
#101 and one unbuilt thing in #91.
