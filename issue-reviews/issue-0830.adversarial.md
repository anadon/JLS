## Findings, most severe first

### 1. (Critical) AC-2's edit target does not exist in the tree
The whole task is framed as replacing a sentence at `docs/parity-contract.md:469-477`, and AC-2 requires that file's "remains unverified" sentence be "replaced by the measured answer with the run IDs recorded." I checked: `docs/parity-contract.md` **does not exist anywhere in this repository** — confirmed with both `find /home/user/JLS -iname "parity-contract*"` (no hits) and `Glob docs/*.md` (29 files, none named `parity-contract.md`). The only places the string `parity-contract` appears in the actual tree are ~180 files under `issue-reviews/*.md` (other review artifacts quoting the same citation) plus `ARCHITECTURE.md`/`CHANGELOG.md`/etc. matching unrelated substrings — never a real `docs/` file with that name.
`#333`'s body cites the identical `docs/parity-contract.md:469-477` quote verbatim, so this isn't a typo local to #830 — it's a citation that has propagated through an entire family of issues without anyone having actually created the document. As written, AC-2 is unexecutable: there is no sentence at that path to replace. Before this task can be worked, someone must either (a) locate the real document under a different path/commit, (b) author `docs/parity-contract.md` from scratch as an in-scope prerequisite (not mentioned anywhere in this issue's scope or `ordering_after`), or (c) the issue must be corrected to point at wherever this claim actually lives. **Recommendation:** block this task on resolving the citation before any CI work starts; add an AC-0 that names the real source of the "remains unverified" sentence.

### 2. (High) The core premise — "nothing in the tree asserts... bit-identical across operating systems" — is already partially contradicted by existing tests
`test/jls/VcdExportGoldenTest.java` and `test/jls/BatchSimulationGoldenTest.java` pin simulation output "byte for byte" / "byte-exactly" against a single committed golden (see `docs/batch-interface.md:314-319`, and `BatchSimulationGoldenTest.java:361-364` doing a literal `assertEquals` against a fixed string). Neither test class carries `@DisabledOnOs`/`@EnabledOnOs`/`assumeTrue(os...)` guards (checked by grep — no hits), and both the Windows job (`ci.yml:143-224`, `mvn -B verify -Djacoco.skip=true -Djls.test.headless=false`) and the macOS job (`ci.yml:259+`, same full-suite `mvn -B verify`) run the entire test suite, not a Linux-only subset. That means these two golden fixtures are **already** implicitly asserting cross-platform byte-identity on every push/PR today — just not gated (both jobs are `continue-on-error: true`) and not framed as "the parity experiment." AC-1 proposes a brand-new job to do something structurally similar to what already silently runs. The issue doesn't acknowledge this overlap or explain why the existing golden-vs-committed-file comparison is insufficient evidence (e.g., it's not *pairwise* across all three OSes at once, and failures on the advisory legs may not be getting looked at) — that's a real distinction worth making, but the issue should make it explicitly rather than asserting "nothing in the tree asserts" a claim the tree partly contradicts already.

### 3. (Medium) AC-1's new gating job skips the project's own CI-promotion discipline
Every other cross-platform CI lane in this repo follows a documented "advisory → 20-consecutive-run burn-in → promote to required" discipline (see `#265`'s own body: "each following the #188/#101 advisory → 20-run → required promotion discipline so no stage can wedge CI"; both `windows` (`ci.yml:146`, job-level `continue-on-error: true`) and `macos` (`ci.yml:259+`, same) are *still advisory* today, with #265 Stage 3 — promoting even the plain headless build to required — explicitly unfiled/not landed. AC-1 says the new diff job should be "failing on any difference," full stop, with no mention of whether it starts advisory or required, and AC-4 only disclaims *promoting the platform lanes*, not the new diff job itself. A hard-failing check bolted directly onto two lanes the project has explicitly not yet trusted to gate on (because they're still accruing their own stability record) inherits their flakiness with no burn-in of its own. **Recommendation:** state explicitly that the new job starts `continue-on-error: true` and is subject to the same 20-run promotion rule before AC-1's "failing on any difference" becomes gating.

### 4. (Medium) Missing/failed upstream artifact is unhandled — and gameable
AC-1 doesn't say what happens when one platform's build step itself fails before producing output (routine today on the advisory Windows/macOS legs per their own `continue-on-error` framing). Three outcomes are all consistent with the letter of AC-1 and none is specified: (a) the diff job errors confusingly on a missing file, (b) it's coded to skip the comparison when an artifact is absent — which lets AC-1 report green while zero platforms were actually compared on a bad day, or (c) it treats "missing" as "differs" and reports a false determinism refutation, wrongly triggering AC-3's REPLAN. Since this is precisely the "gameable acceptance criteria" failure mode, it should be nailed down: e.g. "a missing artifact from any lane is itself a hard failure of this job, distinct from and reported separately from a byte diff."

### 5. (Medium) Success path leaves #333 permanently stale
AC-3 only requires posting a `REPLAN:` on `#333` in the *failure* branch (diff non-empty). If the experiment succeeds (bytes match), nothing in this issue requires updating `#333` itself — but `#333`'s own body quotes the exact "remains unverified" sentence verbatim in its Integration Criteria (§5, item 8) and in Open Question 3, as prose, not merely as a doc citation. Fixing `docs/parity-contract.md` per AC-2 does not touch `#333`'s own quoted text, which will keep asserting an assumption that has since been measured and settled. `#333`'s own machine block (`blocked_by: [318, 332, 348, 363]`) also never lists this task, and `#333`'s `planned_tasks` has no line item for the cross-platform experiment (it only appears under "Open Questions" #3) — so there is no REPLAN hook on #333's side for a successful #830 to resolve into, only for a failed one. Recommend adding an AC that on success, `#333`'s quoted assumption text is also updated (or a `STATUS:` comment posted) rather than leaving a stale, contradicted quote live on an open feature issue.

### 6. (Minor) "one committed circuit" is unspecified
AC-1 never says whether this is a new fixture or a reuse of an existing golden (e.g. `VcdExportGoldenTest`'s clocked-register fixture, `docs/batch-interface.md:311-319`). Given `#333`'s later planned "partition-count invariance suite" will need something structurally similar, leaving the choice open invites either duplicated fixture-building effort or an implementer picking a circuit too trivial to exercise the interesting nondeterminism sources (hash-order, `HashMap`/`HashSet` use noted in `BatchSimulator.java:25,34,37,202`). A concrete circuit name/path would tighten this.

### 7. (Minor) "first differing byte" across three pairwise diffs and two artifact kinds is underspecified
Three platforms means three pairs (Linux–Windows, Linux–macOS, Windows–macOS), each compared on two artifacts (watched output, VCD) — six diffs. AC-1 doesn't say how a report with multiple simultaneous mismatches should be summarized (first pair found, first artifact, or all six enumerated). Not a blocker, but worth pinning down so the "REFUTED" comment format in AC-3 is predictable rather than ad hoc per run.

## What's solid (checked, not just trusted)
- **AC-4's boundary is clean and correctly scoped.** It explicitly disclaims new runner classes, new toolchains, and required-check promotion, correctly deferring those to `#265`. No overlap or contradiction found there.
- **The two most obvious sources of cross-platform nondeterminism are already engineered around.** `Simulator.initSimulation` (`src/jls/sim/Simulator.java:189-196`) deliberately seeds from `circ.getElementsInStableOrder()` rather than a `HashSet`, with a comment citing exactly this class of bug (issue #181). The VCD writer omits `$date`/`$version` headers by design (`BatchSimulator.java:376,420-423`) and both the VCD writer (`docs/batch-interface.md:306`) and the watched-output printers (`Pin.java:288-292`, `Register.java:681-684`, using literal `"\n"` in `printf`, not `println`/`%n`) are already platform-independent on line endings — so the experiment is unlikely to trip on cosmetic OS artifacts unrelated to real determinism. I checked this rather than assuming it; it meaningfully de-risks the task technically, even though the process issues above remain.
- **The task correctly implements #333's own stated recommendation** (Open Question 3: "run it first, as a standalone change") rather than folding the experiment into #333 itself — the right shape of task.
