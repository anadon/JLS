# Issue #450: TASK-0055: the 74-series and DIP teaching set exists as licensed, provenance-carrying data on the classpath, with the electrical columns shipped inert
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

A transcription task (74-series/DIP part data → a schema TASK-0085/#400 will define) wrapped in a heavy evidence-and-hypothesis apparatus. The core mechanical claims (no part data in `resources/`, 35 registered element types, ArchUnit already a test dependency) check out against the current tree. But the issue leans on a whole planning corpus (`docs/plan/**`) that does not exist in this repository, contains a citation it has already flagged as wrong in a comment but never fixed in the body, and is filed in a state where it cannot start (its sole hard blocker, #400, is itself gated on two of its own parent's "blocks execution" open questions). None of this is fatal to the underlying idea, but an executor picking this up today hits dead links and an unresolved dependency chain before writing a line of code.

## Findings, most severe first

**1. [High] The evidence corpus this issue's licensing rationale rests on does not exist in the repository.** The body cites `docs/plan/evidence/BRIEF.md` (decisions D8, D9) and, transitively via #349, `docs/plan/evidence/capstone-plan.md` and `docs/plan/features/FEAT-040-package-and-pinout-library-as-data.md`, as the justification for the licensing policy (GPL-3.0-or-later can absorb GPL-2-or-later/GPLv3/BSD/ISC/MIT/Artistic-2.0) and the audience/cost framing this task inherits. `find / -iname "BRIEF.md"` and `find / -iname "FEAT-040*"` return nothing anywhere on the filesystem, and `find docs -maxdepth 2 -type d` shows no `docs/plan` directory at all — only `docs/standards-adoption` and `docs/capability-roadmap` exist alongside ~28 flat `docs/*.md` files. Issue #450's own Completion Criteria requires "Every cited evidence document and permalink resolves on the default branch at close" — by that standard the issue already fails its own bar at filing, not just at close. Recommendation: either land the missing planning corpus first, or replace these citations with an in-tree, self-contained statement of the license allow-list (which §14 Open Question 1 already half-does) so the task doesn't depend on unauditable documents.

**2. [High] The issue misstates a dependency's status in its own body, and says so in a comment it never applied.** §1 and §12 both state "**#78** (closed)". The issue's own comment (posted 6 minutes after creation, same author) retracts this: "#78 — **open** — *Element authoring contract, final stage (H2)*... citing an open residual as a closed decision is exactly the citation error rule 1 forbids... the body edit itself is left to the link pass." Verified independently: `mcp__github__issue_read` for #78 was not fetched here, but the correcting comment is authoritative and unambiguous. An executor who reads only the body (the normal case) still gets a false "closed" status for a related dependency. Recommendation: apply the body fix now rather than deferring it to an unscheduled "link pass" — a self-known defect left uncorrected in a filed issue is worse than one nobody noticed.

**3. [Medium] The task cannot start, and its blocker is itself two open questions away from being unblockable.** `blocked_by: [400]` is real and current (#400/TASK-0085 is `state: open`). But #400 is not just unimplemented — its parent #349 (FEAT-040) marks Open Questions 1 ("what is a section when sections aren't identical / shared pins") and 5 ("is the footprint column present from entry one") as **"Blocks filing TASK-0085."** So #450 sits behind a task that is itself behind two undecided design questions in a third issue. The issue's Method checklist item "Confirm #400 has landed" treats this as a simple landed/not-landed check, but the real state is "landed, or its own prerequisites haven't been ratified yet" — worth stating plainly so whoever triages this doesn't treat #450 as near-term-actionable.

**4. [Medium] H2's falsifiability test is set up to only check one of the two sources the cost estimate relies on.** §6 Materials names "Logisim-Evolution's TTL component library (GPLv3, O3) as the primary candidate; any other machine-readable part library, each checked before use." But the parent feature #349's own cost justification explicitly leans on *two* GPL-3.0 Java sources to shrink the estimate from 6-10 to 4-8 weeks: *"Two GPL-3.0 **Java** simulators carry exactly this data: Logisim-Evolution's `std/ttl/` (69 `Ttl74xxx` files of 108) and hneemann's Digital."* #450 never names hneemann's Digital anywhere in its body, hypotheses, or materials list. If TASK-0055 checks only Logisim-Evolution and that source's coverage is materially incomplete (H2's own stated refutation condition), the task will report more omissions than the parent feature's cost band assumed — but the parent's cost basis already priced in checking both. Recommendation: name the second candidate explicitly in §6/Materials so H2 is tested against the same evidence the cost estimate used, or explain why it was dropped.

**5. [Medium] The evidence-commit citations cannot be independently verified in this checkout.** `evidence_commit: 2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7` and the claimed HEAD-at-filing `839fb3a` both fail to resolve (`git cat-file -t` / `git rev-parse` error "unknown revision") in this shallow clone (`git rev-parse --is-shallow-repository` → true, 268 commits reachable). This may simply be shallow-clone depth rather than a fabricated hash, but it means a reviewer cannot mechanically reproduce the issue's central "RULE 3, THE OBSERVED FAILURE" claim from the stated commit — only from the current HEAD, which happens to still support P1's premise (`resources/` still holds only `help` and `packaging`; the 74LS/74HC/pinout/footprint grep still returns nothing). Recommendation: note in the issue that verification requires an unshallowed clone, or re-pin evidence to a commit reachable from a standard fetch depth.

**6. [Low] P8's "zero production call sites" criterion is well-guarded against the obvious gaming vector but not against reflection.** The issue itself already anticipates the vacuous-pass failure mode ("If P8 passes but a downstream surface still reports a fan-out number, the number is coming from somewhere else") and commits to ArchUnit (`test/jls/ArchitectureRulesTest.java`, `test/jls/ui/DialogCoverageRatchetTest.java` confirm the idiom is real and already used, not aspirational). That's solid. What's unaddressed: ArchUnit's default `noClasses().should().callMethod(...)` rules match static/direct bytecode call sites; they do not by default catch a field accessed via reflection or a MethodHandle from `src/` — a realistic way a later contributor "reads" the electrical columns without tripping a naive rule. Not a reason to block the issue, but worth a one-line note in the P8 test's design so the ArchUnit rule is written defensively (e.g., also asserting no `Field`/`Method` reflection targeting the accessor's declaring class).

**7. [Low] Scope-creep surface, self-acknowledged but still present.** The task frames itself as "transcription, not design" (§11: "Two weeks is transcription, not design... A schema debate inside a transcription task is how two weeks becomes six"), yet its own Method list requires three new test classes (one of which, `LicenseAuditTest`, is confirmed absent from `test/` today — `find test -iname "LicenseAuditTest.java"` returns nothing), a new `NOTICE`-style file, an ArchUnit rule, and a packaging-pipeline assertion, on top of the transcription itself. That's a reasonable amount of infrastructure for a first-of-its-kind data file, but the two-week estimate implied by the parent feature's cost table (§349 Cost: "TASK-0055 at 2 wk") looks tight against it. This is a estimation-confidence concern, not a correctness one.

## What's solid (no action needed)

- O1/O2 are independently verified true against the current tree: `resources/` holds exactly `help` and `packaging`; the 74LS/74HC/SN74/DIP/pinout/footprint grep over `src/` and `resources/` returns no hits; `ElementRegistry.java` has exactly 35 `new ElementType(...)` entries, with no physical-package field.
- The ArchUnit dependency claim (pom.xml, "core artifact, not archunit-junit5") is accurate, and the idiom it points to is already in production use, not invented for this issue.
- The scope boundary against #400 (schema/loader) and #341 (interpreting the electrical columns) is clean and consistently stated across all three issues (#450, #400, #349) — no contradiction found there.
- The inertness requirement (H3/P8) is well-motivated and the "redefine, don't abandon" fallback for H3-refuted is a sensible falsification response.
- The omit-and-list policy for unlicensable parts (rather than guessing from an unclear source) is the right call and is stated consistently in both the hypothesis and the failure-mode sections.
