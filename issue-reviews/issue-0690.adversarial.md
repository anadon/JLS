# Issue #690: TASK-C524-3: the CLI can be asked which contract version it implements, so an adapter refuses an incompatible build by name instead of misgrading
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

The task is small (`band_mw: 0.5`) and its shape — a queryable version for a frozen interface — is not novel for this codebase: `Circuit.FORMAT_VERSION`/`NEWER_FORMAT` (ARCHITECTURE.md, "The save/load pipeline" §3) already does exactly this for the file format. But #690's four ACs lean on two things this review could not verify: (1) that its sibling task TASK-C524-2 (#687) will actually produce a stored, queryable "source of truth" for the version rather than just a versioning *policy* and a CI test, and (2) that any consumer will ever call the query surface being built. Both are load-bearing for the issue's stated purpose ("Silent misgrade is the failure mode this exists to make impossible") and neither is nailed down.

## Findings, most severe first

### 1. AC-4's "same source of truth" points at an artifact TASK-C524-2 never commits to producing

AC-4: *"The version reported is derived from the same source of truth the ratchet in TASK-C524-2 enforces, so the two cannot disagree."* I fetched #687 (TASK-C524-2) directly. Its four ACs are: (a) a written prose versioning policy (semver + deprecation window), (b) a CI test that a seeded contract violation fails the build before any adapter test runs, (c) a distinction between additive and breaking changes enforced by the ratchet, (d) a demonstration that the policy admits one concrete verdict evolution from #369/#466 without a major bump. None of these is "a stored version identifier the codebase can read back." #687 describes a *process* ratchet (a policy plus a CI gate), not a data artifact. #690's AC-4 assumes such an artifact exists to be the shared "source of truth," but the issue that's supposed to create it doesn't promise to. As filed, an implementer of #690 has nothing concrete in #687 to point the version query at, and "so the two cannot disagree" is unfalsifiable — there's no second thing on record to compare against. Recommend #687's ACs be amended to name a concrete, stored artifact (e.g., a version constant/file this ratchet's CI test reads and #690's query surface also reads), or #690's AC-4 be reworded to state where that source of truth actually lives if it's meant to originate here instead.

### 2. Contract version vs. application version is never distinguished, and the codebase already has one of the two

`JLSInfo.versionString` (`src/jls/JLSInfo.java:16-40`) is already single-sourced from `pom.xml` via `version.properties`, already follows semver (CHANGELOG.md line 5-6: "semantic versioning ... from 4.3.0 onward"), and is already exposed — but only into the GUI window title (`JLSStart.java:1281`, `setTitle(JLSInfo.version)`), not on the CLI. #690 never states whether the "contract version" it wants is this same value or a distinct counter that only advances when the frozen CLI surface itself changes. The distinction matters: if an implementer takes the path of least resistance and reports `JLSInfo.versionString`, then every unrelated release (a GUI fix, a new gate type, anything touching `pom.xml`'s version) changes the "contract version" too, even when invocation/exit-codes/artifact-paths/xUnit-schema are untouched — an adapter pinned to "5.0.5" would spuriously refuse "5.0.6" that changed nothing it depends on. If instead a separate counter is invented with no tie to a release process, nothing in #690 (or in #687, per finding 1) requires that counter to actually advance when the contract breaks — the "cannot disagree" guarantee has no enforcement mechanism named on either side. Recommend the issue body state explicitly that the contract version is independent of `JLSInfo.versionString` and name what change class increments it.

### 3. The stated purpose depends on adapter-side work this issue's own Boundary disclaims

The Outcome section justifies the whole task on "an autograder adapter pinned against contract version X can ask... and refuse... rather than... producing a plausible, wrong score." The Boundary explicitly pushes "each platform adapter's own use of it" to #525, #526, #528, #530. I fetched all four (confirmed real, open, `ordering_after: ["FEAT-C21-1"]`, i.e. behind #524 not #690 specifically): their ACs cover byte-identical score vectors across adapters, pinned/cached builds, README doc-tests in CI, and platform-specific format drift (Gradescope `results.json`, GitHub Classroom checks, PrairieLearn `externalGrader`, nbgrader cells). **None of the four mentions querying a contract version or refusing an incompatible build.** So the mechanism #690 builds may pass its own conformance test and AC-2's "reference adapter check" while zero real adapters in this lineage ever call it — the feature could ship fully conformant and never prevent a single misgrade, which is precisely the failure mode the issue exists to make impossible. Recommend at least one of #525/526/528/530 get an AC requiring it to query and enforce the contract version at startup, or #690 name a maintained reference-adapter fixture (see finding 4) that outlives this issue's closure and is re-run in CI, not just demonstrated once.

### 4. AC-2's "reference adapter" is undefined, ownerless, and gameable

*"A reference adapter check demonstrates refusal: given a build reporting an incompatible version, the adapter exits with a named error identifying the expected and actual versions, and produces no scores."* A "reference adapter" implementing what integration surface? Per finding 3, none of the four real adapters budgets for this in their own ACs, and #690's Boundary excludes adapter work from this issue. That leaves two readings: either AC-2 is scope creep into territory explicitly assigned elsewhere, or "reference adapter" means a disposable fixture built and thrown away inside #690 — in which case a two-line shell script that string-compares an expected version, prints an error, and exits non-zero satisfies the checkbox literally without ever being wired into a real grading platform, and without a regression test keeping it honest after this issue closes. Recommend naming the fixture's permanent home (a `test/` class or a script under `scripts/` with a CI lane) so "demonstrates" means "is continuously checked," not "was true once."

### 5. AC-3's "no license state" clause names a precondition that doesn't exist in this codebase

*"The version query works on a build with no circuit, no lab and no license state..."* "No circuit" and "no lab" map to real JLS preconditions (no `.jls` file loaded; no CAP-06 lab-as-data format present). "No license state" does not: JLS has no licensing/activation mechanism — the MTU EULA acceptance gate was removed outright (`src/jls/JLS.java:40-41`, "the superseded MTU EULA acceptance gate is gone (issue #40)"), and the project ships under plain GPLv3 with no runtime license check anywhere (confirmed by a repo-wide grep: the only "license" hits are GPL/EULA references and unrelated third-party-tool mentions). This phrase is identical boilerplate to #524's own AC-5 text and appears to be copied from a shared CAP-21 acceptance-criteria template without adaptation to JLS's actual state space (other reviews in this pass — #524's and #713's — already flag the same phrase verbatim). It's low-severity because it can't actually fail (there's no license-state code path to break), but that's exactly the problem: an unfalsifiable clause in a "frozen contract with a conformance test" is dead weight, not rigor. Recommend dropping "no license state" or replacing it with a precondition JLS actually has.

### 6. Minor: task-id cross-referencing has no resolution table

`ordering_after: ["TASK-C524-2"]` uses the task_id string, consistent with #687's own self-reference style ("TASK-C524-1") but inconsistent with #524's parent body, which uses raw issue numbers (369, 466) for cross-feature edges. A repo-wide search turned up no mapping file from `task_id` strings to issue numbers, so a scheduler or tooling script parsing these YAML blocks structurally (as #524's own review thread insists it must, per that issue's finding 1) has to resolve "TASK-C524-2" → #687 by search, not by lookup. Not a defect specific to #690 — noted for completeness, matching the same observation #524's adversarial review made about its own body.

## What's solid

- **AC-3's headless/no-precondition requirement is cheap and has a working precedent already in tree.** `-h` is `Arity.NONE` (`JLSStart.java:760-761`) and exits at `apply` case "h" (line 1027) before any operand or circuit file is ever required — a `-version`-shaped flag can slot into the same `FLAGS` table and `apply` switch with no new parsing machinery.
- **The overall mechanism is architecturally native to this codebase.** `Circuit.readFormatHeader`/`FORMAT_VERSION`/`NEWER_FORMAT` (ARCHITECTURE.md, save/load pipeline §2) is the exact same "ask an artifact what version it speaks, refuse a mismatch by name" pattern already proven for the file format; extending it to the CLI contract is consistent with how this project already solves this class of problem.
- **The task's own Boundary text is internally consistent with #686 and #687's boundary text** — each of the three sibling tasks names the other two correctly and does not contradict them on scope (content vs. ratchet vs. query surface), unlike the cross-issue-vs-comment drift found in #524 itself.
- **`band_mw: 0.5` is plausible** given the actual work implied (one flag, one machine-readable output line, one conformance test) — assuming findings 1-4 don't expand it into cross-adapter integration work.

## Verdict rationale

The mechanical piece — add a version query, cover it with a conformance test — is small and well-precedented. What's not resolved is whether the thing being queried is well-defined (finding 1: the "source of truth" it must agree with isn't promised by the issue it's ordered after; finding 2: it's never distinguished from the existing application version) and whether the feature has any actual consumer (findings 3-4: the four adapters this exists to protect don't budget for calling it, and the one demonstration AC names no durable owner). An implementer could satisfy every checkbox as literally worded — print some version string, write one conformance test, write one throwaway refusal script — while leaving the stated goal, "silent misgrade is the failure mode this exists to make impossible," entirely unachieved in practice. That's a needs-rework, not a should-not-proceed: the fixes are scoping edits to this issue and #687, not a redesign.
