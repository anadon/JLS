# Issue #868: TASK-C590-3: one release actually goes out under the checklist, with the writeup and the posting links in its release notes — a checklist nobody has run proves nothing
- Lens: visionary
- Date: 2026-08-08
- Reviewer: Claude Opus 5
- Verdict: endorse-with-reframing

## What this issue is really for

Stripped of its wording, #868 asserts one thing about what JLS should become: **a project
whose claims about itself are practiced, not merely documented.** That is exactly the
instinct that runs through the whole repository. The README does not say "reproducible" —
it ships `.buildinfo`, `SHA256SUMS`, and a CI lane that rebuilds and re-checks the jar on
every push. It does not say "works on Wayland" — it ships `scripts/wayland-rig.sh`, a
`gui-wayland` lane, and a *self-test of the rig's own failure classification*
(`scripts/wayland-rig-selftest.sh`), because a rig that can only report success proves
nothing either. `HelpTopicsTest` link-checks the help tree. `docs/batch-interface.md` is a
stability contract with tests behind it. The project's real architecture — the one
`docs/grand-architecture.md` is trying to name — is **truth maintained by lanes**.

Seen that way, #868's parent (#590, AC-3) is right that AC-2 without AC-3 "is a file", and
the boundary-note comment on #590 is right to defend it. My disagreement is not with the
goal. It is that **the mechanism #868 chooses to reach it is the one mechanism in this
repository that has no lane behind it**: a human performs a ceremony once, and the evidence
that it happened is prose in GitHub-generated release notes. That is the shape of thing
this project otherwise refuses to accept from itself.

## Two structural problems the issue does not see

**1. Completion depends on an event the repo cannot produce.** #590 names the flare moment:
the Linux-boot demo (#508 item 4). `riscv/README.md` is honest about where that stands —
RV32I base integer only, word-granularity `lw`/`sw` (byte/half explicitly out of scope), no
M/A extensions, no CSRs, no supervisor mode, no Sv32 MMU. Booting Linux is not a polish
pass away; it is a different machine. So AC-1 ("at least one release goes out under the
checklist") resolves one of two ways: the task sits open for years, or someone declares an
ordinary patch release a flare moment to close it — which corrupts precisely the definition
#867 AC-3 exists to protect. A 0.25–0.5 mw task whose gate is an external event is
mis-shaped for a single-maintainer tracker.

**2. The audit trail is put in the least auditable place available.** `release.yml` sets
`generate_release_notes: true`. Release notes are therefore machine-generated, not in-tree,
not diffable, not covered by any check, and not reviewable in a PR. Recording "the writeup
and the posting links" there is the opposite of how this project records everything else it
considers normative (`docs/*.md`, `CHANGELOG.md`, `SHA256SUMS`, the attestation). AC-3's
"re-checked at posting time, with the check dated" is unenforceable in that location — the
date is a sentence someone typed, and when a competitor link rots nothing goes red.

## Reframing: make the announcement payload a build product, not a ceremony

**Invert the polarity.** Do not rehearse a checklist once and hope the muscle memory
survives to the flare. Instead, keep the announcement payload **permanently one command
from ready**, regenerated by CI on every tag, so that the question "have we exercised it?"
becomes vacuous — it is exercised every release, and the first genuine flare has zero
cold-start.

Concretely, three artifacts, all of which reuse machinery that already exists:

- **`docs/release/announcement-kit.md` plus a `make`/script target that builds it.** Its
  "demonstrable artifact" (AC-2) is not hand-assembled: the container one-liner already in
  the README, an SVG exported by `-i out.svg`, a `grim` screenshot from the existing
  `wayland-rig.sh` artifacts directory, and the `riscv/verify.py` transcript. Every one of
  those is already produced by a green lane. AC-2 stops being a person's afternoon and
  becomes a file CI refuses to omit.
- **An in-tree posting ledger** (`docs/release/announcements.md`, or a tracked data file in
  the shape #582 already uses for release-API counters): one dated row per release —
  tag, writeup URL, venue, post URL, competitor-claim recheck date. Release notes *link*
  the ledger rather than being the record. Now AC-1's audit trail is diffable and
  reviewable, and a lane can assert the freshness rule AC-3 states: fail the tag when a
  competitor citation's recheck date predates the tag by more than N days.
- **Link coverage on both.** #866 (TASK-C590-1) is already building exactly this
  mechanism for the positioning paragraph — single source file, drift check, every link
  covered by link checking. #868 should *consume* that, not invent a parallel prose
  discipline. Two sibling tasks inventing two ways to keep the same kind of claim honest is
  the duplication risk here.

Under this framing, AC-4 ("fix the checklist where it proved wrong") stops being a memory
exercise — "this step took an hour longer than it claimed" — and becomes a red build: a
venue that no longer exists is a dead link in a checked file; a step that cannot be
executed is a target that fails.

## Explicitly disregarding AC-1 as written

I am setting aside AC-1's gate. "At least one release goes out under the checklist" should
not be the completion criterion, because it makes an in-repo capability contingent on an
event outside the repo, and because the honest version of it is trivially satisfiable in a
way that damages #867. Replace it with: **the kit builds and the ledger row is written on
the next tag, flare or not** — and a row reading `venue: none (not a flare moment; no
posting)` is a valid, honest row. That satisfies the real intent (the path has been walked
end to end, not just written down) on the next ordinary release, while leaving the *actual
posting* to a genuine flare where it belongs. AC-2, AC-3 and AC-5 survive intact; AC-5's
"reception is out of scope" is one of the better lines in this cluster and should not be
touched.

## The out-of-the-box move: the flare is already in the tree

#590 is waiting for a Linux boot that is architecturally years away. Meanwhile the
repository already contains a stronger demo than most tools in this niche can produce:
**a single-cycle RV32I CPU built from ordinary JLS elements — no special mode, no plugin —
differentially fuzzed against an independent reference emulator, runnable headless in a
signed multi-arch container, exportable to structural Verilog.** That is a flare moment; it
is simply an unannounced one. "Draw a RISC-V CPU, fuzz-verify it against a reference
emulator, export it to Verilog — one `docker run`" is a piece with a demonstrable artifact
behind every clause, and the artifact is CI-green today.

I would say this in the issue outright: the flare-moment definition in #867 should
recognize **capability milestones already shipped and never announced**, not only future
spectaculars. Otherwise the project's strongest evidence keeps aging in-tree while the
announcement discipline waits for a machine that does not exist yet.

## Alignment

The work belongs to the project's arc — CAP-36's thesis (prominence in this niche flows
from citable evidence, not features) is well-evidenced and this is its cheapest slice. It
does not pull against the codebase; it is non-code by construction. The only thing that
pulls against the arc is the chosen medium: prose in generated release notes, verified by
nobody. Move the record in-tree, make the payload a build product, and #868 stops being the
one claim in this repository that only a human's word supports.

## Suggested shape

Split the closable from the unclosable. This issue keeps: the kit target, the in-tree
ledger with a freshness lane, the link coverage, and AC-4's corrections. A second, small
item — "post the writeup when a real flare arrives" — is a checklist line in #867, not a
tracker issue, because no amount of work in this repository can close it.
