# Issue #397: TASK-0100: the analog solver is checked against real ngspice nightly inside a derived envelope, with detectors that catch a regression staying inside it
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Findings, most severe first

**1. (High) The task's real prerequisites are unfiled, and the machine `blocked_by` block hides that.** `blocked_by: [386]` is the only machine-readable dependency, but the body says outright: *"Two further task-to-task edges are in scope and cannot yet be named, because those tasks are being filed concurrently"* — TASK-0098 (determinism/golden-header format) and TASK-0099 (controlled sources/waveforms). Checking the named parent, #351 (FEAT-046), confirms TASK-0097 (solver core), TASK-0098, and TASK-0099 are all listed there as `unfiled`. So #397 depends on the shape of three pieces of code and one wire format (§7.3: *"the golden header's statistics block from TASK-0098"*, §7.4: *"the digest writer's record format, both of which only TASK-0098 defines"*) that do not exist as filed issues, let alone landed code, and `src/jls/analog` is confirmed absent in this checkout (`ls src/jls/analog` → no such file or directory). Any agent or maintainer trusting the machine block alone would see #386 satisfied and mark this "ready" when it structurally cannot start. Recommend: either add placeholder `blocked_by` entries once TASK-0097/98/99 are filed, or mark #397 explicitly not-ready in its own status block instead of only in prose.

**2. (High) The detector suite's "catches a regression" claim has no standing enforcement — it is asserted once, at dev time, then left to human vigilance.** R1/R3/R4/R5 live entirely inside the `analog-oracle` nightly job, which is `continue-on-error: true` by explicit design (well-justified by O5's build-to-build noise measurement) and is never part of the PR gate. The one place the issue tests that a detector actually fires is a single Method step: *"Verify H3 by injecting a regression that stays inside 1e-4 and confirming at least one detector catches it; record which"* — a one-time development exercise, not a test that runs on every future change to `jls.analog`. R4 in particular is a literal stored number (*"the stored value moves only with a reviewed change, so e_{n+1} > e_n ⟹ the golden's diff shows it"*) — nothing stops a future PR from bumping that literal in the same commit that introduces the regression it exists to catch; "visible in the diff" is not "blocks the merge," and the lane that would eventually notice (nightly) doesn't gate anything. Recommend: (a) keep the H3 injection test as a permanent, always-run mutation test rather than a one-off dev step; (b) add a check that the ratchet value can only move upward without an explicit `WAIVED:`/reviewed marker, rather than relying on a reviewer noticing a diff line.

**3. (Medium) Load-bearing numeric claims are unfalsifiable in-repo.** O5's "two ngspice builds differed in 66% of internal time points and 99.3% of sample values... worst relative difference 5.38e-04" and "987 of 1,022 rows" between `.options klu`/`.options sparse`, and O6's five-point ulp-perturbation linearity table, are the entire empirical basis for the 1e-4 envelope (H1, §7.10) and for "this lane must never become a required gate." None of the decks, rawfiles, or perturbation harness that produced these numbers are committed or linked, and no `ngspice`/`jls.analog` exists in this checkout to rerun them. As filed, a reviewer has to take the numbers on faith. Recommend: commit the raw experiment artifacts (or a script that reproduces them) so the tolerance derivation is auditable rather than asserted.

**4. (Medium) `evidence_commit` does not resolve in this checkout, so the issue's own verification command is not runnable as given.** `git diff --quiet 2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7 HEAD -- src test pom.xml .github/workflows` fails with `fatal: bad object 2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7` in this (shallow) clone. The same hash is reused verbatim in #386, #351, and #359, so this is a shared, not #397-specific, defect, and may be nothing worse than shallow-clone unreachability rather than a fabricated hash — but as filed, nobody working from a normal clone without that exact history can confirm "IDENTICAL" the way the issue instructs. Recommend: tag the evidence commit (e.g. an annotated tag) so it survives shallow clones and garbage collection.

**5. (Medium) Scope is task-tier in name only.** #397 is filed `tier: task`, but its own §11 Threats to Validity states *"the stage is 7-11 maintainer-weeks including the full 26-fixture build-out and the jls.analog JaCoCo and PIT floors; FEAT-046's band carries the remainder"* — while the parent (#351) prices the printed TASK-0100 row at 2 weeks, a 3.5-5.5x gap the parent names but #397 does not reconcile for itself. The Method/DoD checklist nonetheless commits to all of: 10 Tier A fixtures with individually-derived tolerances, 11 Tier B convergence-torture fixtures with pinned statistics, 5 Tier C required-lane invariants, four detector classes wired into the golden header, CI wiring (apt line + nightly job + promotion-policy comment), and a deliberate-regression validation exercise — in one task. That is feature-sized work wearing a task label, which risks either a chronically-incomplete DoD or an unreviewably large PR. Recommend: split fixture build-out (which can land incrementally, tier by tier) from the CI/detector wiring, or state an explicit per-tier time-box up front.

**6. (Low) The anti-cheat lower bound is a nonzero check, not a floor — mildly gameable.** P4 only requires `0 < disagreement` and `0 < numerical error`; §9 says a "suspiciously small disagreement is printed... so it is visible before it becomes a habit," but visibility is not enforcement, and no falsification criterion names a minimum acceptable disagreement. A deck subtly derived from JLS's own solved output (e.g. copied and perturbed at the last representable bit) would pass ">0" while still not being an independent oracle in spirit. Recommend: add an explicit minimum-disagreement constant (symmetric to `ε_abs` on the low side) rather than relying on a human reading a printed value.

**7. (Low, solid) Cross-checked observations are accurate.** O1-O4 all verify against the current checkout: `src/jls/analog` is absent, `grep -rn ProcessBuilder src/` returns 0, `test/jls/hdl/GhdlCompileTest.java:35` / `IverilogCompileTest.java:34` carry the cited `Assumptions.assumeTrue` self-skips, and `.github/workflows/ci.yml` matches the cited cron (`:13`), concurrency group (`:23-24`), apt line (`:73`), and `continue-on-error` idiom at the cited style (many lines, consistent usage). The linear-error-propagation argument for why a tolerance comparison is meaningful (O6/H2), the three named exception classes (self-oscillators, chaotic circuits, bifurcations), and the discipline of landing the rawfile header-stripping rejection test (P5) *before* any comparator code is genuinely good engineering and should survive any rework.

## Verdict rationale

The core design — tiered fixtures, a derived (not arbitrary) tolerance envelope, anti-cheat bounds, and an explicitly-advisory nightly lane — is sound engineering reasoning. But the issue is not yet actionable as filed: it depends on three sibling tasks that don't exist yet and that dependency isn't machine-visible (finding 1), its headline claim that regressions get "caught" has no enforcement path once the fixtures exist (finding 2), and its own text concedes the task-tier label understates the work by several times (finding 5). These are structural, not cosmetic, and should be resolved before implementation starts.
