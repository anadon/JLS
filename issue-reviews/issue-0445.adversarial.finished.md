# Issue #445: TASK-0034: a memory image rides in an optional, length- and hash-checked binary section instead of consuming the whole 64 MiB text budget as escaped hex
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

The core measurement is real and reproduces against current HEAD: `MAX_CIRCUIT_TEXT_BYTES = 64L << 20` (`src/jls/FileAbstractor.java:65`), `Memory.save`'s only encodings are `initrle`/`init` escaped text (`src/jls/elem/Memory.java`'s `setValue`/`save`, matching the issue's `:404-467` citations to within a few lines), and `docs/file-format.md`'s evolution policy (§9, `:420-471`) does put "a new attribute of an existing item kind" in the no-bump column, supporting H4. The problem is not the arithmetic; it is that the issue's own dependency bookkeeping is stale in a checkable, easily-fixed way, and several parameters the issue calls "blocks execution" are left fully open with no numeric floor — including one that can be gamed to silently defeat the #38 hardening this task promises not to weaken.

## Findings, most severe first

**1. (High) The "hard prerequisite whose number does not exist yet" already has a number, and the real blocking chain is far deeper than the declared `blocked_by: [439]`.**
The issue states: *"TASK-0033 ... is being filed concurrently and its number cannot be verified here. A link pass must add it."* That is false as of this review: TASK-0033 is issue **#444** — *"a saved file stops being one indivisible unit"* — filed one issue number before this one, in the same batch, open. `#445`'s machine block never mentions it; only `blocked_by: [439]` is declared. Worse, the real chain is: `#315` (FEAT-001) → `#436` (TASK-0005, open, itself `blocked_by: [315]`) → `#444` (TASK-0033, open, `blocked_by: [436]`) → `#445` (this issue), in parallel with `#439` (TASK-0013, open, no blockers, so closer to landable). None of that four-hop chain is visible from `#445`'s own Status block, which a contributor would read as "blocked on one thing." I verified all four issues' states and `blocked_by` fields directly via the GitHub API.
*Recommendation:* Add `444` (and transitively note `436`, `315`) to `blocked_by` now — the "link pass" this issue defers is a one-line fix that was possible at filing time, since `#444 < #445`.

**2. (High) The payload-size bound is left numerically unconstrained, and as written it can be satisfied by a value that reopens the #38 hole this task claims to close.**
§7.11 and Open Question 2 require only that the `IMAGE` payload bound *"must not be `MAX_CIRCUIT_TEXT_BYTES`"* and be *"a separate constant with its own #38-style justification."* No floor, ceiling, or derivation is given — contrast with TASK-0013 (#439), which pins its analogous constant to an explicit formula (`B_max ≥ h · 34,078,720`) in the same batch of issues. Under #445 as written, an implementer satisfies every stated criterion (P4, P5, P6, the DoD line "no changes to `MAX_CIRCUIT_TEXT_BYTES`") by setting the new bound to, say, `Long.MAX_VALUE` — technically "a separate constant," technically not `MAX_CIRCUIT_TEXT_BYTES`, and yet it removes exactly the size guard §7.3 calls "hostile" input and #38 exists to bound. None of P1–P10 would catch this because they test refusal *correctness* (length/hash mismatches), not that the bound is tight.
*Recommendation:* State a concrete number (or an explicit formula tied to a cited target, as #439 does) before this ships, and add a prediction that a payload above the stated bound is refused — not just a mismatched one.

**3. (Medium) The writer's threshold θ is also undecided, and nothing prevents the two open numeric decisions from being decided inconsistently with each other or with #439's budget.**
Open Question 1 ("What is the writer's threshold θ?") is marked "Blocks execution" with only "Recommended: ... one order of magnitude below C" — vague, and self-admittedly mirrored from #364's Open Question 4 rather than fixed here. Because P9 only checks that the threshold is "at the stated boundary" (whatever that ends up being) and P10 only checks existing goldens are untouched (all far below any plausible θ), an implementer can pick θ anywhere in a huge range and pass every stated prediction. This is consistent with Finding 2: the issue's falsifiable-hypothesis apparatus is rigorous about *behavioral* correctness (refusal wording, byte-identity) but leaves the two load-bearing size constants as unchecked free variables.
*Recommendation:* Fix θ and the payload bound to specific numbers (or a specific formula) in this issue rather than deferring both to "the executor," and add acceptance tests that assert the chosen values are within the range implied by #439/#364's own budget arithmetic — the issue already claims (§12) that #364 §6 records "TASK-0013 → TASK-0034" as a critical-path edge with "a necessity clause," so the arithmetic dependency is asserted but not made checkable here.

**4. (Medium) The issue cites a governing document and a base commit that do not exist in this repository, so its "verbatim" rulings cannot be checked from the tree a contributor actually has.**
`evidence_commit: 2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7` and the claimed HEAD-at-filing `839fb3a` both fail `git cat-file -e` in this checkout. `docs/plan/evidence/BRIEF.md` (cited for decisions D1, D15, D16) and `docs/plan/tasks/TASK-0013-*.md` do not exist anywhere in the tree (`find . -ipath '*docs/plan*'` returns nothing; `docs/` has no `plan/` subdirectory). The issue treats "BRIEF.md decision D15" as dispositive for scoping guest-image residence away from this task ("do not read D15 as cancelling this task") — a contributor cannot independently verify that ruling exists or says what's quoted, only take the issue's word for it. I was able to corroborate the *code*-side observations (O1, O2, O5, O8, O9) against current HEAD, so this is not evidence of fabricated arithmetic, but the "verbatim" governance citations are unverifiable as filed.
*Recommendation:* Either commit `docs/plan/**` to the repository (or link to wherever it actually lives), or restate the D1/D15/D16 rulings inline in the issue body so they don't depend on an inaccessible document.

**5. (Low) O9's "exactly one writer" claim narrows scope correctly but is asserted, not searched, in the citation given.**
O9 quotes `RegisterFile.save` to show it has no initial-contents attribute, which is accurate (`grep` confirms `RegisterFile.java` has no `init`-style String attribute), but the issue never greps the full `jls.elem` package for *any* other element with a bulk `String` payload attribute before concluding "Memory is the only producer." I did not find a second one in a quick scan, so the conclusion likely holds, but the issue's own evidentiary standard elsewhere (exhaustive `git grep` for `imgref`/`IMAGE`) is not applied here — a smaller, easy gap to close.
*Recommendation:* Add the `git grep` for other `String init`-shaped save attributes across `src/jls/elem/` to make O9 as rigorous as the rest of §2.

## What's solid (no action needed)

- The core defect is real and reproducible: current `Memory.save` has no binary path, `MAX_CIRCUIT_TEXT_BYTES` is measured against decompressed text, and a large image genuinely can produce a file JLS writes and then refuses to reopen — this matches the current `FileAbstractor.java` guard logic.
- H4's "no second FORMAT bump" reasoning correctly reads the current `docs/file-format.md` §9 evolution-policy rule (a new attribute of an existing item kind needs no bump); this part of the issue is consistent with the spec as it stands today.
- The mutual-exclusion and refusal-message requirements (P4–P7, each naming the section id and both compared values) are concrete and hard to satisfy with a stub implementation — a solid anti-gaming design for the parts they cover.
- Explicit scope exclusions (§13: not touching `MAX_INIT_WORDS`, not generalizing `imgref` beyond `Memory`, not settling guest-image residence) are stated plainly and reduce scope-creep risk for the executor.

## Verdict rationale

The measured problem and most of the technical design are sound, but the issue is not ready to hand to an executor: its own dependency graph is demonstrably out of date in a way a two-minute check would have caught (Finding 1), and two of the numbers the whole capability depends on (payload bound, writer threshold) are left open in a way that lets an implementation satisfy every stated prediction while reopening the hardening gap this task exists to avoid widening (Finding 2). Fix the `blocked_by` list and pin the two size constants before this is picked up.
