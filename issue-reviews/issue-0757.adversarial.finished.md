# Issue #757: TASK-C576-2: one command grades a directory of submissions and returns per-student verdicts with counterexamples
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

The scoping instinct is right — "consumes CAP-06's report slice... builds none" is a clean boundary in principle, and the dependency on TASK-C576-1's submission-layout spec is correctly identified. But the issue as it stands today (body plus its single comment) fails on the same axis several sibling issues in this tracker already failed on: the machine-readable dependency block in the body is stale and contradicted by the issue's own newest comment, and two acceptance criteria are either non-falsifiable or mutually inconsistent once you check what actually exists in the tree. None of this is fixable by an implementer picking a reading; it needs the maintainer to edit the body.

## Findings, most severe first

### 1. The body's `ordering_after` is stale, self-contradicted by the issue's own comment, and never corrected in the body itself

The body's YAML block reads `ordering_after: ["TASK-C576-1", 369, 466]`. The issue's own (and only) comment — posted the same day, `2026-08-08T17:33:12Z` — retracts the `369` entry outright: *"`ordering_after: [369, …]` is wider than the real prerequisite… Correction: `ordering_after: [TASK-C576-1, 466]`."* Naming #369 (FEAT-053) transitively imports #369's real `blocked_by: [316, 321, 347]` — the SimpleEditor decomposition, the Yosys JSON writer, and the parity harness — none of which #757 consumes. #369's own comment thread (`issuecomment-5227456832`, `18:15:24Z`, an hour *after* #757's comment) independently confirms the same correction from the other end: "#524, #686 and #757 [were re-pointed] from `ordering_after: [369, 466]` to `[466]`." Three sources (body, #757's comment, #369's mirror comment) now disagree on the literal value, and **the body itself — the part a scheduler or a new implementer reads first — still shows the wrong, wider dependency set.** GitHub gives no way to strike a body's YAML from a comment; only a body edit fixes this. Recommendation: maintainer edits the body's `ordering_after` directly to `[755, 466]` (TASK-C576-1 = #755, confirmed by cross-reference in `issue-0759.adversarial.md` and by #755's own `blocks: [757]`).

### 2. AC-1 is non-falsifiable as written, and the issue's own fix for that has not been applied to the checklist

AC-1: *"One documented command grades a directory... and emits per-student verdicts consuming CAP-06's report slice (AC-2)."* The issue's own comment names this defect directly: *"Consuming a slice is not observable in an artifact."* It proposes a concrete, checkable replacement — the per-student file this command emits must be **byte-identical** to running `jls -b -t v -check e -report r.xml` directly on the same submission — but that sharpened wording lives only in a comment, not in the checklist AC-1 actually is. As filed, an implementer can satisfy AC-1 by reimplementing comparison logic that merely resembles CAP-06's report shape, which is precisely the boundary violation the Outcome section says it is avoiding ("verdict semantics... are not re-owned here"). Recommendation: fold the byte-identity criterion into the body's AC-1 (or a new AC), not just the comment.

### 3. AC-2 and AC-3 contradict each other under the degraded-mode path, and that path is the only one available today

AC-2 unconditionally requires: *"Each per-student result names the failing tests and carries their counterexamples."* AC-3 permits, per KC-33-1, that if CAP-06's verdict slice has not landed, the command ships "against today's three-exit-status contract in a degraded but real form." I verified directly that the degraded path is in fact the *only* one available right now: `grep -n "\-check\|\-report" src/jls/JLSStart.java` returns nothing — no `-check`/`-report` flags exist; #466 (the task that would add them) is open, and its own Observation O1 records `jls -b -check e.txt ...` failing with `unknown option -check`, exit 2; #300 (CAP-06) is open, capstone-tier, with no landed code. Under today's three-status contract there is no comparator and no notion of a "failing test" at all — batch mode only dumps watched-element values. AC-2 does not carve out an exception for the degraded case, and AC-3 does not say what a degraded "failing test... with a counterexample" even means. The gap is gameable: the repo already ships `examples/autograde/autograde.py`, which grades by diffing three literal stdout lines against `EXPECTED_STDOUT_LINES` — exactly the "string diff" grading experience CAP-06's own abstract exists to retire (*"Today the shipped grading story is a Python script diffing three literal lines of a text report for one input vector. A submission wrong on every other vector and right on that one passes."*). An implementer can satisfy AC-2's letter today by wrapping that exact script in a per-submission-directory loop, ship a "degraded but real form," and check every box while delivering nothing better than what already exists. Recommendation: AC-3 needs a stated floor for "real" (e.g., "must diff every watched output line, not a maintainer-chosen subset") or AC-2 needs an explicit degraded-mode carve-out.

### 4. The overlap with #350 (the campaign runner) is unresolved on both ends, and #350's own process names this exact scenario as its worst failure mode

The Boundary section says: *"Cohort-scale dispatch across cores is #350's campaign runner — this command may consume it but does not reimplement it."* But #350 (FEAT-057) is confirmed to have zero code (`git grep -ic "campaign" -- src/` returns nothing per #350's own evidence) and is itself `blocked_by: [354, 363]`, with none of its planned tasks filed. #757 must therefore build its own directory walk, per-student artifact handling, and (per AC-4) order-independent aggregation — which is precisely the "job description... and aggregation format" #350 §7 warns about: *"Two independent implementations of 'run many things and collect the output' is the named failure mode... Whichever of the two ships first owns the job description and the aggregation format, and the other consumes it. Either resolution is acceptable; no resolution is not."* Neither #757 nor #350 records a resolution — #350's `related` list does not even name #757 or #576. This is the same class of un-mirrored boundary problem as finding 5.

### 5. #300 (CAP-06) — whose title is nearly a restatement of #757's own outcome — has no reciprocal boundary note naming #757 or #576

#300's title: *"one batch invocation turns 300 student submissions into deterministic per-student verdicts with counterexamples, replacing a three-line string diff."* #757's Outcome: *"turns a submission directory into per-student verdicts in one invocation... an instructor can answer 'why did this student fail'."* I searched #300's full body and found zero occurrences of "757", "576", or "755" — #300 predates #576/#757 by two days and has never been revisited to record the split. #757's body draws the boundary unilaterally ("Consumes CAP-06's report slice... not re-owned here"), but this tracker's own convention (demonstrated repeatedly on #369/#466: "Boundary drawn, recorded on both ends") requires the reciprocal issue to carry the mirror. #300's Definition of Done still describes "a real 300-submission corpus" walk-through as if #300 itself owns the cohort command — which is exactly the ambiguity #757's comment resolved for #466 but never asked #300 to resolve for itself.

### 6. Feasibility: "thin tooling" framing and the 1-1.5 mw band are hard to square with what AC-3's degraded mode actually requires

The Outcome states this is "thin tooling over existing batch mode." That is true only in the case where CAP-06/#466 land first and this command is a directory-walk wrapper around an existing verdict engine. But AC-3 (via KC-33-1) mandates a degraded-mode fallback that must produce real per-student verdicts against a contract that today has *no comparator at all* (finding 3) — building that is not thin tooling, it's building a second, throwaway grading engine that the "real" one later supersedes. The issue doesn't say whether the 1-1.5 mw band assumes CAP-06 has landed by the time this is picked up (making the degraded path dead code nobody exercises before close, which then makes AC-3/AC-5 unverifiable at close) or whether the band already prices building the fallback comparator. Recommendation: state which scenario the band assumes.

### 7. Sound — the TASK-C576-1 (#755) dependency is real and correctly identified

Unlike the #369 edge (finding 1), ordering after #755 is genuine: #755's own boundary states the layout spec exists "so the grading command in TASK-C576-2 has a contract to rely on," #755 is confirmed still open, and #757's requirement to grade "a directory conforming to the submission layout" is meaningless until that layout is specified. No issue with this half of the dependency graph.

### 8. Sound — the boundary against #466 is well-drawn and reciprocal

#757's Boundary ("consumes the grading engine; builds none") matches #466's own re-scoped retained boundary ("a minimal conformance fixture... not a general grading command") stated in #466's comment on the same day. This is the one boundary in this issue that *was* properly resolved on both ends — contrast with findings 4 and 5.

## Verdict rationale

The core scope (thin directory-grading wrapper, consuming an engine it doesn't own) is a legitimate and well-bounded idea, and two of its dependency edges (TASK-C576-1, and the #466 boundary) are solid. But the issue cannot be picked up as specified: the body's own ordering data is stale and contradicted by its own comment and by #369's mirror comment; AC-1 is not falsifiable as written even though the fix is sitting in a comment nobody folded back in; AC-2 and AC-3 conflict in exactly the scenario (CAP-06 unlanded) that is verified to be the current reality; and the overlap with #350 and #300 is unresolved on both of those issues, not just unmentioned here. **needs-rework** — a maintainer body edit consolidating the comment's corrections, plus a sharpened AC-1/AC-3, plus a boundary comment on #300 and #350, is what would make this safe to hand to an implementer.
