## Findings, most severe first

**1. [Critical] Two documents the issue cites as already-existing normative sources — `docs/parity-contract.md` and `docs/plan/evidence/BRIEF.md` — do not exist anywhere in this repository, at any commit.**
The issue leans on `docs/parity-contract.md` §2.4 as the source that "states [the replay invariance] as the replay invariant" (§7.10), and on `docs/plan/evidence/BRIEF.md` §12 decision D7 as binding, quoted verbatim, with a landing commit `3a81a4a7d6a0f108ec201e632732d308cc02b3fc`. Verified: `ls docs/parity-contract.md` and `ls docs/plan/evidence/BRIEF.md` both fail on the working tree, and `git log --all -- docs/plan` / `git log --all --diff-filter=A -- docs/parity-contract.md` return nothing — neither has ever existed in this repo's history. This is the identical defect independently found in the fleet's review of sibling issue #347 (`issue-reviews/issue-0347.adversarial.md`, finding 1), confirming it is systemic to this planning corpus rather than a one-off. An implementer cannot check §7.10's "the replay invariant is stated in docs/parity-contract.md §2.4" against anything, and D7 — the load-bearing decision that "-serial stdio" is a grant model, cited as binding across at least three sibling issues (#455, #424, #390) — is unverifiable. Recommendation: before this issue is picked up, either commit these documents for real or strip the "already specified elsewhere" framing and restate the governing decisions directly in the issue body.

**2. [Critical] The evidence commit `2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7` does not exist in this repository.**
`git cat-file -t 2d0ca9d` fails with "Not a valid object name." Every one of Observations O1–O10, every file:line permalink, and the "Evidence-commit note" claiming `src/`, `test/`, `pom.xml`, etc. are byte-identical between `2d0ca9d` and HEAD are all anchored to a commit nobody can check out, diff, or `git blame`. The issue's own Method step 1 ("Re-verify O1–O10 at the executor's checkout and re-run the O3 commands... If P1 no longer fails, this issue is superseded") and rule 6 depend on being able to do exactly that comparison — which is impossible as written. Mitigating fact, checked independently: every quoted line of code and every claimed line number *does* match current HEAD (`5b05d67`) exactly — the 14-entry `FLAGS` table, zero `System.in` hits, no `jls/io` package, the `BatchSimulator.java:420-422` `$comment` line, `:562-572` `displayOutcome`, `InteractiveSimulator.java:626` `Thread("Runner")` plus the eight `invokeLater` sites, `docs/simulation-semantics.md:91`, and `docs/vcd-interop.md:18-23` all verified byte-for-byte. **3. [High] `-serial replay:FILE`'s grammar directly conflicts with `-serial`'s already-defined operand space in the hard prerequisite's prerequisite (#424), and the issue flags this as unresolved while writing the design as if it were resolved.**
#424 (TASK-0067) formally specifies (§7.10): `f_grant(G) = NullPort if G ∈ {none, absent}; StdioPort if G = "stdio"; FilePort(G) otherwise` — i.e. any operand that isn't literally `none`/`stdio` is treated as a **file path to grant live bidirectional access to**, full stop. Under that already-specified grammar, the literal string `replay:FILE` is not special syntax; it is a file path named `replay:FILE`, and `-serial replay:FILE` would open (or attempt to create) a file with that literal name as a **live** `FilePort`, not dispatch to a threadless replay reader keyed on transcript stamps. Issue #455 Open Question 2 explicitly says this is unresolved ("**Blocks execution**; must be agreed with #424") — yet §7.4 ("A `FilePort` serving recorded input bytes at their recorded stamps"), H3, P1's example invocation, and the entire Method checklist step "Add `-serial replay:FILE` binding a threadless `FilePort`" are all written as finished design, not as design pending that negotiation. Nothing in the Definition of Done gates on Open Question 2 being resolved before implementation starts (it's listed under "Open Questions" but the DoD only requires "every decision... resolved (or explicitly deferred), none left blocking" — self-certified, not independently checkable). Recommendation: resolve the `-serial` grammar collision with #424 *before* this issue is picked up, and add an explicit DoD line requiring the resolution to be shown, not merely asserted.

**4. [High] The threadless-replay hypothesis (H3) is not reconcilable with #424's own type contract for `FilePort` without either modifying #424's sealed interface (explicitly out of scope) or leaving the transcript's stamped-triple format unexpressed through the existing port abstraction.**
#424 §7.4 defines `FilePort` as one of five permits of `sealed interface HostBytePort`, with a plain `int poll()` / `void emit(int b)` contract carrying "no framing, encoding or length... a byte is a byte" (§7.3). #455's `Transcript` is `record Stamped(long stamp, StampKind kind, Direction dir, byte value)` — a structured, stamped record, not a plain byte stream. For replay to feed a `HostBytePort.poll()` call, either (a) a *new* permit is added to #424's sealed interface (which #455 says is out of scope — "this task must not re-implement any of them" — and which would violate #424's own H1 stating the sealed set "cannot be walked back" without going out-of-process), or (b) the existing `FilePort` permit is reused and the stamp/kind/direction semantics live entirely inside `jls.io.Transcript`'s parsing layer, with `FilePort` reduced to serving plain bytes at the right moments — which the issue never states explicitly and which changes what "threadless... a `FilePort` serving recorded bytes at recorded stamps" (§7.4) actually means mechanically: something has to translate simulated-time or retirement-index stamps into "is it time to hand this byte to `poll()` yet," and that translation needs to observe the simulation's own clock/retirement counter, which is exactly the kind of `jls.sim` touch #390 and #424 both forbid. The issue never names which side (transcript vs. sealed port) owns this translation. Recommendation: before implementation, write down explicitly whether `Transcript` wraps a plain `FilePort` and self-paces against the running simulation's exposed retirement/time counters (and which accessor exposes those, since `Simulator` in #424's design does not appear to expose either), or whether this requires an addition to #424's permit set that must be renegotiated there first.

**5. [Medium] Acceptance criterion P5 (the golden-provenance ratchet) is exactly the kind of vacuously-passable scanner #424's own precedent test explicitly warns against — and #455 doesn't apply that warning to itself.**
#424 §11 states the risk in so many words: "**A test that passes because nothing ran.** Both new ratchets scan source substrings; a scanner whose baseline is empty **and** whose corpus is empty passes forever. Assert the corpus is non-empty." #455's P5 ("Scan `test/resources/**`, `test/fixtures/**` and the in-source golden constants under `test/**.java` for the `LIVE` marker; observe zero hits — asserted as an empty baseline") copies the *idiom* (O10) but the Method/Data-Collection sections for P5 never add the non-vacuity check #424 explicitly calls for. Nothing in §5, §8, or §9 requires demonstrating that the scanner actually detects a `LIVE`-tagged artifact when one is deliberately introduced (a "the ratchet was tried against a known-LIVE golden and observed to fail" step, analogous to how P4 in #390 is required to be shown non-vacuous: "a per-callback implementation was tried and observed to fail it, with the output recorded"). As written, P5 can pass forever on a scanner that is silently disabled, mis-scoped, or matching a marker string nothing ever writes — which is precisely the failure mode the issue's own §11 ("Threats to Validity") warns about elsewhere in the corpus but not here in its own predictions list. Recommendation: add a non-vacuity test for P5 — e.g., construct a fixture golden carrying `LIVE` provenance and assert the ratchet fails on it — mirroring #424's and #390's own stated discipline.

**7. [Medium] The `#405` "precedent to copy" for incremental-write discipline is itself an open, unlanded task, and #455 treats its described defect and fix as settled fact rather than as a design still in flux.**
§8 Method says "do not accumulate in a `StringBuilder`; that is the exact defect **#405 is removing** from the waveform dump" (present tense, "is removing," implying #405's approach is in progress/settled). Checked: issue #405 is open, unimplemented, and `BatchSimulator.java` at HEAD still literally uses `StringBuilder out = new StringBuilder()` in `toVcd()` (`src/jls/sim/BatchSimulator.java:386`) — the defect #405 targets has not been fixed yet, and #405's own Open Question 1 hasn't been settled (whether to bound `eventTrace`/`probeTrace` retention or merely document the residual). #455 doesn't depend on #405's code landing (it only needs to avoid repeating the same *mistake*, which is a legitimate and checkable independent discipline), so this is not a hard blocking defect — but citing an unlanded, still-undecided task as an established "the defect X is removing" pattern to imitate is imprecise, and if #405's eventual API shape changes (e.g., its Open Question 1 is answered as "bound the trace store," adding new incremental-writer machinery #455 could have reused), #455's independently-built transcript sink risks diverging from a pattern that doesn't exist yet. Recommendation: reword to "the same defect #405 documents" rather than implying an in-flight fix to imitate, or explicitly wait for #405 to land first.

**8. [Low] Scope surface is large for a single task-tier issue, even though the issue's own "explicitly out of scope" list is unusually disciplined.**
This issue touches: a new package (`jls.io`), two CLI flags, VCD output format (an additive `$comment` line), batch stdout format (`displayOutcome`'s second line), two normative docs (`docs/simulation-semantics.md`, `docs/vcd-interop.md`), a new GUI pane in `jls.edit`, three new test classes, and regeneration of in-source VCD golden constants "in one commit." That's seven distinct subsystems for one task-tier ticket. The issue does mitigate this somewhat by explicitly deferring TASK-0068, #390, and TASK-0021 to co-requisite status, and by listing out-of-scope items concretely (§13) — better discipline than many peer issues in this tracker — but the GUI console pane alone (with its own EDT/ring/keystroke-never-reaches-`post` concurrency contract, P7's dedicated test, and a stated dependency on #440's unlanded coverage floor being either landed first or explicitly waived) is arguably a separable task. Recommendation: consider splitting the console pane (GUI, `jls.edit`, display-tagged CI lane per #162) from transcript capture/replay (headless, `jls.io`) into two PRs even if they stay one tracked issue, given the pane's dependency on an unlanded, unrelated coverage-floor task (#440) that this issue's Open Question 4 waves off with "rides along."

- The "append a line, never edit the frozen block" discipline for `displayOutcome` (O6, P9) is concrete, checkable by byte-diff, and consistent with the same discipline already established and cross-referenced in #424.
- The mention-vs-construct distinction borrowed from `SocketConfinementRatchetTest` (O10) for the LIVE-marker ratchet is a sound acceptance-criteria pattern in principle — the concern in finding 5 is that its non-vacuity isn't independently demonstrated, not that the underlying idiom is flawed.
- The reconciliation with #63's live-co-simulation rejection (O5, H5) — "the console pulls and is never called back into" — is a coherent and correctly-motivated position, and the issue is honest that it must be settled in writing rather than left to drift, which is good practice even though the mechanical detail (finding 4) is underspecified.
