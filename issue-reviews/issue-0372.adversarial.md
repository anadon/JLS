## Summary

The core technical claim — `ElementRenderers.BY_TYPE` and `ElementDialogs.BY_TYPE` are non-total over `ElementRegistry.all()`, and `RegisterFile` is consequently invisible on the canvas — is real and reproduces on the current tree (verified independently below, not just re-quoted from the issue). That part is sound. But the issue's evidentiary apparatus is built on a commit (`2d0ca9d`) that lives only on an unmerged, soon-to-be-deleted branch, and the issue's own maintainer has already had to post three separate corrective comments admitting that citations in the body are false when read against `master`/`HEAD`. Two of those corrections land directly inside the Method section's first executable step, which as written would inject false "already covered" rows into the very inventory document this task exists to make trustworthy. The issue needs a body edit, not just comments, before anyone should execute §8.

## Findings, most severe first

### 1. [CRITICAL] The evidence commit is orphaned, unmerged, scheduled for deletion — and the issue still treats it as ground truth
Every observation (O1–O8), every prediction, §7's data contract, and the "Operative clause" quote in §1 are pinned to `evidence_commit: 2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7`. The repo's own maintainer comment states: *"This issue declares `evidence_commit: 2d0ca9d...`, which exists only on a branch that will not be merged and will be deleted. The surviving equivalent is `master` at `8288226`... part of what this issue cites is branch-only code — it does not exist on `master` and never did."* I confirmed this directly:
```
$ git merge-base --is-ancestor 2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7 HEAD && echo yes || echo no
no
$ git branch -a --contains 2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7
  remotes/origin/claude/jls-virtual-hardware-linux-njsoma
```
The issue's own §2 boast — "`git diff --stat 2d0ca9d..HEAD -- src/ test/ pom.xml config/` (no output)" — was true only transiently, at filing time, against whatever HEAD then was; it is not true now, and the issue provides no mechanism to notice when it stops being true short of a human (or another review pass) re-running the command. **Recommendation:** re-pin the issue to a commit reachable from `master`, or explicitly convert every "measured" claim into "claimed, unverified on master" until re-derived.

### 3. [HIGH] Load-bearing commit hashes used as "measured precedent" don't exist on the branch anyone will actually build from

### 5. [MEDIUM] Ownership of the `SaveTags` and `HdlExporter` rows is contested between #372 and #488, and the issue's own §8/§7.12 assert ownership a sibling comment says belongs elsewhere
A comment on this issue draws the boundary explicitly: *"#372 owns... plus the inventory `docs/registry-keyed-tables.md` itself... #488 owns `SaveTags.WRITABLE`... the one totality assertion that pins the (registry → SaveTags) direction nobody checks."* But §7.12 of this issue still asserts *"`FieldExtend`/`RegisterFile` are already in `SaveTags` (`970db41`)"* as a **compatibility invariant this task relies on holding**, and §8 still lists `SaveTags.WRITABLE` as a row *this issue's own inventory* should record as covered. ### 6. [MEDIUM] The verification protocol is largely self-attested prose, and the issue's own history shows that fails
Multiple Definition-of-Done items ask for a *paste of command output into the PR* rather than an automated, CI-checked artifact: "command and output recorded in the PR" (P1–P7), "outcome... recorded in the PR" (§10 falsification criteria), "that command and output pasted in the PR" (P5). Nothing in the issue specifies who re-runs those commands against the merge-base at review time versus trusting the pasted transcript. This is not a hypothetical gap — it is the exact mechanism that produced findings #1–#3 above: the issue's own filer pasted output against a since-orphaned commit, and it took three separate follow-up passes to catch it, one of which (comment 3) explicitly says the false credit had already "propagated" into two other issues' close-out decisions before being caught. A reviewer who is not equally suspicious will accept the same kind of transcript at face value. **Recommendation:** any PR closing this issue should re-run P1–P7 against `HEAD` at merge time as part of CI, not accept pasted output from an arbitrary earlier point.

### 7. [MEDIUM] Scope bundles five materially independent workstreams behind one issue number
§8's checklist spans: (a) writing and sweeping for `docs/registry-keyed-tables.md`; (b) fixing two GUI tables for `RegisterFile`/`FieldExtend`; (c) rewriting `DialogConstructionSmokeTest`'s 25 hand-written methods into a parameterized form; (d) resolving the `ElementVocabulary` registry-delegation-vs-literal decision in coordination with #170's owner; (e) adding CLI incompatible-flag-pair rejection to `JLSStart`/`FlagSpec`, a behavior-breaking CLI change unrelated to GUI rendering. Item (e) in particular is not a "registry-keyed table" in any sense the title or abstract advertises — it rides along because a sibling planning issue (#315) grouped it in as "the same shape of hole," which is an assertion, not a demonstrated relationship (a CLI flag conflict has nothing to do with `ElementRegistry`). Bundling a GUI rendering fix, a UI test-harness rewrite, a cross-issue collaboration-security coordination point, and a CLI behavior break into one PR-shaped deliverable makes atomic review difficult and raises the chance that an unrelated failure (e.g., #170's owner being unavailable to bless the `ElementVocabulary` decision) blocks landing the uncontroversial renderer/dialog fix. **Recommendation:** split (e) out to its own issue; it has no dependency on the registry inventory work.

### 9. [LOW] Undisclosed backward-compatibility risk in the CLI behavior break
§7.1 states plainly that the CLI change moves "an invocation that today is accepted-and-partly-ignored" to a "non-zero exit." That is an honest disclosure, but unlike the analogous behavior-break in sibling issue #314 (which explicitly adopts a "load-and-report for one epoch, then reject" migration policy specifically to protect users of the old, silently-tolerant behavior), this issue proposes an immediate hard break with no deprecation window for graders/instructors who might have scripts invoking, e.g., `-p` and `-v` together today relying on one being silently dropped. Given `README.md`'s stated audience (autograders, CI pipelines consuming the batch interface — see "Container image (batch mode only)" and `docs/batch-interface.md`'s "documented stability contract" framing), a same-release hard break is a real compatibility hazard the issue doesn't weigh against its own project's stated stability contract for the batch interface.

- **Citations that don't depend on the orphaned evidence commit check out**: `PaletteContractTest`'s exemption set and method name, `DialogConstructionSmokeTest`'s 25 `@Test` methods, `FlagSpec`/`CliFlagTableTest`'s five existing tests, `SealedHierarchyTest`'s existence, and `ElementVocabulary`'s javadoc deferring to #78 — all verified present and matching as described.

## Bottom line

The problem this issue targets is real, narrowly scoped, and well-understood technically. But the issue-as-written is not safe to hand to an executor without a body edit: its first actionable Method step would write false data into the deliverable, its dependency graph to a sibling task is stale by a filed-but-unlinked issue number, and its entire evidentiary basis sits on a commit the maintainer has already disclaimed. The pattern of three separate after-the-fact corrective comments on a single still-open issue is itself a signal that this document format is one an executor (LLM or human) can superficially satisfy — pasted transcripts, cited-but-unreachable commits — without the underlying claims being true, which is a methodological risk for every other issue authored the same way, not just this one.
