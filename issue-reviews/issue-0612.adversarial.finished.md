# Issue #612: TASK-C558-1: a .dig file parses as untrusted XML into an in-memory Digital model — XXE-proof, bounded, with its test sections preserved
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of the ask

Parse Digital's (`hneemann/Digital`) `.dig` file — XStream-serialized XML — into an in-memory model, hardened against XXE-class attacks, size/depth bombs, and malformed input, while preserving embedded test sections byte-recoverably for a downstream consumer (#562). Explicitly parsing-only: element mapping, layout, and reporting are other tasks (#558's siblings).

## Findings, most severe first

**1. (HIGH) The issue's own framing misstates the state of the codebase it depends on.** The Outcome paragraph claims this work happens "to the #38 standard that CAP-16 already holds `.circ` to" — implying an existing, working precedent to model against. That is false at present: `git grep`-equivalent search of `src/` for `DocumentBuilderFactory|SAXParser|XMLInputFactory` returns nothing (confirmed independently here, matching #451 O2's own finding), there is no `jls.imp.circ.CircReader` anywhere in `src/`, and the `.circ` importer that would embody "the CAP-16 standard" is itself issue **#451 (TASK-0054), still open**, and #451 is `blocked_by: [404]` (TASK-0003), which is also **open**. So no hardened XML parser exists in this tree yet, and CAP-16 does not "already hold" anything to that standard — it merely states the requirement on paper. Compounding this: #612's own `ordering_after: [314]` omits #323/#451 entirely, even though #558 (#612's parent feature) lists `#323 FEAT-025 ("the .circ path defines the shared infrastructure and the importer discipline")` as an explicit prerequisite, and this issue's own newest comment (2026-08-08) states "#612 is that second caller" after #451. Nothing in #612's machine-readable metadata (`ordering_after: [314]` only) actually blocks it on #451/#323, so a scheduler that respects only the stated metadata could pick up #612 *before* #451 lands — at which point #612, not #451, becomes the tree's actual first XML parse, contradicting its own "already holds" framing and leaving the executor with no in-tree hardened-parser example to consult, review, or diff against (the exact risk #451 §7.5 and §11 warn about: "a mistake here has no counterexample to be caught against").
   - *Recommendation:* either add `451` (or `323`) to `ordering_after`, or strike the "already holds" claim and state plainly that this may be the tree's first or second XML parse depending on execution order, with the hardening written and reviewed from scratch either way.

**2. (HIGH) The threat model in AC-1 omits XStream's own deserialization/RCE surface, which is arguably the more dangerous half of parsing a file this format's own producer describes as "XStream XML."** AC-1 lists four hardening vectors — "XXE, billion-laughs, external DTD, SSRF-via-entity" — all classic XML-entity attacks. But `.dig` is not merely XML; it is the *serialized object graph* of a library (XStream) whose default unmarshalling maps XML tag names directly to Java class names and invokes constructors/setters/reflection accordingly. Unless configured with a strict class-permission allowlist (`XStream.addPermission`), that mechanism is a well-documented remote-code-execution vector (the Java ecosystem's counterpart to Python `pickle` or Java native serialization gadget chains) — completely orthogonal to and untouched by disabling external entities or bounding document size. Nothing in the issue's acceptance criteria, boundary notes, or outcome statement says whether the *actual* `com.thoughtworks.xstream.XStream` library will be invoked to deserialize the file (catastrophic if so, since arbitrary classes on the runtime classpath become instantiable from attacker-controlled tag names) versus a from-scratch hardened XML reader that treats tag/attribute text as inert data (safe, and consistent with this codebase's own documented discipline — ARCHITECTURE.md's save/load section notes JLS's own loader routes `ELEMENT` tags through `SaveTags.resolve` specifically so "tag text never reaches `Class.forName`"). An implementer taking the path of least resistance — "just use the library the source format was written with" — would introduce a security defect none of AC-1's four named tests would ever catch.
   - *Recommendation:* add an explicit acceptance criterion: the parser never performs reflective/class-mapped deserialization of any kind (no `XStream` library dependency, no `Class.forName` on document content); tag and attribute names are read only as data, mirroring `SaveTags.resolve`'s discipline. Add a dedicated test asserting a `.dig` file naming an arbitrary/dangerous class (e.g. `java.lang.ProcessBuilder`) as an element tag is rejected or ignored as unrecognized input, never instantiated.

**3. (MEDIUM) AC-2's size/depth bound is unspecified and untested against real data, making it gameable.** "Oversized and deeply-nested documents refuse loudly with a named bound rather than exhausting memory" names no number and requires no calibration. Compare sibling task #451, whose corresponding prediction (P9) requires assembling **a corpus of published `.circ` files** with accept/reject rates "recorded in the PR as numbers," explicitly because "fixtures are not a corpus" and a hand-picked bound proves nothing about real-world files. #612 has no equivalent requirement. An executor can satisfy the letter of AC-2 with an arbitrary constant — too low (legitimate large `.dig` circuits from real courses get rejected) or too high (no real memory protection) — and no acceptance criterion would catch either failure mode.
   - *Recommendation:* require the bound to be exercised against at least one real, published `.dig` file (Digital ships example circuits in its own repo, GPL-compatible per #451's licensing note) and record accept/reject behavior, not just a synthetic bomb fixture.

**4. (MEDIUM) AC-1's four-vector taxonomy silently narrows the precedent it claims to follow.** The issue cites "#38 standard, CAP-16 AC-5 standard" (via #558) as the bar. #451 — the concrete task instantiating that CAP-16 standard for `.circ` — enumerates **five** distinct hardening vectors in its own falsifiable hypothesis (H3/P6): DOCTYPE declaration, external *general* entity, external *parameter* entity, billion-laughs expansion, and a `file:`-URI system identifier. #612's AC-1 collapses this to four ("XXE, billion-laughs, external DTD, SSRF-via-entity"), folding general and parameter entities into one undifferentiated "XXE" bucket. If the implementation disallows DOCTYPE declarations outright (the OWASP-recommended, and #451's own, primary defense), this distinction is moot in practice — but the issue doesn't say so, and "one test per attack vector" against a four-item list is a weaker falsification net than the five-item list its own stated precedent uses.
   - *Recommendation:* either explicitly adopt #451's five-vector list for consistency across the sibling tasks (#612/#621/#629's shared-discipline comment argues for exactly this kind of consistency), or state the DOCTYPE-blanket-refusal rationale for why four suffices.

**5. (LOW) No explicit "no new Maven dependency" constraint, unlike its own cited precedent.** #451 states plainly: "`javax.xml` from the JDK — no new dependency; a third-party XML library would add a supply-chain surface to the one parse in the tree." #612 is silent on this. Given Finding 2, this silence is not merely a style gap — it leaves room for an implementer to add the actual `com.thoughtworks.xstream` dependency (compounding the RCE risk) or an unaudited third-party XML library, neither of which the issue rules out.
   - *Recommendation:* copy #451's explicit "JDK `javax.xml` only, no new dependency" constraint verbatim.

## What's solid

- The scope boundary is clean and well-isolated: parsing only, with element mapping (TASK-C558-2), layout (TASK-C558-4), and the report/atomic-import discipline (TASK-C558-5) explicitly deferred to sibling tasks — a real, testable slice rather than a vague "import Digital files" ask.
- AC-3 (malformed/truncated input refuses with a located diagnostic, no partial model) and AC-4 (embedded test sections byte-recoverable) are concrete, specific, and directly testable — no ambiguity in what "done" means for either.
- The "no code path from document content to filesystem or network" boundary note is exactly right for this threat class and correctly generalizes beyond just XXE.
- The posted comment on this issue (2026-08-08) does real, useful work distinguishing #612/#621/#629 from each other by threat surface (XML entities vs. JSON structural limits vs. numeric-overflow-in-text) — that differentiation is accurate and the "not duplicates" call is correct.

## Net assessment

The task decomposition and the parsing-only scope are sound, but this is a security-hardening issue whose acceptance criteria have a real gap (XStream's own deserialization surface, distinct from and more dangerous than the XXE-class attacks actually enumerated), whose central "we already hold this to a standard" claim is unsupported by the current codebase (the standard-setting sibling task is itself unbuilt and unlanded), and whose size/depth bound is specified with no calibration requirement. None of these are unfixable, but the security-critical gap in particular should not ship un-remediated in an issue whose entire purpose is untrusted-input hardening.
