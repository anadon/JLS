- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

The technical premises (O1–O9) are unusually well grounded: I checked `src/jls/elem/SubCircuit.java`, `src/jls/Circuit.java`, `src/jls/elem/Element.java` and `docs/file-format.md` against the current tree and every cited line/behavior (inline per-instance save at `SubCircuit.java` L282-289, the `setValue` String arm at L311-326, the canonical sort in `Circuit.save` using `Element::getStableId`, `BASE_ATTRIBUTES` in `Element.java`, the no-`FORMAT`-bump evolution policy in `docs/file-format.md` §9) matches. That rigor makes the two failures below more damaging, not less: this issue holds itself to an "every citation verified" standard and then fails it in a load-bearing place, and it contradicts its own parent feature on the one open design decision it labels "blocks execution."

## Findings, most severe first

**1. [High] The evidence corpus this issue's strategic justification rests on does not exist in the repository.** §1 Background quotes `docs/plan/evidence/BRIEF.md` §13 (Decision D10: *"the absence of the capability is the PREMISE OF THE QUESTION, not a rebuttal to it"*) and §12 (Decision D7: *"Circuit libraries are DATA, not plugins... This is also the biggest single win"*) as the basis for overriding `docs/standards-adoption/08-ipxact-export.md`'s own "do not build this yet" verdict — i.e., the entire justification for why TASK-0039 should be executed now rather than deferred rests on D7/D10. `find / -iname "BRIEF.md"` and `ls docs/plan` both return nothing; `docs/plan` doesn't exist at all in this checkout, only `docs/standards-adoption` and `docs/capability-roadmap` alongside flat `docs/*.md` files. This is not unique to #417 — sibling issues #340, #357, #450, #552, #766 all cite the same missing file, so it looks like a corpus-wide provenance defect rather than a one-off typo — but #417 leans on it specifically to license going ahead against the cited prior art's explicit "not adopted" verdict. Recommendation: land the missing planning corpus first, or restate D7/D10 as an in-tree, self-contained maintainer statement (a paragraph in this issue or in `docs/grand-architecture.md`) so the override doesn't depend on an unauditable document.

**2. [High] The collision policy §7.10/P5 specifies directly contradicts the parent feature's own recommended policy for the exact case this task covers.** #417's own Open Question 1 states: *"Options: (a) **hard refusal** — recommended, and what §7.10 stage 4 and P5 specify... (b) diagnostic plus auto-rename... **Blocks execution** of the collision half."* But #340 (FEAT-016, `part_of_feature` of this very task) already answered this question with an asymmetric policy: *"Recommended default: (a) for a library resolved by reference, **(b) for a definition inlined in a circuit file**, with the asymmetry stated normatively."* Every collision #417 can actually produce is the inlined case — TASK-0040 (the library container) doesn't exist yet, so at the point this task ships there is no "library resolved by reference" to collide inside; P5's own worked example is "two `SubCircuit` blocks in one file." By #340's own recommendation that is precisely the case that should get (b) — diagnostic plus disambiguating rename — and #417 instead hard-refuses it. This isn't a stylistic disagreement; §11 Threats to Validity of #417 admits the likely trigger: *"P5's refusal will fire on files whose authors both left the defaults"* — i.e., ordinary classroom files with unset vendor/library/version will get a hard load refusal under this issue's chosen policy, which is exactly the harsh outcome #340 recommended avoiding for inlined definitions. Recommendation: either #417 must justify diverging from #340's recommendation explicitly (and update #340's Open Question 1 to match), or adopt #340's asymmetric policy — which changes §7.10 stage 4, P5's expected observation, and the `DefinitionIdentityTest.sameDefidDifferentDigestIsRefused()` test's semantics.

**3. [Medium] `docs/component-naming.md` already exists and is about something unrelated; the issue's materials list doesn't check.** §6 Materials & Apparatus lists `docs/component-naming.md` as "the home for the version-string rule; must be created or extended," and Open Question 4 asks where it "lives relative to `docs/file-format.md`" as if its content were still undecided. The file already exists (issue #210) and its entire subject is the Swing UI component naming scheme (`palette.<slug>`, `dialog.<slug>.<field>`, `setName()` for the accessibility/automation harness) — nothing in it concerns subcircuit definitions, vendor/library/version strings, or VLNV semantics. "Component" means a UI widget throughout that document, not a reusable circuit/subcircuit. Silently appending vendor:library:name:version semantics to a document titled "Stable Component Naming Scheme" that already has an established, tested meaning for "component" will read as two unrelated specs sharing a title. Recommendation: name the new content's home explicitly (e.g. extend `docs/component-naming.md`'s scope note to disambiguate "UI component" vs "circuit definition component," or put the VLNV rule in `docs/file-format.md` directly, which the issue itself says "owns the grammar").

**4. [Medium] P4 ("renaming an element changes the digest") is untestable, as stated, for most element types.** The projection elides by attribute name over `BASE_ATTRIBUTES` (`id`, `x`, `y`, `width`, `height`, `trpos`, `sid`), which contains no `name` field — element names are subclass-specific attributes. Grepping `src/jls/elem/*.java` for `StringAttribute("name")` finds it on only 8 of the ~30 element types (`JumpEnd`, `JumpStart`, `Memory`, `Pin`, `Register`, `RegisterFile`, `StateMachine`, `TruthTable`); ordinary gates (`AndGate`, `OrGate`, `NotGate`, etc.) carry no per-instance name at all. `renamingAnElementChangesTheDigest()` (§8 Method) is therefore only exercisable on a narrow subset of element types, and the issue's "names are structure, not annotation" framing (Open Question 2) reads as a general claim about "an element" when it can only be demonstrated on named elements. Recommendation: state P4/OQ2 in terms of the specific named-attribute element types it actually applies to, and add an explicit note (or falsification criterion) covering what happens to the digest when a *port/pin* name on a `SubCircuit`'s own I/O changes — that is the case that actually matters for downstream HDL consumers (§ Intended Audience) and it isn't named anywhere in §5's predictions.

**5. [Low] "the four-field name every interchange format already assumes" overstates the comparison set.** IP-XACT's VLNV genuinely is four-field, but Yosys JSON netlist module names are single hierarchical tokens (no vendor/library/version fields), and `.circ` (Logisim) library references are a filename plus a component name, not a VLNV tuple. Only IP-XACT actually assumes this shape; the other two examples cited in the Intended Audience section don't. This doesn't break the design (a VLNV-shaped `defid` is still a reasonable choice for IP-XACT alignment), but the "every interchange format already assumes" claim should be softened to avoid setting an expectation §7 doesn't need to meet.

**6. [Informational] P7's file-rename half is a tautology, not a test.** "Rename the enclosing file; observe equality" — the digest is computed purely over `Circuit.save`'s nested-block text (§7.10 Stage 1-3), which never mentions the enclosing filename in the first place, so this half of P7 is true by construction and adds no falsification power beyond the save/load round trip already covered by the first half. Harmless, but worth pruning from the Definition-of-Done checklist so a reviewer doesn't waste PR-comment space "verifying" a property that can't fail.

## What's solid

- O1–O9's code citations (SubCircuit.save inlining, setValue's String arm, the canonical stable-id sort, BASE_ATTRIBUTES, the FORMAT-header/CIRCUIT-line asymmetry for nested blocks, StateMachine's documented significant sequence) all check out against the live tree, not just the stated `2d0ca9d` commit.
- The no-FORMAT-bump decision (H3/P9) is consistent with `docs/file-format.md` §9's actual evolution policy text ("adding a new attribute... no bump needed... Writers SHOULD prefer a bump... whenever dropping the attribute would change simulation behavior") — `defid`/`defdigest` don't affect simulation, so the policy genuinely supports no bump; this part is correctly reasoned, not just asserted.
- The headless constraint (H4/P8) is correctly scoped: `jls.elem` is covered by `HeadlessCoreRatchetTest`'s `CORE_PACKAGE_PREFIXES`, confirmed in the test file, so the constraint is enforced by existing infrastructure rather than trust.
- The scope boundary against #340/#357 (no library container, no parameterization, no `FORMAT` bump — deferred explicitly to TASK-0041) is clean and doesn't smuggle in adjacent work.
- The "recompute, never trust" rule for a loaded `defdigest` (§7.11) is the right call given `.jls` is documented hostile input (issue #38) and is stated plainly rather than left implicit.

## Recommendation

Resolve finding 2 before filing implementation work — it is a real, sourced contradiction between this task and its own parent feature on the single decision both call blocking, and picking wrong here changes the shipped diagnostic's severity for the common classroom case. Fix finding 1 by grounding the "build now, not later" justification in something that exists in the repo. Fix finding 3 before touching `docs/component-naming.md` so the PR doesn't need a second pass to disentangle two unrelated "component" vocabularies. Findings 4-6 are worth a revision pass but don't block starting the digest/`DefinitionId` implementation itself.
