# Issue #817: TASK-C168-4: two real machines on a LAN join and verify by reading glyphs aloud, and the record says which machines, which build, and what was on screen
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

#817 is the manual-evidence closing task (I3) for feature #168 (collab
Stage 1a: P2P transport + SAS verification). It asks a human to run the
Share/Join/Verify flow between two real hosts on a LAN, compare seven SAS
glyphs out loud, and write the result down. The intent is sound — a
loopback unit test genuinely cannot stand in for a real network — but the
issue is both premature (its prerequisites do not exist in the repo yet)
and loosely enough specified that its acceptance criteria can be satisfied
without the claim they exist to support actually being true.

## Findings, most severe first

### 1. [High] Not actionable yet — the code this task exercises does not exist

`ordering_after: ["TASK-C168-3 (Verify dialog + glyphs)"]` names one direct
predecessor, but #816 (TASK-C168-3) itself is `ordering_after` #814
(glyph assets) and #815 (Share/Join dialogs) — neither of which has
landed either. Checked directly against this checkout:

```
$ find src/jls/collab -maxdepth 2 -type d
src/jls/collab, src/jls/collab/net, src/jls/collab/session,
src/jls/collab/op, src/jls/collab/crdt
```

There is no `src/jls/collab/ui` at all. `src/jls/collab/net/Sas.java`
says so explicitly in its own javadoc: *"the images are a follow-up asset
task, the names are the contract"* (`Sas.java:18`), and
`package-info.java:54-55` calls the dialogs *"the following #168
slice."* The most recent comment on parent #168 (2026-08-08,
`issuecomment-5227019162`) confirms the same at commit `2d0ca9d`: *"there
is no `jls.collab.ui`."* So there is no Share dialog, no Join dialog, no
Verify dialog, and no glyph image to display — the three things #817
proposes to run and screenshot are all unbuilt. Filing/grooming #817 as
independently actionable right now invites someone to attempt AC-1–AC-3
against nothing, or to backfill a "record" once the dialogs exist without
re-deriving whether this issue's own criteria are still accurate at that
point (e.g., whether the Verify dialog even has the "both panels
rendered" gate this record is supposed to exercise).
**Recommendation:** mark #817 blocked on #814/#815/#816 explicitly (not
just its one direct predecessor), or don't groom it until #816 closes.

### 2. [High] The acceptance criteria cannot distinguish a real run from a fabricated one

Nothing in AC-1–AC-5 requires evidence that is hard to fake. The record
is: prose ("two humans compare... out of band"), screenshots (captured
and supplied by the same executor on both ends), and a written procedure.
Given this repository's own visible practice — every comment on #168 is
explicitly "_Generated by Claude Code_" and describes agents landing
work — an executing agent has every incentive and every opportunity to
write a plausible two-machine narrative and a pair of screenshots taken
from two terminal windows on one box, or from two VMs that never actually
exercised distinct network paths. AC-1 ("executed between two distinct
hosts... both operators see matching SAS glyphs") and AC-3
("screenshots... with platform, JDK and build identified") are both
satisfiable by self-reported text and self-captured images with no
independent corroboration (no second GitHub identity co-signing, no
artifact — log line, connection tuple, packet capture — that structurally
requires two distinct machines to produce). **Recommendation:** require
at least one piece of evidence that is mechanically hard to fabricate
from a single machine: e.g., cite the differing local IP/hostname pair
that `SessionListener`/`SocketSession` would have logged or that `ip a`
on each box shows, or require a second person (different GitHub account)
to comment confirmation rather than trusting one executor's write-up end
to end.

### 3. [Medium] "Not loopback" is a loophole, not a bar

AC-1 says "over a LAN (not loopback)"; the Outcome paragraph says "two
separate physical **or virtual** machines." Two VMs on one hypervisor
joined by a host-only or NAT virtual switch are provably "not loopback"
(no `127.0.0.1`) yet may never touch a physical NIC, external switch, or
per-host firewall — exactly the conditions AC-5 wants findings about
("timeouts, firewall behaviour, address selection"). The Outcome section
itself states the goal is testing "two hosts and a real network," but the
AC as written lets an executor satisfy the letter (two VMs, no loopback
address) while defeating the purpose (no real network segment involved).
**Recommendation:** either require bridged networking with host-visible,
routable IPs (and say so), or require physical hardware; and require the
write-up to name the topology (bridged / NAT / host-only / physical) so a
reviewer can tell which was used.

### 4. [Medium] Evidence-location requirement is an either/or with no floor

AC-2: "written down in-tree (**or** in the closing comment on #168)."
This repo otherwise insists on permalinked, commit-pinned evidence — every
comment thread on #168 cites specific file/line permalinks at named
commits, precisely because comments and issue text churn (the thread
shows issues repeatedly merged, absorbed, and REPLAN-restructured, e.g.
`issuecomment-5154380202` rewriting #168's own body wholesale). A
GitHub-comment-only record for the one criterion CI can never
independently re-check is weaker than every other evidentiary norm this
repo holds itself to, and it isn't even durably part of the repository —
a clone or mirror loses it entirely. **Recommendation:** make the in-tree
document (e.g. `docs/collab-lan-verification.md`) the required artifact;
let the closing comment merely link to it.

### 5. [Medium] AC-5 is unbounded scope creep dressed as an acceptance criterion

"Any discrepancy found... is recorded as a finding with a named owner
issue rather than smoothed over" obligates whoever runs this task to also
triage and file new issues for whatever surfaces (a firewall prompt, an
address-selection ambiguity, a timeout) — with no cap on count or
severity, and no statement of whether such a finding blocks this issue's
own closure. Given `band_mw: "0.25-0.5"` implies a small, fixed-size task,
an environment that turns up even one nontrivial finding (plausible: this
is the *first* time the transport runs on a real network instead of
loopback or the in-memory `LoopbackTransport`/`ChaosTransport` doubles)
turns a bounded evidence-gathering task into an open-ended one.
**Recommendation:** state explicitly that environmental findings are
filed but do not block this issue's closure, while a protocol-level bug
routes to #168's REPLAN process instead of being absorbed here silently.

### 6. [Low] AC-4 partly duplicates coverage #816 is already committed to producing

"A reconnect... shows no second verification prompt" is (a) already
pinned at the model layer by `KnownPeersTest` (per #168's Prior Work) and
(b) explicitly #816's own AC-3 at the dialog layer via a display-tagged
test. Re-demonstrating it by hand on two real machines has some value as
belt-and-suspenders for the "human, real-network" claim, but the issue
doesn't say why the automated layers aren't sufficient for this specific
sub-claim — worth a one-line rationale, not a blocking defect.

### 7. [Low] Platform coverage gap the issue doesn't acknowledge

AC-1 pins the run to Linux only, matching #168's Linux-GUI-lane gating for
the dialog work. But README.md advertises Windows, macOS, Linux and
RISC-V installers as first-class distribution targets, and AC-5's
"firewall behaviour" framing reads as if the network path is being
generically validated — it will only ever be validated on Linux by this
task or, as far as either issue reveals, by any sibling task. Not a
defect in #817's internal logic, but a coverage limit worth stating
plainly in the record rather than leaving implicit.

## What's solid

- Correctly scoped as the one CI-can't-verify claim (I3) rather than
  re-litigating transport or dialog design — matches #168 §5's own
  framing.
- AC-3's requirement to name platform/JDK/build alongside screenshots is
  concrete and checkable by inspection.
- Recognizing that a loopback/in-memory test (`LoopbackTransport`,
  `ChaosTransport`) cannot stand in for a real two-host network is the
  right instinct — real NICs, real address selection, and real firewalls
  are exactly the class of thing those doubles cannot exercise.

## Bottom line

The premise is right, but as written the task is (a) not yet executable
against real code, and (b) gameable on every criterion that matters for
its stated purpose (distinct hosts, real network, durable record). It
needs the dependency chain made explicit and the AC tightened — evidence
requirements, network-topology floor, and evidence location — before a
"the feature closes on evidence rather than assumption" claim actually
holds.
