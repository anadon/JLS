# Issue #622: TASK-C559-2: every CircuitVerse element maps to a JLS element by semantics from a written table, or refuses by name
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what's being proposed

TASK-C559-2, one of five tasks under FEAT-C29-3 (#559, the `.cv`/CircuitVerse importer): turn the parsed CircuitVerse model from TASK-C559-1 (#621) into JLS elements and nets via a written, code-read table in `docs/`, refusing anything with no semantic equivalent, and preserving net-partition connectivity. It explicitly excludes the `delay` attribute (owned by #626/TASK-C559-4) and report carriage (owned by #556). Band 1-2 mw.

## Findings, most severe first

**1. (High) The declared dependency graph contradicts the issue's own prose.** The `ordering_after` machine block lists only `["TASK-C559-1 (the parsed model this maps from)", 323]` — no #556. Yet the Boundary notes state as a real, load-bearing dependency: "Report entries go through #556's shared contract; this task supplies content, not carrier." A task that must emit into a shared contract it does not itself define has a real ordering dependency on that contract existing, and the sibling task #626 (TASK-C559-4) is more precise about exactly this kind of dependency — it names a specific task, `"TASK-C556-1 (the disposition vocabulary this uses)"`, in its own `ordering_after`. #622 should do the same (cite the concrete #556 sub-task that defines the schema/vocabulary this task's "content" must conform to) rather than silently omitting the dependency from the machine block that #323 and #556 both treat as the authoritative, mirrored ordering record ("LINK PASS" convention, #323's own text). As written, a scheduler reading only the YAML header would start this task before its report-shape dependency is even identified, let alone landed.

**2. (High) AC-1's "read by the code" is ambiguous between two very different architectures, and the issue picks neither.** "The mapping is a written, reviewable table in `docs/`... read by the code rather than restated in it" could mean (a) production code parses the `docs/` document as data at runtime/build time, or (b) a test cross-checks a hand-written table in `docs/` against a separately hand-written map in code — the pattern this codebase actually uses elsewhere (`docs/extension-points.md` + `ExtensionPointCatalogTest`, `docs/file-format.md` + `FileFormatSpecTest`, per ARCHITECTURE.md's "Recorded decisions" section). These are materially different engineering commitments: (a) requires a doc format stable and structured enough to parse (table syntax, YAML front matter, or similar) and a parser with its own hardening story; (b) requires none of that, just doc discipline enforced by a test, and "restated in it" becomes trivially true of the *test* even if the runtime code has its own independent copy. Nothing in AC-1 states which is intended, and no acceptance criterion distinguishes them — an implementer can satisfy the letter of AC-1 with interpretation (b) while producing exactly the "restated in the code" outcome the criterion says to avoid (the docs table is transcribed, not consumed).

**3. (High) No acceptance criterion requires breadth or a real corpus, so all four ACs can pass on a near-empty mapping table that defeats the parent feature's actual goal.** Contrast with #323 (the `.circ` precedent this issue explicitly invokes for its collision rule): #323's Integration Criteria gate on a *corpus* of public files with a mechanical net-partition equality per file (I1) and a committed accept/reject table (I6) — "the estimate has been replaced by a measurement." #622 has none of that. AC-1 requires a table exists and is "read by the code" for whatever rows it happens to contain; AC-2 requires *one* fixture with a name collision; AC-3 requires unmapped elements refuse (which is easy — refuse everything); AC-4 requires net-partition equality on *an* imported circuit, not named as a corpus. A table covering three trivial gate types with everything else refused by name would pass all four ACs of #622 as literally written, while leaving #559's actual AC-1 ("one real published `.cv` project imports with zero unexplained losses") unreachable. The task that is supposed to make real course material openable carries no criterion that measures progress toward that on real material — it is entirely satisfiable in the abstract.

**4. (Medium-High) The upstream contract this task consumes (#621/TASK-C559-1) does not clearly supply what AC-4 needs.** AC-4 requires "an imported circuit's net partition matches the source's, asserted structurally" — i.e., wire/node-level connectivity data must survive parsing. But #621's own acceptance criteria describe only "per-circuit structure and inter-circuit references, so TASK-C559-3 has a hierarchy to rebuild" (AC-4 of #621) — framed entirely around subcircuit hierarchy for TASK-C559-3, with no explicit mention of preserving wire/node/net-level connectivity for TASK-C559-2's use. If #621's parsed model doesn't retain per-wire endpoint data at the granularity #622's AC-4 needs, this task cannot assert net-partition equality without either amending #621's contract (not this task's to do, per its own boundary framing) or quietly extending the parser under a different task's number. This is exactly the kind of cross-task interface gap #323 calls out by name for a different pair of components (`NetlistImporter.Builder`'s promotion, Open Question 4) — here it isn't even flagged as an open question.

**5. (Medium) AC-2's collision fixture has no concrete instance named, unlike its own cited precedent.** The issue leans on #323's collision rule ("#323's name-collision rule is format-agnostic and applies here unchanged") and #323 grounds that rule in a *specific, real* case: JLS's own `HdlExporter.java:84` documents `ShiftRegister` as combinational while the source tool's same-named part is sequential. #622's AC-2 asks only for "a fixture with a cross-tool name collision" — no CircuitVerse element is named as the actual colliding case. Without a real instance identified up front (the way #323 did the work of finding one), an implementer can satisfy AC-2 with a synthetic, invented collision that proves the mechanism works in principle but was never checked against CircuitVerse's actual element names, which is the entire point of the rule.

**6. (Medium) No CircuitVerse version/schema is pinned, and no source of truth for its element semantics is cited.** #323 grounds its Logisim-Evolution work in a specific evidence commit and even reasons explicitly about the licensing risk of reading the source tool's code to replicate its semantics (Open Question 2: clean-room vs. documented compliance). #622 names no CircuitVerse version, no link to CircuitVerse's simulator source or save-format docs, and raises no analogous question about how "semantics" is to be determined authoritatively for a live, externally-evolving web project. Given CircuitVerse element behavior is defined by its own JS implementation (not a public spec), "map by semantics" silently assumes someone reads that source — a licensing/attribution question #556's sibling issue #559 also leaves unaddressed (noted independently in that issue's own review), and #622 inherits the gap without repeating even #559's partial framing of it.

**7. (Medium) Feasibility/cost: ordering_after names an entire unlanded, cost-disputed feature (#323), not a specific artifact within it.** #622 (band 1-2 mw) is ordered after #323 in full — a feature whose own Open Question 1 states its cost band (6-12 mw) exceeds its own task-row sum (4 mw) by up to 3x and is explicitly "superseded," and which is itself `blocked_by` #314 and #349 (both open). If `ordering_after: 323` means "wait for #323 to close," a 1-2 mw task is gated behind a feature whose true cost isn't yet known and could run long past its stated band. If it instead only means "reuse #323's *already-written* collision rule text" (which is quotable today, independent of #323's implementation landing), then citing the whole issue number in the scheduling machine block overstates the actual dependency and should instead cite the specific rule/section, not the issue. Either reading needs the issue to say which one it means; right now it's read either as an inflated blocker or a mis-scoped citation.

**8. Solid, no rework needed:**
- The delay-attribute carve-out ("deliberately not handled here... TASK-C559-4 owns saying so") is a clean, correctly-scoped boundary and matches #626's own framing exactly — no drift between the two issues on this point.
- AC-3's "refused by name... never approximated" is the right default posture for an importer and is consistent with the no-partial-circuit / no-silent-loss discipline documented at `NetlistImporter.java:46-47` and reused throughout this planning corpus (#323, #559).
- The report-carrier/report-content split ("this task supplies content, not carrier") is architecturally sound in principle — it's the *missing citation* (finding 1) that's the problem, not the split itself.

## Verdict rationale

The core shape — a reviewable, code-consumed mapping table with a hard refuse-by-name fallback and a structural connectivity check — is the right design and correctly inherits #323's proven pattern in spirit. But the issue has a real citation gap between its own prose and its machine-readable dependency list (#556), an ambiguous "read by the code" requirement that admits a much weaker implementation than it appears to require, no criterion that ties completion to any real CircuitVerse project or corpus (so it can be satisfied while defeating #559's actual goal), an unverified assumption about what data #621 hands it, and no named concrete collision case for AC-2 despite citing one that exists for `.circ`. These are fixable with sharper wording and cross-references, not a redesign — hence needs-rework rather than should-not-proceed.
