# Issue #769: TASK-C578-2: a validator checks a kit directory against the convention and names what is missing — and CI runs it over every shipped kit
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of the ask

TASK-C578-2 (task tier, `part_of_feature: 578`, `band_mw: 0.5-1`, `ordering_after: ["TASK-C578-1"]`) wants a validator that (1) checks a kit directory against the TASK-C578-1 (#767) convention and names each missing/malformed part with a location, (2) runs in CI over every shipped kit and fails the build on a violation, (3) distinguishes missing-required from missing-optional from present-but-malformed, and (4) validates the Donzellini pack (#575) and any other in-tree kit clean, with the run recorded.

## Findings, most severe first

**1. AC-4 requires validating a kit that does not exist yet, and #769 does not declare that dependency directly — it leans on an unstated transitive chain.**
`grep -ri kit` and `grep -ri donzellini` across the tree turn up nothing that is a course-kit artifact (only unrelated "toolkit" substring matches); #575 (the Donzellini pack) is open with AC-1 ("At least 8 labs ship") unmet. #769's own `ordering_after` lists only `["TASK-C578-1"]` (#767) — not #575. The chain only holds because #767's *own* `ordering_after: [575, 576]` happens to route through #575 first. If a reader (or an implementer) looks at #769 in isolation, nothing in this issue says "do not start until #575 has shipped labs" — they'd have to go read #767 to discover that. Since these YAML `ordering_after` blocks are prose, not an enforced dependency graph anywhere in this repo (no tooling that blocks work), this is a real risk: #769 could be executed the moment #767's spec document lands, well before #575 has a single lab, and AC-4 would then be unsatisfiable except by inventing a stub kit that isn't the real pack. Recommendation: list #575 explicitly in `ordering_after`, not just #767, so the dependency survives a reader who doesn't chase the chain.

**2. A chicken-and-egg with TASK-C578-3 (#772) on the content-license field the validator is supposed to check.**
#767 (TASK-C578-1) requires kit metadata to carry, at minimum, "its content license." For AC-4 here ("Donzellini pack ... validate clean") to mean anything, the validator must accept whatever is in that field. But the actual open-license *decision* is TASK-C578-3's job (#772), and #772's `ordering_after` is `["TASK-C578-2", 509]` — i.e., #772 is sequenced **after** this issue, not before it. So at the moment #769 executes and checks the Donzellini pack's metadata, the license field can only be a placeholder (no real license has been chosen yet) — meaning either the validator is checking "field is non-empty" rather than "field names a real, valid license" (a shallow, gameable check), or AC-4 quietly can't be honestly closed until #772 finishes too, contradicting the declared task ordering. The issue doesn't acknowledge this dependency loop at all. Recommendation: state explicitly that the validator only checks the license field is *present* (structural), not that its value is *valid*, or reorder so licensing lands before the "validates clean" claim is made.

**3. No delivery mechanism is specified — "pointed at a kit directory" implies a standalone tool, but nothing requires one to exist outside the test suite.**
`grep -in validat src/jls/JLSStart.java` finds no existing validate-style flag, and `JLSStart.FLAGS` (the authoritative CLI table per ARCHITECTURE.md) is not mentioned anywhere in this issue. The Outcome text says "Pointed at a kit directory it reports, by name, every part that is missing or malformed — so a third-party author gets a list rather than a rejection" — language that implies an external author, outside this repo, can run the tool. But every AC is satisfiable by a JUnit test under `test/jls/**` that only runs via `mvn verify` inside the checked-out repo, which a third-party kit author (per this project's own framing) has no reason to have set up. If that's how it ships, the stated goal — "a third-party author gets a list rather than a rejection" — is not actually delivered to that author. Recommendation: an AC requiring a standalone invocation path (new `-validate-kit <dir>` CLI flag, or a documented standalone script with no Maven/test dependency) is needed if the third-party-usability claim in the Outcome is meant literally.

**4. "reports ... by name and location" doesn't define what "location" means, so the bar is gameable with coarse messages.**
Nothing pins "location" to a file path, a line number, or a metadata field name. A validator that only ever emits "labs/ directory missing" or "metadata malformed" (no field, no line) technically satisfies AC-2/AC-3 as literally written while giving an author far less than the "list rather than a rejection" the Outcome promises. Recommendation: require at minimum a file path + field/line for every reported item, matching the granularity of the existing `LoadError` taxonomy this project already uses (`src/jls/LoadError.java` — category + location + detail + hint, per ARCHITECTURE.md's error-reporting contract) rather than inventing a looser convention for kits.

**5. "malformed" has no stated validation depth, and the project has a live precedent (untrusted-input hardening) this issue doesn't reference.**
It's unclear whether a "malformed" starter circuit means only "file present with the right extension" or means "the validator actually loads it through `Circuit.load` and gets no `LoadError`." If the latter, the validator inherits the same untrusted-input surface the project already treats seriously elsewhere: ARCHITECTURE.md's loader step 1 explicitly calls out "hostile-input caps (issue #38, `UntrustedFileHardeningTest`)" because loaded files can come from outside the project, and #578's own boundary/threat framing (recorded decision "#222") treats externally-authored content crossing a boundary as needing an explicit trust story. A kit-directory validator that parses third-party-authored `.jls` files as part of "malformed" detection is exactly that boundary, yet #769 never mentions resource caps, malformed-file handling, or reuse of the existing hardening pattern. Recommendation: state explicitly whether "malformed circuit" means load-tested or presence-tested, and if load-tested, require it go through the same hardened path as `FileAbstractor`/`UntrustedFileHardeningTest` rather than a fresh, unaudited parse route.

**6. Kit-discovery convention is assumed, not established anywhere in scope.**
AC-2 says "CI runs it over every shipped kit" — this presumes a way to enumerate what counts as a shipped kit (e.g., a top-level `kits/` directory or a registry file). No such directory exists in the tree today (`Glob **/kit*/**` returns nothing), and #769's Boundary section attributes the convention entirely to TASK-C578-1 without stating that kit-discovery-for-CI is part of what #767 must supply before #769 can be wired into the build. Recommendation: one sentence noting the discovery mechanism is TASK-C578-1's deliverable and naming it, so CI wiring in #769 isn't building against a moving target.

**7. AC-2 is vacuously satisfiable if read apart from AC-4.**
"CI runs the validator over every shipped kit and fails the build on a violation" is trivially true over an empty kit set — nothing forces at least one real kit to be present when this AC is checked off. AC-4 closes this gap for the Donzellini pack specifically, but the two ACs aren't tied together in the text, so a reviewer signing off criterion-by-criterion could tick AC-2 with zero kits in tree and treat AC-4 as a separate, later concern. Recommendation: merge AC-2 and AC-4's verification, or state AC-2 is not considered met until AC-4 is.

**8. "the run is recorded" (AC-4) has no defined artifact.**
Could mean "a green CI check exists" (ephemeral, not really a durable record) or "a report file is checked in." Left as-is, it's satisfiable by pointing at a passing CI run URL that may not be retrievable later. Recommendation: name where the record lives (a checked-in log, a CI badge with a permalink policy, etc.).

## What's solid

- The Boundary section correctly scopes out the convention itself (TASK-C578-1/#767) and licensing/external review (TASK-C578-3/#772) — clean, non-overlapping task decomposition in principle, matching the maintainer's own pass-1/pass-2 dedup notes on #575/#578.
- AC-3 (distinguish missing-required from missing-optional from present-but-malformed) is a genuinely good, testable three-way requirement — a real improvement over a validator that just says "invalid."
- Depending on TASK-C578-1 rather than duplicating the layout spec inline is the right call — no spec/validator drift risk from this issue's own design.

## Verdict rationale

The core validator concept and its boundary are sound, but the issue has two real structural gaps rather than just wording nits: (a) its declared dependency chain to a kit that doesn't exist yet is indirect and easy to lose track of (finding 1), compounded by an unacknowledged ordering loop with the sibling licensing task (finding 2); and (b) several of its acceptance criteria (delivery mechanism, "location," "malformed" depth) are underspecified enough that the letter can be satisfied — a passing CI check, a JUnit-only tool, a coarse message — while the stated goal ("a third-party author gets a list rather than a rejection") goes unmet. These are fixable with issue edits, not a redesign, so `needs-rework` rather than `should-not-proceed`.
