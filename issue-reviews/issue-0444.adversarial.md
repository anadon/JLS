## Findings (most to least severe)

**1. The load-bearing authority for the whole task — decision D3 — is a citation to a document that does not exist anywhere in this repository, at any commit reachable from HEAD.** The issue's entire justification chain rests on: *"`docs/plan/evidence/BRIEF.md` §11 decision D3 is the maintainer requirement... That document landed in commit `3a81a4a7d6a0f108ec201e632732d308cc02b3fc` and is not present at the evidence commit `2d0ca9d`."* I searched the full working tree (`find … -iname '*BRIEF*'`, `find … -path '*/docs/plan*'`) at the current HEAD (`5b05d67`, 2026-08-08) — no `docs/plan/` directory exists at all, under any name. Neither `2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7` nor `3a81a4a7d6a0f108ec201e632732d308cc02b3fc` resolves in this checkout's git history (`git cat-file -e` fails on both — though note the local clone is shallow/squashed to one commit, so commit-hash absence alone is weak evidence). What is *not* weak: the file itself, `docs/plan/evidence/BRIEF.md`, is absent from the tree that ships with the repository today, regardless of history depth. An executor picking up this issue cannot read the "operative clause, quoted verbatim including the maintainer's own words" against a real document — they can only trust the issue's own transcription of it. The identical pattern (same missing `docs/plan/evidence/BRIEF.md`, same phantom commit hash, same "not present at the evidence commit" hedge) also appears verbatim in sibling issues #436 and #319, which confirms this is a systemic trait of this issue-generation programme rather than a one-off slip — but that makes it *more* concerning, not less: the ground truth for an entire multi-issue design decision (D1/D2/D3, FEAT-003/012/013/014) lives nowhere an implementer or reviewer can independently verify it. **Recommendation:** before work starts, either commit `docs/plan/evidence/BRIEF.md` to the tree (even as a design-note, not code) or excise the "quoted verbatim" framing and restate D3 as this issue's own, directly-owned decision — right now the issue cites an authority it cannot produce.

**2. Scope is large enough that "task" tier undersells it, and the schedule-critical coupling to #436 doubles the risk.** The Definition of Done has ~25 checkboxes spanning: a new file-format grammar construct (SECTION frame with kind/version/required-flag/merge-participation), a generalized per-section `formatVersionNeeded()`, a re-specified two-level size cap, a brand-new `-migrate` CLI subsystem with atomicity/idempotence/stable-id-preservation guarantees, resolution of *six* explicitly-still-open decisions (duplicate sections, section ordering, per-kind size bounds, whether `Memory.sync`/`initrle` bump the version, and how `-migrate` writes), a closed-over answer to a previously-open question in `docs/file-format.md` (§9's `Memory.sync` treatment, O6), two new test files with ~13 named test methods, and a **joint golden-corpus regeneration with #436 (TASK-0005)**, itself an equally large, independently-scoped, currently-*open*-and-unlanded task (own abstract: 3-week-plus surface touching every reference in the file format). The issue is explicit that these two must land as "one epoch" ("weeks apart forces users through two migrations") — meaning #444 cannot be reviewed, merged, or golden-regenerated in isolation; its critical path includes another task of comparable size that has 3 open discussion comments and its own unresolved falsification questions (H2 in #436 could force a further format change to the `id` line, which would ripple back into #444's epoch numbering). **Recommendation:** either split this into independently-landable sub-PRs (frame mechanics vs. `-migrate` vs. the `Memory.sync`/`initrle` policy decision) or explicitly re-tier it as `feature`, since the blocking coupling to #436 alone makes single-epoch, single-review delivery optimistic.

**3. The "diagnostic" acceptance criterion is underspecified against the codebase's actual single-outcome error model, which makes it gameable.** P1/completion-criteria requires `anUnknownOptionalSectionIsSkippedWithADiagnostic()` to "assert that a diagnostic naming the skipped kind was recorded." But per `ARCHITECTURE.md`'s own "Error-reporting contracts" section, the existing model is built around **one** `LoadError` per load, surfaced via `JLSInfo.setLoadError` and shown through `TellUser` — a *failure* channel. This issue introduces a fundamentally new kind of outcome — *success-with-a-warning*, potentially *several* warnings if multiple unknown optional sections are skipped — and never specifies where that lives: is it a new field on a successful load's return value? A list surfaced through `TellUser` (which issue #81 restricts to "the only place allowed to create message dialogs")? Section 7.1 only says diagnostics are "seen by users and by grading scripts reading stderr," which describes the batch/CLI path but says nothing about the interactive editor path — exactly the audience (`"Students drawing and simulating circuits in the editor"`) the Abstract leads with. As written, a test can pass by asserting some internal list is non-empty after `Circuit.load()` while the GUI never shows the user anything, which reproduces the exact O4-D failure mode ("indistinguishable from success") this task exists to close, just one layer deeper. **Recommendation:** the issue should specify the diagnostic's concrete carrier type/API (e.g., an addition to `LoadError` or a new `List<Diagnostic>` return alongside a successful load) and require an assertion that the *editor* surfaces it, not just that a batch/stderr assertion passes.

**4. `formatVersionNeeded()`'s generalization is stated but its writer-side algorithm is not, leaving a hole in the "no false negatives" property.** O2/§7.10 Stage 4 states the postcondition ("the emitted epoch is the lowest whose features the file uses," now per-section) but the Method checklist item is just "Generalize `formatVersionNeeded()`... from a whole-file `max` to a per-section answer" with no algorithm for how a section's version is computed from its constituent elements' `saveFormatVersion()` values when elements can belong to no section, one section, or (per the "machinery for GEOMETRY/CHECKPOINT/IMAGE... to be added later") potentially participate in cross-section features later. This is a smaller gap than #1–#3 but is exactly the kind of thing that becomes a silent-regression discovery mid-implementation rather than a design decision made up front, which is what the issue claims to avoid ("must be answered in TASK-0033 rather than discovered").

**5. Minor: the "written epoch policy" and "designed, not a regression" framing invites a plausible but unaddressed UX regression.** §7.12/O5 correctly notes a version-2 reader meeting a framed file will report `malformed file` (the corruption taxonomy) and calls this the *designed* behavior. That is consistent with today's `FORMAT`-header semantics, but it means the exact O4-C failure this issue exists to fix (a confusing "malformed... recover from `.jls~`" message for something that is not corruption) will recur for **every user on the previous JLS version who receives a section-framed file** until they upgrade — the issue accepts this as a policy statement but doesn't require any softening (e.g., detecting the `SECTION` keyword specifically and pointing to a "needs a newer JLS" message even in the old build, which would need a *separate*, back-ported patch to be effective and is out of this issue's scope by construction). Worth flagging as a known, accepted cost rather than a defect, but the issue undersells it by framing the malformed-file report as fully "designed" without noting it reproduces this issue's own motivating pain point for old readers rather than genuinely eliminating it.
