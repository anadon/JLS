# Issue #628: TASK-C559-5: one real published .cv project imports as a single undoable operation with zero unexplained losses
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what this issue actually is

A closeout/integration task in a five-task chain (TASK-C559-1..5, #621/#622/#624/#626/#628) under feature FEAT-C29-3 (#559), itself under capstone CAP-29 (#513). It asks for zero unexplained import losses on a real CircuitVerse `.cv` project, atomic/undoable import, a shared-schema migration report (#556/FEAT-C29-1), and a committed CI regression fixture. `ordering_after` names TASK-C559-3 (#624), TASK-C559-4 (#626), and TASK-C556-2 (#610).

Repo verification: `grep -ril "circuitverse\|CircuitVerse"` across `src/`, `test/`, `docs/`, README, ARCHITECTURE, CHANGELOG returns **nothing**. There is no `.cv` parser, no CircuitVerse element-mapping table, no importer package, no fixture. Every dependency this task orders itself after is equally unbuilt.

## Findings, most severe first

**1. The dependency chain this task sits atop is unbuilt three levels down — feasibility risk, not just sequencing risk.**
`ordering_after` names TASK-C556-2 (#610), whose job is "the dropped set equals the reported set, asserted once in shared infrastructure — and the .circ report round-trips through the shared schema losslessly." That task depends on FEAT-C29-1 (#556), which explicitly states its scope: "This feature extends CAP-16's FEAT-025 (#323) report infrastructure... It must not fork, re-implement, or alter `.circ` mapping decisions." I pulled #323 (FEAT-025, the `.circ` importer this all leans on): its own body records, in `evidence_commit`, that its two child tasks are "**not filed**," marks its part-data and parser prerequisites "**ABSENT**," and its own open questions (band vs. task-sum mismatch, an unresolved licensing question that "blocks filing children") are unresolved. So: #628 (this issue) depends on #610, which depends on #556, which depends on #323's mapping infrastructure — and #323 has not started. This is not "do the tasks in order," it's "the load-bearing foundation four hops down doesn't exist yet," and none of that is disclosed in #628's body — a reader of #628 alone would not know the totality-assertion machinery it leans on for AC-1/AC-3 is contingent on an entirely separate, unstarted feature for a different file format.
*Recommendation:* state the true transitive dependency (down to #323) in the boundary notes, or block #628 from being worked until #556/#610 land, whichever the maintainer prefers — but don't let the issue read as "three siblings and a shared-infra task" when it's actually gated on a fourth format's unstarted importer.

**2. AC-1's "one real published `.cv` project" is a gameable, unbounded acceptance bar.** Quoted: *"One real published `.cv` project imports with zero unexplained losses."* There is no minimum-complexity requirement, no corpus, no representativeness argument. Contrast with #323 (`.circ`), which explicitly requires "a corpus of public files," a mechanical connectivity-comparison harness, and published accept/reject tables (I1, I6) precisely because a single hand-picked file is gameable — the parent feature #323 itself calls out that "the measurement exists before the estimate is trusted." #628 could be satisfied by picking the simplest public CircuitVerse project (e.g., a two-gate demo with no subcircuits, no sequential ICs, no bus splitters) and passing trivially, while the stated reader — "the grading-burned instructor of #510 §3" — is explicitly a course-scale user hitting subcircuits, timing, and Verilog, none of which a minimal fixture would exercise. AC-4 then locks this one arbitrarily-chosen fixture into CI forever as the regression oracle.
*Recommendation:* set a minimum-complexity bar for the qualifying fixture (e.g., must contain ≥1 subcircuit, ≥1 sequential element, ≥1 of whatever CircuitVerse's queue-priority-delay construct is) so the "real project" can't be selected to dodge the very constructs #559 AC-2/AC-3 exist to test.

**3. KC-29-1 kill criterion is invoked but not applied.** Quoted: *"Kill criterion KC-29-1 applies: at 1.5× #559's 3-5 mw band the format downgrades to a documented external-conversion recipe, and the decision is recorded here."* This sentence commits a future edit of this issue to "record the decision" but sets no trigger check, no owner, no current spend-to-band ratio, and none of the four ACs test whether the kill criterion was ever evaluated. As written it's inert boilerplate, not a boundary decision — a task can close all four ACs while KC-29-1 silently never gets checked.
*Recommendation:* either drop the sentence (if it's not this task's job to check it) or add an AC: "at close, the actual mw spend across TASK-C559-1..5 is compared to the 3-5 mw band and the kill-criterion verdict is recorded."

**4. The atomicity/undo requirement (AC-2) has no owner among the sibling tasks, and conflicts with the existing undo model.** None of TASK-C559-1 (#621, parser), -2 (#622, element mapping), -3 (#624, subcircuits), or -4 (#626, delay flagging) mention transactionality or undo in their titles — "single undoable operation... a mid-import failure leaves no partial circuit" appears to surface for the first time at this integration task. Worse, it may not be achievable with existing machinery as documented: ARCHITECTURE.md states undo is per-circuit (`CircuitSnapshot` "stores the circuit as deflated save-format text," `SimpleEditor.undos`/`redos` are per-editor-tab), and `src/jls/edit/SimpleEditor.java` shows subcircuits are imported as **separate circuit files** (`"Import the subcircuit named by this menu item"`, line ~481, `sub.setSubCircuit(impCirc)`). A CircuitVerse project with subcircuits (which TASK-C559-3/AC-2 requires JLS subcircuits for) therefore produces *multiple* JLS circuits/files, not one — "one undoable operation" restoring "the workspace exactly" across multiple circuit files is a capability this codebase doesn't currently have anywhere (the netlist importer at `src/jls/hdl/imp/NetlistImporter.java`, cited as this family's structural precedent, only guarantees "no partial circuit," a single-artifact guarantee, not cross-file transactional undo).
*Recommendation:* name which task actually builds the transactional-import wrapper (a new task, or fold it explicitly into one of the four siblings) before #628 can be a pure verification/closeout task; otherwise #628 is quietly the task that has to invent multi-circuit atomic undo with a 1 mw budget.

**5. Cost band looks materially underestimated given #1 and #4.** `band_mw: "1"` for: sourcing/vetting a real public `.cv` fixture (with the complexity bar problem in #2), wiring a CI job, validating the totality assertion against machinery that (per #1) doesn't exist yet, and potentially building or exercising cross-file atomic undo (#4). The sibling feature #323 already documents its own band-vs-task-sum mismatch as "3x at the high edge" for comparable scope; nothing here suggests TASK-C559-5 is cheaper.
*Recommendation:* re-band after #556/#610 land and the actual undo mechanism is scoped, per KC-29-1's own logic (finding #3).

**6. Provenance/licensing of the "real published .cv project" fixture is unaddressed.** AC-4 commits a real, presumably third-party-authored CircuitVerse project to this repo's CI as a permanent fixture. CircuitVerse hosts user-submitted circuits; nothing in this issue (or #559, its parent) states how the fixture's authorship/license is checked before committing someone else's design into a GPLv3 project's test tree. #323's own body flags exactly this class of problem for `.circ`/Logisim absorption ("Open Question 2... blocks filing children") — the same question is silently absent here for `.cv`.
*Recommendation:* add a line requiring the chosen fixture to carry a compatible license/permission before commit, mirroring the diligence #323 already demands for its own corpus.

## What's solid

- The report-format discipline (AC-3, "no `.cv`-specific dialect") correctly defers to #556's shared schema rather than reinventing one — consistent with #556's own stated boundary.
- AC-4 (a committed CI fixture that turns the build red on regression) is the right shape for guarding against silent mapping drift, independent of the fixture-selection weakness in finding #2.
- Grounding the acceptance in a named persona (#510 §3's instructor) rather than an abstract pass/fail is a reasonable anti-gaming instinct even though the single-fixture bar (finding #2) undercuts it in practice.
