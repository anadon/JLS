- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5

## Summary

The core factual claims check out. On the checked-out repo (`src/jls/hdl/HdlExporter.java`), the classification loop is exactly the bare fall-through the issue describes (`:179-192`, offenders recorded via `describe(el)` at `:191`, no reason storage), and there is genuinely no `REJECTED` map anywhere in the tree (`grep -rn REJECTED --include=*.java` returns nothing). The 35-registered / 4-unpoliced count is reproducible directly: `ElementRegistry.ALL` has exactly 35 entries, `EXPORTED` has 22, `SKIPPED` has 6, `TOPOLOGY` contributes 3 more registered types (`WireEnd`, `JumpStart`, `JumpEnd`; `Wire` isn't registered), and `35 − 31 = 4` = exactly `{FieldExtend, Memory, RegisterFile, SubCircuit}`. `RegisterFile` genuinely has variable `readPorts`/`writePorts` fields (`src/jls/elem/RegisterFile.java:66-69`), so AC-4's port-count framing is grounded in real code, not invented. `FieldExtend` genuinely has a two-mode sign/zero fill (`src/jls/elem/FieldExtend.java:39-51`) consistent with "the IR already carries the pieces." The `blocked_by: [492]` dependency is real and correctly directioned — #492 is open and is what would actually create the bucket #873 needs to remove entries from. The corrective comment on #291 withdrawing `blocked_by: [61]` and re-homing to #873 exists and is consistent with #873's text. The scope exclusions (SubCircuit/#292/#358, write-mask/#457, import-mapping/#61) are each independently verifiable against those issues' own bodies. This is a well-grounded issue; the concerns below are about acceptance-criteria gameability and a few unreconciled cross-issue edges, not about the premise.

## Findings, most severe first

**1. AC-3's "verified" workaround claim has no defined pass bar — gameable.** AC-3 says `FieldExtend`'s workaround must be "demonstrated equivalent on a fixture corpus before the sentence ships," and the Kill Criteria/Cost sections treat this as possibly discharged by "a maintainer sentence rather than a branch." Nothing in the issue specifies how many fixtures, what widths/fill-modes must be covered (sign vs. zero, extend-by-0, in-width==out-width edge case, the widest legal width), or what "equivalent" means operationally (bit-for-bit on a golden? one hand-checked example?). As written, a single trivial fixture (e.g. one 4-to-8-bit zero-extend) could "verify" the workaround and satisfy AC-3's letter while leaving the sign-extension path or width-boundary behavior completely unchecked — exactly the "wrong workaround that looks authoritative" failure mode the issue itself warns against in its own "Why this feature exists" section. *Recommendation:* AC-3 should name the minimum fixture set explicitly (at minimum: sign-extend, zero-extend, and a width-equal no-op case) rather than leaving "fixture corpus" undefined.

**2. AC-4 can be fully discharged with zero code and zero new tests, and the issue doesn't say whether that counts as the feature "landing."** KC-3 states plainly: "If the maintainer rules that multi-port storage is out of scope for HDL export entirely, AC-4 is discharged by recording that ruling as the permanent reason." That's a legitimate design stance (deferral-vs-ruling is explicitly reasoned about), but it means one of the feature's two "planned_tasks" — RegisterFile export — can close by fiat with a single sentence, while the Cost section still bands the whole feature at "2-4 mw" as if AC-4 were an open engineering question. There's no criterion distinguishing "AC-4 satisfied by real analysis of the port-count boundary" from "AC-4 satisfied by a one-line maintainer opinion with no falsifiable content," and AC-5 ("every refusal is falsifiable... not a general appeal to portability") doesn't obviously apply to a refusal grounded in "the maintainer says so." *Recommendation:* if AC-4 is discharged by ruling rather than analysis, require the ruling to itself satisfy AC-5's falsifiability bar (name the specific construct/port-count that fails), not just assert "out of scope."

**3. The dependency direction against #457 (byte-lane write masks on Memory) is stated backwards from what #457 itself records, and #873 gives it no ordering edge.** #873's scope boundary says: *"Byte-lane write masks on Memory — #457 (TASK-0076). That presupposes Memory exports; it is a successor, not a sibling."* But #457's own machine block declares `blocked_by: []` — it is *not* gated on #291/#873 landing first — and #457 explicitly records the reverse obligation in its Related Work: *"HDL export already refuses Memory, so the new port is invisible to it today. When #291 lifts that refusal it must render or refuse the mask by name; that obligation belongs there and is recorded here so it is not lost."* So #457 can land before, after, or concurrently with #291/#873, and if it lands first, `Memory` will have gained an optional `WM` input and a `lanes` attribute that #291's AC-2 export work (in-scope of #873) has not been told to expect. #873 neither sequences against #457 the way it carefully sequences against #292 ("Sequence against #292... #292 first, then this feature") nor updates AC-2's golden-corpus scope to say what happens if lanes exist when Memory export lands. *Recommendation:* add an explicit ordering note (or an AC-2 caveat: "if #457 has landed, the export must render or explicitly refuse the `WM` port") mirroring the #292 treatment.

**4. `serves_capstones: [202, 302, 304]` claims #202 is a capstone this feature serves, but #202's own machine block says `tier: feature`, not `tier: capstone`.** Fetched directly: #202 ("RV32I CPU worked example...") declares `tier: feature` and its own `blocked_by: [59, 62]` still points at the now-closed #59 rather than at #291/#873/#492 — it has not been updated the way #291 was to reflect the #59 restructuring. Two separate problems follow: (a) #873 mischaracterizes #202's tier in its own machine block, which matters if any tooling in this repo's planning convention treats `serves_capstones` as a typed edge (compare #358, which correctly lists only genuine `tier: capstone` issues — #298/#302/#304/#307/#310 — in the same field); (b) the claimed "serves" relationship is not mirrored on #202 the way this repo's own convention requires (#358's Re-planning Protocol: "Adding or removing [an edge] obliges the same REPLAN to add or remove the mirror on the far issue"), so #202 currently has no comment or edge acknowledging #873 exists at all, and a reader arriving at #202 would still believe Memory export is gated on closed #59. *Recommendation:* either drop #202 from `serves_capstones` (it isn't one) and place it in `related`, or, if the intent is "downstream consumer," say so and file the mirroring correction on #202 the same way #291 got one.

**5. Minor: the totality-test fixture helpers this issue depends on don't exist yet, and #873 doesn't flag the prep work.** #492 (the blocker) explicitly notes: *"The `HdlCircuitBuilder` may need `registerFile(...)` and `fieldExtend(...)` helpers for P3's per-type message assertions; check before assuming."* Verified directly: `test/jls/hdl/HdlCircuitBuilder.java` currently has `memory(...)` and `subCircuit(...)` builder methods but no `registerFile(...)` or `fieldExtend(...)`. #873's AC-1 ("each has a per-type message assertion pinning that the reason is emitted") implicitly requires these fixtures to exist, but #873 doesn't list them as prerequisite work distinct from #492's scope — a minor gap, since whoever picks up #873 will discover it immediately, but worth naming so it isn't silently absorbed into #492's diff instead of #873's.

**6. Process/bookkeeping wrinkle, not a defect in #873's content: GitHub's native sub-issue parent links and this repo's custom `part_of_feature` YAML field disagree in multiple places cited by #873.** #492 (`has_parent: true`, parent `#315`) declares `part_of_feature: none` in its own body text; #292 (`has_parent: true`, parent `#358`, matching #873's claim that #292 "has now been re-homed to #358") still shows `part_of_feature: 59` in its machine block with a stale "re-home if refiled" note. None of this breaks #873's specific claims (which route around it correctly, citing #358/#292's comment threads rather than the stale YAML), but it does mean a downstream reader trusting only the machine-block text (as opposed to GitHub's actual parent field or the comment ledger) would get a wrong picture from more than one of the issues #873 cites as settled. Worth a one-line caveat in #873 that the machine-block `part_of_feature` fields on #292/#492 are known-stale pending their own Link-pass edits.

## What's solid

- **The central defect claim** (four unpoliced element types, bare fall-through with no reason storage) is verified byte-for-byte against the current tree, not just against the cited historical commit.
- **`blocked_by: [492]` is correctly justified** — #492 is open, and its diff is genuinely the only mechanism by which #873's unit of work ("delete a REJECTED entry") becomes possible.
- **The `#291` correction chain is real**: the comment withdrawing `blocked_by: [61]` and re-homing to #873 exists on #291 and is internally consistent with #873's own text and timestamps.
- **KC-1 and KC-3** are honest, falsifiable kill criteria that narrow claims in writing rather than widening tolerances — good practice, no notes.
- **The SubCircuit/#292/#358 exclusion** is accurately scoped: #358's own text confirms element-level coverage (Memory/RegisterFile) was never in its roster.
- **AC-4's self-aware framing** ("the same claim made for Memory, which AC-2 refutes for the single-port case") correctly anticipates the most obvious objection to RegisterFile's stock refusal reason, which is a real strength — most such reasons in this codebase's history (per #492) were never interrogated this way.

## Net assessment

The issue is well-evidenced against the actual codebase and its dependency ordering is basically right. The concerns are all about how the acceptance criteria could be satisfied on paper without the underlying goal (a user-actionable, non-authoritative-sounding refusal; or a genuinely verified workaround) being met — AC-3 and AC-4 in particular have no defined floor for "verified" and "decision," which is exactly the kind of gap that turns into a rubber-stamped PR. The #457 ordering gap and the #202 tier/mirroring mismatch are real but narrow-scope inconsistencies that a reviewer should require fixed before work starts, not blockers to filing.
