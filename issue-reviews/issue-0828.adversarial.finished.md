## Summary of the issue

A task-tier follow-up to feature #571 (itself under capstone #514/CAP-30): post a comment on each of the 2026 bounced external PRs (#4, #5 by AmityWilder; #187 by Dodothereal) stating the real outcome, linking to where the work landed, acknowledging the bounce was the project's process failing, and inviting the authors back with a pointer to the current contributor on-ramp (#567's templates, #568's first-issue shelf). AC-4 additionally requires linking the follow-ups from #571.

## Findings, most severe first

### 1. AC-2 asks the comments to point at an on-ramp that does not exist yet — and the task's own front matter hides the dependency
`ordering_after: []` in #828's YAML front matter says this task has no prerequisites. But AC-2 reads: "Each comment extends an explicit invitation back and points at the current contributor on-ramp (templates from #567, first-issue shelf from #568)." Both #567 and #568 are **open**, unimplemented, as of this review:
- `.github/ISSUE_TEMPLATE/` contains only `capstone.md`, `feature.md`, `scientific_task.md` — no bug-report or feature-request template (#567 AC-1 not met).
- `CONTRIBUTING.md` has no quickstart section and no mention of "good first issue" or an on-ramp anywhere (grep returns nothing).
- The `good first issue` label carries zero open issues (confirmed independently by the sibling review at `issue-reviews/issue-0568.adversarial.md`, which live-verified `label:"good first issue" is:open` → 0 results).

The parent feature #571 is explicit that this exact step is gated: "invitations go out only after #567, #568, and #316 have landed (per the capstone's PF-1..3 gate)" (#571 AC-2). #828 is supposed to be the narrower "bounced 2026 PRs" slice of #571's AC-1, but it drops #571's own gating language and ships `ordering_after: []`, which reads as "start any time." Acting on #828 today, as filed, means either (a) posting an invitation that links to a template directory and a labeled shelf that don't exist — a broken, embarrassing link in a public comment aimed at winning back a burned contributor — or (b) the task-doer has to independently rediscover and impose the #567/#568 gate that #571 already states but #828 omits. **Recommendation:** add `ordering_after: ["#567", "#568"]` (or explicitly scope AC-2 down to "invitation only, on-ramp pointer deferred to a follow-up edit once #567/#568 land") before this is picked up.

### 2. AC-1's "each of the bounced 2026 external PRs" undercounts against AC-1's own comment-per-PR requirement, and the outcome for #187 is not yet substantiated in the issue body
The issue names "the two ... developers ... (#4/#5, #187)" — three PRs, two people, which is factually correct (verified via `search_pull_requests is:pr is:closed is:unmerged created:2026-01-01..2026-12-31`: exactly #4, #5, #187 are the external unmerged closed PRs in 2026). Good — that part is accurate. But the issue body never states *what actually happened* to #187 (the `addToBook` determinism fix). Investigation shows the underlying bug (#182) was independently fixed and closed 2026-07-18, four days before #187 was closed (2026-07-22), and the current code (`src/jls/edit/CircuitRenderer.java:259`) implements exactly the `getStableId()`-sorted-order fix #187 proposed, citing "#182" in the comment — so the claim "merged by other means" is *plausible and checkable*, but the issue itself does the task-doer no favors: it asserts an outcome-writing task without giving the outcome, forcing whoever executes AC-1/AC-3 to redo this archaeology from scratch for #187, with no guardrail against getting it wrong (AC-3's "no comment claims a change was merged that was not" has real teeth here — #187's actual disposition needs a specific commit citation, which is not trivial to find and isn't pre-researched in the issue). **Recommendation:** the issue should either pre-supply the outcome-per-PR mapping (as #571 or a linked doc) or explicitly flag that outcome verification is in-scope work, not just comment-posting.

### 3. AC-3's "accurate record" bar conflicts with what already exists on #4 and #5 — the task doesn't say whether to supersede or leave stale partial comments
PR #4 already has an anadon comment ("Closing as fixed in another branch.", 2026-07-17) — terse, gives no link, no acknowledgment, no invitation. PR #5 already has a fairly complete anadon/Claude-Code closing comment (2026-07-17) citing #34, #15/#81, #174, and thanking the contributor — it satisfies AC-1 and most of AC-3 already, but not AC-2 (no explicit "this was our process failing" framing, no invitation back, no on-ramp pointer). The issue's acceptance criteria are written as if no comment yet exists on any of the three PRs ("Each closed PR carries a comment stating the real outcome") — it does not address whether a *second* comment should be added to #4/#5 (creating duplicate/redundant history) or whether the existing comments should be edited/superseded. This is gameable: a shallow implementation could satisfy AC-1 literally by adding a *second*, redundant comment to #5 that repeats the existing one, technically meeting "carries a comment stating the outcome" while doing nothing for the actually-missing piece (the invitation + on-ramp link, AC-2). **Recommendation:** state explicitly whether existing comments are to be edited-in-place, appended-to, or left and supplemented, and call out that #5's comment already covers AC-1/AC-3 so the real gap is AC-2.

### 4. AC-5 quietly forecloses the honest failure mode without saying what happens if the authors actually do respond
"No response is required ... their silence is not a failure condition" is fine as written, but it says nothing about what happens if AmityWilder or Dodothereal *does* respond (e.g., asks a follow-up question, disputes the "declined" characterization, or points out the outcome summary is wrong). Since this is a `tier:task`-banded (`band_mw: 0.25`, i.e. cheap/small) item, there's a real risk the task is marked "done" the moment the comment is posted, and a substantive reply sits unanswered — which is exactly the kind of process failure #571/#828 are trying to make amends for. Not a blocking defect, but worth one line of acceptance criteria: "if an author replies within some window, a human follow-up is owed," since the small band-width suggests no attention was budgeted for that.

### 5. AC-4 makes this task's completion depend on editing a different live, open issue (#571)
"The follow-ups are linked from #571" requires editing #571's body or adding a comment there once #828 finishes. That's low-risk but non-self-contained: #571 is itself an open, actively-scoped feature issue that other task-tier children (per its `ordering_after` list) may also be editing concurrently. A minor scope/coordination note, not a blocker — flagging so whoever executes this checks #571's current state before editing it, rather than clobbering another concurrent edit.

## What's solid
- The core premise — two external developers, three PRs, all bounced/stalled in 2026, none merged — is factually verified against the repo and matches the issue's framing exactly.
- AC-3's "no comment claims a change was merged that was not" is the right bar, and is checkable against the actual commit history (#4 needs verification of "fixed in another branch," #187 needs the #182 fix cited above) — the standard is sound even though (per finding #2) the issue doesn't do the legwork for the author.
- The `band_mw: 0.25` sizing is plausible for the "post an accurate, warm comment" work described, once the AC-2 dependency gap (finding #1) is resolved.
