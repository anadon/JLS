## Findings, most severe first

The comment thread (posted after the body, same day and later) shows TASK-0111 filed as **#466**, TASK-0112 as **#483**, TASK-0073 as **#423** — and further that #466 was itself split three ways (verdict channel → #466, panel → #214, cohort grading → #757). One comment in the thread (`5227301023`) even re-asserted "#483/#423 not filed" incorrectly, and had to be corrected by the *next* comment (`5227543907`). The body's own DoD requires "Machine block, roster table, and mermaid graph agree with reality at close (rule A)" — that is already false of the artifact as written, and a reader who trusts only the body (not six chronologically-ordered corrective comments) gets an actively wrong picture of what exists. Recommendation: edit the body's §2 table, `planned_tasks`, and mermaid graph in place before treating this issue as a scheduling input; a tracker node whose truth requires replaying its comment history is not reliable.

**2. (HIGH) The cited `evidence_commit` no longer exists in the repository, so the DoD's own permalink criterion is already unsatisfiable as written.** `2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7` — confirmed via the comment thread's own `git cat-file -t` failure — is gone; every permalink in the body's "Evidence" section 404s. DoD explicitly requires "Every cited evidence document and permalink resolves on the default branch at close." I independently re-verified the *content* of every evidence item against the live tree and it all still holds (see Summary above), but content-happens-to-still-be-true is not the same as the stated acceptance criterion being met, and the body itself has not been edited to the corrected anchor (`29afb26`, per comment) — only a comment says so.

**3. (MEDIUM-HIGH) The vacuity criterion is gameable as stated.** §3's formal definition — `vacuous(φ,D) ⟺ ∄ run r of D in the explored space: r ⊭ φ` — leaves "the explored space" completely unbounded: nothing in the issue states whether TASK-0112 explores via bounded model checking to some depth, random simulation, or full enumeration. §5 criterion 5 ("the vacuity detector has a null") can be discharged by asserting exactly one hand-picked unfalsifiable property and one hand-picked falsifiable property both get their expected label — satisfying the literal test while leaving the detector's soundness over real student properties (where "explored" is whatever the implementation happens to reach) completely unverified. A detector that explores too little space will systematically under-report vacuity and pass students' unfalsifiable properties as meaningful checks — the exact failure this feature exists to prevent for the exit-status trichotomy, but nothing analogous is stated to prevent it here. Recommendation: pin the exploration strategy and its bound as an invariant in §4, not leave it to be decided inside TASK-0112 with only a two-example acceptance test.

**4. (MEDIUM) Two "blocks filing" Open Questions are marked unresolved, yet the child they gate has already been filed.** Open Question 2 ("what class of equivalence does the feature decide?") is explicitly labeled "**Blocks filing TASK-0112**," and Open Question 4 (whether `Assert`/`Cover` ship as drawn elements, paying the sealed-hierarchy registration tax) is labeled "Blocks TASK-0112's filing to the extent of one paragraph." The comment thread confirms TASK-0112 is filed as **#483**. Either the gate was skipped (the body's own stated pre-filing condition was not honored) or it was resolved and the resolution is recorded nowhere accessible from this issue — a reader of #369 alone cannot tell which. This is a process integrity gap, not just a staleness one: a "blocks filing" label that turns out not to have blocked filing undermines trust in every other "blocks" label in the document.

**5. (MEDIUM) Cost/sizing is admitted-wrong at filing time and never re-totaled.** The body's own cost reconciliation flags a 1.13x–3.75x gap between the summed task estimate and the stated 9–15 mw planning band and explicitly punts it to "a maintainer's answer" (Open Question 5) without blocking anything on it. Worse, the comment thread reveals TASK-0111's original 2-week estimate silently bundled three deliverables that have since separated into three issues (#466, #214, #757) — meaning the per-task sizing that fed the original band comparison was wrong by a factor nobody has re-derived. A feature whose own arithmetic is known-wrong and not recomputed after a 3-way split should not be treated as scoped for effort/scheduling purposes yet.

**6. (MEDIUM) Scope span bundles a small mechanical change with an open-ended verification-engine build under one feature node.** §1's observable capabilities range from "the exit code distinguishes pass/fail" (glue code over existing simulation machinery, per #466's own evidence O1–O2 this is nearly done) up through property checking with vacuity detection and design equivalence whose decidable class is explicitly *still undetermined* (Open Question 2) — i.e., a from-scratch bounded-equivalence or SAT-style checking engine for a pedagogical Swing app. The body's own §2 rationale for splitting TASK-0111/TASK-0112 ("the cut is between a verdict and what you can say with one") is itself the argument for two separate *features*, not one feature with two children of wildly different research risk — yet three capstones (#300, #306, #311) are wired to the combined node, so descoping the harder equivalence/coverage half (a real possibility per §7's own re-planning protocol) drags capstone notification obligations along with it unnecessarily.

**7. (LOW-MEDIUM) `blocked_by: [316, 321, 347]` overstates what actually gates the verdict half, and this has already caused real scheduling mistakes.** Per the comment thread's own correction, the three prerequisites gate only the TASK-0112 (property/equivalence/coverage) half — not the already-filed, already-scoped #466 verdict channel. The body's top-level machine block still reads `blocked_by: [316, 321, 347]` undifferentiated — anyone scheduling off the machine block alone (rather than the sixth comment) will repeat the same mistake.

The underlying capability statement and invariants are sound and worth keeping.
