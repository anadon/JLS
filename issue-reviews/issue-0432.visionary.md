# Issue #432: TASK-0095: the path from a drawn design to a submitted shuttle entry is written down, self-tested with no external tools, and walked once with the record filled in
- Lens: visionary
- Date: 2026-08-08
- Reviewer: Claude Opus 5
- Verdict: rethink

## What this issue is really for

Two things, fused into one task, with very different half-lives.

1. **An anti-pattern detector.** The genuinely new idea here is
   `theSubmissionRecordHasNoTbdCells()` — make "documented but never executed"
   a *build failure*. That idea is worth more than the shuttle. It is
   project-wide, it is cheap, and it is not blocked by anything.
2. **A silicon on-ramp ritual** — a markdown recipe plus a bash wrapper that
   copies three generated files into somebody else's template repo.

The issue's own weighting is inverted: (2) is the deliverable and (1) is
treated as a test detail on it. (2) is the least JLS-specific work in the
whole P6 program — Tiny Tapeout ships its own submission documentation,
maintained by people who control the template — while (1) is a discipline
only this repository can install in itself, and (3), below, is a capability
only JLS can ever have.

## The alignment check

`docs/capability-roadmap/README.md:1152-1188` places the shuttle target as
"In. Real. Cheap. And strictly gated… **ship it last**", 2–4 weeks *given*
A, B and C, "effectively infinite without them". `sweep-06-physical-boundary.md:55`
records why: `HdlExporter` covers 21 of 33 element types and hard-rejects
`Memory`, `SubCircuit` and `ShiftRegister`. So the only design walkable
through this path today is a gate toy, and `docs/capability-roadmap/README.md:1180`
already names that as failure mode 1 of shipping the shuttle early.

Layer the dependency chain on top: #432 ← TASK-0094 (**not filed**) ← #339,
#327, #359 (none landed) ← plus a shuttle window, a payment, and a fab
cycle. This task cannot start, and its terminal deliverable is 12+ months
out. Meanwhile item (1) above could land this week. That mismatch is the
finding.

## Objection 1 — the acceptance mechanism is self-defeating in its own terms

The issue exists to prevent a second permanently-unfilled `_TBD_` row. Its
mechanism is a test that is red until an external, unfunded, calendar-bound,
foundry-mediated event occurs — and §8 and Open Question 1 already concede
the likely outcome: ship it red with a `WAIVED:` comment. That relocates the
permanent placeholder from a markdown cell into a permanently-red test with
a waiver beside it. Same defect, worse home: a red test that is *expected*
to be red trains everyone to stop reading the red.

The conflation causing this is **"walked" = "submitted"**. Those are two
different claims:

- **The engineering claim** — *the artifacts JLS emits are accepted by the
  flow, harden through LibreLane, and produce a GDS that fits the tile.*
  Falsifiable, reproducible, machine-checkable, and — critically — *not*
  gated on a window or a purchase, because the Tiny Tapeout template's CI
  runs the flow on every push.
- **The procurement claim** — *a chip came back.* Not falsifiable by CI, not
  repeatable, not a property of this repository's code.

Bind acceptance to the first. The second is a CHANGELOG line and a photo,
not a test assertion. `#328` invariant 5 already says "a returned chip is not
a returned test"; #432 asserts the opposite by making the returned submission
the completion criterion.

And note the deeper weakness: **a path walked once decays exactly like the
document it replaced.** A hand-typed row dated 2026 proves nothing about the
tree in 2027. A *flow record regenerated by each CI run* — template commit,
LibreLane version, cell count, tile utilization, DRC/LVS verdict — is
strictly stronger evidence, is the same amount of work, and never goes stale.
I am explicitly disregarding P1, and the §14 criterion "The walk happened",
as written.

## Objection 2 — the apparatus is out of proportion to the problem

§7.2 says the tools consumed are `git` and a GitHub account; LibreLane runs
in the template's CI. So P3 ("each single missing prerequisite prints its own
message") and P4 ("all missing, one pass") are an all-or-nothing preflight
over a set of size ~1, and P7 is a CI lane whose job is to prove that
`command -v git` works. The iCEstick precedent's preflight aggregates *four*
real tools; that is what earns the stub-`PATH` harness. Copying "the exact
shape" copies the machinery without the reason for it.

Worse, the shape is being hand-copied for the sixth time. The tree already
carries `icestick-handoff.sh`, `wayland-rig.sh`, `macos-rig.sh`, `x11-rig.sh`
and `windows-rig.ps1`, each with its own near-identical `command -v` loop and
its own `-selftest` twin. Six instances of a shape is not a precedent to
follow; it is a seam asking to be cut. And §7.2's "POSIX shell run on the
three supported platforms" is already false on the project's own terms —
Windows is a supported platform and the repo's answer there is PowerShell.

## Objection 3 — the drift test defends a problem that need not exist

H3/P2 propose a JUnit test parsing the document's claimed-file list and
asserting set equality with what the emitters emit. That is the correct
defense *if* the document is hand-written prose. It is unnecessary if the
document's prerequisites table and claimed-file list are **generated from the
same declaration the emitter and the script read**. Drift between a document
and code is not a testing problem; it is a single-source-of-truth problem.
`ShuttleDocsAccuracyTest` is a monument to a duplication that should not be
created.

## The alternative design

**A. Land the record facility now, alone, unblocked.** One in-tree,
machine-readable evidence store (`docs/records/*.yaml` or equivalent) plus
one test that enforces every declared record. Today the repo has *two
incompatible conventions* for manual-walk evidence — `icestick-bitstream-handoff.md:113`
puts it in an in-tree table (unfilled since it shipped), while
`wayland-desktop-checklist.md:107` says "Paste as a comment on issue #100",
which is precisely what #432 §9 correctly calls a record nobody finds. #432
would make a third decision by hand-copy. Decide once. Give each record a
declared `expires` or `pinned_to` field so a stale walk fails too, not just an
absent one. This closes #432's real contribution, closes the icestick gap
(#264's six cells), and is perhaps a week of work with zero prerequisites.

**B. Make the target a manifest, not a script.** The roadmap already asked
for this: generalize `Board` "to a target descriptor that can carry a
**wrapper template**" (`README.md:635`). Extend that descriptor with the
handoff data — destination path map, pinned upstream revision, prerequisite
table with role and source. Then: one generic runner, one generic self-test
that enumerates manifests, and documents whose tables *render* from the
manifest. The seventh target costs a data file. Objection 3 dissolves; P2's
drift test becomes structurally impossible to violate rather than caught
after the fact.

**C. Put the placement in Java, where the project already proved it.**
§7.1's "no JLS code surface changes at all" reads as discipline but is the
opposite: it routes a file-placement-with-all-or-nothing-refusal — the exact
contract `PcfEmitter` implements and `UnbindablePortsTest` already pins —
into untested bash. `jls -export -board tinytapeout -o submission/` writing
the whole submission-shaped tree inherits the test suite, SpotBugs, the
existing refusal discipline, and Windows, and needs no stub-`PATH` harness
because there are no external tools left to stub. The document then documents
*one command*, which is the strongest possible form of "commands, each of
which has been run".

**D. Spend the two weeks on the loop back into the editor instead.** P8 —
"the document must state what the open flow does to their design: constant
propagation, technology re-mapping, drive-strength replication and renaming"
— is a paragraph *telling* a student what happened. The roadmap says JLS's
unique asset is the opposite: "no external viewer can ever know that… Click a
NAND you drew; its two `sky130_fd_sc_hd__nand2_1` instances light up"
(`README.md:663-669`). `src/jls/hdl/imp/NetlistImporter.java` already reads
Yosys JSON. A mapping report — *your drawn `NandGate` became these three
cells; your design is 62% of a tile* — is a small slice of that, feeds the
roadmap's own lab exercises ("map your adder to sky130 and count the cells",
"fit your design in a tile"), and is available the moment the flow runs in
CI, with no window and no fab. #432 names this ("post-route annotation
import… the genuinely interesting follow-on") and puts it out of scope. That
ordering is backwards: the annotation import is the capability; the
submission ritual is paperwork around it.

## What I would endorse unchanged

The honesty note discipline (P9), the refusal-rather-than-overwrite rule
(P6), pinning by commit rather than transcription (§7.7), and O2's correction
that the scan must count occurrences rather than rows. Those are right, and
(A)+(B) preserve all four.

## Bottom line

Keep the goal — a silicon path backed by evidence rather than assertion.
Replace the deliverable set. Split #432 into (A) the record facility, which
lands now and retires #264's placeholder too; (B) the target manifest, folded
into TASK-0094 where the emitter already lives; and (C) a *flow record*
regenerated by CI, which is the honest, repeatable, unblocked form of "the
path has been walked". Leave "a chip came back" to the CHANGELOG, and put the
freed effort behind (D), the returned-netlist annotation that is the only
part of this program no other tool can do.
