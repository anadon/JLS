# Issue #515: CAP-31: a truth table becomes a minimized drawn circuit and a drawn circuit becomes its truth table and minimal expressions — and an FSM is designed as states, not gates
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: sound-with-concerns

## Summary

#515 is a capstone (open, `tier:capstone`, no parent/children per the GitHub API) that bundles four planned features (PF-1 truth-table extraction, PF-2 minimization, PF-3 table→circuit synthesis, PF-4 FSM parity) behind five acceptance criteria and two kill criteria. It is filed as a deliberately "lean filing" (its own YAML: `filed_by: session review directive 2026-08-04 — lean filing`), with the real detail meant to live in four child issues (#563–#566) filed the same session per the sole comment. The competitive rationale (#510 §2) checks out on inspection. The concerns below are concentrated in undeclared dependencies, unquantified/gameable acceptance criteria, and a scope claim that ignores what the codebase already does with don't-cares.

## Findings, most severe first

**1. (High) PF-3's dependency on #62 is real but undeclared in `ordering_after`.** The body says PF-3 "uses ... the HDL-import layouter lineage (#62) where available." #62 is open, and by its own tracking table every quality gate on the landed `HeuristicLayeredLayouter` (IC1–IC6, IC9, IC10) is unverified — "No — built by #290" — because the goldens directory `test/resources/hdl/layout-goldens/` doesn't exist yet. #515's `ordering_after` array names only `#306`; #62 is absent. So a 2–4 mw estimate for PF-3 quietly assumes a layout engine that hasn't cleared its own rubric, with no fallback stated (hand-rolled grid placement? wait for #290?). Recommend: add #62 to `ordering_after` or state PF-3's fallback if #62/#290 aren't done first.

**2. (High) AC-3's bound is unstated and untested, making it unfalsifiable as written.** "Bounds are stated and enforced: above N inputs the tool refuses with the arithmetic, never hangs" — N is never given, and AC-1's only golden test is a 4-input circuit, nowhere near any plausible bound. Nothing in the ACs exercises the boundary (N vs. N+1) or specifies what "the arithmetic" message must contain (contrast `TruthTable.entryConstraint`, whose exact wording is pinned by `DialogValidationTest`). As written, an implementation could pick N=6 for developer convenience, ship a refusal message of any shape, and technically satisfy AC-3 while badly missing the "parity with Digital/Issie" pitch the capstone is sold on. Recommend: fix N (or a formula) in the issue text and add an AC that specifically golden-tests N and N+1.

**3. (High) PF-1 silently inherits #306's extractor refusal list, which #515 never discloses.** #306's own body states: "Any extractor built over the same walk inherits exactly these four refusals" — `Memory`, `SubCircuit`, `RegisterFile`, `FieldExtend` (from `HdlExporter.REJECTED`, `src/jls/hdl/HdlExporter.java:460-477`). `SubCircuit` is one of JLS's core pedagogical constructs (ARCHITECTURE.md's element/hierarchy discussion), yet #515's Outcome section ("A student draws a combinational circuit and reads its truth table...") makes no mention that hierarchical circuits are out of scope for PF-1 if it truly shares #306's extractor as claimed. An instructor who draws a subcircuit-based combinational block — an entirely ordinary use — hits an undisclosed capability gap. Recommend: state the inherited refusal set explicitly in #515 (or in #563) and soften the unconditional "a student draws a combinational circuit" claim.

**4. (Medium) AC-4 + KC-31-2 form a self-certifying escape hatch for PF-4.** AC-4 requires only "a written document" with gaps "closed or refused by name," and KC-31-2 says: "If PF-4's assessment shows the existing state-machine element already at parity, PF-4 closes as verified with the document as the artifact." Unlike AC-1/AC-2/AC-3 (golden tests, round-trip checks), PF-4 has no independent oracle — the same work item performs the assessment and gets to declare victory. The codebase already has a fairly complete FSM editor (`src/jls/elem/StateMachine.java`, `src/jls/edit/StateMachineDialog.java`: states, conditional/unconditional/"if no other condition" transitions, signal-value conditions), which makes "we assessed it and it's already at parity, ship the document" a plausible, cheap way to close 2–3 mw of budget without building anything. Recommend: name at least one concrete, checkable parity criterion up front (e.g., "a canvas-based state-diagram view, not just a list dialog" — visibly absent from the current `StateMachineDialog`) rather than leaving the verdict entirely to the self-authored document.

**5. (Medium) The issue body is already stale relative to its own comment, and the linkage is prose-only.** The YAML front matter still reads `planned_features: [PF-1 unfiled, PF-2 unfiled, PF-3 unfiled, PF-4 unfiled]`, but the sole comment (~1.5 hours later) reports all four filed as #563–#566. The body was never edited to match, and — consistent with `has_parent: false, has_children: false` returned by the GitHub API for #515 — none of #563–#566 were registered as GitHub sub-issues, so the only link from capstone to its own feature set is a comment's markdown table, not a structural relationship. Given this repo's own convention (visible in #306, #62) of treating the YAML block as the authoritative status source, a reader or tool that trusts the body over the comment gets wrong data. Recommend: edit the body's YAML to the real issue numbers and register #563–#566 as sub-issues.

**6. (Medium) AC-1's "golden-tested against exhaustive simulation" bar collides with a documented value-domain bug that #515 itself cites via #306 but never addresses.** `src/jls/elem/TruthTable.java:1447-1449` forces output don't-cares to concrete 0 during simulation ("// don't care becomes false"), and `:1432-1434` silently no-ops on an unmatched input row instead of signaling unknown. #306 — the very issue #515 orders after and shares an extractor with — names this exact code as evidence that JLS's 2-state value domain cannot honestly represent "unknown." Exhaustive simulation of a circuit with output don't-cares will therefore observe concretized 0s, not the don't-care a table author intended, so "truth table extracted by simulation" and "truth table minimized by PF-2's Quine–McCluskey" (which needs genuine don't-cares to be useful) are working from two different notions of the same concept. #515 doesn't scope around this at all. Recommend: either scope PF-1/PF-2 to input-side don't-cares only (fully specified outputs), or state explicitly how output don't-cares will be represented consistently with #306's eventual value-domain work.

**7. (Low) Quantification is thinner than sibling capstones filed the same day.** #306 gives numeric kill thresholds ("15 mw actual / 1.36x overrun," "60% of element instances," a named corpus manifest) and #62 gives numeric rubric constants (`MAX_OVERLAPS = 0`, `MAX_CROSSINGS_PER_NET = 0.5`, etc.). #515's `band_mw: "8-13"` has no per-PF derivation shown beyond the four PF line-ranges (which sum to 8-13 correctly, at least — arithmetic checks out), and KC-31-1/KC-31-2 are qualitative. Given the issue explicitly self-labels "lean filing," this may be intentional deferral to #563-566, but it does mean #515 itself is less auditable than its neighbors.

**8. (Low, solid) The competitive evidence citation is accurate.** #510 §2 does say JLS "*loses* today on ... circuit analysis (truth-table synthesis, FSM editors in Digital/DEEDS/Issie)" — the rationale is real, sourced, and independently corroborated, not fabricated or exaggerated.

**9. (Low) Title overpromises relative to PF-4's actual floor.** "...and an FSM is designed as states, not gates" reads as a delivered capability, but per KC-31-2 the PF-4 deliverable can legitimately resolve to "no change, here's a document" if today's `StateMachine` element is judged sufficient — so the title's third clause could end up satisfied only in the loosest "already true" sense rather than by anything #515 causes to be built.

## What's solid

- The core mechanical claims (AC-1/AC-2 round-trip, reusing #306's extractor rather than building a second one) are a reasonable, low-duplication design.
- KC-31-1 (no Espresso-class heuristic minimizer in v1) is a sensible, explicit scope cliff that keeps PF-2 bounded.
- AC-5 (headless/batch callable) is consistent with this repo's established batch-interface contract and its instructor/grader audience.
