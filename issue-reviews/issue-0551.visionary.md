# Issue #551: FEAT-C27-4: every shipped example is browsable as a published SVG gallery page — a prospective user sees real circuits before installing anything
- Lens: visionary
- Date: 2026-08-08
- Reviewer: Claude Opus 5
- Verdict: endorse-with-reframing

## What this issue is really for

CAP-27 (#511) exists because of one finding: a switcher from a rival "bounces in the
first ten minutes without ever discovering the parts of JLS that are genuinely
superior." PF-4's job in that stack is **pre-install evidence** — the artifact a
stranger can look at before committing a download.

Judge the issue against that job rather than against its own ACs and a gap opens.
What #551 proposes to publish is *drawings of circuits*. A drawing of a full adder is
the single least differentiated thing JLS produces: Logisim-Evolution, Digital,
CircuitVerse and Falstad all put circuit pictures on their front pages, and three of
them put a *running* one there. The parts of JLS that are actually superior — the
documented batch-interface stability contract (`docs/batch-interface.md`), VCD export
for autograders, the headless multi-arch container, the byte-reproducible jar, the
normative simulation-semantics spec — appear nowhere on the page this issue
describes. The gallery as specified is a correct, cheap artifact that shows the
prospective user the one axis on which JLS is ordinary.

That is the reframe worth having. Everything else here is scaffolding.

## Reframe A (primary): a gallery of *worked examples*, not a gallery of pictures

Each entry should be: the SVG render, the caption, **and the circuit's actual batch
output** — the watched-element table from its `-t` test vectors, or the `-r` trace
excerpt, verbatim, generated by the same command.

The cost is close to zero above the picture, because that output already has to
exist. #548 AC-3 requires that every listed example "simulates under the batch
simulator in a headless test" — the `SampleCircuitsTest` shape. So the corpus already
ships with test vectors and known-good output; #551 would merely stop throwing it
away at publication time. The generator becomes `-i out.svg` plus `-b -t`, both
shipped, both already exercised (`test/jls/CliImageExportTest.java`,
`test/jls/BatchSimulationGoldenTest.java`).

The payoff is disproportionate:

- It is the only pre-install surface in the whole CAP-27 stack that speaks to the
  **instructor with an autograder** — the switcher who actually has budget and
  institutional inertia to overcome, and the audience #510's teardowns say JLS wins
  on and never tells.
- It stops the gallery from being a strictly weaker version of #573. The #551↔#573
  adjudication in the comment thread draws the line as "one is a picture, the other
  is a running simulator," and on that line #573 wins every visitor. Draw the line
  instead as **"one shows a circuit *and what it computes*, checkably; the other lets
  you poke it"** and both surfaces have a reason to exist even after CAP-32 lands. It
  also survives #572's go/no-go saying *no*, which is the case #551 should be
  designed for.
- It makes the page self-verifying in a way no drift check can: a published
  input/output pair that a reader can reproduce with one `docker run` line the README
  already documents.

This does not breach any fence in the boundary notes. It adds no runtime (AC of #573
untouched), no print styling (#536 untouched), no manual (#519 untouched).

## Reframe B: publish it as `docs/gallery.md`, not as a site

AC-2/AC-3 offer "the repository or GitHub Pages." Take the repository, and say so
explicitly — the alternative is quietly worse than it looks.

There is no Pages infrastructure in this repo today (nothing in `.github/workflows/`
touches it), and CAP-35 (#519) PF-2 owns "a hosted versioned manual … per release
(`/5.0.x/`)" with AC-3 "screenshots in README/docs are build products." Standing up a
second, one-page web-publishing seam now means CAP-35 either absorbs it or fights it.
A generated `docs/gallery.md` plus `docs/gallery/*.svg`:

- needs zero new infrastructure and zero operational upkeep;
- is versioned with the circuits it depicts, and reviewable as a diff — SVG is text,
  so a re-render shows up in PR review as a readable change;
- works in a clone and offline, which matches the lab-machine deployment model
  ARCHITECTURE.md's help-delivery decision treats as load-bearing;
- satisfies AC-4 exactly and for free: GitHub Markdown honors `<picture>` with
  `prefers-color-scheme` sources, so light/dark is a template detail, not a design
  project;
- becomes a *build input* to CAP-35's site when that lands, rather than a page CAP-35
  has to migrate or deprecate;
- structurally cannot grow into #519's scope. A markdown file in `docs/` does not
  turn into a documentation site by accident; a Pages deployment does.

And it collapses AC-3's second half. If the gallery is markdown in-tree, the README
can inline the best two or three entries directly and link the rest — at which point
"get the prospective user to navigate to the gallery" stops being a problem anyone
has to solve. The gallery becomes the README's tail rather than a destination
competing with it.

## Reframe C: the corpus is the asset; the gallery is a pure function of it

This issue is the fourth consumer of a corpus no issue owns *as data*: the Examples
menu (#548/#764), this gallery, #573's demo pages, #574's links, CAP-33's course
kits, and later #536's handouts and #546's tactile profile. The one thing #551 must
not do is mint a gallery-only copy of anything — a caption, a category, an ordering.

#773 AC-3 already says captions come from #548's metadata. Raise that from a task
constraint to the feature's own invariant, and state it as a negative: **the gallery
contributes no metadata of its own and holds no second copy of any string.** If the
sibling recommendation on #768 is taken (caption lives in the circuit as its header
`Text` element, exercise as an attribute on it), then a caption in the gallery cannot
diverge from the picture beside it, because both are renders of the same bytes. That
is the elegant end state, and #551 is the consumer that most benefits from it.

## On AC-2's drift check — I am disregarding it as written

"Regenerated by one scripted command in CI … so renders cannot silently drift" is the
right *goal* and the wrong *mechanism*, and the mechanism borrows a guarantee this
feature does not own. `test/jls/SvgExportTest.java` says so in its own header
comment: "Deliberately no full-document golden — text layout coordinates depend on
the JDK's font metrics, which differ across machines." Every renderer under
`src/jls/edit/` sizes text through `SwingTextMetrics`/`FontMetrics`, and the SVG
branch (`CircuitRenderer.java:312-358`) shares that paint path. Cross-platform
byte-identical vector output is precisely what #536 AC-2 funds at 4-6 mw *with a kill
criterion* — and #551 correctly declares it does not block on #536, then writes an AC
that presumes its result.

Two clean exits, both better than a committed-render byte diff:

1. **Do not commit the renders.** Generate them in the publish step. A stale picture
   is not detected, it is unconstructible. (This is the route the #773 review takes,
   and it is right.) It costs the in-clone/offline property of Reframe B, so pick
   deliberately.
2. **Pin the renderer to the shipped container image.** `ghcr.io/anadon/jls` is
   already a released, signed, headless JLS with `fonts-dejavu-core` baked in — i.e.
   an environment where fonts, JDK and JLS version are all fixed. Generating the
   gallery with one pinned tag on one arch makes the byte diff meaningful today,
   keeps the renders in-tree, and has a second payoff the issue never considers: the
   gallery build becomes a standing end-to-end smoke test of the artifact autograders
   actually consume.

Prefer (2) if the renders stay in the repo, which Reframe B wants.

## Ordering: build the generator before the corpus, not after

`ordering_after: [548]` is defensible for *publication* and backwards for
*construction*. The gallery generator is the cheapest curation instrument CAP-27 has:
a circuit that renders illegibly at gallery scale, or whose caption does not fit
beside its picture, is a circuit that will also teach badly and menu badly. Run the
script against the 3-5 sample baseline #381 lands and use it as the feedback loop
while #548's ten circuits are authored. The gallery *page* still ships after #548 —
"a gallery of test fixtures is not the product" stands — but the tool should exist
first.

## Residual and band

At 1-2 mw the band prices a project that, after #548/#768 land the corpus and
captions, after `-i out.svg` and `-b -t` are shipped, and after Reframe B removes the
hosting question, is a shell script and a markdown template: ~0.5 mw, which is what
#773 already carries. The honest residual of #551-the-feature above its tasks is a
decision, not labor — *what the page shows and where it lives*. That is exactly the
decision the two reframes above make, and it is worth more than the code.

## Verdict

**endorse-with-reframing.** The outcome is right and the capstone needs it. Change
what the page contains (worked examples, not pictures), where it lives
(`docs/gallery.md`, not a new Pages seam), and how drift is prevented (pinned
container render or no committed renders at all — not a bare byte diff that #536 has
not paid for yet).
