## Findings (numbered by severity)

**1. (High) The issue's own escalation about the shared `Theme`/`UserPrefs` seam is not reflected anywhere in the binding contract.** The 2026-08-04 comment states plainly: *"the Theme seam has six declared consumers and no named seam owner"* — #289, #542, #543, #546, #570 (via #289), and #596 all transform or extend it, on top of cross-cluster SVG-export consumers #536/#551. Yet §3 (Feature-Level Interface & Data Contract), §4 (Global Invariants), and the Completion Criteria checklist never mention this risk or add a criterion for it. As written, #76 can satisfy every box in "Completion Criteria (Definition of Done)" — its own three children closed, its own three planned tasks filed/descoped, IC1–IC4 verified — while the cross-issue seam-ownership question the maintainer's own comment flagged as escalated remains completely unresolved. That is a goal/verification gap: the stated finish line does not require fixing the problem the issue itself identified as its most consequential open risk.
   - Recommendation: add a Completion Criteria line (or a follow-up filed issue named in a REPLAN) requiring an explicit seam-owner designation before #76 is closed, given it gates at least six other open features.

**2. (High) IC1–IC4 verification is self-attested prose, not a gate.** §5 says IC1's evidence "Does not exist yet; built at this issue's close-out," and the DoD checklist item is "IC1–IC4 … verified at a named commit; command and output recorded in a closing comment." Nothing in the contract requires that verification to be an automated, reviewed test that stays in the suite — a closing comment claiming a command was run and pasting output is exactly the kind of criterion that can be satisfied by an agent asserting success without anyone re-running it. Contrast with §4 invariant 4, which *is* backed by a real, currently-passing ratchet (`ThemeTest`'s ≥25 delta-E bar) — the integration criteria have no equivalent ratchet, only a promise to write one later.
   - Recommendation: require IC1–IC4 to land as permanent, CI-run tests (as #542's `CvdStateDistinguishabilityTest` apparatus is already proposed to be) before close, not merely narrated in a comment.

**3. (Medium) Five weeks of comments, zero landed children.** The issue was filed 2026-07-08; the latest comment is 2026-08-04 (today is 2026-08-09 per session context). In that span it accumulated 12 comments — two REPLANs, a full template restructuring, and three separate cross-feature deduplication passes (#355/#542/#543/#570, then a second consolidated pass, then a third boundary pass covering #380/#381/#546/#596) — while `requires_tasks: [286, 287, 289]` still shows all three open with **no PRs against any of them** (the 2026-07-28 comment states outright: "no PR this cycle delivered remaining #76 scope — Theme.java and UserPrefs.java were untouched"). The bulk of the issue's growth is process scaffolding (dedup boundaries, machine blocks, mermaid graphs) rather than shipped scope. That's a feasibility/velocity signal worth flagging before assigning more work here: the coordination overhead is now large relative to the three genuinely small, well-scoped remaining child tasks.
   - Recommendation: before further REPLAN passes, land #286/#287/#289 (each already precisely scoped with real line counts) rather than continuing to accrete cross-issue boundary commentary on the parent.

**4. (Medium) `blocked_by: []` reads as inconsistent with the rest of the machine block.** `requires_tasks: [286, 287, 289]` and the mermaid graph both show #76's close-out strictly gated on those three (`T286 --> F76`, etc.), yet `blocked_by` is empty. If the template's convention is that `blocked_by` only names *external* blockers and children are tracked separately via `requires_tasks`, that convention is never stated in this issue (or in the visible parts of the other referenced issues), so a reader has to infer it. As written it looks like a self-contradiction: three required tasks are open, but the field that should say "this is blocked" says nothing is blocking it.
   - Recommendation: either populate `blocked_by: [286, 287, 289]` or add one line making explicit that `blocked_by` is reserved for non-child blockers.

**5. (Low) Two different, unreconciled counts for the same hardcoded-color sweep.** `ARCHITECTURE.md` (§ "Look-and-feel: FlatLaf light is the default") and the `Theme.java` javadoc both say "~126 hardcoded chrome/canvas color call sites"; this issue and #289 say "~113-site hardcoded-black foreground sweep" (and the grep confirms 113 for `Color.black`/`Color.BLACK` specifically). These are plausibly different subsets — 126 likely counts all hardcoded `Color` literals (chrome + canvas, including the 12 CYAN/yellow/WHITE sites #286 owns), 113 counts only black foregrounds (#289's scope) — but the issue never states the relationship or the arithmetic (113 + 12 ≈ 125, close but not stated), leaving a contributor to reconcile two "canonical" numbers themselves.
