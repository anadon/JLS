# Issue #410: TASK-0011: an event that arrives past the time limit survives the stop, so raising the limit and resuming continues the run instead of silently skipping a transition
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of the claim

The issue asserts `Simulator.runEventLoop` (`src/jls/sim/Simulator.java` L215-L241) polls the head event and removes it from `dupCheck` *before* testing the time limit, so an event past `maxTime` is permanently discarded rather than deferred, and that "the interactive simulator offers exactly the workflow that makes this observable: raise the limit and resume." I verified the quoted code against the current tree: it matches line-for-line (`eventQueue.poll()` at L224, `dupCheck.remove(event)` L225, `now = event.getTime()` L228, discard at L231-234). The engine-level defect — `runEventLoop()` called twice on the same un-reset state loses whatever event straddled the first limit — is real and reproducible exactly as O3 describes for a raw `Simulator` subclass.

## Findings, most severe first

**1. (Correctness of the central causal claim) The GUI workflow the issue says demonstrates the bug does not appear to exist — resume-after-limit-stop always re-inits, not resumes.**
O5 argues the bug is user-reachable because `InteractiveSimulator.setMaxTime()` "writes maxTime and nothing else... `Simulator.reset` is not called," and calls this "the workflow that makes this observable." I traced the actual call graph:
- The sim thread's `run()` (`InteractiveSimulator.java` ~L326-L710) calls `runEventLoop()` **exactly once**, then unconditionally sets `sim = null` at the end (L710 region) — there is no outer loop that re-enters `runEventLoop()`.
- Every button handler that calls `setMaxTime()` — Start (L317), Step (L345), Animate (L389) — is gated on `sim == null`: when true it calls `runSim()`, which unconditionally calls `initSimulation()` (`runSim(boolean)`, ~L600-L603: "reset clock/queues and initialize all elements"), clearing `eventQueue`/`dupCheck`/`now` and re-running the circuit from time 0.
- The *only* non-reset continuation path (Step/Animate's `else` branch, and the literal "Resume" button at L479) requires `paused == true` (`if (!paused) return;` in Step's handler). But `paused` is a distinct flag from the limit-stop path: pausing happens in `beforeEvent()` *before* the poll each iteration (L220-225), and the drop only occurs *after* a poll, at which point the loop `break`s and the thread runs to completion (`sim = null`) without ever setting `paused`. The action bar shown after a limit stop is `start, step, animate, print, help` (no "resume" — confirmed at the epilogue's `action.add(...)` calls), consistent with this: the shipped UI does not offer a "Resume" affordance after a limit stop at all.
- Consequently, for the drop to occur (event polled and found past `maxTime`) the run must have fully terminated (not paused); and the only GUI paths that re-enter simulation from that state (`sim == null`) go through `initSimulation()`, which discards the *entire* queue and restarts from time 0 — not a silent one-event skip, but a full, deterministic re-run that (for a deterministic circuit with no external test-vector state) would actually *reach* the event at the new limit correctly. Conversely, the one path that truly avoids `initSimulation()` (genuine pause, `paused == true`) cannot exhibit the drop, because pausing happens strictly before the poll that would trigger it.
- If this tracing is right, the "Intended Audience & Impact" claim — "Today that resume silently omits the transition... After this, the resumed run is the continuation the student was told it is" — describes user-visible behavior that the current GUI wiring does not actually produce. The defect is real in the shared engine method (reachable by any future caller that invokes `runEventLoop()` twice without an intervening reset — which is exactly what checkpoint/resume in #363 would need), but the issue's own justification for urgency and for the "suspended" recommendation ("it is what the shipped UI already implies," O5) is not established by the evidence given.
- Recommendation: before implementing, re-verify against the actual `InteractiveSimulator` GUI (not the `red.LimitProbe` harness) whether any code path re-enters `runEventLoop()` on a live thread without going through `initSimulation()`. If none exists, rewrite the Impact section honestly as "the shared engine method is not resumption-safe, which matters for #363's checkpoint/resume and for any future GUI affordance that resumes a truly-paused run across a raised limit" rather than claiming today's students are silently losing transitions.

**2. (Gameable acceptance criterion) P3 is not a valid regression test — it already passes on unfixed code, by the issue's own admission.**
O4 states explicitly: "That assertion passes at `2d0ca9d`... The defect is not a set/queue disagreement." Yet P3 ("every member of eventQueue is in dupCheck and vice versa") is still listed as one of only four required test methods and one of the "must hold after" predictions, and `theDedupSetAndTheQueueHoldTheSameMembersAfterALimitStop()` is on the required test list in §8. A test that is green before and after the change verifies nothing about the fix; it can pass while the real defect (event loss) remains, because it was never red. This directly matches the adversarial pattern of "verification could pass while the real goal fails." Recommendation: either drop P3 from the required test list (it's already covered by existing code, not this task) or explicitly label it a non-discriminating sanity check, not a fix-verifying assertion, so a reviewer doesn't credit it as fix evidence.

**3. (Self-undermining process) The issue asks for a decision "before writing code" while simultaneously spelling out the full implementation, file names, and test method names for its own recommended answer.**
Open Question 1 says the choice "**Blocks execution**, not filing," implying a maintainer should rule on suspended-vs-terminated first. But §8's Method, §7 (Interface & Data Contract), and §5 (Predictions) are written almost entirely in terms of "suspended" being correct (P1/P2 "must hold after, under 'suspended'"), with "terminated" treated as an afterthought bolted on via conditional clauses. An implementer under any time pressure has every incentive to just ship "suspended" and treat the "decision" checkbox as pro forma, since the alternative requires inventing an entire refusal UX (P7) that the issue itself only sketches ("a `protected` predicate... may be needed; if so it is added with its contract stated here in the PR, not invented at the call site" — i.e., not actually specified). Recommendation: either get the ruling recorded as a separate, prior, small issue/comment (as the issue itself suggests when it says "Get it ruled on before writing code"), or drop the pretense of an open decision and just recommend "suspended" outright with the terminated-branch material moved to a "rejected alternative" note.

**4. (Verifiability / provenance) The issue cites a planning corpus that does not exist in this repository checkout.**
O4 cites `docs/plan/tasks/TASK-0011-past-limit-event-drop.md` and the Threats-to-Validity section cites `docs/plan/evidence/BRIEF.md` §13. Neither `docs/plan/` nor any file matching `*BRIEF*` exists anywhere in the checked-out tree (`find`/`Glob` both empty); only `docs/*.md` design docs exist, and there's no `docs/plan` directory at all. `evidence_commit: 2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7` also does not resolve in this (shallow, 275-commit) clone, though the quoted `Simulator.java` content matches the current tip byte-for-byte, so the *code* claims are independently verified even though the *corpus* claims (what some other document asserts, and the PinChanged allocation count/commit in Threats to Validity) are not checkable from this repo alone. Recommendation: either commit the referenced planning corpus into the repo (if it's meant to be normative, per the pattern used for `docs/simulation-semantics.md`), or stop treating it as citable evidence in a GitHub issue that reviewers are expected to ground against the repo.

**5. (Minor / internal inconsistency) O5 refers to "`Simulator.reset`," a method that does not exist.**
The actual method, used correctly elsewhere in the same issue (O2), is `initSimulation()`. `grep` for `void reset(` or `.reset(` in `Simulator.java`/`InteractiveSimulator.java` returns nothing. Cosmetic, but in an issue this dense with precise line citations, a wrong method name is exactly the kind of small slip that costs an implementer time chasing a nonexistent API. Recommendation: fix the reference to `initSimulation()`.

## What holds up

- The core engine defect (O1/O3, poll-then-check ordering losing an event across two `runEventLoop()` calls) is real, precisely located, and reproducible from the quoted code alone — I confirmed every cited line number and snippet against the current `src/jls/sim/Simulator.java`.
- O2's claim that `post()`/`initSimulation()` are the only touch points for `eventQueue`/`dupCheck` synchronization is accurate.
- O6's `stopping`-before-pad ordering and the #51 citation are accurate (`InteractiveSimulator.java` L650-L661 matches).
- O7's peek license from the `runEventLoop` javadoc is accurately quoted (L207-213 matches, including the "queue is only modified on this thread" sentence).
- O8's batch-mode claim (`JLSStart.java` L249 sets the limit once; `JLSInfo.defaultTimeLimit = 100000000`) is accurate, so the "no batch golden can move" containment argument is sound.
- The `SimulationSemanticsRegressionTest.CountingSimulator` reuse pointer and the `SealedHierarchyTest`/`CONTRIBUTING.md` sealed-dispatch citations in Threats to Validity both check out against the repo.
- `docs/simulation-semantics.md` §4 currently only gives the loop's pseudocode and three termination reasons without stating suspend-vs-terminate semantics for a raised-then-resumed limit — so the claim that this task "adds" rather than contradicts an existing section is correct; no conflict there.

## Verdict rationale

The engine-level bug is real and worth fixing regardless. But the issue's central narrative — that this is observably broken for students today via the shipped interactive UI — rests on a chain of reasoning (O5) that a careful trace of the actual button handlers and thread lifecycle does not support: reaching the drop requires the run to have fully terminated, and every GUI path that restarts a terminated run goes through a full `initSimulation()` reset, not a resume. That changes both the urgency framing and the "suspended, because the shipped UI already implies it" justification for the recommended fix. Combined with a non-discriminating required test (P3) and a "decision-first" process the issue's own content undercuts, this needs rework — specifically, re-verifying and correcting the GUI-reachability claim — before implementation should proceed.
