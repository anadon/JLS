## Summary of the ask

`part_of_feature: 593` (FEAT-C37-2), `ordering_after: [TASK-C593-2]` (#805). Fix wire-segment hit-test resolution so a click selects the segment under the cursor (Digital #882-class fix), make the selected segment manipulable (move/split/delete) while preserving connectivity or refusing by name, record bsiever-fork #18's disposition, re-measure the timed 4-bit-counter benchmark against #592's baseline, and land none of it inside `SimpleEditor` (KC-37-1).

## Findings, most severe first

**1. [Critical — feasibility] The prerequisite decomposition this task depends on has not shipped, and #806 doesn't say so.** KC-37-1 forbids landing new logic in `SimpleEditor`; the parent feature #593 is explicit that new behaviour must land "in the decomposed collaborators #316 produces, driven through #441's `MouseMachine`/`InteractionState`." I verified against the current tree (`53116252116b9e74bbdf64d7df1f5e08b4e1768b`): no `MouseMachine`/`InteractionState` file exists under `src/jls/edit/` (`ls src/jls/edit | grep -iE "mousemachine|interactionstate"` → nothing), `SimpleEditor.java` is still 5,852 lines, and the actual hit-test loop this task must change is inline in that file at `src/jls/edit/SimpleEditor.java:2617-2618` (`for (Element el : circuit.elementsAt(x,y)) { if (el.contains(x,y)) {`), repeated at `:2673` and `:3348`. #316 (FEAT-008) is open with all its planned tasks "not filed" per its own body, #84 (the extraction task) is open with zero landed code, and #441 (TASK-0020, the specific task that would have produced the headless `MouseMachine`) is **closed as a duplicate merged into #84** — i.e. deduplicated bookkeeping, not completed work. There is currently no legal home for the fix this task demands. Its sibling **#805 (TASK-C593-2), filed the same minute, explicitly states "Nothing lands inside `SimpleEditor` (KC-37-1); if #316 stalls, this task waits rather than growing the god class."** #806 carries the identical KC-37-1 constraint but omits that clause entirely. Recommendation: add the same explicit `ordering_after`/wait-on-#316 language #805 already has, or the task is unstartable as filed without silently violating KC-37-1.

**2. [High — hidden dependency] AC-4 depends on a baseline that doesn't exist yet, and the issue doesn't order after it.** AC-4 requires the 4-bit-counter timing to be "re-measured under the same procedure as #592's baseline." #592 (FEAT-C37-1, the parity catalog) is itself open; its own AC-5 ("A timed baseline for the CAP-37 AC-4 task ... is recorded in the catalog") has not landed — I confirmed via `get_comments` that #592 has only two deduplication-pass comments, no baseline recording. #806's frontmatter `ordering_after` lists only `[TASK-C593-2]` (#805); it does not name #592, even though the parent feature #593 explicitly orders after "#592 FEAT-C37-1 (the parity catalog — no row, no funding)." As filed, #806 could be picked up before a baseline exists, making AC-4 unsatisfiable through no fault of the implementer.

**3. [High — untestable acceptance criterion] AC-5's blanket testability clause cannot cover AC-4 as written.** AC-5 says "each behaviour is pinned by a test that fails at the pre-change commit." Sibling tasks #804/#805 are careful to scope this correctly — e.g. #804 AC-3: "pinned by a #91-harness or headless-interaction-machine test ... no behaviour asserted only by a screenshot or a manual pass." #806's AC-4, by contrast, is a *human* editing-speed benchmark ("the timed 4-bit-counter task ... is re-measured ... and is not slower"). There is no described mechanism by which "build a 4-bit counter and time it" becomes a JUnit test that "fails at the pre-change commit" in the sense used everywhere else in this task family. Either AC-5 implicitly exempts AC-4 (and should say so), or AC-4 needs a scripted/replayable gesture-benchmark definition compatible with the project's headless-testing discipline — neither is specified.

**4. [Medium — factual mischaracterization of the defect] The issue's diagnosis of current behavior appears to be wrong, which risks steering the fix.** The Outcome text frames the bug as clicking selecting "whichever segment the hit test happened to find nearest" — implying today's code does a nearest-distance computation. I read the actual code: `SimpleEditor.java:2617-2618` does `for (Element el : circuit.elementsAt(x,y)) if (el.contains(x,y))` — a **first-match scan in spatial-index bucket order**, and `Wire.contains(x,y)` (`src/jls/elem/Wire.java:243-258`) is a boolean radius predicate (`ptSegDist < SPACING/2`, excluding the endpoint zones), not a distance-ranking function. There is no "nearest" computation anywhere in this path; the current selection is an artifact of iteration/insertion order, not proximity. AC-1 asks the catalog row to state "tolerance, tie-break, z-order" — that framing is closer to correct than the Outcome prose. Recommendation: fix the issue's own description before it becomes the spec someone implements against; conflating "arbitrary first-match" with "nearest" could lead to a fix that adds a distance-minimization step that isn't actually what's broken.

**5. [Medium — cross-repo authority] AC-3's "bsiever-fork #18 is recorded closed by name or refused by name" is ambiguous about who can act on it.** bsiever-fork is a separate GitHub repository under a different owner; anadon/JLS maintainers have no authority to close an issue there. The likely intent (matching #592/#521's identical phrasing) is "recorded in JLS's own catalog/docs as closed-or-refused," not "close the upstream issue," but the AC as worded could be read either way by an implementing agent. Tighten the wording to "recorded in #592's catalog" explicitly.

**6. [Medium — accountability diffusion] Four separate issues claim ownership of the same bsiever-fork-#18 disposition.** #521 (CAP-37) AC-3, #592 (FEAT-C37-1) AC-4, #593 (FEAT-C37-2) AC-5, and #806 AC-3 all state that bsiever-fork #18 gets "closed or refused by name." No single one of them is named as the source of truth; #806 recording it and #592's catalog recording it independently risks either double-work or drifting/contradictory text with nothing to reconcile them.

**7. [Low — gameable acceptance criterion] AC-2's "refuse by name" escape hatch can satisfy the letter while delivering none of the outcome.** "A selected segment can be manipulated — moved, split, deleted — as the segment the user clicked on, preserving the rest of the wire's connectivity or refusing by name" can be trivially satisfied by refusing every move/split/delete operation with a named message, passing AC-2 and even AC-5's "pinned by a test" requirement while shipping zero of the Digital #882-class UX improvement the task exists for. Recommend a floor requirement (e.g., at least move and delete must succeed in the common case; only genuinely ambiguous topology may refuse) rather than leaving "refuse" universally available.
