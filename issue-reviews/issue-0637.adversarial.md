# Issue #637: TASK-C562-2: a Digital test construct with no -t equivalent is a named loss in the report, never a quietly thinner vector file
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

The task's thesis — "the failure mode this task exists to prevent is a translated suite that runs green because it tests less" — is a genuinely valuable guardrail, and the division of labor between this task (test-language content) and #556 (report carrier) is clean in principle. But the task is built on two unfiled prerequisites (`TASK-C556-1`, `TASK-C556-2`) that exist nowhere in this repository outside the issue-review corpus itself, routes its output into a shared report contract (#556) whose own body does not list this task's parent feature as a consumer, and understates how large the "loss" category actually is given the current `-t` grammar has no expectation/comparison production at all. AC-4's single-fixture bar is also gameable in exactly the pattern the fleet's own review of the parent feature (#562) already flagged.

## Findings, most severe first

### 1. AC-1/AC-2 feed a shared report contract that, per its own text, does not list this task's feature as a consumer

AC-1 cites "FEAT-C29-5 AC-2" (i.e. #562's AC-2) and AC-2 requires reporting into "the shared FEAT-C29-1 report" — #556. #556's own body, under "Boundary and reference notes," enumerates its consumers explicitly: *"Consumers: FEAT-C29-2 (.dig), FEAT-C29-3 (.cv), FEAT-C29-4 (Falstad text)."* FEAT-C29-5 (#562, this task's parent) is absent. This is not a new observation — the fleet's own review of #562 already caught it (`issue-reviews/issue-0562.adversarial.md` Finding 2) — but #637 is the task that would actually *write* the entries into that schema, and it inherits the contradiction unresolved: the schema this task's AC-1/AC-2/AC-3 all assume exists (construct → disposition → location → explanation, sized for *test-language* constructs) has never been confirmed to fit a vocabulary that isn't circuit elements. Digital's test DSL and its circuit-element set are different vocabularies, and nothing in #556 or #637 reconciles that.

**Recommendation:** block this task on #556 being amended to list FEAT-C29-5 as a consumer and confirm the schema fits test-construct dispositions, not just circuit-element dispositions, before this task starts.

### 2. Both named prerequisites — TASK-C556-1 and TASK-C556-2 — are not filed anywhere in the tracker

`ordering_after` names `"TASK-C556-1 (the report schema)"` and AC-3 depends on "the totality assertion from TASK-C556-2." A search of every markdown file in this repository (including `CHANGELOG.md`, `docs/capability-roadmap/**`, and the entire `issue-reviews/` corpus) for `TASK-C556` finds **zero** occurrences of `TASK-C556-1` or `TASK-C556-2` outside the review files being generated by this same fleet — i.e., these tasks are referenced but do not exist as filed issues. Confirmed mechanically: `mcp__github__issue_read get_sub_issues` on #556 returns an empty list, and `get_parent` on #637 itself returns `null` despite `part_of_feature: 562` in the YAML — there is no GitHub-native issue-hierarchy link anywhere in this cluster (#556 → TASK-C556-*, #562 → #635/#637/#639). The entire task graph is prose-only and unverifiable by any tool that isn't a human cross-reading YAML comments.

**Recommendation:** file TASK-C556-1 and TASK-C556-2 as real issues (or fold the report-schema and totality-assertion work directly into #556's own AC-1/AC-2) before this task can be scheduled against them, and use GitHub's actual sub-issue links for the #562 family so the graph is machine-checkable.

### 3. The premise treats "constructs with no -t equivalent" as an edge case; the batch interface's actual shape makes it the default case for nearly every real test

`docs/batch-interface.md` §2.2's grammar is `file ::= { signal }`, `signal ::= name initial { step } "end"`, `step ::= ("for" duration | "until" time) value` — every production posts *stimulus*; there is no expectation/comparison production anywhere in the file (independently confirmed by #466's own investigation: *"the word 'expect' does not appear in the document at all"*). TASK-C562-1 (#635, "the translation this reports on") is explicitly scoped to emit only the runner's input format: *"This emits the runner's input format; it does not extend the runner."* Given that, **every** Digital test case that carries an expected-output assertion — which is what makes it a test rather than a stimulus script — will have 100% of its assertion content dropped by the translation this task reports on, not merely "some" constructs occasionally. AC-2's `mapped-with-caveat` disposition and the Outcome's framing ("An instructor reading the report knows exactly which of their assertions did not come across, instead of discovering it when a wrong submission passes") read as though caveat-bearing entries are the exception; per the actual channel, they are the norm for any test case with a pass/fail meaning at all. The issue never states this plainly, never budgets for report volume at that scale, and never asks whether "mapped-with-caveat" is the right label when the caveat covers the entire verdict-bearing half of the test case.

**Recommendation:** state explicitly, in the Outcome or a boundary note, that assertion/expected-value content is *categorically* undroppable-to-`-t` given the current batch interface (not a rare construct), and confirm the shared schema (#556, once fixed per Finding 1) is designed for "this is the common case, not the rare one."

### 4. AC-3's totality claim has no defined universe to be total over

AC-3 requires "the set of test constructs dropped equals the set reported, in both directions." That is only checkable against an enumerable list of Digital test-language constructs. This repository contains no reference to Digital's test-DSL grammar anywhere (`grep -r Digital` turns up only sibling importer issues and their reviews, never a construct list), and this issue does not cite one. An implementer has to reverse-engineer Digital's test syntax from scratch before AC-3 is even well-posed, and nothing in the issue names that discovery work, budgets time for it, or points at an authoritative source (Digital's own docs/grammar) to anchor the totality check against.

**Recommendation:** add a boundary note naming the authoritative source for Digital's test-language grammar (or file the discovery work as its own prerequisite), so "the set of constructs" in AC-3 has a fixed referent.

### 5. AC-4's single-fixture bar is gameable in the same way the fleet already flagged one level up

AC-4: "A fixture containing **at least one** untranslatable construct proves the reporting path is live." Given Finding 3 (assertions are the dominant, near-universal loss category, not an exotic one), an implementer can satisfy AC-4 by choosing a fixture whose single untranslatable construct is some minor Digital feature (e.g. a data-table generator or a breakpoint directive) while never exercising the report path against the loudest and most consequential loss category — dropped expected-value assertions — in any golden or mutation-guarded test. The parent feature's own adversarial review (`issue-reviews/issue-0562.adversarial.md` Finding 4) already identified this exact single-fixture gaming pattern for #562's AC-4 and recommended requiring coverage across construct categories; that critique was not carried down into this child task when it was filed.

**Recommendation:** require the fixture corpus to cover at least: (a) a dropped expected-value assertion, (b) a partially-translated test case naming specific dropped assertions, and (c) one other construct category, rather than "at least one."

### 6. Solid — the anti-vacuity mechanism itself is feasible and consistent with existing practice

AC-4's "a mutation that drops it silently fails the build" pattern is good discipline, and this repository already has real mutation-testing infrastructure and culture to draw on (`docs/mutation-testing-trial-2026-07.md`, PIT scoped to `jls.sim.*` and other core packages). Whether implemented via full PIT or a hand-written negative test, the mechanism is well-precedented here. No issue with feasibility of the *technique*, only with what it is required to cover (Finding 5).

### 7. Solid — the report-carrier/content-supplier split is a clean boundary, contingent on Finding 1

"Report carrier is #556's; this task supplies the test-language content of the entries" is the right shape for a shared-infrastructure design and mirrors the same split already used by #556's other named consumers (#558, #559, #561). No objection to the division of responsibility itself — only to the fact that the contract on the other side of it (Finding 1) doesn't yet acknowledge this task exists.

## Verdict rationale

Three high-severity findings compound: the shared schema this task must write into doesn't list it as a consumer (Finding 1), the two prerequisite tasks named in `ordering_after`/AC-3 are not filed anywhere and have no tooling-visible link to this issue (Finding 2), and the Outcome/AC-2 materially understate how much of every real Digital test case will end up in the "loss" bucket given the current `-t` grammar (Finding 3). Combined with an easily-gamed AC-4 (Finding 5) and an unanchored AC-3 (Finding 4), this cannot be executed as a single coherent spec without rework upstream (#556) and downstream (filing the missing TASK-C556-* prerequisites) first. **needs-rework.**
