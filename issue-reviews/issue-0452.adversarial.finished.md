# Issue #452: TASK-0062: a higher-radix design exports, dumps a VCD a third-party viewer can interpret, and is testable with -t vectors — while a binary circuit's bytes stay identical on all three paths
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Findings, most severe first

**1. [Critical] This issue's central HDL-export deliverable directly contradicts the design of its own hard prerequisite, #453 (TASK-0061), which explicitly puts N-ary HDL rendering out of scope and leans toward the opposite classification bucket.**
#452's Abstract promises "a higher-radix design exports... This task adds explicit policy rows and a binary-encoded-ternary lowering," and P4 requires: "Export a two-input ternary MIN gate; observe emitted Verilog byte-equal to a committed golden whose header declares the 2-bit-per-digit encoding." But #453 — the issue that actually creates the four batch-1 N-ary element types this lowering would apply to (`RadixBridge`, `MvlConstant`, `MvlGate`, `MvlNot`) — states in its own §7.12: **"`EXPORTED` is not widened. The four new classes stay out of it deliberately... Adding any of them to `EXPORTED` without a rendering would reintroduce the fails-open defect."** Its §13 Conclusion lists "HDL rendering of N-ary elements (they fail closed here by design)" as explicitly **out of scope**, and its Open Question 1 asks "Do the four new classes go into `HdlExporter.SKIPPED`, or stay unclassified?" with the **recommended default: `SKIPPED`**, i.e. warn-and-skip with no rendering at all — not `EXPORTED` with a BET lowering. If #453 lands as its own text recommends, there is no exported N-ary class left for #452's P4 golden to attach to, and #452's Abstract oversells what the prerequisite actually delivers. Neither issue's Related Work section flags this tension to the other. Recommendation: before either is picked up, reconcile the two — either #453's Open Question 1 must be answered "EXPORTED, with the lowering #452 defines" and both issues' text updated to say so, or #452's scope and its promised P4 golden must be renegotiated against a `SKIPPED` outcome.

**2. [Critical] The four-bucket HDL policy model this issue's plan depends on (`REJECTED`, for refusing classes "with an actionable reason") does not exist on `master` — confirmed independently and already flagged on this very issue by the maintainer.**
Reading `src/jls/hdl/HdlExporter.java` at HEAD (`5b05d67`) directly: only three policy sets exist — `EXPORTED` (line 422), `SKIPPED` (431), `TOPOLOGY` (436) — and an unclassified element falls straight to the offender list with no reason attached (`grep -n REJECTED src/jls/hdl/HdlExporter.java` returns nothing). Issue #452's own O1 quotes a `REJECTED` map with a javadoc at `:446-460` as though it exists today, and its Method says "with a BET lowering for the exported ones and **an actionable reason for any refused one**" — machinery that is not there to use. The issue's own comment thread (comment id 5171420206, posted by the maintainer on 2026-08-03) already flags this: `REJECTED` is branch-only, absent from `master`, and "on `master`... it just rests on three buckets rather than four... treat the `REJECTED` half as *proposed*, not present; on `master` it is the work described by #492." **#492 is not filed until roughly two hours after #452** (created_at 19:05 vs #452's 16:57 on the same day) and remains open/unlanded five days later. Yet #452's `blocked_by` and `related` lists (`[361, 376, 419, 422, 63, 232]`) never name #492, so a picker-upper following the machine-readable dependency data has no signal that the `REJECTED` bucket — which the Method section treats as pre-existing scaffolding to add rows to — must first be built by a separate, unlinked issue. Recommendation: add `#492` to `related` (or `blocked_by`, since a refused-with-reason row cannot be written without it) and correct O1's framing from "the map exists" to "the map is proposed by #492."

**3. [High] The hard prerequisite TASK-0061 now has a filed, open issue number (#453) — filed the same day, two minutes after #452 — yet #452's `blocked_by` is still `[]` five days later, with the same "a link pass must add it" placeholder unedited.**
#452's machine block reads `blocked_by: []` with the comment "TASK-0061 (the N-ary element family) is a genuine hard prerequisite but is not yet filed and its number cannot be verified here" and "**A link pass must add it.**" That was true at filing (16:57:21Z); #453 was created at 16:57:38Z the same day — plausibly concurrent, as the issue anticipated. But at the time of this review (2026-08-08, five days later), #453 is open and easily discoverable (`gh`/search finds it immediately), and #452's structured `blocked_by` field has not been updated to `[453]`. A picker-upper reading only the YAML front-matter — which is precisely the audience `blocked_by` exists to serve — would not see the dependency at all. This is the same defect class independently found in the fleet's review of sibling issue #455 (finding 6: stale `blocked_by` after its own named successor was filed). Recommendation: update `blocked_by` to `[453]` (and add `#492`, per finding 2) before this issue is worked.

**4. [High] O6/P10's fix — an explicit binary-only guard on `BatchSimulator.vcdValue` — is independently proposed as the identical fix by sibling issue #419 (TASK-0059), and #452 explicitly disclaims any ordering relationship despite the overlap.**
#452 O6 observes `vcdValue(int bits, BitSet value, String code)` (`src/jls/sim/BatchSimulator.java:538-554`, verified present at HEAD) reconstructs the HiZ marker from a bit count and states "Under a radix-3 signal the `bits` it is given must be the **binary** width, not the digit count," with P10/§8's Method requiring: "Give `vcdValue` an explicit binary-only guard." Separately, #419 (TASK-0059) §5 P9 requires, for the same function: "`HdlExporter` and `BatchSimulator.vcdValue` carry an explicit **binary-only guard** rather than relying on the shim (O10), and neither throws on a binary circuit" — word-for-word the same target, same mechanism. #452's Related Work section addresses #419 only to say "No ordering edge claimed; the guard in P10 is this task's own" — asserting independence rather than resolving the overlap. Two issues independently modifying the same 17-line private method with no cross-reference in either's `blocked_by`/`blocks` risks either a merge conflict, duplicated work if both land, or a silent behavior gap if one lands first with a guard shaped differently than the other assumed. Recommendation: pick one task to own `vcdValue`'s guard (likely #419, since it owns the general non-binary-radix validation `getBits()` shim this guard is a variant of) and have #452 consume it rather than re-deriving it.

**5. [Medium] The dependency graph this task actually needs is four unlanded issues deep, not the "one hard prerequisite" the issue foregrounds.**
Beyond TASK-0061 (#453, finding 3) and the `REJECTED` bucket (#492, finding 2), #453 itself is `blocked_by: [419, 422]` (TASK-0059's per-put radix validation and TASK-0060's operator kernel), neither of which has landed. So #452's real precondition chain is: #422 → #419 → #453 → (#492, unlinked) → #452, a five-issue chain, none landed, three of them not even referenced from #452's own `related`/`blocked_by` fields (#453 is referenced only in prose, not YAML; #492 is not referenced at all). The parent feature #361 (FEAT-029) prices each child task at "2 wk" in its roster table, but its own §6 Sequencing section admits the *feature's* critical path is FEAT-028 → TASK-0060 → TASK-0061 → TASK-0062, and that the `jls.elem` coverage floor caps TASK-0061 at "roughly four to six new element classes per release... two release cycles even at full effort" — i.e. #452 cannot start in earnest until a multi-release critical path clears. None of this is disputed by #452, but presenting itself as a self-contained "2 wk" task with one named-but-unfiled blocker understates how deep in the queue it actually sits.

**6. [Medium] The "Evidence-commit note" claiming several directories are byte-identical between the (deleted) evidence branch and HEAD-at-filing is contradicted by the maintainer's own measurement on the sibling tracking issue #493.**
#452 states: "`src/`, `test/`, `pom.xml`, `scripts/`, `resources/`, `.github/workflows/`, `proofs/` and `examples/` are byte-identical between `2d0ca9d` and `839fb3a` (HEAD at filing)." But #493 (filed the same day, the durable replacement pin for the dying evidence commit) measures `git diff --stat 2d0ca9d 8288226 -- src/ test/ pom.xml .github/workflows/` and finds **seven files differ**, including exactly `src/jls/hdl/HdlExporter.java` (60 lines — the `REJECTED` map and its accessor) and `test/jls/hdl/HdlPolicyTest.java` (38 lines — its totality test). `8288226` and `839fb3a` are presented in the two issues as two different "HEAD at filing" pins, which is itself confusing, but the substance is the same: independently verified against current HEAD (`5b05d67`), `HdlExporter.java` does **not** contain a `REJECTED` map, which is inconsistent with an "byte-identical, nothing to see here" framing for `src/`. Recommendation: correct or drop the byte-identical claim for `src/`; #493 is the authoritative measurement and should be cited instead.

## What checks out

- O3/H2's core mechanism — the VCD header's `$comment` line is deliberately byte-pinned (no `$date`/`$version`) so a manifest line must be conditional on a non-binary signal existing, never unconditional — is verified accurate against `src/jls/sim/BatchSimulator.java:420-435` at HEAD, and P5's "byte-identical for binary circuits, not a hope" framing is a genuinely hard-to-game acceptance criterion.
- O4's reproduction (the `-?0[xX][0-9a-fA-F]+` pre-pass regex in `src/jls/elem/SigSim.java:52` does not match `0t+0-`, `0t101`, or `0q31`) is independently verified: the code at HEAD is unchanged from what the issue quotes, and the claimed disjointness from the hex grammar (`t`/`q` are not hex digits) is correct, making P7's "an existing hex-token stimulus file is unaffected" a consequence of the grammar rather than of test luck, as the issue itself argues.
- O5's distinction between `BitSetUtils.ToString(bs, radix)` (radix-general, reusable for balanced rendering) and `ToStringSigned` (binary two's-complement only, would silently mis-render a balanced value) is verified accurate against `src/jls/BitSetUtils.java:83-118` at HEAD, and correctly identified as the sharpest correctness hazard in the whole task (a "plausible-looking wrong number," §11).
- The Threats to Validity section's handling of the SigSim quadratic-concatenation overlap with #376 (TASK-0009) is handled honestly and non-dogmatically: it names the real risk (adding token branches to code #376 is simultaneously rewriting), states a recommended sequencing without asserting a hard `blocked_by` edge, and gives a concrete reason why ("the branches can be added to whatever #376 leaves behind"). Verified against current `SigSim.java:40-75`: the quadratic `+=` concatenation is still present and unfixed, consistent with the issue's framing.
- The "no coercion, ever" discipline (a base-3 digit `2` down-converted has no image in `{0,1}` and must not be silently folded) is consistent with the same discipline #419 and #453 independently state, and is a sound, well-motivated invariant regardless of which issue ends up owning `vcdValue`'s guard (finding 4).
