# Issue #418: TASK-0046: EDIF, BLIF and a SPICE netlist become documented recipes CI actually runs, and the direct-emitter refusal is written where a reader searching for "EDIF" will find it
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

This is a densely-specified documentation task with a genuinely good testing
idea (parse commands out of a doc, run exactly those, assert set equality
both directions, copying the shipped `ExtensionPointCatalogTest` precedent).
But its evidentiary base is significantly broken in ways that are not merely
stale line numbers: one of its three headline claims is false on inspection
of the cited document, its single richest piece of code evidence (the
`HdlExporter.REJECTED` map) does not exist on `master` and never did, and its
entire planning-corpus citation trail (`docs/plan/**`) is unrecoverable —
confirmed independently by grepping the checkout and corroborated by the
maintainer's own bot-posted correction already sitting on this issue
(comment 2026-08-03T20:34:20Z) and by the tracking issue #493.

## Findings, most severe first

**1. [CRITICAL] The "three costed rejections" premise is false for two of the three formats it claims.**
The Abstract states: *"Three separate costed rejections in `docs/standards-adoption/` say JLS should not write EDIF, BLIF or SPICE directly."* `docs/standards-adoption/11-costed-rejections.md` is real and its own title is *"The costed rejections: SDF (#89), EDIF (#74), JEDEC JESD3-C (#83), IEEE 1149.1 BSDL (#129)"* — SDF, EDIF, JEDEC, BSDL, not BLIF or SPICE. Grepping the whole `docs/standards-adoption/` tree for "blif" or "spice" (case-insensitive) turns up exactly one BLIF hit — a passing mention that Yosys's own ecosystem covers BLIF de facto (line 265) — and zero SPICE hits (the only "spice" match anywhere is "Automotive SPICE", an unrelated process-quality standard, `04-tool-qualification-and-scope.md:403`). There is no costed rejection for BLIF or SPICE anywhere in the tree. The task's own §12 admits this in passing — *"No issue proposes these recipes... none of them was ever converted into a route"* — but the Abstract and §1 still assert three rejections exist to be converted. **Recommendation:** rewrite the premise to what's actually true — one costed rejection (EDIF) and two formats (BLIF, SPICE) that were never rejected because nobody proposed a direct emitter for them, so the "refusal, written where a reader will find it" framing only applies to EDIF; BLIF/SPICE need a different justification (they're routes, not un-rejections).

**2. [CRITICAL] O5's central code citation — the `HdlExporter.REJECTED` map — does not exist on `master` and never did.** The issue quotes a 19-line `private static final Map<Class<?>, String> REJECTED = Map.of(...)` at `src/jls/hdl/HdlExporter.java` L460-478 naming exactly `Memory`, `SubCircuit`, `RegisterFile`, `FieldExtend` with per-type reason strings, and builds P8 ("limitations section names all four `REJECTED` types") directly on it. Independently grepping the current checkout: `grep -n "REJECTED" src/jls/hdl/HdlExporter.java` returns nothing; the file has no `RegisterFile` or `FieldExtend` reference at all; the actual reject mechanism (`buildModel`, ~L171-230) is a generic dynamic `offenders` list built by elimination (`isTopology`/`isSkipped`/`isExported`, else offender), with a uniform `describe(el)` message (`ClassName "name" at (x,y)`) — no per-type reasons. This matches, verbatim, a correction the repo owner already posted on this very issue: *"Anchors in this issue that fall in branch-only ranges: `src/jls/hdl/HdlExporter.java:460-478` — 19 cited lines absent from `master`... Branch-only symbols quoted or named here: `HdlExporter.REJECTED`, `REJECTED = Map.of`. None of these exist on `master`."* That comment further identifies this exact map (and its reason-carrying refusal path) as the subject of a *different*, separate proposed issue, #492. **Recommendation:** do not treat O5 as ground truth. Re-derive the actual reject set on `master` before writing P8's limitations section — today it is an unnamed catch-all, and `RegisterFile`/`FieldExtend` reach it only by accident of not being classified elsewhere, not by declared policy. This task and #492 have an undeclared ordering dependency that the machine block does not record.

**3. [HIGH] The cited planning corpus (`docs/plan/**`) does not exist in this repository at all.** The issue cites `docs/plan/tasks/TASK-0046-document-tool-mediated-netlist-paths.md`, `docs/plan/evidence/BRIEF.md` §13 (for "Decision D8"), and `docs/plan/capstones/CAP-14-ngspice-interoperation-parity.md` as load-bearing sources — the D8 quote is the entire justification for why a costed refusal is still allowed to stand today. `find /home/user/JLS/docs -iname "*plan*"` returns nothing; there is no `docs/plan/` directory anywhere in the checkout. This is confirmed by #493 (posted the same day, by the same author, against the same evidence commit), which lists 195 files under `docs/plan/**` as "**Unrecoverable by re-reading** — these files never existed on `master`" and names #418 explicitly in its "wrong about master" list. A contributor picking up this task cannot check the D8 quote, the CAP-14 SPICE-consumption claim, or the TASK-0046 planning doc against anything — only the paraphrase inside issue #418 itself survives. **Recommendation:** either the D8 decision and the CAP-14 dependency get restated as durable, in-repo text (an ADR-style doc or a comment on #321) before this task is picked up, or the task proceeds accepting that a chunk of its own rationale is unverifiable folklore.

**4. [HIGH] A genuine hard blocker is declared non-blocking in the structured field.** The prose is explicit: *"TASK-0045 (the synthesis-tool netlist writer, owned by FEAT-019) is a genuine prerequisite... and its issue is not yet filed"* — and O1 demonstrates this concretely: `-export exp.json` exits 2 with "output file must end in .v, .vhd or .vhdl", so there is no netlist for any recipe to consume. Independently confirmed: `src/jls/hdl/` has no JSON/Yosys-writing emitter (only `VerilogEmitter`, `VhdlEmitter`), and the sibling feature issue #321 lists TASK-0045 as `planned, not filed`. Yet #418's own machine block declares `blocked_by: []`. The prose defends this via an internal convention (`blocked_by` only tracks filed issues; `part_of_feature` is composition, "task rule 8") — but that convention lives only in the missing `docs/plan/` corpus (finding 3), so a tool or a hurried maintainer reading the structured field alone would see "unblocked" and could start work on a task that is provably a no-op today. The safety net is entirely in prose (§8 step 1: "re-verify O1... if `-export foo.json` now succeeds, unblocked; otherwise..."), not in anything a scheduler enforces. **Recommendation:** either add a synthetic placeholder entry to `blocked_by` or add a bold, unmissable "DO NOT START" banner ahead of the Abstract — a checklist item eleven sections down is easy to skip.

**5. [MEDIUM] Acceptance criteria are testable in the narrow sense but gameable in the honest-documentation sense.** P1-P8, P10 are concrete and mechanically checkable (exit codes, substring assertions, set equality). But "the honest limitation" (§7.1, "the consumer and the honest limitation" per route) and H4's "a reader can tell proven from described" (P9) are qualitative and unenforced by any test — a contributor could satisfy every literal prediction with a minimal document (one trivial fixture circuit, one `synth_xilinx` call, a one-line "limitation: none known" per route) and pass `mvn verify` while missing the actual goal (a genuinely useful, honestly-limited recipe set). The falsification criteria for H4 concede this ("that is a documentation defect... testable by review", §10) — meaning the real gate is human review quality, not CI, but nothing in the Definition of Done requires a second reviewer to specifically assess documentation honesty rather than test-greenness. **Recommendation:** add an explicit DoD line requiring a reviewer (not the author) to independently attempt one recipe manually and confirm the stated limitation matches observed behavior.

**6. [MEDIUM] The golden-netlist fixture is a second, uncontrolled moving target.** §7.3 correctly flags that the Yosys JSON schema is "defined by an implementation... rather than a standard with a change process" and that an upstream release can force fixture regeneration — but the only stated mitigation is "pin it," with no process for detecting when CI's yosys (installed by the *also-unfiled* #386/TASK-0051) has drifted from the pinned fixture's assumptions until the test fails opaquely. Given this task explicitly depends on two other not-yet-landed tasks (TASK-0045 for the writer, #386 for the CI toolchain), the "3 days, documentation not an emitter" pricing in §11 understates integration risk: the recipes are pinned against tool behavior this task's author does not control and cannot fully test until both prerequisites land.

**7. [MEDIUM] The task-numbering apparatus this issue depends on is undocumented anywhere a new contributor can find.** Terms load-bearing to interpretation — "task rule 3/6/8/10," "tier: task," "part_of_feature," decisions "D8"/"D10" — appear nowhere in `README.md` or `ARCHITECTURE.md` (both read in full for this review) and, per finding 3, their home (`docs/plan/`) doesn't exist on `master`. A contributor without access to the dead branch or to issue #493's excavation has no way to know these conventions exist, let alone what they mean.

## What's solid

- The drift-prevention design (marker-keyed fenced blocks, both-direction set-equality between parsed and executed commands) is sound and correctly modeled on a real, verified precedent: `test/jls/ExtensionPointCatalogTest.java` exists and does cross-check a doc against code the way this task proposes.
- The skip-when-absent idiom (`ToolLocator.findOnPath`) is a real, already-shipped pattern (`test/jls/hdl/ToolLocator.java` exists) and reusing it for a new yosys-gated test is low-risk.
- Scope is otherwise well-bounded: no `src/` changes, no emitter, explicit non-goals section, and the O4 two-place suffix dispatch is correctly identified as out of scope for this task (owned by TASK-0045), matching what's actually in `src/jls/JLSStart.java` L381-385 and L1088-1092.

## Verdict rationale

`needs-rework`, not `should-not-proceed`: the test-design core is good and the true blocker (no netlist writer yet) is at least self-flagged with a re-verification step. But the issue cannot be picked up as written — its factual premise about BLIF/SPICE rejections is wrong, its richest piece of code evidence is fiction on `master`, and a chunk of its rationale cites documents that don't exist. These need correcting (not merely re-deriving line numbers) before an implementer starts, or the resulting `docs/tool-mediated-netlists.md` will itself misstate what was actually rejected and why.
