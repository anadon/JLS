## Summary

The issue is unusually rigorous in its own terms — line citations against the checked-out tree are almost all accurate (verified below), and it pre-empts the obvious "golden passes, footprints are empty" gaming risk with a separate P2 assertion. But it has four real problems: (1) it commits a single-maintainer pedagogy project to a large, multi-feature PCB programme that the project's own standards survey never once considers or ranks; (2) its single most load-bearing technical claim (KiCad silently drops any footprint-less component) is sourced to documents that do not exist anywhere in this repository, so it cannot be checked by a reader; (3) it is blocked on three open issues plus one *unfiled* task, making it not actionable now; (4) its TriState-refusal rule (O3/P6) misdiagnoses the codebase — `TriState` already has an honest, working rendering today via `HdlModel.TriStateStatement`, independent of `Direction`, which the issue never engages with.

### 4. O3/P6's TriState-refusal rule misreads the codebase: tri-state is already handled today, without touching `Direction`
O3 argues that because `HdlModel.Direction` has only `INPUT`/`OUTPUT` (`src/jls/hdl/HdlModel.java:28-33`, confirmed), "`TriState` has no honest rendering yet" and mandates that *any* design containing a `TriState` be refused outright by the new emitter, citing TASK-0049 (bidirectional `Direction`) as the unblocker. But `src/jls/hdl/HdlExporter.java:549-554` and `src/jls/hdl/HdlModel.java:317-350` show `TriState` is already exported today via a dedicated `TriStateStatement` construct — rendered by both `VerilogEmitter.java:187,296` and `VhdlEmitter.java:220,345` — entirely independent of `Direction`. `Direction` governs top-level **module port** direction; `TriStateStatement` governs an **internal** tri-state driver onto a shared net, which is the overwhelmingly common use of `TriState` in a drawn circuit (a bus with several enabled drivers). The issue conflates these two mechanisms and, as a result, mandates refusing *every* design with an internal `TriState` element — not just the genuinely unhandled case (a `TriState` wired directly to a bidirectional top-level board pin). This is over-broad: it would make the emitter unusable for the common tri-state-bus teaching circuit that JLS already exports correctly to Verilog/VHDL today.
**Recommendation:** narrow O3/P6 to the actual gap — a `TriState` driving (or driven from) a top-level port that needs bidirectional `Direction` — and reuse `TriStateStatement`'s existing pattern for internal tri-state nets, the same way `HdlExporter` already does. As written, P6 and the DoD checklist item ("A design containing a `TriState` is refused...") would fail the acceptance test on a circuit the project's own exporter already handles.

### 5. Gameable checkbox: the only check on the load-bearing external claim (H1) is an unrecorded manual step
P/DoD requires "**H1 verified manually once against a named KiCad version, recorded in the PR**: footprints placed, nets applied." There is no specified evidentiary bar for that record (no required screenshot, no required before/after diff, no required KiCad log excerpt) — "recorded in the PR" could be satisfied by a one-line "verified, works" comment. Since H1 is the only empirical check on the entire artifact's usefulness (§11: "the KiCad behaviour is read from source, not measured... the single manual verification is the only empirical check"), a superficial check-the-box pass here would let the whole task close green while the emitted file is still wrong against real KiCad in ways an inattentive open/close pass wouldn't catch (e.g. wrong pin numbers within a correctly-non-empty footprint — P4's golden pins *shape*, not correctness against the real pinout).
**Recommendation:** specify the manual verification's evidence requirement (e.g., a screenshot of the imported board with all four NAND gates placed and a net highlighted, or the KiCad Python console's post-import net/footprint count matching predicted values) rather than leaving "recorded in the PR" open to a rubber-stamp.
