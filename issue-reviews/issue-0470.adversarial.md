### 2. Open Question 1 treats field-addressing as undecided, but the codebase already has a stronger, purpose-built, ratcheted mechanism than either recommended option (High)

Section "Open Questions & Decisions Needed" frames field-addressing as genuinely open and **recommends option (a) "by accessible name"**, justified by "the accessibility work (#75, #380) is already putting accessible names on these components." That justification is true but incomplete in a way that matters: `ElementFormDialog.labelled(JLabel, JComponent, String)` (src/jls/edit/ElementFormDialog.java:157-170) does three things in one call — sets the field's **accessible name**, sets the field's **stable Swing component name** (`field.setName(name)`), and wires `setLabelFor`. The component-name half is documented as the *primary* automation-lookup mechanism in `docs/component-naming.md`, whose own text says: *"Names are the lookup contract: tests and tools resolve components with `getName()` matching instead of tooltip text, Swing class, or positional index."* Every labelled dialog field already carries a name of the form `dialog.<slug>.<field>` (e.g. `dialog.adder.bits`), and `jls.ui.ComponentIdentityTest` already enforces the scheme live. Accessible name, by contrast, is derived from the *label text minus trailing colon* — it changes if a label is reworded for clarity or i18n, which is exactly the "brittle under any layout/wording change" property the issue attributes to option (b) (component index), not to (a). The issue's own rejected option (c) — "a test-only registry each dialog populates, which is production code added for tests" — is closer to what's actually needed to notice, except it isn't needed: the registry already exists as `setName`, is *not* test-only, and long predates this task (issue #210). Recommend: change Open Question 1's recommended answer to "by stable component name (`getName()`, the `dialog.<slug>.<field>` scheme of `docs/component-naming.md`)," not accessible name, and drop the "genuinely new input" framing — it isn't new, it shipped with #210 before this task was filed.

### 3. H3's "same 25-entry obligation" arithmetic doesn't match `DialogCoverageRatchetTest.SWEPT`, which has 26 entries (Medium)

H3 states keying the new ratchet on the dialog class "yields the same 25-entry obligation, not a 35-entry one." O2's `constructAndCancel`-driven sweep does have exactly 25 `@Test` methods (verified: `grep -c '@Test' DialogConstructionSmokeTest.java` → 25, matching O7's `Tests run: 25`). But `DialogCoverageRatchetTest.SWEPT` (test/jls/ui/DialogCoverageRatchetTest.java:34-41) lists **26** distinct strings — `Adder, AndGate, Binder, Clock, Constant, Decoder, DelayChange, DelayGate, Display, Element, Extend, InputPin, JumpEnd, JumpStart, Memory, Mux, OutputPin, Register, ShiftRegister, SigGen, Splitter, StateMachine, SubCircuit, Text, TriState, TruthTable` — because one test method (`elementDelayChangeDialog`) discharges two SWEPT entries at once (`Element` and `DelayChange`, since it opens `DelayChangeDialog.open(el)` on a plain `AndGate` element rather than calling `constructAndCancel`). The 25-vs-26 discrepancy is real and reproducible, and it means "key the validation ratchet on the dialog class, get 25 obligations" is not quite what will happen — a naive implementer copying `SWEPT` verbatim gets a 26-entry obligation with one entry (`Element` or `DelayChange`) needing to be satisfied by a case shaped like `elementDelayChangeDialog`, not like `constructAndCancel`'s 24 siblings. This isn't fatal (the mechanism to handle it already exists in the code being copied), but H3's own falsification criterion — "H3 refuted if keying on the dialog class produces an obligation count other than 25" — is worded to fire on a count that will, in fact, not be 25. Recommend: correct H3/§7.10 to state the true count (26, or note the one-test/two-SWEPT-entries wrinkle explicitly) so the falsification check doesn't spuriously trip on day one.

### 4. P6's "executed-count gate" is easy to satisfy vacuously if implemented as a raw count rather than per-suite (Medium)

P6/O7's fix is stated as: *"On a lane where the display is armed, the display execution reports a non-zero executed count... A lane claiming the display suite passed while executing zero tests fails."* As specified, the obligation is `armed ⇒ (n_run − n_skip > 0)` over the *whole display execution* (§7.10). That's satisfiable by a single test in a single class running one assertion while 30+ other display-tagged classes still silently self-skip via `assumeFalse` for some unrelated reason (a JVM property drifting, a new class picking the wrong `@Tag`, a regression in one dialog's construction being masked because the aggregate count is still positive from everything else). The stated acceptance test (P6) as written only proves the aggregate isn't *entirely* zero — it does not prove *this* new suite, or any specific existing suite, actually ran. Given that O7's whole finding is "25 of 25 skipped, build green," a fix that only guards the sum is a weaker property than the sum-of-25 finding it's responding to; a partial regression (e.g. `DialogConstructionSmokeTest` starts self-skipping again while `MenuBarSpecTest` keeps running) would pass the aggregate gate and reproduce exactly O7's bug for one class. Recommend: state the gate per display-tagged test class (or explicitly justify why an aggregate is sufficient), and have the DoD's "prove the executed-count gate fails on an armed-but-zero-executed lane" experiment include a partial-skip scenario, not only the total-skip scenario O7 observed.

### 5. The rerun-audit acceptance criterion (P8) is unusually costly for a residual/task-tier issue and has no automated check (Low-Medium)

P8 requires "surefire reports from three consecutive CI runs show zero reruns for the new cases" as a completion-criteria checkbox, and it is explicitly manual ("this is not optional... Manual verification, platform recorded in the PR: one dialog driven by hand"). For 25+ new validation cases across dialogs run under Xvfb with no window manager (the issue's own stated cause of flakiness, §11 T1/T2), demanding a *zero-rerun* record across three full CI runs before calling the cases "stable" is a real cost — and it's a criterion the PR author self-attests to rather than one CI enforces, so it's exactly as gameable as any other "I promise I checked" checkbox: a rushed PR can paste three green run links without actually confirming the rerun count was zero rather than 1-of-2 successful retries (surefire's summary line doesn't distinguish "passed clean" from "passed on retry" without opening the raw per-attempt output). Recommend: either script the rerun-count check (grep the surefire XML `flakyTests`/rerun attributes) so the DoD item is machine-verifiable, or scope the audit to the newly-added test classes only rather than requiring a human to certify three full-suite runs.

### 6. §7.11's "hard failure on unlocatable field" is a good instinct but has no explicit poisoning defense against a case that matches a substring (Low)

The issue calls this out itself as **T3 — "the assertion that asserts nothing"**: *"A refusal case that cannot find its field, or that matches a substring of any message, passes vacuously."* Good — this is exactly the right thing to worry about, and P3/§7.10 do specify verbatim equality with the element's constant rather than substring containment. This item is not a defect; noting it because the self-identified threat is real and the mitigation (verbatim `assertEquals`, not `contains`) is correctly specified in the interface contract. One gap: nothing in §5/§14 requires a *negative* test proving `driveAndExpectRefusal` actually fails when given a value the element accepts (i.e., that the refusal helper itself can fail) — `GestureAssertTest.EveryAssertionCanFail` (P7) covers the new `GestureAssert` vocabulary but not the private `DialogValidationSmokeTest` helpers `driveAndExpectRefusal`/`driveAndExpectCommit` themselves. Recommend: add one mutation-tested case (seed a wrong expected string, confirm the helper goes red) for the two new private helpers, the same discipline P7 already requires of `GestureAssert`.
