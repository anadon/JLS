## Findings, most severe first

**1. (High) The issue's own evidentiary base is partly unreachable from the branch anyone will actually work on.** The issue pins `evidence_commit: 2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7`. The maintainer's own comment on this issue (posted same day) states that commit "exists only on a branch that will not be merged and will be deleted" and that citations into `docs/plan/**`, `docs/machine-calibration.md`, `docs/parity-contract.md`, `docs/virtual-hardware-parity.md` — "195 files" — "cannot be re-pinned at all" because they do not exist on `master`. I confirmed this directly: `ls docs/plan` on the checked-out `master`-derived tree fails ("No such file or directory"). That matters here specifically because O2's central "correction" — the claim that the real site count is nine, not seven — is framed as a correction *against* `docs/plan/tasks/TASK-0008-net-and-probe-names-off-stable-id.md`, a document no implementer working from `master` can open to check the issue's characterization of it against the original. Likewise, Open Question 1's justification for filing despite an unresolved blocker quotes "D10" from `docs/plan/evidence/BRIEF.md §13` — also absent from `master`. **Recommendation:** either inline the corpus document's actual seven-row table into this issue (so the "7 vs 9" claim is self-contained and checkable) or drop the "correction" framing and just state the nine sites as this issue's own enumeration, verified against `master` directly (which I was able to do independently in under a minute — the nine-site claim itself is fine, it's the "vs. the corpus doc" framing that's unverifiable).

**2. (Medium-High) `blocked_by: []` is misleading; there is a real blocking dependency, just not a tracked one.** The machine block states `blocked_by: []` and the prose underlines "no FILED prerequisite." But §8 Method's first checkbox is "Answer #336's Open Question 1 ... and record the answer here," and the Open Questions section states three separate times that OQ1/OQ2/OQ3 "Blocks execution." A scheduler or agent that reads only the YAML (which is exactly what the machine-block format exists to let automation do — see #336/#353/#358's own "DAG walk, recorded per the tier-model note" sections, which explicitly reason from `blocked_by`/`blocks` fields) will conclude this task is startable today. It is not: step one requires a decision on a *different* issue (#336) that #336 itself marks as "Blocks filing TASK-0008" and has not resolved (I confirmed #336 is still open with that open question unanswered as of the fetch above). Recording a real blocking dependency only in prose, while the structured field says `[]`, is exactly the kind of gap that makes automated dependency graphs (which this repo's issue family relies on heavily) silently wrong. **Recommendation:** either add a synthetic `blocked_by` entry for "#336 OQ1/OQ2 answered" or make the machine block carry a `blocked_by_decision` field distinct from `blocked_by_issue`, and stop asserting "no FILED prerequisite" as if that settles startability.

**3. (Medium) Two of three prerequisites are literally unfiled, and the one filed sibling (#336) they gate against is itself unresolved on the exact question this issue needs answered first.** TASK-0005 and TASK-0007 "do not exist yet" by the issue's own words, and TASK-0007 in particular is flagged as editing the same file (`HdlExporter.java`) with a stated conflict cost ("the naming work roughly again"). There is no mechanism here — only prose — preventing two agents (plausible in this repo's evident AI-fleet workflow) from picking up #373 and a not-yet-numbered TASK-0007 concurrently and colliding. Given `blocked_by: []`, nothing stops an automated picker from doing exactly that.

**4. (Medium) Scope is large for a single PR and mixes independently-shippable units.** The Definition of Done bundles: (a) a frozen naming-derivation convention with an *externally unresolved* digest choice, (b) rewriting 9 call sites plus deleting the `%09d` key, (c) proving `HdlNames.synth`'s collision break is order-independent, (d) regenerating and manually reviewing 54 golden files, (e) validating 5 probe-attach sites with 4 distinct failure behaviors, (f) a new escape-or-reject rule in the VCD writer, (g) two documentation-file edits, and (h) status comments on three other issues. The issue itself calls out (§9, §11) that "reviewing 54 golden diffs ... is the largest single cost of the task and must be budgeted, not skipped" — a tacit admission this is oversized for casual review. Net-name stability (nine call sites + goldens) and probe-name validation (five call sites + VCD guard) are logically independent (different bug, different files, different tests) and could ship as two PRs against two sub-tasks without losing anything except a slightly awkward "the rule is one predicate" narrative in H3.

**5. (Medium) P7/P8's negative control is not actually enforced by anything mechanical.** §9 states the analysis for P7/P8 (that all 54 regenerated golden diffs are "identifier substitutions, never structure") "is a reviewer reading 54 golden diffs" — an unautomated step. The only cited mechanical backstop, `VerilogStructure.assertSane` / `VhdlStructure` (confirmed to exist at `test/jls/hdl/VerilogStructure.java`, `VhdlStructure.java`), is asserted to already run on every export, but the issue never demonstrates that those structural checks would actually *catch* a name-shaped bug that also perturbs structure (e.g., a collision-break tie going the wrong way and silently renaming the wrong net to a value that happens to still be a legal, unique identifier). As written, "every hunk is an identifier substitution" can be signed off by an implementer skimming 54 diffs, and CI will stay green regardless of whether that's true. **Recommendation:** name a specific automatable check (e.g., a script that parses old and new goldens, extracts the non-net-name tokens, and diffs them) rather than relying on "a reviewer reading."

**6. (Medium) The privacy/reproducibility risk the issue itself flags is not actually gated by this issue's completion criteria.** §8 and §11 both warn that choosing the raw stable id (as opposed to a digest) as the net-name suffix leaks a per-install `replica` string (from `jls.replicaId`/`JLS_REPLICA_ID`, confirmed live in `src/jls/elem/ElementId.java`) into every exported netlist a student hands in. But the digest-vs-raw-id decision is explicitly deferred to #336 OQ1, and #373's own Definition of Done only requires "record the answer here" — it does not require the answer be the digest, and none of P1-P8 or the falsification criteria in §10 would fail if the raw, privacy-leaking id were chosen instead. So this issue can be marked fully done, all checkboxes ticked, while shipping the exact hazard its own risk section names. **Recommendation:** if the privacy concern is real (it looks real — a replica id is effectively a per-install/per-user token), make "digest, not raw id" a hard completion-criterion line item in *this* issue, not just a recommended default deferred elsewhere.

**7. (Low) Internal cross-issue arithmetic is consistent but adds a layer that's easy to get wrong by hand.** #373 claims `blocks: [353, 358]`; #353's own machine block shows `T8 --> F5` (TASK-0008 blocks FEAT-005/#353) and #358 shows `blocked_by: [315, 336]` with #336 (not #373 directly) as the mediating edge. This is internally consistent once traced, but it means #373's completion is a prerequisite for #358 only transitively through #336 — the issue's flowchart draws `T --> F358` directly, which is a simplification that could mislead a scheduler into thinking #373 alone unblocks #358 (it does not; #315 and the rest of #336's scope still gate #358). Worth a one-line disambiguation in the mermaid caption.

## What's solid (no further action needed)

- The core defect (net/register/mux/etc. names keyed off a save-order integer rather than permanent identity) is real, reproducible from the cited line numbers, and the "54 of 79 goldens affected" blast-radius figure is plausible given the `net_` grep count matches (54) against the shipped corpus.
- The probe-validation gap (O5/O6) and the raw `$var` write-through (O7) are both real and independently confirmed; reusing `Util.isValidName` rather than inventing a second rule is a reasonable default, and H3's falsification criterion (check it against the VCD identifier grammar before assuming) is exactly the right level of caution.
- The failure-mode table (§7.11) correctly distinguishes GUI re-prompt vs. collaborative-op rejection vs. load-time diagnostic-not-refusal — this differentiated handling matches the existing code patterns at each site (confirmed: `AttachProbe.java` already throws `OpRejected` for an adjacent case; `Wire.java`'s GUI path already re-prompts on empty).
- Backward compatibility framing (§7.12: old files still load, save bytes unchanged, only exported-HDL names move) is coherent and matches how the format doc treats net names as derived-at-emission-time, never stored.
