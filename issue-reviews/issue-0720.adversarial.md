# Issue #720: TASK-C539-1: a pure-Java APNG and GIF encoder with deterministic frame timing and a declared size budget
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what's being asked

A pure-Java APNG writer plus a GIF alternative, decoupled from circuits (synthetic frame sequence + timing table in, encoded bytes out), with a determinism test and a "declared size budget." It is `TASK-C539-1`, one of two tasks (`TASK-C539-2` = #722, the capture half) splitting `FEAT-C24-4` (#539), itself a planned feature of capstone `CAP-24` (#505).

## Findings, most severe first

**1. The issue instructs the reader not to start it, and that precondition is still unresolved as of this review — yet nothing marks the issue as blocked.** The body's second paragraph: *"Recorded before work starts: #508 recommends cutting FEAT-C24-4 entirely. Do not fund ahead of an explicit REPLAN on #505 adopting or rejecting that recommendation."* I checked both sides of that gate directly: #505's only comment (2026-08-04) records the cut as "pending" ("the adjudicating REPLAN on this issue has not happened yet"), and #508's most recent comment (2026-08-08, the same day as this review) still carries CAP-24 in its re-based queue as "2–3 mw slice retires the hard risk; **cut PF-4 animation**; ≈9–14 mw realistic" — i.e. the recommendation to cut this exact task's parent feature stands, unadjudicated, four days after #720 was filed. Despite that, #720 carries no `blocked` label, `state` is `open`, and its own machine block declares `ordering_after: []` — machine-readable "nothing gates this." A contributor or automated agent triaging by label/machine-block rather than reading the prose would pick this up today in direct contradiction of the issue's own instruction. This is exactly the "name the criterion, not the issue" / stale-machine-block failure mode #508's own round-2 ordering-coherence comment catalogs elsewhere in this tracker generation — it recurs here, unfixed, in the very issue that raised it. **Recommendation:** either close/park #720 with a `blocked`/`on-hold` label until #505 gets its REPLAN comment, or add a real `blocked_by` edge to #505 so tooling — not just careful humans — respects the stated precondition.

**2. AC-2's determinism test is strictly weaker than the risk this task exists to retire, and is gameable as written.** AC-2 says: *"Encoding a fixed frame sequence twice produces byte-identical output."* "Twice" on what platform? The capstone this task serves states the actual hard requirement elsewhere: CAP-24's KC-24-1 kill criterion and AC-2 require byte-identical output **across CI platforms** (Linux/macOS/Windows), precisely because platform-dependent encoding is the named failure mode for this whole figure-export effort (see #536's PF-1 risk enumeration in #505 §3.1: "OS font fallback varies per platform"). A PNG/GIF encoder's compressed output is not exempt from that risk merely because it's "pure Java" — `java.util.zip.Deflater`, the obvious implementation route, its default strategy/level, and any timestamp or PRNG-seeded ordering in chunk emission are all places non-determinism or platform variance can enter. An implementation could trivially satisfy AC-2 by running the same JVM on the same OS twice and never touch the actual risk (byte identity across platforms) this task was carved out of the capstone specifically to de-risk in isolation ("isolated so its determinism can be asserted without a canvas in the picture"). **Recommendation:** state AC-2 as cross-platform (or explicitly scope it to single-platform and say so, deferring the cross-platform claim to a named later criterion), and enumerate the concrete determinism hazards (Deflater settings, chunk/frame ordering, no wall-clock or hash-map-iteration-order leakage into byte output) the implementer must rule out.

**3. AC-1's "no native library and no new runtime dependency" test is underspecified and has an obvious gap.** As written, a test that inspects the shipped jar's declared Maven dependencies (or its manifest/classpath) would not catch an implementation that shells out via `ProcessBuilder`/`Runtime.exec` to a system encoder (`pngcrush`, `gifsicle`, `ffmpeg`) or loads a `.so`/`.dll` via `System.load`. That adds zero Maven dependencies and zero new jar entries, so a naive "dependency diff" test passes, while clearly violating the stated hard constraint ("Pure Java is a hard constraint — the single-jar deployment model means no native encoder"). The project already has ArchUnit as a test dependency (`pom.xml:109-114`), which is the right tool to assert "no call sites to `ProcessBuilder`/`Runtime.exec`/`System.load`/`System.loadLibrary` in this package" — but the issue doesn't ask for that, only for a dependency-list assertion. **Recommendation:** name the mechanism explicitly (ArchUnit rule banning process-exec and native-load APIs in the encoder package) rather than leaving "asserts no native library... enters the shipped jar" to be satisfied however the implementer likes.

**4. AC-3's "declared size budget" declares nothing.** *"A declared size budget is enforced... stays under the stated byte budget."* No number appears anywhere in this issue, in the parent feature #539, or in CAP-24's AC-5 (#505), which uses the identical phrase "stays under a declared size budget" without a value either. The budget is asserted to already exist ("declared", "stated") but has not actually been declared anywhere in the visible corpus, so the implementer is left to invent the number that the acceptance criterion claims to be checking them against — which inverts the purpose of a declared budget (a constraint set by someone with the pedagogical/distribution context, not by whoever happens to write the test). **Recommendation:** either put a concrete number (with rationale — e.g. "under 500 KB for an 8-cycle capture at the hazard-demo's default region size, scaling to N KB/frame") in this issue or in #539, or explicitly flag it as an open question this task cannot close until upstream supplies it.

**5. The `part_of_feature: 539` relationship is prose/YAML-only, not a native GitHub sub-issue link.** I called `issue_read get_parent` on #720; it returns `parent: null`, and the `get` call shows `has_parent: false`. The task claims membership in FEAT-C24-4 (#539) only inside a fenced YAML block in the body. Any tool or reviewer that walks GitHub's native issue-hierarchy API (which #508's own comments repeatedly recommend adopting — "native sub-issues over hand-mirrored YAML/comments") will not see #720 under #539, #539 under #505, or #505 under CAP-24's tracking. This is a minor but concrete instance of a governance defect this same tracker generation has already flagged against itself.

## What's solid (no rework needed)

- **Cost arithmetic actually closes here**, unusually for this corpus: #720 (1–1.5 mw) + its sibling #722/TASK-C539-2 (1–1.5 mw) sum to 2–3 mw, matching FEAT-C24-4's own declared band exactly. #508 found 3 of 4 sampled capstones had bands *below* their own row sums; this split doesn't repeat that defect.
- **The encoder/capture split is a genuine, defensible seam.** Making the writers take "an ordered frame sequence and a timing table" and know nothing about circuits (AC-4) mirrors the project's existing headless-core discipline (`Simulator`/`BatchSimulator` import no AWT/Swing, enforced by `HeadlessCoreRatchetTest`, ARCHITECTURE.md "Threading model"). It is testable with synthetic fixtures without any editor/canvas machinery, which is exactly the isolation the issue claims.
- **The pure-Java/no-MP4 constraint is correctly derived and consistent with its cited source** (CAP-24 Open Question 4's recorded default, quoted accurately) and with the project's actual deployment model (single self-contained jar per README.md "Installing JLS").
- **APNG is a real implementation gap, correctly identified.** The repo's only existing raster export path is screen-styled PNG/JPEG/SVG (`src/jls/edit/CircuitRenderer.java`, uses `ImageIO`), and stock `javax.imageio`'s PNG plugin does not emit APNG's `acTL`/`fcTL`/`fdAT` chunks — so this genuinely needs hand-written chunk encoding, not a reachable library call, which is consistent with "pure Java... in pure Java" being treated as work rather than a formality.

## Verdict rationale

Not `should-not-proceed`: the task is a coherent, correctly-scoped slice of real missing capability, and its cost/split discipline is better than average for this corpus. But it fails "sound" because (a) it is currently workable in direct contradiction of its own stated precondition with no machine-enforced block, and (b) three of its four acceptance criteria (AC-1, AC-2, AC-3) have concrete, exploitable gaps that would let an implementation "pass" while missing the actual point the task exists to serve (cross-platform byte-identity, genuine pure-Java-ness, an actual budget number). Tighten those four items before funding.
