# Issue #598: FEAT-C38-2: every refusal on the way to the board names the fix — unassigned pins, wrong directions, un-exportable elements and an absent toolchain each get a specific diagnostic before the cable is touched
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Findings

### 1. (High) The "wrong pin direction" refusal class has no data model to detect it against
AC-1/AC-2 name four refusal classes and claim "the existing all-or-nothing disciplines are the model and are reused rather than re-derived." That is true for three of the four, but not for direction. `Board` (`src/jls/hdl/board/Board.java:26-27`) is `record Board(String name, String fpga, Format format, Map<String, String> pins)` — a pin is just a name-to-physical-location string pair. `Boards.ICESTICK` (`src/jls/hdl/board/Boards.java:34-78`) transcribes 34 pins (`CLK`, `UART_RX`, `UART_TX`, `LED1..5`, …) with zero direction annotation, even though several of them are obviously fixed-direction on real hardware (an HDL output bound to `UART_RX` or `CLK` would contend with the FTDI chip or the oscillator — a real hazard, not a style nit). `PcfEmitter` never reads or validates direction against the board; it only checks that a pin name exists in `board.pins()` (`PcfEmitter.java:88-94`). A repo-wide `grep -i direction` under `src/jls/hdl/board` returns nothing. The only sketch of a direction-carrying pin type (`Board.Pin`, `BoundPin(String key, HdlModel.Direction direction, String pinName, Board.Pin pin)`) lives in `docs/standards-adoption/06-fpga-constraint-formats.md:87-90` — an unrelated, unimplemented research/design document scoped to issue #82 (adding XDC/QSF/LPF formats), not cited anywhere in #598. **Recommendation:** either fold the `Board`/`Boards` schema migration (per-pin direction, migrating the one existing board table) into this issue's scope explicitly, or split "wrong direction" into a prerequisite task that lands the data model first — as written, AC-1/AC-2's "wrong direction" clause cannot be implemented without a change to code #598 never mentions touching.

### 2. (High) Boundary note routes bugs to a closed issue
"**#59 owns what is and is not exportable** — an element wrongly judged un-exportable is filed there, not fixed here." Issue #59 (the HDL-interoperability capstone) is **closed**, `state_reason: not_planned`, closed 2026-08-03 — one day before #598 was filed (2026-08-04). The live mechanism for "why is this element rejected" is issue #492 (open: adds a `REJECTED` class→reason map to `HdlExporter`, `src/jls/hdl/HdlExporter.java`), which #598's own child task #640 correctly cites ("the reason lives in the exporter's rejection map (#492)") but #598 itself never mentions. Anyone triaging a misclassified-element report against #598's stated boundary will file it on a closed, not-planned issue. **Recommendation:** replace the #59 reference with #492 (and note #492's own open questions — e.g. whether `Memory`/`RegisterFile` refusal reasons are maintainer-ratified — since #598's diagnostic text is only as good as that reason string).

### 3. (Medium) The issue has already been superseded by three more-precise child tasks that aren't linked to it
`TASK-C598-1` (#638), `TASK-C598-2` (#640), `TASK-C598-3` (#643) were filed the same day as #598 (2026-08-04, ~9 hours later), each declaring `part_of_feature: 598` in its YAML frontmatter, and together their acceptance criteria cover #598's AC-1 through AC-5 almost clause-for-clause — with corrections (e.g. #640 cites live #492 where #598 cites dead #59; #638 states the direction check more precisely: "an output port bound to an input-only pin or the reverse"). Yet none of the three is wired up via GitHub's sub-issue relation: `issue_read get_parent` on #638 returns `{"parent": null}`, and #598's own `get` response reports `has_children: false`. #598's YAML frontmatter also carries no `requires_tasks`/`planned_tasks` field at all — sibling feature #264 (same tier) lists both and closes them off in a Definition-of-Done checklist; #598 has no such roster or checklist section. **Recommendation:** either establish the sub-issue links and add a `requires_tasks: [638, 640, 643]` roster to #598 (turning it into a real tracking parent), or close #598 as absorbed into its three children and point future work at them — as filed, #598 is duplicate, drifting paperwork: work against it risks reproducing the less-accurate version of its own spec.

### 4. (Medium) A cited dependency (#288) is not scheduled
The boundary notes lean on "**#288 supplies the export-rejection dialog pattern** (its P4: exporter error list in a dialog, nothing written) for one of the four classes" as something to reuse. But #288 is itself open and unimplemented — its own body states "No HDL export menu item exists" (Observation 2) and its Predictions are all "post-fix" future states. #598's `ordering_after` list is `[264, "FEAT-C38-1 (this capstone's PF-1 GUI board flow)"]` — #288 is omitted even though the GUI half explicitly depends on its pattern. If #598's GUI-facing work (AC-4, and child #643) is picked up before #288 lands, there is no dialog pattern yet to reuse, undercutting the "reused rather than re-derived" framing for that class. **Recommendation:** add #288 to `ordering_after`, or state explicitly that AC-4 is headless-only until #288 lands (the issue's closing sentence gestures at this — "the diagnostics themselves are testable headlessly and can land ahead of it" — but AC-4 itself, "surfaces these diagnostics in a dialog," cannot be verified until #288 exists).

### 5. (Medium) "Nothing is written to disk on any refusal" is underspecified across the pipeline's stages
AC-3 promises no disk writes on any refusal and "before any stage runs." That is true today for the *preflight* case in `scripts/icestick-handoff.sh:100-134` (checked before `yosys` runs at all) and for `PcfEmitter`/`PinBindings` (both return text/throw rather than writing). But the four-class layer this issue adds sits across two runtimes (Java emitters + the bash handoff script) glued together by a not-yet-built GUI flow (#643/#597). Nothing in #598 names what happens if a refusal-adjacent *mid-pipeline* failure occurs after a stage has already run and left an artifact — e.g. `yosys` succeeds and writes `design.json`, then `nextpnr-ice40` fails for an unrelated reason. That's arguably out of AC-3's stated scope ("no external tool" is a preflight-time check), but the issue's language ("never a partial artifact left on disk") reads broader than what the current script actually guarantees post-preflight. **Recommendation:** scope AC-3's "nothing on disk" claim explicitly to preflight-time refusals, or extend it (and add a cleanup/rollback requirement) to cover mid-pipeline tool failures too — as worded it invites a test that passes on preflight-only refusals while leaving the broader claim in the issue's prose unverified.

### 6. (Low) Testability precedent exists and is sound
AC-1's requirement to assert on "specific diagnostic text" is not novel or ungrounded — `test/jls/hdl/board/UnbindablePortsTest.java:49-57` already does exactly this via `message.contains(...)` assertions against `PcfEmitter`'s output, and `PcfEmitter`/`PinBindings`'s aggregation contracts (`PcfEmitter.java:66-119`, `PinBindings.java:52-86`) are real, tested code, not aspirational. AC-2's aggregation requirement for the "unassigned pin" class is essentially already satisfied by existing code and needs no new mechanism, only a direct test. Low risk, no action needed beyond what #638 already plans.

### 7. (Low) Band estimate roughly holds together, but only by omission
`band_mw: "2-3"` for #598 as a whole is close to the sum of its three (undeclared) children — #638 (0.5-1), #640 (1-1.5), #643 (0.5-1) ≈ 2-3.5 — so the top-line estimate isn't obviously wrong. But #638's 0.5-1 mw figure for "unassigned port and wrong-direction binding" implicitly prices in the `Board`/`Boards` schema change from Finding 1 as if it were free; if that schema work turns out to need its own design decision (record shape, migration of the one existing board table, and a decision about pins with no fixed direction at all — most of an FPGA's GPIO), the 0.5-1 mw figure for #638 is optimistic and #598's roll-up estimate inherits that risk silently.

## Solid, no further action
- Reuse of `PcfEmitter`/`PinBindings`'s existing all-or-nothing aggregation (Finding 6) is real and load-bearing, not aspirational.
- The "missing external tool" preflight (AC-3's toolchain half) is already fully implemented and tested in `scripts/icestick-handoff.sh:100-134` — extending it to a shared diagnostic vocabulary is a modest, well-scoped ask.
- `serves_capstones: [522]` accurately reflects #522's PF-2 wording ("unassigned pin, wrong direction, unsupported element, toolchain absent") — #598 is not inventing scope beyond its parent capstone, it is inheriting the capstone's own gap (including the same unaddressed "wrong direction" data-model hole, which is worth flagging back to #522 as well).
