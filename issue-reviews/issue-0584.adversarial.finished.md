# Issue #584: FEAT-C35-1: one plain-text source tree builds both the in-jar help and a static site — today's content migrates mechanically and the offline jar stays complete
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: sound-with-concerns

## Findings, most severe first

### 1. AC-1's "no file in either output is hand-edited" has no verification mechanism, and the build-lifecycle change it implies is unstated
The AC reads: "one `mvn`-reachable goal produces both targets from one source tree, and no file in either output is hand-edited." That is a claim about *process* (how a file came to exist), not a *property* of the shipped tree, and none of AC-1–AC-5 name a check that could catch a hand-edit after the fact. Concretely: `resources/help/**` is today a plain Maven `<resource>` directory (`pom.xml:147-153`) copied verbatim into `target/classes` during the default `process-resources` phase, which is what makes it visible to `HelpTopicsTest` (`Help.class.getResource("/help/Map.jhm")`, `test/jls/HelpTopicsTest.java:61-62`) at `mvn test` time. For the new pipeline to satisfy AC-2 ("passes today's `HelpTopicsTest` unchanged") the generator must run *before* that phase and its output must land in the same classpath location — but the issue never says whether `resources/help/**` stops being committed (pure build output, regenerated every time, nothing to hand-edit) or stays committed as checked-in generated output (in which case a hand-edit is a silent, undetected `git diff` away, since nothing regenerates-and-compares it in CI). Pick one and say so; if the latter, AC-1 needs its own enforcement clause (regenerate in CI, diff against the committed tree, fail on mismatch).

### 2. AC-5's "byte-auditable" diff report has no defined artifact, location, or reviewer gate — gameable as written
"a diff report shows what the generator emits versus what ships today, and every intentional difference is named" sets no format (unified diff? HTML-normalized diff? per-file list?), no location (`docs/`? a build log? a PR comment?), and no acceptance threshold for what counts as adequately "named." An implementer can satisfy this literally with a one-line note ("front matter added, whitespace reflowed") while masking a real content loss (e.g., a paragraph silently dropped by a lossy HTML→Markdown→HTML round-trip) inside "reflowed." Compare to AC-2, which is airtight because it points at a specific, already-existing, already-adversarial test (`HelpTopicsTest`, esp. `everyInlineLinkAndImageResolves` and `everyHelpFileIsReachableFromTheTopicMap`, `test/jls/HelpTopicsTest.java:296-349`). AC-5 needs the same treatment: name the tool, the output path, and who/what gates on it before merge.

### 3. AC-4's "enforced by the build" names no mechanism, and a weak implementation can pass while `JEditorPane` rendering still regresses
The viewer that actually renders the in-jar tree is a Swing `JEditorPane` doing HTML 3.2 (`ARCHITECTURE.md:28-30`, `:254-255`). `JEditorPane`'s HTML/CSS support has well-known gaps well below "valid HTML 3.2" (partial CSS, quirky table/list rendering, no modern layout). A tag-whitelist linter — the obvious cheap way to satisfy "enforced by the build" — proves the markup avoids banned elements, not that it *renders correctly* in the actual viewer. That leaves a gap against the parent issue's own bar ("the offline lab machine renders the same content tree it renders today, or better") that AC-4 as worded cannot catch. Recommend AC-4 require an executable check against the real viewer (e.g., extend `HelpTopicsTest` or a sibling test to actually load each generated page through `Help`'s rendering path, not just grep the markup), or explicitly scope AC-4 down to "documented lint rules only, rendering regression is out of scope for this slice."

### 4. Reproducibility is a named architectural invariant the issue never touches
`README.md` states the jar and `bom.json` are "bit-for-bit reproducible from the tagged source," backed by `docs/reproducibility.md` and a CI rebuild-and-recheck step. A Markdown/AsciiDoc→HTML generator is a new build step capable of breaking that guarantee in ordinary ways (embedded generation timestamps, non-deterministic map/set iteration order in the tool's output, absolute paths leaking into generated `<meta>` tags, etc.), and neither `docs/reproducibility.md` nor the CI rebuild check is mentioned as in scope here. Given the repo already treats reproducibility as load-bearing enough to document and CI-check separately, this omission is a real gap, not a nitpick — recommend an explicit AC or at least a sentence committing the new step to determinism, and a note that the reproducibility CI job covers it.

### 5. Toolchain selection carries unpriced license/dependency risk for a GPLv3 project with zero current docs-generation tooling
`pom.xml` currently has no Markdown/AsciiDoc processing dependency or plugin (`grep` over `pom.xml` plugins turns up compiler/jar/shade/surefire/jacoco/javadoc/cyclonedx/enforcer/spotbugs/spotless only). Whatever library renders the chosen source format to HTML is a new transitive dependency that must clear the same bar the project applies elsewhere (e.g. FlatLaf's Apache-2.0-and-zero-transitive-deps evaluation is written up in `docs/flatlaf-evaluation-2026-07.md` per `ARCHITECTURE.md:274-276`). The issue asks only for "the decision recorded in `docs/`" for source-format choice, not a license/dependency evaluation of the *tool* that implements it — worth folding in given the project's established practice of writing these evaluations up before adopting a dependency.

### 6. Band estimate (2-3 mw) looks tight against the actual surface, increasing schedule/quality-tradeoff risk
Within 2-3 maintainer-weeks this slice must: pick and integrate a new markup toolchain, mechanically migrate 95 existing help files (`find resources/help -type f` = 95, spanning nested dirs: `elements/{components,gates,memory,stmach,timing,truth,wiring,other,import}`, `editor/{editing,subcircuits}`, `menus/{file,global,sim}`, `simulator/{interactive,batch}`, `execution`), wire a new Maven lifecycle phase, write a viewer-safe-subset linter, produce a byte-audit diff mechanism, and pass `HelpTopicsTest` byte-for-byte-equivalent-in-behavior. Each of findings #1-#3 above, if taken seriously, adds unscoped work (CI diff-and-fail wiring, a real rendering-regression test, a defined diff-report format). None of that is unreasonable to ask for, but it is more than "2-3 mw" as currently scoped once the underspecified ACs are tightened — flag for re-estimation once ACs are firmed up, not necessarily for this reviewer to price.

### 7. AC-3's "no generated in-jar page depends on a network fetch to render its content" is narrower than the offline-completeness intent
Restricting the no-network guarantee to rendering *content* leaves room for a compliant-on-paper implementation that pulls a remote stylesheet or web font for *presentation* only, which still breaks on an offline lab machine (a blocked/slow request during `JEditorPane` load, or a visibly unstyled page). Recommend widening the wording to cover any external network resource — content, image, style, script, or font — consumed at render time, matching the stronger language already used in `ARCHITECTURE.md:261-263` ("plain HTML 3.2 with relative links and no viewer-specific markup").

## What holds up

- **AC-2 is precisely and adversarially specified.** It points at a real, already-adversarial test suite (`HelpTopicsTest`, confirmed at `test/jls/HelpTopicsTest.java`) that already checks case-sensitive link resolution, orphan-page reachability, and palette-topic coverage — this is the strongest AC in the issue and leaves little room to game.
- **The scope boundary against #585 (hosting/URLs) is real and was already checked by the maintainer's own bounce-pass comment** ("this issue closes with a site directory that has never been served; #585 cannot start without that directory") — no merge/overlap defect found here.
- **The "mechanical migration, not a rewrite" instruction is the right call** given AC-2's byte-level test dependency — a hand rewrite of 95 files would make regressions far more likely and harder to attribute.
- **KC-35-1's escape hatch (upgrade the viewer rather than degrade the source) is properly cross-referenced** from the parent capstone (#519) and correctly deferred rather than re-litigated in this slice.

## Verdict rationale

The core shape (one source, mechanical migration, existing link-checker as the regression floor) is sound and the boundary against sibling issues (#585, #586, #587) is clean. What keeps this from a plain "sound" is that three of five acceptance criteria (AC-1's hand-edit clause, AC-4, AC-5) describe outcomes without describing how they're checked, which is exactly the kind of gap that lets a technically-compliant PR land while the real goal (drift-proof, byte-audited, offline-safe help content) quietly doesn't hold. None of these are fatal — they're all fixable by naming a mechanism — but they should be tightened before implementation starts, not discovered during review of the resulting PR.
