# Issue #357: FEAT-017: one subcircuit definition, N instances that reference it with bound parameters — editing the definition changes every instance instead of one copy
- Lens: adversarial

- Reviewer: Claude Sonnet 5

## Summary of what's being proposed

Replace `SubCircuit`'s per-instance deep-copy `Circuit` (`src/jls/elem/SubCircuit.java:26`) with a shared definition table on `Circuit` plus per-instance parameter bindings, and add a headless elaborator (`jls.elab`) that resolves bindings into a concrete design and reports every unresolvable binding by instance path and parameter name. All code evidence in the issue was independently re-verified against HEAD (`3b6d6ec`): `getSubCircuit()` at `SubCircuit.java:102-106`, `save()` inlining the nested circuit at `:282-289`, `copy()` deep-copying at `:332-338`, and the 25-call-site count with its exact per-file distribution (`Circuit.java` 2, `JLSStart.java` 3, `CircuitRenderer.java` 1, `InteractiveSimulator.java` 1, `SimpleEditor.java` 3, `SubCircuitDialog.java` 1, `SubCircuit.java` 12, `BatchSimulator.java` 2) all match exactly. The technical grounding is accurate, not fabricated — noted here once and not relitigated below.

## Findings, most severe first

**1. The issue's own Definition-of-Done is already false, and the body wasn't updated to match.** The Decomposition table states "planned — TASK-0041 (2 wk) ... Not filed" and "planned — TASK-0042 (2 wk) ... Not filed," and the `planned_tasks` YAML block lists them as free-text strings, not issue links. But the issue's own comment thread (2026-08-04) records both as filed: TASK-0041 = #447, TASK-0042 = #473 — and #473 in turn declares `part_of_feature: 357` and `blocked_by: [447, 472]`. The DoD checklist item "`planned_tasks` empty (each resolved to a filed issue or descoped)" is therefore unmet in the primary document a new contributor would read first. The issue's own re-planning protocol requires "Roster and `planned_tasks` updated in the same edit as the REPLAN comment" when a child is filed — that edit never happened here. A contributor who reads only the body (not all three comments) will believe the two tasks are still unfiled and either re-derive their scope from scratch or miss that #447/#473 already carry binding, more-detailed contracts. **Recommendation:** edit the issue body's machine block and table to link #447/#473 before anyone picks this up.

**2. The cost band admits it cannot be trusted, and the issue proceeds anyway.** Named task rows sum to 4 wk (TASK-0041 2wk + TASK-0042 2wk) against a stated band of 25–36 mw — a 6.25×–9× gap the issue itself calls "the largest such gap in the plan." The gap is entirely the "residual — no task id" row: migrating the 25 measured `getSubCircuit()` call sites (13 outside `SubCircuit.java`, across the batch simulator, interactive simulator, renderer, and CLI entry point) and re-greening the golden corpus behind them. The issue explicitly rejects splitting this residual by file ("not atomic — a file that loads as a definition table and copies as a deep copy is a corrupt intermediate state"), so it stays one large, unfiled, unsized, unowned unit. Open Question 4 says plainly: "Does not block filing children; it does block trusting the schedule." That is an admission that the schedule is not currently trustworthy, filed as an open question rather than resolved before work starts. For a feature whose critical path is stated as having "essentially no internal parallelism" until this exact residual, shipping two child tasks against an untrustworthy schedule is a real execution risk, not a paperwork nit.

**3. TASK-0041 (#447) appears to have been filed before its own stated filing gate closed.** Open Question 1 ("Does a pre-split file auto-share structurally identical copies on load?") is explicitly marked "**Blocks filing TASK-0041**" in this issue's body, and is still listed under "Open Questions & Decisions Needed" with only a *recommended* default, not a ratified answer. Yet comment 2 (2026-08-04) states TASK-0041 is already filed as #447. Either the decision was ratified somewhere not reflected on #357 (a recording gap that #357's own DoD explicitly forbids — "Open Question 1 ratified by a maintainer and its answer asserted by the test in §5.4, not merely implemented" is still an unchecked box), or #447 was filed against an unmet gate. This should be resolved — confirm where/whether Open Question 1 was ratified — before treating #447 as ready to implement, since criterion 4's whole test design depends on the answer.

**4. Byte-identity is a joint constraint across two independently filed, independently implemented tasks, with no shared coordinating test named in #357 itself.** TASK-0041's evidence bar is golden byte-identity of the representation change; TASK-0042's H2 hypothesis is that elaborating a parameter-free fixture reproduces its own canonical save byte-for-byte, and TASK-0042's own falsification criteria flag the likely failure mode themselves: "the unordered iteration — most likely a `HashSet` or `HashMap` reaching stage 4's fold order." That is a real, specific engineering risk (nondeterministic Java collection iteration order silently breaking a byte-identity guarantee two separately-scheduled implementers must independently uphold), and it is well-anticipated in #473's text — but #357, the parent issue that owns the joint claim (§5 criterion 3: "Simulation golden byte-identity across the full migration ... not at each child's own green run"), names no shared fixture or canonical-order contract the two children must agree on ahead of time beyond "TASK-0041 provides ... TASK-0042 consumes." If the two land out of sync on iteration order, this surfaces only at integration, late.

**5. The dependency tower is three deep and none of it has landed.** `blocked_by: [318, 319, 340]` is internally consistent (verified: #340's `blocks` includes 357, #319's `blocks` includes 357), so this is not a contradiction — but all three are themselves open `tier:feature` issues with their own multi-week bands, their own unresolved Open Questions (#319 alone gates four separate decisions before its own children can be filed; #340 has an un-priced-as-of-filing new scope row), and #319 is additionally gated behind #334 → #315. #357's two child tasks (#447, #473) are consequently blocked several hops deep on infrastructure that doesn't exist yet, which makes "two tasks already filed" read as more actionable than it is — nothing here is unblocked today.

**6. Acceptance criteria are largely solid and explicitly anti-gaming.** Worth stating plainly rather than only listing complaints: §5 criterion 4 ("A test that asserts *whichever happened* is not evidence; the test must assert the decision") and §5 criterion 5 (diagnostic totality — a code with no fixture, or no negative fixture, is incomplete) are both concrete, hard to satisfy by accident, and specifically designed to block the two most common ways a feature like this gets marked done while quietly not doing what it claims. No changes recommended here.

**7. The "not a duplicate of #447" and "not owned by #340" boundary rulings are genuine, not hand-waved.** Comment 1 and comment 2 give specific, checkable reasons (subject, demonstrability, cost-visibility) for why import-to-subcircuit lives on #340 and not here, and why #447/#473 don't subsume #357. Both hold up against the fetched #340 body. No finding here — noted so it isn't mistaken for an oversight.

## Verdict rationale

The technical premise is real and accurately evidenced, the acceptance criteria are unusually resistant to being gamed, and the scope boundary against neighboring issues is argued rather than asserted. But the issue's own bookkeeping is already stale (finding 1), its own cost estimate is self-described as untrustworthy while children are filed against it anyway (finding 2), and there is at least one apparent filing-gate violation worth confirming (finding 3) before treating #447/#473 as ready. None of these are fatal to the design, but all three should be closed before implementation proceeds in earnest.
