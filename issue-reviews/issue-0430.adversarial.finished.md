# Issue #430: TASK-0088: a net that drives more load than its weakest driver can carry is reported with both numbers, a floating input is caught statically, and a family whose DC check is vacuous never reads "PASS"
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of the ask
A static (no-simulation) fan-out/floating-input/contention checker over a future packed physical netlist, gated on three prerequisite tasks (#400, #394, and the since-filed #427), producing `loading.txt` with a four-verdict vocabulary. The prose, math (§7.10) and test list are unusually rigorous for a paper design. That rigor is exactly what makes its internal contradictions easy to pin down with evidence rather than guesswork.

## Findings, most severe first

**1. The required "mixed-family threshold" data (P8, §7.10's `M` formula) is not actually promised by the schema this issue depends on.**
§7.3 of #430 states the consumed `PartLibrary` carries "drive capability in unit loads, input load in unit loads, the vacuous-DC-check flag, **and input/output threshold data**. Schema owned by TASK-0085." §7.10's mixed-family predicate needs four numeric fields per pin: `V_OH(q) < V_IH(p) ∨ V_OL(q) > V_IL(p)`. But #400 (TASK-0085), the blocking dependency that owns this schema, defines `Electrical` in its own §7.4 as: *"drive capability and input load, both in unit loads of the part's own family, plus a flag for families where the DC fan-out check is vacuous. TASK-0088 consumes this and nothing else."* No VOH/VIH/VOL/VIL fields appear anywhere in #400's interface contract, predictions, or Definition of Done. #430 is depending on data its own cited blocker never commits to shipping. Either P8/the `M` formula is unimplementable as scoped, or #400 needs an undocumented schema addition — and #430's `blocked_by` does not flag this gap at all. **Recommendation:** before work starts, amend #400's `Electrical` schema to add the threshold fields (with #430 as the citing consumer) or drop P8/mixed-family checking from this task's scope and file it separately.

**2. #430 will trip an architecture test its own blocker's Definition of Done requires to keep holding forever — and the author's own bot comments on this issue flag the contradiction as unresolved.**
#400's Definition of Done: *"The electrical columns have **no non-test reader**, pinned by an architecture test that keeps holding **after close**"* (P10), and #400 §12: *"`Electrical` is consumed by TASK-0088 and nothing else; that narrowness is what makes P10 checkable."* Read literally, #400 ships an architecture test asserting zero non-test readers of `Electrical`, and that test is required to still pass after #430 lands — but #430's entire purpose is to become a non-test reader of `Electrical`. The issue's own comment thread (comment id 5226966306, posted by the author) names this directly: *"this task is the first legitimate consumer of `Electrical`, and it is the pass that will trip that architecture test. Landing this work means retiring or re-scoping that test, and doing so is only honest once the semantic prerequisite is satisfied — which is a #341 question, not a #365 one."* Yet #430's `blocked_by` is `[400, 394]` only, and its body explicitly argues #341 is *not* a dependency ("Deliberately not a dependency... the temptation is to wait for drive strengths... do not"). So the issue asserts, in its own body, the very ordering the issue's own comment says is required before this work is honest to do — and never resolves the tension. **Recommendation:** either add a real `blocked_by` edge (or an explicit, reasoned waiver) addressing when/how #400's P10 architecture test gets retired, or change #430's stance on #341 with justification, before this is picked up.

**3. Stale dependency graph: TASK-0087 has since been filed as #427 (open), but #430's machine block and blocked_by list still describe it as "not yet filed" and omit the edge.**
The issue body: *"TASK-0087 (width decomposition and the cascade rule, owned by FEAT-041) is the third prerequisite and is **not yet filed**"* and `blocked_by: [400, 394]`. A live search shows TASK-0087 is issue **#427** ("an 8-bit adder becomes two cascaded parts with one synthetic carry net in the IR..."), open, filed after #430. The issue's own Completion Criteria anticipate this ("#400, #394 and TASK-0087, **whose issue the link pass adds**") but nothing enforces that the link pass actually happens — as of now it hasn't. A picker could start work believing only two prerequisites are outstanding. **Recommendation:** update `blocked_by` to `[400, 394, 427]` before assignment.

**4. Exit-status contract is gameable in exactly the way the issue says it must not be.** Per §7.10's exit mapping, `UNDECIDABLE` never causes exit 1 — only `OVER_FANOUT`, contention, and undriven inputs do. A `-parts` library with sparse or entirely-missing electrical data (plausible early on, since #400 has no committed shipped-set size beyond "named, bounded") makes every net `UNDECIDABLE`, and the run **exits 0**. Per `docs/batch-interface.md` (confirmed at lines ~33-40), exit status is the documented failure signal graders and CI are told to key on, not stream content. A grading script or CI gate reading only the exit code would see "0 = run completed" on a design that was never actually electrically checked — the precise "confident wrong answer" H3/P4 are built to prevent for the DC-vacuous case, reappearing for the missing-data case via the exit code rather than the string. §7.11 handles this in `loading.txt`'s per-net text but the issue never addresses the exit-code framing, which is what automated tooling actually consumes. **Recommendation:** add a prediction/test asserting the exit-status behavior when a large fraction (or all) of a design's nets are `UNDECIDABLE`, and consider whether that should be distinguishable from a real "0 findings" pass in the batch contract (e.g., an `UNDECIDABLE` count surfaced outside `loading.txt`).

**5. TriState-as-conditional-driver risks silently reintroducing the value-domain work H1 explicitly rules out.** §7.10 treats `TriState` as a "conditional driver" and Open Question 3 recommends counting it as a driver for undriven-input purposes but not for push-pull contention. Whether a tri-state output is actively driving a given net is, on real hardware and in JLS's own simulation semantics, a function of its enable input's *value* — not a static structural fact decidable from `Put`'s two permits (O4). The issue's own H1 falsification clause anticipates exactly this: *"Refuted by: a case requiring a simulated value to classify."* The issue asserts this case is fine because it only needs "is this pin capable of driving," not "is it driving right now" — but that reading is not stated anywhere in §7.10's formal definitions, and the contention/floating predicates as written (`|{q : kind(q)=push-pull}| > 1`, `drivers(N) = ∅`) don't actually specify whether a `TriState` output counts as occupying `drivers(N)` unconditionally or only under some static approximation. **Recommendation:** state explicitly, in the formal definition (not just an Open Question), that TriState counts as a driver unconditionally (worst-case/conservative) for both undriven- and contention-purposes, and record that as the falsification-guard answer to H1 rather than leaving it implicit.

**6. Open Questions marked "Blocks execution" are largely pre-decided by the normative math earlier in the same document, making the completion-criteria checkbox for resolving them close to decorative.** E.g. Open Question 1 ("Does an UNDECIDABLE net make the run exit 1?") is presented as unresolved and blocking, but §7.10's exit-mapping formula already hard-codes the answer (`0 ... including NOT_DC_LIMITED and UNDECIDABLE`) earlier in the same issue. Completion Criteria only requires the decision be "resolved (or explicitly deferred)" — trivially satisfied by pointing back at §7.10, no actual review needed. This doesn't invalidate the design, but it inflates the appearance of open deliberation where none is left to do, and a reviewer skimming the Definition of Done could be misled into thinking these are live gates.

## What's solid
- O1/O2's evidence for the core defect (floating input invisible in simulation via `initInputs()`) is directly reproducible against `src/jls/elem/LogicElement.java` at the cited lines — verified in this checkout.
- The driver/sink totality argument from `Put`'s sealed `permits Input, Output` (O4) is accurate against `src/jls/elem/Put.java` lines 16-17.
- P2/P4/P5's insistence on exact-string and both-numbers reporting is a good defense against a check that technically passes its tests while being useless to the stated audience (students at a workbench).
- The determinism/no-floating-point requirements (H5, P10) are well-justified and cheaply testable; no objection.
- Explicitly scoping out capacitive loading, transmission-line effects, decoupling, supply drop, and temperature derating (P12) rather than silently omitting them is honest and matches the project's own documented discipline elsewhere (`Board`'s natural-order precedent, `PinBindings`' aggregate-error idiom).

## Bottom line
The check's *shape* is sound and its self-honesty about DC-vacuous families is a genuine strength, but the issue is not ready to pick up: it depends on schema data (§7.10's `M` predicate) that its own cited blocker doesn't promise, its own comment thread has flagged an unresolved conflict with #400's permanent architecture-test invariant that the issue body doesn't address, and its dependency list is already stale against a since-filed prerequisite (#427). These are fixable with edits to this issue and #400, not a redesign — hence needs-rework rather than should-not-proceed.
