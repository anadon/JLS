# Issue #643: TASK-C598-3: one diagnostic vocabulary, two surfaces — the GUI dialog shows the text the headless path reports, and no path can claim success when a stage did not run
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: sound-with-concerns

## Summary of what's being asked

TASK-C598-3 is the GUI-facing tail of FEAT-C38-2 (#598): render all four board-flow refusal classes (unassigned port, wrong-direction pin, un-exportable element, missing tool) in a dialog with text byte-equal to the headless path, keep aggregation intact, guarantee no silent partial success, and make the dialog keyboard-reachable and #91-harness-drivable. `ordering_after: [597, TASK-C598-1(#638), TASK-C598-2(#640)]`.

## Findings, most severe first

**1. (High) "Byte-equal to what the headless path reports" is ambiguous about which layer of text it means, and the ambiguity is gameable.** `ARCHITECTURE.md`'s CLI contract states diagnostics are "one `jls: error: …` line on stderr" — that prefix is added by `JLSStart`, not by the underlying exception. `PcfEmitter.emit` (`src/jls/hdl/board/PcfEmitter.java:116-119`) throws `HdlExportException("cannot bind module \"...\": " + String.join("; ", errors))` — no `jls:` framing at all. AC-1 says the GUI text must be "byte-equal to what the headless path reports for the same condition" without saying whether "reports" means the raw exception message or the full CLI-framed stderr line. A test author can satisfy the letter of AC-1 by literally putting `jls: error: cannot bind module "top": port "a" has no pin binding; ...` inside the dialog — CLI chrome bleeding into a GUI surface, which is exactly the kind of surface-mismatch bug this task exists to prevent — and the test would still pass because it compares two strings that happen to be equal by construction. *Recommendation:* name the exact seam explicitly — e.g. "byte-equal to `HdlExportException.getMessage()`/the equivalent diagnostic object, not to the formatted stderr line" — so the comparison test can't be satisfied by piping CLI framing into the dialog.

**2. (High) AC-3's "stub each stage into a no-op in turn" assumes an interposable stage abstraction that doesn't exist yet.** The board flow's downstream stages (place & route, packing, flashing) live entirely in `scripts/icestick-handoff.sh`, an external shell script invoked as a subprocess (`docs/icestick-bitstream-handoff.md:9-13`, `31-35`) — there is no `Stage`/pipeline interface in `jls.hdl` for this flow (`grep -rn "Stage" src/jls/hdl` turns up only unrelated "Stage 1/2" prose in the HDL-import/export doc comments, not a stubbable seam for the board pipeline). A JUnit test that "stubs each stage into a no-op" needs that seam to exist first — export, constraint emission, and script handoff have to become individually substitutable units, which is new architecture, not reuse of #264/#598's existing all-or-nothing preflight discipline. The issue presents this as a straightforward test to write; it is actually a design task with no owner assigned and `band_mw: "0.5-1"` does not obviously cover it. *Recommendation:* either scope the stage-seam design explicitly in this task (and re-estimate), or split it into its own prerequisite task the way TASK-C598-1/2 were split out of #598.

**3. (Medium) Acceptance criterion 4 (retry without re-entering bindings already given) has no stated verification method.** Compare the phrasing discipline used elsewhere in the same list: AC-1 says "pinned by a test that drives both," AC-3 says "asserted by a test that stubs each stage." AC-4 — "A refusal leaves nothing on disk and leaves the flow in a state the student can correct and retry from, without re-entering bindings already given" — states a real, valuable UX guarantee (dialog state must survive a submit-time refusal) but names no test. As written, a naive implementation that clears the whole form on any refusal would fail nothing in this criteria list yet defeat the exact property AC-4 exists to guarantee. *Recommendation:* add an explicit test requirement, e.g. "a test that triggers a refusal, asserts prior field values are still present, and re-submits successfully without re-entry."

**4. (Medium) "Stably named per `docs/component-naming.md`" cites a document that doesn't yet cover this dialog's shape.** I read `docs/component-naming.md` in full: it defines exactly two naming families — palette buttons/menu mirrors, and "Element create/modify dialogs" that extend `jls.edit.ElementFormDialog` (lines 30-58, `dialog.<slug>.<field>`). A board picker / pin-assignment wizard reached from the File menu is neither a palette entry nor an element create/modify dialog, so there is no defined naming pattern for it in that document today. AC-5 (and #597 AC-4, which this task's naming citation mirrors) both treat the doc as an already-settled contract for this new dialog type; it isn't — extending `component-naming.md` with a new family (or fitting this dialog awkwardly into the existing `dialog.*` family it wasn't designed for) is undocumented, unscoped prerequisite work. *Recommendation:* either extend `docs/component-naming.md` with an explicit non-element-dialog naming rule as part of #597 (the task that actually builds the dialog shell) and have #643 merely comply, or state the rule inline in this issue so implementers aren't left guessing.

**5. (Medium) Feasibility/estimation risk: every text this task must pin byte-equal is unwritten.** `ordering_after: [597, TASK-C598-1, TASK-C598-2]` and all three are open/unimplemented — I confirmed zero board-picker/pin-dialog GUI code exists anywhere in `src/` (`grep -rn "picker|BoardPicker|BoardDialog|PinAssign" src` — no hits), and #638/#640 (which own the exact diagnostic strings AC-1 pins byte-equal) haven't landed either. This is disclosed via the ordering field, not hidden, but it means #643's core acceptance criteria reference text that doesn't exist anywhere in the repo yet, so the "0.5-1" size band is really "0.5-1 once three other open tasks have shipped and frozen their wording" — and any post-#643 wording tweak to #638/#640's diagnostics silently reopens the exact drift AC-1 was written to catch, since nothing re-runs the byte-equal test on the upstream text alone. *Recommendation:* make the byte-equal test live where the diagnostic string is defined (in #638/#640's test module) or add a cross-reference note so a future wording edit to TASK-C598-1/2 is required to touch this test too.

**6. (Low) AC-2's "shown as several, not truncated" is satisfiable with a weak test.** "Several unassigned ports are shown as several" could be verified with as few as two offenders, which exercises string aggregation but not the dialog widget's actual failure mode — a fixed-size `JLabel`/text component silently clipping a long, real-world PCF error list (which can run to many ports on a wide bus). *Recommendation:* require the aggregation test to use enough offenders (e.g. one per bit of a multi-bit bus, or 10+) that a naive dialog widget would visibly truncate, so the test exercises the actual risk rather than just the string-join logic.

## What's solid

- The reuse premise is well-grounded, not aspirational: `PcfEmitter.emit` (confirmed at `src/jls/hdl/board/PcfEmitter.java:116-134`) and `PinBindings.parse` already implement collect-all-then-throw-one-aggregated-exception, so AC-2's ordering/non-truncation guarantee rides on tested infrastructure rather than being invented here.
- The one-vocabulary-two-surfaces model has direct project precedent: `ARCHITECTURE.md`'s error-reporting contract already runs this pattern for load errors (`JLSInfo.setLoadError` → `JLSInfo.loadError` "derived view, so every front end shows the same message"), so the general shape of AC-1 is not a novel idiom for this codebase.
- AC-5's keyboard-reachability + `#91`-harness-drivability requirement reuses an established test pattern (`MenuAcceleratorPolicyTest`, cited the same way in #597 AC-4) rather than inventing new harness machinery.
- The "never report success when a stage did not run" framing is squarely aligned with the project's existing all-or-nothing discipline (nothing-on-disk-on-refusal, per `PcfEmitter`/handoff-script preflight) and does not conflict with anything in #598 or #91.
