# Issue #594: FEAT-C37-3: a user who knows what a part is called finds it by typing — palette search, recently-used and keyboard palette navigation close Logisim-Evolution's oldest findability complaint
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Findings, most severe first

**1. AC-5's "K9" invariant and "startup cost ratchet" are not defined anywhere in this repository.**
AC-5 reads: *"K9 holds — no new default-visible chrome, and the search index's construction does not move the startup cost ratchet."* A repo-wide search (`grep -rn "K9"` and `grep -rn "startup cost ratchet"` across `src/`, `docs/`, `README.md`, `ARCHITECTURE.md`) returns zero hits outside this fleet's own prior review outputs under `issue-reviews/`. There is no K9 clause in `ARCHITECTURE.md`'s "Recorded decisions" section, no startup-cost benchmark or CI gate anywhere in the tree. As written, AC-5 cannot be checked by anyone who only has this codebase in front of them — it references an external convention the issue assumes but never states. This is a criterion that can be claimed satisfied ("K9 holds, trust me") or claimed violated with equal unfalsifiability.
*Recommendation:* either inline K9's actual content (what specifically counts as "default-visible chrome," what the startup-cost ratchet number is and where it's measured — e.g. a JMH/wall-clock startup benchmark that doesn't exist in this repo either) or drop the shorthand and restate AC-5 in terms of a concrete, greppable assertion.

**2. The dependency chain #594 rests on includes at least one unfiled task, not just an open issue.**
The issue's own boundary note says the search index/recently-used model/keyboard-nav state are "model-side collaborators… produced by #316 (FEAT-008)/#84, driven through #441 TASK-0020's `MouseMachine`/`InteractionState`." But #316's own body lists `TASK-0020` under `planned_tasks` as **"not filed"**, and #316 states plainly: `git ls-tree -r --name-only 2d0ca9d src/jls/edit/ | grep -iE "MouseMachine|InteractionState"` returns nothing — confirmed independently against HEAD (`src/jls/edit/` has no such file; `SimpleEditor.java` is still 5,852 lines with the 9-state enum in-file, per `ARCHITECTURE.md`'s own description of `SimpleEditor`). So #594 is written as if it will slot into infrastructure (`MouseMachine`/`InteractionState`) that is two levels removed from existing: #316 hasn't started TASK-0020, and TASK-0020 hasn't even been filed as an issue yet. #594's own text ("if #316 stalls, this feature waits") is honest about the gate but understates how far upstream the actual blocker sits — this is not "wait for #316 to land," it's "wait for a task inside #316 that doesn't exist as a filed issue yet."
*Recommendation:* either file TASK-0020 first (per #316's own "the plan is committed first" rationale) or state explicitly in #594 that it cannot be scheduled until that filing happens, rather than citing `MouseMachine`/`InteractionState` as if they were an available seam today.

**3. AC-4's verification is circular: the catalog it must score against doesn't exist yet.**
AC-4: *"…each corresponds to a scored GAP row in #592's catalog."* `docs/` contains no parity/catalog file (`Glob docs/*parity*` → no matches; full `docs/` listing has no candidate). #592 itself says: *"Nothing in PF-2..5 is funded until it has a row here and a score; this catalog is the gate."* #594 is PF-3's feature. So by #592's own text, #594 cannot legitimately be funded/started before the catalog exists — yet #594 is filed, scoped, and has five acceptance criteria as though it's ready to execute. There's also no stated fallback if #592's catalog, once written, scores palette-search as REFUSE or lower priority than #594 assumes — AC-4 as written can only be "verified" by an artifact that must be produced by a different issue first, with no owner-visible mechanism in #594 for what happens if that artifact disagrees with #594's premise.
*Recommendation:* either state AC-4 as "blocked until #592's catalog publishes a row for this feature" explicitly (which the `ordering_after` field gestures at but AC-4's prose doesn't), or drop AC-4's grading dependency and let #594 stand on its own acceptance criteria.

**4. AC-1's "alias" vocabulary is undefined and could be satisfied by internals never meant for end users.**
AC-1 requires matching "at least one alias form" but never says which alias set. The only alias concept that exists in the codebase today is `SaveTags`' canonical-tag + alias map, described in `ARCHITECTURE.md` ("`ELEMENT Foo` resolves via `SaveTags.resolve(tag)` (canonical tags + alias map, issue #79 — tag text never reaches `Class.forName`)") — a *file-format* concern, not a UX-naming concern. `PaletteEntry.java`'s own doc comment insists on a hard split: the core half (`ElementType`, in `jls.elem`) carries what "loading, saving, and headless tooling need," while `PaletteEntry` (GUI-side) "never leaks into the core." If palette search is implemented by matching against `SaveTags` aliases, it either violates that documented layering (core format concept leaking into GUI search) or requires inventing an entirely new alias vocabulary that AC-1 doesn't ask for or scope — and a naive implementation could satisfy the literal AC-1 text by matching internal tag aliases like `AND2`/`XOR3` rather than human-meaningful names ("AND gate"), which defeats the "closes Logisim's no-component-search gap" goal while technically passing the letter of AC-1.
*Recommendation:* name the alias source explicitly (a new user-facing synonym table vs. reusing `SaveTags`) and add an acceptance example (e.g., typing "flip flop" must find the D-latch/register element) so the criterion can't be satisfied by matching only internal tags.

**5. AC-2's "persists across a session" is ambiguous between in-memory and durable, and the two readings have very different costs.**
"Session" most naturally reads as in-memory-only (cleared at editor close), but the outcome prose ("puts the last handful of placed elements one gesture away") reads like a durable, cross-restart UX expectation similar to IDEs' recently-used lists. `JLSInfo` is named in `ARCHITECTURE.md` as the holder of "global settings/statics" — if recently-used is meant to survive restarts, it needs a new persisted-preference path through that mechanism (or a new one); if it's session-only, a trivial in-memory `Deque` suffices with no persistence work at all. The band estimate (`1.5-2 mw`) for the whole feature doesn't disambiguate which of these two very different implementations it assumes, and AC-2's literal text ("persists across a session") is satisfiable by the cheap, likely-unsatisfying reading.
*Recommendation:* state explicitly whether recently-used state must survive an application restart, and if so, where it's stored (new `.jls`-adjacent prefs file? `JLSInfo` statics serialized how?).

**6. AC-3's accessibility claim risks appearing more complete than it is.**
AC-3 asks that "focus order and accessible names [be] asserted." #75 — the very issue #594 says it extends — is explicit that automatable focus/name assertions and *manual* assistive-tech verification (VoiceOver/Orca) are different tiers, and #75's own I3 criterion (manual AT pass) is still outstanding at time of writing (listed under "planned_tasks," "Awaiting human + hardware"). #594 doesn't distinguish these tiers: a purely headless focus-order/accessible-name test (Layer 1, already the kind of thing `test/jls/ui` supports per `ARCHITECTURE.md`) would technically satisfy AC-3's text while leaving the actual screen-reader experience of palette search completely unverified — exactly the gap #75 flags as still open for the rest of the editor. This is a way the stated verification could pass while the real accessibility goal (a screen-reader user can actually use search) fails.
*Recommendation:* either scope AC-3 explicitly to headless/Layer-1 assertions only (and say so, so nobody mistakes it for an AT-verified claim) or fold a manual AT check into this feature's own DoD, consistent with how #75 treats the same distinction.

**7. Minor: "Logisim-Evolution's oldest findability complaint" is an unverifiable editorializing claim.**
Nothing in this repo can confirm Logisim-Evolution issue #1234 is their "oldest" findability complaint (as opposed to merely a cited one, as it's referred to in #521/#592). This is cosmetic — it doesn't affect implementability — but it's the kind of unverifiable superlative that shouldn't sit in a title driving scope/priority framing.

## What's solid

- The three-way scope split against #593 (canvas manipulation) and #595 (error messages) is explicit and well-fenced in the issue's own follow-up comment — a real deduplication pass, not just an assertion.
- AC-3's "reuse #75's shared `Action` layer rather than a parallel one" is a concrete, checkable, non-negotiable constraint that correctly heads off the classic mistake of a second accelerator/dispatch scheme; `EditOp.java` and the `Action`-layer substrate cited (PR #197) do exist at HEAD, so the reuse target is real, not aspirational.
- The hard decomposition gate (nothing lands inside `SimpleEditor`) is consistent with #316/#84's own documented state and is the correct call given `SimpleEditor.java` is still 5,852 lines with no `MouseMachine`/`InteractionState` type — the issue doesn't try to sneak scope into the god class.
- `ordering_after` correctly lists both real blockers (#592, #316/#84) rather than hiding them.

## Bottom line

The scoping and dedup work (comment pass) is genuinely careful, but the acceptance criteria have real holes: one criterion (AC-5) is unverifiable against this codebase as written, one (AC-4) is circularly dependent on an artifact that doesn't exist and may not even confirm this feature's priority, and two more (AC-1, AC-2) are ambiguous enough to be satisfied by an implementation that misses the stated user-facing goal. Combined with a dependency chain that bottoms out in an unfiled task (#441 TASK-0020), this issue is not ready to hand to an implementer without rework of the acceptance criteria and an explicit filing of its true prerequisite.
