# Issue #625: TASK-C490-4: a first-year drawing an adder never meets the transmission line — visibility derived from context, not an exclusion list, and an overshoot that names the receiving element
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what's being asked

Two deliverables: (1) a "context-derived" mechanism to keep a not-yet-built transmission-line element out of the default palette, replacing the current `NON_PALETTE_TAGS` exclusion-list pattern; (2) an overshoot diagnostic naming the receiving element and peak voltage, clearing once a series termination is applied. This is TASK 4 of 4 under FEAT-059 (#490), itself rung 3 of capstone CAP-18 (#313).

## Findings, most severe first

**1. AC-1's core mechanism is undefined, in this issue and in its parent.** "Palette visibility is derived from context" never says what the context is: an app-wide advanced-mode toggle? a per-circuit opt-in? presence of another SI element already placed? I grepped `Palette.java` and `SimpleEditor.java` for any existing notion of mode/experience-level/course-profile — there is none (`grep -rn "context.derived\|visibility\|advanced mode\|experienceLevel\|CourseProfile" src/jls/edit/Palette.java src/jls/edit/SimpleEditor.java` returns nothing). #490 (the parent feature) is equally silent on what "context" cashes out to; it only rules out the exclusion-list *implementation*, not the visibility *policy*. As written, an implementer could satisfy AC-1's letter with, e.g., a rule that is functionally identical to a fourth `NON_PALETTE_TAGS` string (a hard-coded `if (type.tag().equals("TransmissionLine")) return false;`) while merely not literally touching that named `Set`. That passes the stated test and defeats the stated intent. **Recommendation:** the issue needs a concrete definition of "context" (e.g., "visible only when the circuit already declares a length/edge-rate attribute via #486," or "visible only behind an explicit advanced-elements toggle persisted in `JLSInfo`") before work starts, not left to the implementer to invent.

**2. The two declared prerequisites are both still open — this task cannot be built yet.** `ordering_after: ["TASK-C490-1", "TASK-C490-3"]` names the element itself and its golden/K18-1 cross-check as gating work. I confirmed via `search_issues` that TASK-C490-1 is #618 and TASK-C490-3 is #623, and both are `state: open` — neither the transmission-line element nor the four-termination golden corpus exists in `src/` or `test/` today (`grep -rln "TransmissionLine|ReflectionGoldenTest|EdgeRateCollapseTest" src test` returns nothing). There is no diagnostic surface, no trace row for a real-valued waveform, and no element to attach a visibility rule to. Filing/reviewing this task now, ahead of its own prerequisites landing, invites it being picked up and partially built against a moving/nonexistent target. **Recommendation:** either close this as not-yet-actionable until #618/#623 land, or explicitly label it blocked so it isn't picked off the open-issues list by mistake.

**3. AC-3's "no edge-rate field" is not this task's dependency, and can be satisfied vacuously.** The criterion says a first-year "sees no transmission line, no edge-rate field and no SI dialog." The edge-rate field belongs to FEAT-058 (#486, `state: open`, unimplemented) — a feature this task's `ordering_after` does **not** list, and #490's own dependency graph draws no edge from FEAT-058 into this task's visibility scope (T1→T4 only). Today there is no edge-rate field anywhere in the codebase, so this half of AC-3 is trivially true for reasons having nothing to do with any visibility rule this task builds — it will pass whether or not the rule works, and nothing re-checks it once #486 actually ships a field to hide. **Recommendation:** either drop the "no edge-rate field" clause from this task's AC (it's #486's to guarantee) or add #486 to `ordering_after` and phase the check to run again after #486 lands.

**4. The cited evidence commit does not exist in this repository.** The issue states: "at `2d0ca9d` the registry's 35 types against 32 palette entries." I ran `git cat-file -t 2d0ca9d` and searched `git log --all --format="%H" | grep "^2d0ca9d"` — no match anywhere in the 271-commit history of this checkout. `docs/plan/` (the directory #487/#490 cite as the source of this evidence trail) also does not exist here. The specific counts happen to still be true at current HEAD (`bd54461`, verified below), but the citation itself is unverifiable against this repository, which undercuts the task family's own stated discipline of pinning every claim to a resolvable commit. **Recommendation:** re-cite evidence at a real, resolvable commit in this repo, or drop the hash and cite "current HEAD" with the date.

**5. "A green test currently enforces the violation" is misleading as stated.** I verified directly: `grep -c "new ElementType(" src/jls/elem/ElementRegistry.java` → 35; `grep -c "entry(Group\." src/jls/edit/Palette.java` → 32; `PaletteContractTest.java:44-45`'s `NON_PALETTE_TAGS` has exactly 3 entries (`SubCircuit`, `WireEnd`, `TestGen`). 35 − 3 = 32 = 32: `paletteIsTotalOverTheElementRegistry` passes cleanly today; there is no numeric violation in the working tree. What the issue actually means — that the *only currently available mechanism* for hiding a future element is growing the exclusion set, which it considers a design smell — is a defensible position, but "enforces the violation" reads as "a bug exists right now," which is false. An implementer skimming this issue could go looking for a failing test that doesn't exist. **Recommendation:** reword to something like "the only mechanism this test currently accepts for hiding an element is growing `NON_PALETTE_TAGS`, which is the pattern this task replaces" — describe the future risk, not a present defect.

**6. `SiPaletteVisibilityTest` is claimed "shared with #487," but #487's own invariants forbid it from ever touching the palette.** #487 (FEAT-060, SI constraint export) states as Global Invariant #8: "No new element type and no new palette entry." A test literally named for palette visibility, jointly authored across two issues worked independently (possibly by different people/agents, in either order), with no stated file-ownership or merge protocol, is a coordination hazard: whichever PR lands second must extend rather than recreate the file, and nothing in either issue says how. **Recommendation:** name which issue creates the test file and which extends it, or split into two differently-scoped tests.

**7. "Startup time" and "per-edit cost... unchanged" have no measurement infrastructure to check against.** `grep -rln "startup time|per-edit cost|startupTime|perEditCost" test src` returns nothing — there is no existing perf harness in this codebase for either metric. As written this clause of AC-3 cannot be objectively verified by a command; it will likely be waved through by inspection rather than pinned by a test, which is inconsistent with this task family's stated evidence discipline elsewhere in the same issue (AC-2's exact grep commands). **Recommendation:** either drop this clause (it's already covered qualitatively by "default palette size are unchanged," which *is* checkable) or specify the harness that will measure it.

## What's solid

- **AC-2's verification commands are exact and independently reproducible.** I ran both greps against HEAD and got the stated 35/32 split; this is good, mechanically-checkable acceptance criteria writing, in contrast to finding 5 above.
- **The K18-4 stop-clean escape hatch (AC-5) is a genuinely sound risk provision.** Explicitly permitting "stop at the headless CSV form" as a successful outcome if the visibility rule can't be built is the right way to decouple a hard, underspecified UX problem (finding 1) from the rest of the deliverable, and it correctly treats a recorded stop as success rather than failure.
- **The diagnostic requirement (AC-4) — naming the receiving element and peak, clearing on series termination — is concrete and testable**, conditional on the element existing (finding 2).

## Bottom line

The issue is well-connected to its dependency graph and admirably precise where it cites code (AC-2), but its headline mechanism (context-derived visibility) is undefined, one of its acceptance clauses is checkable only vacuously today, its evidentiary commit hash doesn't resolve in this repository, and its actual prerequisites (#618, #623) are both still open. Sound in structure, not yet sound in content — needs the "context" concept specified and the edge-rate-field clause reconciled with its true dependencies before anyone should pick it up.
