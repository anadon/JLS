## Findings, most severe first

**1. [Critical] The governing spec this task is told not to restate — `docs/parity-contract.md` — does not exist anywhere in this repository.**
The issue says outright: "`docs/parity-contract.md` ships at `2d0ca9d` and specifies what this task implements — §2.5 … §2.6 … §3.1–§3.5 … §3.6 … §5.2 … §5.3 … §9.3 … **Do not restate it; implement it.**" Verified: `ls docs/parity-contract.md` fails on the working tree, and no such path appears anywhere in `git log --all`. Every quoted section (O2's normativity notice, O4's four-row exclusion table, O5's sync-point definition, O6's interrupt-problem analysis) is sourced to a document that has never been committed. An implementer told "do not restate it, implement it" has nothing to implement against, and the eight quoted excerpts in §1/§2 of this issue are the *only* copy of the contract that exists anywhere — meaning the issue itself is silently doing the specification work it disclaims doing, without labeling itself as the source of truth. Recommendation: either commit `docs/parity-contract.md` for real before filing this task, or rewrite the issue to own the specification explicitly instead of citing a phantom external document.

**2. [Critical] The evidence commit `2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7` does not exist in this repository, so O1–O9 are unfalsifiable as written.**
`git cat-file -e 2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7` returns "commit MISSING"; the hash appears nowhere in `git log --all`. The Method's very first checklist item is "Re-verify O1–O9 at the executor's checkout; re-derive line numbers if HEAD has moved" — but there is no baseline to re-verify against, since it never existed. This is not an isolated slip: the sibling review of #347 (this task's parent feature, `issue-reviews/issue-0347.adversarial.md`, finding 2) independently found the identical hash fabricated in that issue too, and #390 (this task's sole `blocked_by`) repeats the same hash in its own YAML frontmatter. The whole TASK-0069–0082 planning corpus appears to share one fabricated provenance anchor. Recommendation: strip every "pinned to `2d0ca9d`" claim and re-derive citations against a real, resolvable commit (or HEAD) before this task is picked up.

**3. [Critical] `SyncPointDigest`'s required inputs (all GPRs, every implemented CSR) cannot be sourced from the only record format this task is blocked on.**
§7.4 requires: "at each declared instruction index and at exit, both implementations present PC, **all GPRs**, **every implemented CSR** minus `E`, and a digest over the non-volatile memory regions." But this task's sole blocker, #390 (TASK-0072), defines `RetireRecord` with exactly twelve components: `order, pc_before, pc_after, insn_word, rd_index, rd_value, mem_addr, mem_rmask, mem_wmask, mem_wdata, privilege, trap` — one destination register per retirement, not "all GPRs," and **no CSR field at all**. #390's own Threats to Validity section states plainly that "the `rvfi_csr_*` family" was "deliberately not adopted" from the record. #423 itself says of #390: "this reads two traces in a format only that task defines and compares fields only its record declares" — yet `SyncPointDigest` needs data `RetireRecord` structurally cannot carry. Nothing in #423, #390, or any cited related issue defines a second channel (a live query into `jls.mach` or the drawn circuit at a sync point) through which GPRs and CSRs would actually reach the digest. This is a genuine, checkable contradiction between what #423 promises to build and what its only declared input format supplies. Recommendation: either add a second, explicitly-scoped state-snapshot interface (and cite it as a real dependency, not folded silently into "the trace format #390 defines"), or drop the GPR/CSR digest to what `RetireRecord` can actually project.

**4. [High] `jls.mach` — required for the null family (P6) — is not `blocked_by` anything, and does not exist.**
`grep -ril "jls.mach" src/ test/` returns nothing; the package does not exist in this checkout. Yet the Definition of Done calls the null family "the feature's central criterion" and requires "four subtly wrong `jls.mach` implementations" committed as fixtures, each independently rejected with its own field named. The task that would deliver a *correct* `jls.mach` to subtly break is never named with an issue number in #423's YAML — #390 mentions an unnumbered "TASK-0070 (the machine package and its reference runner)" as a "co-producer" of #390, and #392 ("TASK-0079… sibling consumer, open") is explicitly out of #423's `blocked_by: [390]`. So TASK-0073 depends, for its central acceptance criterion, on a machine implementation that no cited task is chartered to deliver before this one starts, and that dependency is invisible in the structured `blocked_by` field a scheduler would actually read. Recommendation: add the real machine-package task to `blocked_by` (not just `related`), or explicitly scope a minimal correct-plus-four-wrong `jls.mach` stub inside this task.

**5. [High] "Assert the report text" is gameable because no report grammar is pinned anywhere in the issue.**
P1, P5, and P6 all require tests to assert on "the report text" / "the report string" rather than a boolean, explicitly to defeat `assertFalse(agrees)`-style vacuous tests (O8's stated rationale). That is the right instinct, but the issue never pins what correct report text actually looks like — no format grammar, no fixture, no example transcript for a two-component divergence. An implementer who writes both the formatter and the test in the same PR can make the report say anything and then assert exactly that string; "the report contains the differing field's name" is satisfiable by a formatter that always concatenates every field name from the record type, which would pass P1's `|F*| = 2` check on a two-component fixture without ever actually localizing anything on a fixture with three or more differences. Recommendation: commit at least one golden report transcript (e.g., for the P1 fixture) as part of this task's own deliverable, checked byte-for-byte, not just "contains" assertions.

**6. [Medium] A third citation to nonexistent provenance (O9), even though the underlying fact happens to be true today.**
O9 cites "`docs/plan/evidence/BRIEF.md` §11, landed in `3a81a4a7d6a0f108ec201e632732d308cc02b3fc`" as already deciding that `riscv/` must be deleted and that nothing in this task may route through it. Neither the file (`find -iname BRIEF.md` — empty) nor the commit (`git cat-file -e 3a81a4a7d6a0f108ec201e632732d308cc02b3fc` — missing) exists in this repository. The raw fact O9 leads with — `riscv/` currently holds 26 tracked files — is independently verified accurate (`git ls-tree -r --name-only HEAD riscv/ | wc -l` → 26), but the claim that a document *already* mandates its deletion, owned by a "TASK-0025" that this reviewer could not locate, is unverifiable. Combined with findings 1 and 2, this is the third distinct fabricated-provenance citation in one issue, which should raise real doubt about every other "already decided" claim in the document that this reviewer did not independently check line-by-line.

**7. [Medium] The DoD's PIT threshold requirement on `jls.parity` has no corresponding Method step to make it measurable.**
`pom.xml:780-786` scopes the `pitest` profile's `<targetClasses>` to `jls.sim.*, jls.BitSetUtils, jls.Util, jls.SpatialIndex, jls.collab.op.*` — `jls.parity` is not in that list, and this is verified against the actual file, not a citation. The DoD says "the 80/82 PIT thresholds met on `jls.parity`," but §8's Method checklist only says "`mvn verify`, meeting the 80/82 PIT thresholds (O8)" with no step to add `jls.parity` to `targetClasses`. As written, `jls.parity`'s mutation score is simply never measured, so the DoD line can be checked off by omission rather than by evidence. Recommendation: add an explicit Method step editing `pom.xml`'s `targetClasses`.
