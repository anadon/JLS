## Findings, most severe first

**1. [High] The R-form encoding is self-contradictory, and the gap is exactly the kind of undefined case the issue claims to forbid.** §7.6 declares R-form as `[op:3][rd:3][rs1:3][rs2:3][fn:4]` — a 4-trit function field (3+3+3+3+4=16, arithmetic checks out). But the very next sentence says "the 1-trit function modifier in the R-form spare field gives 81" (27 opcodes × 3 = 81). The document itself uses the phrase "spare field," i.e. it acknowledges only 1 of the 4 `fn` trits is meaningful — yet nowhere in §7.11's failure-mode table (the table this issue insists must enumerate "every undefined-value case... each as a defined result or a defined trap," H1/P8) is there an entry for "the other 3 `fn` trits hold a nonzero value." That is 3^3 − 1 = 26 unaccounted trit-combinations *per R-form instruction*, silently dropped. This directly breaks P5 ("a pure decoder written from the field table... round-trips every corpus instruction word") — a decoder built strictly from §7.6's field table has no defined behavior for the other 3 trits, so two implementers will guess differently (ignore them / require zero / trap on nonzero), which is precisely the independence-defeating ambiguity §1 and H1 exist to prevent. **Recommendation:** shrink the declared field to `[fn:1]` with the remaining 3 trits explicitly named (reserved-must-be-zero, or folded into a wider immediate) and add the corresponding row to §7.11's table before this issue is picked up.

**2. [High] The issue leans on repository artifacts that do not exist at HEAD, and on an unexplained internal citation scheme.** Materials & Apparatus (§6) lists `docs/parity-contract.md §3` as existing reference material ("the retirement-indexed methodology the differential tier adopts"); sibling issue #347 (FEAT-034) quotes this file's contents by line number and calls it "present at `2d0ca9d`." A repo-wide search (`find`/`grep`, no path restriction) finds **no `docs/parity-contract.md` anywhere in the current tree** — only unrelated `*ParityTest.java` files. Separately, O2's `git ls-tree` output claims `docs/plan/tasks/TASK-0081-...md`, `docs/plan/features/FEAT-039-...md` and `docs/plan/capstones/CAP-03-...md` existed at the evidence commit; **`docs/plan/` does not exist anywhere in HEAD**. The issue also repeatedly cites an authority it never names or links — "task rule 8," "rule 3," "rule 6," "rule 2," "rule 10" — and no `RULES.md`, `CONTRIBUTING.md` section, or any other file in this checkout defines a numbered task-rule set (checked `CONTRIBUTING.md`, `ARCHITECTURE.md`, `README.md`, `docs/`). A contributor picking this task up cannot verify §11's threat list, cannot read what "rule 8" (part_of_feature vs blocked_by) actually requires, and cannot confirm the parity contract's normative status that TASK-0073 (§7.11's expected-report-wording requirement) depends on. **Recommendation:** either restore/link the cited planning tree and rules document, or strip the issue of citations to files that are not in the repository a contributor will actually check out.

**4. [Medium] No cost estimate in this issue, and the one figure that exists elsewhere contradicts the scope described here.** #428 itself carries no `## Cost` section. Its parent #345 prices this exact task (TASK-0081) at "2 wk" — while explicitly warning "two weeks buys a specification draft... **do not read 10 wk as the feature**." But #428's own Completion Criteria (§14) run to 20 checklist items plus every P1-P10 and H1-H5 re-verified, a 4-tier corpus with a pinned $10^6$-vector seeded generator, a full field-layout decoder, and six named JUnit methods — considerably more than "a draft." The issue that actually defines the deliverable doesn't carry its own estimate, and the only number on record for it (from a different issue) is explicitly disclaimed as insufficient for what's being asked. **Recommendation:** add a cost estimate to #428 itself rather than relying on an upstream figure its author already says undercounts the work.

**5. [Medium] The "no Java" claim in §6 contradicts the issue's own method.** §6 states flatly: "Nothing else. No Java, no circuit, no assembler, no simulator." §8's checklist then requires writing `test/jls/mach/t3/IsaSpecCorpusTest` with "package-private static parsers for the instruction table, the undefined-value section and the manifest" (§7.5) plus a from-scratch field-layout decoder (P5) — this is real Java implementation work, just filed under `test/` instead of `src/`. Calling that "no Java" is a scope-boundary claim §7.1/§7.2 also repeat ("None at `2d0ca9d`'s surfaces... no `.jls` grammar, no CLI flag") that a reviewer relying on the stated scope would take at face value and then be surprised by the actual PR diff. **Recommendation:** rephrase to "no `src/` Java" and own the test-tier implementation cost explicitly (it's non-trivial parsing/decoding logic, not boilerplate).

**6. [Medium] P1's drift check is underspecified enough to be gameable.** The check is "parse the instruction table out of the document; assert each mnemonic appears in the corpus manifest," and §7.5 requires the parser to "return **all** rows" so a first-match parser can't hide a missing instruction. But §7.6's own worked example crams the whole mnemonic list into a single free-text table cell ("`ADD SUB MUL DIV MOD NEG`"), not a one-row-per-mnemonic structure. Nothing in the issue fixes the actual markdown schema (column delimiters, how `LIT k` is written vs. bare `LIT`, whether families get their own sub-tables) that the eventual parser must key on — §7.3 only promises "a stable structure the parser keys on" without saying what it is. Two implementations of this same task could produce structurally different (and differently gameable) parsers that both "pass" P1 while parsing different things. **Recommendation:** pin the exact table grammar (e.g., one mnemonic per row, fixed columns) in this issue, not left to whoever writes the doc.

**7. [Medium] The issue's own open questions contradict its central hypothesis.** H1 claims "every case an implementer could resolve two ways is enumerable in advance, so the specification can be **total**." Yet §"Open Questions & Decisions Needed" lists five items explicitly marked "Blocks execution" — the exact `DIV` rounding rule for non-power-of-three divisors, `MOD`'s sign convention, whether the illegal `00` code traps or reads as zero, and the `ECALL` ABI — each with only a "recommended default," not a decision. These aren't peripheral: they're the arithmetic core P8 says must be "each as a defined result or a defined trap, none left to the implementation." An issue that ships with its foundational rounding/sign-convention decisions still open is asking the implementer to make exactly the implementation-level judgment calls H1 claims to eliminate — and if two different pickups resolve them differently, TASK-0082 and TASK-0083 stop being independent constructions from one document, defeating this task's entire stated purpose (§1, §11). **Recommendation:** resolve open questions 2-4 inside this issue before it's marked ready, since "recommended default, decide later" is the specific failure mode §11 warns against ("choosing late means every program written before the choice is wrong afterwards").

**8. [Low] Instruction count is imprecise for a document whose thesis is turning claims into counts.** §7.6 lists the seven families: 6 arithmetic + 6 logic (MIN/MAX/INV/CYCP/CYCN/LIT) + 2 shift + 4 memory + 5 control (JMP/JAL/JALR/SIGN/BR3) + 6 binary-interop + 2 system = **31 mnemonics**, not "~28." Minor on its own, but ironic given P3/P4 exist specifically to replace "exhaustive" and "all sixteen" with exact counts — the total instruction count is the one number in the document that isn't counted precisely.

## What's solid

- O3 (`RegisterFile.java` L141-154, independent read/write address ports making register count free) and O4 (`Memory.java` L1224/1234-1236, the `1<<22` dense-store threshold making a 32-bit 16-trit word fit with zero headroom) were checked against the current source and quote it accurately; both are honestly scoped as "evidence, not dependencies," which is the right call.
- The core arithmetic is internally consistent: word range ±21,523,360 = (3^16−1)/2, imm7 range ±1093 = (3^7−1)/2, and the status-alphabet bound R≤5 all check out by hand.
- The `SHR3`-rounds-to-nearest-by-truncation proof (the Knuth property) is a genuinely nice, correct piece of reasoning and gives T-null model (a) real teeth.
- The "spec before either implementation" thesis itself (§1, invariant enforced via §10/§11) is sound methodology and the right call for a from-scratch ISA with no external oracle — the criticism above is about execution gaps, not the premise.

## Verdict rationale

Two High findings — a self-contradictory encoding field that the document's own P8/H1 standard would forbid, and load-bearing citations to files (`docs/parity-contract.md`, `docs/plan/`, an undefined "task rule" numbering) that don't exist in this checkout — mean the issue cannot be executed as literally written without a contributor first resorting to guesswork the issue claims to have eliminated. Combined with unresolved "blocks execution" open questions and no cost estimate of its own, this needs a rework pass (fix the `fn` field, resolve or link the missing citations, close the open rounding/sign/trap questions) before implementation starts — the underlying spec-first methodology and math are otherwise sound.
