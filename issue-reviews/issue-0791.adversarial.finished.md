# Issue #791: TASK-C584-1: the help source format is chosen and recorded, and the in-jar viewer's safe subset is written down and enforced by the build
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Findings, most severe first

### 1. AC-1 doesn't require reconciling the existing, contradicting recorded decision in ARCHITECTURE.md — two canonical documents can legally disagree after this ships
ARCHITECTURE.md already carries a dated, named "Recorded decisions" entry: **"Help delivery: in-jar now, hosted docs are the planned future (recorded 2026-07)"**, which states plainly: *"help content stays plain HTML 3.2 with relative links and no viewer-specific markup"* (`ARCHITECTURE.md:252-263`). That is itself a source-format decision — HTML 3.2 — made and recorded five weeks before this issue was filed (2026-08-04). #791's AC-1 only requires "The source-format decision is recorded in `docs/`" (a *new* file); it never requires amending or superseding the existing ARCHITECTURE.md entry. A literal-minded implementation can add `docs/help-source-format.md` choosing Markdown while leaving ARCHITECTURE.md's "HTML 3.2 ... no viewer-specific markup" sentence standing untouched — satisfying AC-1's text while leaving the repository's own architecture map asserting something the new decision contradicts. This is exactly the failure mode the issue's own Outcome paragraph claims to fix ("stops being folklore ... becomes a written contract") — except the folklore would now be duplicated into two conflicting written contracts. The project's own convention (see the "Look-and-feel", "Plugin trust boundary", and "Simulation execution strategy" entries in the same ARCHITECTURE.md section) is that decisions of this weight live in ARCHITECTURE.md itself, with `docs/*.md` used for the supporting evaluation write-up it links to (`docs/flatlaf-evaluation-2026-07.md`, `docs/picocli-evaluation-2026-07.md`). AC-1 deviates from that convention without saying why, and doesn't require updating the stale entry either way.
**Recommendation:** add an explicit AC requiring ARCHITECTURE.md's "Help delivery" entry to be rewritten (not just cross-linked) as part of this task, and follow the project's established pattern: decision summary in ARCHITECTURE.md, detailed rationale/alternatives in a new `docs/*.md` it points to.

### 2. AC-4's "priced" has no defined artifact, method, or threshold — gameable exactly like the sibling issue's already-flagged AC-5
"KC-35-1 is priced before choosing: if the in-jar renderer's subset would force the source format below usefulness, the recorded answer is the cost of upgrading the in-app viewer, not a degraded source format." Nothing says what "priced" means operationally: no unit (mw? dollars? a bounded estimate range?), no required artifact (a `docs/` write-up? a comment on #519?), no reviewer gate, and no definition of "below usefulness" that would trigger the pricing exercise at all versus let it be skipped as inapplicable. An implementer can satisfy this literally with a single unsupported sentence ("upgrading the viewer would cost ~2 mw") with no actual investigation of what "upgrading the in-app viewer" would require (a new rendering library, `Desktop.browse` fallback, etc.) — while the real intent, per the capstone's KC-35-1 wording it's quoting (`#519`: "priced before chosen"), is a genuine costed comparison. This is the same category of gap flagged against `#584`'s AC-5 ("byte-auditable diff report... no defined artifact"), and it recurs here because #791 imports the kill-criterion's language without giving it the specificity the rest of #791's own ACs have (AC-3, by contrast, names a concrete mechanism: "a planted violation turns it red with the transcript recorded").
**Recommendation:** name the artifact (e.g., a short section in the same `docs/` decision record), require it to state at least one concrete upgrade path and its estimated cost, and require it before AC-1's format choice is finalized (the issue's own ordering — "priced before choosing" — is right; only the verification is missing).

### 3. AC-1 omits the license/dependency/build-floor evaluation that the project's own precedent requires — and the likely AsciiDoc toolchain conflicts with a stated architectural constraint
`pom.xml` currently has zero Markdown/AsciiDoc processing dependencies or plugins (confirmed by grep over all `<artifactId>` entries — compiler, jar, shade, surefire, jacoco, javadoc, cyclonedx, enforcer, spotbugs, spotless, pitest, error-prone/nullaway only). Whichever format wins, some library will render it to HTML, and that library is a new dependency. The project has an established practice of writing up exactly this kind of evaluation before adopting a UI/tooling dependency — `docs/flatlaf-evaluation-2026-07.md` and `docs/picocli-evaluation-2026-07.md`, both cited from ARCHITECTURE.md — but AC-1 asks only for "rationale and alternatives rejected," not a license/dependency/build-floor evaluation. This matters concretely here: the standard Java AsciiDoc implementation, AsciidoctorJ, embeds a JRuby runtime (tens of MB, a second language runtime inside the build), which sits awkwardly against README's stated build floor — "Nothing beyond Maven and a JDK is required to build, test, or run JLS" (`README.md:205`) — and against the jar's byte-reproducibility goalpost (`README.md:92-95`, `docs/reproducibility.md`) if that runtime's artifacts leak into build output. Markdown's common Java implementations (commonmark-java, flexmark) carry no such baggage. AC-1 as worded lets an implementer pick AsciiDoc purely for its admonitions/cross-ref features (a real, defensible reason) without ever being forced to weigh this cost against the project's own stated bar.
**Recommendation:** fold a lightweight dependency/license/build-floor evaluation into AC-1's required rationale, explicitly checking against README's "Maven and a JDK" floor and the reproducible-build guarantee.

### 4. AC-2's "written down" is satisfiable by pointing at the sentence that already exists, undercutting the issue's own stated problem
The Outcome paragraph asserts the viewer-safe subset today is "folklore discovered through user-visible breakage." That overstates the current state: ARCHITECTURE.md already states it in prose ("help content stays plain HTML 3.2 with relative links and no viewer-specific markup," `ARCHITECTURE.md:261-263`). What's actually missing is not that it's undocumented — it's that it's a one-sentence description rather than an enumerated grammar (which specific tags, which specific link forms, what the fallback behavior is for a violation), and that it isn't build-enforced. AC-2 as worded ("permitted markup constructs, permitted link forms, and what happens to anything outside it") is fine as a target, but doesn't require it to supersede or materially exceed the existing one-liner, so a minimal-effort implementation could satisfy AC-2 by lightly rewording the existing sentence rather than producing the itemized contract AC-3's build check actually needs to enforce against.
**Recommendation:** state explicitly that AC-2's output must be an enumerated, machine-checkable subset definition (not prose restating the existing ARCHITECTURE.md sentence), since AC-3's build check has to be implemented directly against whatever AC-2 produces.

### 5. Band estimate (0.5–1 mw) is tight once AC-4's real pricing work and AC-3's real tooling work are taken seriously
This task bundles: a genuine format comparison with license/build-floor evaluation (finding #3), an enumerated markup-safe-subset spec (finding #4), a working build-integrated content linter proven via a planted-violation red/green demonstration (AC-3), and a real costed pricing of the viewer-upgrade escape hatch (finding #2). Each of the last two is implementation work, not documentation — AC-3 in particular requires writing and wiring an actual Maven-reachable check, which is the same category of work the sibling task #792 (TASK-C584-2, "one mvn goal emits the in-jar help tree from source") is separately budgeted for at what is presumably a larger band. 0.5–1 mw is plausible for the decision-and-writeup half of this task but looks optimistic once a real linter and a real cost estimate are included, especially given the same fleet review of `#584` already flagged that fleet's 2–3 mw band as tight for comparably-sized surface.

## What holds up

- **AC-3's build-check methodology is concrete and adversarially sound.** "A planted violation turns it red with the transcript recorded" is a real, falsifiable verification method, consistent with the project's existing conventions for this kind of claim (`scripts/wayland-rig-selftest.sh`'s stub-driven classification checks, `docs/mutation-testing-trial-2026-07.md`). This is the strongest AC in the issue.
- **AC-4 correctly imports KC-35-1 verbatim from the capstone (#519) rather than re-litigating it**, and gets the ordering right ("priced before choosing") — the content of the rule is sound even though its verification is underspecified (finding #2).
- **Ordering as the first task (`ordering_after: []`) is the right shape.** The format decision is a genuine prerequisite for #792 (which emits the in-jar tree from source) and #793 (which migrates content and emits the static site); sequencing it first is correct scope decomposition of the #584 feature.

## Verdict rationale

The task picks the right first slice of #584 (decide before building), and AC-3 is a genuinely strong, hard-to-game criterion. But AC-1 and AC-4 both describe outcomes ("recorded," "priced") without naming the artifact or gate that would catch a minimal-effort implementation, and AC-1 specifically risks landing a *second*, contradicting source-format decision alongside the one ARCHITECTURE.md already has on record — which is the precise kind of drift this whole feature (#519, CAP-35) exists to eliminate. These are fixable by naming mechanisms and requiring the ARCHITECTURE.md amendment explicitly, not by re-scoping the task, so **needs-rework** rather than **should-not-proceed**.
