## Abstract

A reviewer or grader who did not draw a circuit gets a machine-readable verdict about it: properties checked, equivalence proved or refuted with a counterexample that replays in the GUI, and coverage reported as data. Today the shipped alternative is diffing three literal lines of formatted stdout, and the batch interface has no exit status that means &#34;the run completed and the answer was wrong&#34;. The feature set that gates this is a formal core (extractor, AIG, CNF, solver, miter) riding on a value core that can say &#34;unknown&#34;, plus the measurement and CI discipline that makes a verdict about someone else&#39;s design credible rather than merely confident.

## Intended Audience &amp; Impact

- **A grader opening a submission for the first time.** The shipped grading criterion is `examples/autograde/autograde.py:45`, `EXPECTED_FINALS = {`, and `:53`, `EXPECTED_STDOUT_LINES = [` — three literal stdout lines for one input vector, pinned in CI by `test/jls/AutogradeBridgeExampleTest.java`. A submission wrong on 254 of 256 inputs and right on one passes. After this capstone the same grader gets a proof or a counterexample.
- **A reviewer of code they did not write, inside or outside a course.** This is the same problem as reviewing a pull request without running it. The verdict must be *about the design*, not about whether the reviewer thought of the right stimulus.
- **Anyone scripting around JLS.** `docs/batch-interface.md:36-40` defines exactly three exit statuses — `| 0      | run completed    | results on stdout (section 3), stderr empty    |`, `| 1      | runtime failure  | one-line diagnostic \`jls: error: ...\` on stderr |`, `| 2      | usage error      | one-line diagnostic \`jls: error: ...\` on stderr |` — and none of them can carry a verdict. The status lattice is a public interface and it must be extended once, deliberately.
- **Every user who draws a `TruthTable` with a don&#39;t-care.** Don&#39;t-care is destroyed on the output side today: `src/jls/elem/TruthTable.java:1447-1449`, `// don&#39;t care becomes false` / `if (outValue == 2)` / `outValue = 0;`, and an unmatched row returns silently holding its outputs at `:1432-1434`, `if (matchingRow &lt; 0) {` / `return;` / `}`. A verdict machinery built on a value domain that cannot represent &#34;unknown&#34; gives confident wrong answers on exactly the designs people get wrong.

## 1. Outcome Statement

A reviewer executes this walk-through and observes each result.

1. Open a submission never seen before. Run `jls -b -equiv ref.jls -cex cex.t -formal-report result.xml submission.jls`.
2. Observe **exactly one of three** outcomes, and nothing else:
   - **PROVED** over the declared care set, with the report printing the **matched port table it actually proved** — not an assertion that ports matched, the table itself;
   - **COUNTEREXAMPLE**, delivered as a `-t` file;
   - **UNKNOWN**, with a stated reason and an exit status that is **never a pass**.
3. Take the counterexample from the second case, run `jls -b -t cex.t submission.jls`, and observe it reproduce the disagreement. Open it in the GUI and observe the failing cone highlighted.
4. Run the same submission under a property and coverage suite. Observe an xUnit report naming which properties held, which nets never toggled, which `TruthTable` rows were never matched and which `StateMachine` transitions were never taken.
5. Re-run step 4 on a second machine, a different OS and a different JDK. `cmp` the coverage reports. Observe empty diffs.
6. Point the same suite at a design whose correctness is attested **by something outside this project and outside this suite** (AC-7 states the two admissible attestations) and observe it clean. Then point it at the same design carrying a **known, deliberately introduced** defect from the committed catalogue, and observe it caught, with the counterexample naming the defect&#39;s cone.
7. Feed the suite a corpus of deliberately uncheckable circuits — a `Memory`, a two-driver net, a combinational loop, an incomplete `TruthTable`, a 24-bit multiplier. Observe **UNKNOWN with a reason** for each, never PROVED and never a crash.

Steps 2 and 7 are the falsification guards, and they fail today at the interface level, not at the algorithm level: there is no verdict channel at all. `grep -rn &#39;&#34;-equiv&#34;\|&#34;-formal&#39; src/` → `0`, and `docs/batch-interface.md:36-40` has exactly three exit statuses, none of which can mean &#34;wrong&#34;.

### The two reference corpora, and what they are

Three numeric criteria in this issue — KC-09-3, KC-09-4 and AC-6 — are measured over &#34;the reference lab corpus&#34; and &#34;the reference submission corpus&#34;. **Neither existed and neither was defined when this issue was filed**, which made two of five kill criteria and one acceptance criterion uncomputable despite carrying numbers. They are defined here, made deliverables of FEAT-053 (#369), and placed in the Definition of Done.

Both are absent at `2d0ca9d`, and this is the whole of what is there: `git ls-tree -r --name-only 2d0ca9d examples/` returns exactly one path, `examples/autograde/autograde.py`; `git ls-tree -r --name-only 2d0ca9d test/fixtures/` returns exactly four, `fork-4.6-shiftregister.jls`, `headless-canary-gate.jls`, `legacy-4.1/README.md` and `riscv-sum1to10.jls`. There is no corpus of any kind in the tree.

**The reference lab corpus** — committed at `test/fixtures/corpus/lab/`, one `.jls` per assignment shape a first digital-logic course actually sets, drawn in tree and committed so it is redistributable. It carries a manifest recording, per circuit, the count of element instances **by `ElementRegistry` type name**. Two constraints make the KC-09-3 percentage a real measurement rather than a choice made at measurement time:
- the **denominator is the manifest&#39;s total element-instance count**, published in the corpus and fixed before the checker is written; and
- the corpus must contain at least one instance of **every** registered element type a course assignment can legally use. `src/jls/elem/ElementRegistry.java:38` declares `private static final List ALL = List.of(` and the list runs to `:77` with **35** `new ElementType(...)` entries; the corpus&#39;s type coverage is measured against that census. Without this floor, &#34;60% of element instances are checkable&#34; can be made true by populating the corpus with checkable types.

**The reference submission corpus** — committed at `test/fixtures/corpus/submissions/`, produced by applying a published **mutation catalogue** to the lab corpus. It is explicitly **not** real student work: real submissions cannot be committed (redistribution and student privacy), and a corpus that cannot be committed cannot make KC-09-4 reproducible. Each entry carries a recorded ground-truth verdict in the manifest — correct, or defective with the defect&#39;s cone named — so:
- KC-09-4&#39;s UNKNOWN rate has a fixed denominator and a fixed answer key;
- KC-09-1&#39;s false-pass check has something to be false against; and
- **the mutation catalogue is the same artifact as AC-7&#39;s planted-defect catalogue.** One catalogue, two consumers.
Minimum size, stated so the threshold is an integer rather than a rounding argument: **at least 30 submissions per lab problem**, at which 0.20 × 30 = **6**, so KC-09-4&#39;s 20% trips at the sixth UNKNOWN and not at a judgement call.

**Consequence for the kill criteria.** KC-09-3 and KC-09-4 are **not evaluable until the corpora land**. They cannot fire on an absent measurement, and — because the corpora are committed and their manifests fixed before the checker exists — they cannot be evaded by choosing a favourable corpus after the fact.

**Sufficiency (rule E).** §1 makes four claims and the eight required rows are exactly what makes them true. *There are exactly three answers and one of them is never a pass* needs FEAT-053 (the verdict channel, the status lattice and the corpora the answers are measured over) and FEAT-026 (a value domain in which UNKNOWN is representable rather than coerced). *A refutation is replayable* needs FEAT-053&#39;s counterexample-as-`-t` and FEAT-034&#39;s comparison alphabet. *The verdict is credible about a design nobody here wrote* needs FEAT-023&#39;s residual: it is the independent witness of AC-5 and, after AC-7&#39;s re-derivation, the source of the attestation that step 6&#39;s calibration target is actually correct. *The verdict is reproducible and affordable* needs FEAT-005, FEAT-006 (the run finishes without silent corruption), FEAT-007 (step 5 is actually run on more than one platform, and the oracle leg is required rather than skipped) and FEAT-009 (the budget is measured, not asserted). Every §1 step has an owner in this list and nothing else is needed.

**Minimality.** Remove FEAT-053 and nothing in §1 exists, including the corpora three of the criteria are measured over. Remove FEAT-026 and step 7&#39;s UNKNOWN silently becomes a definite answer — the single worst failure here, and the one KC-09-1 kills the feature over. ## 3. Cross-Feature Integration Risks

- **The status lattice is a one-shot public design spanning every consumer.** `docs/batch-interface.md:36-40` has three statuses; this capstone needs at least PROVED / COUNTEREXAMPLE / UNKNOWN mapped onto statuses that never collide with &#34;wrong answer&#34; from the grading side. CAP-06 (#300) is designing the *same* lattice for the *same* file, at the same time, for a different verdict kind. **If both extend it independently, one of them renumbers and every script written against the first version breaks.** Neither capstone&#39;s own criteria detect this; it is resolved by designing the lattice once with both consumers&#39; verdicts in it, before either&#39;s first checker.
- **The formula extractor inherits the exporter&#39;s refusals.** The refusal map at `src/jls/hdl/HdlExporter.java:460-477`, declared at `:460` as `private static final Map, String&gt; REJECTED = Map.of(`, is `{Memory, SubCircuit, RegisterFile, FieldExtend}` — `:461` `Memory.class,`, `:465` `SubCircuit.class,`, `:469` `RegisterFile.class,`, `:473` `FieldExtend.class,` — while `ShiftRegister` is in the *exported* set at `:435`, `TruthTable.class, StateMachine.class, ShiftRegister.class);`. Any extractor built over the same walk inherits exactly these four refusals. That makes `SubCircuit` a day-one exclusion unless the formal-only flattening elaborator is funded, which is why the demo slice includes it (Open Question 4). It is also the single largest determinant of KC-09-3&#39;s percentage, which is why the lab corpus&#39;s element-type census (§1) has to be published before the elaborator is scoped.
- **Coverage determinism is a composition property.** Step 5 compares coverage reports across machines, JDKs and platforms. Every contributing piece can be deterministic in isolation while the composition is not: map iteration order in the report writer, locale in number formatting, and enumeration order of the design&#39;s elements. KC-09-5 kills the feature over this, and the criterion must be written against the *composed artifact* before the report format is designed.
- **Four-state lands on the hot path FEAT-030 is trying to speed up.** FEAT-026 adds a bit-plane to a representation #232 already identifies as GC-churning. FEAT-030 promises the existing golden corpus stays **byte-identical**. If FEAT-026 lands first and changes goldens, FEAT-030&#39;s byte-identity claim is measured against a moved baseline and its 2.26x becomes unverifiable. Ordering matters and neither feature owns it — **and the filed blocks confirm that: #322 (FEAT-026) declares `blocks: [341, 344, 370]` and does not name #362, while #362 (FEAT-030) declares `blocked_by: [335]` and does not name #322. So nothing in the tracker sequences them.** FEAT-030 is beneficial here, so the ordering obligation has to be recorded on whichever capstone funds it.
- **A false pass is unrecoverable and no feature&#39;s test suite can rule it out.** Every checker will be tested against circuits its author understood. AC-7&#39;s calibration against an *externally attested* design and AC-1&#39;s deliberately-uncheckable corpus are the only places that circularity is broken, and they are broken by concrete adversarial artifacts rather than by definitions. **This is the risk the issue as originally filed instantiated rather than avoided**: its AC-7 calibrated against a golden this project wrote, checked by a reference emulator `docs/machine-calibration.md:87` records as &#34;written by the same author as the design under test, so it is a self-consistency oracle, not an independent one&#34;. AC-7 is re-derived below to close that loop.
- **The oracle can be green because it never ran.** FEAT-023&#39;s shipped half is `Assumptions.assumeTrue(...)`-gated (`GhdlCompileTest.java:35`). On a CI matrix where the tool is absent, AC-5 reports green forever — and after AC-7&#39;s re-derivation the same skip would silently remove the attestation AC-7 depends on. Property of the workflow configuration; owned by no feature, which is why FEAT-007 is required.
- **UNKNOWN must be a first-class report to a course, not a soft failure.** Statuses meaning UNKNOWN are never passes, and a grading bridge must report them as *ungraded-by-tool*, not as failures. Reported as failures they punish students for the tool&#39;s limits; reported as passes they are KC-09-1. This constrains FEAT-053 and the CAP-06 bridge jointly.
- **There is no timestamp-closure hook for a property checker to fire on.** `src/jls/sim/Simulator.java:215`, `protected void runEventLoop() {`, advances `now` per event with no &#34;all events at this timestamp are done&#34; callback. A property asserted mid-timestamp sees a partially-settled circuit. The `Assert` archetype itself already exists — `src/jls/elem/Stop.java:147-161` and `src/jls/elem/Pause.java:167-180` are 1-bit-in, zero-out elements whose whole job is a side effect when a condition holds — so the element is cheap and the *hook* is the real work.
- **Two features this capstone does not carry at all are prerequisites of its payload.** Filed FEAT-053 (#369) declares `blocked_by: [316, 321, 347]`: #316 is FEAT-008 (editor decomposition) and #321 is FEAT-019 (Yosys JSON write). Neither appears in this issue&#39;s roster in any grading. #369 cannot land until both do, so this capstone cannot close until both do, and yet nothing here tracks them. Recorded as a risk rather than resolved: adding them to `requires_features` would need a §1 minimality answer neither has (§1 never asks for an in-editor panel or a netlist writer), and adding them to `blocked_by` would be an unmirrored capstone-side edge. **CAP-08 (#304) carries #321 as a required row**, so the two capstones&#39; schedules are coupled through a feature only one of them names.

## 4. System-Level Acceptance Criteria

- **AC-1 — the result type is total and refuses to guess.** `FormalResultTotalityTest` (new; FEAT-053 #369): the result type has exactly three constructors, `PROVED(proofLog) | COUNTEREXAMPLE(model) | UNKNOWN(reason)`, and **no default**. A committed corpus of deliberately uncheckable circuits — a `Memory`, a two-driver net, a combinational loop, an incomplete `TruthTable`, a 24-bit multiplier — each exits 4 or 5. **Written before the solver exists**, so the solver is built against a total contract rather than the contract being fitted to the solver. Not covered by any feature&#39;s own criteria: totality across an adversarial corpus is a property of the composition.
- **AC-2 — every counterexample reproduces.** `CounterexampleReplayTest` (new; FEAT-053 #369, FEAT-034 #347): every counterexample is written as a `-t` file, re-simulated through the batch simulator, and **must reproduce the disagreement**. A counterexample that does not reproduce **fails the build**. This closes the loop between the formal engine and the simulator, which are two independent implementations of the same semantics.
- **AC-3 — port matching refuses ambiguity, and shows its work.** `MiterPortMatchTest` (new; FEAT-053 #369): miter construction refuses on any ambiguity of name, order or width, and **the matched-port table is printed for passing runs too**. A PROVED verdict over a mis-matched port map is a false pass with a proof attached — the most dangerous artifact this capstone can produce.
- **AC-4 — coverage is byte-stable, run to run and across platforms.** `CoverageReportGoldenTest` (new; FEAT-053 #369, FEAT-007 #317): toggle, transition, row and bin coverage over a fixture is byte-identical run to run on one machine **and** across the platform/JDK matrix. Fires KC-09-5 on failure. Spans the report writer, the element enumeration order and the CI matrix; no feature owns all three.
- **AC-5 — an independent witness agrees, with the exclusion set as data.** `DifferentialOracleAgreementTest` (new; FEAT-023&#39;s residual #359, FEAT-034 #347, FEAT-026 #322): an external toolchain and JLS, run over the same design, agree **per retired instruction**, with the exclusion set **stated as data rather than hidden in the comparator**. The CI leg must be confirmed to have actually run, not `Assumptions`-skipped.
- **AC-6 — a verdict carries a budget, and the budget was measured.** Over **the reference submission corpus as defined in §1** — committed, manifested, at least 30 entries per lab problem — record per submission: wall clock, the verdict, and, for UNKNOWN, whether the reason was a resource bound or a structural refusal. The budget divides by measured engine constants on the tracked fixture (`docs/machine-calibration.md:149`, `3.14 × 10⁶ events/s`); any figure derived from ns/node states node count and pass count. Spans FEAT-009 (#335) and FEAT-006 (#354). **It does not depend on FEAT-030 (#362)**, which is beneficial: FEAT-030 would make the budget easier to meet, but FEAT-009 is what makes it measurable, so AC-6 is satisfiable on the required set alone.
- **AC-7 — calibrate against an attestation this project did not write, then against a planted defect.** Two halves, both required.
  - **The calibration half.** Point the whole suite at a design whose correctness is attested by an authority **outside this project and outside this suite**, and observe it clean. Exactly two attestations are admissible, and either alone is sufficient: **(a)** a design imported from a published third-party core that ships its own reference model and firmware — the pinned core of CAP-08 (#304), whose correctness is attested by its author&#39;s reference rather than by anything JLS wrote; or **(b)** any design whose behaviour over the calibration stimulus is independently confirmed by FEAT-023&#39;s (#359&#39;s) external simulator leg (`iverilog`/`ghdl` over the exported HDL), so the attestation comes from a second implementation nobody here wrote. The attestation used, and its source, are recorded in the closing comment.
  - **What is explicitly not admissible, and why.** `test/fixtures/riscv-sum1to10.jls` does **not** qualify as the attestation on its own, though it may serve as a stimulus fixture. Its correctness rests on a golden this project wrote, checked by a reference emulator that `docs/machine-calibration.md:87` records verbatim as &#34;`riscv_ref.py` was written by the same author as the design under test, so it is a self-consistency oracle, not an independent one&#34; — and its regeneration path is already broken (`docs/machine-calibration.md:83`). Calibrating a verification suite against a design whose correctness rests on the same project&#39;s own oracle is precisely the circularity §3 names and this capstone exists to break; the issue as originally filed asserted it as AC-7&#39;s basis, and that is corrected here.
  - **The power half.** Inject the committed mutation catalogue of §1 — a stuck-at, an off-by-one in a control decode, a missing reset, a swapped mux select, at minimum — and observe each caught with a counterexample naming its cone. **Record every defect the suite missed.** This is the half that measures the suite&#39;s power rather than its confidence, and no feature&#39;s own tests can supply it.
  - Spans FEAT-053 (#369), FEAT-023&#39;s residual (#359) and FEAT-034 (#347). **It no longer depends on beneficial FEAT-038 (#326)**, which is why FEAT-038 can sit outside the required set without stranding this criterion.
- **AC-8 — an unfamiliar subcircuit is verified at its boundary.** **Conditional on beneficial FEAT-031 (#325) and FEAT-024 (#360).** If both are funded, take a design containing one subcircuit whose internals are unreadable (black-boxed or fidelity-toggled) and observe a verdict about the *rest* of the design that states the boundary assumption explicitly rather than absorbing it silently. **If either is descoped, AC-8 is struck by an explicit `REPLAN:` and §2&#39;s sufficiency is re-derived without it** — recorded this way rather than as an unconditional criterion because a criterion that can only pass on optional work can never be closed. **Read this against the Recorded DAG walk:** #325 is a declared prerequisite of required #347 and must land before it, so &#34;FEAT-031 is descoped&#34; is not a state this capstone survives — the strike clause protects against a *scope* decision on FEAT-024 (#360), which really is free-standing, more than it does against one on FEAT-031.
- **AC-9 — the false-pass guard.** Take the submission that passes today — wrong on 254 of 256 inputs, right on the one vector `examples/autograde/autograde.py:45,53` checks — and observe it reported **COUNTEREXAMPLE**, with the counterexample replaying per AC-2. This is the single criterion that makes the whole capstone falsifiable against the shipped state of the tree.

## 5. Re-planning Protocol

- **A required feature is descoped or refuted** → re-derive §2 (Required Feature Set &amp; Sufficiency)&#39;s sufficiency and minimality for the reduced set in a `REPLAN:` comment; give orphaned scope a rule-G disposition.
- **A beneficial feature is promoted into the required set, or a required one demoted** → that is a rule-E change, not bookkeeping: the `REPLAN:` moves the row, re-derives its minimality answer (&#34;what breaks in §1 if removed&#34;), **re-prints the required-feature sum in the Cost section**, because the standalone band is defined as that sum, **and adds or removes the corresponding node and composition edge in the mermaid graph**, so the three counts in §2 stay equal.
- **One false pass reaches a user** — a submission reported PROVED that a `-t` vector refutes → KC-09-1. Equivalence is withdrawn from the grading path **permanently**; vectors remain the only supported grader. The `REPLAN:` records the artifact, the root cause, and the withdrawal — this response is not negotiable and not time-limited.
- **The floor slice exceeds 15 mw actual against its 8–11 mw estimate** → KC-09-2. Stop before any sequential tier and ship the combinational capability only. That changes §1 (Outcome Statement) (steps 4 and 6 narrow), so the `REPLAN:` quotes the old and new §1 in full.
- **Either reference corpus is changed after the checker exists** → the numbers KC-09-3, KC-09-4 and AC-6 are measured against move with it. `REPLAN:` records the old and new manifests, re-states the denominators, and re-measures rather than carrying the old figure forward.
- **The checkable subset covers less than 60% of element instances in the reference lab corpus after the flattening elaborator** → KC-09-3. Stop at the coverage half; do not build the formal half. `REPLAN:` re-derives §2 with FEAT-053&#39;s formal scope removed.
- **The UNKNOWN rate on the reference submission corpus exceeds 20%** → KC-09-4: the feature is a demo. `REPLAN:` re-scopes rather than tuning the corpus.
- **Coverage reports are not byte-stable on a single platform** → KC-09-5. Stop. A non-deterministic verdict about someone else&#39;s design is worse than no verdict.
- **The exit-status lattice is extended a second time** → every script written against the first extension is broken. `REPLAN:` records why the one-shot design failed and what the compatibility path is, and must be mirrored onto CAP-06 (#300), which extends the same table.
- **FEAT-026 (#322) lands before FEAT-030 (#362) and moves a golden** → §3 (Cross-Feature Integration Risks)&#39;s byte-identity risk fires. `REPLAN:` re-baselines FEAT-030&#39;s 2.26x claim against the moved corpus and states the new baseline commit, on whichever capstone funds FEAT-030. Note the filed blocks sequence neither against the other, so nothing prevents this.
- **A required feature is filed** → `REPLAN:` moving its scope from `planned_features` to `requires_features` by number, walking that feature&#39;s machine-block edges outward to confirm no path returns to this capstone, recording the walk against the one already recorded above, and regenerating the mermaid graph. **Discharged 2026-08-03 for all eight rows; `planned_features` is now empty and this trigger re-arms only if a REPLAN adds a new planned scope.**
- **A filed feature&#39;s own machine block changes its ordering edges** → re-derive the mermaid graph from the filed blocks and re-run the DAG walk, exactly as the 2026-08-03 REPLAN did. Seven edges this issue drew at filing were withdrawn on that basis and four were added; re-asserting a withdrawn edge means fixing the FEATURE first and mirroring it back here.
- **Any ordering edge is added** → mirror it on both issues in the same `REPLAN:`. An edge drawn at a beneficial feature, at a sibling capstone, or at any issue carried only in `related` is not an edge at all and does not belong in the graph.
