# Issue #596: FEAT-C37-5: the small stuff the incumbents' users waited eight years for lands in catalog-score order — wire coloring, monospace text, viewport polish — and the bucket closes instead of running forever
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

#596 (FEAT-C37-5, serving CAP-37 PF-5) proposes to land the ergonomic "long tail" — wire coloring, monospace text in text elements, zoom/viewport polish — strictly in the score order of a catalog produced by #592, with a per-item 1.5x stop-loss (KC-37-2) so the bucket has a defined end. The stop-loss/score-order containment idea is sound design. The issue is not startable as written: its sole input (#592's catalog) does not exist in the repository, one of its three named deliverables ("wire coloring") is explicitly flagged by the issue's own follow-up comment as unscorable, and the hard decomposition gate (#316/#84) that the issue itself invokes has not landed against a 5,852-line `SimpleEditor.java` that viewport/zoom work would plausibly have to touch.

## Findings, most severe first

**1. [High] The catalog AC-1 depends on does not exist yet — the issue cannot be started as scoped.**
AC-1: "Every item worked here is drawn from #592's catalog and taken in score order; an item with no catalog row is not started." #592 (FEAT-C37-1) is itself open, unimplemented, and its own AC-1 requires publishing the catalog "under `docs/`". A repo scan (`ls docs/`) turns up no parity/ergonomics/catalog document — `docs/` contains `grand-architecture.md`, `extension-points.md`, `file-format.md`, etc., but nothing matching `parity|ergonom|catalog`. Until #592 lands and produces that document, AC-1 cannot be satisfied by construction: there is no catalog to draw from or score against. The issue should either declare itself blocked-by #592 explicitly in the machine block (it currently only lists #592 in `ordering_after`, softer language than a hard block) or be filed as not-yet-fundable.
Recommendation: add `blocked_by: [592]` semantics (or equivalent explicit statement) and do not schedule work until the catalog document is verifiably on the default branch with the per-row owning-feature column the issue's own comment calls for (see finding 4).

**2. [High] "Wire coloring" is a named, gradeable AC-2 item that the issue's own comment says cannot be scored yet.**
AC-2 requires "wire coloring, monospace text rendering and viewport/zoom polish each land or are refused by name with a reason." The issue's single comment (posted the same hour as filing) directly contradicts this being ready: it identifies two incompatible readings of "wire coloring" — (a) colouring by wire *state*, which collides with #542's registry-keyed totality test and #76's 25 CIE76 delta-E floor, or (b) user-assignable per-wire colour (what Digital #1308 actually requests), which introduces durable per-wire state and is a `.jls` format change that #76 §4 invariant 2 forbids for presentation work and that "no CAP-37 issue is scoped to make." The comment concludes plainly: "Neither reading is safe to start from the catalog row as currently described... the row is not scorable, and AC-1 forbids starting it." The issue body was never updated to reflect this — AC-2 still lists wire coloring as a plain deliverable alongside the other two, with no caveat. An implementer working from the issue body alone (not the comment) would not know this item is currently unstartable.
Recommendation: fold the comment's blocking condition into AC-2 itself (e.g., "wire coloring is refused-by-name pending #592's row stating which reading it grades and naming the owning seam") rather than leaving it only in a comment that a future reader might not load.

**3. [High] The SimpleEditor decomposition gate is invoked but not satisfiable by the current codebase, and the issue doesn't explain how PF-5 work proceeds without it.**
The issue states: "no item here lands inside `SimpleEditor`; rendering and viewport behaviour go into the decomposed collaborators #316 produces. If #316 stalls, this feature waits." Verified against the checked-out tree: `src/jls/edit/SimpleEditor.java` is 5,852 lines (`wc -l`), and #316/#84's own tracking confirms the 9-state mouse machine extraction (TASK-0020) has not landed — no `InteractionState`/`MouseMachine` type exists under `src/jls/edit/`, and #84's completion criteria (GoF State objects, zero `switch (currentState)`) are all still open checkboxes. "Zoom/viewport polish" is exactly the kind of behavior that historically lives in `SimpleEditor`'s mouse handlers (`mouseDragged`, `mouseMoved`, per #84's own line citations at L3503/L3736). The issue asserts the gate but gives no account of which viewport-polish items are actually implementable in code that exists *today* outside `SimpleEditor` — it just says the feature "waits" if #316 stalls, without saying whether #316 is expected to land first or whether this issue is effectively empty of startable work until then.
Recommendation: before funding, name — per catalog row — which items are implementable against current non-`SimpleEditor` collaborators (e.g., a pure font-family change in a renderer class might qualify) versus which genuinely need #316/#84 first, so "the feature waits" isn't a blanket answer applied after work has already been miscategorized as viewport-only.

**4. [Medium] Catalog exhaustiveness/disjointness with #593/#594/#595 is only "recommended," not confirmed, which undermines AC-1's implicit disjointness assumption.**
The issue's own comment notes AC-1 ("every item worked here is drawn from #592's catalog... taken in score order") is enforceable "only if #592's rows are both exhaustive and disjoint from #593/#594/#595's scopes," and recommends (not requires) that #592 add "a per-row owning-feature column... so 'the long tail' is defined by subtraction rather than by judgement at funding time." This recommendation has no acceptance criterion forcing it to happen before #596 starts drawing from the catalog. If #592 ships without that column, an implementer funding an item here has no mechanical way to verify it isn't also claimable under #593 (compound selection/wire-segment resolution), #594 (palette search/keyboard nav) or #595 (diagnostics/identifier rules) — risking double-funded or contested work across sibling features.
Recommendation: make the owning-feature column on #592 a precondition of #596's AC-1, not a recommendation living only in a comment.

**5. [Medium] The 1.5x stop-loss (AC-4/KC-37-2) has no defined estimate source, unit, or auditor — gameable in both directions.**
AC-4: "each item carries its estimate and its actual, and any item exceeding 1.5x is stopped, written up and re-scored." Neither #596 nor #592 (which owns "a funding score... express[ing] KC-37-2... as a column") specifies: who sets the initial per-item estimate, in what unit (hours? mw fractions?), or at what point in the workflow (catalog-scoring time vs. pickup time). Without a named owner and a fixed unit, the stop-loss is easy to satisfy on paper while missing its intent — pad the estimate upfront and 1.5x never trips, or lowball it and generate spurious "stop and re-score" churn on trivial items. This is the exact mechanism meant to prevent the "forever-bucket" the issue title warns against, so its looseness is a containment risk, not a cosmetic one.
Recommendation: pin the estimate to #592's funding-score column value at scoring time (immutable once set), state the unit explicitly, and name who is authorized to re-score after a stop-loss trip.

**6. [Medium] AC-2's "refused by name with a reason" sets no bar for reason quality — gameable acceptance criterion.**
"Deferred without a reason is not an outcome" rules out the empty case but not the trivial one: a one-clause reason ("not worth it," "low value") technically satisfies AC-2's literal text while sidestepping exactly the kind of substantive blocker the comment surfaced for wire coloring (format-change implications, delta-E floor interactions). No reviewer or rubric is named to adjudicate whether a stated reason is adequate, so AC-2 could be closed by writing a thin one-liner for all three items and calling PF-5 done.
Recommendation: require refusal reasons to name the specific blocking seam/invariant (as the comment itself models for wire coloring) rather than accept any non-empty prose.

**7. [Low] K9 ("no new default-visible complexity... per-edit and startup cost ratchets") is cited in AC-5 but its mechanical definition is not locatable anywhere in this checked-out repository.**
A repo-wide grep for "K9" across `README.md`, `ARCHITECTURE.md`, and `docs/*.md` returns nothing; the only hits in the tree are other agents' issue-review files referencing the same undefined term. AC-5 asks this feature to hold K9 "unmoved," but there's no artifact in-tree an implementer or reviewer can check the ratchet values against. This may be defined in tooling/CI config not surfaced by a doc grep (e.g., a JaCoCo-style rule), but as an acceptance criterion it should cite where the ratchet lives (file/line) the way #316 and #84 do for the `jls.edit` coverage floor.
Recommendation: cite the concrete artifact (config file, CI check) that encodes K9's ratchets, or drop the reference if none exists yet.

## What's solid

- The core containment mechanism — fund strictly in catalog-score order, per-item 1.5x stop-loss, refuse rather than silently defer — is a well-aimed answer to the real risk named in the title (ergonomic polish becoming a forever-bucket). One line, and correct.
- The `SimpleEditor`/#316 hard-gate boundary (KC-37-1) is the right instinct given #84's documented history of the file growing while extractions "succeeded" — refusing to add more inline surface to a 5,852-line god class is consistent with the codebase's own stated lessons.
- Explicitly disclaiming dark mode / subcircuit dive / rebindable keys as #570's territory (not re-litigated here) is a clean scope boundary and matches #570's own body.
