# Issue #640: TASK-C598-2: an un-exportable element and an absent tool are both caught before the cable is touched — each named with its role, its source and nothing left on disk
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

TASK-C598-2 asks for two refusal classes (un-exportable element, missing
external tool) to be surfaced with actionable reasons before any board-flow
stage runs. The intent is sound and consistent with its parent (#598) and
sibling (#638/TASK-C598-1), but the issue leans on infrastructure that does
not exist on `master` and points its own escape hatch at a closed issue. As
written, AC-1 is not implementable today and the issue does not disclose
that.

## Findings, most severe first

**1. (High) AC-1 depends on a rejection-reason map that does not exist on `master`, and the dependency is undeclared.** The issue states: *"the reason lives in the exporter's rejection map (#492), and this task's job is that the board flow surfaces it rather than flattening it into 'export failed'."* I checked `src/jls/hdl/HdlExporter.java:176-196` directly: the offender arm is still `offenders.add(describe(el));` — no `REJECTED` map, no `classifiedElementClasses()`, no reason storage anywhere in the class. #492 is **open**, and its own most recent comment (2026-08-08, same day I'm reviewing) says this explicitly: *"The reading to hold: the REJECTED map, its reason strings and the totality test exist only as the proposed diff in this issue body... Anyone who encounters them cited as present is reading a branch-only artifact."* That comment was written specifically to correct two other issues (#385, #384) that made the exact same mistake #640 makes here — citing #492's proposed map as shipped code. #640's own `ordering_after: [264, "TASK-C598-1"]` does not list #492, so nothing in the task's stated sequencing surfaces this gap. AC-1 ("asserted on the specific text... carried through from the exporter's rejection policy") cannot be satisfied until #492 lands, and #492 itself flags open questions about whether its reason strings (e.g. `FieldExtend`'s unverified workaround) are even correct. *Recommendation:* add `492` to `ordering_after`/`blocked_by`, or descope AC-1 to only the elements #492 will not touch, or absorb #492's scope into this task and re-estimate `band_mw` accordingly.

**2. (High) AC-1's escape valve points to a closed issue.** *"An element wrongly judged un-exportable is filed on #59, not fixed here."* Issue #59 was closed `not_planned` on 2026-08-03T16:03:33Z — the day **before** #640 was filed (2026-08-04T15:11:52Z). #59's HDL-export-policy successors have since been re-homed: #492 (the rejection-map fix) now reports its parent as #315, not #59, and #492's most recent comment files a *new* successor issue (#873) for exactly the "wrongly refused element" disposition question #640 is routing to #59. Filing against a closed, `not_planned`, superseded parent is either a dead link or (charitably) means "reopen #59," which the issue doesn't say and which contradicts the closure. *Recommendation:* repoint AC-1's escape valve to #873 (or whatever the current live successor is at pickup time) and re-verify before the task starts, since this tree is visibly still being reorganized.

**3. (Medium) AC-3 assumes an integrated preflight-before-export pipeline that has no code seam today.** AC-3 requires a test asserting "no export, no constraint emission and no toolchain invocation occurs when the preflight fails." At `master`, export (`jls -export`, Java, `JLSStart`/`HdlExporter`) and the toolchain preflight (`scripts/icestick-handoff.sh`, bash) are two separate, sequential CLI invocations with no shared pipeline object — I found no `BoardFlow`/stage-abstraction class anywhere under `src/jls/hdl/board/` (only `Board.java`, `Boards.java`, `PcfEmitter.java`, `PinBindings.java`). Today the *toolchain* preflight already runs before synthesis/P&R/flash (that part is real, per `docs/icestick-bitstream-handoff.md:31-35` and `scripts/icestick-handoff.sh`), but by the time that script runs, `design.v`/`design.pcf` have *already* been written by a prior, separate `jls -export` call — so "no export... occurs when the preflight fails" is not true of the current architecture and can't be tested against it without first building the unifying flow AC-3 presupposes. This mirrors a finding independently raised against sibling issue #643 (`issue-reviews/issue-0643.adversarial.md:15`) about the same missing stage-seam. Also relevant: the GUI half this eventually feeds (#598's "FEAT-C38-1... PF-1 GUI board flow", filed separately as #597) is itself open and unimplemented — confirmed by another reviewer's grep for `BoardPicker`/board-selection widgets (`issue-reviews/issue-0647.adversarial.md:15`) turning up nothing. The task does say diagnostics should be testable headlessly ahead of the GUI, which is fine, but AC-3 as worded needs a concrete integration point (what calls export, what calls preflight, in what order) that doesn't exist and isn't specified here. *Recommendation:* either scope the unifying "board flow" entry point explicitly in this task (and re-estimate `band_mw`), or narrow AC-3 to what's actually testable now: the toolchain preflight already gates toolchain stages; a new headless test would need its own invocation order (export → preflight → toolchain) to be introduced by this task, and the issue should say so.

**4. (Medium) AC-3 is gameable as worded.** "A test asserts no export, no constraint emission and no toolchain invocation occurs when the preflight fails" can be trivially satisfied by unit-testing an isolated `preflight()` function that returns a boolean/exception and asserting a side-effect counter stayed at zero — without ever wiring that preflight into the real invocation order of a "board flow" that (per finding 3) doesn't exist yet. Nothing in the acceptance criteria requires the test to exercise the *actual* export → preflight → toolchain sequence end-to-end; a narrow unit test of the preflight in isolation would pass while the real flow (once #597's GUI lands) could still call export first. *Recommendation:* require the test to invoke the same entry point the eventual GUI flow will use (or explicitly declare that entry point doesn't exist yet and this task must create it), not just the preflight predicate in isolation.

**5. (Medium) The "#91-class silent toolchain failure" anti-pattern citation is ambiguous and, read literally against this repo, wrong.** The issue says: *"Logisim-Evolution's #91-class silent toolchain failure is the named anti-pattern."* In **this** repository, issue #91 is "Automated UI test harness (P5 residual): retire display-suite retry masking and produce the 20-run zero-flake record" — a test-flake-discipline task with no connection to toolchains, silent failures, or Logisim-Evolution. The phrasing "Logisim-Evolution's #91" presumably means issue #91 in Logisim-Evolution's own tracker, but that is (a) unverifiable from within this repo/session and (b) exactly the kind of bare cross-repo issue-number reference that collides with this repo's own #91 for any reader or tool that resolves `#91` against `anadon/jls` by default (as GitHub's own UI would if this text were rendered here without qualification). *Recommendation:* cite the external issue with a full URL, not a bare `#91`.

**6. (Low) "Extends and surfaces" the bash preflight without specifying the mechanism.** The task says the missing-tool preflight "already exists for the iCEstick handoff... this task extends and surfaces it rather than rebuilding it," but doesn't say *how* a Java-side board flow surfaces a check whose only implementation today is inside `scripts/icestick-handoff.sh` (bash). Two very different designs satisfy that sentence: (a) reimplement the same tool-presence checks in Java (risking drift between two independent preflight implementations of the same tool list), or (b) shell out to the script (or a `--check`-only mode of it) and parse its output/exit code from Java. The issue doesn't pick one, and the two have materially different testability and failure-mode properties for AC-2/AC-3. *Recommendation:* name the mechanism explicitly, or flag it as an open question the way the task's siblings (#492, #264) do.

## What's solid

- AC-2's "one all-or-nothing preflight... every missing tool in one pass" matches real, already-landed behavior in `scripts/icestick-handoff.sh` (preflight block, `--flash`-gated programmer check) and `docs/icestick-bitstream-handoff.md`'s prerequisites table — this half is not invented.
- AC-4's `--flash` distinction ("programmer required only for flashing") is accurately described against the script: the programmer-tool check is explicitly gated behind `FLASH=1` at `scripts/icestick-handoff.sh:117-126`.
- The aggregation discipline this task is asked to reuse (rather than re-derive) is real and precedented: `PcfEmitter`'s unbindable-port aggregation (`src/jls/hdl/board/PcfEmitter.java:109-118`) already joins multiple errors into one thrown exception, so AC's "one pass, not one per run" framing has a working model to copy.
- Scope boundary against #59/#492 (declining to fix wrongly-judged-un-exportable elements here) is the right call in principle — the routing target is just stale (finding 2).

## Verdict rationale

`needs-rework`: two of the four acceptance criteria (AC-1, AC-3) rest on
infrastructure that is either unimplemented (#492's rejection map) or
architecturally absent (a unified export→preflight→toolchain flow), and one
of the issue's own scope-boundary pointers (#59) resolves to a closed,
superseded issue as of the day before filing. None of this is fatal to the
task's goal, but the issue should not be picked up as scoped without first
resolving the #492 dependency and naming a concrete integration seam for
AC-3.
