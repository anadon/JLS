# Issue #776: TASK-C588-2: the timing-honesty note publishes, sourced to CircuitVerse's and Logisim-Evolution's own reports of their timing behaviour
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

A 0.5-1 mw task to write `docs/comparisons/timing-honesty.md`, citing five external issues (CircuitVerse #1412, #5328, #1753, #2198; Logisim-Evolution #2454) plus at least one named JLS disadvantage. The scope is narrow and the tone requirement ("quoted back at us without embarrassment") is a genuinely good discipline. But the acceptance criteria have a real reachability gap, a broken/misapplied dependency, and no enforcement mechanism for the one criterion (word count, "checked against" freshness) that would actually catch a corner-cut implementation.

## Findings, most severe first

### 1. AC-1's "reachable from the docs site" names infrastructure that does not exist, and nothing tests it
Quoted: "The note is in tree at a published path, under ~2500 words... (AC-1)" — AC-1 is inherited near-verbatim from parent #588's "in-tree and reachable from the docs site." Checked in this tree: `.github/workflows/` has `ci.yml`, `codeql.yml`, `mutation.yml`, `release.yml`, `repro-installers.yml`, `scorecard.yml` — no Pages/deploy job. There is no `docs/README.md`, `docs/index.*`, or any table-of-contents file linking the ~20 files already in `docs/`; the only cross-linking is ARCHITECTURE.md's own "Documentation" section, and it does not enumerate a `docs/comparisons/` slot. A prior review of a related issue (`/home/user/JLS/issue-reviews/issue-0574.adversarial.md`) independently confirmed the identical absence of any Pages workflow. As written, "reachable from the docs site" is satisfiable by literally any interpretation an implementer chooses (a raw GitHub blob URL counts; a link from README counts; nothing at all could plausibly be argued to count too, since no test enforces it) — this is a gameable, unfalsifiable acceptance criterion. **Recommendation:** either define "docs site" concretely (e.g., "linked from README's Documentation section and from a `docs/comparisons/README.md` index") or drop the reachability clause and keep only "in tree at a published path," which is the part that's actually checkable.

### 2. The cited evidence base is not in this checkout, so the citations can't be checked against anything local
Parent #588 sources its "required starting set" from `docs/reviews/evidence/2026-08-niche-survey/circuitverse.md` and `logisim-evolution.md`. Grepping and `find`-ing this repository (`/home/user/JLS`) for `docs/reviews`, `niche-survey`, `circuitverse.md`, `logisim-evolution.md` turns up nothing — per #510's own text those files live only on branch `claude/jls-project-review-505pnf`, which is not merged here. So the implementer of #776 has no in-repo checkpoint to verify the five cited issue numbers against; they are re-deriving citations from a synthesis-of-a-synthesis (#776 quotes #588's summary of #510's summary of an off-tree evidence file) rather than from a committed source. For a task whose entire acceptance test is "every claim is cited... accurately" this is a real provenance gap: a wrong issue number, a stale status ("#2454" may since have been fixed or renumbered upstream), or a mischaracterized claim would sail through review because there is no local artifact to diff against. **Recommendation:** land (or explicitly re-cite) the niche-survey evidence files in-tree before or alongside this task, or require the note's own citations to link directly to the competitor issue URLs (not just bare `#nnnn` numbers) so at least the reader can verify independently.

### 3. `ordering_after: [300, 512]` is a mismatched copy from the parent feature — one entry is irrelevant, the other more-relevant one is missing
Quoted from #776: `ordering_after: [300, 512]`. Confirmed via #588 (the parent): its combined ordering list is `[300, 512, 560]`, and 588 explains #300's rationale as "the grading verdict must exist as shipped behavior before a note can compare it" — that justification is specific to the **grading-determinism** note (its sibling task, confirmed by search to be #774, "TASK-C588-1"), not to the timing-honesty note #776 is about. #776 has nothing to do with grading determinism or CAP-06. Meanwhile #560 (FEAT-C28-4, the cross-tool perf harness) — the actual dependency for #776's own AC "Performance numbers, if any, cite #512 / #560" — is dropped from #776's `ordering_after` even though it's named in #776's own acceptance criteria. This reads as an unedited copy-paste from the feature's combined list: a spurious hard blocker (#300, a large CAP-06 grading capstone, currently open) sits in the way of a task that doesn't need it, while a criterion the task does reference (#560) carries no ordering guarantee at all. **Recommendation:** set `ordering_after: [512]` (and `[560]` only if the note ends up quoting a performance number; drop #300 entirely), or explain in the task body why grading capstone #300 actually gates a timing note.

### 4. AC-1's word cap and "checked against" freshness line have no enforcement, unlike this repo's usual pattern
"under ~2500 words" (note the "~") and "a dated 'checked against' line" are prose-only requirements with no test analogous to `HelpTopicsTest`'s link-checker/completeness checks that ARCHITECTURE.md documents for other docs surfaces, and no CI lane comparable to `mutation.yml`'s gate is proposed for this doc. A reviewer skimming for the literal AC could pass a note that is far over 2500 words (the "~" gives cover) or that carries a "checked against" line with a plausible-looking but unverified date. Given finding #2 (no local evidence to check against), this is exactly the kind of criterion that could pass while the real goal — a note that survives outside scrutiny — fails. **Recommendation:** add a lightweight word-count assertion and a regex check that the "checked against" line names a parseable date and at least the five required issue references, mirroring the discipline `HelpTopicsTest` applies to help content.

### 5. Ambiguous relationship among the three CircuitVerse citations
Quoted: "CircuitVerse #5328 with #1753 and #2198." The word "with" doesn't specify whether #1753/#2198 are duplicates, earlier reports of the same bug, or distinct-but-related bugs (contention errors vs. wrong Verilog-subcircuit assignments, per #588's fuller description, are two different claims bundled under one citation group here). An implementer who cites all three as one undifferentiated blob risks either double-counting one bug as three data points or mischaracterizing three distinct failures as one — exactly the kind of imprecision the issue's own stated bar ("quoted back at us without embarrassment... accurate") is meant to rule out. **Recommendation:** the task body should state explicitly what each of the three numbers documents, as #588 partially does ("contention errors thrown wrongly/cryptically; embedded Verilog subcircuits produce wrong assignments") — #776 as filed strips that detail and leaves only the bare numbers.

### 6. Interim-integrity gap versus the parent's AC-2 (minor, sequencing risk)
Boundary note: "Prose and citations. Appendices and freshness are TASK-C588-3" (confirmed as #778, open). Parent #588's AC-2 requires "Each note ships an appendix... a reviewer running that command... obtains the output the note quotes." If the timing-honesty note makes any claim about JLS's own timing behavior (plausible, since the Outcome text is "what a simulator claiming to model time owes its users, and what the alternatives actually do" — a comparison implies a JLS side), then between #776 landing and #778 landing, the published note contains unappendixed JLS claims, which is non-compliant with its own parent's bar. This may be an acceptable, explicitly-scoped intermediate state, but the task doesn't say so — it's worth one sentence making the interim state deliberate rather than accidental.

## What's solid

- The outcome is genuinely well-scoped and narrow (five citations, one named JLS disadvantage, no re-measurement of performance) — a good example of a task-sized slice.
- "Performance numbers, if any, cite #512 / #560 rather than being measured here" correctly avoids scope creep into re-benchmarking.
- The tone bar ("respectfully worded, and naming where a competitor's timing model is better than JLS's") is a real, checkable-by-a-human requirement and a good discipline against marketing-speak.
- The task correctly defers appendices/freshness to a separate task (#778) rather than bundling everything into one PR.

## Verdict rationale

Not `should-not-proceed` — the core work (write a short, sourced note) is real and valuable. Not `sound` — AC-1's docs-site clause is currently meaningless in this repo, the `ordering_after` list is demonstrably wrong (irrelevant blocker present, relevant one absent), and the citation chain traces back to an off-tree evidence file this checkout doesn't have. These are fixable with small edits to the issue text, not a redesign, hence `needs-rework` rather than `sound-with-concerns`.
