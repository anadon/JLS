# Issue #443: TASK-0027: all five installer legs become required checks, the bundled Wayland runtime is pinned by digest, and every OS asserts the .jls association README already claims
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what the issue gets right

Before the attack: the factual observations (O1–O10) are all independently verifiable against the current tree and check out exactly as cited — `scripts/build-installer.sh` is 514 lines, four of five `installers` matrix legs in `.github/workflows/release.yml` carry `experimental: true` (lines 300/303/307/310) under `continue-on-error: ${{ matrix.experimental }}` (line 312), both `JBR_SHA256` values are literally `UNVERIFIED-PLACEHOLDER-fill-in-real-sha256-see-issue-101` (lines 298–299), `--file-associations` is wired at lines 363/409/477, README.md:48 does state the `.jls` association as an unqualified cross-platform fact, and only the Linux smoke step (release.yml:453–470) touches the mime association — msi (490–511) and dmg (513–525) install/launch/uninstall but never query the association. `test/jls/InstallerMatrixPolicyTest.java` does not exist yet and `CliFlagTableTest.java` (the idiom it's modeled on) does. This is unusually well-grounded fact-finding.

## Findings, most severe first

**1. (Critical — duplicate/conflicting work item already filed and tracked elsewhere) This task substantially re-files work that already exists as two open, more specific sub-issues of #82, and the issue never names them.** #82 has real GitHub sub-issues #284 (*"Installer verification: first green msi/dmg install → launch → .jls open on real runners, then retire the experimental flags"*) and #285 (*"Linux installer runtime: arm the pinned JBR sha256s and Wayland-verify a JBR-bundled deb"*), both `has_parent: true` pointing at #82, both open since 2026-08-02. #284's own predictions are P1 "trigger a dry-run; observe green … windows-latest and macos-latest, run IDs recorded" and P2 "double-click a sample `.jls`, observe it open" — this is #443's P3/P5/P6 verbatim. #285's predictions are P1 "armed pins … logs the JBR-image line instead of the fallback warning" — this is #443's H2/P7 verbatim. The parent feature #338 (filed the same day as #284/#285, one day before #443) says so explicitly in its own Related Work section: *"#284 — … Substantially overlaps TASK-0027 and should be resolved as that task's issue rather than duplicated"* and *"#285 — … Substantially overlaps TASK-0027's digest half."* Yet #443's own `related:` list is `[338, 82, 101, 111, 265, 188, 184, 134]` — #284 and #285 are absent, and §12 Related Work never mentions them either. Filing #443 as a fresh, unlinked issue creates exactly the "unordered pile of open distribution issues" that #338's abstract says it exists to fix — now with three issues (#82's two sub-issues plus #443) claiming the same residual, no `blocks`/`blocked_by` edge between them, and a real risk of two executors independently editing `release.yml`'s matrix flags and `build-installer.sh`'s digest constants and colliding. **Recommendation:** before any work starts, either close #443 as a duplicate and continue the work under #284/#285, or explicitly supersede #284/#285 from #443 (and #338) with a recorded disposition, per #338's own re-planning protocol which requires "no dangling owners."

**2. (High — internal contradiction on sequencing between #443 and its own parent) #443's recommended flip strategy contradicts #338's explicit sequencing guidance.** #443 Open Question 1 recommends: *"one commit flipping all four flags, so a revert is one commit."* But #338 §6 (Sequencing & Parallelism) says: *"Within TASK-0027 the five legs are mutually independent and can be armed one at a time as each goes green on a real run … A scheduler may arm them in any order."* A single-commit batch flip is the opposite of arming legs incrementally as each is independently verified — it means a genuine, isolated failure on (say) `windows-11-arm` blocks promoting the three legs that are actually fine, or worse, tempts the executor to flip all four before all four have individually gone green (violating H4's own stated safety condition: promotion is safe *only after* a green run *of that leg*). The task should pick one strategy and state it consistently with its parent, not carry both.

**3. (High — the acceptance criterion for the existing single-OS "check" it wants to extend is not actually a hard gate, undermining P5/P6 as written) The Linux mime-association assertion the issue calls "already asserted" is soft-fail, not a hard check.** release.yml:465–469: if `xdg-mime query default …` doesn't return `jls-JLS.desktop`, the step does not fail — it emits `::warning::` and continues (*"no desktop-menu provider on this runner … the mime type, icon, and launcher are still verified above"*). So O8's framing — "the deb leg already checks the mime association" — overstates what exists: today even the one OS the issue holds up as the model produces a *soft* signal, not a fail-closed one. P5/P6 as written ("assert it resolves to JLS … observe it is gone") are silent on whether a runner-environment gap (no registered file-manager/URL handler on a minimal Windows/macOS runner image) should also degrade to a warning, and if it does, "gameable" describes exactly what could happen: a msi/dmg association assertion added in the same soft style as the Linux one would make P5/P6 pass on every run regardless of whether the association actually works, which is the same failure mode §11 warns about for log-text assertions ("a smoke test that greps the log for its absence passes trivially") but the issue does not apply that same scrutiny to its own P5/P6. **Recommendation:** explicitly state whether the msi/dmg association checks must be hard-fail (unlike the current deb one), and reconcile the deb check's soft-fail status against O7's blanket README claim in the same pass — right now the README asserts the property as fact on a check that only warns.

**4. (Medium — README claim is already internally inconsistent, which the issue's fix doesn't address) O7 quotes README:48-50 as an unqualified claim, but the same install section already qualifies it for AppImage two bullets above.** README.md:22-24: *"The `.jls` association comes along only if your desktop integrates AppImages (e.g. via AppImageLauncher)"* — i.e. the README already narrows the claim for one Linux packaging format while stating it as unconditional fact at line 48. The issue treats README:48-50 as a single flat promise to be "asserted on all three OSes," but the promise is not actually flat today; the fix should either preserve the existing per-format qualification or explicitly decide to drop it, and the issue's Method (§8) and Completion Criteria (§14) don't mention the AppImage carve-out at all.

**5. (Medium — feasibility risk repeated from #285 without adding anything, presented as if novel) The JBR-digest work is entirely gated on an environmental blocker (`cache-redirector.jetbrains.com` unreachable, 403 from the egress proxy) that #285 has already been sitting on since 2026-08-02 with no resolution recorded.** #443 restates the same requirement ("must be obtained outside CI … from an unproxied machine") as if it were new scope, but supplies no new mitigation, no fallback plan if the blocker persists, and no owner for actually reaching an unproxied machine. If #285 has been blocked on this for a week, #443 inherits the same block silently — Hypothesis H2 and Prediction P2 are simply unfalsifiable until someone off-issue actually gets network access, and neither the Materials (§6) nor the Method (§8) name who does that or by when.

**6. (Medium — TASK-0015, a stated prerequisite, may not exist as a filed issue) The issue leans on TASK-0015 ("explicit workflow timeouts, being filed concurrently") as the reason promotion is risky without it, but never gives it an issue number, and the current tree confirms the underlying problem: `grep -n timeout-minutes .github/workflows/release.yml` returns nothing — no job in the entire release workflow has a timeout.** The issue correctly treats this as a real risk (§11: *"the single largest operational risk in this task"*) and sequences around it ("strongly advised before promotion" rather than `blocked_by`), which is honest — but "strongly advised" is not enforced anywhere in §14's Definition of Done; nothing in the completion criteria actually requires TASK-0015 to have landed, or requires the executor's confirm-or-record step (§8, first checklist item after the read-the-script step) to block promotion if it's absent. As written, an executor can tick "confirmed TASK-0015 has not landed, recorded here" and proceed straight to flipping all four experimental flags anyway, which is exactly the six-hour-stall-blocks-a-release scenario §11 warns about.

**7. (Low — untestable/manual-only acceptance criterion for macOS) P6 and Open Question 4 admit the macOS `.jls` binding query is unresolved empirically ("no option is recommended here because the answer is empirical").** That's honest framing, but it means one of the six numbered Predictions in a task whose whole premise is "replace #82 §7's manual matrix with a recorded run" may have no automatable form at all, and the issue's own Falsification Criteria (§10, H3 refuted branch) concedes the fallback is to narrow the README rather than deliver the check. A task whose central selling point is "turns a hand ritual into a workflow run" (Abstract, Intended Audience §4) should not have a load-bearing prediction it already expects might not be automatable.

**8. (Low — scope-creep risk flagged but not fenced) The digest-mismatch-must-hard-fail requirement (Open Question 2, §7.11) is new behavior beyond what #285 (the issue that actually owns "arm the pins") asks for.** #285's own predictions only require the armed pins to produce a JBR image and a green smoke test; it does not require a *mismatch* (as opposed to a placeholder) to become a build failure. #443 adds this as "a deliberate behaviour change" with no test coverage requirement beyond P7's "assert by a recorded property," and no explicit unit/CI test that intentionally corrupts a digest to prove the new failure path exists (contrast with #338 IC-5's explicit "run the verification job against a deliberately unsigned msi" null test for signing) — the equivalent null test for "digest mismatch fails the build" is not in §5's Predictions or §14's Completion Criteria at all, despite the issue's own §11 warning that "a leg that has been silently failing … will look like a regression."

## Verdict rationale

The factual grounding is excellent and the write-up is unusually rigorous for a CI-only task, but Finding 1 is disqualifying as filed: this issue duplicates two already-open, already-more-specific sub-issues of #82 (#284, #285) without acknowledging them, creating three competing trackers for the same edits to the same two files. Findings 2–3 are real internal contradictions (with the parent feature's sequencing guidance, and with the issue's own standard for what counts as a non-gameable check) that should be resolved before an executor starts. The rest are real but survivable if the duplication and sequencing issues are fixed first.
