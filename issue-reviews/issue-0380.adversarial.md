## Findings, most severe first

**1. The issue's own evidentiary anchor is not on the default branch, contradicting its own closing gate — CONFIRMED.** `evidence_commit: 2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7` is declared at the top, and `git merge-base --is-ancestor 2d0ca9d HEAD` returns false — it lives only on a working branch. Issue #493 (filed the day after #380, "The evidence_commit every filed issue declares … is on a branch that will be deleted") confirms this in detail and gives the durable master pin `8288226`. Issue #380's own comment (2026-08-08) acknowledges the correction. Yet §14 Completion Criteria demands: *"Every cited evidence document and permalink resolves on the default branch at close — no branch-path links, no deleted docs."* The issue holds its own future PR to a bar its own filing does not meet at creation. Practically the damage is contained — #493 §1 shows the seven files that actually differ code-wise don't include anything #380 cites, so #380's `src/`/`test/` line citations happen to survive a relabel — but a picker-upper who trusts the body's `2d0ca9d` literally (rather than finding the correcting comment or #493) will chase dead permalinks once the branch is deleted. **Recommendation:** edit the issue (or pin a comment prominently, not buried as comment #2 of 2) to state `evidence_commit: 8288226...` before work starts, and re-verify the `docs/file-format.md` §8 citation specifically — #493 flags that file as one of two non-code documents that differ in content/line numbers between the two commits, and #380 cites `docs/file-format.md §8` for the `ElementId` stable-key contract.

**2. `blocks: []` in the machine block is stale and superseded only by a comment, not the body — CONFIRMED.** Status & Dependencies declares `blocks: []` with the note "no filed feature declares this a prerequisite; its beneficiary is #296 via the parent feature's composition edge." A later comment (2026-08-08) retracts this: *"DOWNSTREAM CONSUMER RECORDED … `blocks: [739]` … was `[]`… That note was true when this issue was filed and stopped being true when the CAP-26 accessibility cluster landed."* This is exactly the kind of drift the issue's own template is designed to prevent via `REPLAN:`/mirrored-edge discipline elsewhere in the corpus, yet here the body was never edited — a scheduler reading only the machine block (which is what the YAML front matter is for) will miss that #739 now depends on this landing first, and will not know to sequence accordingly. **Recommendation:** edit the `blocks:` line in the body directly rather than relying on a comment to carry a load-bearing scheduling fact.

**3. O1's own "measured" evidence table has a factual/classification error — CONFIRMED.** O1 states: *"The only accessibility calls anywhere in `src/` are `setAccessibleName` on individual widgets — nine call sites across five dialog classes and two in `SimpleEditor`."* Actual count at HEAD (`grep -rn setAccessibleName src/`) is **10** total, not 9+2=11: `KeyPad.java` (3 sites), `MemoryDialog.java` (2), `SigGenDialog.java` (1), `TextDialog.java` (1), `ElementFormDialog.java` (1) = 8 outside `SimpleEditor.java`, plus `SimpleEditor.java:2412-2413` (2) = 10. Worse, the classification is wrong, not just the count: `KeyPad` (`src/jls/KeyPad.java:15`, `public final class KeyPad extends JButton`) is not a dialog class at all — it's a keypad widget — so "five dialog classes" over-counts by at least one. This is a small thing individually, but O1 is presented as *the* rigorously "measured" evidence anchoring the whole task's premise ("measured below" is used as a rhetorical guarantee), and it doesn't survive a two-minute grep. It doesn't change the conclusion (the canvas genuinely has zero accessible children), but it undercuts the issue's implicit claim that every number in it has been checked. **Recommendation:** fix the count/classification before using this issue as a citation source elsewhere (it already is — #380 is cited by #739, #756, #758, #753/#754).

**4. Bundling four largely-independent verification problems into one task is a real feasibility/scope risk, softened but not eliminated by H2 — PLAUSIBLE.** The task packages: (a) a new `AccessibleContext` scene model over the canvas (genuinely new, nontrivial code with a totality contract over `ElementRegistry.all()`), (b) a modal-dialog-worker-thread test mechanism used for both accelerator inertness and three popup ops, (c) a `Robot`-driven Alt-navigation spike that the issue itself rates as "most likely to be replaced by a bound rather than satisfied," and (d) promoting/adding faithful-keyboard test classes to the `macos-gui` CI job (a distinct-platform, distinct-toolchain change). H2 argues (b)'s two consumers share one mechanism, which is reasonable, but (a), (c), and (d) don't reduce to each other — they're three unrelated risk profiles (new production code + coverage floor, flaky UI automation, and CI-lane surgery on a job that is `continue-on-error: true` at `.github/workflows/ci.yml:598`, confirmed) shipped under one Definition of Done with 17 checklist items. A partial landing (e.g., scene model ships, Alt-navigation gets bounded instead of tested, macOS lane deferred) is plausible and the issue's own falsification criteria anticipate some of this, but the DoD doesn't say which subset is an acceptable partial close versus which blocks the whole task. **Recommendation:** either explicitly rank (a)-(d) as independently closeable sub-milestones with their own merge boundary, or accept that this ships as one large PR touching production code, four new test classes, a CI workflow file, and a verification doc — and say so as a stated cost.

**5. The `blocked_by: [316]` dependency is real but the issue's "waive it" escape hatch is more load-bearing than it appears — PLAUSIBLE.** The issue candidly states execution is not blocked (tests can be written today) but "durability" is, and that if a scheduler runs it early anyway, "item 1's coverage has no floor until #316 lands, and item 1 lands outside the decomposition seam and must be moved." #316 (open, feature-tier) is itself a large, multi-task, currently-unstarted feature (`planned_tasks` all "not filed") with its own `blocked_by: [317, 337]`. So the realistic scheduling outcome is: either #380 waits on a feature-sized dependency chain of unknown length, or it proceeds now and *guarantees* a second migration cost later ("must be moved" — stated as fact, not risk). The issue is honest about this, which is a point in its favor, but the Completion Criteria checkbox — *"`blocked_by` #316 has landed, or the dependency was waived per rule 10 with the two costs named in Status & Dependencies recorded as accepted"* — makes waiving procedurally easy (two lines of acceptance) relative to the actual cost (new `jls.edit` code with no coverage floor, sitting in a file already flagged at 5,852 lines against #84's stale 4,119-line title). A maintainer skimming the checklist could tick this box without weighing that cost seriously. **Recommendation:** treat this as a real go/no-go decision, not a checkbox — the issue would be stronger if it stated a default (block vs. proceed) rather than leaving it fully open.

**6. Acceptance criteria for P6 (Alt-navigation) and Open Question 5 (screen-reader pass) are structured to be hard to fail — worth flagging, not fatal.** P6/H4: *"Attempt it once, timeboxed; if reruns do not absorb the flake, record the bound with the flakiness data. Either outcome replaces the current deferral paragraph."* This is honest framing (an explicit non-pass is an allowed outcome), but it means the task's Definition of Done cannot be failed by Alt-navigation being genuinely infeasible — every branch of the decision tree closes the checklist item. Similarly, Open Question 5 lets the executor pick *any one* of Orca/NVDA/VoiceOver for the mandatory manual screen-reader pass, on any one platform, with no criterion for what "passes" means beyond "recorded." Given §11's own admission that *"a passing accessibility test is not a working screen reader… None of those bridges is exercised here,"* the one piece of evidence meant to close that gap has no pass/fail bar — a screen reader emitting garbled or unhelpful output during the pass would, on a literal reading, still satisfy "one manual pass … recorded" as long as the platform and tool are named. **Recommendation:** add an explicit success criterion for the manual pass (e.g., "reader announces role and name for at least N of the M elements in the fixture circuit, unprompted") rather than leaving "recorded" as the only bar.
