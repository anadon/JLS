- Lens: adversarial

- Reviewer: Claude Sonnet 5

## Summary of the ask

A "capstone" (tier:capstone, 5-9 mw, "writing-heavy, engineering-light") whose deliverables are: two published comparison notes with runnable appendices (PF-1), a grading-contract white paper (PF-2), a positioning statement + release-announcement discipline (PF-3), and an actual submission to a peer-reviewed CS-education venue (PF-4). Filed 2026-08-04 by the same review pass that produced #508 (product/direction review) and #510 (niche comparison survey), which it cites as its evidence base.

## Findings, most severe first

**1. AC-4 is not achievable by engineering effort at all, and the band ignores that.** "One venue submission actually submitted" (SIGCSE/WCAE/ASEE-class, PF-4, 1.5–3 mw) is gated on external, calendar-fixed CFP deadlines and on human co-authorship — the issue itself says PF-4 is "co-authored with the #509 pilot if it materializes." #509 states the WashU adoption is conditional ("interested… if it becomes well enough matured" — not a commitment) and KC-36-2 already concedes the co-authorship may not happen. A capstone whose headline AC depends on hitting an annual conference deadline with an uncommitted co-author, priced only in writer-hours (mw), understates the real bottleneck: this can slip a full year past any mw estimate if the nearest CFP window is missed, independent of effort spent. Recommend: split PF-4 into its own issue with a concrete target venue + CFP date, or drop AC-4 from this capstone's must-close set and track it as best-effort.

**2. Acceptance criteria are self-graded — nothing in AC-1/AC-2/AC-4 is machine-checkable.** "Reproducible from its appendix by a third party" (AC-1) and "actually submitted" (AC-4) have no defined verifier, reviewer, or CI gate. Compare to this repo's own culture: `BatchSimulationGoldenTest`, `HeadlessCoreRatchetTest`, `NotificationRatchetTest` (ARCHITECTURE.md "Test layout") turn every other stability contract into an enforced test. Nothing stops an author from writing "reproducible" in the note without anyone having reproduced it. Recommend: require each appendix's exact command to run in CI as a doc-golden test (the same discipline the batch-interface docs already get), and require AC-4's evidence to be a link (submission confirmation / EasyChair receipt), not a checkbox.

**3. The capstone bypasses #508's own planning-ratchet rule with same-day evidence of the violation.** #508 (filed 2026-08-03, one day before #520) states as a process finding: *"Planning ratchet: no new tier:feature/tier:task until two capstones close."* At the time #520 was filed (2026-08-04) the only capstone dispositions in #508's own table are "Closed (not planned)" for CAP-03 and three "Merged (duplicate)" entries — none is a completed capstone. Yet #520's single comment, same day, files four new `tier:feature` issues (#588, #589, #590, #591) to cover its PFs. That is a direct violation of the rule the maintainer's own review just laid down, by the same review process, in the same 24-hour window. Recommend: either revert #588–591 to draft/unfiled until the ratchet condition is met, or explicitly note in #520 that the ratchet was knowingly overridden and why.

**4. CAP-36 was never triaged through #508's own disposition framework.** #508's capstone disposition table (Keep-core / Keep-strategic / Merged / Closed / Defer) enumerates every capstone the review considered — CAP-00 through CAP-26 — and CAP-36 is absent, because #520 postdates #508 by a day. #508's "direction (next two quarters, ≈30–45 mw total)" list — reconcile with the live user base, stop corpus bleed, grading-integrity wedge, prominence flare, accessibility, debug-loop parity, distribution — contains no publication/paper item. A brand-new 5-9 mw capstone (whose transitive dependency chain, see #5, is considerably larger) appearing outside that disposition process the day after it was written is scope creep against the review's own prioritization, not an application of it. Recommend: run CAP-36 through the same Keep-core/Keep-strategic/Defer disposition #508 applied to everything else before treating it as active.

**5. `ordering_after` understates true blocking cost; band_mw double-fails the exact failure mode #508 flagged.** #520 orders after #512 (CAP-28, itself `planned_features: [PF-1 unfiled, PF-2 unfiled, PF-3 unfiled, PF-4 unfiled]`, 3-6 mw, not started) and #300 (CAP-06, "12-20 mw marginal" per its own abstract, not started). Its own child #588 (PF-1) adds a further dependency on #560 (FEAT-C28-4, a cross-tool harness that does not yet exist) on top of #512/#300. So the "5-9 mw" band for CAP-36 sits behind roughly 15-26 mw of prerequisite engineering work before PF-1's demo slice is even reachable, none of which is reflected in the band. #508 itself names this exact failure mode as a known problem: *"Spot-audit machine-generated arithmetic before filing (3 of 4 sampled capstones had bands below their own row sums)."* CAP-36 reproduces it one day later. Recommend: state a critical-path estimate (through #512 and #300) alongside the isolated writing-effort band, or mark CAP-36 explicitly blocked-not-orderable until those land.

**6. Internal contradiction: the issue body is already stale relative to its own comment.** The YAML front-matter reads `planned_features: [PF-1 unfiled, PF-2 unfiled, PF-3 unfiled, PF-4 unfiled]`, but the sole comment (same day) reports all four filed as #588-591. A reader who — as this review was instructed to — reads "its body" gets contradicted information the issue never corrected. This is exactly the tracker-hygiene problem #508 calls out ("Planning prose belongs in `docs/` on master, not issue bodies; issues become thin"). Recommend: edit the body's `planned_features` line, don't leave it to the comment thread.

**7. Competitor bug citations are asserted, not independently verified by this review pass — and the freshness gate only applies going forward.** PF-1/#588 cite specific issue numbers on Logisim-Evolution and CircuitVerse's own trackers (e.g., LE #1546/#598/#950/#1123/#441/#185/#2454; CircuitVerse #1412/#5328/#1753/#2198) sourced from `docs/reviews/evidence/2026-08-niche-survey/`, itself produced by the same review lineage as #510/#508/#520. AC-2/KC-36-1 require the citations be checked "against the current release at publication time," which is good discipline for the future, but nothing gates the *initial* citation set against having already gone stale or been mischaracterized between survey-write time and PF-1 start time. A "respectfully and accurately" comparison note that ships with even one already-fixed or mischaracterized citation undermines AC-3 on day one and risks the reputational goodwill the capstone's own stated purpose (drawing competitors' user/developer base, per #510 §5) depends on. Recommend: an explicit re-verification pass against the live competitor trackers immediately before PF-1 drafting starts, not only "at publication time."

**8. "Respectfully and accurately" (AC-3 / boundary notes) is an unenforceable tone requirement for content that is, by design, a catalog of a rival project's bugs.** Nothing in the ACs defines a reviewer or standard for tone; a factually-cited but condescension-reading note could pass every listed AC while actively working against the stated goal of drawing Logisim-Evolution's 147-contributor community (per #510 §5) toward JLS. Recommend: name a second reviewer (not the author) for tone sign-off before publication, mirroring the "two-lens adversarial synthesis" method #508 itself used.

## What's solid

- The kill criteria (KC-36-1 stale-retraction-not-defense, KC-36-2 recorded fallback if #509 doesn't materialize) are genuinely well-specified for a documentation capstone — better risk discipline than most "just write it" issues get.
- Sequencing PF-1's grading-determinism note after #300 (CAP-06, which ships the actual verdict behavior) is correct: publishing a claim about a documented grading contract before that contract exists would be the report contradicting itself (#300's own abstract admits today's grading story is "a Python script diffing three literal lines").
- AC-5 in child #588 ("a note with no losses in it fails review") is a good anti-marketing guardrail and mitigates part of finding 8, though it does not fully substitute for a tone review.
- Every issue #520 references in its `ordering_after` and evidence (`#510`, `#508`, `#512`, `#300`, `#509`) resolves to a real, open issue — no dangling references found.
