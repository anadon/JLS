## Findings, most severe first

**1. [Critical] The evidence corpus this issue is pinned to does not exist in this repository.**
`evidence_commit: 2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7` and the cited `3a81a4a7d6a0f108ec201e632732d308cc02b3fc` (source of the cost band and "Related" pricing) are both unresolvable: `git cat-file -e <hash>` fails for each against this checkout's full 267-commit history. `docs/plan/`, home of `docs/plan/features/*.md`, `docs/plan/evidence/BRIEF.md` and `format-adoption-plan.md` — all quoted verbatim as in-tree sources for the DAG walk, the capstone cross-checks, and the 6-12 maintainer-week cost band — has never existed anywhere in this repo's git history (`git log --all --diff-filter=A --name-only | grep docs/plan` returns nothing). Every `blocked_by`/`blocks`/`serves_capstones` claim, every cost number, and every "corrected walk" paragraph in this issue rests on documents this reviewer cannot verify exist anywhere reachable from `anadon/JLS`. Spot-checks of code-level claims (below) happen to still hold, but the planning apparatus itself is unauditable from the tree it claims to be pinned to. Recommendation: before funding, either point at the actual repository/branch this evidence lives in, or strip every claim sourced from the missing corpus and re-derive scope and cost from what is verifiably in tree.

**2. [High] `docs/parity-contract.md` — cited as the already-settled governing spec for the differential leg — does not exist.**
§3: "The parity framing that places all timing in the permitted-to-differ column — `docs/parity-contract.md` owns it and this feature does not restate it." §7 Re-planning Protocol repeats it: "the REPLAN must go to `docs/parity-contract.md`'s owner." Verified: `docs/parity-contract.md` is absent from the working tree and from all of git history. The hardest technical question this feature has to answer — what counts as a legitimate JLS-vs-external-simulator divergence at a settling point, versus a real bug — is delegated to a document that was never written. Nothing in `planned_tasks` creates it. This is not a restatement problem, it's a missing prerequisite the issue treats as already resolved.

**3. [High] The one criterion that "distinguishes this feature from what already ships" has no filed owner.**
§5 criterion 2 (catching a knowingly-wrong emitter via the differential leg) is explicitly the issue's own litmus test, and the roster marks it "Not filed; the registry's task id space is closed at TASK-0112." The issue's own closing comment declares the decomposition resolved as "`#359 = #386 + #416`" — but #386 covers only TASK-0051 (CI arming) and #416 only TASK-0052 (second board + hardware flash); TASK-0044 (hierarchical goldens) is owned by #358, TASK-0100 (analog corpus) by #351, and the behavioral differential leg has **no issue at all**. A reader trusting the dedup comment would conclude the feature is fully decomposed into two tracked tasks; the actual load-bearing piece is untracked and could silently never get filed.

**4. [High] Acceptance criterion 2 is gameable as written — a one-time demonstration, not a standing test.**
"Introduce a deliberate semantic error into an emitter... observe the differential leg go red... Does not exist yet." Nothing in the criterion or the Definition of Done requires this to land as a permanent regression test; "verified at a named commit; command and output recorded in a closing comment" reads as a one-off PR demonstration. The repo already ships a PIT mutation-coverage ratchet (`.github/workflows/mutation.yml`, issue #159) that this issue never mentions or integrates with, despite it being the obvious existing mechanism for "a mutation must be caught." As written, someone can hand-edit an emitter once, screenshot red CI, revert, and close the criterion — after which the differential leg can silently stop catching anything, which is exactly the "a leg can pass by not running" failure mode this issue exists to eliminate, recreated one layer up. Recommend requiring a named, permanent test class asserting the mutation is caught on every run, or explicit wiring into the existing mutation ratchet.

**5. [Medium] TASK-0052 ownership contradiction is unresolved and self-documented as unresolved.**
#359's Open Question 3 / DoD explicitly requires "Open Question 3 resolved and TASK-0052's single owner recorded, so #264 and this issue do not both claim it," recommending re-homing to #264. Instead, #416 (TASK-0052) was filed under `part_of_feature: 359` anyway, and #416 itself restates the same unresolved contest verbatim ("OWNERSHIP IS CONTESTED... Blocks nothing; decide before execution starts"). Neither #359, #264, nor #416 records a resolution as of this review. If both #264 and #359 independently close claiming the same second-board-plus-flash deliverable, the tracker double-counts one piece of shipped work — the exact defect class (a half-edge / ambiguous single-owner claim) this planning apparatus otherwise polices rigorously elsewhere in the same document.

**6. [Medium] Cost/feasibility mismatch with the project's own stated bus factor.**
This issue's own Impact section names "The maintainer (bus factor 1)" as a stakeholder, and ARCHITECTURE.md independently confirms JLS is a single-maintainer pedagogy tool. The issue then prices itself at 6-12 maintainer-weeks and makes one deliverable (TASK-0052/#416) contingent on a physical ECP5 board, a human, and a hardware flash that "cannot be automated" and has "no automated defence" against a wrong pin transcription. For a single-maintainer educational project this is a large, hard-to-schedule, easy-to-silently-stall commitment; the issue's own extensive hedging (REPLAN protocols, descope defaults on nearly every deliverable) reads as tacit acknowledgment that the plan does not expect to land as specified.

**7. [Low] The DAG walk is self-admittedly error-prone and only partially re-verified here.**
The issue text itself records a prior self-correction: an earlier revision overstated its `blocked_by` closure by six issues (#334, #319, #318, #337, #340, #357), later "withdrawn" as declared by no real edge. That the issue needed a public in-text correction of its own dependency graph is a sign of how fragile this prose-DAG bookkeeping is. This review independently confirmed #317's `blocks`/`blocked_by` fields are mutually consistent with #359's citation of them, but did not re-walk the full closure (#315, #336, #353, #354) — a future reviewer should not assume the current walk is error-free merely because one prior error was caught and fixed.
