# Issue #404: TASK-0003: an attribute name no element declares becomes a named load diagnostic instead of vanishing
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

The issue is unusually well-evidenced against the actual codebase — I checked essentially every cited file:line (`Element.java:344/359/374/389`, `Circuit.java:1067/1078/1089/1105/1116`, `LoadError.java:38-66`, `WireEnd.java:626-664`, `docs/file-format.md` §5, `Element.java:17` sealed permits list, `Attribute.java`'s `setInt`/`setLong`/`setBigInt`/`setString`) and every one matches HEAD verbatim, including the `26`-overrides/`17`-files count from `git grep -n "public void setValue" -- src/jls/`. That rigor makes the one hole I found more serious, not less: the issue's central feasibility claim — that the ripple is "bounded and compiler-found" because `Element` is sealed (O7) — is false for at least one of its own 17 listed files, and the issue's H1 ("every silent drop is exactly the fall-through at `Element.java:344/359/374/389`") is refuted by code already in the tree, not by a hypothetical.

## Findings, most severe first

### 1. (Critical) `State.java` is miscounted into the "26 overrides, compiler-enforced" ripple — it isn't an `Element` override at all, and its own silent-drop bug is out of scope but never named

O4 lists `State` among "the 17 files" with `public void setValue`, and §8's plan says "Fix the compile: 26 declarations across 17 files (O4). Each override returns `true` for names it handles itself and the `super.setValue(...)` result in its `else` (O5)." That is false of `State`:

- `src/jls/elem/State.java:19`: `public class State {` — no `extends Element`, no `implements`. It is a plain helper class owned by `StateMachine`.
- `src/jls/elem/State.java:403`: `public void setValue(String name, int value) {` carries no `@Override` (verified — none present). It only coincidentally shares `Element.setValue`'s signature.
- The method body is `if (name.equals("x")) {…} else if ("y") {…} else if ("diameter") {…} else if ("init") {…}` with **no trailing `else`** — an unrecognized name is dropped with nothing executed, no delegation to anything. The same shape recurs in `State.setOutputValue(String,int)` (`:437`), `State.setOutputValue(String,long)` (`:466`), `State.setTransValue(String,String)` (`:484`), `State.setTransValue(String,int)` (`:525`) — five more silent-drop sites, none of them `Element` overrides, none inside `savedAttributes()`/`Attribute`.
- These are reached from `StateMachine.setValue(String,int)` (`:402-420`): `case newState: if (buildState != null) buildState.setValue(name,value); break;` — and the parallel `newOutput`/`newTransition` cases. **None of these three cases calls `super.setValue(...)`.** Only `case machine:` does. So O5's prescribed shape ("handle your own names, else `super.setValue(...)`") does not exist for 3 of `StateMachine`'s 4 dispatch states — there is no `else` branch to convert.
- Worse, `StateMachine.setValue(String,long)` (`:429-441`) has `case machine: case newState: case newTransition: break;` — for those three loader states, a `long` attribute is dropped with **no action at all**, not even the (already-present) delegation the `int` overload has in its `machine` case.

Consequence: a `.jls` file with a typo'd attribute name inside a `STATE`/`OUTPUT`/`TRANS` block inside a `StateMachine` element (e.g. `int xx 3` instead of `int x 3`) is silently dropped today, exactly like O3's headline defect — but this path never touches `Element.java:344-389`, so H1 ("every silent drop is exactly the fall-through" there) is refuted by code that already exists, not by a hypothetical the Falsification Criteria imagine ("an `Attribute` implementation that accepts the name and then silently coerces or discards"). This is a second, structurally different silent-drop mechanism inside one of the issue's own 17 in-scope files, and because `State` isn't part of the sealed `Element` hierarchy, O7's "the compiler finds all 26 override sites" safety net does not reach it — nothing forces `State.setValue`/`setOutputValue`/`setTransValue` to be touched, or even noticed, by this task's compile-driven method.

**Recommendation**: correct O4's inventory to separate genuine `Element` overrides from same-named unrelated methods (a `grep -B2 "public void setValue"` filtered for `@Override`, or checking each class's supertype, would have caught this). Either (a) explicitly scope `State`'s three dispatch methods into this task as a second, non-mechanical piece of work with its own design for what "consumed" means when `buildState` is null or the state machine is mid-block, or (b) carve it out explicitly as follow-on and say so in §13's "Explicitly out of scope" list, which currently does not mention it. As written, an executor following the checklist literally will make `Element`'s hierarchy total and ship P6 green (`git grep "public void setValue" -- src/jls/` returns zero — trivially achievable by renaming `State`'s three methods to return `boolean` without touching their internal logic) while `State`'s own silent drops keep silently dropping, which is a **gameable acceptance criterion**: P6 can pass while the actual defect class (per H1's own scope) survives in the very file the issue cites as converted.

### 2. (Moderate) P1/P6 are satisfiable without fixing the semantic defect

Following from #1: P6 ("`git grep -n \"public void setValue\" -- src/jls/` returns zero lines") is a syntactic ratchet, not a behavioral one. An executor under schedule pressure can make every method matching that grep return `boolean` — including `State`'s three, mechanically renamed with `return true;`/`return false;` inserted wherever convenient — and pass P6, P4 (three tracked fixtures, none of which appear to exercise a mistyped state/output/transition attribute per Threats to Validity §11's own admission that the corpus is thin), and even H3, while the `newState`/`newOutput`/`newTransition` branches of `StateMachine.setValue` still don't call anything that could report a genuine miss. Nothing in §5 Predictions or §9 Data Collection specifically exercises a typo inside a `STATE`/`OUTPUT`/`TRANS` block, so this exact regression class has no falsifying test in the plan as written.

**Recommendation**: add a P-series prediction (or fold into P2) that loads a `StateMachine` block with an undeclared attribute inside a `STATE`, `OUTPUT`, and `TRANS` sub-block respectively, and asserts `UNCONSUMED_ATTRIBUTE` warnings naming them — this is exactly the kind of case P2 claims to cover ("one warning per kind... proves all five call sites were converted") but doesn't, because it only varies item *kind* (int/long/Int/String/ref), not element *internal dispatch shape*.

### 3. (Minor) O4's "five loader arms" and "four overloads" language obscures that `ref` and `int` are the same overload

O2 lists five `Circuit.java` call sites — `int` (`:1067`), `long` (`:1078`), `Int`/BigInteger (`:1089`), `String` (`:1105`), `ref` (`:1116`) — and P2 says testing all five "is what proves all five call sites were converted and not just the first." But `Circuit.java:1107-1117` shows the `ref` arm reads `input.nextInt()` and calls the exact same `el.setValue(name, value)` as the `int` arm two overloads up — both go through `Element.setValue(String, int)` (verified: there is no separate `setValue(String,int,boolean isRef)` or similar). So P2's five sub-tests only prove five *call sites* check the return value, not five independently-converted *dispatch paths* — there are really only four (matching O1's "four overloads"). This is accurate as far as it goes but the framing overstates what P2 demonstrates; a reviewer skimming §5 could believe `ref` exercises a distinct code path from `int`, which it does not.

**Recommendation**: rephrase P2 to say it proves the five *call sites* were converted, not the underlying dispatch, or note explicitly that `int`/`ref` share an overload.

### 4. (Minor) Evidence commit `2d0ca9d` is unreachable in this checkout, so O1-O8 could not be independently re-derived from history — only cross-checked against HEAD

`git cat-file -t 2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7` fails ("bad object") in this repo; the checkout is shallow (`git rev-parse --is-shallow-repository` → `true`, 276 commits visible). This is very likely a shallow-clone artifact rather than a fabricated hash — every line-numbered claim I checked against current HEAD matches exactly (Element.java:344/359/374/389, Circuit.java:1067/1078/1089/1105/1116, LoadError.java categories, WireEnd.java:626/659, the 26/17 grep count) — so I do not read this as evidence the commit is invented, just that the issue's own rule 6 ("re-verify O1–O8 at the executor's checkout; re-derive line numbers if HEAD has moved") is not idly stated: an executor with a shallow clone cannot mechanically run the cited `git diff --stat 2d0ca9d HEAD` command either, and will hit the same wall. Worth flagging as a friction point, not a defect in the issue's content.

### 5. (Minor) P7's aggregation cap is unspecified, so "observe an aggregated report, not 1,000 separate messages" is under-defined as an acceptance test

§7.10 defines the cap $C$ symbolically; Open Question 2 says the value is "rides along" and left to the executor, with only a vague "recommended default: the same order as the existing hostile-input caps in `jls`" (no cross-reference to an actual constant). Any $C$ from 1 to 999 satisfies P7's literal wording ("not 1,000 separate messages"), so P7 as stated cannot distinguish a well-chosen cap from a degenerate one (e.g. $C=1$, which arguably defeats the diagnostic's usefulness for the ordinary multi-typo case).

**Recommendation**: either pin $C$ in the issue (point at the actual existing hostile-input cap constant and its file:line, the way every other numeric claim in this issue is pinned) or explicitly state the acceptable range for reviewers to check against.

## What's solid

- The forensic grounding (O1, O2, O4, O7, O8, the `docs/file-format.md` §5 quote, the `Attribute.setInt/setLong/setBigInt/setString` boolean-return groundwork already in `Attribute.java`) is verified byte-for-byte against HEAD; this is unusually trustworthy evidence for an issue of this size.
- H2/P4/P5's compatibility argument (accepted-attribute behavior is pointwise unchanged; only the discarded complement gains a report) is sound and matches `Circuit.java`'s actual control flow — `failLoad` is a genuinely separate function from the new non-fatal path, so P5's "load-and-report, not refusal" claim is architecturally plausible, not just asserted.
- Scoping `setPair`/`probe` out (§7.12 point 5) is correct and matches `Circuit.java:1118-1149` — `setPair` takes no name argument, so "unconsumed by name" is genuinely undefined for it.
- The `LoadError.Category` no-`default:`-arm discipline (verified: no exhaustive `switch (category)` construct currently exists that would need one) is a reasonable ratchet, though I could not find the "every existing switch over Category" the checklist references — worth double-checking there is in fact at least one such switch before an executor treats that checklist item as satisfied trivially.

## Verdict rationale

The issue's dependency graph, compatibility argument, and interface contract are solid, but its central feasibility claim — a bounded, compiler-enforced, mechanically-uniform ripple across "26 overrides in 17 files" — does not hold for `StateMachine`/`State`, one of its own cited files, and the acceptance criteria (P6 in particular) can be satisfied without closing the semantic gap that H1 claims to close. This needs a scope correction (either explicitly extend the task to `State`'s three dispatch methods with real design work, or explicitly exclude them and file the exclusion as its own issue) before execution, not a full rewrite — hence `needs-rework` rather than `should-not-proceed`.
