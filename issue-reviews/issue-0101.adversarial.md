## Summary of what's being asked

The bulk of the described apparatus (`scripts/wayland-rig.sh`, `scripts/x11-rig.sh`, `HelloSwingControl`, the `gui-wayland`/`gui-x11` CI lanes, nightly cron, README docs) is already merged and verified present in the working tree at HEAD (`53116252`), one commit ahead of the cited `evidence_commit` 29afb26 (only change since: `e02758a`, a dependabot actions-version bump that doesn't touch the cited lines). What remains is three "planned_tasks": (1) post a first-light report comment, (2) calibrate `PIXEL_DIFF_MIN` from "0" to a real value, (3) register the two job names as required branch-protection checks. I verified `.github/workflows/ci.yml` still has `PIXEL_DIFF_MIN: "0"` on both lanes and `JBR_SHA256: "UNVERIFIED-PLACEHOLDER-..."`, matching the issue's claims.

## Findings, most severe first

**1. [HIGH — feasibility] One-third of the Definition of Done cannot be satisfied by any PR.**
Task 3 — "Register 'GUI boot (Linux, Wayland/JBR)' and 'GUI boot (Linux, X11/Xvfb)' as required branch-protection contexts" — is explicitly a "maintainer repo-settings action," not a code change; GitHub branch protection is not exposed through anything in this repo's tree. Yet the issue lists it as a co-equal `planned_tasks` entry and a DoD checkbox indistinguishable in form from the two code-completable tasks. Any contributor (human or agent) picking up "close out #101" from the roster table alone will hit a wall on this item with no PR to open against it. The issue does note this ("needing repo-settings permission the other two do not") but only in a rationale aside (§2, "Why these cuts"), not as a structural flag on the task itself.
*Recommendation:* Mark task 3 distinctly (e.g. a separate `blocked_by: [maintainer-action]` style tag, or move it out of the DoD checklist into an explicit "requires @anadon" callout) so automated/fleet workflows don't loop trying to "complete" it via code.

**2. [HIGH — gameable acceptance criterion] The P2 calibration formula is too loose to verify or falsify.**
"`PIXEL_DIFF_MIN` set to ~10% of the first green run's recorded AE (~10% of observed)" (machine block `planned_tasks`, and §5) is calibrated from a **single** run on a **software (pixman) renderer**, which the issue itself elsewhere concedes is noisy ("headless sway on the pixman software renderer is not a GPU desktop"). One sample gives no noise floor: if that one run happens to have unusually low AE (e.g. because font hinting settled quickly), the threshold could be set so tight that ordinary anti-aliasing jitter across runs flakes the now-required check; if the run happens to have unusually high AE, the threshold could pass through a partially-blank or badly-misrendered frame and still satisfy the checkbox. The completion bar itself is soft too: "a blank frame demonstrably fails" (§5) is the easiest possible case to pass — it says nothing about a *partial* render (e.g. window chrome only, canvas blank) surviving under a loose threshold, which is the more realistic regression this gate exists to catch.
*Recommendation:* Calibrate from the AE distribution across several (not one) green runs before fixing the constant, and require the demonstrated failure case in the DoD to be a partial/mostly-blank render, not merely a fully blank one.

**3. [MED — scope gap] The unpinned `JBR_SHA256` supply-chain gap has no owner in this issue's DoD.**
Comments across three weeks (2026-07-09 through 2026-07-19) document repeated failed attempts to reach `cache-redirector.jetbrains.com` from the authoring sandbox (403/blocked) to compute the real hash, leaving `JBR_SHA256` permanently `UNVERIFIED-PLACEHOLDER-...`. The env-block comment in `ci.yml` (lines around `JBR_URL`/`JBR_SHA256`) notes CI runners *do* print the observed digest on every green run — so filling it in is a one-line copy-paste from a log — yet none of the three `planned_tasks`, nor the Completion Criteria checklist, mentions pinning it. The "Honest limits" paragraph (§5) treats the unpinned download as an accepted, permanent trust-boundary decision ("TLS is the trust boundary... an optional hardening pin"), but that framing quietly forecloses ever picking the low-cost hardening step up, since nothing tracks it as outstanding.
*Recommendation:* Either explicitly WAIVE the checksum pin with a successor issue reference (per this project's own template rule — "every skipped or waived criterion carries a `WAIVED:` comment naming its successor issue" — which this issue's own DoD requires elsewhere but doesn't apply here), or add it as a fourth trivial planned task.

**4. [MED — internal consistency / underspecified interface] The two artifact-producing tasks aren't required to agree on which CI run they cite.**
§3 states the first-light report "consumes the artifact bundle of a green `gui-wayland` run" and calibration "consumes the `pixel-diff.txt` artifact the lanes already emit," and §6 explicitly invites them to be picked up independently and concurrently ("all three planned tasks are mutually independent and safe to execute concurrently... No task depends on another's output"). But if two different contributors pick these up separately, nothing requires them to cite the *same* green run — so the published "here's what a good boot looks like" screenshot/log baseline and the numeric threshold that gates future boots could silently originate from two different runs with different observed AE, undermining the claim that the first-light report is "the published baseline of what a good boot looks like" (§5) against which the calibrated gate is meant to be judged.
*Recommendation:* Require both tasks to cite the same qualifying CI run ID.

**5. [LOW-MED — naming/trust hazard for the least-informed reader] The required-check name overstates the guarantee once fail-open is factored in.**
The issue is honest internally that `gui-wayland` fail-opens on JBR CDN failure (job succeeds via `skip=true` without running P1/P2 at all) and that `gui-x11` is "the genuinely fail-closed hard gate." But a maintainer registering branch-protection contexts by name alone (task 3, a repo-settings click, disconnected from this issue body at the point it's performed) sees two symmetric-looking required checks — "GUI boot (Linux, Wayland/JBR)" and "GUI boot (Linux, X11/Xvfb)" — with no signal in the name itself that one of them can go green having verified nothing. This is a plausible way for the stated feature-level outcome ("a change that stops the GUI booting... cannot merge to master," §5) to *appear* satisfied by branch protection while a CDN hiccup silently exempts the Wayland lane on exactly the PR that broke it.
*Recommendation:* Carry the fail-open caveat into whatever surface documents the branch-protection setup itself (not just this issue body), since that's the artifact the person doing task 3 will actually be looking at.

**6. [LOW — process cost, not correctness] Documentation overhead is large relative to the remaining substance.**
The three remaining actions are: post a comment, change two string constants in `ci.yml`, and click a settings toggle. The issue carries a full feature-tier template — machine block, mermaid dependency graph, four numbered sections of interface/invariant/sequencing prose, a re-planning protocol, and a nine-item Definition of Done — to track them. This isn't wrong (the roster table at §2 does make "what do I actually do" locatable), but it's worth naming as a cost: a future contributor or reviewer has to read ~9,000 words of restructuring history and retired-decision bookkeeping to extract three one-line action items, and every one of those cross-references (line numbers, commit hashes, other issue numbers) is a maintenance liability that will go stale the next time any of the cited files move.

## Verdict rationale

Nothing here is fundamentally broken or contradicts the codebase — the apparatus genuinely exists and works as described. But the remaining work packet has one item that isn't PR-completable at all (finding 1), one acceptance criterion that's statistically underpowered and easy to satisfy without protecting against the regression it's meant to catch (finding 2), and a silent gap in what the DoD actually tracks (finding 3). These are process/verification-design issues, not reasons to block the underlying work — hence "sound-with-concerns" rather than "needs-rework."
