# Issue #573: FEAT-C32-2: the curated examples run on a static demo page — no backend, no accounts, no persistence, nothing that can die and take user data with it
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

#573 is PF-2 of CAP-32 (#516): host "the mechanism that won FEAT-C32-1's [#572] go/no-go" as a static demo page serving #548's curated examples. It is well-bounded on paper (clean non-duplication of #548, correct `ordering_after`), but it is written as though #572 has already resolved in favor of a genuinely interactive, self-contained mechanism — it has not (#572 is still open, no go/no-go comment exists) — and several of its acceptance criteria assert properties ("read-only by construction," "static files only... zero operational upkeep") that the leading candidate mechanism (CheerpJ) does not actually guarantee without additional, unspecified design work. Confirmed against the checkout: `grep -rli "javascript" src/` returns `0` — there is no JS anywhere in this project today, so this issue is the one that would introduce the first, with no build-tooling story for it.

## Findings, most severe first

**1. The whole Outcome text presupposes an interactive win that #572 is not guaranteed to deliver.**
Quoted: "a prospective user clicks a link and, with nothing installed, watches and pokes a running JLS example circuit (toggle inputs, observe signal trace)." #573's own `ordering_after` says #572 "picks this page's mechanism," and #572 AC-4 names two no-go fallbacks if CheerpJ fails: (a) an interactive SVG + JS VCD player (still plausibly "pokeable"), and (b) "recorded video walkthroughs" — explicitly *not* interactive. If PF-1 lands on fallback (b), #573's title, Outcome ("watches and pokes"), and AC-1 ("reaches a running example") are false on arrival, yet nothing in #573 hedges this contingency or says what the issue becomes if the upstream spike resolves to a video. This is the same defect independently found in the downstream issue #574 (finding 4 there): the whole three-issue chain writes "running demo" language before the one issue whose job is to determine whether that's achievable has reported back. Recommend: either block #573 from starting until #572's go/no-go lands, or reword Outcome/AC-1/AC-4 to be robust to all three PF-1 outcomes.

**2. AC-2's "read-only by construction" claim has no enforcement mechanism if the winning artifact is a CheerpJ-wrapped, otherwise-unmodified Swing jar.**
Quoted: "AC-2: The page is read-only by construction: no save, no upload, no user content." CheerpJ (the mechanism #572 proposes to test first) runs the actual Swing GUI in the browser — same menus, same `File > Open`/`Save`, same dialogs — unless something strips or disables them for a demo build. Neither #573 nor #572 mentions building a restricted "demo variant" of the jar/menu set; "read-only by construction" is asserted as a property of *hosting*, but as written the artifact being hosted is the ordinary interactive editor. A visitor with the unmodified GUI can open `File > Open` and load an arbitrary local file into the same reflective loader `ARCHITECTURE.md` describes (the `#38` hardening now protects the *user's own browser tab*, but "no user content" is still contradicted the moment that menu path exists and is reachable). Recommend AC-2 name the actual mechanism (e.g., a build flag or wrapper that removes file-menu I/O) rather than asserting the property with no supporting design.

**3. AC-3's "static files only... zero operational upkeep" is in tension with the leading candidate mechanism's actual runtime dependency, and is written so it can pass while the substantive goal fails.**
Quoted: "AC-3: Hosting is static files only; deployment is a file copy, and the page keeps working with zero operational upkeep." CheerpJ's standard (free/community) deployment path loads its runtime loader from Leaning Technologies' own CDN at every page view — a live, third-party-operated dependency at load time, not merely a build-time one. "Deployment is a file copy" can be trivially, literally true (the demo HTML/JS files are static and copied to a host) while the page's actual availability still depends on a service this project does not control and cannot fix if it changes terms, rate-limits, or goes dark — precisely the simulator.io-style failure mode the issue's own title invokes ("nothing that can die and take user data with it"). This is a gameable AC: it can be satisfied on a literal reading while undermining the permanence property that is the entire stated rationale for the feature. This was independently flagged in #574's adversarial review (finding 3) as a risk #574 merely inherits; #573 is the issue that actually builds the hosting and should be the one that resolves it (e.g., require self-hosting the CheerpJ runtime, or make CDN-freedom a hard AC), but neither #573's ACs nor its boundary notes mention it.

**4. AC-4 commits to serving the full curated set "as is," including a circuit whose feasibility was never actually spiked.**
Quoted: "AC-4: The demo serves the CAP-27 curated example set (#548), each with its caption." #548 AC-2 requires the curated set to include "the RV32I showcase" — a large, multi-cycle CPU design, by a wide margin the heaviest circuit in the repository (`riscv/`). #572's feasibility spike, which this issue's mechanism rests on, is scoped only to "the three biggest example circuits" (#572 AC-1) — not explicitly RV32I, and not the full ≥10-example set #548 requires. There is no language in #573 for what happens if the winning mechanism handles small combinational/sequential examples acceptably but the RV32I showcase blows the 30-second or interaction-fidelity bar: does AC-4 get satisfied by quietly dropping RV32I from the demo (in which case "the CAP-27 curated example set" is false), or does the whole page ship with one badly-behaved demo tile? Neither #573 nor #572 names a per-example fallback or a minimum-coverage bar, so AC-4 is gameable by omission with nothing to catch it.

**5. No verification mechanism (test or CI check) is named for any acceptance criterion, unlike sibling issues in the same filing batch.**
AC-1 (<30s), AC-2 (read-only), AC-4 (full example coverage with captions), and AC-5 ("states plainly") are all self-attested prose with no test, script, or CI job named. Contrast with the project's established pattern for adjacent work: #551 AC-2 requires "one scripted regeneration command" so renders "cannot silently drift," #545 AC-4 requires a build-time drift check, and #548 AC-3 itself specifies `SampleCircuitsTest`-shaped coverage. `ARCHITECTURE.md`'s Test layout section documents this project takes automated-check discipline seriously (`HelpTopicsTest`, `ElementConstructorContractTest`, etc.); #573 breaks that pattern with nothing analogous for its own ACs, so once shipped, none of the four properties above (load time, read-only-ness, coverage, messaging) has anything guarding against silent regression.

**6. Cost estimate looks optimistic against the JS-tooling gap it would open, if the fallback (a) mechanism wins.**
`band_mw: "1-2"` covers productionizing whichever mechanism won #572's spike across the *entire* curated set (≥10 examples, 4+ categories, plus RV32I) with captions. Confirmed: this project currently ships zero JavaScript anywhere (`grep -rli "javascript" src/` → `0`, matching #500's background note). If #572 falls to fallback (a) — hand-building an interactive SVG renderer plus a JS VCD-driven signal player — #573 would be introducing the project's first JS artifact, its first non-Maven build step, and its first client-side test story, with no npm/build/vendoring plan mentioned anywhere in this issue or #572. 1-2 maintainer-weeks to design, build, and validate that toolchain end-to-end across a dozen circuits (not just #572's three spike circuits) is a tight estimate for what would be net-new infrastructure, not incremental feature work.

**7. AC-5's "states plainly" is unfalsifiable as literally worded.**
"AC-5: The page states plainly what the full desktop tool adds beyond the demo and links the installers." No content requirement, placement, or completeness bar is given — any minimal disclaimer technically satisfies it. Low severity; a human reviewer will likely catch an obviously inadequate implementation, but as written it cannot be checked mechanically (same pattern flagged for "prominent" in #574's AC-1).

## What's solid

- The non-duplication reasoning against #548 ("This feature adds no circuits... If a demo needs a circuit that does not exist, it is filed against #548, not authored here") is a clean, correctly-argued scope boundary.
- `ordering_after` correctly sequences on #572 (mechanism) and #548 (content) — the dependency shape itself is right even though finding 1 shows the issue's *wording* doesn't yet respect that dependency.
- The KC-32-2 scope cliff (no in-browser editor, citing CAP-19/#500's `not_planned` closure) is stated clearly and consistently with #516 and #572 — good defense against the most predictable scope creep for this kind of feature.
- The provenance comment distinguishing #573 from #551 ("one is a picture, the other is a running simulator... if #572 returns no-go, this feature does not ship and #551 is completely unaffected") is accurate and shows real risk-isolation thinking.

## Recommendation

Do not schedule implementation on #573 until #572 has actually produced its go/no-go comment — right now #573 is written as if the answer is already known and favorable. Once it lands, rewrite AC-2 and AC-3 to name the concrete mechanism that will make "read-only by construction" and "zero operational upkeep" true (menu-stripping/build-flag design; CDN-freedom or self-hosted runtime) rather than asserting the properties, add a named coverage bar and fallback rule to AC-4 for examples the winning mechanism can't handle at production quality (especially RV32I), and add at least one automated check per AC to match this project's existing test-discipline pattern.
