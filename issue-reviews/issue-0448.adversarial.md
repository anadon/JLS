# Issue #448: TASK-0047: every cell the validator accepts becomes a drawn element — the importer stops passing a design and then refusing it
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: sound-with-concerns

## Summary

The core diagnosis is real and reproducible against the checked-out tree: `CellValidator.SUPPORTED` (`src/jls/hdl/yosys/CellValidator.java:58-68`) lists 19 cell types, `NetlistImporter.mapCell`'s switch (`src/jls/hdl/imp/NetlistImporter.java:235-259`) realizes exactly 5 (`$not/$and/$or/$xor/$mux`), and the `default:` arm apologizes for the other 14 — all confirmed by direct grep against current `src/`. The element types the plan needs (`Register`, `Memory`, `Adder`, `TriState`, `Splitter`, `SubCircuit`) are indeed already registered (`src/jls/elem/ElementRegistry.java:39,53,61,67,74`), so H1's "no new element type" premise checks out. This is a well-specified, evidence-heavy issue by the standards of this repo. It has real defects, though: one internally contradicts a sibling issue's own reasoning about the exact same code path, one creates an unenforceable dependency on external-tool availability that the issue's own `related` link already documents as broken, and the `part_of_feature` pointer is stale (already half-corrected by later bot comments, easy to miss).

## Findings, most severe first

**1. (HIGH) The "fixtures must be extended or replaced" directive is very likely wrong, and contradicts the sibling issue's own diagnosis of the identical mechanism.**
O4 asserts that `reject_dff.json` and `reject_ram_sync.json` trip a *second*, independent problem — "input OutputPin.input reads a bit pattern that no single element drives as a whole ... a Splitter/Binder mesh, which this importer increment does not yet build" — and instructs (§6, §11, Method step 3): "the fixtures must be extended or replaced so the cell realization is provable independently of it," calling it "a different residual." Tracing the code contradicts this: `mapPorts` (`NetlistImporter.java:169-192`) registers every `OutputPin` as a *reader* (`builder.reader(out, "input", port.bits())`, line 182) queued for later resolution; `importNetlist` runs `mapPorts(...); mapCells(...); builder.resolveReaders(...)` in that order (`:94-96`); and every existing cell mapper (`mapUnaryGate`/`mapBinaryGate`/`mapMux`, lines 286/288/323/361) registers its own output as a *driver* via `builder.driver(y, elem, "output")`. Since `resolveReaders` only runs after every cell in the module has been mapped, the "no single element drives" failure for `reject_dff.json`'s `q` output and `reject_ram_sync.json`'s `rdata` output is a direct, deterministic side effect of `$dff`/`$mem_v2` never calling `builder.driver(...)` today — not an independent bit-slice/concatenation case in the fixture data (neither fixture actually contains a slice or concat; `d`/`q` and `rd_data` are whole contiguous bit vectors, see the fixture JSON). Once this task adds `builder.driver(y, register, "output")` for `$dff` (as its own Stage 2 plan requires anyway), the second problem should disappear for free. Sibling issue #449 (filed by the same author, same evidence commit, same day) reaches exactly this conclusion about its own structurally identical probe: "the top module's output pin reads an undriven net and the importer reports a slice/concatenation problem that has nothing to do with hierarchy ... it is a consequence of the first refusal and should disappear with it" (#449 §Observations O3, §Threats to Validity). #448 treats the same mechanism as a distinct residual requiring separate fixture engineering. Recommendation: drop the "extend or replace the fixtures" work item (or downgrade it to "verify the second problem line disappears; if it doesn't, that's the actual new finding"), so an executor isn't pushed into building unwanted Splitter/Binder scaffolding, or padding the corpus, to force these two specific fixtures to pass.

**2. (HIGH) P8 — the only evidence that any realization simulates correctly — depends on tool availability the issue's own `related` list shows is currently broken, and is listed as `related`, not `blocked_by`.**
§5 calls P8 (`aSyncResetCounterImportsAndSimulatesLikeIverilog`, gated on `yosys`+`iverilog`) "the only evidence that any of this simulates correctly," and the DoD requires it "**actually ran** — not skipped for a missing tool." Issue #386 (`related: [...386...]`), filed the same day, measured the actual CI/dev machine state: `yosys` present, but `iverilog`, `ghdl`, `nextpnr-ice40`, `icepack`, `verilator` all **absent**, and documents that under this condition "the build succeeded" while the differential oracle silently skipped — explicitly naming this "indistinguishable from a passing one" in a green build. #448 depends critically on exactly the tool #386 shows is missing (`iverilog`), yet declares only `related: [..., 386]`, not `blocked_by: [386]`. Nothing in #448 enforces that P8 actually executes in CI rather than once, locally, by whoever happens to have `iverilog` installed at PR time — after which CI can silently regress to skipping it forever with no red signal, exactly the failure mode #386 exists to close. This is a gameable acceptance criterion: the DoD checkbox "`aSyncResetCounterImportsAndSimulatesLikeIverilog()` actually ran" can be satisfied once, in a screenshot/paste, without any standing guarantee it keeps running. Recommendation: either add `blocked_by: [386]`, or have #448 add its own CI-level assertion (in the spirit of #386's own `ToolchainArmedTest`) that P8 is not silently skipped on the required lane.

**5. (MEDIUM) The "`$pos` → plain wiring" plan has an unaddressed ordering hazard.**
Open Question 5 (recommended default) and Stage 2's map (`ρ($pos) = ⟨⟩`, "plain wiring") require `$pos`'s output net to be aliased directly to its input's existing driver rather than routing through a new element. But `Builder.driver(int[] vector, Elem elem, String port)` (`NetlistImporter.java:672-681`) records a driver keyed by a vector and requires a concrete `Elem` at call time — there is no deferred/two-phase alias mechanism analogous to `reader()`/`resolveReaders()`. `mapCells` iterates `module.cells().values()`, backed by a `LinkedHashMap<String, Cell>` (`YosysNetlist.java:180`) in Yosys's JSON emission order, which has no topological guarantee. If a `$pos` cell appears in the netlist before the cell that drives its input, aliasing `y`'s key to `a`'s driver at `$pos`-processing time will find no driver yet registered, and either mis-fire the exact "no single element drives" problem this task is trying to eliminate, or need new deferred-alias machinery the interface contract (§7.4 "New `Builder` verbs," §7.5) never mentions. This is a real, non-trivial gap for a document this detailed about every other cell family.

**6. (MEDIUM) Very large, monolithic, all-or-nothing scope for one "task" issue.**
The DoD bundles: 14 independent cell-family realizations (arithmetic, two flip-flop trigger types plus latch, tri-state, two memory port shapes, five-plus reduction/logic ops via a shared Splitter helper), a new derived-residual parity test, "one minimal committed netlist per member of `SUPPORTED`" (≥19 fixtures) plus per-family targeted fixtures, an `ImportSummary` category rewrite, a full class-javadoc rewrite, feedback-edge marking that exercises a downstream layouter (#388) the issue itself flags as heuristically ambiguous for mutual-recursion designs (§11 Threats to Validity), and the yosys+iverilog-gated differential oracle from Finding 2 — all gated together ("No changes outside the scope of § Method," all of P1-P12 required). A legitimate, narrow defect discovered in one family (e.g., memory `init`-width validation) blocks landing of unrelated, already-correct realizations (e.g., `$add`), with no described mechanism to split the PR without violating the DoD as written.

**7. (LOW) The O8 silent-`setValue` hazard is honestly disclosed but is a real, uncovered gap, not a mitigated one.**
§7.11/§11 candidly state that P7's round-trip assertion "catches a *structural* error but not a *value* error — a `Register` saved with `type \"pff\"` when it should be `\"nff\"` round-trips perfectly." That's an accurate and welcome admission (verified: `Element.setValue`'s silent-miss behavior and the five unconditional `Circuit.java` call sites are exactly as O8 describes the pattern, and #404/TASK-0003 is open and unresolved). But it means P4 ("`CLK_POLARITY=1` becomes `\"pff\"`; `CLK_POLARITY=0` becomes `\"nff\"`") has *zero* structural backstop today — correctness rests entirely on hand-written per-test assertions of the emitted attribute string, with no ratchet against a future refactor silently swapping the two. Worth calling out explicitly as standing risk rather than letting the honest disclosure read as "handled."
