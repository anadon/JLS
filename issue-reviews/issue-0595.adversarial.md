# Issue #595: FEAT-C37-4: every editor refusal names the fix instead of the rule — Issie's width-inference philosophy applied to JLS's connect, width and name diagnostics, and identifier rules relaxed to what engineers actually write
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of the ask

Rewrite JLS's connect/width/name editor refusals to name both disagreeing
parties and a concrete fix (AC-1), relax `Util.isValidName` toward
conventional identifier practice including active-low forms (AC-2),
require byte-faithful round-trip and cross-path acceptance parity (AC-3),
pin every change with a headless pre-change-failing test tied to a #592
catalog row (AC-4), and close/refuse bsiever-fork #4 by name (AC-5).

## Findings, most severe first

**1. (High) The issue's own dedup pass flags an unresolved ownership conflict with #318, and the issue body never absorbed it.** The single comment on #595 (2026-08-04) states plainly: *"AC-2's identifier-rule relaxation reaches into core naming... are not GUI-local... If #318 does not own it, this issue owns the grammar change and should say so, because AC-3's byte-faithful round-trip and the HDL-path acceptance rule are core-format commitments, not ergonomics."* This is a real conflict, not a formality: #318 (FEAT-014) is the addressing/identity feature and explicitly claims naming grammar territory is FEAT-004's (a different, unfiled issue), while #595 claims the "conventional practice… as far as the `.jls` file format's constraints actually permit" relaxation as its own boundary note. Nothing in #595's body was edited after the comment to record which issue owns the grammar change, and #595 carries no re-planning protocol (contrast #316/#318, which both have explicit `REPLAN:`/§7 sections for exactly this kind of ownership ambiguity). **Recommendation:** do not fund #595 until the #318 cross-check the bot comment asks for is actually performed and recorded as an ordering edge, per the comment's own recommendation.

**2. (High) AC-2/the boundary note conflate "uses `Util.isValidName`" with "constrained by the file format grammar," and the format grammar does not in fact constrain most of the fields in scope.** `docs/file-format.md:149-155` (§3.1 Names) is explicit: the `letter (letter | digit | "_")*` restriction (citing `Util.isValidName`) applies only to **nested `CIRCUIT` names** (subcircuit definitions) and **the base `.jls` file name**. Everything else the issue's own call-site inventory would touch — pin names, register names, memory names, wire probe names — is saved as a `string-item` (`"String" attr-name quoted`, file-format.md:132), e.g. `String name "out"` (file-format.md ~521), which is a quoted, escaped, effectively-arbitrary string, not a `name`/`token` production. Yet `Util.isValidName` (`src/jls/Util.java:219-234`) is reused verbatim for both kinds of field across `PinDialog.java:181`, `RegisterDialog.java:325`, `MemoryDialog.java:279`, `SubCircuitDialog.java:128`, `TruthTableEditor.java:163`, `JumpStartDialog.java:149`, and `Editor.java:161`. The issue's own escape hatch — *"where the `.jls` grammar genuinely forbids a character, the catalog row is graded REFUSE with the grammar citation"* — is exactly the criterion this conflation breaks: an implementer (or #592's catalog scorer) can cite `file-format.md:154` to REFUSE relaxing a *pin* name, when §3.1 never actually governs pin names at all. AC-2 as written cannot detect that misuse; it only requires "a stated… constraint," not that the constraint is the right one for the field. **Recommendation:** AC-2 must require the catalog to name *which* field is being graded and to distinguish token-grammar fields (CIRCUIT/subcircuit name, file base name — 2 places) from quoted-string fields (nearly everything else), or the "format constraint is real, not an excuse" language is decorative.

**3. (Medium-High) AC-3's "HDL path also accepts" clause is close to vacuously satisfiable today, and passing it proves nothing about the feature's actual goal.** `src/jls/hdl/HdlNames.java:9-24` already legalizes *any* input deterministically: every character outside `[A-Za-z0-9_]` becomes `_`, collisions get `_2`, `_3`, … suffixes. That means "any identifier the editor accepts is one the... HDL path also accepts" is already true for arbitrary strings, with zero relaxation work — the HDL path has no reject path to test against. Worse, the specific motivating case (active-low naming, e.g. `!OE`, `~OE`, `#OE`) legalizes toward the same base identifier and gets disambiguated only by suffix order, silently discarding the active-low marker the feature is being funded to preserve. A test asserting AC-3's letter can pass while the semantic goal (active-low identifiers surviving meaningfully into HDL) fails outright. **Recommendation:** AC-3 needs a companion assertion that the *meaning* (not just legality) of a relaxed identifier survives HDL legalization, or drop the HDL clause and scope it explicitly to the editor/batch paths where it's testable.

**4. (Medium) Hard external blocking dependency with no fallback plan.** The boundary note states plainly: *"if #316 stalls, this feature waits (KC-37-1)."* #316/#84 (SimpleEditor decomposition, the mouse-state-machine extraction) is a large, actively re-baselining refactor (5,852 lines, five recorded re-baselines in July 2026 per #84's own body) with multiple unfiled sub-tasks. #595 inherits a hard gate on that work landing but, unlike #316 and #318, carries no §7-style re-planning protocol describing what happens to #595's scope if #316 stalls for months. **Recommendation:** add an explicit stall/re-plan clause mirroring #316's own KC-37-1 framing, since #595 is exactly the kind of downstream feature that clause exists to protect.

**5. (Medium) AC-1's "corpus of refusal cases… asserted against expected message content" has no defined size, coverage rule, or rubric for what counts as a "concrete reconciling edit" versus a longer restatement of the rule.** Message-content assertions are easy to game by writing the test and the message together with no independent judgment of quality — the acceptance criterion as stated cannot distinguish a genuinely actionable message from a verbose one that merely repeats the violated rule with more words. **Recommendation:** require the corpus to enumerate refusal *categories* (at minimum: width mismatch, unconnected input, duplicate name, invalid name, missing subcircuit port) with one fixture per category, and state a message template contract (e.g., "names both locations + one concrete edit, ≤N characters") that a reviewer — human or CI — can check mechanically rather than by taste.

**6. (Low-Medium) AC-5's "bsiever-fork #4… recorded closed or refused by name" is unverifiable from this repository and is a bookkeeping criterion, not a technical one.** `bsiever-fork` is an external fork, not `anadon/jls`; this review cannot fetch it, and neither can any CI gate implied by the other ACs. Satisfying AC-5 requires only a sentence in a closing comment, decoupled from whether the underlying relaxation actually addresses whatever bsiever #4 asked for. **Recommendation:** at minimum, quote bsiever-fork #4's actual request in #595 or a linked comment so "closed… by name" has a concrete target to check against, rather than trusting a label.

**7. (Low) No independent cost estimate for #595 itself.** `band_mw: "2-3"` is carried from #521's PF-4 row with no breakdown for #595's three real cost drivers: rewriting messages across ~7 dialogs plus wire/width diagnostics, the identifier-grammar audit finding 2 above implies is larger than "relax a regex," and new round-trip/cross-path tests. Sibling issues in this same filing pass (#316, #318) print explicit band-vs-task-sum reconciliation and flag when the two disagree; #595 does not, so its 2-3mw figure is unexamined.

## What's solid

- The underlying problem is real, not invented: `PinDialog.java:182`, `RegisterDialog.java:326`, `SubCircuitDialog.java:129`, `TruthTableEditor.java:164` all currently reject with generic, location-free text like `"Missing or invalid name, try again"` — exactly the "restates the rule, not the fix" pattern AC-1 targets.
- The decomposition boundary (diagnostics/validation belong in model-side collaborators, not `SimpleEditor`) is a reasonable, consistent constraint given #316's own stated direction.
- AC-4's "test that fails at the pre-change commit" discipline is a genuinely good, gameability-resistant requirement, well specified compared to AC-1/AC-2/AC-3.

## Verdict rationale

The stated outcome is worthwhile and the AC-1 diagnosis is well grounded in the real codebase, but AC-2/AC-3's core factual premise (that identifier restrictions are mostly file-format-driven) is contradicted by `docs/file-format.md` itself for the majority of the fields in scope, the issue's own dedup comment flags a live, unresolved ownership conflict with #318 that was never folded back into the issue body, and two acceptance criteria (AC-3's HDL clause, AC-5's bsiever-fork bookkeeping) can be satisfied without the underlying goal being achieved. These are fixable with clearer criteria and a resolved ordering edge to #318, not a reason to abandon the feature — hence needs-rework rather than should-not-proceed.
