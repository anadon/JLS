# Issue #469: TASK-0014: an hours-long batch run can be paused, watched and interrupted without losing its output — and pause stops being a second name for stop
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Findings, most severe first

### 1. (HIGH — correctness) The design as specified cannot satisfy its own "stop() while paused must still terminate the run" requirement

Section 7.4 states plainly: "**`stop()` while paused must still terminate the run** — the park predicate checks `stopping`, not only `paused`." Section 7.11's failure table repeats it: "the predicate's `stopping` conjunct is false, `wait` returns, loop condition fails, loop exits normally. **A `paused`-only predicate would hang the JVM here** — this is the failure this row exists to forbid."

That description of `wait()` is wrong. Under standard Java monitor semantics, a thread blocked in `Object.wait()` does **not** re-evaluate its predicate and return merely because some other thread flips a field it's watching — it stays blocked until `notify()`/`notifyAll()` is called on that monitor (or it's interrupted, or a timed wait elapses). The issue's own Method checklist only touches `notifyAll` in "Reimplement `pause(boolean which)` to set/clear `paused` and `notifyAll`" — it never asks for `stop()` to be touched. `BatchSimulator.stop()` (`src/jls/sim/BatchSimulator.java:74-78`) stays the two-line body the issue itself quotes as O1: `stopping = true;`, nothing else. If the task is implemented literally as specified, calling `stop()` (from the shutdown hook, per section 7.11's own row: "body is `sim.stop()` plus `join(timeout)`") while the batch thread is parked in `wait()` will not wake it. The bounded join then times out, "the hook returns and the JVM exits anyway rather than blocking shutdown" (7.11) — meaning the "clean interrupt" this entire task exists to deliver silently degrades into the same forced-exit truncation as `SIGKILL` for the one scenario (paused + interrupted) the issue explicitly calls out as the failure mode to forbid.

The fix is known and already in this codebase: `InteractiveSimulator.stop()` (`src/jls/edit/InteractiveSimulator.java:948-963`) sets `stopping = true` **and then calls `pauseSem.release()`** for exactly this reason — a flag write alone does not wake a parked thread. The issue's Method checklist even instructs the implementer to "Read `jls.edit.InteractiveSimulator`'s existing pause before finalising the design" (step 8), but the design in section 7 doesn't carry over this specific, load-bearing detail.

**Recommendation:** add an explicit interface obligation — either override `BatchSimulator.stop()` to also notify the pause monitor, or specify a timed `wait()` in the park loop — and add it to the DoD checklist and to P4/the falsification criteria for H1/H3.

### 2. (HIGH — gameable acceptance criteria / scope gap) Nothing in the batch CLI ever calls `pause()`

Section 7.1 ("External interfaces modified") lists exactly one CLI change: `-heartbeat`. No flag, signal, console command, or other production trigger is specified anywhere in the issue for invoking `BatchSimulator.pause(boolean)` from `jls -b`. `JLSStart.java`'s batch sequence (O6, lines ~245-261) is left untouched except for the shutdown hook and heartbeat wiring; there's no step in section 8's Method that wires any input to `pause()`.

P3 and P4 — the predictions that actually exercise pause/resume semantics — are both specified as calling `pause(true)`/`pause(false)` **directly on a `BatchSimulator` instance from a test**, not through any user-facing surface. So the Definition of Done can be fully satisfied — H1 through H4 not refuted, P3/P4 green, `mvn verify` green — while an instructor running `jls -b -t vectors.txt circuit.jls` from a terminal still has **zero way to pause** a running batch job. That directly contradicts the Abstract's headline claim: "an hours-long batch run can be paused, watched and interrupted without losing its output." "Watched" (heartbeat) and "interrupted" (SIGINT/SIGTERM) are genuinely CLI-reachable; "paused" is not, in this task's own scope — it's built purely as a library seam for future consumers (#214's panel, #350's campaign runner), which is a legitimate thing to build, but the issue markets it as if a user gets it today.

**Recommendation:** either (a) narrow the Abstract/title to "pause becomes a real, resumable operation on the engine, consumed by #214/#350" rather than implying CLI-level pause exists after this task, or (b) add the missing CLI/signal wiring and its own predictions.

### 4. (MEDIUM — feasibility/portability) "Clean interrupt on all three CI platforms" glosses over a real Windows gap

Open Question 1's recommended default and Threat T3 both assume `SIGINT`/`SIGTERM` delivered via one shutdown hook is a portable mechanism testable "on all three CI platforms," with the fallback being "tag and skip with a recorded reason... never silently skip." On Windows, the only way a JUnit test can ask the JVM to terminate a *child* process (the batch subprocess under test) via `java.lang.Process` is `destroy()`/`destroyForcibly()`, and `Process.destroy()` on Windows is implemented via `TerminateProcess` — there is no POSIX-style graceful-SIGTERM-then-run-shutdown-hooks distinction exposed by the JDK's Process API on that platform the way there is on POSIX. This is exactly the "apparatus risk" the issue itself flags in section 6 ("Signalling a subprocess portably is the one apparatus risk") but the issue never resolves it, and Threat T2 only distinguishes clean-interrupt from `SIGKILL` in the abstract, without naming this concrete platform gap. Given T3's own worry about a silently-skipped interrupt test, Windows is the platform most likely to legitimately need the tag-and-skip escape hatch, and the issue should say so up front rather than leave it for the executor to discover.

**Recommendation:** name the Windows signalling gap explicitly in section 6/Threat T3, and decide now whether the interrupt test is POSIX-only-with-a-recorded-Windows-waiver, or find an actual Windows-portable mechanism (e.g., a well-known sentinel file the batch process polls in addition to the shutdown hook) before filing this as "must hold after" on all platforms.
