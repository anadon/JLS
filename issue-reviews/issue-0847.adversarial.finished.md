# Issue #847: TASK-C574-2: each gallery entry links to its own demo page, generated from the same manifest — an example with no demo cannot advertise one
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what's being proposed

A task-tier issue: wire the published example gallery (#551) so each demo-enabled
example links to its own hosted demo page (#573), with links generated from a
shared manifest and a build-time check that catches drift. It is filed as
`part_of_feature: 574` (FEAT-C32-3), itself under capstone CAP-32 (#516).

Nothing in this chain has landed yet. `resources/samples/**` and any
gallery-generation code do not exist in the repository at HEAD (confirmed by
glob); #548 (the curated example set), #551 (the gallery), #572 (the browser-demo
feasibility spike) and #573 (the demo pages) are all still open. #847 is being
filed four layers deep into a tree of unbuilt infrastructure.

## Findings, most severe first

**1. The task's central assumption — a checkable "demo bundle" with one
target per example — depends on an upstream go/no-go that hasn't happened.**
#847 orders after #573 (FEAT-C32-2), whose own header says `ordering_after:
["FEAT-C32-1 (#572) — its go/no-go picks this page's mechanism"]`. #572 is open
and its AC-4 explicitly frames three possible outcomes: (a) CheerpJ-wrapped
Swing GUI, (b) SVG render + JS signal player driven by pre-computed VCD, or (c)
"recorded video walkthroughs" if both fail. AC-3 of #847 — "A check fails the
build when the gallery claims a demo link whose target is not present in the
demo bundle" — presumes a bundle of discrete, per-example static-page targets
that a build step can enumerate and diff against. That shape holds for
mechanisms (a)/(b) but not for fallback (c): a set of hosted videos is not a
"demo bundle" with per-example build targets in the same sense, and the check
as specified would need to be redesigned or dropped. Filing this task with a
concrete build-check AC before #572's spike concludes bets on a specific
answer to a question the project has explicitly not yet answered.
*Recommendation:* block #847 on #572's go/no-go landing, or rewrite AC-3 to be
mechanism-agnostic ("a check fails when the gallery claims a demo for an
example the demo surface does not serve," without assuming a file-bundle
model).

**2. Possible direct contradiction with #573's own scope boundary.** #573's
boundary notes read: *"No export feature and no per-circuit HTML artifacts —
that was CAP-19's scope, closed not_planned; this page is a hosted demo of
curated examples only."* #847's outcome requires "each demo-enabled example
links to its **own** demo page" — i.e., a distinct addressable page per
example. Whether that's satisfied by a single generic viewer taking a
`?circuit=` query parameter (compatible with #573's "no per-circuit artifacts"
disclaimer) or requires one static HTML file per example (arguably exactly the
"per-circuit HTML artifact" #573 says is out of scope, and which traces back
to the CAP-19 capstone that was **closed `not_planned` at maintainer
direction**) is never resolved in #847's text. CAP-32 itself (#516) carries a
live warning that the maintainer may judge this whole lineage "inside the
CAP-19 refusal's intent" and close it. A task this concrete should not be
filed while its own parent feature's scope boundary is ambiguous on exactly
the point (per-example artifacts) that got the sibling capstone killed.
*Recommendation:* have #573 or #574 explicitly state the addressing scheme
(query-param anchor vs. discrete file) before #847 commits to a link-generation
contract against it.

**3. "The shared example manifest" is asserted, not established.** AC-2 says
"The links are generated from the shared example manifest, not hand-written."
Neither #551 (gallery) nor #573 (demo pages) commits to producing a single
shared manifest artifact: #551 AC-2 only promises "regenerated by one scripted
command," and #573 AC-4 only promises "serves the CAP-27 curated example set
(#548)" — with no shared-schema commitment between the two. If #551 and #573
land independently (plausible, since neither cites the other as a hard
schema dependency beyond "the gallery renders the curated example set" /
"serves the CAP-27 curated example set"), #847 may find there are *two*
independently-shaped manifests, not one, and its "not hand-written" premise
collapses into needing new integration work that isn't costed here.
*Recommendation:* either #551 or #573 (whichever lands first) should be
amended to name the manifest file/schema explicitly as a public contract the
other consumes, before #847 is actionable.

**4. Whole lineage is at nontrivial risk of not existing to build against.**
CAP-32's own provenance note states the sibling capstone CAP-19 (single-file
HTML circuit export) was closed `not_planned` at maintainer direction one day
before CAP-32 was filed, and CAP-32's text says plainly: *"If the maintainer
judges even this inside the CAP-19 refusal's intent, close this too."* Filing
a granular integration task (#847) three levels below a capstone that
self-flags a real chance of being closed as redundant is premature — if CAP-32
closes, #847 is wasted filing/planning overhead and possibly wasted
implementation if anyone starts on it before that's resolved.
*Recommendation:* hold task-tier filings under CAP-32 until the capstone's
go/no-go on scope (not just #572's technical go/no-go) is confirmed by the
maintainer.

**5. AC-3's build check is underspecified and gameable.** It doesn't say
which build: `mvn verify` (this is a Java/Maven repo per README/ARCHITECTURE,
with no existing web-tooling pipeline) or a separate static-site CI job. It
also doesn't say whether "present in the demo bundle" means the target *file
exists* or the target *page actually works* (loads, is interactive per the
capstone's own AC-1/AC-2 bar). A zero-byte placeholder file with the right
name at the right path would satisfy AC-3 as literally written while
violating the issue's own stated purpose ("an example with no demo cannot
advertise one" / no placeholder links) in spirit for the demo side.
*Recommendation:* name the actual build stage, and require the check to
validate against the same manifest entries the demo page build asserts as
"real" (e.g. cross-reference against #572/#573's own completeness signal,
not mere file presence).

**6. Minor — AC-1 tests absence, not correctness of presence.** "Examples
without a demo render without a broken or placeholder link" is satisfied by
simply omitting a link — trivial and fine — but nothing in #847's ACs
verifies that links which *are* emitted actually resolve post-deploy (only
that a local build-time bundle contains a same-named target, per AC-3). A
renamed or moved demo page after deploy would break the live gallery link
while every stated AC still passes. Low severity since this is a common
static-site gap and may be covered by more general link-checking
infrastructure (README mentions `HelpTopicsTest`'s link checker as prior art
for exactly this kind of problem, `ARCHITECTURE.md:216-218` — worth reusing
the pattern here).
*Recommendation:* note the link-checker precedent explicitly as the intended
mechanism, or accept the gap as out of scope and say so.

## What's solid

- **AC-5 (keep the install call-to-action)** is well-grounded: #551 AC-3
  already commits the gallery to linking back to install instructions, so
  this AC is a non-regression check, not new scope. One line, no issue.
- **The core motivation** — generated links so an undemoed example can't
  falsely advertise a demo, and a newly-demoed example doesn't need a human
  to remember to wire it up — is a reasonable, narrowly-scoped engineering
  goal once its prerequisites actually exist.
- **`part_of_feature`/`ordering_after` bookkeeping** correctly mirrors #574's
  own AC-2, so the task is at least traceable to a real parent AC rather than
  invented scope.

## Bottom line

The idea is sound in isolation, but the issue commits to a concrete
build-time contract (a "demo bundle" with per-example checkable targets, a
"shared manifest") against upstream work that (a) hasn't chosen its
mechanism, (b) hasn't committed to the schema this task assumes, and (c) has
a live, self-acknowledged risk of being scope-closed entirely. File this task
again — or amend it — once #572's go/no-go lands and #573/#551 name their
shared manifest explicitly.
