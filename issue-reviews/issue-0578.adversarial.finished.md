# Issue #578: FEAT-C33-4: a third party can author a course kit from the documented convention, and one complete worked course proves the convention holds
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of the ask

Define a "course kit" convention (labs + grading vectors + schedule + rubric), ship a validator that checks a kit directory against it, ship one worked kit (the FEAT-C33-1 Donzellini pack), give kit content a license distinct from GPLv3 code, and have a named external instructor review the kit and the authoring doc. Zero course-kit scaffolding exists in the tree today (confirmed: no `course-kit`/`CourseKit` hits anywhere under `/home/user/JLS`), so this is greenfield convention design, not a refactor of something already partially built.

## Findings, most severe first

**1. The title's central claim is never actually tested by any AC.** The title and Outcome promise "a third party can author a course kit from the documented convention... without asking a maintainer how." None of AC-1 through AC-5 requires a third party to independently *author* a new kit from the doc alone. AC-5 only requires a named external instructor to *review* the existing worked kit and the authoring doc and have their feedback "addressed or refused by name" — reviewing prose is not attempting to follow it. It is entirely possible to satisfy all five ACs — spec written, validator green, one maintainer-authored kit shipped, license stated, reviewer comments logged — while the actual claim in the title (a stranger, working only from the doc, produces a conforming kit unassisted) remains unverified. Recommendation: add an AC that gates on a person who is not a project maintainer and did not co-design the convention producing a kit (or a kit fragment) that passes the AC-2 validator with no maintainer intervention beyond the published doc — this is the one AC that would actually falsify the title's claim, and it is the one missing.

**2. AC-5's external-reviewer dependency is soft and already double-booked.** AC-5 requires "a named external instructor — starting from #509." #509 records only that Dr. Siever "is interested... if it becomes well enough matured" — a conditional expression of interest, not a commitment to review anything, let alone twice. #575 (FEAT-C33-1, this issue's own designated worked instance) already carries its own external-review gate at AC-4: "a non-author completes each lab within its stated time budget." If the same single named candidate (there is only one external instructor named anywhere in this cluster) is expected to serve both #575's per-lab completion review and #578's kit-and-authoring-doc review, that's two review cycles asked of one person whose only recorded commitment is "interested if mature." If they decline, are unavailable, or the courtship (#509) stalls, both #575 AC-4 and #578 AC-5 stall together with no fallback named. Recommendation: name a second candidate reviewer or an explicit fallback (e.g., a different instructor from the CAP-33 evidence base) before this AC is treated as plannable, and clarify whether #575's and #578's reviews are the same review event or two.

**3. Sequencing risk is real and understated.** `ordering_after` lists "FEAT-C33-1 (the worked instance)" and "FEAT-C33-2 (the workflow a kit plugs into)" — i.e. #575 and #576 by the comment-thread's own mapping. Both are open, unlanded (band 3-5 mw and 2-3 mw respectively), and #576 in turn orders after "#300 CAP-06 verdict slice," which is itself open and unlanded (confirmed via `issue_read` — `"state":"open"`). So AC-3 ("walked end to end through the FEAT-C33-2 workflow") cannot even begin until a three-deep chain of open, independently-scoped features lands: #300 → #576 → #578-AC-3, with #575 needed in parallel for the kit content itself. None of that chain depth is called out as a risk in this issue's own text; it is only recoverable by cross-reading three other issues. Recommendation: state the transitive dependency depth explicitly in this issue (not just the immediate `ordering_after`) so the band_mw estimate and any kill-criteria decision account for it.

**4. Cross-issue references use feat_id strings instead of issue numbers, inconsistent with sibling issues.** `ordering_after: ["FEAT-C33-1 (the worked instance)", "FEAT-C33-2 (the workflow a kit plugs into)"]` — no `#nnn` anywhere in the frontmatter, unlike #552 (`ordering_after: [548]`) or #517 (`"#300 CAP-06 verdict slice"`, `"#511 CAP-27 PF-5"`). The mapping from feat_id to issue number only exists in a *comment*, not in the issue body itself, and the comment even flags the ids as "PROVISIONAL — renumbered in the adversarial phase." If FEAT-C33-1/2 get renumbered, this issue's own ordering_after goes stale with nothing in the body pointing at a stable anchor. #575's boundary note has the same fragility in reverse ("under the kit content license (see FEAT-C33-4)" — a feat_id self-reference, not `#578`). Recommendation: put the issue numbers in the frontmatter alongside or instead of the feat_ids now that they're known (#575, #576), matching the convention every sibling issue in this batch already uses.

**5. AC-2 cannot be meaningfully exercised until AC-3 lands, despite being listed as if independently gatable.** "A validator checks a kit directory against the convention... CI runs it over every shipped kit." At filing time there are zero shipped kits (grep confirms nothing in the tree). The validator can be unit-tested against synthetic fixtures, but the "CI runs it over every shipped kit" clause is vacuously true until #575's kit exists — so AC-2 as literally written could be declared "done" on a validator that has never actually validated a real kit. Recommendation: make AC-2 explicitly require at least one non-trivial real-kit run (i.e., tie it to AC-3 landing) rather than leaving it satisfiable by an empty CI matrix.

**6. Licensing AC is underspecified on the boundary that actually matters here.** AC-4 says kit content "carries a stated open license distinct from the code license" but does not say what happens to the parts of a kit that are also loadable inputs to the GPLv3 program — starter `.jls` circuit files and `-t` grading-vector files are structurally "content" by this issue's framing but are also machine-consumed artifacts the same way `resources/help/**` (in-jar, shipped inside the GPLv3 jar per ARCHITECTURE.md) is. The issue doesn't say whether kit `.jls`/vector files are covered by the content license or the code license, nor whether they physically live inside the same distribution artifact as GPLv3 code (jar) or a separate one. README.md's license section shows this project is already careful about provenance and license attribution (the pop_GPLv3.pdf letter, the "or-later" election note) — a course-kit license clause this loosely specified is a real hazard for a project with that level of license hygiene elsewhere. Recommendation: specify per-file-type license assignment (prose vs. `.jls` circuits vs. `-t` vectors vs. schedule/rubric) and where in the distribution kits live (in the GPLv3 jar, a separate repo, a separate release asset) before AC-4 is called satisfied.

**7. AC-1's "specified in tree" leaves the artifact format completely open.** No indication of whether the kit-layout spec is a schema file, a doc page, a directory of examples, or all three, and no acceptance test can distinguish "specified" from "described in prose somewhere." Minor relative to 1-3, but worth tightening so AC-2's validator has a fixed contract to validate against rather than a moving prose target.

## What's solid

- The four-way split with #575/#576/#577 (content vs. workflow vs. real-course fixtures vs. convention+validator+enforcement) is coherent and each issue's own boundary notes agree with each other — no overlap contradiction found across the four bodies.
- AC-2's core idea (a validator that names what's missing/malformed, wired into CI) is concrete, automatable, and the right mechanism for a "convention, not just a doc" outcome.
- `serves_capstones`/band_mw (3-4 mw here) is consistent with #517 CAP-33's own PF-4 line ("Course-kit template + one complete worked course (3–4 mw)") — no inflation or mismatch against the parent capstone.
- The boundary notes correctly push platform delivery to #502 and the grading engine to #300 rather than re-owning either, and #502/#300's own bodies confirm they don't claim kit-authoring territory back.
