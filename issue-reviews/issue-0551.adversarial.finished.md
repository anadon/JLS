# Issue #551: FEAT-C27-4: every shipped example is browsable as a published SVG gallery page — a prospective user sees real circuits before installing anything
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: sound-with-concerns

## Summary

The core idea — a static SVG gallery built on the already-shipped `-i out.svg`
export — is real and low-risk technically (`src/jls/JLSStart.java:353-355`,
`src/jls/edit/CircuitRenderer.java`, backed by `test/jls/SvgExportTest.java`
and `test/jls/CliImageExportTest.java`, which do exist and do pass a
byte-identical-export goldenness bar). The issue's own boundary notes
against #536, #516, #519 and the dedup pass in the one comment (vs #573,
#574) hold up against those issues' actual text — no contradiction found
there. The problems are in the acceptance criteria: several are either
unverifiable by this issue alone or satisfiable by doing (close to)
nothing.

## Findings, most severe first

**1. AC-3 depends on a hand-off (#545) that isn't sequenced against this issue, so AC-3 may never become verifiable from #551's side.**
Quote: "AC-3: The README links to the gallery (hand-off to FEAT-C27-1,
#545)." But #545's own body only commits to "links to the FEAT-C27-4
gallery page **when it exists**" and #545's `ordering_after: [381]` does
not list 551, while #551's `ordering_after: [548]` does not list 545.
Nothing forces #545 to actually land the link once #551 ships, and #551
has no criterion that is verifiable by #551's own PR — closing #551
"done" requires either editing #545-owned README prose from inside this
issue's PR (scope creep into #545) or trusting a future, un-sequenced
issue to pick it up. Recommend: either add `ordering_after: [545]` isn't
right either (it's a forward link, not a prerequisite) — instead, change
AC-3 to something #551's own PR can satisfy end-to-end, e.g. "this PR
adds the README link itself, coordinating with #545's owner" or drop the
word "hand-off" and state plainly which issue's PR contains the edit.

**2. AC-2's regeneration contract is underspecified and gameable.**
Quote: "AC-2: The gallery is regenerated by one scripted command in CI or
the release flow, so renders cannot silently drift from the circuits they
depict." This doesn't say whether CI (a) fails the build when a fresh
regeneration differs from the committed gallery (a drift *gate*), or (b)
auto-commits/publishes fresh renders on every run (a drift *eliminator*
that pushes back to the repo). These are very different builds: no
existing workflow in `.github/workflows/` grants `contents: write` by
default (see `release.yml`'s explicit least-privilege elevation pattern
at the top of that file) or auto-commits back to the tree; a push-back
gallery job would be new infrastructure with its own loop/permission
risk. As written, a PR could add a working shell script that is never
wired into any workflow trigger and technically satisfy "regenerated by
one scripted command" (the command exists and works when run by hand)
while the checked-in gallery quietly goes stale — exactly the drift the
AC claims to prevent. Recommend: state explicitly whether CI gates on
diff or CI publishes fresh, and name the workflow/job.

**3. AC-4's dark/light-theme criterion is trivially satisfiable and therefore checks nothing.**
Quote: "AC-4: The page renders acceptably in both light and dark browser
themes, or ships a single theme deliberately and says so." The exporter
this issue reuses verbatim already only ever produces a hard-coded white
background — `svg.setColor(Color.white)` at
`src/jls/edit/CircuitRenderer.java:323` (SVG export path) and again at
line 372 (print path). Because "ships a single theme deliberately and
says so" is an accepted branch, the AC is satisfied by writing one
sentence and doing zero design work — the exact do-nothing outcome the
existing code already produces. If the real goal is "the gallery doesn't
look broken to a visitor on a dark-theme browser," the AC needs a
positive requirement (e.g., the gallery page itself always renders each
SVG inside a fixed light card/frame regardless of page theme), not a
disjunction where the null option wins by default.

**4. The gallery's entire content source (#548) doesn't exist yet, and its shape is still open, which makes #551 unestimatable in isolation.**
Verified: `examples/` in this checkout contains only `examples/autograde/`
(an autograder script), and every `.jls` file in the repo
(`test/fixtures/*.jls`, `riscv/gui/cpu.jls`) is a test fixture, matching
CAP-27's own baseline finding ("`examples/` contains no user-facing
circuits — every .jls in the repo is a test fixture or the unsurfaced
RV32I showcase," #511). #551 correctly declares
`ordering_after: [548]`, so this is not a contradiction — but AC-1 ("every
circuit in the Examples set") means #551's scope, size, and even the
on-disk location of its source material are all unknown until #548 lands
and decides where the curated `.jls` files live (`resources/samples/`
per #548's boundary note, i.e. classpath resources bundled into the jar,
not loose files in a repo directory). The CLI's `-i` export path takes a
filesystem path (`JLSStart.java` around line 353, loading via a
`Scanner`/`FileAbstractor`, not the classpath), so the CI step generating
the gallery must run against pre-jar source files on disk, not the
packaged resources — a detail #551 never states and that #548 doesn't
pin down either. Recommend: #551 should not be estimated/started until
#548 fixes both the final example count and the on-disk source location
CI will point `-i` at.

**5. No page-weight or size ceiling despite an explicit scope-cliff warning.**
The issue warns itself off CAP-35's scope ("the gallery is a single page
and must not grow into that scope") but gives no numeric or structural
bound. #548 AC-2 requires "the RV32I showcase" (a CPU-scale design, per
ARCHITECTURE.md's own note about `riscv/` designs) among the curated set;
a full-resolution SVG render of a datapath-scale circuit embedded inline
in a one-page gallery alongside ≥10 other renders has a real risk of
producing a large, slow-loading page with no criterion catching it.
Recommend: add a concrete constraint (thumbnail + link-to-full-SVG, or a
byte/count ceiling) rather than leaving "must not grow into that scope"
as the only guardrail.

**6. "Published via the repository or GitHub Pages" treats two very different-effort options as interchangeable.**
Checked `.github/workflows/*.yml` (`ci.yml`, `release.yml`,
`repro-installers.yml`, `mutation.yml`, `codeql.yml`, `scorecard.yml`):
none reference `actions/deploy-pages`, `actions/upload-pages-artifact`,
or any `gh-pages` publishing step — there is no existing Pages
infrastructure in this repo today. Standing up real GitHub Pages hosting
(enabling Pages in repo settings, a new `pages: write`/`id-token: write`
permission block, a new workflow) is meaningfully more work than
committing a static HTML/SVG page into the existing repo tree and linking
GitHub's raw/blob rendering of it. Because AC-2/AC-3 don't distinguish
between the two, the path of least resistance (repo-committed page) is
also the one that least matches the stated outcome — "a prospective user
browses real circuits before installing anything" reads much more
naturally for an actual public Pages URL than for a page a visitor has to
already be inside the repo to find. Recommend: pick one mechanism
explicitly rather than leaving it an implementation detail.

**7. No inherited licensing/provenance discipline for the published assets.**
#548 records "Fresh authorship rule... samples are authored clean for
licensing" as a load-bearing constraint for the very circuits this
gallery renders and republishes as standalone SVG/HTML assets outside the
jar. #551 says nothing about carrying that guarantee forward (e.g., an
explicit license/attribution line on the gallery page), even though the
README elsewhere in this project is unusually careful about provenance
(the GPLv3 letter, `pop_GPLv3.pdf`, custody rationale for release
signing). Minor, but worth a one-line AC given the project's own stated
care here.

## What's solid (no rework needed)

- The core mechanism claim is accurate and tested: `-i out.svg` genuinely
  ships and works headlessly (`CliImageExportTest.java`,
  `SvgExportTest.java`), so "rides on export machinery that already
  ships" is not an overstatement.
- `ordering_after: [548]` is the correct dependency and is honestly
  stated rather than glossed over.
- The boundary notes against #536 (print styling), CAP-32/#516 (browser
  runner), and CAP-35/#519 (versioned manual/screenshot pipeline) are
  consistent with those issues' own stated scopes, and the one existing
  comment's dedup pass against #573/#574 draws a real, non-overlapping
  line (static picture vs. running demo) rather than papering over
  duplication.
