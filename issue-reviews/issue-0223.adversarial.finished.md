## Findings (most severe first)

### 1. The issue body's machine block is self-contradicted by its own latest comment
**Evidence:** The body's YAML states `requires_tasks: [277]` and §6 says *"#277 is unblocked now and independent of all three pending-row landings."* But the last comment on the issue (`#223#issuecomment-5227342747`, created `2026-08-08T17:45:50Z` — the same timestamp as the issue's `updated_at`) opens: *"This comment supersedes the `requires_tasks` line of the machine block and the §6 claim that '#277 is unblocked now'... Corrected: `requires_tasks: [277, 403]`"* and *"#277 is now `blocked_by: [403]`."* The body itself was never edited to reflect this — I fetched it fresh and it still reads the old way.
**Why it matters:** This project's own REPLAN protocol treats the YAML machine block as the authoritative, parseable state (that's the entire premise of "machine block, roster, and mermaid agree with reality" appearing in nearly every Completion Criteria in this repo's issues). Here it does not agree with reality by the project's own admission, in a comment attached to the very issue whose body is stale. Anyone acting on the frontmatter alone — including an automated agent — would start #277 believing it has no blockers, when the issue's own latest analysis says it must wait on #403's determinism apparatus first.
**Recommendation:** Before any work is picked up, edit the issue body (not just add another comment) to reflect the corrected `requires_tasks`/`blocked_by`/§6 state, or explicitly mark the current body as superseded pending a REPLAN edit. Do not let a fourth comment further correct a body nobody is updating.

### 3. The stated acceptance criterion for the dispatch consumption is gameable, and the issue's own thread admits it without fixing the criterion
**Evidence:** §5 criterion 3 says: *"After #277: consumer call sites exist and a contribution registered before boot is consumer-visible, with golden suites unchanged."* The final comment on the issue directly undercuts this: *"criterion 3... its evidence value now depends on #403 having landed first — otherwise 'golden suites unchanged' is a weaker claim than it appears, since nothing in the tree yet distinguishes 'contribution order is correct' from 'contribution order happens to match today's static-table order.'"*
**Why it matters:** This is exactly the kind of acceptance criterion this review is supposed to hunt for: it can be satisfied (golden suite green) for a reason unrelated to the real goal (deterministic, registry-driven dispatch order). A future engineer, or an autonomous agent, working only from §5 as written would consider criterion 3 met by a green `mvn verify` run even if the underlying ordering bug the criterion was meant to catch is present but happens not to be triggered by today's fixed four-module contribution set. The issue's own comment flags this but only as prose — §5's actual text is unchanged.
**Recommendation:** Rewrite criterion 3 to require the permuted-declaration-order determinism test (already specified in #403 as P4/H3) as a precondition of "golden suites unchanged" counting as evidence, not as a separately-tracked nice-to-have in a sibling issue.
