# Issue #528: FEAT-C21-4: a PrairieLearn question grades a JLS lab through the in-tree external-grader image, driving batch mode only
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: sound-with-concerns

## Summary of the ask

FEAT-C21-4 (PF-4 of capstone CAP-21, #502) asks for an in-tree PrairieLearn
external-grader image plus an example static question kit: a course points a
question at a JLS lab in the CAP-06 lab-as-data format, the image invokes JLS
batch mode against the pinned CLI contract of FEAT-C21-1 (#524), and returns
per-test results in PrairieLearn's native format. Confirmed against the repo:
no file mentions PrairieLearn (`grep -rli "prairielearn" .` outside
`issue-reviews/` returns nothing), consistent with #502's own background
section. This is greenfield work; nothing here is buildable yet.

## Findings, most severe first

**1. (High) The real dependency chain is several times deeper than `ordering_after` discloses, and `band_mw: 2` reads as the whole cost.** The front matter declares `ordering_after: ["FEAT-C21-1"]` only. #524 is itself `ordering_after: [369, 466]` — FEAT-053 (#369, open, its own cost note says its task rows already sum to 8 wk against a 9-15 mw band with two sub-tasks unfiled) and TASK-0111 (#466, open, itself blocked on an unfiled TASK-0021). None of `Expectations`, `TestVectorRunner`, `GradeReport`, `-check`/`-report`, or exit status 3 exist in the tree (`docs/batch-interface.md` §1 still documents exactly three exit statuses: 0/1/2). So #528's real critical path is TASK-0021 (unfiled) → #466 → #369 → #524 → #528 — several maintainer-months of unstarted work — none of which the issue body states. A reader who takes `band_mw: 2` at face value, without walking the graph, will underestimate this by an order of magnitude. This is the identical defect the sibling nbgrader issue (#530, finding 1) was flagged for; it recurs here verbatim. **Recommendation:** state explicitly that the estimate is marginal-only and excludes the unlanded #524/#466/#369 chain, as #466 and #369 already do for themselves.

**2. (High) AC-2's "byte-identical" claim has no referent inside this issue, and the one place that referent should live (#531/#719) doesn't own it cleanly either.** The acceptance criterion reads: *"Per-student scores for the fixture class are byte-identical to the other adapters' vectors from the same xUnit input (feeds CAP-21 AC-1)."* PrairieLearn's `results.json` payload (a nested JSON structure with `gradable`, `score`, per-test `feedback` blocks) has no byte-level correspondence to Gradescope's `results.json`, a GitHub Action summary, or an nbgrader gradebook export — comparing raw bytes across these is definitionally impossible, only a derived, normalized per-student score vector can be compared. That normalization step is not defined in #528, and per my reading of the sibling #531 review (issue-reviews/issue-0531.adversarial.md, finding 1), it currently lives only in child task #719, not in #531 either — so as of this writing there is no filed issue anywhere in the tree that actually specifies what "byte-identical" is measured over. An implementer following #528 alone has no way to know whether they are extracting `score` fields, `points`/`max_points`, or some other field, and could satisfy the letter of the AC by wrapping PrairieLearn's payload in an arbitrary envelope that happens to match whatever #531 eventually decides. **Recommendation:** either replace AC-2 with "produces a normalized per-student score vector per the schema #531/#719 defines" (deferring the comparison, as the issue's own comment already frames it — "this adapter supplies an input, #531 performs the comparison"), or block AC-2 explicitly on that schema landing first.

**3. (Medium) AC-1 depends on "the CAP-21 fixture lab," which #528 never declares as a dependency.** AC-1 says the kit is run "against the CAP-21 fixture lab" — that fixture (the one lab + 300-submission corpus) is PF-6's deliverable, tracked as #531, which the sibling review (issue-0531.adversarial.md) already flags as `needs-rework` with an untestable AC-1 of its own. Yet #528's `ordering_after` lists only `["FEAT-C21-1"]`; #531/PF-6 is absent. #502's own mermaid graph has `PF6 --> CAP21` (the capstone), not `PF6 --> PF4`, so the capstone-level graph doesn't require it either — but #528's own acceptance text plainly needs a fixture that doesn't exist and isn't scheduled ahead of it. A maintainer scheduling work strictly off `ordering_after` fields (the convention this repo's issue graph documents and relies on, per the #531 review's finding 3 making the identical point in the opposite direction) would conclude PF-4 is startable once #524 lands, then discover it has no fixture to run against. **Recommendation:** add 531 (or whichever issue ultimately owns the fixture lab) to `ordering_after`.

**4. (Medium) "No interactive session is ever opened" names no verification mechanism for an external-grader image.** AC-1 cites CAP-21 §1 step 3, AC-4, and #498 §7.2, but all three are capstone-level references, not a concrete test scoped to *this* image. PrairieLearn's `externalGrader` contract runs the grading container itself, invoking arbitrary entrypoint logic inside it — "no interactive session" here has to mean something like "the container's entrypoint never launches JLS without `-b`" or "no AWT/Swing class ever loads in that container's JVM," verifiable by the same classpath-scan idiom `HeadlessCoreRatchetTest` already uses (per `ARCHITECTURE.md`: "`Simulator` and `BatchSimulator` import no AWT, Swing, or `jls.edit`"). As written, an implementer could satisfy AC-1's letter by asserting something trivial (e.g., "the entrypoint script never calls the interactive JLS jar") without ever proving the invoked process stays headless end to end. This is the same gap the nbgrader sibling (#530, finding 2) was flagged for, recurring here for the image-based adapter. **Recommendation:** name the concrete mechanism (e.g., a `HeadlessCoreRatchetTest`-style scan of the image's JVM invocation) rather than relying on the capstone-level AC-4 by reference.

**5. (Low) Missing the sibling's "graceful degradation, named error" boundary note.** #525 (Gradescope, the closest sibling in shape) carries an explicit boundary note: "the adapter... degrades with a named error, never a silent misgrade, if the spec moves" — a runtime behavior distinct from the CI-lane drift detection both issues also state. #528 has the CI-lane note ("externalGrader contract drift surfaces as a red lane in the adapter's dedicated CI lane") but no equivalent runtime-degradation note for a course actually running the image against a shifted PrairieLearn contract mid-semester. Given PrairieLearn is also a third-party platform whose contract can move on its own schedule, the same silent-misgrade risk applies. **Recommendation:** copy #525's degrade-with-named-error clause.

**6. (Low) `band_mw: 2` is a bare point estimate where every other issue in this cluster uses a range.** #524 (`2-3`), #525 (`2-3`), #530 (`1-2`) all state ranges; #528 states a single value `2` (matching #502's own cost breakdown line "PF-4: 2 mw," so it's at least internally consistent with the capstone, not a transcription slip). Still, given finding 1's point that the marginal estimate already excludes several maintainer-months of unlanded prerequisite work, a bare point value reads as more precise than the underlying estimate can support. **Recommendation:** widen to a range or add the same "marginal only" caveat as finding 1 recommends.

## What's solid

- The static-vs-randomized-generator scoping is clean and consistent with CAP-21 Open Question 4: "the randomized-generator kit is CAP-21 Open Question 4, deferred to the Java-first `jls.api` (M2-gated per #498 §7.2)" is a real boundary, not scope creep dressed as a boundary note.
- "Targeting PrairieLearn's documented externalGrader contract only" in the outcome statement correctly inherits CAP-21 risk 5's "documented contract only, no scraping" discipline, matching #525's Gradescope framing.
- `ordering_after: ["FEAT-C21-1"]` at least correctly names the direct blocker (#524), even though (per finding 1) it omits the transitive chain.
- The issue's own comment records a real pass-1/pass-2 deduplication adjudication against the other three platform adapters (#525/#526/#530) and the parity fixture (#531), with a stated, defensible "no merge" verdict and rule citation (rule 3(c): same shape, different outcome) — genuine cross-issue scrutiny already happened before this review, not just asserted.
- The CI-lane drift-detection acceptance criterion (bullet 5) is present and correctly cited to CAP-21 risk 1 / KC-21-3, unlike sibling #530 which the fleet review caught omitting it entirely.

## Note

Findings 2 and 3 both trace back to the same root cause already diagnosed in the #531 review: the cross-adapter comparison apparatus (PF-6/#531/#719) is itself unsettled, so every adapter issue that references it — #528 included — inherits an acceptance criterion it cannot locally verify. Fixing #531/#719 first would resolve this issue's AC-2 and the fixture-dependency gap (finding 3) as a side effect, without #528 needing its own rewrite of that logic.
