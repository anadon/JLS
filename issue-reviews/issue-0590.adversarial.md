# Issue #590: FEAT-C36-3: the successor positioning statement has a published home, and a flare-moment release ships with a writeup submitted somewhere instead of a bare tag
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what's being asked

A non-code documentation feature (CAP-36 PF-3, `serves_capstones: ["#520 CAP-36 PF-3"]`): publish the #510 §5 positioning statement ("the maintained successor in the Digital tradition") identically in the README and a site "about" page, add an in-tree flare-moment announcement checklist, exercise that checklist at least once, and hold announcement competitor-claims to the same evidentiary bar as a sibling feature. Five ACs, one prior boundary-dedup comment against #582 already resolved cleanly on the issue itself.

## Findings, most severe first

**1. AC-1 requires publishing to a "site 'about'" page, but this project has no website, and the boundary note directly contradicts that requirement.** AC-1: *"the statement appears in a canonical location (README and site 'about')."* The Boundary notes then claim: *"Non-code deliverable. No new machinery is required beyond publishing text and keeping a checklist honest."* Both cannot be true. `docs/standards-adoption/10-desktop-and-housekeeping.md:104-119` states plainly: *"an offline-first project with no website ... GitHub Pages. The project has no published site today (`ARCHITECTURE.md` § 'Help delivery: in-jar now, hosted docs are the planned future'), so this presupposes work not yet done."* `ARCHITECTURE.md`'s own recorded decision ("Help delivery: in-jar now, hosted docs are the planned future") confirms hosted web documentation is a future direction, not a shipped artifact. As written, AC-1 is unsatisfiable without first building and deploying site infrastructure — work this issue's own boundary note says isn't required. Recommendation: either scope AC-1 to README-only until a hosting capstone exists and ships, or add an explicit `ordering_after` dependency on that (currently unfiled) site-launch work, and strike the "no new machinery" claim.

**2. AC-4 cites the wrong acceptance criterion from the feature it depends on.** AC-4: *"Claims in announcements inherit the AC-2 standard of FEAT-C36-1."* FEAT-C36-1 is #588, whose actual **AC-2** reads: *"Every JLS claim has a runnable appendix."* That is about reproducibility of JLS's own claims, not about citing or freshness-checking competitor claims. The behavior #590's AC-4 actually describes — *"cites the competitor's own tracker and is checked against their current release at posting time"* — matches #588's **AC-3** ("Every competitor claim is cited to the competitor") plus **AC-4** ("Freshness is a gate, not a promise"), not AC-2. A future implementer following the letter of #590 AC-4 back to "the AC-2 standard" lands on the wrong requirement entirely. Recommendation: correct the citation to "AC-3/AC-4 of FEAT-C36-1" before this cross-reference is treated as load-bearing.

**3. AC-1's evidence requirement ("links to the comparison notes and white paper") outruns the issue's own `ordering_after` list, which omits the white paper dependency.** The frontmatter's `ordering_after` names only two items: `"#545 FEAT-C27-1"` and `"#520 PF-1"` (= #588, the comparison notes). It does not list PF-2, the grading-contract white paper — confirmed as #589 by #520's own coverage-verification comment ("PF-2 — Grading-contract white paper ... #589"). Yet AC-1 requires the published paragraph to link "the comparison notes **and white paper** as its evidence." A positioning statement written and closed against the stated `ordering_after` set can satisfy AC-1's letter with a dead or missing white-paper link, because nothing forces #589 to exist first. Recommendation: add #589 to `ordering_after`, or relax AC-1 to make the white-paper link conditional on #589 having shipped.

**4. AC-3 is gameable on which release counts as "exercised."** AC-3: *"At least one release has gone out under it, with the writeup and the posting links recorded in the release notes."* The Outcome paragraph frames the checklist's whole purpose around a "flare moment" (the Linux-boot demo, #508 item 4) — but AC-3's text does not require the exercising release to actually be a flare moment. A routine patch release run through the checklist with a perfunctory two-line "writeup" and no real venue posting would satisfy AC-3's letter while leaving the goal this feature exists for — the Linux-boot demo actually shipping with a real writeup instead of a bare tag — completely unaddressed. Recommendation: require the first exercised release to be self-identified as a flare-moment release per the checklist's own criteria, or add a second, explicit AC tied to the actual #508-item-4 release.

**5. "Worded identically in both places" (AC-1) has no enforcement mechanism, unlike this codebase's established convention for exactly this failure mode.** The sibling feature #545 (FEAT-C27-1) has AC-4: *"A drift check fails the build when a README-referenced image path does not exist on disk."* `ARCHITECTURE.md`'s "Help delivery" section and `HelpTopicsTest` show the project routinely backs duplicated-content claims with an automated ratchet. #590 has no analogous check for the two-copies-must-match claim it makes in AC-1: a reviewer can confirm identical wording at merge time, but nothing prevents the README and the (not-yet-existing) site copy from drifting apart on the next unrelated edit, and AC-1 as worded would already read "satisfied" from that point forward. Recommendation: add a lightweight identity check (e.g., one copy generated/included from the other, or a test asserting byte-equality of the extracted paragraph) or explicitly accept manual sync and say why it's sufficient here.

**6. Feasibility/cost: AC-3's real gating factor is release timing, which is outside this feature's control and outside its stated band.** `band_mw: "0.5-1 mw"` is plausible for AC-1/AC-2/AC-4/AC-5 (writing and a checklist file), but AC-3 cannot close until *some* release ships and gets a checklist-driven writeup — and the release that matters per the Outcome (the Linux-boot flare moment) is CAP-02's own ≈10 mw item (#508 item 4), not scoped here. The Boundary notes correctly disclaim control over reception ("not that it was received well") but say nothing about the schedule dependency, which is the more binding constraint on AC-3 actually closing. Recommendation: note the AC-3 schedule dependency explicitly, or decouple "checklist exists and is exercised once (on any release)" from "the flare moment specifically used it," matching the fix suggested in finding 4.

## What's solid

- AC-5 ("falsifiable, not promotional") is well-specified and checkable: every clause must map to something a reader can verify, unbacked clauses are cut rather than softened — a real, testable discipline rather than a platitude.
- The scope boundary against #553 (switcher map: existing competitor user vs. stranger-facing positioning) is precise and creates no overlap.
- The prior boundary-dedup comment against #582 (download-count instrumentation vs. this issue's self-description) is a clean, correct no-merge call — the only shared surface (a download number quoted in an announcement) is rightly treated as citation, not shared ownership.
- The honesty carve-out in the Boundary notes ("the AC is that the writeup exists and was posted, not that it was received well") is a mature, non-gameable framing of an otherwise-tempting reception metric, and correctly redirects any future reception-metric urge to #582's KPI policy instead of scope-creeping here.
