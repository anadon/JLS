# Issue #476: TASK-0063: the two data structures that cost 47.7% of warm loop time are replaced by a calendar queue and an intrusive queued flag, retiring the identical event sequence
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

The issue is unusually rigorous in form — a falsifiable-hypothesis structure, exact line citations, an explicit ordering proof (H1/stage 2), and a named threat list that correctly identifies the two subtlest real bugs a naive implementation would hit (T1 `seq` bucketing, T2 clear-before-`react`). Those parts are sound and I did not find fault in them against the current source (`src/jls/sim/Simulator.java`, `src/jls/sim/SimEvent.java` match the quoted excerpts almost verbatim). However, the issue's evidentiary foundation — the claim that its citations are current against HEAD — is independently falsifiable and I falsified it, its `blocked_by` list omits a dependency its own text says is necessary, it cites a closed-as-duplicate issue as active related work, and it commits to a benchmark location (a CI lane) that does not exist and is not a blocking dependency. A maintainer already filed one adversarial review comment on this issue (2026-08-08) catching three of these; my read confirms those findings independently from the checked-out source and adds one the existing comment did not raise (the long-run-lane dependency gap) plus a few second-order ones.

### 2. `blocked_by` omits #442, which the issue's own text calls necessary, not optional

Section 8 (Method) opens with *"Confirm #410 has landed"* and `blocked_by` in the machine block lists only `410`. But P6 says *"If #442 has landed, extend its gate instead of adding a second one"* — phrased as permissive, not blocking. The maintainer's own review comment on this issue quotes the parent feature #362 §6 stating the opposite: *"necessity under K3: the byte-identity gate is what decides whether each change may land. Landing a speedup and then building the gate that would have rejected it inverts the entire safety argument."* I fetched #442 directly: it is **open**, itself blocked by three other open issues (#377, #379, #413), so it has clearly not landed. If #476 is picked up before #442, the assignee either (a) invents an ad hoc byte-identity check that #442 will later have to reconcile with (duplicated, possibly divergent gate logic), or (b) blocks in place waiting on a dependency the issue never told them about. **Recommendation:** add `442` to `blocked_by` before assignment, as the maintainer's own comment already recommends.

### 3. `related: 475` cites a closed-as-duplicate issue

Section "Status & Dependencies" lists `475 # TASK-0056 - the other 37.6% of the same profile; independent, do not merge` and Threat T5 repeats the instruction not to merge #476 with #475. I fetched #475: `"state":"closed","state_reason":"duplicate"`, closed 2026-08-08 (the same day as this issue's last update). The maintainer's own review comment already caught this and redirects to `#878`/`#879` as the successor issues — but those numbers are unverified from inside this review (I did not fetch them; they may not exist yet, since #476 is well past #475's number and the successors are is-cited-but-not-visible in this issue body). Anyone reading the DoD item "Not landed together with #475, so each profile stays attributable" and checking off "#475 is closed, so this constraint is vacuously satisfied" would be wrong — the actual constraint (don't land alongside the value-representation work) still applies, just under different issue numbers. **Recommendation:** the issue body must be edited to replace `475` with its live successor(s), not left to a comment to silently correct — a DoD checklist item referencing a closed issue by number is a latent trap for exactly the kind of literal-minded verification this issue's own rigor otherwise demands.

### 4. The long-run CI lane P7 depends on does not exist and is not a blocking dependency

Section 5 lists P7: *"`SameTickScalingBenchmark.sameTickCostIsNearLinearInBurstSize()` — ... in the long-run lane"*, and Materials & Apparatus says *"a **long-run CI lane** existing for P7 - #378 owns that lane."* I fetched #378: it is **open**, and its own evidence section confirms `grep -rn "longrun" ... .github/workflows/` returns nothing at its evidence commit. I re-ran the equivalent check against the current tree and it likewise returns nothing — `pom.xml` has exactly two surefire executions (`default-test` excluding `display`, and `display-tests`), no `longrun` group. Yet `378` appears only in `related`, never in `blocked_by`, for #476. Section 8's checklist item *"Add `SameTickScalingBenchmark` in the long-run lane"* is therefore a checklist item pointing at infrastructure that must be built by a different, unblocked-for issue before this one's own DoD can be satisfied. This is the same class of error as finding #2 (a real, text-acknowledged dependency left out of the machine-readable `blocked_by`), independently found — the existing review comment did not flag this one. **Recommendation:** add `378` to `blocked_by`, or explicitly descope P7/the scaling benchmark to a follow-up if the long-run lane isn't ready, rather than asking the assignee to build CI infrastructure as an undeclared side quest inside a data-structure-swap task.

### 5. Underspecified acceptance criterion: "derived from measurement" for the bucket policy has no falsifiable bar

Open Question 1 asks for the bucket store shape and states *"Blocks execution. Decide by measuring against the census shape (H5, Threat T4), and record the measurement — not the constant."* P7's bound is likewise "a committed bound derived from measurement... nothing here is adjusted to fit." Compare this to TASK-0026 (#442)'s section 7.10, which is exhaustively specific about how bands must be one-sided, best-of-N, warm-up-discarded, etc. #476 provides no comparable discipline for its own "derived from measurement" requirements — there is no stated warm-up protocol, no stated number of reps, no stated ratio threshold for "near-linear," and no stated fallback if the measured curve is noisy (unlike #442's O4, which found and adjusted for a measured 4.2x same-JVM spread). An implementer could satisfy "near-linear... under a committed bound" by picking an extremely generous bound after a single noisy run and never be caught by any of the stated predictions, because P7 only asks that *a* bound exist and be met, not that the bound be tight enough to actually catch the quadratic-cliff regression T4 and the mermaid graph both cite as the reason this benchmark exists. **Recommendation:** either inherit #442's banding discipline explicitly (cite it, don't just imply it) or state a concrete acceptance ratio (e.g., "cost(32k)/cost(1k) must be within Nx of the same ratio for a linear reference") before this is picked up.

### 6. Gameable criterion: "does not compare" (H1) is not independently checked by any prediction

H1's headline claim — "reproduces `compareTo`'s total order **without ever comparing**" — is central to the issue's motivating performance story (avoiding heap-sift comparisons is presumably most of the claimed win alongside removing the hash). But no prediction in section 5 actually asserts that no comparison happens; P3 only checks that the *retirement sequence* matches the `PriorityQueue`'s. An implementation that quietly calls `compareTo` somewhere in the bucket-store's minimum-tracking (e.g. a `TreeMap<Long, List<SimEvent>>` keyed by time, which does compare on every `put`/`firstKey`) would pass every stated prediction (P1-P10) while violating H1 and, more importantly, while potentially not achieving the underlying performance claim the whole task exists to deliver. Falsification Criteria section 10 only checks H1 via P3 (order), never via a "no comparison happened" instrumentation check. **Recommendation:** add a prediction (or extend P10) that explicitly measures/asserts that `SimEvent.compareTo` is never invoked by the new queue on the hot path — a call-count instrumentation test, not just an outcome-equivalence test — or drop the "without ever comparing" framing since it currently isn't gated by anything falsifiable.

### 7. Interface contract for the intrusive flag conflicts with its own "no hashing" goal for value-carrying payloads, and the issue defers the hard case as "an implementation choice"

Section 7.5 states the flag "must be reachable from the `(callBack, todo)` identity without hashing (H3)" but then immediately says "the exact shape is an implementation choice constrained by 7.10 stage 3, not by this issue." H3's own falsification criterion (section 10) already anticipates this will likely fail for value-carrying payloads: *"most plausibly because value-carrying payloads need a content lookup... if hashing is unavoidable for a payload class, the achievable share is smaller and must be restated honestly."* So the issue's own hypothesis section predicts its own headline number (151.8 ns / 47.7%) is likely overstated for the general case, yet the Abstract and Intended Audience sections state the 47.7% figure as if it is the number this task will recover, with no caveat. This isn't a defect in the reasoning (the falsification criteria are honest about the risk) but it is a real internal tension: a reader skimming only the Abstract, not section 10, would expect a bigger win than the issue's own hypotheses consider likely. **Recommendation:** hedge the Abstract's headline figure, or state upfront (not buried in section 10) that the achievable share may be materially smaller once `NewValue`/`MemoryWrite`/`TableOutput`/`StateChanged` (all payload-carrying, non-`PinChanged`) are accounted for.

### 8. Scope-creep risk flagged by the issue itself is real but under-firewalled

Section 8's checklist includes "Consider interning `PinChanged` to a singleton" as a rideable item within this task, alongside the primary queue/flag work. The issue does correctly note interning changes allocation, not semantics (O5), and marks it optional ("if it is genuinely free; if it is not, file it") — but bundling *any* optional, independently-motivated micro-optimization into a task whose DoD is already ~28 checklist items long is exactly the kind of scope growth that makes review and bisection harder later, especially given T5's own insistence that #475/#879 (the value-representation leg) must **not** be merged with this task "so each profile stays attributable." Interning `PinChanged` inside *this* task blurs that same attribution boundary in miniature — a profile delta after landing #476 would be partly queue-swap, partly allocation-reduction from interning, and the issue provides no separate prediction isolating the two. **Recommendation:** drop the interning item from this task's scope entirely (file it under #232/#879 where the value-representation attribution already lives), rather than relying on assignee discretion mid-task.

## What's solid (brief)

- The core data-structure argument (H1, section 7.10 stages 1-2) is mathematically sound and matches the actual code: `seq` is assigned in the `SimEvent` constructor at the `post` call site (confirmed at `SimEvent.java:113-120`), so per-bucket FIFO ordering does reproduce `(time, seq)` order without comparison, given the stated invariant holds.
- The clear-before-`react` edge (T2, stage 4) is correctly identified as the subtlest real hazard in the existing code — confirmed against `Simulator.java:224-225` vs. `:239` — and the re-post-from-inside-`react` non-suppression case is a genuine, non-obvious behavior worth a named test.
- The `PinChanged`-equality trap (T3, O5) is correctly diagnosed: `SimEvent.equals` is reference-identity on callback and structural on payload, and `PinChanged` is confirmed as a zero-field record in the current source, so all instances are indeed mutually equal — a flag keyed on object identity would be a real, easy-to-miss bug.
- P9 (process-wide `seq`, never reset by `initSimulation`) is correctly derived from the code at `SimEvent.java:87` and `Simulator.java:181-182`, and is a genuinely non-obvious trap for anyone tempted to bucket on `seq % N`.

## Verdict rationale

`needs-rework`, not `should-not-proceed`: the technical design (H1-H5, the interface contract, the threat list) is largely correct and re-derivable against live source — this is not a fabricated or confused proposal. But the issue as filed has stale/false evidentiary claims about its own currency (finding 1), an incomplete `blocked_by` graph that its own prose contradicts (findings 2 and 4), a dangling reference to a closed issue in a DoD checklist item (finding 3), and at least one genuinely gameable acceptance gap (finding 6) plus an unbounded "measure it" criterion (finding 5). These are process/dependency defects, not physics defects, and a five-minute edit pass (add `442` and `378` to `blocked_by`, fix the `475` reference, tighten P7 and add a no-compare check) would move this to sound-with-concerns.
