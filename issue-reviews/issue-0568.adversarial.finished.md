# Issue #568: FEAT-C30-2: an outsider picks a labeled first issue from a stocked shelf of fifteen, and their fork tells them green or red with no maintainer in the loop
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

Issue #568 (open, filed by @anadon, labels `enhancement`/`area:test`/`tier:feature`) asks for a stocked `good first issue` shelf (≥15 items), a restocking rule, unattended fork CI feedback, and a guardrail against routing newcomers into `SimpleEditor`. It correctly serves capstone #514 (CAP-30) and its bot-generated comment already did a careful deduplication pass against the near-duplicate #317. But the four acceptance criteria have real gaps: one hides a security-relevant repository-settings change behind "a workflow adjustment," two are gameable as written, and one is likely infeasible for the task genre (new elements) that would otherwise be the easiest source of curated items.

## Findings, most severe first

**1. [High] AC-3's "zero maintainer action" claim skips over a GitHub repo-settings gate this issue doesn't scope or analyze.**
Body: *"AC-3: CI workflows run on forks: a first-time contributor's push to their own fork produces a green/red verdict with no maintainer approval step."* `ci.yml` already has `on: pull_request` (`.github/workflows/ci.yml:11`) with a least-privilege `contents: read` token (`:16-17`), so the trigger mechanics exist today. The actual obstacle to AC-3 is that public GitHub repos default to **"Require approval for first-time contributors,"** which blocks a fork PR's workflow runs until a maintainer clicks Approve — precisely the friction AC-3 wants gone. That is a repository Settings toggle, not a file in this tree, yet the issue's Notes section calls the remaining work "the fork-CI workflow adjustment" as though it's a YAML edit. Turning that gate off is a real security-policy decision (untrusted fork code executing in Actions, even against a read-only default token — and other workflows in `.github/workflows/` such as `release.yml`/`mutation.yml`/`codeql.yml` may carry different permissions) that this issue neither names nor sizes. **Recommendation:** rewrite AC-3 to explicitly cover the repo-settings change and require a companion audit of what each of the 6 workflow files exposes to a fork-triggered run before flipping the approval gate off.

**2. [High] The issue is written in exactly the style its own parent capstone flags as a contributor repellent.**
#514 (CAP-30, the capstone #568 serves) names as a top finding: *"the tracker's spec-prose reads as an internal monologue."* #568 itself opens with a raw machine block (`feat_id`, `serves_capstones`, `band_mw`, `ordering_after`) and the aside *"provisional; renumbered in the adversarial phase"* before any human-readable content — the same pattern. The stated candidate pool for curated items is "existing open task-tier issues," and the two related feature-tier issues actually inspected for this review (#316, #317) are multi-thousand-word specs with LaTeX-notation invariants, DAG-walk prose, and mermaid dependency graphs. Nothing in #568 requires curated items to be rewritten into plain short-form tasks rather than pointed at as-is. **Recommendation:** add an explicit note/AC that curated issues must be excerpted or rewritten into a short, plain description for the newcomer, not merely linked to a planning-corpus issue.

**3. [Medium] AC-1's "one-PR-sized" and "names its entry-point files/tests" bars are unverifiable and gameable.**
No objective measure is given (diff size, file count, estimated time), and nothing requires the named file/test pointers to be sufficient or accurate. A maintainer could satisfy the letter of AC-1 by relabeling 15 arbitrarily-scoped issues with a token "see X.java" line. **Recommendation:** define "one-PR-sized" concretely (e.g., diff ≤ N files/M lines within one package) and require at least one dry-run completion as evidence the sizing claim holds.

**4. [Medium] AC-1 and AC-2 leave a gap between a one-time snapshot and the sustained health the parent capstone actually needs.**
AC-1 only requires ≥15 "at filing time"; AC-2's restocking rule only fires below 10. The shelf can sit at 11-14 indefinitely, or oscillate 9↔10 forever, without ever triggering a sustained restock, while nominally compliant. AC-2 itself is satisfied by "a written rule exists" — a documentation criterion with no enforcement mechanism (contrast with this repo's own convention of standing tests like `HelpTopicsTest`/`ExtensionPointCatalogTest` for exactly this kind of drift). This under-delivers what capstone #514's own AC-2 needs: *"The good-first-issue label holds ≥10 open items continuously for a quarter"* — a continuous claim that a written rule alone cannot verify. **Recommendation:** either add a periodic/scheduled label-count check that fails loudly, or explicitly state that continuous verification is deferred to #514's own acceptance evidence.

**5. [Medium] Ongoing curation labor is understated and uncosted.**
Notes: *"this feature files no new code work of its own beyond the fork-CI workflow adjustment."* But hand-picking, scoping, and verifying correct file/test pointers for 15 items against a codebase where even adding one new element touches ~16 places (`ARCHITECTURE.md:115-142`) is real, recurring analyst work — and AC-2's restocking rule makes it perpetual, not one-time, for a project this repo's own docs describe as single-maintainer (README i18n section). `band_mw: "1-2"` reads as a one-time filing cost with no line for standing maintenance. **Recommendation:** split into a one-time filing task and an explicitly ongoing commitment with its own time budget, the way #514's PF-6 treats response-time SLOs.

**6. [Medium] AC-4's "internals" boundary is undefined and likely excludes the easiest task genre it should include.**
Body: *"Each curated issue is completable without touching `jls.edit`'s SimpleEditor internals, or explicitly warns when it does."* `ARCHITECTURE.md`'s own "Adding an element today" checklist (lines 115-142) shows a new element necessarily touches `SimpleEditor.makeElements` (item 12, palette entry) — i.e., `SimpleEditor.java` — which is otherwise the best-documented, most self-contained task genre in this codebase (a 16-step recipe already exists as a guide). AC-4 doesn't say whether a one-line palette-registration addition counts as "internals" versus the mouse/keyboard state machine #316 is actually worried about (5,852-line class, per #316's own body). As written this is either overbroad (disqualifying the easiest good-first-issue genre) or gameable (any curator can wave the palette line through). **Recommendation:** define "internals" precisely — e.g., excludes `State`, the mouse/keyboard listeners, `paintComponent` — and explicitly permit `makeElements` palette registration.

**7. [Low] No evidence the candidate pool actually exists; the label is currently unused.**
`search_issues repo:anadon/jls label:"good first issue" is:open` returns 0 results (verified live), and the label exists in the repo but carries zero issues. #568 names no specific candidate issue numbers, unlike its siblings #316/#317, which cite exact numbers and line-anchored evidence for every claim in this same tracker's convention. **Recommendation:** name 3-5 real candidate issue numbers in the body as a feasibility spot-check.

**8. [Low] `ordering_after: []` is contradicted by the issue's own comment thread.**
The bot comment on #568 records: *"any fork-triggered lane or workflow-trigger change this issue makes will be subject to [#317's timeout lint]... whichever lands second inherits the other's rule."* That's a real soft ordering dependency on the same `.github/workflows/` files, but the machine-readable header declares `ordering_after: []`, so automation reading only the header would miss it. **Recommendation:** record the coordination note in the machine block (even as a non-blocking `related` entry), not only in a comment.

## What's solid

- The outcome statement is concrete and in the spirit of what "good first issue" funnels should deliver (shelf, pointers, unattended CI feedback).
- AC-4's underlying rationale — keep first-timers out of the SimpleEditor decomposition, which is explicitly #316's job — is correct and well-cited.
- The linked bot comment already ran a careful, evidence-based deduplication pass against #317 before any work started, which is exactly the right discipline for a crowded, densely cross-referenced tracker like this one.
- Correctly and tightly scoped to a real, named parent capstone (#514) whose AC-2/AC-3 it mirrors rather than inventing new language.
