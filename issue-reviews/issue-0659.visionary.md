# Issue #659: TASK-C566-3: a machine entered as states and transitions simulates to the same trace as its hand-built register-and-logic equivalent
- Lens: visionary
- Date: 2026-08-08
- Reviewer: Claude Opus 5
- Verdict: endorse-with-reframing

## What this issue is really for

Stripped of its test-harness clothing, #659 asserts a claim about JLS's
meaning: *the state-machine element is not a magic box; it denotes a
register plus logic, and JLS can prove it.* That claim is exactly the
discipline ARCHITECTURE.md already records for the simulator itself —
"observably identical to the event model … agree bit-for-bit with the
#202 RV32I integration golden as a differential oracle" (§ Simulation
execution strategy). #659 is that same idea applied to an element rather
than a strategy. The goal is right and I endorse it.

What I do not endorse is the shape: a bespoke JUnit fixture set,
comparing one element family against hand-drawn circuits, in a harness
nothing else can use. That is the third private differential rig in this
repo (`riscv/fuzz_diff.py`, `RiscvCpuGoldenTest`, and now this) and the
project has already written down, in its own roadmap, the general
capability all three are instances of.

## The reframing: this is capability F, not an FSM test

`docs/capability-roadmap/sweep-04-verification.md` §F, "In-tool
differential/equivalence checking," specifies precisely what #659 needs:
"a batch mode (and a GUI action) that drives two circuits — or a circuit
and a declarative model of it — from the same stimulus and asserts
equality at sampling points … The change is a driver plus an `Assert`,
not new model concepts." Sized 1–2 maintainer-weeks. #659's band is 1 mw
for a private version of the same driver.

Cut the seam there instead:

1. **A trace-equivalence oracle in the product, not the test tree.** Two
   circuits, one `-t` stimulus, watched pins matched by name, equality
   asserted at defined sampling points. `BatchSimulator.getTraceSamples`
   already produces the per-element sample lists; nothing in `test/`
   currently shares a comparison helper (only `BatchTracePrinterTest`
   touches that API), so there is no duplication to fight — only a
   choice about where the thing lives.
2. **#659's FSM fixtures become its first two callers**, one Moore
   machine and its hand-built equivalent, expressed as a pair of
   committed `.jls` files plus one invocation — not 400 lines of
   `CircuitBuilder` string-appending in the mold of
   `test/jls/SequentialGoldenTest.java`.
3. **The same oracle then pays for itself four more times**: the #221
   equivalence criterion binding on any future compiled evaluation pass;
   Yosys-import round-tripping (#61); subcircuit-refactoring safety; and
   the pedagogy payoff §F names outright — "is your adder equivalent to
   the reference" replacing "does it match my 20 vectors." That last one
   is the instructor-pull argument #510/#515 keep reaching for, and it
   arrives as a side effect of doing #659 one seam over.

An FSM-only harness cannot become any of that later. A general one is
this task's work plus a flag.

## Disregarding AC-1 and AC-3 as written

**AC-3 ("hand-built equivalents … not generated by the same code path
under test") already has a better answer in the tree, and the issue never
looks at it.** `src/jls/hdl/HdlExporter.java:866` `buildStateMachine` is
a complete, carefully specified lowering of the element to a state
register plus case logic — binary state encoding with the initial state
at code 0 "mirroring `StateMachine.initSim`", transitions folded in
canonical save order, the absent-input rule, the #98 S5 hold-on-no-match
behavior. It is compiled by `iverilog` and `ghdl` in CI, and
`test/jls/hdl/IverilogCompileTest.java` says in its own javadoc:
"Simulation parity against JLS batch goldens is the next slice." That
slice is #659, unclaimed. A cross-tool differential — element trace
versus `vvp` running the exported Verilog — is a *stronger* independent
implementation than a hand-drawn JLS circuit, because the hand-drawn one
still runs through the same `jls.sim.Simulator`, the same `WireNet`
propagation, the same event queue. Keep one hand-built pair for the
pedagogical claim ("states mean gates *in JLS*"), and add the co-sim pair
for the semantic claim ("the element and its exported model agree").
Two oracles, both cheap, and the second one retires a pending slice.

**AC-1 ("identical traces … one Moore machine and one Mealy machine") is
not satisfiable as stated, for two independent reasons.**

*Mealy does not exist.* `src/jls/elem/State.java` hangs outputs off
states (`State.Out`, `sendOutputs`); `State.Transition` carries
`signal`/`equal`/`value`/`nextState` and no output. `HdlExporter` names
its output type `MooreOutput` for the same reason. So AC-1 silently
presupposes a specific outcome of #658 — that Mealy is *closed*, not
*refused*. But #658's AC-1 makes refusal-with-a-reason an equally
legitimate disposition, and #566's KC-31-2 verified-close path can make
this whole task vacuous. #659 should state its own dependency honestly:
"a fixture for each output mode the element supports after #658," not a
hard-coded Mealy row that a legitimate refusal upstream turns into a
permanent red test.

*"Identical" is the wrong relation.* The element drives its outputs at
`edge + propDelay` (default 30) as one atomic step. A hand-built
equivalent drives them at `edge + registerDelay + gateDelays`. Under
`docs/simulation-semantics.md` §6.2/§7 those are different times, so the
raw traces differ by construction and equality can only hold under a
stated sampling abstraction (settle-then-sample at each clock boundary).
Worse, there is a real semantic divergence hiding underneath: the
element goes **busy** during a transition and *drops* clock edges that
arrive while a transition is in flight (§8.2, `StateMachine.react`); a
register does no such thing. For any stimulus with clock period below
`propDelay`, the two forms provably disagree. A harness that asserts
"identical" will be tuned until it passes — which means it will encode
the element's limitation as if it were the specification, silently.

## What I would put in AC-1's place

Make the deliverable the *equivalence domain*, not the equality:

- The task states, in `docs/simulation-semantics.md` §8.2, the conditions
  under which the states-and-transitions form and the register-and-logic
  form agree — clock period > propDelay, sampling at settle points,
  Moore outputs, the no-match hold rule — and the harness pins each
  condition with a fixture.
- The task additionally commits **one deliberately divergent fixture**:
  clock faster than `propDelay`, asserting that the two forms differ and
  that the difference is the documented edge-drop. A differential rig
  whose whole fixture set passes has told you nothing about its own
  sensitivity; one committed divergence proves the oracle can see.
- AC-4 (report cycle, signal, both values) is the one criterion I would
  keep verbatim and strengthen: have the mismatch reporter emit a `-t`
  vector file reproducing the divergence, per the counterexample-loop
  pattern §G already argues for. Then a failing equivalence check hands
  the student (or maintainer) a runnable circuit, not a log line.

## The out-of-the-box alternative worth naming

The deeper opportunity #566/#659 keep circling but never state: JLS's
state-machine element **hides** the registers, which is pedagogically
backwards for the course this tool serves. Digital's FSM path is
compelling to instructors not because it simulates correctly but because
it *shows you the circuit your diagram became*. JLS already has the
lowering (`buildStateMachine`) and, via #515 PF-3, a planned
table-to-drawn-circuit synthesizer with a layouter lineage (#62). A
"Expand this state machine into a subcircuit" action is that same
lowering aimed at `jls.elem` instead of at Verilog — and it makes #659's
entire problem disappear, because the hand-built equivalent stops being a
committed fixture someone must hand-draw and becomes an artifact the tool
produces and the student can open, probe, and break. The equivalence test
then guards a *feature* rather than existing for its own sake.

That is a bigger swing than a 1-mw task should take, so I am not asking
#659 to become it. I am asking #659 not to foreclose it: build the
equivalence oracle as a general, product-level capability, and the
expansion feature arrives later with its acceptance test already written.

## Verdict

**endorse-with-reframing.** The claim — the element means the gates, and
JLS can prove it — belongs in this project and strengthens its arc.
Three changes: build the driver as capability F rather than an FSM-local
JUnit rig; add the HDL co-simulation oracle that
`IverilogCompileTest` has already flagged as the next slice; and replace
"identical traces" with a documented equivalence domain plus one
committed divergence. Drop the hard-coded Mealy row until #658 has
actually disposed of that gap.
