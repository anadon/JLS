# Issue #290: HDL layout goldens: commit the three hand-drawn showcase references (ALU slice, counter, small FSM) and run the corpus metrics rubric against the heuristic layouter
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of the issue's ask
Commit three hand-drawn `.jls` goldens sourced from MTU's JLS distribution, build one deliberately large (~100-150 element) Yosys-JSON fixture, and add a parameterized JUnit test that imports the #61 corpus (+ the new large fixture), lays it out, and asserts `LayoutMetrics` thresholds, a 4x-golden compactness bound, and a new under-1s timing bound.

## Findings, most severe first

### 1. (Critical) The recommended large-fixture design cannot be imported by the mapper as it exists today
The issue's Open Question 2 recommends: *"synthesize a multi-bit datapath (e.g. a small ALU + register file slice) through the same Yosys flow that produced the existing corpus."* But `NetlistImporter.mapCell` (`src/jls/hdl/imp/NetlistImporter.java:234-259`) realizes only `$not`/`$and`/`$or`/`$xor`/`$mux` and constants; everything else — explicitly including arithmetic (`$add`) and registers (`$dff`) — hits the `default` branch and is emitted as a hard `builder.problem(...)`: *"is a recognized cell that this importer increment does not yet realize... later increments add the Adder, Register, TriState, Memory, reductions and hierarchy."* Sibling issue #61 confirms this is still "planned... not filed" work, not a landed capability. Per #61's own Global Invariant 4 ("Rejection is total or import is total: no half-imported circuits, ever"), a netlist containing even one `$add` or `$dff` cell fails the whole import — it never reaches `LayoutMetrics.measure` at all. The corpus's existing fixtures (`and2.json`, `aoi.json`, `const_and.json`, `mux2.json`) are pure combinational logic for exactly this reason, and `reject_dff.json`'s own fixture comment says `$dff` is "validator-supported but not yet realized by the mapper." An "ALU + register file slice" is neither an ALU (needs `$add`) nor a register file (needs `$dff`) under the current mapper. Worse, bit-slicing/concatenation (Splitter/Binder mesh) is also unrealized (`NetlistImporter.java:739`), so even wiring a wide combinational fixture together from raw gates is constrained to whole-word connections.
**Recommendation:** Before work starts, either (a) explicitly scope the large fixture to pure word-level `$not`/`$and`/`$or`/`$xor`/`$mux`/constant logic (no arithmetic, no state, no bit-slicing) and drop "ALU + register file slice" from the issue text, or (b) make this task `blocked_by: [61-mapper-completion]` for Adder/Register realization. As written, the issue's own recommended default is not executable against the current codebase, and an executor following it will burn time before hitting the rejection wall.

### 2. (Critical) The MTU golden-sourcing plan ignores a documented network blocker in the very issue it cites
§1 says the sourcing path was fixed by "the 2026-07-08 adjudication on #62" and cites "#56's sourcing note" for authenticity. But #56's actual comment thread (which #290 links to) records that `pages.mtu.edu` is **proxy-403-blocked from every session's work environment so far**, and the analogous legacy-corpus sourcing effort in #56 was ultimately **formally deferred** rather than completed: *"the MTU distribution is unreachable from CI environments... disproportionate for a fork... No fixture files were fabricated,"* with sourcing left to "a maintainer with normal egress." #290's Method §8 treats golden selection as a plain checklist item ("Select the three showcase circuits... commit them") with no acknowledgment that the identical sourcing step was already attempted and abandoned by the same class of executor in #56. Open Question 1 even calls this step something that merely "rides along, blocks neither filing nor execution start" — which is false if the network path is closed for the whole session, since it blocks the entire golden-dependent half of this task (goldens, IC5, IC6 trace trial), not just a decision that can be deferred.
**Recommendation:** Either confirm (and record) that this specific execution environment has open egress to `pages.mtu.edu` before filing this as workable now, or split the task: file the goldens-and-compactness half as blocked on maintainer sourcing (per #56's precedent), and let the corpus-metrics-plus-timing half (which needs no external asset) proceed independently.

### 3. (High) No mechanism specified for computing the imported layout's bbox area for two of three showcase circuits
IC5/§7.10 needs a "layout bbox area" to compare against each golden's bbox — the data-transformation chain given is "Yosys JSON → NetlistImporter → LayoutResult → ... goldens → parsed bbox area → compactness ratio." Two of the three named showcase circuits are inherently sequential (counter, small FSM — state requires registers). Per Finding #1, `NetlistImporter` cannot realize `$dff`, so there is no way to produce a `LayoutResult` for a counter or FSM via the documented Yosys-import path. The issue never says how the "layout" side of the compactness ratio is obtained for these two circuits (hand-build a matching `LayoutGraph` directly, bypassing the importer? something else?). Left unresolved, an executor could satisfy the letter of "layout bbox area ≤ 4x golden bbox area per showcase circuit" by comparing an unrelated layout run's bbox to the golden — the criterion as written doesn't pin down *which* layout must be produced, so a sloppy implementation could pass IC5 without ever laying out the showcase circuit's own connectivity.
**Recommendation:** Add an explicit sentence: goldens compared for compactness are laid out by hand-constructing the matching `LayoutGraph` (mirroring the golden's own connectivity, using `LayoutGraph.java`'s register-feedback back-edge support directly) rather than through `NetlistImporter`, since the importer cannot realize the needed cells.

### 4. (Medium) Observation 6's timing gap and IC9 assume `LayoutResult`/`HeuristicLayeredLayouter` timing is dominated by `layout()` itself
The plan wraps `nanoTime`/`currentTimeMillis` "around the `layout` call" only. If `LayoutMetrics.measure`'s own O(segments²) crossing/overlap detection (`LayoutMetrics.java:208-226`, `300-320`) turns out to be the actual cost driver at ~150 elements (several hundred wire segments), a green IC9 timing result would still hide a real scaling risk in the metrics computation itself, which is on the same synchronous path a future GUI import would run. Not fatal — 1s is generous per the issue's own Threats to Validity — but the stated instrumentation point doesn't fully cover what the timing claim (imported circuit "laid out... in negligible time") implies to a reader.
**Recommendation:** Either times the whole import→measure pipeline, or note explicitly in the PR that `LayoutMetrics.measure` cost is out of scope for IC9.

### 5. (Low) Provenance/licensing of MTU-sourced circuits is asserted, not demonstrated
Even setting aside Finding #2's access blocker, the issue doesn't address whether Poplawski's MTU-hosted textbook-collection circuits (attributed to Patterson-Hennessy / Patt-Patel course material) carry redistribution terms compatible with committing them into this GPLv3 repository as test fixtures. The README's provenance section covers the JLS *software*, not necessarily third-party-inspired circuit files hosted alongside it. This is likely fine (same author, same distribution site) but is asserted rather than checked.
**Recommendation:** One line in the PR noting the specific license/permission basis for redistributing the three golden files, mirroring how README.md documents JLS's own provenance.

## What's solid

- Observations 1, 4, 5, 6 are independently verifiable and were re-checked against the current tree: the goldens directory is indeed absent, `aoi.json` is indeed 3 cells, and no `nanoTime`/`currentTimeMillis` exists in `src/jls/hdl/layout/` — the issue's evidence-gathering here is accurate.
- The re-verification-at-pickup clause in the Completion Criteria (superseded-if-already-landed) is good hygiene against stale re-litigation.
- Scoping out layouter tuning and the ELK path (owned by #62) keeps this task's blast radius contained to fixtures + one test file, which is appropriately sized *if* Findings #1-#3 are resolved first.

## Verdict rationale
Two of the five findings (#1, #2) are not nitpicks — they mean the issue's own recommended defaults are not executable against the codebase as it stands today, and the primary external dependency (MTU network access) was already tried and abandoned once in the exact issue #290 cites as having "fixed" it. The task needs its Materials/Method sections revised before an executor should start, hence `needs-rework` rather than `should-not-proceed` — the corpus-metrics-plus-timing half of the work is genuinely landable once the large-fixture design is corrected to the mapper's real supported cell set.
