# Issue #314: FEAT-002: a saved attribute no element declares becomes a named diagnostic instead of vanishing at load
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

The core technical claim is accurate and verified against the working tree: `src/jls/elem/Element.java:344,359,374,389` are indeed four `public void setValue(...)` overloads that silently fall through on an unmatched attribute name, and `src/jls/Circuit.java:1067,1078,1089,1105,1116` are indeed the five unconditional `el.setValue(name, value);` call sites that cannot observe a miss. `git grep -c "public void setValue" -- src/jls/` returns 26 across 17 files, matching the issue's own count, and `test/resources/silent-loss/`, `docs/registry-keyed-tables.md`, and `src/jls/imp/` are all genuinely absent. As a bug report the diagnosis is sound. But the issue as filed is not a bug report — it is a heavyweight, self-referential planning artifact (DAG YAML, mermaid graph, task roster, cost-band arithmetic, capstone obligations, a "REPLAN protocol") wrapped around roughly one day of actual code change, and it contains one substantive technical contradiction with the project's own normative spec that the issue never reconciles.

## Findings, most severe first

### 1. Open Question 1's "reject" option directly contradicts the project's own normative evolution policy — and the issue never reconciles this
`docs/file-format.md` §9 ("Evolution policy") states, as a **normative, already-decided** rule: "adding a new attribute (any existing item kind) to an existing element type — older readers silently ignore unknown attribute names (§5)" requires **no format version bump**, and calls this "the format's main forward-compatibility valve" (§5, line 224). The doc gives a worked historical example (Memory's `initrle`, issue #47) of exactly this mechanism working as intended. Issue #314's Open Question 1 lists as a live option "(b) reject immediately" on an unmatched attribute name, and recommends "(a) load-and-report for one format epoch, then reject" as the *eventual* target state. Either of those options, once the epoch in (a) elapses, **breaks §9's contract**: a file that legitimately carries a newer, no-bump-required attribute (the exact case §9 exists to allow) would stop loading in a JLS build that has adopted "reject." The issue cites `docs/file-format.md:141` in its Related Issues section only to note that unknown attribute names are "handled," but never engages with §9's explicit rationale for *why* silent-drop is the chosen forward-compat mechanism, nor states that landing "reject" as a future policy is itself a rewrite of a normative, tested document (§9's version-history table, `FormatHeaderTest`). This is not a hypothetical: §7's "Re-planning Protocol" only triggers a REPLAN if "FEAT-013 rules the epoch policy differently" — it treats the target-state decision as owned entirely by a *different*, still-open issue (#319), so #314 can close having recommended a policy that, if ever adopted, is a breaking change to a currently-passing test (`FormatHeaderTest`) and a currently-true README/spec guarantee, with no gate in this issue's own Definition of Done that requires that conflict to be checked.
**Recommendation:** Before filing child tasks, add an explicit criterion reconciling Open Question 1 against `docs/file-format.md` §9: either scope this issue to diagnostic-only (never reject), or add a §9 amendment as an explicit, reviewed deliverable of this issue (not silently deferred to #319).

### 2. The cost estimate is internally inconsistent and the issue resolves this by declaring the discrepancy "superseded" rather than fixing it
"The registry band is **1-2 mw** [maintainer-weeks]. The four task rows named for it sum to **1.5 + 1.0 + 0.4 + 2.0 = 4.9 weeks**... The rows do not sum to the band and the band is **superseded** rather than the rows adjusted... The tasks this feature exclusively owns sum to **1.4 weeks**." This is the issue admitting, in its own text, that its headline cost figure (1-2 mw) is wrong by more than 3x when read literally, and resolving the discrepancy by asserting a *third*, uncomputed number (1.4 weeks) is "what the band actually prices," deferred to "Open question 3... does not block filing children." A cost estimate that contradicts itself and defers reconciliation indefinitely is not a basis for scheduling.
**Recommendation:** Fix the cost estimate before treating this as fundable work; do not let three mutually inconsistent numbers (1-2, 4.9, 1.4 weeks) all stand as "the" cost.

### 3. The acceptance criteria are gameable: the diagnostic's exact content is never pinned down
§5 criterion 1 requires the diagnostic to "contain the file name, the line number, the element identity and the attribute name," and TASK-0004's corpus is described as asserting "the diagnostic *text*, not a flag" — but the issue never specifies the actual message format, wording, or a machine-checkable schema (e.g. an error code and a template). "Contains X, Y, Z as substrings" is satisfiable by a technically-compliant but useless message (e.g. dumping a stack trace that happens to mention the four facts), and a fixture corpus written after the fact by the same implementer who wrote the diagnostic will tend to assert whatever that implementer produced, not an independently specified format. Contrast with `LoadError`'s existing fixed category taxonomy (`ARCHITECTURE.md` "Error-reporting contracts": `IO_ERROR`, `NOT_A_CIRCUIT`, `MALFORMED`, `NEWER_FORMAT`, `UNKNOWN_ELEMENT`, `ELEMENT_ERROR`, `LIMIT_EXCEEDED`) — this issue never states whether the new diagnostic gets its own `LoadError` category (e.g. `UNCONSUMED_ATTRIBUTE`, mentioned only in passing in a comment, not in the issue body itself) or free-text.
**Recommendation:** Pin the diagnostic to a specific, named `LoadError` category (consistent with the existing taxonomy in `src/jls/LoadError.java`) with a fixed field set, not prose describing "a diagnostic string."

### 4. The issue itself performs zero of the actual engineering work — it is a coordination shell around four other issues, at least two of which (per its own comments) already exist and disclaim its scope
Every concrete deliverable — the code change, the fixture corpus, the registry inventory, the `.circ` reader — is explicitly pushed to child issues #372, #404, #408, #451 (per this issue's own comment thread), each of which "disclaims the rest of this feature's scope in its own words." #314's own Definition of Done is entirely process: "Every entry in `requires_tasks` closed," "Every capstone... notified with a STATUS comment," "Machine block, roster table, and mermaid graph agree with reality." None of the eleven DoD bullets is itself a code change or test. A reviewer approaching this "issue" expecting a scoped, closeable unit of engineering work will find nothing to implement here; the actual bug (silent attribute drop) is fixed, if at all, by #404/#408, not by any action taken against #314.
**Recommendation:** If this project's process genuinely needs a tracking/coordination layer of this weight, say so explicitly and label it as process (not `enhancement`/`tier:feature` implying shippable code); otherwise fold #314's content into #404 and close #314 as redundant scaffolding.

### 5. `blocked_by` was wrong when filed and required two follow-up comments to correct — the DAG this issue depends on is not trustworthy at face value
The issue as filed declares `blocked_by: [315]`. A later comment on this same issue concedes the edge "over-constrains" and that #314's *own* §6 already says TASK-0001/#315 is "convention... not necessity," then narrows it to `requires_at_closeout: [372]`. A second follow-up comment further concedes the commit pin used to re-verify the code claims (`07a0bea`) is "not on master" and points to a third commit (`8288226...`) as canonical, warning "do not write `2d0ca9d` or `07a0bea` into future comments here." Three rounds of self-correction on basic facts (blocking edge, evidence commit) before the issue reaches a stable state is a strong signal that the DAG apparatus (`blocked_by`, `blocks`, `serves_capstones`, the mermaid graph, cross-issue "mirrored edge" obligations) is more failure-prone than the thing it's meant to coordinate, and that anyone acting on this issue today needs to re-derive the graph from the comment thread rather than trust the issue body.
**Recommendation:** Treat the machine block in the issue body as stale on principle; require any executor to re-derive `blocked_by` from the latest comment before starting, and consider whether this DAG-in-issue-text pattern is worth the maintenance cost it is visibly incurring across this issue alone.

### 6. Scope-creep risk in "aggregate count" and "headless-aware reporter" requirements is underspecified against existing infra
§3 "Provides" says the diagnostic routes "through the project's existing headless-aware reporter... and an aggregate count so a file with a thousand stale attributes produces a summary." `TellUser` (`ARCHITECTURE.md`, `src/jls/TellUser.java`) is that reporter, but it is designed for one-shot user-facing messages (issue #81), not accumulation/aggregation across a load pass — the issue doesn't specify whether aggregation happens in `Circuit.finishLoad` (per §3 "Ephemerally used") and gets flushed to `TellUser` once, or whether `TellUser` itself needs new aggregation capability. This is a real design gap papered over by "rides along" language (Open Question 2) rather than resolved.
**Recommendation:** Specify where the per-load miss list lives and how/when it's flushed to `TellUser`, or explicitly hand that design decision to TASK-0003 with a concrete interface sketch.

## What's solid (brief)
- The core code citations (line numbers, overload count, file count) are all independently verified accurate against the current working tree.
- The "out of scope" section correctly excludes the write-side of data loss and the `.circ`/FEAT-025 work, keeping this slice bounded in principle.
- Aggregation-to-avoid-DoS (§5 criterion 3, tied back to #38's hardening threat model) is a genuinely good, specific safety requirement.
- Global invariant 1 (byte-identical re-save for files that load cleanly today) is a correct, testable non-regression bar and ties to an existing closed issue (#166) as oracle.

## Bottom line
The underlying defect is real and precisely located. But the issue conflates "file a scoped bug fix" with "operate a multi-issue planning bureaucracy," self-corrects basic facts (blocking edges, evidence commit) across three follow-up comments, states an internally contradictory cost estimate without fixing it, and — most importantly — proposes a policy option (reject-on-miss) that is not reconciled against the project's own normative forward-compatibility contract in `docs/file-format.md` §9. Rework should (a) resolve finding 1 explicitly before any "reject" language ships anywhere, (b) fix or drop the cost figures, and (c) pin the diagnostic contract to the existing `LoadError` taxonomy so the acceptance corpus can't be gamed by incidental string matches.
