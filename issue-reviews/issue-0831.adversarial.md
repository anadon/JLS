# Issue #831: TASK-C571-3: Digital's rejected-PR authors are invited by name — but only after the on-ramp exists, and with the kill criterion written down before the first invitation goes out
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of the issue

TASK-C571-3 is one of three sibling tasks (#828, #829, #831) decomposing feature
#571 (FEAT-C30-6), itself under capstone CAP-30 (#514). #831 covers #571's AC-2
(named-invitation list for Digital's rejected-PR authors, gated on #567/#568/
#316) and AC-5 (KC-30-2 kill criterion, written down before the first
invitation). It is open and has no comments. It is not linked via GitHub's
sub-issue mechanism to #571 (`has_parent`/`has_children` are both `false` on
both issues) — the relationship exists only in the `part_of_feature: 571`
YAML field and in the title's `TASK-C571-3` prefix.

## Findings, most severe first

**1. [High] The task's own AC-5 evaluation date is computed off the wrong
prerequisite set, and this is an inherited defect from #571, not a new
independent error.** Capstone #514 defines KC-30-2 precisely: *"If two
quarters pass **post-PF-1..4** with zero external PRs, the outreach premise is
falsified."* PF-1..4 are #567 (templates), #568 (funnel), #316 (SimpleEditor
decomposition), and **PF-4 — the published extension API, #223 + #399
TASK-0107** (2-3 mw, "Digital's custom-component API has no stability
guarantee"). #831's own Outcome text redefines "the on-ramp" as only three
items — *"invitations go out only after the on-ramp gate (#567, #568, #316)
has actually landed"* — and AC-5 fixes the kill-criterion evaluation date
against that same three-item gate ("two quarters after the on-ramp pass").
PF-4 never appears in #831's `ordering_after`, its Outcome, or any AC. Whoever
executes AC-5 will write down an evaluation date keyed to #567/#568/#316
landing, label it "the KC-30-2 kill criterion" per AC-5's own text, and start
a clock the capstone's actual definition says should start after a fourth,
unlisted item lands too. **Recommendation:** either (a) add #223/#399 to
`ordering_after` and to the AC-5 evaluation-date computation, or (b) if PF-4
is deliberately excluded (e.g., because AC-2's invitation gate genuinely only
needs PF-1..3, which is defensible), say so explicitly in the issue body and
stop calling the resulting date "the KC-30-2 kill criterion" — it would then
be a different, task-scoped criterion that happens to share KC-30-2's name.
As written, the label and the computation disagree.

**2. [High] `ordering_after` adds a fourth prerequisite — #829/TASK-C571-2 —
that no upstream document sanctions, and #831 gives no reason for it.** The
machine block reads `ordering_after: ["#567 ...", "#568 ...", "#316 ...",
"TASK-C571-2 (published response objectives)"]`. But #571's own
ordering-correction comment (`issuecomment-5227450446`, posted the same day
as #831 was filed) explicitly tabulates the gate per criterion and states for
AC-2 (the criterion #831 embodies): `AC-2: [567, 568, 316]  # unchanged; the
criterion's own gate` — no dependency on AC-3/AC-4 (571's response-objective
half, which #829 implements). AC-5 in that same table is also `[567, 568,
316]`, again omitting 829. Nothing in #831's Outcome or its five ACs explains
why the named-invitation task should wait on the response-SLO task; AC-3 of
#831 ("invitation text points to a specific first issue and the fork-CI
loop") does not reference a published response-time commitment at all. This
reads as an undocumented dependency quietly added below a sibling task,
contradicting the parent issue's own explicit per-criterion gate table.
**Recommendation:** either delete the #829 dependency (matching #571's
correction table) or, if a real reason exists (e.g., "don't recruit before
the response-SLO commitment is public"), state it as prose in the Outcome and
add a corresponding note to #571's own table so the two issues don't disagree
about the gate for the same acceptance criterion.

**3. [High] No human-sign-off checkpoint exists before real messages go out
to named third parties, and every AC as written can be satisfied by fully
autonomous execution.** AC-1 through AC-4 describe compiling a list of real
people (found via another project's PR history), drafting per-person
invitation text, and sending it — "invitations go out," "outreach respects
the venue." Nothing in the issue requires a maintainer review-and-approve
step between "list compiled" and "message sent." Given this issue cluster is
explicitly agent-workable (sibling issues carry "_Generated by [Claude
Code]_" comments, and #571's Notes call this "deliberately a partly non-code
feature" filed for agent execution), an agent could legitimately read AC-1-4,
compile the list, draft the text, and post it to real GitHub users — including
potentially on Digital's own tracker — without any person having read the
specific wording sent to specific named individuals. Soliciting a
competitor's spurned contributors is a judgment call with real reputational
stakes (to this project, to the maintainer, and to the people contacted); it
should not be satisfiable by an unattended agent run. **Recommendation:** add
an explicit AC requiring maintainer review/approval of the compiled list and
the exact invitation text before any message is sent — not just that the
list "exists," but that it is approved.

**4. [Medium] AC-4's "respects the venue" doesn't say what the venue is, and
the natural reading enables exactly the hazard #571's own review already
flagged.** AC-4: *"Outreach respects the venue: public, one message per
person, no repeat solicitation."* "The venue" is never identified. The most
available public venue for someone found via "Digital PR history" is a
comment on their PR/issue thread on Digital's own tracker — which is also
the venue most likely to read as poaching to Digital's maintainer, a concern
#571's own review (see `issue-reviews/issue-0571.adversarial.md`, finding 4)
already raised against the parent AC-2 without resolution. #831, filed to
carry out that exact AC, doesn't name a permitted or forbidden channel either.
A literal execution — commenting directly on Digital's closed PRs — satisfies
AC-4's text ("public," "one message," "no repeat") while landing squarely in
the hazard the parent review flagged. **Recommendation:** AC-4 should name
the channel explicitly (e.g., "only via a channel the recipient made public
and reachable outside Digital's own tracker — GitHub profile contact, a
listed email, a public social handle — never a comment on Digital's PRs or
issues").

**5. [Medium] AC-1's "plausible fit" and "no scraped bulk mailing" are
judgment calls with no check that survives a rushed pass.** "Compiled from
public sources, with each entry noting what the person contributed and why
they are a plausible fit — no scraped bulk mailing" sets a good bar in
principle, but nothing distinguishes a genuine per-person assessment from a
templated one-liner repeated 20+ times ("submitted a PR to Digital" as the
"plausible fit" note for every entry) — which is functionally the "scraped
bulk mailing" the criterion forbids, just reformatted as a table. #510 §5,
the evidentiary base, names exactly two of the "26 open PRs" by number
(#1464, #1470); the rest of the pool is undifferentiated in every document
this task inherits from. Compiling genuine per-person fit notes for an
unspecified-but-plausibly-large remainder is real research work the 0.25-0.5
mw band (see finding 6) does not obviously cover. **Recommendation:** require
the list to cite, per entry, the specific PR/issue and a concrete
contribution detail (not a template phrase), and cap or explicitly scope how
many of the 26 are actually pursued in this pass versus deferred.

**6. [Low] Cost band plausibility.** 0.25-0.5 mw (roughly 1-2 days) covers
compiling a curated list from up to 26 external PRs with individualized
fit-notes (AC-1), drafting and sending personalized per-recipient text that
each names a specific first issue (AC-3), respecting a one-message-only norm
(AC-4), and writing the kill criterion (AC-5) — while also carrying the
recording obligation back onto #571 (AC-2: "the gate check is recorded on
#571"). Compare sibling #828 (TASK-C571-1), banded at 0.25 mw for two known
comments on two known PRs. #831's list-compilation-plus-personalized-outreach
scope for a two-digit number of unknown people is a meaningfully larger
research-and-writing task than #828's, yet the band is barely larger.
**Recommendation:** re-derive the band after AC-1's scope (how many people,
how much research per person) is pinned down, or explicitly bound AC-1 to a
small named subset (e.g., only the PRs #510 §5 already names) for this pass.

## What's solid

- AC-2's ordering rationale itself — real outreach should not go out before
  there's a template, a first-issue shelf, and a codebase that survives
  inspection — is sound and matches #571's own correction comment for this
  specific criterion (modulo finding 1's PF-4 gap).
- AC-5 correctly treats "the recruitment half retires" as a legitimate
  completed outcome rather than a failure, consistent with capstone KC-30-2
  and with #571's boundary-note comment on the same point.
- AC-3 ("a specific first issue... not a generic 'contributions welcome'")
  is a concrete, checkable bar that meaningfully raises invitation quality
  over a form letter.
- The task's `ordering_after` is at least directionally correct in requiring
  #567/#568/#316 before any invitation — the core sequencing idea is right,
  even where the specific set is wrong (finding 1) or has an unexplained
  extra member (finding 2).

## Verdict rationale

The core sequencing idea (recruit only after there's somewhere to land, and
pre-commit to a kill criterion) is sound. But this task is the one in the
#571/#828/#829/#831 cluster where the acceptance criteria translate directly
into unattended messages sent to real, named strangers on a competitor's
tracker, and it inherits a kill-criterion date computed against the wrong
prerequisite set (finding 1), adds an unexplained fourth gate (finding 2),
and — unlike its siblings — has no checkpoint requiring a human to read the
list and the exact text before it goes out (finding 3), while leaving the
channel/venue hazard #571's own review already flagged unresolved (finding
4). These are fixable with edits to the machine block and one added AC, not
a redesign, but they should not ship as-is. **needs-rework.**
