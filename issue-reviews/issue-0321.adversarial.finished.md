## Findings, most severe first

**1. The issue's own machine block is already stale relative to its own comments — `planned_tasks` claims "not filed" for tasks that are filed.** The issue body's §2 roster and YAML `planned_tasks` list TASK-0045 and TASK-0046 as "(planned, not filed)" with evidence "ABSENT at 2d0ca9d... not filed." But the issue's own two comments (2026-08-04, 2026-08-08 — both from the same author account) state plainly that TASK-0045 is filed as #414 and TASK-0046 as #418, and both are confirmed still `open`. The Completion Criteria checklist explicitly requires `planned_tasks` empty ("each resolved to a filed issue or descoped"), yet the body was never edited to reflect this — the mermaid diagram still draws `T45`/`T46` as bare "(planned)" nodes disconnected from any issue number, and a DAG-walking tool or a new contributor reading only the body (not the comments) would conclude two of the three child tasks don't exist yet. Recommendation: edit the issue body's machine block and roster table to point at #414/#418 before anyone picks up TASK-0111 or attempts the close-out; a reader who trusts the machine block over the comments will misplan.

**2. Key evidence citations have already drifted from the current tree, undermining the plan's numeric specificity.** #414 and #418 (this issue's own filed children, cited as authoritative background) pin a `HdlExporter.REJECTED` map at `HdlExporter.java:460-478` — `Map<Class<?>, String>` with exactly four entries: `Memory.class`, `SubCircuit.class`, `RegisterFile.class`, `FieldExtend.class`. Checked against the current checkout: no `REJECTED` identifier exists anywhere in `src/jls/`, the class-level javadoc at `HdlExporter.java:87-89` now names only two reject types by name ("SubCircuit, Memory, and anything unrecognized"), and the file itself is 1364 lines, not the 1422 recorded at the evidence commit. `RegisterFile.java` and `FieldExtend.java` exist as element classes (added by commit `38a0544`) but appear in neither the Exported nor the named-Reject bucket of the current javadoc — they're presumably swept into "anything unrecognized," but that's inference, not verification. Since TASK-0046/#418's "limitations section" (P8, a Definition-of-Done item) is contractually required to name "all four `REJECTED` types... with the date the list was taken," and that data structure no longer exists under that name, the task as currently specified will need non-trivial re-derivation before it can even start. This is exactly the kind of drift the repo's own "rule 6" anticipates ("re-derive line numbers if HEAD has moved") — but the drift here is structural (a map disappeared, two new element types were added with unclear bucket membership), not just a line-number shift, and #321's own cost estimate for TASK-0045 (2 wk) and TASK-0046 (0.6 wk) was set against the old, now-invalid picture. Recommendation: before filing/starting TASK-0111 or touching TASK-0046, re-verify the current export-policy bucket membership for `RegisterFile` and `FieldExtend` explicitly, and re-price if the rejection mechanism changed shape.

**3. Possible double-counting of TASK-0111's cost between #321 and #369.** #321's Open Question 3 says TASK-0111's 2 wk is "shared with another feature and counted once at the task level" (i.e., shared with #369/FEAT-053), and recommends "carry TASK-0111's 2 wk on whichever feature schedules it first." But #369's own cost-reconciliation section calls out TASK-0021 as shared with FEAT-008 (#316) and TASK-0073 as shared with FEAT-034 (#347) — it does **not** name TASK-0111 as shared with FEAT-019 (#321) anywhere, and folds TASK-0111's 2 wk directly into its own "unshared remainder" (4 wk = TASK-0111 + TASK-0112). If a scheduler sums both issues' "unshared" figures independently (2.6 wk here, 4 wk there), TASK-0111 is silently counted twice, or once-and-dropped depending on which issue's bookkeeping is followed — the two issues disagree about which side owns the sharing discount. Recommendation: state explicitly, on one issue with a mirrored note on the other, which feature's ledger actually absorbs TASK-0111's cost.

**4. The round-trip criterion (I3) is unverifiable by construction from any single child, and no owner is named for building the comparator.** §5 states I3 "spans the writer and the shipped importer, so no single child asserts it" and is "this issue's close-out." But this issue's own Completion Criteria never lists a task, PR, or even a placeholder for who writes the stable-id partition-isomorphism comparator itself — TASK-0045 (#414) explicitly disclaims it ("this issue does not restate them"), TASK-0046 doesn't touch it, and TASK-0111 doesn't either. Issue #321's own comment thread flags this exact gap for a sibling case ("I3 versus #523/#627... a later pass should decide which issue owns the shared comparator") but leaves it as an open note rather than a resolution for #321 itself. As written, "this issue's close-out" is not an actionable task — it's a criterion with no assigned executor, which is a good way for the feature to sit "90% done" indefinitely with I3 unaddressed and no red flag until someone tries to close it.

**5. The acceptance criteria for `StateMachineStatement` are gameable.** §7 (Open Questions #1 in #414, inherited here via §3's totality contract) recommends refusing `StateMachineStatement` "by name," and the totality requirement is only that the switch be `default`-less and every kind get *either* a mapping or a refusal. That satisfies I1/I5/I6 and the letter of "no approximated cell," but a circuit containing any state machine — a large fraction of pedagogically interesting designs, since FSMs are core CS curriculum content — simply cannot be exported to the format this feature exists to produce. The corpus goldens can be constructed entirely from FSM-free fixtures, so I1 ("emit every fixture in the corpus and validate") could pass 100% while the feature is useless for a meaningful slice of real student circuits. This isn't flagged as a risk anywhere in §5's Integration Criteria or the Completion Criteria — there's no criterion requiring the refusal rate over a representative sample to be bounded or reported. Recommendation: add an explicit criterion measuring what fraction of the existing `test/resources/hdl/` corpus (or of typical course circuits) actually contains a `StateMachineStatement` and would be refused, so "the writer works" doesn't quietly mean "the writer works except on the circuits students draw in the FSM unit."

**6. The 6-10 maintainer-week cost for a native gate-level emitter, used to justify the entire "recipe not writer" design decision, could not be independently verified in the checked-out tree.** The claim originates from #418's citation of `docs/standards-adoption/11-costed-rejections.md`; that document exists in the repo and covers EDIF/BLIF/SPICE costing, but this reviewer did not find the specific "6-10 maintainer-weeks" figure or its derivation reproduced in #321's own body beyond the bare assertion — it's presented as settled fact ("costed at 6-10 maintainer-weeks before a line of syntax is written") without a citation to a line number or section the way nearly every other quantitative claim in this issue is pinned. Given how load-bearing this number is (it's the entire justification for TASK-0046 over a native emitter), the absence of an inline citation here — unlike almost everywhere else in the document, which is citation-disciplined to a fault — stands out. Recommendation: pin the 6-10 mw figure to a specific line/section the way every other number in this issue is pinned, or drop the precision ("6-10", not "several" or "some") if it can't be sourced that precisely.

**7. `evidence_commit: 2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7` does not resolve in this checkout** (`git cat-file -t` fails: "Not a valid object name"). This is very likely an artifact of the review environment being a shallow clone (`git rev-parse --is-shallow-repository` → true, only 269 commits reachable, HEAD is a "Checkpoint: issue review snapshots" commit) rather than evidence the commit never existed — treat this as a low-confidence environmental note, not a claim that the citations are fabricated. It does mean this reviewer could not directly diff against the exact pinned commit and instead compared against current HEAD, which is how findings #2 and #6 were surfaced.

## Minor / non-blocking observations

- The `HdlExtensionPoints.EXPORTER` code snippet quoted in the issue body drops the generic type parameter (`ExtensionPoint` vs. actual `ExtensionPoint<HdlEmitter>`) — cosmetic, doesn't affect the argument.
- The corpus-size correction from #414's comment ("37 .v and 33 .vhdl, not ~20 paired") is independently confirmed against the current tree (`find` returns the same 37/33/8 counts) — a real and now-doubly-confirmed correction to the planning corpus that #321's own Open Question 3 cost math doesn't visibly incorporate (golden-writing effort for TASK-0045 may be underpriced at 2 wk if it assumed ~20 pairs).
- Determinism requirement (criterion 6, byte-identical re-emission "across runs, JVMs and platforms") is a strong claim worth stress-testing early — canonical JSON key ordering across `HashMap`-backed intermediate structures is a classic source of flaky non-determinism; nothing in the plan calls out *which* JLS internal structures the emitter will walk and whether any of them are unordered.

## Verdict rationale

The core technical grounding (file states, line numbers for the CLI dispatch and the parse-only `JsonValue`, the DAG edges to #336/#369) is unusually well verified and mostly holds up against the live tree. The issue is not fundamentally broken. But it has already fallen out of sync with its own filed children (finding 1), rests some cost/scope claims on structures that have since moved or disappeared from the codebase it cites (finding 2), and has at least one real cross-issue cost-accounting disagreement (finding 3) plus an unowned closing criterion (finding 4). None of these individually block starting TASK-0045, but they should be cleaned up — ideally in a `REPLAN:` comment per the issue's own stated protocol — before TASK-0111 or the I3 close-out work begins, since those depend on state this review shows is currently inconsistent.
