# Issue #535: FEAT-C23-6: dragging the time cursor rewinds the canvas by deterministic re-simulation to T — no checkpoints, honest replay progress — and a cursor-synced external viewer follows for the professional handoff
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

Two independently shippable capabilities are bundled under one FEAT number: (a) checkpoint-free rewind-by-replay to a cursor time T, and (b) a bidirectional cursor-sync link to an external waveform viewer (Surfer). Both AC sets are reasonably shaped in isolation, but the issue asserts a central technical claim — "no per-element snapshot/checkpoint code path, ever" — that the repository's own engineering analysis of this exact problem contradicts with numbers, and pairs it with an acceptance criterion (AC #2) that is not machine-checkable as written. The viewer-sync half is separately flagged, in the issue's own text, as the review-recommended item to cut.

## Findings, most severe first

**1. (HIGH) The issue's core technical mandate contradicts the repo's own design study for this exact feature area.**
`docs/capability-roadmap/lf-03-causal-debug.md` §"(b) Time travel — checkpoint and replay" (lines 248–382) is a detailed engineering analysis of rewind for CAP-23's causal-debug loop — the same capstone (#504) that spawned this issue. It concludes the opposite of what #535 mandates: "Format. Decision: a new `jls.sim.SimCheckpoint`..." (line 287), with a concrete size/interval budget ("≈9 KB raw / 2–3 KB deflated" per checkpoint, "16 checkpoints ≈ 40 KB deflated" for a 6004-cycle run) and the explicit argument "Checkpoints let you **not keep it** ... **the checkpoints are the index**" (lines 374, 381). It computes that the flagship demo run has 2,331,793 events at 318 ns/event (line 325–327) — i.e. pure O(T) replay to an early T on that run is multiple seconds to minutes of wall time, not the "honest and acceptable at teaching scale" the issue asserts without a number. Issue #535 never cites or reconciles this document; it instead treats the checkpoint ban as settled via #498 exclusion 2 (see finding 7). Whether "teaching scale" circuits stay small enough that this gap never bites is an assumption the issue does not state or bound.
**Recommendation:** either cite and rebut `lf-03-causal-debug.md`'s numbers explicitly (why the CPU-scale case doesn't apply to "teaching scale"), or define a numeric ceiling on T/event-count that pure replay must stay under, with a fallback plan (e.g., degrade to "rewind unavailable past N events, use batch mode") when exceeded.

**2. (HIGH) AC #2 is not testable as written.** "Rewind uses no per-element snapshot/checkpoint code path" has no proposed enforcement mechanism — no ratchet test, no bytecode/reflection scan, nothing analogous to `HeadlessCoreRatchetTest` or `NotificationRatchetTest` (both cited in `ARCHITECTURE.md`'s error-contract section as the pattern this project uses to keep "no X anywhere" claims from rotting). Contrast with #498's own admission about K9: "K9 is currently unenforceable... The highest-ranked criterion in this document is a sentence" until a concrete test was proposed. AC #2 is in exactly that state today. As written, a reviewer can only check this by reading the diff at merge time, and a later refactor (e.g., a "coarse periodic state cache" under a different name, functionally a checkpoint) could silently violate it with no red build.
**Recommendation:** add a concrete enforcement test before this ships — e.g., a static/reflective scan asserting no new serializable per-element "resume state" fields are added to `jls.sim`/`jls.elem` classes outside the existing save/load attribute set, or a size/behavior probe that fails if rewind cost stops scaling linearly with T.

**3. (MED-HIGH) AC-3/AC-4 (`ViewerSyncTest`, "a scripted session against the pinned viewer version") is asserted without addressing the project's own documented finding that Surfer cannot be automated.** `docs/standards-adoption/07-waveform-formats.md:394-396`: "Surfer has no headless verification mode I am aware of, so Surfer stays a manual check — which is already the documented posture (`VcdExportGoldenTest`'s class Javadoc says 'GTKWave/Surfer validation stays manual, outside CI')." Issue #535 requires a scripted, presumably CI-runnable, bidirectional interaction test against real Surfer with no discussion of how that squares with this existing precedent, and no fallback (e.g., a protocol-level mock) is proposed.
**Recommendation:** either verify Surfer's remote-control protocol is scriptable headlessly (and record the evidence, the way #63's HDL toolchain integration recorded CI installation and locator logic) before committing to AC-4 as a CI gate, or scope AC-4 down to a protocol-level test against a stub/mock server and treat real-Surfer verification as a manual release-cadence check like the existing GTKWave/Surfer VCD posture.

**4. (MED) The citation grounding AC #5 / KC-23-4 borrows a rationale built for a different problem.** AC #5 and KC-23-4 lean on "#498 §7.2, and the #63/#216 stance" to justify that viewer sync "never feeds values back into the simulation." But #498 §7.2 is about the *grading/batch console* contract (an interactive GUI session vs. what a grader may depend on — "the console pulls, it is never called back into"), and #498 §7.2 itself flags that a stronger, permanent "no callback direction, ever" clause is currently being proposed for a normative document ("This window is closing... If that lands first, this becomes a documented reversal of a permanent normative clause"). Cursor-sync as specified here requires JLS to receive an asynchronous notification from an external process (the viewer) while a live session is open — structurally a callback into JLS, even though it only moves a cursor rather than injecting simulation values. The issue does not establish that this distinction (navigation callback vs. value callback) survives if the stricter §7.2 wording lands first.
**Recommendation:** flag KC-23-4 as directly at risk from the in-flight #498 §7.2 process, and note in the issue that viewer-sync's fate is coupled to that unresolved documentation decision, not just to the maintainer's PF-6 descope call.

**5. (MED) The issue documents its own likely obsolescence but doesn't hedge sequencing.** Quoting the issue itself: "the review's funded CAP-23 wedge covers only the chronogram slice and the cause-chain inspector — it recommends cutting the PF-6 viewer-sync scope... the viewer-sync half is the first candidate to descope." Filing an issue whose own body predicts ~half its acceptance criteria (AC-3, AC-4, and half of AC #5) will likely be REPLAN'd away is defensible for "capstone coverage completeness," but the issue gives an implementer no guidance to build/land the rewind half independently first and treat viewer-sync as a separable follow-on PR — so a contributor picking this up could spend a working session on Surfer protocol plumbing before the REPLAN that cuts it arrives.
**Recommendation:** explicitly split the acceptance criteria into two milestones in the issue text — rewind (AC-1/AC-2) mergeable standalone, viewer-sync (AC-3/AC-4/AC-5's sync half) gated on #508's REPLAN outcome — rather than one FEAT with a single completion bar.

**6. (MED) AC-2's determinism precondition is asserted, not verified, for the specific engine it will run under.** #504 §3 risk 4 (the parent capstone, which #535 implements a slice of) says plainly: "the replay claim extends [determinism] to 'truncate at T equals state at T', which must hold under the interactive engine, not just batch. Interactive-engine batching hygiene (roadmap standalone item) may be a prerequisite discovered during the demo slice." That hygiene item is real and unresolved: `docs/capability-roadmap/README.md:710` — "`InteractiveSimulator.afterEvent:879-896` runs per-event with a `BitSet` clone per probe, violating `grand-architecture.md` §6's 'batched, rate-limited, never per-signal' rule." Issue #535 does not list this as a blocker or even mention it, despite #504 flagging it as a possible prerequisite for the very claim AC-2 makes. KC-23-3 ("if replay cannot reproduce state byte-identically... stop and file the determinism finding") is a reactive kill switch that fires after implementation effort is sunk, not a preflight check against a known, named risk.
**Recommendation:** add the interactive-engine batching-hygiene item (or a targeted determinism spike under `InteractiveSimulator`) as an explicit precondition/blocked_by entry, not something discovered mid-implementation.

**7. (LOW-MED) Exclusion 2's scope is being imported without re-deriving whether it fits.** #498's exclusion 2 is scoped to "a permanent per-element serialization tax across the whole element library in service of re-running a boot" — i.e., avoiding paying a checkpoint tax across ~35 element types to make a multi-hour Linux boot resumable (CAP-02/#301 territory). Issue #535 reuses that exclusion, via #504, to forbid *any* checkpoint mechanism for a GUI convenience feature on ordinary classroom circuits — a much smaller problem with a plausibly much smaller checkpoint (`lf-03-causal-debug.md` estimates ≈2–3 KB deflated per checkpoint for a 1,551-element flagship circuit, not a "whole element library" tax). The issue does not re-derive whether exclusion 2's cost/benefit calculus, made for the Linux-boot case, actually transfers to this narrower case.
**Recommendation:** either explicitly widen exclusion 2's stated rationale to cover this case (with its own cost numbers) or acknowledge in #535 that a small, non-persisted, in-memory quiescent-point cache is a materially different proposal than what exclusion 2 was written to prevent, and argue why it's still out of scope.

**8. (LOW) AC-2's "randomized fixture circuits and times T" is unspecified in scale.** Unlike sibling AC-6 in #504 ("a seeded two-path glitch"), there's no stated population (element count range, event count range) for the fixtures. A fixture set of small/fast circuits would pass AC-2 trivially while never exercising the cost regime that finding 1 raises, letting the letter of the criterion pass while the real goal (usable rewind at the sizes JLS actually targets) goes unverified.
**Recommendation:** name a size band for the randomized fixtures (e.g., spanning from trivial to the flagship RV32I circuit's event count) so AC-2 actually stresses the O(T) claim, not just correctness on toy circuits.

## What's solid (no rework needed)

- AC-1 (`RewindEqualsReplayTest`) is well-formed: a clear, comparable oracle (byte-identical to a fresh truncated run) rather than a vague "looks right" criterion.
- AC #4 ("the in-tool loop stands alone when no external viewer is installed — sync is degradable, never required") is a good guardrail against a hard external dependency creeping into the core product.
- `ordering_after: [FEAT-C23-1]` points at a real, filed, open issue (#527) rather than a placeholder — the stated dependency is concrete and checkable.
- Deliberately excluding FEAT-035 (#363, general checkpoint/resume) as a dependency is consistent with #504's own framing and avoids scope creep from that much larger feature.
