# Issue #636: TASK-C597-3: one button carries the design from the dialog to a programmed board — export, constraints and the handoff script run from the GUI with the outcome reported, and no terminal
- Lens: adversarial
- Date: 2026-08-08

- Verdict: needs-rework

## Summary

This task (part of feature #597, "GUI board flow") is internally self-contradictory as filed, and the contradiction has already been identified by the repository owner in a same-day review comment — but the fix lives only in that comment, not in the issue body or title. A picker reading the raw issue (API body, as this review itself was instructed to treat as authoritative unless comments say otherwise) would be directed to build a feature the issue's own kill criterion forbids.

## Findings, most severe first

**1. [Critical] The issue body still asks for the thing its own kill criterion prohibits, and the fix is comment-only, not merged.**
The Outcome paragraph states plainly: *"KC-38-1 binds this task — no vendor-toolchain process driving lives in this surface."* Two sentences earlier, AC-1 asks for the opposite: *"One action from the dialog runs export + constraint emission + the handoff script and reports the outcome in the GUI."* AC-2 compounds it, requiring per-stage progress reporting for "a long-running handoff" that must not "present as a frozen window" — language that only makes sense if a multi-minute `yosys`/`nextpnr-ice40` run is being driven synchronously from the GUI. Running `scripts/icestick-handoff.sh` from a Swing action *is* vendor-toolchain process driving; the script's own header says "it does NOT synthesize, place, route, pack, or flash anything (issue #215 H2: delegate, do not reimplement)," and I independently verified the shipped invariant this would break: `grep -rn "ProcessBuilder\|Runtime.getRuntime().exec" src/` returns 0 matches on this checkout, matching #359 §4 invariant 1 ("No subprocess in `src/`... a student who never installs a toolchain must still get a working JLS"). The 2026-08-08T17:34 comment on this issue (by the repo owner) catches exactly this and proposes a corrected 5-point AC list. But it is a comment, not an edit — the body, title, and labels carry no marker that AC-1/AC-2 are superseded. **Recommendation:** edit the issue body directly (strike AC-1/AC-2, substitute the comment's corrected criteria) or at minimum prefix the body with a `STATUS: superseded — see corrected AC below` line, per this repo's own documented convention (other issues in this cluster use `STATUS:`/`REPLAN:` comment tags for exactly this).

**2. [High] The title itself still asserts the false claim, and the comment never touches it.**
"...export, constraints and the handoff script run from the GUI..." and "...carries the design from the dialog to a programmed board..." are both false under the corrected scope: the handoff script is not run from the GUI, and the flow does not reach "a programmed board" — the bitstream step still delegates to a terminal the student runs themselves. Titles are what shows up in every issue list, search result, and dependency graph (`part_of_feature`, `ordering_after` on sibling issues) in this repository; leaving it uncorrected means every downstream reference continues to carry the wrong claim even after the body is fixed. **Recommendation:** retitle to something like "GUI produces export + board constraints and a copyable handoff command line; no terminal to produce artifacts, hardware programming still runs from the toolchain."

**3. [Medium] AC-4's dependency on #598 is real but undeclared in `ordering_after`.**
AC-4 says: *"The diagnostic vocabulary itself is #598's; this task calls it and surfaces it."* But the YAML front-matter's `ordering_after: [264, "TASK-C597-2"]` omits #598 entirely. #598 is itself open, zero comments, not started, and its own boundary note reads: *"Depends on FEAT-C38-1's surface for the GUI half; the diagnostics themselves are testable headlessly and can land ahead of it."* FEAT-C38-1 is #597, this task's own parent feature — so there is a soft circularity (#636 wants to consume #598's vocabulary; #598's GUI-facing half wants #597, of which #636 is a child, to land first) that #598 resolves only by splitting itself into a headless-first subset, a resolution #636 never states or relies on explicitly. **Recommendation:** add #598 to `ordering_after` (scoped to its headless subset) and record the circularity-avoidance reasoning inline rather than leaving it to be inferred from a different issue.

**4. [Medium] Even the corrected AC ("`grep -r "ProcessBuilder\|Runtime.getRuntime().exec" src/` returns nothing... required check, not a nicety") is a lexical check, not a structural one, and is gameable.**
It does not catch subprocess spawning added via a new dependency that itself wraps `ProcessBuilder` (called from `src/` without the literal banned strings appearing there), reflective construction (`Class.forName("java.lang.ProcessBuilder")`), or `Desktop.open`/`Desktop.browse` used to hand a generated script to the OS. None of these require touching the two greppable tokens. This matters because the repo already treats an analogous invariant (headless core, no AWT/Swing in `jls.sim`) as something a grep alone is *not* trusted for — it is enforced by `HeadlessCoreRatchetTest`, a structural test, per ARCHITECTURE.md. A plain grep for two string literals is a weaker bar than the project's own precedent for "this must never come back." **Recommendation:** pair the grep with a structural test (ArchUnit-style or a hand-rolled bytecode/import scan) banning `java.lang.Process*`/`Desktop.open`/`Desktop.browse` reachability from the new GUI action and from `jls.hdl.board`, not just the two string forms.

**5. [Medium] Ordering-array hygiene: mixes an issue number and a task-id string in one array.**
`ordering_after: [264, "TASK-C597-2"]` — 264 is a bare issue number, "TASK-C597-2" is a task id that (I confirmed via search) resolves to issue #634, but nothing in this issue states that mapping. The sibling capstone/feature issues in this repo (#359, #264) maintain machine-readable `blocked_by`/`blocks` arrays of bare issue numbers specifically so a dependency walker can resolve edges without a side lookup. An automated tool walking this repo's DAG by issue number alone will silently fail to resolve this edge. **Recommendation:** normalize to `[264, 634]`.

**6. [Low] `band_mw: "0.5-1"` is stale relative to at least one reading of the task.**
0.5–1 maintainer-week is plausible for the *corrected* scope (write two artifacts, render a copyable command string) but not for the *literal* body (orchestrate 3–4 external processes, stream output, support cancellation on a multi-minute place-and-route, per-stage progress UI) — the latter is closer to the 6–12 mw band #359 prices for arming and differential-testing the same toolchains. Since the body hasn't been edited to match the correction, the cost estimate silently assumes the correction already happened while the acceptance criteria it's attached to do not. **Recommendation:** restate `band_mw` in the same edit that fixes the ACs.

## What's solid

- **AC-3 (byte-identical GUI vs. CLI artifacts)** is well-posed, evaluable today, and reuses an existing pattern (`PcfGoldenTest`-style byte comparison over `PcfEmitter`/`jls.hdl.board`) — this is the strongest criterion in the issue, in both the original and corrected forms.
- **AC-5's keyboard-reachability / stable-naming requirement** is concrete and checkable against the shipped `docs/component-naming.md` scheme and `ComponentIdentityTest` pattern; no ambiguity there.
- **The "surface, not reimplementation" framing** (delegating to `jls.hdl.board` and `scripts/`, not duplicating logic) is architecturally sound and consistent with #264's and #359's recorded invariants — it is specifically the *handoff-script-invocation* half of the task that breaks those invariants, not the framing as a whole.

## Verdict rationale

The task's underlying goal — get artifacts and a runnable command line out of the GUI without a terminal — is legitimate, already scoped correctly by the owner's own comment, and cheap. But the issue as it stands (body + title) still describes the forbidden version, the correction is not merged or even flagged in the body, a real dependency (#598) is missing from the ordering metadata, and the "required check" meant to backstop the correction is a two-string grep that a careless-but-compliant implementation can slip past. `needs-rework`, not `should-not-proceed`: the path to a good version of this task is already written down, it just isn't in the issue yet.
