# Issue #848: TASK-C370-4: the column store and the event queue resolve an element to the same index, and a test fails the moment either grows a private mapping
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of the ask

TASK-C370-4, a small (`band_mw: "1-2"`) child of FEAT-054 (#370), wants one test that (AC-1) resolves every registered element type through both "the column store" (from TASK-C370-2, #843) and "the event queue" (from FEAT-030/#362's TASK-0063, #476) and asserts identical indices, (AC-2) fails if either side grows a private second element→index map, and (AC-3) requires the index contract to be stated in exactly one place, cited by both #370's layout work and #362's queue work, with no behaviour change (AC-4). The instinct — turn "the queue and the arrays use the same index" from a comment into a test — is sound. The execution has real gaps.

## Findings, most severe first

**1. (High) The ordering block omits the one issue the prose says must satisfy AC-3.**
The YAML status block lists only `ordering_after: ["TASK-C370-2 (the index must exist)", "TASK-C370-3 (the queue's element identity must already be flat-backed)"]` — i.e. #843 and #846, both under #370 itself. But the prose says AC-3's concrete proof point is "#362's queue work (#476) cites the same contract rather than restating it." #476 (TASK-0063, the calendar-queue task under #362/FEAT-030) is never named in the machine-readable ordering block, and as of this review it is still open with no landed queue implementation. Every sibling issue in this family (#370, #362, #476, #843, #846) treats the YAML `ordering_after`/`blocked_by` block as the authoritative dependency graph, mirrored on both ends — #370's own body brags about exactly this discipline ("Every edge in `blocked_by` and `blocks`... is written on both issues"). #848 breaks that discipline: its prose names a hard dependency its own machine block doesn't encode. A worker who reads only the YAML (as the other issues train you to) can start this task before #476 exists, at which point AC-3 is literally unsatisfiable — there is no "queue work" code yet to cite the contract from.
*Recommendation:* add #476 (or, more precisely, "TASK-0063 landed" ) to `ordering_after`, or explicitly scope AC-3 down to "the layout side only, WAIVED for the queue side until #476 lands" the way sibling issues use `WAIVED:` comments for exactly this situation.

**2. (High) The title's premise doesn't match what #476 actually specifies the queue to be.**
#848 asserts "the event queue resolve[s] an element to the same index" as the column store, and AC-1 requires sampling "every registered element type through both the column store and the event queue" for identical indices. But #476 (§7.5, O5) specifies the queue's pending-event identity as `(callBack reference identity, payload structural equality)` — not a single per-element slot. `Reacts.react(long now, Simulator sim, SimEvent.Payload todo)` (`src/jls/sim/Reacts.java`) confirms a callback can have multiple simultaneously-pending events distinguished by different `Payload` values (`PinChanged`, `NewValue`, etc. per `SimEvent.java`'s sealed hierarchy referenced in #476). #476 itself is explicit that the slot design is unresolved: "the exact shape is an implementation choice constrained by 7.10 stage 3, not by this issue." So #848 presupposes a design decision — that the queue's dedup structure reduces to one index per element, matching the column store's dense per-element index — that no prerequisite issue has actually committed to. If the eventual queue design keys on `(element-index, payload-kind)` rather than `element-index` alone (plausible, since one element can have several pending payload kinds), then "the queue resolves element X to index N" isn't well-defined, and AC-1/AC-2 as written can't be implemented without first pinning down what "the event queue's index" even denotes.
*Recommendation:* either (a) make #848 block on a resolved TASK-0063 design that explicitly commits to one index per callback, or (b) rewrite AC-1/AC-2 to name the actual data structure ("the intrusive queued flag's slot address") rather than the informal "the event queue['s] index."

**3. (Medium) Child-task ids were minted while the parent's blocking question about minting them was still open.**
#370's own "Open Question 1" states plainly: "The task ids do not exist and minting them is a maintainer decision... **Blocks filing children**," and recommends option (a), "mint ids in a registry addendum," using the project's existing `TASK-0xxx` registry (closed at TASK-0112, per #362/#476's `TASK-0063`, `TASK-0064`, `TASK-0026` etc.). Instead, #848 and its five siblings (#842-#851) were filed with ad hoc `TASK-C370-N` ids that don't fit that registry at all, and #370's Open Question 1 shows no resolving comment. This is a process contradiction on the very issue that explicitly names itself as a filing blocker, not a stylistic nit — it means the task-id scheme #848 relies on (`ordering_after: ["TASK-C370-2 (...)", ...]`) may itself be renumbered or reconciled later, silently invalidating the cross-references this issue depends on.
*Recommendation:* resolve #370 Open Question 1 (mint real registry ids, or explicitly ratify the `TASK-C370-N` scheme as the exception) before treating #848's dependency ids as stable.

**4. (Medium) AC-2's "asserted structurally (architecture rule or equivalent)" has no real precedent in this repo and is easy to satisfy narrowly while missing the real hazard.**
There is no ArchUnit or comparable architecture-testing framework anywhere under `test/`. The closest analogue, `test/jls/HeadlessCoreRatchetTest.java`, is a hand-rolled bytecode/import scan for a much narrower property (no AWT/Swing imports in `jls.core`/`jls.sim`). A naive "structural" check for "no private element→index map" — e.g. reflectively banning `java.util.Map`/`HashMap` fields — would miss a private `int[]`/`long[]` array keyed by element ordinal, a `WeakHashMap`, or an index cached inside a wrapper object, all of which are functionally "a second mapping" but wouldn't trip a narrowly-written check. The issue never says what counts as a disqualifying private mapping (any secondary lookup structure? anything not delegating to the shared allocator introduced by #843?), so two implementers could write structurally-different "passing" tests, one of which leaves the real drift hazard open. This is exactly the "gameable acceptance criterion" failure mode the issue is trying to avoid with AC-2's own framing ("not only by sampling values") — the intent is right, the criterion doesn't yet constrain the implementation enough to deliver on that intent.
*Recommendation:* name the concrete mechanism (e.g., reflective field-type/name scan over `jls.sim` and the column-store package with an explicit allow-list) in the issue itself, or file it as its own decision so review has something concrete to hold the PR to.

**5. (Low) AC-3's "exactly one place" names no owner or location for the canonical statement.**
Is the contract a Javadoc block on a shared constant, a section in `docs/simulation-semantics.md`, or a new short doc under `docs/`? Without a named location, "a second statement of the contract fails review" is enforced by reviewer judgment call rather than anything checkable, which is a soft version of the same gaming risk as finding 4: one file's comment plus a loose "see X" from the other file could pass a lenient review and fail a strict one, with no way to tell from the issue text which was intended.
*Recommendation:* name the artifact (e.g., a `jls.sim` package-info paragraph, or a subsection of `docs/simulation-semantics.md` §3) as the canonical location.

**6. (Low) AC-1's "sample spanning every registered element type" is explicitly weaker than AC-2 and the issue does not reconcile the gap.**
The issue itself acknowledges sampling isn't enough ("not only by sampling values"), which is good, but AC-1's sample is bounded to one instance per of the ~35 registered element types (per #843's AC-1 language) with presumably one pending event each. It won't exercise the multi-pending-event-per-element case that finding 2 shows is exactly where "the queue's index" gets ambiguous. If AC-2's structural check is weak (finding 4), AC-1's sampling is the only thing actually asserting the property, and it's asserting it on a fixture too small to hit the interesting case.
*Recommendation:* extend the AC-1 fixture to include an element with two or more simultaneously pending, differently-payloaded events, once finding 2 is resolved and there's a defined "queue index" to sample.

## What's solid

- AC-4's scope discipline ("golden corpus unchanged; this task adds a test and a citation, not behaviour") is correctly narrow and matches the pattern used by sibling tasks (#843's own AC-3, #846's AC-2) — no objection here.
- The core idea — replace a load-bearing informal invariant ("the queue and the arrays use the same index") with a test rather than a comment — is exactly the right instinct, and the issue is honest that a value-only sampling test is insufficient (AC-2's rationale). The problem is implementation underspecification, not the goal.
- `band_mw: "1-2"` is a reasonable size estimate *if* the dependency and design gaps above are resolved first; it is not overscoped for what a corrected version of this task would need to do.

## Bottom line

The task's goal is right-sized and the reviewer discipline it's asking for (one contract, cited not restated, checked structurally not just sampled) is good practice. But as filed, it has a real contradiction between its prose and its own machine-readable dependency graph (finding 1), rests on a queue design (#476) that hasn't actually committed to the property being tested (finding 2), and its two central acceptance criteria (AC-2, AC-3) are underspecified enough to be satisfied by a narrow implementation that doesn't deliver the anti-drift guarantee the issue exists to create (findings 4-5). None of this is fatal to the concept; it needs the ordering block and the "what is the queue's index" question resolved before someone can implement it as literally written.
