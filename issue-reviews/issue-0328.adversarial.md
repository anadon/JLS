# Issue #328: FEAT-044: a design drawn in JLS is wrapped in a shuttle's fixed top-level signature and carried along a submission path that has actually been walked
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

The issue is a large, formally-structured feature spec (Tiny Tapeout / open-silicon-shuttle wrapper + submission handoff) built on top of the real `src/jls/hdl/board/` mechanism. The design idiom it reuses — all-or-nothing binding, digest-pinned external templates, no-placeholder acceptance — is genuinely sound and matches the codebase's existing `PcfEmitter`/`PinBindings` discipline. But the issue's own bookkeeping is already internally inconsistent at filing time, one of its two named tasks appears to have been filed in violation of a blocking rule the issue itself states, and a "compile-time trap" the issue treats as an existing discipline to be *preserved* does not currently exist in the code and must be *invented* as unscoped work.

## Findings, most severe first

**1. The issue's own machine block and roster are already stale, contradicted by its own comments — before any code has been written.**
The body's `planned_tasks` YAML block and §2 roster table both say TASK-0094 and TASK-0095 are `not filed`. But comment `#issuecomment-5181357795` (posted 2026-08-04T15:44:10Z, essentially the same instant as the issue's own `updated_at` of 2026-08-04T15:44:11Z) states flatly: *"`#328 = #429 + #432`"* and confirms both tasks are filed and open (verified: #429 and #432 both exist, open, `part_of_feature: 328`). The DoD checklist item *"planned_tasks empty (each resolved to a filed issue or descoped)"* is therefore already falsifiable against the issue's own comment thread, and no one has gone back to edit the body, roster, or mermaid graph to match. This is exactly the failure mode the issue's own DoD line *"Machine block, roster table, and mermaid graph agree with reality at close (rule A)"* exists to catch — and it is already failing pre-close.
*Recommendation:* edit the issue body now to mark both tasks filed (link #429, #432) and update the mermaid graph; do not let a planning document drift out of sync with its own comment log by design.

**2. TASK-0094 (#429) appears to have been filed in violation of #328's own stated blocking rule on Open Question 1.**
#328's Open Question 1 says explicitly: *"Which shuttle program and which template revision? ... **Blocks TASK-0094's filing** — it decides the signature."* Yet #429 was filed 2026-08-03T15:54:08Z already hard-coding a specific signature (`ui_in[7:0], uo_out[7:0], uio_in/out/oe[7:0], ena, clk, rst_n` — Tiny Tapeout's `tt_um_*`) as P3's "hard-coded expected list," with no digest recorded and no commit noted as resolving the choice. #429's own Open Questions section then *repeats* "Which shuttle program and which template revision? ... **Blocks execution**" as still unresolved. So either (a) the choice was made informally and never recorded per #328's own recommended default ("pin its template by digest in the same commit, and record the choice's date"), or (b) the filing rule was simply not followed. Either way, a concrete filed task now encodes assumptions about an external interface the parent feature says must not be assumed until pinned.
*Recommendation:* either retroactively record the digest-pinning decision on #328 (with date) and note it in #429, or treat #429 as filed prematurely and correct the record.

**3. Invariant 3 / "the extension-dispatch switch" leans on a mechanism that does not exist in the codebase today.**
The issue (and TASK-0094) repeatedly frames adding `TT_WRAPPER` as breaking "the extension-dispatch switch," calling the compile failure "the intended trap, not a defect," and Global Invariant 3 forbids ever adding a `default` arm to "a format dispatch switch." I verified via `grep` that no `switch` over `Board.Format` exists anywhere in `src/`. The only two call sites are `PcfEmitter.java:61` — `if (board.format() != Board.Format.PCF) { throw ... }`, a two-way guard, not an exhaustive switch — and `JLSStart.java:473`, a plain `.extension()` call with no branching at all. An `if (!= PCF)` guard does not fail to compile when a new constant is added; it silently routes any non-PCF board (including a future `TT_WRAPPER` one) into the wrong emitter's runtime exception path, which is a *runtime* discovery, not the compile-time trap the issue's Alternatives-Considered section explicitly claims to be preserving ("Add the format constant with a `default` arm in the dispatch switch. Rejected... `default` arm converts a compile error into a runtime surprise" — but today there is no exhaustive switch to add a `default` arm to in the first place). Building the actual exhaustive-switch-expression dispatch this invariant assumes is real, uncosted work that neither the feature's cost band nor TASK-0094's task list names as a deliverable in those terms.
*Recommendation:* have TASK-0094 explicitly name "convert the format dispatch from an if-guard to an exhaustive switch expression" as a deliverable, and verify with a scratch branch (as P6 already promises) rather than asserting the trap already exists.

**4. Acceptance criterion 5 (no placeholder cells) has an issue-sanctioned escape hatch that can satisfy the letter while missing the intent.**
§7's Re-planning Protocol and Open Question 3 both pre-authorize replacing `_TBD_` with an "outcome cell that may say 'window closed'" if the shuttle submission window closes mid-walk — explicitly to keep criterion 5 "satisfiable without lying." That is a reasonable design choice on its own, but it means the acceptance check `∀c ∈ C(R): c ≠ _TBD_` can pass with a record table that contains zero evidence a design was ever actually accepted by a shuttle — every cell can legitimately read "window closed" forever, satisfying "no placeholder" while never delivering criterion 4's actual "walked once, with the result recorded" claim, which is the thing invariant 5 ("a returned chip is not a returned test") and the whole feature exist to certify.
*Recommendation:* the acceptance check should assert more than "no `_TBD_`" — e.g., require at least one row whose outcome is a genuine submission result, or track "walked" as a separate boolean the DoD gates on, distinct from "no placeholder cells."

**5. Cost band is admittedly off by up to 3x, with a named-but-unpriced residual.**
The issue states its own registry band (11.5–18 mw) versus the summed task rows (6 wk, 4 wk exclusive) disagree by "1.92x to 3x," calls the band "superseded," and separately names "the ASIC-flow hardening between a synthesizable wrapper and a submittable entry" as a residual "no task id covers... because the registry's task space is closed at TASK-0112." This is disclosed honestly rather than hidden, which is to the issue's credit, but it means roughly a third to two-thirds of the feature's true cost is acknowledged-unknown at filing time. Combined with finding 3 (an uncosted dispatch-mechanism build) the true remaining scope is larger than either printed number.
*Recommendation:* not blocking, but the residual should get its own tracked placeholder issue/estimate rather than living only as prose in §"Cost," so it doesn't silently vanish at close.

**6. Deep, not-yet-startable transitive dependency chain.**
`blocked_by: [327, 339, 359]`, and each of those is itself an open, multi-week, "planned_tasks: not filed" feature with its own further prerequisites (#327 → #336; #359 → #317, #358 → #315). None of #328's three direct blockers has a filed child task yet. This is disclosed candidly in §6 ("Two other programs gate the start... scheduling honesty rather than an excuse"), so it is not a hidden flaw, but it does mean a large amount of formal specification effort (the full §1–§7 apparatus, LaTeX-style transformation definitions, an 8-item evidence plan) has been sunk into a feature that cannot begin implementation for what is realistically months, and whose external interface (the shuttle program itself) is not yet chosen. That is a real feasibility/prioritization concern worth a maintainer sanity check, even though the issue itself flags the ordering honestly.

## What's solid (brief)

- The core reuse argument — this is `PcfEmitter`'s all-or-nothing port-binding idiom retargeted at a fixed external signature — is accurate and well-grounded against the actual code (`Board.java`, `Boards.java`, `PinBindings.java` all match the issue's citations).
- Criterion 5's motivating evidence (`docs/icestick-bitstream-handoff.md:119`, six `_TBD_` cells) is accurate; I confirmed the exact placeholder row via direct file read.
- Digest-pinning the upstream template rather than transcribing it (invariant 1) is a genuinely good call given the cited history of an obsolete template being referenced elsewhere in the corpus.
- Scope boundaries (no PDR/DRC/LVS/GDS, no design authorship) are drawn clearly and consistently across #328, #429, and #432.
- Dedup comments show real cross-issue diligence (#487, #429/#432 split) rather than rubber-stamped filing.
