# Issue #706: TASK-C528-1: the in-tree PrairieLearn external-grader image drives batch mode and nothing else
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of the ask

TASK-C528-1 is the first of three tasks decomposing FEAT-C21-4 (#528, PF-4 of
capstone CAP-21 / #502): commit an in-tree PrairieLearn `externalGrader`
image that pins a specific headless JLS build by digest, invokes batch mode
against a CAP-06 lab-as-data lab, and is structurally incapable of driving an
interactive session. Sibling tasks are named only in prose ("TASK-C528-2",
"TASK-C528-3") but resolve to real, open issues: #708 (the question kit) and
#710 (the CI drift lane), confirmed via `search_issues`. Nothing in the tree
mentions PrairieLearn today (`grep -rli prairielearn .` outside
`issue-reviews/` is empty) — this is greenfield work.

## Findings, most severe first

**1. (High) The issue asserts as settled fact a constraint that its own cited source explicitly disclaims authority over.** The outcome states: "the recording-not-session clause of #498 §7.2 is a constraint on the image, not a convention its author remembers." But #498 is a *rescued, self-declared non-normative* branch document — its own text reads "**It is explicitly non-normative.** … Nothing in it may be cited as settled policy," and §7.2 itself says "**There is no recorded decision to reopen**… The correct action is recording a decision that was never recorded" and lays out a "Process" (a decision issue, an `ARCHITECTURE.md` decision block, a CHANGELOG entry, a five-site consistency pass) that, per the document's own words, has not happened. #706 states this unratified proposal more assertively than any sibling in the cluster ("a constraint… not a convention," presented as already-binding), which is the opposite of what #498 says about itself. The underlying requirement is real and already achievable, but the citation is wrong: `docs/vcd-interop.md` at HEAD already states, in force today, "Graders must not depend on interacting with a running simulation" — that is the actual normative anchor, not #498 §7.2's still-unadopted replacement text. **Recommendation:** cite `docs/vcd-interop.md`'s current (already-normative) sentence, drop or downgrade the #498 §7.2 citation, and if the maintainer wants #498's stronger "recording is the contract" language enacted, file the decision issue #498 §7.2 itself calls for first.

**2. (High) The frozen contract this task promises to consume does not exist, and the real dependency depth is undisclosed.** AC bullet 3 requires the image to "consume only the frozen CLI contract of #524 — invocation, exit statuses, artifact paths, xUnit schema." Verified in tree: `docs/batch-interface.md` documents exactly three exit statuses (0/1/2, no status 3), there is no xUnit schema anywhere in `src/` or `test/` (only aspirational mentions in `docs/capability-roadmap/*` planning documents), and no `CliContractConformanceTest` exists. #524 itself is open and was reviewed `needs-rework` (stale `ordering_after` still naming #369, an AC-1 that is false as literally worded at HEAD) and is itself blocked on #369 and #466, both open. #706's own `ordering_after: [524]` names only the direct predecessor, omitting the transitive chain the sibling reviews of #528/#708/#710 already documented in this same cluster. `band_mw: 0.5-1` is given with no "marginal only, contingent on #524/#369/#466" caveat, unlike the discipline #369/#466 apply to themselves. **Recommendation:** state explicitly that this task is not startable until #524 lands (transitively #369/#466), and mark the cost estimate as marginal-only.

**3. (High, novel to this issue) The issue never engages with the already-existing, already-reproducible JLS batch-mode container image, creating a concrete duplication/drift risk.** `resources/packaging/Dockerfile` and `scripts/build-container.sh` already build and publish a digest-pinned, reproducible, headless-only JLS image to `ghcr.io/anadon/jls`: the base image is pinned by sha256 (`FROM ubuntu:26.04@sha256:...`), apt installs are pinned to a fixed archive snapshot, timestamps are clamped via `SOURCE_DATE_EPOCH` (issue #184's reproducibility work), and the entrypoint is already batch-only (`ENTRYPOINT [".../java", "-jar", "/opt/jls/jls.jar"]`, `CMD ["-h"]`). #706's AC-1 ("the image is defined in tree, pins the JLS build by digest, and builds reproducibly from the committed definition") reads as if this reproducibility work is still to be invented, and never states whether the PrairieLearn `externalGrader` image is meant to be a thin layer `FROM ghcr.io/anadon/jls` (reusing the already-solved digest/reproducibility machinery) or an independent image with its own build pipeline. An independently-built image risks silently wrapping a different JAR build than the general-purpose image pins, which directly undermines the "consumes only the frozen CLI contract" promise this same AC makes two lines later — two images claiming to pin "the" build with no stated mechanism keeping them in sync. **Recommendation:** state explicitly that the PrairieLearn image is `FROM ghcr.io/anadon/jls@<digest>` (or give a reasoned exception), rather than leaving the relationship to the existing image unaddressed.

**4. (Medium) AC-1 and AC-2 describe two different artifacts without reconciling them.** AC-1 requires the image to "pin the JLS build by digest." AC-2 requires "an instrumented build asserts no interactive session is ever opened." If the instrumented build is a distinct variant (a classpath-scan agent, an AWT-loading tripwire compiled in) rather than the exact digest-pinned bytes that ship, then AC-2 proves the headlessness property about an artifact that is not the one AC-1 pins — a build could pass AC-2 on an instrumented variant while the shipped, digest-pinned image was never checked for the same property. This is the same shape of gap `ARCHITECTURE.md`'s `HeadlessCoreRatchetTest` avoids for `Simulator`/`BatchSimulator` by scanning the actual shipped classes, not a separate instrumented copy. **Recommendation:** clarify that instrumentation is a test-time harness applied to the same shipped JAR bytes (e.g., a Java agent attached at test-run time, not a recompiled variant), or that the tested build's digest is asserted equal to the shipped build's digest.

**5. (Medium) Two acceptance criteria name no verification mechanism and are gameable as written.** "Builds reproducibly from the committed definition" (AC-1) and "scrapes no incidental output" (AC-3) are both stated as bare prose with no named test, unlike #524's own `CliContractConformanceTest` or #524 AC-2's seeded-violation transcript. As written, "builds reproducibly" could be claimed from a single informal rebuild rather than a repeatable two-build diff, and "scrapes no incidental output" could be claimed by a code-review glance at the entrypoint script rather than a scan proving the entrypoint touches only the paths #524 will eventually freeze. This is the identical gameable-AC pattern the sibling reviews in this cluster already flagged (#708 finding 2, #710 finding 4). **Recommendation:** name concrete checks — a two-build `sha256sum` diff (mirroring `docs/reproducibility.md`'s existing jar recipe) for reproducibility, and a grep/allowlist test over the entrypoint's file and env reads for the scraping clause.

**6. (Low) The lab-as-data fixture this task's own acceptance test needs is not named as a dependency.** AC-2 requires "grading a fixture submission through the image produces verdicts derived from batch artifacts only," which needs *some* CAP-06 lab-as-data lab to exist. `grep -rl "lab-as-data"` returns zero hits anywhere in the tree outside `issue-reviews/`; the format is presumably #300's (CAP-06's) deliverable, and #300 is not in `ordering_after`. Lower severity than finding 2 because #706's boundary correctly defers the *question kit* (which needs a real lab) to #708 — but the image's own fixture-grading test still needs a minimal fixture from somewhere. **Recommendation:** name the fixture source (even a synthetic one committed alongside this task) rather than assuming #708's eventual kit supplies it.

**7. (Low) The sibling-task cross-references are prose-only, with no issue numbers given.** The Boundary section names "TASK-C528-2" and "TASK-C528-3" with no `#` numbers; both resolve to real issues (#708, #710) via search, but `get_sub_issues` on #528 and on #706 both return empty — none of this cluster's parent/child relationships are registered as GitHub-native sub-issues. This matches a repo-wide convention already flagged as low-severity in the #524 review (finding 6), and that review separately documents a case in this same convention where a claimed cross-issue "mirror" of an edit did not actually happen. Noted for completeness, not counted heavily against this issue specifically. **Recommendation:** add the issue numbers inline at minimum.

## What's solid

- **Boundary discipline is clean.** "The image. The question kit is TASK-C528-2; the drift lane and doc-tests are TASK-C528-3" matches #708's and #710's own boundary statements exactly — no scope creep in either direction, verified by reading all three issues.
- **The batch-only design is architecturally consistent with the shipped codebase.** `BatchSimulator`/`Simulator` already have no interactive coupling per `ARCHITECTURE.md`'s threading-model section, and the existing `ghcr.io/anadon/jls` image already ships a batch-only `ENTRYPOINT`/`CMD` — an `externalGrader` image invoking `jls -b` as a subprocess is a natural extension of an existing, working pattern, not a novel risk.
- **"Consumes only the frozen CLI contract… and scrapes no incidental output" correctly inherits CAP-21 risk 5's documented-contract-only discipline**, consistent with how #525/#528 frame the same constraint for their own adapters.
- **The cost figure is internally consistent with the capstone breakdown**: #706 (0.5-1) + #708 (0.5-1) + #710 (0.5) sums to roughly #502's own "PF-4: 2 mw" line, even though (per finding 2) it should be flagged as marginal-only.

## Verdict rationale

The scope and architectural fit are sound, and this task is one of the more disciplined members of its cluster on boundary-setting. But it asserts an unratified document as a binding constraint while the actually-normative anchor for the same requirement sits unremarked-upon two files away, it inherits (without disclosing) the same deep, unlanded dependency chain the sibling reviews in this cluster already caught, it is silent on directly relevant existing container-image infrastructure in a way that creates a real duplication/drift risk unique to this issue, and half its acceptance criteria name no verification mechanism. **needs-rework.**
