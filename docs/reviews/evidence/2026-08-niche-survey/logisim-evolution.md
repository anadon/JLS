INSTALL PATHS: signed-ish platform installers MSI/DMG/DEB/RPM with bundled JRE, plus Snap, Flatpak, Homebrew, Chocolatey, plain JAR (README). No web version. FEATURES: chronogram (timing diagram), FPGA board download flow (Vivado/Quartus/openFPGA), VHDL+Verilog netlist export, VHDL-behavior components, TCL/TK console, appearance editor, big TTL 74xx + SoC component library, per-bit 4-state values (TRUE/FALSE/UNKNOWN/ERROR masks in data/Value.java — richer than JLS's 2-state+HiZ). Backward compat with legacy Logisim files explicitly not guaranteed (docs/docs.md). Autograding is third-party glue: e.g. perona.dev/projects/logisim-evolution-autograder (Python+Docker+Gradescope wrapping `-tty table`).

- contributor_experience: 4 — PRs from first-time contributors merged within 1–4 days (sampled #2786–#2800, Jul–Aug 2026) with responsive maintainers, though CONTRIBUTING.md is six bullet points and there's no architecture onboarding.

## TOP USER COMPLAINTS
- Simulation speed capped by GUI redraw: every signal change redraws the canvas, so big circuits run at ~2-4 kHz despite the 2048 kHz setting (#786 'Redrawing of GUI-windows', discussions #1406, #1894; #1493 'Evolution runs slower than Logisim'). 4.0 improved raw engine speed but redraw coupling remains the tracked bottleneck.
- Autograding/CLI verification is officially 'haphazard': #1546 'Command-line verification cleanup' (docs 'incomplete and possibly misleading'), #441 'Command Line Verification Bugs', #185 (-test silently broke between versions), test vectors can't drive sequential circuits (#598, #950), don't-care 'x' inputs broken (#1123). Instructors build their own Python/Docker Gradescope glue (perona.dev autograder).
- FPGA export reliability: invalid VHDL generated for partially-used buses ('somebus(5) => OPEN', #1871), registers uninitialized in exported HDL, RAM only synthesizable via VHDL not Verilog, Quartus toolchain path detection broken on Windows since Vivado support landed (#91), toolpath setup confusion (discussion #1676), and simulation-vs-HDL behavioral mismatches (S-R flip-flop conflict case).
- File-format/version instability: 4.0.0's Pin Type/Behavior simplification silently breaks older circuits relying on floating-pulls-to-0 (release notes + CHANGES.md); 3.6.0 broke transistors/transmission gates; legacy-Logisim .circ compatibility explicitly not guaranteed (component renaming for VHDL); tick frequency not saved correctly (#2344); custom appearance sometimes not saved (#2209).
- False or opaque simulation halts: 'Oscillation apparent' on legitimate cross-coupled NAND latches (#2454) because detection just gives up after N iterations; 'Simulation halted by internal error' (#65, #2005 ArrayIndexOutOfBounds when generating timing diagram); OutOfMemoryError loading certain files (#1516).
- Stale documentation: in-app help is the Burch-era HTML manual that no longer matches the UI (#2432 'Documentation for Counter doesn't match appearance'); no official manual for Evolution-specific features (FPGA flow documented mostly by third parties like ti-uni-bielefeld/logisim-evolution-basys3).
- HiDPI/UI scaling problems: tiny menus on 4K (#69), scaling breaks after opening a file dialog (#524).
- Editor ergonomics friction: labels behavior (#88 'Frustrating Labels', top-reacted open issue), no component search bar (#1234), rotate/mirror not available for all elements (#309).

## DEV COMMUNITY
Org-run under the logisim-evolution GitHub org; day-to-day gatekeeping by BFH-ktt1 (Bern University of Applied Sciences) who merges nearly every PR, with davidhutchens (academic) as second maintainer voice; historically a federation of university forks (Holy Cross / REDS-HEIG / BFH) — old top-reacted issue #215 ('a lot of effort done in forks but not merged in main; why not merge?') records that fragmentation pain. 147 lifetime contributors; the active set at any time is roughly 5-8, currently including productive newer contributors (V-Zemlyakov, johnb432, hewzhew, META-Xiao) landing multiple PRs per week. WHAT ATTRACTS: a huge guaranteed user base for your feature, an easy `./gradlew run` Gradle build with bundled toolchain, fast merge turnaround (1-4 days on sampled Jul-Aug 2026 PRs), checkstyle/CodeQL keeping style honest, and low process ceremony (CONTRIBUTING.md is six bullets). WHAT REPELS: no architecture documentation whatsoever — the maintainer's stated onboarding method is 'pick a small aspect and trace it through the running software' (discussion #1632); a 217k-LoC Burch-lineage codebase full of 1,400-2,500-line classes where GUI, model, and FPGA netlisting are tangled; a test suite covering ~4% of the code, so contributors can't know if they broke something (which is how 4.0-era sync regressions and the recurring '-test broke between versions' pattern happen); and single-gatekeeper merge dependency on BFH-ktt1. Net: excellent drive-by contributor experience, poor deep-contributor experience — people add TTL chips and GUI fixes, almost nobody touches the propagator or netlist core.

## SWITCH ANALYSIS
### pull_users
The winnable users are INSTRUCTORS WHO GRADE, not students. Concrete JLS pull: batch grading with -t vectors, documented stability contract, deterministic runs, VCD + SVG/PNG export — directly answering LE's own tracker (#1546 'haphazard' CLI verification, #598/#950 no sequential-circuit vectors, #1123 broken don't-cares, #185 grading flags silently breaking across versions), which today forces every course to maintain custom Python/Docker Gradescope glue. Secondary pull: delay-accurate discrete-event simulation for teaching hazards/races/glitches, where LE offers a crude oscillation heuristic that false-positives on NAND latches (#2454) and an undocumented timing model. Migration cost, honestly: enormous — courses have years of .circ files, lab handouts, TA muscle memory, and autograder pipelines; JLS has no .circ importer, so today the switching cost is 'redraw every lab from scratch.' Students individually will not move (they use what the course mandates), so the unit of conversion is a course, and a course converts only if import + grading + docs are all ready on day one.
### pull_devs
JLS's pitch to LE contributors: an 82k-LoC codebase (2.6x smaller), mutation testing + NullAway + SpotBugs + warnings-as-errors versus LE's ~4% test coverage and zero architecture docs, reproducible builds, and a maintainer who reviews everything (same as LE, but with contract tests catching regressions instead of users catching them). The realistic target is the contributor LE structurally repels: anyone who wants to work on simulation semantics or the netlist core, where LE has no safety net and no documentation. Counterweights: LE offers 7.4k-star visibility for your work and 1-4-day merges; JLS offers 3 stars and an audience of nobody, and JLS's own 5,852-line SimpleEditor god class undercuts the 'elegance' pitch on the file a new contributor opens first. Elegance attracts only after users exist.
### jls_deficits
Brutal list of what blocks any pull: (1) no .circ import — the single hard blocker; (2) no chronogram panel while LE ships one (and JLS's own is 'not yet'); (3) LE's per-bit 4-state UNKNOWN/ERROR domain is semantically richer than JLS's 2-state+HiZ — JLS currently loses the 'X-propagation pedagogy' argument it should own; (4) no FPGA board flow at all vs LE's end-to-end (buggy but existing and unique) Vivado/Quartus/openFPGA path; (5) component library breadth: LE's TTL 74xx catalog, SoC/RISC components, VHDL-behavior components, TCL console, appearance editor; (6) no subcircuit parameterization on either side, so no differentiation there; (7) JLS README has no screenshots and 3 stars — below the credibility floor for a department to bet a course on; (8) both are Swing desktop apps, so JLS gets zero on-ramp or UI-modernity advantage; LE additionally has 8 package-manager channels and bundled-JRE installers, so JLS's installer story is at best parity.
### winnable_verdict
Verdict: LE's mass-market student base is NOT winnable in any near term — 7.4k stars, worldwide course lock-in, real momentum (daily commits, on-schedule majors), and fast-merging maintainers mean JLS cannot out-community or out-momentum them. The winnable segment is the autograding instructor and the timing-semantics course: LE's grading/CLI story is its most neglected, self-admittedly broken surface, and its timing model is its weakest documented area — both are JLS's strongest shipped assets. Minimum bar to convert the first course: (a) a .circ importer that round-trips LE's std library and subcircuits for combinational+register labs (without this, nothing else matters); (b) a chronogram panel, since instructors will demo waveforms; (c) README screenshots plus a 'grade 200 submissions in 5 minutes, bit-for-bit reproducible' one-page walkthrough with Gradescope container recipe; (d) an honest migration doc mapping LE's 4-state semantics onto JLS's domain (or per-bit X/Z in JLS) so instructors trust equivalence. Contributor pull is a second-order effect: win 2-3 courses first, then JLS's quality-gate story becomes a credible recruiting pitch against LE's untested 217k-LoC core.
