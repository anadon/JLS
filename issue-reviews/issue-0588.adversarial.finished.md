# Issue #588: FEAT-C36-1: two head-to-head comparison notes publish with runnable appendices — every claim about a competitor's grading or timing cites their own tracker and reproduces on a stranger's machine
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of the ask

Two short docs (`docs/comparisons/grading-determinism.md`, `docs/comparisons/timing-honesty.md`) with committed runnable appendices, citing competitor issues verbatim, published to "the docs site," each admitting at least one JLS loss, gated behind #300 (CAP-06 grading verdict), #512 (CAP-28 perf receipts) and #560 (cross-tool harness).

## Findings, most severe first

**1. All three named prerequisites are unbuilt — the issue is scheduled work stacked on scaffolding that doesn't exist yet, and two of the three are not even this note's dependencies to control.**
`ordering_after` names `#300 CAP-06`, `#512 CAP-28`, and `#560 FEAT-C28-4`. I confirmed all three are open (`state: open` on all). `#300`'s abstract itself says the shipped grading story today is "a Python script diffing three literal lines," and `docs/batch-interface.md:17-48` still documents only the historical 0/1/2 exit-code taxonomy — no "verdict" exit status exists. So AC-1's "grading-determinism.md" cannot honestly describe JLS's own grading behavior as anything beyond that three-line diff today, which directly contradicts the note's implied purpose (showcasing JLS's grading advantage). Recommendation: either re-scope this note to compare only what's shipped today (weaker, but honest), or make the `ordering_after` a hard blocking dependency the tracker enforces, not a comment nobody can act on before #300/#512/#560 land.

**2. AC-1's "reachable from the docs site" assumes infrastructure that ARCHITECTURE.md's own recorded decision says doesn't exist.**
ARCHITECTURE.md:252-267 ("Help delivery: in-jar now, hosted docs are the planned future") states plainly: "Hosted, versioned web documentation is the planned future direction... when it happens, the in-app viewer shrinks." There is no `mkdocs`, Jekyll config, GitHub Pages workflow, or `docs-site` directory anywhere in this repo (checked; none found). AC-1's parenthetical "(or equivalent published paths)" quietly acknowledges this gap but doesn't resolve it — the issue is written as if publishing to a site is a formality when it is, per the project's own architecture doc, unbuilt infrastructure. Recommendation: state explicitly that AC-1 is satisfied by "in-tree + linked from README" until the docs-site capstone lands, or file the docs-site prerequisite as its own blocking issue.

**3. The required citation set depends on evidence files that are not committed to this repository (or any branch visible here).**
The issue says: "Sourced from `docs/reviews/evidence/2026-08-niche-survey/` in this repo." That path does not exist in this checkout (`find` returns nothing). Tracing further: issue #510 (the survey this cites) says the evidence is "committed at `docs/reviews/evidence/2026-08-niche-survey/` on `claude/jls-project-review-505pnf`" — a branch that does not appear in `git branch -a` or the remote branch list fetched to this clone. So "in this repo" is currently false; the cited source material lives (if anywhere) on an unmerged branch. A contributor picking up #588 today cannot verify a single one of the required citations (Logisim-Evolution #1546/#598/#950/#1123/#441/#185, CircuitVerse #1412/#5328/#1753/#2198, Logisim-Evolution #2454) against the promised local evidence file — they'd have to re-derive everything from the live GitHub trackers, making the "in this repo" claim actively misleading about the actual workload. Recommendation: fix the issue text to point at the correct branch/PR, or drop the "in this repo" framing and just list the citations to verify live (which is achievable, but is a different, larger task than "copy from an evidence file").

**4. AC-4's "freshness gate" is unfalsifiable as written — there is no owner, no cadence, and no test.**
"A documented recheck step exists" is satisfied by writing a paragraph that says "recheck periodically" — that's gameable. Nothing in the AC specifies who reruns the check, how often, or what CI/process catches staleness (contrast with the sibling `#560 FEAT-C28-4`, which at least implies re-publication is tied to engine-stack landings). A competitor issue (e.g., Logisim-Evolution #1546 "Command-line verification cleanup") could be closed/fixed the week after publication and nothing in this issue's acceptance criteria would ever surface that, short of a maintainer manually re-reading two docs. Recommendation: add a concrete mechanism — e.g., a scheduled CI job that queries the cited issue numbers' state via the GitHub API and fails the build if any cited issue has closed since the "checked against" date.

**5. "Byte-for-byte where determinism is the claim" (AC-2) is a stronger bar than JLS's own test suite currently enforces, and is silently underspecified for the timing note.**
The grading-determinism note's whole thesis requires byte-identical output from a documented command on "a clean checkout" — but JLS's batch determinism guarantees (see `docs/batch-interface.md`) are about deterministic *simulation results*, not about byte-identical text across JVM versions/locales/line-endings on an arbitrary "stranger's machine" (title's own phrase). Nothing in the AC pins JDK version, locale, or OS for the appendix's expected output, so a reviewer on a different JDK/locale could get functionally-identical but not byte-identical output and the AC would be ambiguous about whether that's a pass or a documented failure of the note. Recommendation: pin the appendix's reproduction environment (JDK version range, `LC_ALL=C`, line-ending policy) explicitly in AC-2, and separately define what "reproduces" means for the timing-honesty note (which is presumably not a byte-diff claim at all — it's about honest description of behavior, not determinism).

**6. Scope-creep risk: "each with a dated 'checked against' line naming the competitor release tested" for two different upstream projects with different release cadences, inside a single small feature (2-3 mw) that also has to write, cite, verify, and appendix-build two notes.**
The band estimate (2-3 mw) is tight for what's actually being asked: verify ~11 competitor issue claims against current upstream state (item 3 above shows this can't even start from the promised local file and must be done live against GitHub), build two runnable, committed fixture+command appendices that a stranger can run byte-identically, and satisfy a tone/voice bar ("no adjectives their maintainers would not recognize as fair") that requires editorial judgment, not engineering. This is either underestimated or scoped to skip the verification work entirely (i.e., trust #510's citations uncritically, which conflicts with AC-3's "any additional claim carries the same standard" and undercuts AC-4's freshness gate on day one). Recommendation: split "verify + refresh the #510 citation list against current upstream" out as its own preparatory task with its own estimate, separate from "write two notes."

**7. AC-5 ("at least one competitor advantage... a note with no losses in it fails review") is a good, sound requirement — no notes here, it's a genuine safeguard against marketing creep and is concretely testable (a human reviewer can grep the note for an admitted loss).**

**8. The tone/citation discipline in "Boundary notes" (quote from trackers, no unfair adjectives, defer performance numbers to #512/#560 rather than re-deriving) is a solid, low-risk scope boundary and correctly prevents this issue from re-doing #512/#560's job.**

## Net assessment

The document-shape acceptance criteria (two notes, appendices, citations, an admitted loss, a freshness statement) are individually reasonable and mostly testable. But the issue is filed as if it's ready to implement when it is gated behind three unshipped capstones (finding 1), assumes a hosting mechanism the project's own architecture doc says doesn't exist yet (finding 2), and points at a source-of-truth file that isn't reachable from this repository or any branch found here (finding 3) — meaning a contributor starting today cannot satisfy AC-2/AC-3 as literally written without first re-deriving the entire evidence base live from GitHub, undocumented in the issue. The freshness gate (finding 4) and the determinism bar (finding 5) are both underspecified enough to be gamed or stalled indefinitely. Recommend reworking the issue to (a) either hard-block on #300/#512/#560 in the tracker, or trim AC-1/claims to what's shippable today, (b) fix or drop the "in this repo" evidence-file claim, and (c) add a concrete, automatable freshness-check mechanism before this is picked up.
