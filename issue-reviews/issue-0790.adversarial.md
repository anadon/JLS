# Issue #790: TASK-C591-3: the paper is actually submitted with the receipt recorded — and if the course pilot did not arrive, the tool-paper fallback is a dated written decision, not a quiet substitution
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what's being asked

TASK-C591-3 (0.25–0.5 mw) is the last link in a four-deep chain — CAP-36 (#520) → FEAT-C36-4 (#591) → TASK-C591-1 (#785, venue+deadline) → TASK-C591-2 (#786, draft+review) → this issue — whose job is to actually submit a SIGCSE/WCAE/ASEE-class paper about JLS's autograding contract, record the receipt, and record a dated fallback note if WashU's course pilot (#509) doesn't land in time. This is a non-code, single-maintainer academic-publishing task riding on the same issue-tracker machinery used for compiler warnings and SpotBugs thresholds elsewhere in this repo, and it inherits problems from that mismatch.

## Findings, most severe first

**1. No human-subjects/IRB path anywhere in the chain, yet the paper's strongest version is built on real student data.** AC-5 and the fallback logic exist specifically because "the course-experience section" depends on #509's WashU CSE 260M pilot — i.e., data from actual enrolled students. Neither #790, #591 (`ordering_after: ["#509 — the WashU CSE 260M pilot supplies the course-experience section if it materializes"]`), nor #509 itself mentions IRB approval, FERPA constraints, or any consent process for using course/student data in a publication. SIGCSE/ASEE-class venues routinely require an ethics/IRB statement for anything touching real students. This is not a boundary-note omission — it's a load-bearing precondition missing from the acceptance criteria of the very issue (#790) that is supposed to decide whether the course-experience section ships at all.
   - *Recommendation:* Add an AC to #790 (or #509) requiring IRB/ethics clearance to be recorded before any course-experience section is drafted, with the "tool-paper fallback" as the explicit default if clearance isn't obtained — not only if the pilot "did not arrive."

**2. The acceptance criteria are gameable on venue quality and on "pursued first."** AC-3 only requires "a submission receipt or confirmation... with its date and the venue named" — it never re-checks that the venue is actually SIGCSE/WCAE/ASEE-class (that judgment lives in TASK-C591-1/#785, which #790 does not re-verify at submission time). A submitter under deadline pressure could submit to a non-selective, non-peer-reviewed workshop, name it, attach a date, and technically close #790. Likewise "co-authorship with the #509 pilot was pursued first and the outcome... is recorded, whichever way it went" has no floor: a single perfunctory email that goes unanswered satisfies "pursued" as literally as a sustained negotiation would, despite #591's own boundary note calling co-authorship "the strongest version" that "should be pursued first."
   - *Recommendation:* Either pin AC-3 to re-validate against #785's recorded venue criteria at submission time, or accept the gap explicitly as trust-the-maintainer (fine for a solo project, but say so).

**3. Effort estimate is not credible for what's actually entailed.** #790 alone is banded 0.25–0.5 mw, and the whole #591 feature (venue selection + full draft + external review + submission) is banded 1.5–3 mw. That excludes: conference-template reformatting, possible submission fees, coordinating a named external reviewer (TASK-C591-2's AC), negotiating co-authorship terms and author order with an external academic (#509's Dr. Siever), and — per Finding 1 — IRB paperwork, which alone commonly takes weeks-to-months at a university and is entirely outside this project's control. The rest of this repo is careful about realistic scoping (e.g. ARCHITECTURE.md's "sixteen places to touch" honesty for a new element); this task inherits none of that rigor for a genuinely harder, externally-gated deliverable.
   - *Recommendation:* Re-band with IRB and co-author negotiation as named, separately-tracked risk items with their own lead time, not folded into "logistics."

**4. Verification lives entirely off this issue, with no enforcement.** Every AC on #790 says "recorded on #591," not on #790 itself — the task whose closure the checkboxes gate isn't where the evidence has to appear. Nothing in the tooling (no bot, no linked-issue check) prevents #790 from being checked off without a corresponding note ever landing on #591. Contrast this with literally every code-facing contract in ARCHITECTURE.md, each backed by a named enforcing test (`FormatHeaderTest`, `SaveTagsTest`, `ElementConstructorContractTest`, etc.) — this task's "ratchet" is a human remembering to cross-post. That's a defensible limitation for a writing deliverable, but it is inconsistent with the project's own stated verification culture and should be named as an accepted gap rather than left implicit.
   - *Recommendation:* State explicitly (in #790 or #591) that this AC set is honor-system/maintainer-attested, not tool-enforced, so reviewers don't mistake the checkbox format for the same guarantee it carries elsewhere in this repo.

**5. Anonymity vs. reproducibility-appendix requirement is unaddressed.** AC-3 of #790 requires "the submitted version's reproducibility appendix matches what is committed in tree at the submission commit, and that commit is recorded" — i.e., a public link to a GPLv3 repo, with commit hash, tied to the submission. If the target venue (chosen in #785) uses single- or double-blind review, publicly linking a repo whose commit history names the author de-anonymizes the submission before review. Neither #790 nor #785's AC list mentions checking the venue's blind-review policy against this requirement.
   - *Recommendation:* Add a check in TASK-C591-1 (#785) or here: confirm the venue's review-anonymity policy is compatible with a publicly-attributed, publicly-linked reproducibility appendix before submission, or prepare an anonymized appendix mirror.

**6. Minor: dependency chain is transitively sound but not self-evident from #790 alone.** #790's `ordering_after` is `["TASK-C591-2", 509]` and omits TASK-C591-1 (#785, venue/deadline selection) even though AC-3 requires "the venue named." This isn't actually a broken dependency — #786 (TASK-C591-2) itself orders after #785, so the chain is transitively closed — but a reader of #790 alone, without pulling #785/#786, cannot tell that venue selection happened upstream. Low severity, easy fix.
   - *Recommendation:* List all three predecessor tasks in `ordering_after` for readability, even though the transitive closure already covers it.

## What's solid

- The core framing — submission-not-acceptance as the criterion (AC-3) — is the right call; acceptance is genuinely outside the project's control, and gating on it would make the task unfinishable by design. One line, moves on.
- The fallback rule (AC-5/KC-36-2: drop the course-experience section and say so in a dated note, rather than fabricate or pad) is well specified and directly falsifiable — either the note exists and says what it must, or it doesn't.
- The Boundary section correctly excludes post-submission outcomes (reviews, camera-ready, presentation), keeping this task's scope bounded to logistics rather than creeping into publication management.
- The reproducibility-appendix-matches-commit requirement (setting aside Finding 5's anonymity conflict) is a concrete, checkable artifact requirement consistent with this project's general commitment to reproducibility elsewhere (README's build/BOM reproducibility story).

## Bottom line

The submission-not-acceptance framing and the fallback rule are sound, but the task as written is missing a load-bearing precondition (human-subjects clearance), has acceptance criteria that can be satisfied without the substance they're meant to certify (venue quality, genuine co-authorship pursuit), carries an unrealistic effort estimate once IRB and external-author coordination are counted, and leaves an unaddressed conflict between its own reproducibility-appendix requirement and typical blind-review norms. None of this is fatal to the goal, but the issue needs rework before "submission logistics" can be treated as a 0.25–0.5 mw task someone can just execute.
