# Issue #390: TASK-0072: a retirement record whose type makes over-constrained parity a compile error, emitted as a canonical trace through the existing probe hook
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

The issue is unusually well evidenced against `src/jls/sim/`, `src/jls/elem/WireNet.java`, and `src/jls/JLSStart.java` — every O1–O6 line citation checked out byte-for-byte against this checkout. But it rests its entire technical mandate on a document (`docs/parity-contract.md`) that (a) does not exist anywhere in this checkout, and (b) even where it does exist (at the pinned evidence commit), carries a status line the issue never surfaces: "proposed normative contract... not yet ratified... binds nothing and no other document may cite it as settled." Its own parent feature issue explicitly records that this is a blocking open question for filing this exact task. There is also an unaddressed architectural question — how one CLI invocation produces both the untouched batch trace and the RVFI trace from a codebase where exactly one `Simulator` instance drives a circuit — that the Method section never confronts.

## Findings, most severe first

**1. The parent feature (#347) explicitly states this task's filing is blocked on an open question this issue never mentions.** #347 (FEAT-034), the `part_of_feature` this issue names, contains: "**The parity contract is unratified, and it governs this feature.** `docs/parity-contract.md:3-7` at `2d0ca9d` reads: `Status: proposed normative contract — written, not yet ratified... until then it binds nothing and no other document may cite it as settled.` ... This feature must surface the decision, not resolve it unilaterally. **Blocks filing TASK-0072 and TASK-0073**, whose acceptance criteria cite contract sections." Issue #390 is TASK-0072. Its own `Status & Dependencies` block declares `blocked_by: []` and never once raises the ratification question, despite building P2 (the "load-bearing" test), the twelve-field alphabet, and the entire permitted-to-differ enforcement mechanism directly on §3.1/§4/§5.1 of that unratified document. This is a direct contradiction between #390 and the feature issue it claims to be scoped under, not a matter of interpretation. Recommendation: resolve #347's Open Question 1 (record the ARCHITECTURE.md §8.3 decision block, or explicitly accept the risk of building to an unratified spec) before this issue proceeds, and update `blocked_by` accordingly.

**2. `docs/parity-contract.md` does not exist in this checkout at all.** `ls docs/` lists no such file; `find . -iname "*parity-contract*"` under `docs/` returns nothing on HEAD. A contributor picking up this issue today cannot open §3.1, §4, or §5.1 to check anything the issue asks them to implement against — they only have the twelve field names restated inline in P2, with no rationale for the four deliberately-omitted families beyond what §11 restates secondhand. (History shows the document existed at points in this repo's timeline and was later removed by a commit reading "docs: remove the planning corpus now that it is encoded in issues" — but that removal is not reflected back into this issue's own body, so the issue cites section numbers of a file whose lifecycle it does not track.) Recommendation: either restore/re-file the contract as a citable artifact, or fold its full content (not just the field list) into this issue so it is self-contained.

**3. Two-pass simulation architecture is required but never specified.** `src/jls/JLSStart.java:246` shows batch mode constructs exactly one `new BatchSimulator()`, stores it in the single static `JLSInfo.sim`, and calls `runSim()` once; `src/jls/sim/Simulator.java:198` shows every `LogicElement.initSim(this)` binds an element to one driving `Simulator` instance per initialization pass. §7.1 requires "Batch stdout is unchanged" (i.e. `BatchSimulator` still runs normally) while a *third* `Simulator` subclass (`RetireTraceRecorder`) must also drive the same circuit to emit the RVFI trace. Since one `LogicElement` set can only be bound to one `Simulator` at a time, this necessarily means running the circuit twice — once under `BatchSimulator`, once under `RetireTraceRecorder` — with a fresh circuit load (or full reset) between passes, doubling batch wall-clock cost and introducing a determinism dependency (two passes must produce identical retirement content) that no prediction (P1–P8) actually tests. Materials & Apparatus and the Method checklist never mention this second pass, its cost, or how `JLSInfo.sim`/element rebinding is handled between the two runs. Recommendation: add an explicit prediction/test that runs `-b -t vectors -rvfi trace.txt` together and asserts both outputs are produced and consistent, and cost the doubled simulation time.

**4. The reserved-name validation this task depends on is itself unfiled at the time this text was written, and the fallback duplicates logic that must later be reconciled.** §7.11 states the recorder must itself reject unrecognized `rvfi.*` names "until [TASK-0008] lands," creating temporary validation logic whose reconciliation with TASK-0008 (issue #373, confirmed open) has no owner, no test, and no `WAIVED:`-style tracking beyond a Definition-of-Done bullet. This is lower severity than findings 1–3 because #390 does correctly flag the coupling and defers rather than ignores it, but the "adopt the validation when it arrives" plan has no acceptance criterion of its own — a second author landing TASK-0008 has no test forcing them to touch `jls.parity`.

**5. P2's "load-bearing" test can pass while the deeper hypothesis it stands in for (H1) is unverified.** The issue is honest about this in §11 ("The fixture is a synthetic circuit, not a CPU. It exercises the sampler, not the alphabet's adequacy; H1 is only genuinely tested when TASK-0070 and a real machine exist") — crediting the issue for stating its own gameable-criterion risk rather than hiding it. But the Definition of Done still lists P2 as a top-level completion bullet with no forward pointer requiring H1 to be re-verified once TASK-0070/a real CPU lands; nothing here blocks FEAT-034's close-out on that later verification actually happening. Recommendation: add a DoD item on #347 (not just #390) that ties H1's real verification to a specific downstream task.

**6. `blocks: []` in the Status block is inconsistent with #347's own graph.** #347's mermaid diagram draws `T0072 --> T0073` (i.e., TASK-0072 blocks TASK-0073/#423), and #347's roster explicitly states "TASK-0073's own blocked-by list names TASK-0072." Issue #390 declares `blocks: []`. This is a second, smaller instance of the same pattern as finding 1: the issue's own dependency bookkeeping does not match what its sibling issues assert about it.

## What holds up

- The cross-references to TASK-0070 (#477, confirmed open, confirmed mutual `related` entry) and #232 (confirmed open, confirmed genuinely orthogonal — `int`/`long` `ArchState` vs. `BitSet` signal churn, as both issues state) are accurate.
- `CliFlagTableTest`, `VcdExportGoldenTest`, and the `SocketConfinementRatchetTest` idiom cited for P6 all exist in `test/` with the described shape; this is not a fabricated test-infrastructure reference.
- The core design idea — a record type whose *shape* forbids a timing field, verified by reflection plus a name-regex, rather than relying on review discipline — is sound engineering and well-motivated by O2's demonstration that a naive per-callback sampler would leak combinational transients (P4 is a genuinely non-vacuous negative test as specified).
- The untimestamped-canonical-trace requirement (P8) correctly cites real precedent in `BatchSimulator.java:420-422`'s VCD header comment.

## Recommendation

Do not start implementation until: (a) #347's Open Question 1 is actually resolved or explicitly, visibly waived on *this* issue (not just acknowledged upstream); (b) `docs/parity-contract.md` is restored or its cited sections are pasted into this issue so the spec is self-contained and re-verifiable at pickup; (c) the two-pass batch execution model is designed and costed, with a prediction that exercises `-rvfi` alongside `-t`/`-vcd` in one invocation.
