# Issue #702: TASK-C535-1: dragging the cursor back to T shows the circuit at T — by deterministic re-simulation, with honest replay progress and no checkpoint code path
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

TASK-C535-1 is the rewind-half of FEAT-C23-6 (#535), split into its own task. It carries forward the parent feature's central technical mandate — pure O(T) replay, "never per-element checkpoint machinery" — almost verbatim, and inherits that mandate's unresolved problems along with it: a repo-internal design document that recommends the opposite approach with real numbers, and a determinism precondition that is a named, unresolved risk the task does not list as a blocker. Two issues are new at the task-split level: an unexplained ordering dependency, and an unstated numeric threshold in AC-3.

## Findings, most severe first

**1. (HIGH) The task's core mandate is contradicted by the repository's own engineering analysis of this exact problem, and #702 neither cites nor rebuts it.**
`docs/capability-roadmap/lf-03-causal-debug.md` §"(b) Time travel — checkpoint and replay" (lines 248–382) analyzes rewind for this same CAP-23 debug loop and concludes: "Format. Decision: a new `jls.sim.SimCheckpoint`..." (line 287), with a costed design — "≈9 KB raw / 2-3 KB deflated" per checkpoint on the 1,551-element RV32I flagship, 16 checkpoints for a full run — built specifically because pure replay is too slow: at the measured 318 ns/event (`keystone-c-performance.md:139`) and 2,331,793 events on the 6004-cycle flagship run, replaying from t=0 to an early T is seconds to minutes, not something a student rewinding a chronogram tolerates. The document states plainly: "the checkpoints are the index" (line 381). #702's Outcome paragraph asserts "Replay is O(T), which is honest at teaching scale" with no number bounding what "teaching scale" means, and treats the checkpoint ban as settled purely by citing #498 exclusion 2 — the same gap flagged against the parent issue #535 (finding 1 of that review) and not addressed in the split.
**Recommendation:** cite and rebut `lf-03-causal-debug.md`'s numbers explicitly, or state a numeric ceiling (element count / event count) beyond which pure replay is out of scope and rewind degrades to something else.

**2. (HIGH) AC #4's determinism kill-switch is reactive; the named, unresolved precondition it should gate on is not listed as a blocker.**
#504 (the parent capstone) §3 risk 4 says: "the replay claim extends [determinism] to 'truncate at T equals state at T', which must hold under the interactive engine, not just batch. Interactive-engine batching hygiene ... may be a prerequisite discovered during the demo slice." That hygiene gap is real and already named: `docs/capability-roadmap/README.md:710` — "`InteractiveSimulator.afterEvent:879-896` runs per-event with a `BitSet` clone per probe, violating `grand-architecture.md` §6's 'batched, rate-limited, never per-signal' rule." AC #4 ("If replay cannot reproduce state byte-identically at T under the interactive engine, the KC-23-3 determinism finding is filed and this task stops") only fires *after* implementation is attempted — it is a kill switch, not a preflight check against a risk the roadmap has already named and located by file/line.
**Recommendation:** add the batching-hygiene item (or a small determinism spike against `InteractiveSimulator.afterEvent`) as an explicit `ordering_after`/precondition, not something discovered mid-task after AC-1's test infrastructure is already built.

**3. (MED) `ordering_after: [TASK-C527-3]` is unexplained and plausibly the wrong predecessor.**
#702's Outcome is about dragging *the* chronogram cursor. TASK-C527-2 (#680) is the task that builds the docked chronogram panel and, by implication, its primary time cursor. TASK-C527-3 (#682) is a *different* feature: a second cursor for delta-time measurement between two points ("two cursors measure a time delta in ticks"), unrelated to rewind. #702 does not say why rewind depends on the two-cursor delta-measurement UI rather than on the panel/cursor task (#680) that logically produces the thing being dragged. If the intent is "ordering_after names the latest task in the prerequisite chain, which transitively covers #680," the issue should say so — as written, a reviewer cannot tell whether this is deliberate transitive sequencing or a copy-paste/off-by-one in the task graph, and it needlessly blocks rewind on unrelated delta-measurement work if it is the latter.
**Recommendation:** state explicitly whether the dependency on #682 is transitive-only or whether TASK-C535-1 actually consumes something #682 introduces (e.g., a shared cursor widget); if the latter, name it, if the former, consider ordering directly after #680 instead.

**4. (MED) AC #3's "stated threshold" is never stated, and the criterion is gameable as a result.**
"A rewind longer than a stated threshold displays replay progress and remains cancellable" — no number, no unit (wall-clock ms? event count?), and no fixture is named to exercise it. An implementer can satisfy the letter of AC-3 by picking a threshold so high (or a test fixture so small) that the progress-UI and cancel path are never actually exercised by anything resembling a real classroom rewind, while the literal test still passes. This is the same "unpinned tolerance" pattern flagged against sibling task #527 (AC-4's baseline fixture) and against #535 (AC-2's unscaled fixtures) elsewhere in this tracker.
**Recommendation:** name the threshold (e.g., in wall-clock ms or event count) and the fixture used to cross it, so `RewindEqualsReplayTest`/the progress-UI test has a falsifiable target instead of an implementer-chosen one.

**5. (MED-LOW) AC #1's "randomized fixture circuits and randomized times T" has no stated scale, so it can pass while never exercising the O(T) cost regime finding 1 raises.**
Nothing in #702 (or in #504's identically-worded AC-2, which this task's AC-1 restates) bounds element count or event count for the fixtures. A fixture set of small, fast circuits would pass `RewindEqualsReplayTest` trivially — correctness holds — while never stress-testing the "honest at teaching scale" claim about replay cost the Outcome paragraph makes.
**Recommendation:** name a size band for the fixtures (e.g., from trivial up to a mid-size multi-hundred-element circuit) so the correctness oracle and the performance claim are tested by the same criterion, not just the former.

**6. (LOW-MED) Exclusion 2's cost/benefit fit for this narrower, GUI-convenience case is asserted, not re-derived.**
#498 §8 exclusion 2 excludes "general simulation-state checkpoint/restore" with the stated rationale "a permanent per-element serialization tax across the whole element library in service of re-running a boot" (i.e., CPU-scale Linux-boot parity, CAP-02/#301 territory) — and its own text flags internal tension: "Note the tension: P15's floor is listed as required for parity-harness bisection. If bisection is wanted, this exclusion is already partly withdrawn — say which." #702 imports the exclusion for a much smaller problem (rewinding a classroom circuit in the GUI) via the phrase "#498 §8 exclusion 2 stays untouched," treating the transfer as self-evidently valid rather than re-deriving it against `lf-03-causal-debug.md`'s much smaller checkpoint estimate (≈2-3 KB deflated) for the same problem.
**Recommendation:** either explicitly widen exclusion 2's stated rationale to cover small in-memory rewind caches, or argue in this task why the Linux-boot cost calculus still applies to a feature two orders of magnitude smaller in scope.

**7. (LOW) AC #2's enforcement mechanism ("a test asserts the rewind path calls no state-serialization entry point") names no such entry point that exists today to assert against.**
This is more concrete than the parent #535's version of the same criterion (which proposed no enforcement mechanism at all), but the codebase has no established "state-serialization entry point" for `jls.sim` object graphs to scan for — the nearest analog, `CircuitSnapshot` (`src/jls/edit/CircuitSnapshot.java`), serializes *circuit structure* text, not simulator/element runtime state, so there is nothing yet to point the assertion at. A literal reading (does the rewind code path call an existing method) would pass by construction even if a new bespoke per-element save/restore mechanism is added under a name the test doesn't know to check.
**Recommendation:** define what the test scans for concretely — e.g., a bytecode/reflection check that no new `Serializable`/custom write-state method is introduced on `jls.sim`/`jls.elem` classes outside the existing `Attribute`/save-format registry — before this ships as the enforcement mechanism.

## What's solid (no rework needed)

- AC #1's oracle (byte-identical to a fresh truncated run) is a well-formed, non-vague comparison rather than a "looks right" criterion.
- Deliberately excluding FEAT-035 (#363, general checkpoint/resume) as a dependency is consistent with #504's own sufficiency argument ("PF-6 must not need it, or exclusion 2's boundary erodes") and avoids scope creep from a much larger, separately-tracked feature.
- AC #4's citation of KC-23-3 quotes the capstone's own kill criterion verbatim and correctly frames a determinism failure as a stop-and-report event rather than a trigger to quietly add checkpoints — the right instinct, even though finding 2 above shows the precondition it should gate on is not yet wired in as a blocker.
- The task is honestly scoped to just the rewind mechanic (viewer-sync is correctly split out to TASK-C535-2, #704), avoiding the bundling problem the parent #535 review flagged.
