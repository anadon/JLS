# Issue #383: TASK-0036: a second view's geometry lives in its own preserved section, and a drag in one view is not a drag in the other
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

The issue is unusually rigorous by GitHub standards — falsifiable hypotheses, a
failure-mode table, a checklist DoD — and most of its file/line citations check
out against HEAD (`53116252`). But it has a genuine internal contradiction
about the #170 dependency, ships in a state where it cannot be started
(two hard prerequisites don't exist in the repo or the tracker), and leaves
the one component whose format actually changed shape (`AddElements`) with
its wire grammar unspecified. These are not nitpicks about an otherwise-solid
plan; they are reasons work on this exact filing would stall or diverge.

## Findings, most severe first

**1. Contradiction: #170 is called a blocking dependency in prose but is only `related` (non-blocking) in the machine block.**
§1/§12 state plainly: "#170 (open, collaboration security hardening) — **depends on**. A new optional field widens the network-facing grammar and must land **inside** #170's strictness discipline, not beside it" and repeats in §8: "Coordinate the grammar widening with #170." That is dependency language. Yet the YAML machine block's `blocked_by` is `[319, 337]` only — #170 appears solely in `related: [163, 167, 170, 171, 165, 166, 183, 279, 280, 357, 333]`, and the sibling issue #319 explicitly defines that field's semantics: "`related` is never blocking" (repeated verbatim in #318's mermaid comment: "`related` is reference-only and never blocking"). By the corpus's own convention, #170 is declared simultaneously blocking (prose) and non-blocking (machine block). If #170 lands after this task and its strictness discipline requires a different shape for the optional `view` field, this task's grammar change ships outside the discipline it was supposed to land inside. **Recommendation:** either add `170` to `blocked_by` (and its mirror to #170's `blocks`) or strike the "depends on"/"must land inside" language and replace it with an explicit coordination note that does not read as a hard gate.

**2. Not actually startable: two of three hard prerequisites don't exist anywhere.**
The task is `blocked_by: [319, 337]` (verified open, consistent — good) but also states two more prerequisites as "hard dependency, not a convention": TASK-0033 (section frame) and TASK-0035 (`ItemKey` type). I confirmed neither exists in the tracker (no issue numbers assigned — "their numbers do not exist yet") nor in the repository: `git grep -l ItemKey -- src/ test/ docs/` returns nothing, and `docs/file-format.md` has no must-understand/skip-and-preserve section-frame vocabulary at all. This task's own §8 first checklist item is "Confirm TASK-0033's section frame and TASK-0035's `ItemKey` have landed" — i.e., step one of the method is itself blocked on filing and landing two other tasks that don't yet have issue numbers. Filing #383 now, fully speced to 14 sections and a DoD with 20+ checkboxes, before its two hardest prerequisites are even filed, invites the spec to go stale (see finding 3) long before anyone can pick it up. **Recommendation:** hold this issue in draft/blocked state explicitly (it already carries no "ready" label signal) or fold it as a sub-task under #318 until TASK-0033/0035 are filed, so the standalone issue doesn't accumulate its own independent drift.

**3. The evidence-commit "byte-identical" claim is already false against current HEAD.**
§2 asserts: "`src/` is byte-identical between that commit and the tree the probe below ran against (`git diff --stat 2d0ca9d..HEAD -- src/ test/ pom.xml config/` produces no output)." I ran exactly that command against the actual repository HEAD (`5311625`, 14 commits ahead of `2d0ca9d`) and it produces substantial output: `pom.xml` (dependency version bumps), `src/jls/elem/ElementId.java` (a 15-line block removing counter-advance-on-parse logic), `src/jls/hdl/HdlExporter.java` (60 lines, several element-type imports removed), `src/jls/elem/SaveTags.java`, and four test files. None of these touch the files this task actually cites (`Element.java`, `MoveElements.java`, `RotateElement.java`, `CircuitOp.java`, `CircuitOpReader.java`, `FlipElement.java`, `AddElements.java` — I re-verified all cited line numbers there and they still match, e.g. `MoveElements.java:27` record header, `:72` `invert`, `CircuitOp.java:34` sealed permits, `:51` `apply` signature, `CircuitOpReader.java:119-178` switch). So the *specific* citations are still accurate, but the issue's own blanket claim of byte-identity between evidence commit and "the tree the probe ran against" is demonstrably false the moment HEAD moves at all — which it already has. §11 anticipates line-number drift ("re-derive at pickup") but the issue asserts a much stronger, already-broken invariant (whole-tree identity) as if it were durable evidence. **Recommendation:** rephrase the O-section claim to name the exact paths verified identical (the seven files actually cited) rather than claiming `src/` as a whole, so a future drift in unrelated files doesn't read as invalidating the observations.

**4. `AddElements`'s new grammar is asserted but not specified.**
§7.12 states plainly that a view alone is insufficient for `AddElements` because "a block is the element's exact save bytes ... and its base attributes include x/y, so an add into a non-default view must carry the view **and** the side-table row." Open Question 4 confirms this ("the op carries the view and the side-table row explicitly... Blocks execution") but never says what that row looks like on the wire — is it a second line type inside the `AddElements` block, one row per added element, keyed how before `ItemKey` exists for the added elements' not-yet-assigned ids? This is a materially different, currently-undefined addition to `AddElements`'s serialized form, and unlike the other three ops (a single optional `view` line) it cannot be filled in mechanically from this issue's own §5/§7 text. Left as an open question flagged "blocks execution," it means whoever picks this up designs a piece of wire grammar without a resolved contract, then must retrofit it into `CircuitOpTest`. **Recommendation:** resolve Open Question 4 in this issue (or split `AddElements`'s handling into its own task) before this is picked up; don't let a load-bearing grammar decision live only as an "open question."

**5. H3 ("no render/hit-test path needs a second `(x,y)`") is unfalsifiable within this task's own scope.**
H3's falsification condition is "a rendering or hit-testing path cannot be served from the side table." But the only consumer of a second view — the breadboard canvas — is #329, explicitly out of scope here (§13: "the second canvas itself is #329"). `SpatialIndex` (`ARCHITECTURE.md`, editor hit testing) has no non-default-view caller in this repo yet. So this task's own tests (`ViewGeometrySectionTest`, `ViewDiscriminatorTest`) can only exercise `ViewGeometry.get/put/rows()` synthetically; they cannot exercise a real render or hit-test path against a second view, because none exists. H3 will read "not refuted" at close purely because nothing capable of refuting it was ever built — a pass that means less than it appears to. **Recommendation:** state explicitly in §9/§10 that H3 is checked only up to the synthetic-service level here and is genuinely tested only when #329 lands; don't let the DoD checkbox read as if H3 were fully exercised.

**6. Unbounded preserve-on-write for dangling `VIEW` rows is a mild DoS/bloat vector, unaddressed.**
§7.11's table: a `VIEW` row keyed to a nonexistent id gets "diagnostic... dropped from the live model but **preserved on write**." That's a defensible anti-data-loss choice, but nothing bounds how many such orphaned rows can accumulate under repeated hostile or careless merges — no analogue of #319's 64 MiB decompressed-text cap is restated for this section, and the row-count isn't otherwise capped. A hostile collaborator (§7.3 explicitly treats the `VIEW` section as "hostile — a user-supplied `.jls` file") could pad a shared file with orphaned rows across successive saves and no read/save path in this task's spec ever prunes them. Likely subsumed by the overall file-size cap #319 already enforces, but this issue never says so. **Recommendation:** state explicitly that the existing whole-file cap covers this, or add a bound.

## What's solid (brief)

- The H1 pin — `schematic` keeps writing exactly where it does today and gets no `VIEW` section — is a clean, well-justified invariant and the right one to protect byte-identical goldens.
- P1-P9/§10 falsification criteria are genuinely falsifiable and each names its own remedy, which is rare and good.
- The "must-be-absent on the other seven kinds" strictness requirement (O3/P3) correctly identifies the one place the compiler won't help, and pairs it with one test per rejected kind.
- Cross-checked against #318, #319, #337 (all fetched): the `blocked_by`/`blocks` edges for those three are mutually consistent — #319 and #337 are open and each records the mirrored edge back to #318/this line of work, so at least that part of the dependency graph is not just prose.

## Verdict

**needs-rework.** The technical design (H1-H4, the strictness discipline, the reader-switch table) is sound, but the issue should not be picked up as filed: resolve the #170 blocking-vs-related contradiction, specify `AddElements`'s wire format instead of leaving it an open question that "blocks execution," and either file TASK-0033/TASK-0035 first or explicitly mark this issue as not-ready until they exist.
