## Findings

**1. (Medium-High) The "six golden suites" in §5 P1 / §14 DoD conflict with the actual discoverable corpus and with the blocking issue this task must extend — a gameable acceptance criterion.**
§5 P1 and the DoD's first checkbox both hard-code: *"the whole committed corpus (`BatchSimulationGoldenTest`, `SequentialGoldenTest`, `ElementSimulationGoldenTest`, `VcdExportGoldenTest`, `RiscvCpuGoldenTest`, `ShiftRegisterTest`)"*. I verified against the tree:
- `ShiftRegisterTest.java` exists (`test/jls/ShiftRegisterTest.java`) but does **not** match the `*GoldenTest` naming pattern.
- The actual discoverable `*GoldenTest` set is **eight** classes, not five-plus-one: the five named above, plus `test/jls/hdl/VerilogExportGoldenTest.java`, `test/jls/hdl/VhdlExportGoldenTest.java`, `test/jls/hdl/board/PcfGoldenTest.java` — none of which #393 mentions anywhere.
- `SimulationSemanticsRegressionTest.java` (which #393's own P5 requires to stay green) is *also* not `*GoldenTest`-shaped, and its own blocking task #442 (TASK-0026) records this exact discrepancy as its **O3 "observed failure"** and leaves *how to enroll it* as an **unresolved, blocking Open Question** on #442 itself.
Since #393's completion criteria literally require *"Extend the byte-identity gate with `everyGoldenIsByteIdenticalAcrossTheZeroDelayClosure()`"* — extending #442's gate, whose membership is not yet decided — #393's own "six suites" DoD item is already wrong relative to the mechanism it depends on, and will diverge from whatever #442 lands. An implementer could satisfy the letter of #393's checklist (five/six named suites pass byte-identical) while three real golden suites and one required regression suite are silently outside the asserted set. Recommend #393 stop enumerating a suite list at all and instead say "whatever #442's gate enrolls," or explicitly resolve #442's Open Question 1 as a prerequisite before #393's DoD can be considered well-defined.

**2. (Medium) Feasibility: a ~2-week estimate carries a formal-proof-grade specification and a ~6.5-week serialized prerequisite chain, inside a project that has already flagged its own scheduling variance as high.**
#362 (FEAT-030, the parent) prices TASK-0064 at 2 wk in its cost table, but the issue itself demands: a cone levelizer with cycle detection, a written seq-conservation proof discharged by a differential test against the pre-closure loop, derivation (not enumeration) of the zero-delay set from declared delay, a named per-element cycle diagnostic specified in the normative doc in the same commit, a stale-doc-paragraph fix, and ~30 DoD checkboxes. It is also `blocked_by` #476 (TASK-0063, priced 2 wk) and #442 (TASK-0026, priced 1 wk), which is itself `blocked_by` three more tasks (#377/#379/#413) ahead of it — a critical path of roughly 6.5 weeks of comparably dense, formally-specified work before #393 can even legally start under its own stated `blocked_by`. #362 already records (Open Question 1) that its five named tasks sum to 8.5 wk against a 12-20 wk band — a 2.35x unexplained gap — and separately calls this program "the highest-variance item in the core column" at "bus factor 1." Nothing in #393 revises the 2-week estimate in light of its own scope; the estimate looks imported from the parent's table rather than derived from this issue's actual content.

The comment calls the keystone-c-performance.md dependency "preference-shaped" ("wants", not "requires") and declines to promote it to a `blocked_by` edge. But that same doc's own staged rollout table (`docs/capability-roadmap/keystone-c-performance.md:687-691`) puts "cache `WireNet` driver/sink arrays" at stage **0.5** and "levelized zero-delay closure" at stage **1**, i.e. the project's own performance roadmap treats the caching as a preceding stage, not an optional nicety. **5. (Low) P2's "unmodified loop" baseline is not pinned to a commit, and this task's own dependency graph makes "unmodified" ambiguous.** §5 P2 and H1 compare the closure's fired-event sequence against "the unmodified loop." Read as "closure-enabled vs. closure-disabled at the same commit" this is fine and is almost certainly the intended meaning, but the issue never says so explicitly, and because TASK-0063 (a hard prerequisite, per the corrective comment) rewrites the same `post`/`runEventLoop` machinery this task's differential test targets, "unmodified" could be misread as "the original `PriorityQueue`/`HashSet` implementation," which will no longer exist in the tree by the time #393 is implemented. A one-line clarification ("unmodified" = same commit, closure feature-flagged off) would remove the ambiguity cheaply.

**6. (Low) P3's pre-fix red state cannot be a normal JUnit assertion, and the issue underspecifies how.** The comment already flags this (a genuine non-terminating storm can't be asserted, only bounded-and-killed), but doesn't specify a mechanism. The repo does have `@Timeout`/`assertTimeoutPreemptively` precedent in 21 test files, so the tooling isn't a green-field problem — worth noting as a mitigant — but none of those existing uses interrupt a live `Simulator` event loop mid-`react()`, and #393 doesn't note that JUnit's preemptive-timeout mechanism interrupts via a separate thread, which the single-simulation-thread contract in §7.9 says nothing else is ever allowed to touch. The fixture author will need to design around that, and the issue's Method checklist doesn't call it out as a hazard even though its own §7.9 states the exact invariant that makes it delicate.
