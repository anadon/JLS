# Issue #593: FEAT-C37-2: a switcher selects, drags, aligns and duplicates a group of elements the way every other editor taught them to — compound selection stops being the first thing that bounces them
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what's being proposed

Compound multi-element selection (additive/subtractive, rubber-band, group drag, align, distribute, duplicate) plus Digital-#882-class wire-segment selection, gated hard on landing only in the decomposed collaborators #316/#84 produce (never in `SimpleEditor`), and scored against a not-yet-published parity catalog (#592).

## Findings, most severe first

**1. Every named technical prerequisite is unbuilt at the repo HEAD this issue is filed against — the feature is currently unstartable, not just "ordered after."**
Verified directly against the checkout (`53116252`): `src/jls/edit/SimpleEditor.java` is still 5,852 lines with no `MouseMachine`/`InteractionState` extraction (`find src/jls/edit -iname "*Mouse*" -o -iname "*Interaction*"` returns nothing); `pom.xml:408` still reads "`jls.edit is deliberately unfloored until the #91/#84 work makes editor code testable`"; #440 (TASK-0019, the floor+plan) is open with zero completed checklist items; #84 and #316 (the extraction itself) are open; #592 (the parity catalog this issue's AC-1 requires a scored row in) has no file under `docs/` (`ls docs/` shows no catalog doc). AC-2 additionally requires "a #91-harness or headless-interaction-machine test" — the headless interaction machine is exactly the thing #84/#316 have not yet produced. So all five of #593's acceptance criteria currently reference infrastructure or documents that do not exist. This is disclosed via `ordering_after`, so it isn't a hidden contradiction, but it means the issue as filed cannot be worked in any form today, and its `band_mw: "3-4"` estimate is for the visible feature slice only — it silently assumes the (much larger, per #316's own 10.5–20mw accounting) prerequisite chain is a sunk cost paid by other issues. Recommendation: either mark this issue explicitly blocked/on-hold in its own metadata (it currently reads as an actionable, scoped feature) or fold a "readiness check" step into its own Method that fails loudly if #440/#84/#592 haven't landed, mirroring the rule-6 supersession checks used elsewhere in this same issue family.

**2. AC-5's "not slower than #592's baseline" has no defined tolerance, trial count, or environment-normalization protocol, and is a manual/human-timed measure — in direct tension with AC-2's evidentiary standard.**
AC-2 states plainly: "no behaviour is asserted only by a screenshot or a manual pass." AC-5 requires re-measuring a human building a 4-bit counter from scratch and comparing it against a baseline that (per #592 AC-5) is itself a single recorded timed run. Nothing in #593 or #592 specifies: how many trials constitute "the" time, who performs the task (same person for both measurements? different skill levels?), what counts as a real regression versus timing noise, or what happens if the *editor* got objectively better but the *person* timing it was having a slow day. As written, "the after is not slower" is gameable in both directions — a single fast run trivially satisfies it, and a single slow run (unrelated to this feature) could block an otherwise-complete implementation. Recommendation: specify N≥3 trials, a stated tolerance band (e.g., median within 10%), and either the same operator or an operator-blind protocol.

**3. AC-3's "preserve connectivity or refuse with a named reason" is underspecified for the operation that most needs it: duplicate of a selection with wires crossing the selection boundary.**
Group drag/align/distribute all move elements that keep their existing `Wire`/`WireEnd` bindings, so "preserve connectivity" is reasonably well-defined for them (the wire graph doesn't change). Duplicate is different: if the source selection has a wire to an element *outside* the selection, the duplicate has to make a decision — wire the copy back to the original external element (surprising, probably wrong), drop the connection silently (data loss dressed as success), or refuse the whole duplicate (frustrating for a common case: duplicating one gate in a chain). The issue never states which, and "preserve connectivity or refuse with a named reason" can be satisfied by any of the three readings, including the silent-drop one, since dropping a boundary-crossing wire arguably "preserves" the internal connectivity of the copy while still being the worst possible outcome for the user. This is exactly the kind of acceptance criterion that could pass while the real goal (a duplicate that behaves the way Logisim-Evolution/Digital users expect) fails. Recommendation: give duplicate its own row specifying boundary-wire behavior explicitly, not a shared clause with drag/align/distribute.

**4. The issue already required a correction four days after filing, and the correction itself is evidence the dependency graph is fragile.**
The second comment (2026-08-08) is titled "STALE REFERENCE — CORRECTION" and fixes two of the three `ordering_after` entries because #441 (originally cited as the source of `MouseMachine`/`InteractionState`) was closed as a duplicate into #84 on the same day. Given `SimpleEditor.java`'s own recorded history — five re-baselines and 4,119→5,852 growth *while under active decomposition* (cited in #84, #316, #440) — the `ordering_after`/boundary-note prose in #593 is likely to go stale again before any of its prerequisites land, and nothing in #593 commits to re-verifying those references at pickup the way #84/#316/#440 explicitly do (their "rule 6" supersession checks). Recommendation: add the same re-verify-at-pickup obligation used elsewhere in this issue family.

**5. The Outcome section promises more than the AC's test.**
"Compound multi-element selection behaves the way a Logisim-Evolution, Digital or CircuitVerse user expects on their first attempt" is a three-way subjective comparison with no user study, no defined task set, and no operational pass/fail. AC-1 through AC-5 are the only things actually graded (per the issue-family convention that ACs are binding and Outcome is aspirational), but a reader — or a future closer of this issue — could reasonably claim the Outcome is met once the five narrower ACs pass, when in fact "first attempt" usability was never tested. Recommendation: either drop the three-incumbent claim from Outcome or tie it to a concrete usability-pass criterion (e.g., a specific gesture checklist run by someone unfamiliar with JLS).

**6. bsiever-fork #18 is an external-repo citation this reviewer cannot verify from this environment.** The GitHub tool available is scoped to `anadon/jls`; bsiever-fork is a different repository entirely. AC-5 makes closing/refusing this issue "by name" a hard precondition for CAP-37 AC-3. Low risk (the broader issue family has evidently done this legwork upstream in #592/#521), but it's worth the implementer independently re-confirming bsiever-fork #18's actual content before citing it as "closed by name," since a citation nobody in this repo can check is an easy place for scope to drift silently.

## What's solid

- The hard gate (KC-37-1, "nothing lands inside `SimpleEditor`") is unambiguous, testable via `grep -c "switch (currentState)"`-style checks already used by sibling issues, and correctly treats a stalled #316 as a blocking condition rather than something to route around.
- AC-1's framing ("nothing lands that the catalog did not score") is a genuinely effective scope-creep guard for a UX-polish feature that could otherwise expand indefinitely.
- The #593/#594/#595/#596 boundary-declaration comment is a well-reasoned, mutually-consistent partition of adjacent ergonomics work, including an honest treatment of the one place #593 and #595 touch (refusal *behavior* vs. refusal *message quality*) with an explicit two-way reconciliation plan for whichever lands first.
- AC-4 correctly refuses to let wire-segment-under-cursor resolution ship as merely "observed behaviour" — requiring it stated as a rule is the right instinct, even though (per Finding 1) the rule's actual home (#592's catalog) doesn't exist yet.
