# Issue #530: FEAT-C21-5: an nbgrader unit's hidden test cells grade from recorded batch artifacts alone — subprocess invocation, and no adapter ever drives a live session
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: sound-with-concerns

## Summary of the issue

FEAT-C21-5 (PF-5 of capstone CAP-21, #502) asks for an in-tree nbgrader example unit whose hidden cells grade a JLS lab by shelling out to the pinned JLS build in batch mode, parse xUnit verdicts, and assign points — proving the still-unfrozen CLI contract is usable from a notebook course with no live JLS session. It is scoped at `band_mw: 1-2` and ordered after `FEAT-C21-1` (#524).

## Findings

**1. (High) The dependency chain it declares is not close to landed, and the 1-2 mw estimate does not disclose that.** `ordering_after: ["FEAT-C21-1"]` names #524, but #524 is itself `ordering_after: [369, 466]`. #369 (FEAT-053) is an open, multi-task feature whose own cost reconciliation states "the feature's own task rows sum to 8 wk" against a "9-15 mw" band, with two of its four sub-tasks (TASK-0021, TASK-0112) not yet filed. #466 (TASK-0111) — the task that would actually build `Expectations`, `TestVectorRunner`, `GradeReport`, the `-check`/`-report` flags and exit status 3 — is also open and itself blocked on an unfiled TASK-0021. I verified against the tree: `grep -rn "GradeReport\|TestVectorRunner\|Expectations.java\|\-check" src/` returns nothing, and `docs/batch-interface.md:36-40` still documents exactly three exit statuses (0/1/2), matching #466's own O1/O2 observations. So #530's real prerequisite chain is: TASK-0021 (unfiled) → #466 → #369 → #524 → #530, i.e. several maintainer-months of unstarted, only-partially-scoped work, none of which is mentioned in #530's own band estimate. `band_mw: 1-2` reads as the *marginal* cost of the nbgrader wrapper alone, which is plausible in isolation, but a reader skimming #530 without walking the graph could easily believe the whole feature is 1-2 weeks away. Recommend the issue body state explicitly (as #466 and #369 do for themselves) that the estimate excludes the unlanded transitive dependency and point at #524/#466/#369 for the real critical path.

**2. (Medium) "An instrumented build asserts no interactive session is ever opened" is unspecified for a Python/notebook consumer.** AC-1 borrows the phrasing from CAP-21 AC-4, which for the Java-native adapters plausibly means something like the existing `HeadlessCoreRatchetTest` pattern (`ARCHITECTURE.md`: "`Simulator` and `BatchSimulator` import no AWT, Swing, or `jls.edit`") or a bytecode/classpath scan. But the nbgrader unit's hidden cells are Python invoking a JLS subprocess; "the build" that gets instrumented is never named — is it the pinned JLS jar (verify no `jls.edit`/Swing classes ever load during the subprocess call, e.g. via a headless-mode assertion or process-monitor check), or the notebook kernel (verify no long-lived JLS process handle is retained across cells)? As written, an implementer could satisfy the letter of AC-1 by asserting something trivial (e.g. "the Python code never imports a JLS Java API") while never actually testing that the invoked JVM stays headless. Recommend the AC name the concrete mechanism, ideally reusing `HeadlessCoreRatchetTest`'s classpath-scan idiom against the JVM the subprocess launches, the way M3 in #498 proposes "a bytecode scan proves no binding touches the event queue" for an analogous claim.

**3. (Medium) The "byte-identical gradebook export" claim doesn't state what nbgrader artifact is being compared, and nbgrader's own gradebook is not that artifact.** AC-2 says "The nbgrader gradebook export for the fixture class is byte-identical to the other adapters' score vectors from the same xUnit input (feeds CAP-21 AC-1)." nbgrader's native gradebook is a SQLite database (`gradebook.db`) with student/assignment/timestamp columns that have no analogue in Gradescope's `results.json` or a GitHub Classroom Action summary — it cannot be byte-identical to those by construction. The AC is presumably about some *derived* export (a CSV of student→score pairs), but that derivation, its schema, and its ordering/determinism rules are left entirely to #531 (`CrossPlatformScoreParityTest`), which this issue's own text acknowledges only supplies "an input" rather than performing the comparison. That's a legitimate division of labor, but as written AC-2 is unfalsifiable on its own terms — there's no artifact named in #530 whose bytes anyone could check before #531 exists. Recommend AC-2 either point to a to-be-defined derived export format owned by #531, or be dropped from #530's own acceptance criteria (since #530's comment thread already says AC-2 here is "an input", not the comparison).

**4. (Medium) Missing "dedicated CI lane" boundary note that its sibling adapter issues carry.** CAP-21 (#502) §3 risk 1 states "The adapters must live in dedicated CI lanes, not the core matrix." Sibling issue #525 (Gradescope) restates this explicitly: "The adapter lives in a dedicated CI lane, not the core matrix (CAP-21 risk 1)." Sibling #528 (PrairieLearn) restates it too: "externalGrader contract drift surfaces as a red lane in the adapter's dedicated CI lane." #530's body never mentions a dedicated lane at all — AC-4 just says the README "executes end-to-end as scripted doc-test steps in CI," with no statement of which lane. Since satisfying AC-4 requires a Python/Jupyter/nbgrader toolchain that nothing else in the tree currently pulls in (`grep -rli nbgrader .` finds only issue-review files, none in `docs/` or `.github/`), an implementer following #530 literally could add nbgrader to the core matrix and violate CAP-21's own no-toolchain-matrix constraint without #530 ever having told them not to. Recommend copying the boundary note the other three PF issues already carry.

**5. (Low) KC-21-2's "no live protocol" framing glosses over nbgrader's own execution model.** nbgrader grades by executing the notebook (hidden cells included) inside a live Jupyter kernel via `nbconvert`/`ExecutePreprocessor` — that is a "live session" in the ordinary sense of the word, just not a live session *of JLS*. The issue's boundary note ("if this adapter turns out to need a live protocol to grade, it stops") is really about JLS not being driven interactively, per #498 §7.2, and the outcome text does say "subprocess invocation... no adapter ever drives a live session" which is the correct target. But the AC wording ("no interactive session is ever opened") doesn't disambiguate "interactive JLS session" from "the Jupyter kernel nbgrader itself runs in," which is exactly the kind of terms-of-art ambiguity #498 §7.2 spent four numbered corrections resolving for the analogous #63/`vcd-interop.md` case. A future implementer or reviewer could get confused about which "session" the kill criterion is about. Recommend one clause making the JLS-only scope explicit, the way #498 §7.2 point 4 did ("the sentence means graders must not build on interaction, not that the simulator must not be interactive").

**6. (Low) "no scraping of incidental output" (AC-3) has no stated verification mechanism.** Unlike AC-1/AC-2/AC-4, which each name a concrete test (`RecordedArtifactOnlyTest`-style instrumentation, byte comparison, doc-test CI run), AC-3 ("no scraping of incidental output") is a code-review-only constraint with no test named. It is easy to satisfy on paper and easy to violate quietly later (e.g. a maintainer adds a convenience regex over `stdout` that happens to work today but isn't part of the frozen xUnit schema). Given the emphasis the rest of CAP-21's family places on machine-checked claims (e.g. #524's "seeded contract violation... fails CI"), a `CliContractConformanceTest`-style check that the nbgrader adapter only touches the documented artifact paths/xUnit schema (not raw stdout) would close this gap; the issue doesn't ask for one.

## What's solid

- The core outcome — an nbgrader example unit driving JLS purely via subprocess/batch artifacts — is coherent with #498 §7.2's recording-not-session discipline and with the existing headless architecture (`Simulator`/`BatchSimulator` already import no AWT/Swing per `ARCHITECTURE.md`).
- The pass-1/pass-2 adjudication already recorded in the issue's own comment (pointing to #525, verdict "no merge," reconciled against #531) shows real cross-issue scrutiny already happened at the fleet level; #530 is correctly the sole owner of the "instrumented build" and notebook-witness distinctives, and that division is well-argued.
- `ordering_after` correctly identifies #524 as the direct blocker and #369/#466 as the transitive ones — the graph is accurate even though (per finding 1) its cost implications aren't spelled out.
- The "files-only kit" / no-service boundary note is consistent with #498 §8 exclusion 7 and with how the sibling PF issues (#525/#528) frame the same constraint.

## Note

If FEAT-C21-1/#369/#466 land with materially different exit-status semantics or report schema than currently drafted (open questions in #466 are still unresolved, e.g. Q1/Q3), #530's acceptance criteria — all of which are phrased in terms of "the frozen CLI contract" and "the xUnit schema" — will need re-verification against whatever those issues actually ship, not just against #524's aspirational description.
