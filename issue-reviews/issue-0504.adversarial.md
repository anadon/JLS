# Issue #504: CAP-23: a student diagnoses a race condition without leaving JLS — from a glitch caught by a triggering logic analyzer to the two unequal-delay paths that caused it, in three clicks
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

The diagnostic-loop vision is coherent, well-motivated, and its evidence checks out where I could verify it (`Trace.java` is exactly 626 lines; `Traces` is exactly at `InteractiveSimulator.java:1102`; `SimEvent` genuinely carries no producer→consumer link, confirming the issue's own claim that causal data is discarded). That accuracy is a real strength. But the issue commits to a scope its own governing documents do not fund, tests a cost ratchet narrower than the feature it gates, and leans on GUI-automation and determinism guarantees that are unverified prerequisites rather than settled facts. None of this is fatal to the idea; it is fatal to filing this as ready-to-execute in its current form.

## Findings, most severe first

**1. Mandatory scope (§2's "required, or the outcome breaks") is not what the maintainer's own #508 funds — and the issue never reconciles the gap.**
§2's sufficiency table marks all six PFs as load-bearing: "Sufficiency. §1 is six observations… Each row names what breaks on removal." Yet #508 (the maintainer's own August 2026 product-direction review, same author, one day earlier) funds only "**Debug-loop parity (≈3–4 mw): CAP-23 chronogram slice; cause-chain inspector after #476's seam**" — nothing about PF-4 (wavefront stepping) or PF-5 (instruments) is funded at all, and #535 (the PF-6 filing) says outright: "the review's funded CAP-23 wedge covers only the chronogram slice and the cause-chain inspector — it recommends cutting the PF-6 viewer-sync scope." By the capstone's own §2 logic, cutting PF-4/PF-5/PF-6 makes steps 3–6 of §1 impossible and the outcome statement false — but the issue's Definition of Done still requires all of §1 and all of §4's AC-1…AC-6 before close. As filed, CAP-23 cannot close on the funding its own author has approved. Recommendation: either descope §1/§4 to what #508 actually funds (chronogram + cause-chain only) via the REPLAN the issue's own §5 calls for, or explicitly flag CAP-23 as unfunded-as-scoped and not ready to start.

**2. The K9/AC-5 zero-cost ratchet is scoped narrower than the cost it needs to bound.**
AC-5 (`ChronogramClosedCostTest`) tests "with the chronogram closed (the default)." But PF-5's triggering analyzer must retain candidate events *before* a trigger fires (§1 step 1: "arm an edge-plus-duration trigger… observe the capture fire on the runt pulse… with pre-trigger history"), and PF-3's cause-chain inspector needs the producer→consumer link retained at the moment of capture — neither requires the chronogram panel to be *open*, only an analyzer element to be *placed and armed*. KC-23-2 half-acknowledges the retention-cost risk ("If cause-chain retention cannot be bounded… without unbounded memory or losing the chain… stop PF-3") but AC-5 as written never measures the "analyzer armed, chronogram closed" case, which is the actual hot path the walkthrough exercises. A student with an analyzer on canvas but the chronogram panel collapsed pays a tap cost with no test protecting them. Recommendation: add an AC (or fold into AC-5) that measures throughput with an armed-but-untriggered analyzer element and the panel closed — the panel-visibility toggle is the wrong proxy for "is the tap live."

**3. AC-2's determinism guarantee is asserted over ground the issue admits is unverified.**
§3 risk 4: "Determinism is load-bearing for PF-6 and step 4… which must hold under the interactive engine, not just batch… Interactive-engine batching hygiene (roadmap standalone item) **may be a prerequisite discovered during the demo slice**." This is an honest admission that AC-2 ("displayed state after cursor rewind is byte-identical to a fresh run truncated at T") depends on a property nobody has yet shown holds for `InteractiveSimulator` — only for `BatchSimulator` goldens. KC-23-3 treats a failure here as a stop condition, which is the right response *if* discovered, but the cost bands (PF-6: 3–4 mw) do not reserve room for "file and fix an interactive-engine batching-hygiene bug" as a probable prerequisite. Recommendation: spike the determinism check first (cheap: run the same fixture twice interactively, diff), before costing or scheduling PF-6.

**4. AC-1 and AC-4 assume GUI test-automation maturity for interactions with no existing precedent.**
`test/jls/ui/package-info.java` documents Layer 2 ("Swing-harness assertions… synthesized mouse/keyboard interaction") as "present, growing" and Layer 3 (render assertions) as "starter present" — real infrastructure exists, contradicting my first read of `ARCHITECTURE.md`'s more conservative "layers 2 and 3 are reserved" (that document is stale on this point). But every existing Layer-2 test (`DialogConstructionSmokeTest`, `MenuBarSpecTest`, `KeyPadDismissalTest`, `InteractiveSimulatorSmokeTest`) automates menus, dialogs, keyboard focus, and the Runner-thread/EDT handshake — nothing that clicks a waveform edge, watches a canvas element flash, or asserts on a docked panel's cause-chain rendering. AC-1's `HazardDiagnosisWalkthroughTest` ("trigger, capture, edge click, cause chain naming both unequal-delay paths… as a scripted GUI test") and AC-4's `ViewerSyncTest` (scripted against a pinned external Surfer version) are a materially new class of UI assertion, and none of PF-1/PF-2/PF-3's cost bands (4–6 / 2–3 / 4–6 mw) mention harness-extension cost separately from feature cost. Recommendation: cost the Layer-2/3 extension needed for waveform-click and canvas-flash assertions as its own line, not folded silently into feature bands.

**5. The REPLAN comment doesn't update the machine block it was supposed to resolve, so the issue is currently self-contradictory.**
§5 states plainly: "A planned feature is filed → REPLAN resolving the PF entry." The one comment on this issue does report all six PFs filed (#527/#529/#532/#533/#534/#535), but the issue **body's** machine block still reads `requires_features: []`, `blocked_by: []`, and `planned_features` still lists all six PF-1..PF-6 as unresolved plain strings — none converted to a `requires_features` entry pointing at the new issue numbers. The Definition of Done's own bullet ("Machine block, roster table, and mermaid graph agree with reality at close") only binds "at close," so this isn't yet a violated checkbox, but it means a reader of the issue body today sees a document inconsistent with its own comment thread. Recommendation: edit the machine block now (cheap) rather than deferring reconciliation to close, since six live dependent issues already exist and current readers (including reviewers) are working from stale state.

**6. Cost-band arithmetic between #504 and #508 doesn't parse the same way twice.**
§Cost fixes: "Demo slice, 3–4 mw: PF-1 minimal chronogram + PF-2 one-way probing… **proves the tap can be free before anything else is funded**" — explicitly excluding PF-3 (cause-chain inspector, priced separately at 4–6 mw). #508's wedge #6 reads "Debug-loop parity (≈3–4 mw): CAP-23 chronogram slice; **cause-chain inspector** after #476's seam" in the same 3–4 mw parenthetical. Read literally, #508 promises the cause-chain inspector inside the same 3–4 mw envelope that #504 itself says buys only PF-1+PF-2. Either #508 is using "3–4 mw" loosely to cover two sequential slices whose costs aren't both in that number, or one of the two documents underprices PF-3 by roughly its own stated band (4–6 mw). #508 §Process findings even flags this exact failure mode elsewhere in the corpus ("3 of 4 sampled capstones had bands below their own row sums") without catching it here. Recommendation: state explicitly, in a REPLAN comment, whether the funded wedge is 3–4 mw or 7–10 mw (3–4 chronogram + 4–6 cause-chain).

**7. External-dependency risk on PF-6's viewer-sync is understated relative to its own kill criterion.**
Open Question 2 picks "Surfer via its remote-control protocol, pinned by version" as the recommended default, but no code in this repository references any Surfer remote-control API today (`grep -rniE 'surfer' src/ scripts/` outside docs turns up nothing beyond the #216 GTKWave/Surfer file-handoff mentions, which is read-only VCD consumption, not a live cursor-sync channel). KC-23-4 already anticipates the protocol being unworkable ("If viewer cursor-sync requires feeding external values into the simulation… drop PF-6's sync half"), and #535 records that #508 recommends cutting this half anyway. Given finding 1, this is likely moot in practice, but as filed the issue treats "pin one viewer version" as a scoping detail rather than the integration risk it is against a third-party tool whose remote-control protocol maturity is asserted, not evidenced from this codebase.

## What's solid

- The "nothing retains the producer-to-consumer relation after an event fires" claim is independently verifiable and true: `SimEvent` has no causal/parent field.
- Exclusion-2 discipline (rewind via re-simulation, never per-element checkpoint) is consistently argued across §1, §3, §5, kill criteria, and the sibling #535 filing — no drift toward the excluded checkpoint mechanism anywhere in the corpus I checked.
- The `related` list is accurate and appropriately marked reference-only; #216 is correctly cited as closed, and #63's live-co-simulation boundary is correctly respected (viewer sync is cursor-only, never feeds values back).
- KC-23-1 through KC-23-4 are genuine falsifiable stop conditions, not decorative — a real strength relative to many capstones in this tracker.
