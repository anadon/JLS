# Issue #845: TASK-C574-1: the README's "Try it in your browser" link lands on a running circuit, and a dead demo URL turns a lane red
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

#845 is `TASK-C574-1`, a README-only slice of #574 (`FEAT-C32-3`), which itself sits at the bottom of a three-deep chain: #572 (`FEAT-C32-1`, picks the browser-demo mechanism, still open, no go/no-go recorded) → #573 (`FEAT-C32-2`, builds the static demo pages, still open, reviewed `needs-rework`) → #574 (README/gallery integration, reviewed `needs-rework`) → #845 (this task). Confirmed against the checkout: `grep -n -i "try it|demo|browser" README.md` returns nothing — there is no existing demo link to modify — and `.github/workflows/` (`ci.yml`, `codeql.yml`, `mutation.yml`, `release.yml`, `repro-installers.yml`, `scorecard.yml`) contains no link-checking job of any kind, so AC-3 asks for infrastructure that does not exist today, wired to a URL that does not exist today either. The task inherits, and in places sharpens, the same defects the fleet's reviews of #573 and #574 already found in the parent chain.

## Findings, most severe first

**1. AC-1 asserts a stronger, more specific promise than its own dependency chain can currently back, and is false-on-arrival if #572 resolves to its named fallback.**
Quoted: "AC-1: ...landing on a #573 demo page that shows a running circuit with no further clicks." This is not hedged language — it is a factual claim about what the linked page does. But #572's AC-4 (per #573/#574's own reviews) names two fallback mechanisms if the primary candidate (CheerpJ) fails feasibility, including "(b) recorded video walkthroughs" — explicitly not an interactive, running circuit. #845's `ordering_after` lists only `#573`, not `#572`; nothing in #845 hedges against, or even acknowledges, the possibility that the page it is told to link to is a video, not a "running circuit with no further clicks." If PF-1 lands on fallback (b), this task is unimplementable as written — either the AC must be violated or the task must be rewritten in place. Recommend #845 be blocked from starting until #572's go/no-go is recorded, or reworded to "lands on whatever #573 ships" with the "running circuit, no further clicks" language demoted to a preference, not a hard AC.

**2. AC-3 asks CI to guard a URL that does not exist yet, in a repo with zero prior link-checking infrastructure — the estimate and the ordering both look wrong.**
Quoted: "AC-3: A CI link check covers the demo URL; a dead or redirected-to-error target fails a lane." Grounding: no `lychee`, `markdown-link-check`, `urlchecker`, or any comparable tool/config appears anywhere in `.github/` or the repo root (checked via grep across `.github/` and a search for `.lycheeignore`/`.mlc*`). This is not "add one line to an existing lane" — it's standing up a new CI mechanism from scratch (tool choice, config, allowlisting, handling upstream flakiness/rate limits) for a single URL that is itself a forward reference to #573's unbuilt output. `band_mw: "0.25"` (consistent with this project's convention of a fraction of a maintainer-week, i.e. roughly a day) is plausible for "add a link + a sentence" but is tight for "add a link + a sentence + a brand-new CI link-check lane," and the task cannot even be exercised end-to-end (link checker passing against a real 200) until #573 ships. Recommend either splitting AC-3 into its own task with its own estimate, or explicitly sequencing it as the last step gated on #573's landing, with the estimate revised upward to reflect net-new CI tooling.

**3. AC-2's "no redirect through anything operated, account-gated or tracking-gated" is the same unresolved ambiguity already flagged against #574, now inherited verbatim plus an added undefined term.**
Quoted: "AC-2: The link target resolves to a static page — no redirect through anything operated, account-gated or tracking-gated." #574's adversarial review (finding 2) already established that GitHub Pages — the hosting mechanism #551 names as the likely default ("published via the repository or GitHub Pages") — is itself infrastructure GitHub *operates*, so a literal reading of "no redirect through anything operated" would rule out the project's own most likely host. #845 does not resolve this; it re-imports the same word ("operated") with no definition, and adds "tracking-gated" with no definition either (does a GH Pages custom-domain HTTPS upgrade redirect count? Does GitHub's own anonymous page-view logging count as "tracking"?). As written this criterion is gameable in both directions: a strict reading fails the obvious implementation, a loose reading passes almost anything. Recommend #845 name the actual allowed host set explicitly (e.g., "GitHub Pages under this project's own domain is fine; third-party demo SaaS, redirect shorteners, and analytics-wrapped redirectors are not"), matching the concrete-allowlist fix already recommended for #574.

**4. AC-4's factual claim ("read-only, curated examples") may not be true of the thing it is asserted about, per #573's own review.**
Quoted: "AC-4: The README states in one line what the demo is (read-only, curated examples) so the link does not over-promise an editor." #573's adversarial review (finding 2) found that #573's AC-2 ("read-only by construction") has no named enforcement mechanism: if the winning mechanism is a CheerpJ-wrapped, otherwise-unmodified Swing jar, the demo would ship the ordinary `File > Open`/`Save` menus, i.e. not read-only by construction at all. #845 AC-4 commits the README to asserting "read-only" as a fact about the demo. If #573 ships without the restricted build #573's own review says is missing, #845's implementer either has to (a) write a README line that is false, or (b) discover mid-task that #573's deliverable doesn't match what #845 was told to describe — a cross-issue inconsistency #845 has no way to detect on its own. Recommend #845 not hard-code "read-only" in its AC text; instead require the one-liner to accurately describe whatever #573 actually shipped, verified against #573's AC-2 at implementation time.

**5. AC-5's "coherent order... rather than competing for the same attention" is unfalsifiable as worded.**
Quoted: "AC-5: The demo link and the install links sit in a coherent order — try, then install — rather than competing for the same attention." "Try, then install" gives a testable sequencing rule (good), but "coherent order... not competing for the same attention" adds a subjective visual/UX judgment with no measurable bar — no heading level, no visual weight, no distance-in-lines requirement. This mirrors the same "prominent"/"states plainly" pattern the fleet already flagged as unfalsifiable in #573 (finding 7) and #574 (finding 7). Low severity — a human PR reviewer will likely catch an obviously bad layout — but as written a minimal-effort placement (e.g., a demo link buried in a footnote right before Installing) technically satisfies "try, then install" while plausibly failing the spirit of AC-5. Recommend dropping the "competing for attention" clause or replacing it with something concrete (e.g., "the demo link's `<h2>`/callout precedes the Installing JLS heading, both above the fold").

**6. Minor: "above the fold" (from the Outcome text, not restated in AC-1) is measured against nothing.**
The Outcome text says the link sits "above the fold," but README.md is a GitHub-rendered Markdown file with no fixed viewport — "above the fold" varies by window size, zoom, and whether the OpenSSF badge line (`README.md:3`) and the intro paragraph (`README.md:5-10`) are counted. AC-1 itself doesn't restate "above the fold" as a criterion (only the Outcome prose does), so this is a soft inconsistency rather than a hard AC defect, but an implementer chasing the Outcome text literally has no fixed target. Recommend AC-1 state the concrete placement rule (e.g., "before the first `##` heading") rather than leaving it only in prose.

## What's solid

- AC-1's "no further clicks" clause is a genuinely concrete, testable requirement (unlike "prominent" elsewhere in this cluster) — good, keep it.
- Scoping this as a README-only task (`TASK-C574-1`) under #574 rather than re-litigating the gallery-linking half is clean task decomposition, not scope creep.
- `ordering_after: ["#573"]` is directionally correct — the task correctly recognizes it cannot be closed before #573 exists, it just doesn't go far enough up the chain to #572 (finding 1).
- AC-3's instinct — that a dead demo link is worse than no demo link, and CI should own that — is the right instinct and matches this project's existing test-discipline pattern (e.g. `HelpTopicsTest` per `ARCHITECTURE.md`); it is the sequencing and cost estimate that need fixing, not the idea.

## Recommendation

Do not schedule #845 until #572 has recorded its go/no-go and #573 has a real page to link to — as written, AC-1's "running circuit, no further clicks" claim may be false on arrival, and AC-3's CI check has no real target to verify against yet. Before implementation: extend `ordering_after` to acknowledge the #572 dependency transitively, replace AC-2's undefined "operated"/"tracking-gated" language with a concrete host allowlist, make AC-4's "read-only" claim conditional on what #573 actually ships rather than asserted as fact, tighten AC-5 to a measurable placement rule, and either re-scope AC-3's CI-lane work with a realistic estimate or split it into its own follow-up task gated on #573 landing.
