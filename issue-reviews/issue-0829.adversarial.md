# Issue #829: TASK-C571-2: a sub-48-hour first response and a one-week merge decision are published as objectives, and the actual times are visible enough to be held to
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of the issue

A task under feature #571 (itself under capstone #514/CAP-30) that asks for
two things: (AC-1) CONTRIBUTING publishes a <48h first-response and <1-week
first-merge-decision objective, explicitly framed as aspirational at bus
factor 1; and (AC-2..AC-5) a rolling record — "a tracker query or a
generated file" — that reports, per external PR/issue, time-to-first-
maintainer-response, with the counting method written down, a computable
trailing-quarter median, and correct handling of quarters with zero external
activity.

## Findings, most severe first

**1. [Critical] The metric's own "not a bot" test cannot detect the exact
gaming vector this repo already practices.** AC-3 requires the method to
define first response as "a substantive human comment, not a bot or a
label." But this repo's maintainer already posts AI-agent-generated content
under their own human account: the two review comments on #571 itself
(`issuecomment-5176175892`, `issuecomment-5227450446`) are both signed
`_Generated by [Claude Code](https://claude.ai/code)_` and posted by
`anadon` (`author_association: OWNER`), not by a bot account. Via the GitHub
API these are indistinguishable from a genuinely human-typed reply — same
`user.login`, same `user.type: User`. A maintainer (or an agent operating
under the maintainer's credentials, which this very review-fleet is an
instance of) could satisfy the <48h objective on every issue by having an
agent post a fast, generic acknowledgment, and the record — built exactly to
AC-3's stated spec — would count it as a real "substantive human comment."
That defeats the issue's own stated purpose: "the objective is measurable
rather than aspirational... including someone deciding whether to bother
contributing." The acceptance criteria as written can pass while the real
goal (a human is actually paying attention within 48h) fails.
**Recommendation:** AC-3's method needs to either exclude
agent-authored-but-human-posted content (hard to detect reliably) or
explicitly acknowledge the limitation and define "substantive" narrowly
enough (e.g., references specific content from the reporter, not a
templated acknowledgment) that a drive-by comment doesn't qualify — and say
so in the written method, not leave it implicit.

**2. [High] The Outcome section offers two implementation options that are
not actually equivalent — one of them cannot satisfy the acceptance
criteria.** The issue says: "The record is a tracker query or a generated
file over external PRs and issues, computing time-to-first-maintainer-
response." A GitHub "tracker query" (a saved search/filter URL) can list or
sort issues by creation date, but GitHub's search syntax has no operator
that computes elapsed time between issue-open and first-comment, and
certainly none that computes a median across a result set. AC-2 ("reports...
the time from open to first maintainer response") and AC-4 ("the median...
is computable... without hand-collection") both require actual computation
that a bare tracker query structurally cannot provide — a human would still
have to open every result and hand-time it, which is precisely what AC-4
says must not be required. This is an internal contradiction: the Outcome
paragraph presents a non-viable option as if it satisfies the criteria that
follow it. **Recommendation:** drop "a tracker query" as a standalone
option, or restrict it to a documented feeder step (e.g., a saved search
that scopes the input set) rather than the deliverable itself.

**3. [High] No handling is specified for PRs/issues that never receive a
maintainer comment — a silent-close survivorship gap that inflates the
reported number in exactly the direction the metric is supposed to guard
against.** AC-3 requires "first response" to mean a substantive human
comment. Nothing in AC-2/AC-3/AC-4 says what happens to an item the
maintainer closes without commenting (a bare "close" click), or leaves open
indefinitely with no reply. Two silent defaults are both bad and neither is
ruled out: (a) exclude such items from the record entirely, which drops the
worst cases out of the denominator and makes the published median look
better than the real experience of contributors who were ignored; or (b)
leave them as permanently-open "still waiting" entries with no defined
median treatment, which AC-4 doesn't say how to fold into a single number.
AC-5 only handles the *zero-external-activity* edge case ("no data"); it
says nothing about the *some-activity-but-no-reply* case, which is the one
that actually matters for judging whether the <48h objective is real.
**Recommendation:** add an explicit AC for unanswered items — e.g., they
count as non-responses in the median (or are reported as a separate
"no-response" count alongside the median) rather than being silently
dropped.

**4. [Medium] Cost is likely underscoped for what's being asked.** The
task's own machine block gives `band_mw: "0.25-0.5"` (plus the parent
feature's "+ ongoing" for the SLO-keeping half). Building this record
correctly requires: paginating the GitHub REST/GraphQL API across all
external PRs and issues, walking each item's timeline (not just the
comments list) to distinguish comments from label/assignment events,
identifying bot accounts, applying the "substantive" test from finding 1,
windowing by rolling quarter, computing a median with the zero-data case
from AC-5 handled, and then keeping it fresh indefinitely. That is a real
small data pipeline, not a one-off doc edit, and the repo has zero existing
tooling in this direction (`scripts/` holds only build/installer/rig
helpers — no API or metrics scripts). 0.25-0.5 mw (roughly 10-20 hours) is
tight for the initial build alone once timeline-event parsing and edge
cases are counted, before any "ongoing" maintenance.

**5. [Medium] "Rolling record" has no defined update cadence, so the
acceptance criteria can be satisfied by a one-time snapshot that is never
refreshed.** AC-2 says the record "reports" the times and AC-4 says the
median is "computable... without hand-collection" — both are satisfiable by
a script that is run once, committed, and never run again. Nothing requires
a scheduled regeneration (a workflow cron, a pre-release check, a staleness
warning) or even a "generated at" timestamp the record must carry. A record
that goes stale after the PR that introduces it would still pass every
stated AC while silently becoming exactly the "aspirational, unmeasurable"
state the issue exists to fix. **Recommendation:** add an AC requiring
either automated regeneration (e.g., a scheduled workflow) or, at minimum, a
visible generation timestamp plus a documented manual cadence.

**6. [Medium] No test obligation for the record-generation logic itself,
inconsistent with this repo's own contribution bar elsewhere.**
CONTRIBUTING.md states "Every bug fix carries a regression test" and the
repo enforces JaCoCo/mutation-testing floors specifically to keep tested
code from regressing (CONTRIBUTING.md:69-124). The median/quarter-window/
no-data logic in AC-4/AC-5 is exactly the kind of small, edge-case-prone
logic (off-by-one quarter boundaries, division-by-zero on an empty set,
correct exclusion of bots) that benefits from a regression test, yet none
of AC-1..AC-5 asks for one. If the deliverable is implemented as a
non-Maven artifact (a shell script or GitHub Actions YAML calling `gh`/`jq`,
say, living outside `src/`/`test/`), it would also fall entirely outside
`mvn verify`, SpotBugs, and the coverage ratchet — a legitimate implementation
choice, but one the issue doesn't make explicit, so a reviewer can't tell
whether this work is expected to meet the project's usual engineering bar
or is deliberately exempt as tooling. **Recommendation:** state the expected
implementation surface (in-repo Java under a test-covered package, vs. an
external/workflow script) and, either way, require a test or a documented
manual verification transcript for the median/no-data logic.

**7. [Low] The published objective doesn't cross-reference the other
published-response-time number already in the repo.** SECURITY.md commits
to "an acknowledgement within two weeks" for vulnerability reports. AC-1's
new <48h/<1wk objectives, once published, will sit in the same repository as
a slower, already-published guarantee for a different channel. Not a real
contradiction (different queues, and the security one is explicitly a
guarantee vs. an "objective"), but worth a one-line cross-reference in
CONTRIBUTING so a reader doesn't wonder why ordinary issues get a faster
published number than security reports.

## What's solid

- AC-3's requirement to write down what counts as "first response" and
  "external" is genuinely good practice and pre-empts the generic
  gameability critique that a sibling review of the parent feature (#571)
  raised in the abstract — this task operationalizes it rather than leaving
  it implicit. (It still doesn't survive finding 1's specific attack.)
- AC-5's explicit "no data, never a satisfied objective" rule is the right
  shape for a low-volume repo and shows real thought about the empty-quarter
  edge case, even though finding 3 shows a related case wasn't covered.
- `ordering_after: []` is correct and consistent with #571's own
  2026-08-08 ordering-correction comment, which found AC-3/AC-4 of the
  parent feature (the two ACs this task implements) "ready now" — unlike
  #571's own machine block, this task's dependency field is already right
  and doesn't need a correction pass.
- AC-1's "objectives rather than guarantees at bus factor 1" framing is
  honest and matches an already-documented reality elsewhere in the repo
  (`ISSUE-AMBIGUITIES-2026-07.md:90` independently notes the project is
  bus-factor 1); this task isn't inventing a new claim, just publishing an
  existing one.

## Verdict rationale

The acceptance criteria are more carefully written than the average task in
this program — AC-3 and AC-5 show real awareness of the obvious gaming
risks. But the specific mechanism proposed still has a hole big enough that
the metric can pass while lying about the underlying reality: an
agent-posted-under-a-human-account comment satisfies the "not a bot" test
(finding 1), a "tracker query" is offered as a valid implementation for a
requirement it cannot meet (finding 2), and unanswered items have no defined
treatment (finding 3) — all three let the published median look good without
the project actually being responsive, which is the exact failure mode the
issue exists to prevent. Combined with an underscoped cost estimate and no
freshness or test obligations, this needs a rework pass before it's safe to
build against, not just a "proceed with concerns" nod.
