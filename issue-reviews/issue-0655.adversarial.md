# Issue #655: TASK-C565-4: a synthesized circuit's extracted table is identical to the table it was synthesized from — the loop closes
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: sound-with-concerns

## Summary of the ask

A CI test: take a fixture truth table, run it through synthesis (#565/TASK-C565-2, #653), extract the resulting circuit's table back out through the extractor path (#563/TASK-C563-1, #641), and assert the two tables are identical modulo a stated don't-care rule. Verified against the actual chain of issues: #641 and #653 both exist, are open, and their titles/AC lists match what #655 assumes of them. AC-1's wording ("a truth table synthesizes to a drawn circuit whose extracted table round-trips identically") is a verbatim quote of CAP-31 (#515) AC-2, not a paraphrase drift — checked against #515's body directly.

## Findings, most severe first

**1. AC-2's don't-care rule is close to unfalsifiable as stated — it can't catch a wrong synthesis on exactly the rows it's supposed to cover.**
Quote: "the synthesized circuit produces *some* definite value there, and the comparison honours the source's don't-care rather than failing on it." Per #641 (TASK-C563-1) AC-1, the extractor always "yields a correct truth table" — every row gets a concrete simulated 0/1, by construction (a combinational circuit has no third state on any input combination). So "produces some definite value" is true unconditionally for any extracted row; it is not a property a broken synthesizer can fail. The net effect is that don't-care rows carry **zero verification weight** in this round-trip test — a minimizer bug that picks a logically-wrong-but-still-definite value on a DC row passes silently. That may be the intended semantics (DC genuinely means "any value is correct"), but the issue presents AC-2 as a meaningful acceptance criterion ("Don't-care rows have a stated round-trip rule") when it is actually a no-op check. Recommend the issue say explicitly: "DC rows are excluded from the equality check; no value assertion is made there" — so nobody mistakes AC-3's don't-care fixture for a row that's actually being verified.

**2. AC-1 ("identical") and AC-2 (silent carve-out for DC rows) are in unresolved tension, and the comparator algorithm is never specified.**
"identical" in AC-1 and "the comparison honours the source's don't-care rather than failing on it" in AC-2 both describe the same comparison step but pull in different directions with no worked example or pseudocode. Concretely unanswered: does the comparator (a) skip DC cells entirely, (b) require the extracted table to also mark the row DC (impossible, since the extractor has no DC concept per `TruthTable.java:1447-1449`'s runtime collapse of DC outputs to false — see finding 4), or (c) treat DC-in-source as "any value accepted, but the row/column must still exist"? Two engineers reading this issue could build divergent comparators that both claim to satisfy AC-1+AC-2. Recommend adding one concrete before/after row example to the issue.

**3. Row/column correspondence between the source fixture and the extracted table is assumed, not stated — and the assumption can break at exactly the "shared product terms" fixture AC-3 asks for.**
#653 (TASK-C565-2) says synthesis builds "the input and output pins the table declared," implying full input arity is preserved even for inputs irrelevant to any output after minimization. #641 (TASK-C563-1) AC-2 requires the *extractor's* enumeration/column order to be "deterministic and documented" — but documented relative to what reference (pin creation order? alphabetical? original table order?) is not pinned down in either issue, and #655 never states that the two orderings must coincide for its equality check to mean anything. If minimization ever drops or reorders an input pin that turns out not to affect any output (a realistic outcome for the "shared product terms" and "constant-output degenerate case" fixtures AC-3 explicitly asks for), a literal table comparison either false-fails on a reordering artifact or silently compares the wrong columns. The issue should state the invariant explicitly: synthesized circuits must preserve the full declared input/output pin set, in the source table's order, regardless of relevance — otherwise AC-1's "identical" is not well-defined for exactly the fixtures AC-3 requires.

**4. Contradicts the codebase's actual don't-care model in a way the issue doesn't reconcile.**
`src/jls/elem/TruthTable.java:1447-1449` (`// don't care becomes false` / `if (outValue == 2) outValue = 0;`) shows the *existing* `TruthTable` element destroys don't-care information at simulation time — a DC output cell silently reports 0. #306 (CAP-09) names this exact code as a bug it intends to fix at the value-domain level ("A value domain that cannot represent 'unknown' gives confident wrong answers"). #655's fixture tables are presumably `TruthTable`-element or table-file inputs to the synthesizer, not outputs of it, so this may not directly collide — but the issue never states whether the *fixture* truth tables it reads are represented using this same 2=DC convention, and if so, whether #306's planned fix to that representation is a prerequisite. Given #306 is explicitly named in #655's own boundary notes as upstream of the extractor, this is worth one clarifying sentence rather than silence.

**5. "Reads back through #563's path" is ambiguous about which path — the internal API or the CLI batch surface — and the batch surface is a separate, unlisted, still-open task.**
#641 (TASK-C563-1) boundary notes: "the batch surface is TASK-C563-4" — filed separately as #646, open, and *not* in #655's `ordering_after`. If "the loop closes" is meant to be demonstrated end-to-end through the public/headless interface (consistent with CAP-31 AC-5's batch-callability requirement, which #655 does not cite), #646 is a missing dependency. If instead the CI test is meant to call internal extractor/synthesizer APIs directly — consistent with this repo's existing convention (`BatchSimulationGoldenTest`, `CircuitRoundTripTest` in `test/jls/`, per ARCHITECTURE.md's Test-layout section, call internal Java APIs, not the CLI) — then #646 is correctly out of scope and this is a non-issue. The issue should say which.

**6. AC-4's failure-diagnostic bar is easy to satisfy trivially.**
"names the first differing row and column on failure" sets no bar on message content (must it show expected vs. actual values, or just coordinates?). Low risk given this repo's established JUnit golden-test idiom, but as written a comparator that prints `"row 3, col 2"` with no values technically satisfies AC-4 while being nearly useless for debugging. Minor; tighten if this criterion matters to reviewers.
