# Issue #611: TASK-C487-2: the constraint set leaves JLS as a netclass and rule file — byte-identical to a golden, and every emitted keyword one the target parser actually accepts
- Lens: adversarial

- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Context established

#611 is the "rule-file emitter" scope of FEAT-060 (#487, "SI constraint authorship + PCB constraint export"), which is itself required by CAP-18 (#313). It sits on top of FEAT-004 (#336, net-partition IR + stable net naming) and FEAT-042 (#366, KiCad/gEDA emitters + manufacturability gate). None of the three exist in the tree yet: `git ls-tree` at the cited evidence commit has no `jls.netlist`, `pkg`, or `pcb` package, no `kicad`/`geda` hits anywhere under `src/`, and `ARCHITECTURE.md`/`README.md` corroborate that today's export surface is Verilog/VHDL/PCF only (`-export out.v`, `docs/vcd-interop.md`, `src/jls/hdl/board/PcfEmitter.java`). The issue's own `ordering_after: [336, 366, "TASK-C487-1"]` is an accurate reflection of #487's dependency graph — it is not fabricated — but it understates how unready those prerequisites are.

## Findings, most severe first

**1. (High — feasibility) The task is not actually startable: two of its three prerequisites are blocked on unresolved open questions, not merely unbuilt.**
`ordering_after` names #366 and TASK-C487-1 as blockers, and #611 reads as ready task-level scope ("Outcome", numbered "Acceptance criteria"). But #366 itself states: *"Open Question 1 … Blocks funding TASK-0089 and TASK-0090"* — the netlist emitter this rule file is supposed to "ride alongside" and name nets identically to cannot be funded until CAP-13 (#307) picks schematic-first vs. netlist-first, and #366's evidence plan calls that route decision "the weakest part of the plan." Likewise #336's naming convention — the exact function that decides what a net is *called* in the emitted rule file — has its own open question: *"The digest function … Blocks filing TASK-0008"*. TASK-C487-1 (the constraint vocabulary/section) is listed in #487 as "Not filed." #611 gives no indication that its acceptance criteria (in particular AC3, "every net named in the rule file appears in the netlist under the same name") are unwritable until both of those upstream decisions land. **Recommendation:** either mark #611 explicitly blocked-not-actionable until #366 Open Question 1 and #336 Open Question 1 are resolved, or state in the issue that the first work item is forcing those decisions, not writing the emitter.

**2. (High — gameable acceptance criterion) AC2's verification mechanism is unspecified and can pass by silently skipping.**
> "Parser legality is asserted separately from byte identity: every emitted keyword is checked against the pinned external parser version rather than against its documentation."

This is the issue's headline discipline, but it names no mechanism: is the check run against a digest-pinned container (the machinery #487 explicitly reserves for its *separate* "external DRC round trip" scope), or a lighter grammar check invented for this task alone? The project's existing precedent for optional external tools (`iverilog`/`ghdl` in README: "skip cleanly when [the tool] is not installed") means that if this check follows the same pattern, an environment without the pinned parser produces a green build with the parser-legality assertion silently never having run — which is exactly the "golden regenerated for the wrong reason still fails the second [assertion]" failure mode the issue is designed to catch, just one layer up. **Recommendation:** state explicitly whether the parser check is mandatory (CI fails without the tool) or skip-clean, and if skip-clean, require a loud, visible skip diagnostic rather than a silently green run.

**3. (Medium — untestable criterion) AC5 has no named test, unlike AC1–AC4.**
> "JLS claims no conformance the external tool does not check: any documentation sentence stronger than what the DRC verifies is a defect closed in this task."

AC1 cites `SiConstraintExportGoldenTest`; AC3 cites a cross-artifact test with #366. AC5 cites nothing — it is inherited verbatim from #487's Global Invariant 5, which also names no dedicated check. As written it can only be enforced by manual reviewer attention to prose, with no CI signal if it regresses later (e.g., a future doc edit re-introduces "controlled-impedance constraint" language). **Recommendation:** name a concrete check — even a grep-based doc-lint asserting the impedance annotation's documentation carries the "annotation, not constraint" qualifier — or mark the criterion explicitly as manual-review-only so it isn't mistaken for a CI-enforced bar the way its neighbors are.

**4. (Medium — scope/interface creep) The example CLI invocation asserts an interface decision that belongs elsewhere and isn't ratified anywhere in the cited graph.**
> `jls -export clk.net -si clk.kicad_dru design.jls`

Today's only `-export` flag is Verilog (`README.md`: `Verilog export (-export out.v circuit.jls …)`); #366 commits only to "an entry point," never a flag name, and #487 is silent on CLI surface entirely. #611 quietly decides that `-export` is repurposed to also mean "PCB netlist" and introduces a new `-si` flag, inside a task issue whose stated scope is the rule-file emitter, not the CLI contract (which `JLSStart.FLAGS`/`CliFlagTableTest` own per `ARCHITECTURE.md`). If a later issue chooses different flags, this text goes stale as a silent, unflagged deviation. **Recommendation:** mark the invocation illustrative or strike it, and let the actual flag naming happen wherever #366/#611's implementer decides it, per the existing `FLAGS` table discipline.

**5. (Medium — regeneration risk not disclosed) The golden this task's AC1 depends on is coupled to a naming convention that will change under it.**
#336 §6 states plainly: *"Name stability must land before any new HDL golden corpus is generated … Every corpus generated before names are stable is regenerated afterward"* (hard gate W0.3), and that gate is already recorded as a machine-block edge for #358. #611's `SiConstraintExportGoldenTest` fixtures name nets, and net names are exactly the thing #336 has not yet frozen. If this task's golden is authored before #336 lands its naming convention, it will need regeneration for a reason that has nothing to do with whether the rule file is correct — undermining the "byte-identical to a golden" bar the issue treats as a clean, mechanical check. #611 does not carry the same explicit warning that #358 (and #336's own text) carries for this identical risk. **Recommendation:** add a note that the golden must not be frozen before #336's naming convention lands, mirroring the warning already given to sibling consumers.

**6. (Low — cosmetic) The machine-readable YAML header is double-HTML-escaped in the rendered issue body** (`band_mw: &#34;1.5-2.5&#34;`, `&#34;TASK-C487-1&#34;`), so it does not parse cleanly as YAML/JSON off the page as posted. This is systemic to the same issue-generation pipeline (visible identically in #366, #336, #487), not unique to #611, but it undercuts this project's own stated completion criterion elsewhere that "machine block, roster table, and mermaid graph agree with reality." Worth a template fix upstream, low severity here.

## What's solid (one-liners)

- The central discipline — separating "byte-identical to a golden" from "every keyword is parser-legal," and refusing to claim a checkable impedance *constraint* when the cited target tool's `NETCLASS` record has `m_TrackWidth`/`m_diffPairWidth`/`m_diffPairGap`/`m_diffPairViaGap`/`m_tuningProfile` and no impedance field — is evidence-backed (quotes the actual data model) and not hand-waved.
- AC1's determinism bar follows an established, working precedent in this repo (`src/jls/hdl/board/PcfEmitter.java` + its byte-deterministic golden), so the ask itself is not novel risk.
- AC4's rule that the resolved track width is "recomputed at emission and never stored as if it were authored intent" closes a real footgun (derived data drifting from its source) and is consistent with this project's existing discipline against storing derived state (see #336's net-name-never-stored rule).
- The issue's scope is appropriately narrow — it does not re-litigate #487's other three scopes (vocabulary, DRC round trip, back-annotation) — and its `ordering_after` list is an accurate, not fabricated, projection of the real dependency graph.
