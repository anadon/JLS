# Issue #558: FEAT-C29-2: a Digital .dig circuit opens in JLS as a working, laid-out circuit — every element mapped by semantics or refused by name, never silently approximated
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of the issue

Proposes a `.dig` (Digital/hneemann, XStream XML) importer for JLS: five ACs covering corpus-of-one import fidelity, a written semantics-based element map, a generics carve-out pending #357, XXE hardening, and undo/no-partial-circuit discipline. Filed as one of five siblings (#556, #559, #561, #562) under capstone CAP-29 (#513), itself justified by the competitive survey #510. Three child tasks already exist (#612, #614, #615). Nothing `.dig`/XStream/Digital-related exists in the repo today (`grep -rli "digital\|\.dig\b\|xstream" src/ docs/` returns nothing), and no XML parser exists anywhere in `src/` (confirmed empty for `javax.xml|org.w3c.dom|DocumentBuilderFactory|SAXParser|XMLInputFactory`), so this and #323 (`.circ`) would each introduce the first XML parse in the codebase.

## Findings, most severe first

**1. AC-1's single-file criterion is weaker than this project's own established bar for the same claim, and is trivially gameable.** AC-1 reads: *"One real published `.dig` circuit imports with zero unexplained losses."* Compare CAP-16 (#311), the sibling capstone for `.circ` filed by the same author days earlier: it explicitly rejects a single-file demonstration as insufficient evidence for exactly this kind of claim — "*parity here is not a round trip... it is opens-honestly, behaves-identically-on-the-source-tool's-own-vectors*" — and backs AC-1 with a quantified corpus requirement (`≥30` files from `≥3` independent public course repositories, a published per-construct coverage table, and KC-16-1: a measured >50%-of-corpus trigger that forces a re-cost). #558 has none of this. As written, AC-1 is satisfied by hand-picking one trivial `.dig` file containing only basic gates — the verification could pass while the real goal (an instructor's actual course material imports) is completely untested. **Recommendation:** import CAP-16's corpus-and-coverage-table discipline (or explicitly justify why `.dig` doesn't need it) before this issue is actionable.

**2. The issue is filed as a bare stub relative to every comparable feature-tier issue in this corpus.** #323 (FEAT-025), #314 (FEAT-002), #357 (FEAT-017) — the very issues #558 orders itself after — each carry `tier`, `evidence_commit`, `requires_tasks`/`blocked_by`/`blocks` with mirrored edges, a mermaid DAG, §1–§7 (capability statement, decomposition, interface contract, invariants, integration criteria with an evidence plan, sequencing, re-planning protocol), Open Questions, and a Definition-of-Done checklist. #558's YAML block is four keys (`feat_id`, `serves_capstones`, `band_mw`, `ordering_after`) and the body is two short sections. There is no decomposition table, no per-task cost sum reconciled against the 4-6 mw band (contrast #323's and #357's explicit "the band and the task sum do not agree" reconciliations), and no integration-criteria/evidence-plan section defining what a reviewer actually checks at close. This isn't cosmetic: without an interface contract or invariants section, it's unclear what "structure intact" or "working" mean precisely enough to fail a bad implementation. **Recommendation:** either flesh #558 out to the template its own siblings (#556, #513) and predecessor features use, or state explicitly that this issue is a placeholder and point to where the real spec lives (the child tasks #612/#614/#615 only cover part of it).

**3. AC-3's generics clause is, in practice, close to a permanent "always refuse," and the issue doesn't say so.** AC-3: *"Generics/parameterized circuits map where JLS semantics agree, and otherwise refuse by name until FEAT-017 (#357) lands."* #357 is priced at 25-36 mw (the largest single-feature band in the whole corpus), is blocked by three more unfinished features (#340, #318, #319), and its own evidence section confirms JLS currently has **zero** parameter/definition-instance representation ("*grep... returns only javadoc `@param` tags... There is no parameter surface to extend; this feature creates it*"). Child task #615 (TASK-C558-3) confirms the mappable branch cannot be exercised at all until #357 ships, and — reasonably — scopes itself to ship only the refusal branch. The strategic problem: #510's own survey (which justifies this whole capstone) scores "Hierarchy/reuse" as Digital's strongest lead over JLS (5 vs 2), driven specifically by Digital's generics. So the importer whose entire premise is "win over Digital's stranded users" will, for the foreseeable future, refuse the one construct class that most differentiates Digital circuits worth migrating — and AC-3 as worded reads as satisfied either way, silently. **Recommendation:** state this trade-off explicitly in the issue (e.g., "until #357 lands, expect most real hierarchical Digital designs to partially refuse") rather than leaving AC-3 to imply parity that won't exist.

**4. A scope ambiguity the issue's own review comment raised is still open.** The 2026-08-04 bot-review comment on this issue flags that "laid-out" in the title is ambiguous between "honour the `.dig` file's own coordinates" (cheap, no engine needed) and "generate placement" (re-owns #62's auto-layout engine, needing a dependency edge that doesn't exist): *"That reading should be made explicit before this issue is executed... Flagged, not resolved; no scope was moved."* The issue body has not been edited since to resolve it. **Recommendation:** add one sentence to the Outcome/AC section stating which reading is intended, and add `blocked_by: [62]` if it's the latter.

**5. Test-section preservation is a load-bearing obligation for a sibling issue but isn't an AC here.** The same review comment: a `.dig` importer "that parses circuits correctly but drops the test sections silently leaves its sibling [#562, FEAT-C29-5] with nothing to read, and would do so while passing all five of this issue's own ACs... Worth an explicit AC if this issue is ever revised." The current "Boundary and reference notes" section states the obligation in prose ("This importer must parse and preserve those sections") but none of AC-1 through AC-5 tests it — so #558 can be marked complete while #562 (which already has three concrete child tasks, #635/#637/#639, expecting those sections) inherits nothing to consume. **Recommendation:** add AC-6 asserting that every embedded test section in the source file is present, unmodified, in the parsed model that #562 consumes.

**6. Schema/tooling inconsistency: `ordering_after` instead of `blocked_by`.** Every other feature-tier issue in this corpus (#556, #513, #323, #314, #357) encodes dependency ordering as a `blocked_by`/`blocks` YAML pair with mirrored edges on both issues, explicitly so the corpus's automated DAG-consistency walk ("regenerate the graph, re-walk, and re-record on every REPLAN") can find it. #558 uses a free-text `ordering_after` list instead — same information, different key. If the DAG walks described in #311/#357/#314 are performed programmatically or semi-programmatically over `blocked_by` fields (as their own text repeatedly implies — "no feature declares any capstone number... in its `blocked_by`" is stated as a checked fact), #558 (and its siblings #556/#559/#561/#562, which share the same pattern) would be silently invisible to that walk. **Recommendation:** either confirm `ordering_after` is deliberately a different, lighter-weight field the tooling also reads, or convert it to `blocked_by` for consistency.

**7. KC-29-1's stop-loss threshold is ambiguous.** Inherited from CAP-29 (#513): *"stop-loss at 1.5× the 4-6 mw band."* 1.5× of the low end (6 mw) or the high end (9 mw)? Contrast CAP-16's KC-16-1, which states a precise, measured trigger (">50% of a ≥30-file, ≥3-repo corpus needs a non-increment-1 construct"). As worded, an implementer could burn anywhere from 6 to 9 mw before anyone can point to the criterion and say "kill it now" — a soft, gameable stop-loss. **Recommendation:** state whether 1.5× applies to the low or high edge, or replace it with a measured trigger analogous to KC-16-1.

**8. No independent cost derivation.** `band_mw: "4-6"` is identical to CAP-29's (#513) own pre-allocated `PF-2 4-6` line — it isn't re-derived here from any task breakdown. Every comparable feature document in this corpus (#323, #314, #357) shows its own task-row sum and explicitly reconciles it against the capstone's band, often finding a mismatch worth flagging (#357's is off by 6-9×). #558 shows no such derivation, so there is no way to tell whether 4-6 mw was actually re-checked against the concrete scope (an XStream reader for a foreign schema with on the order of 50+ component kinds vs. JLS's 35, a written mapping table, the generics carve-out, and a first-in-tree hardened XML parser) or is simply copied forward from the capstone filing. **Recommendation:** add a task-level cost breakdown (the child tasks #612/#614/#615 are a start; sum and reconcile them here).

**9. XXE hardening (AC-4) risks duplicated, potentially divergent effort with #323.** Both this issue and #323 (`.circ`) independently claim to be "the first XML parse in the shipped source tree" (confirmed true today for both — no XML parsing exists anywhere in `src/`). #556 generalizes the *loss report* shape across importers, but nothing generalizes the *hardened XML reader* itself; AC-4 here cites "#38 standard, CAP-16 AC-5 standard" as precedent but names no shared implementation to reuse from #323. Two independently-written XXE-hardening passes (disable external entities, forbid DOCTYPE, neutralise entity resolvers) for two different XML parsers is a plausible place for one to be hardened correctly and the other to regress later. **Recommendation:** name a shared hardened-XML-reader utility (or explicitly land #323 first and reuse its parser configuration) rather than two independent AC-4-style implementations.

## What's solid

- **AC-2's semantics-first mapping rule** ("no mapping by name alone") directly reuses FEAT-025's documented `ShiftRegister` name-collision precedent (`HdlExporter.java:83-84`) — a real, previously-discovered defect class, correctly generalized rather than restated from scratch.
- **AC-4 and AC-5's untrusted-input and no-partial-circuit disciplines** correctly inherit from real precedent (#38's closed hardening work, `NetlistImporter`'s documented no-partial-circuit contract) rather than inventing new policy.
- **The FEAT-C29-5 (#562) test-vector boundary** is correctly drawn and explicitly stated as intentional and confirmed correct by the issue's own review comment — a genuinely settled scope line, not a hidden assumption.
