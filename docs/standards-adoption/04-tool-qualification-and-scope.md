## Safety-critical scope statement, and what tool qualification would actually require (#223-#236)

*Numbering note: `#223`–`#236` here are **entries in
`docs/standards-landscape.md` §12.a**, not GitHub issue numbers. The
collision is real and worth stating once: repo issue **#223** is the
extension-points work already recorded in `ARCHITECTURE.md` ("Extension
points: the typed seam catalog (recorded 2026-07-27, #223)"), while
landscape **#223** is ISO 26262-8 clause 11. Any issue filed for this
playbook item must say "landscape #223" explicitly in its body.*

This section has two deliverables that point in opposite directions:
**(a)** write and ship a scope statement — recommended, cheap, do it;
**(b)** the costed walk-through of actual tool qualification — the thing
the scope statement exists so the project never has to do.

---

### What conformance actually means

#### (a) The scope statement is not a conformance claim

A "not qualified for safety-critical use" statement asserts **no**
conformance to anything. It is a *negative scope declaration*: the
project stating, in the artifact itself and in the artifact's
documentation, the boundary of use it has engineered for. There is no
standard it conforms to, no clause it satisfies, no body that assesses
it. It is pure self-assertion, and that is the correct instrument.

What a claim of "we said so" rests on, concretely, is:

- **the file `docs/intended-use.md` at a given release tag** (to be
  created — see below), which is the canonical text; and
- **the same sentence present in the shipped binary**, reachable
  without network access, via `jls -h` (generated by
  `JLSStart.usageText()`, `src/jls/JLSStart.java:1190`); and
- **a build-failing test** that keeps the two in step
  (`test/jls/IntendedUseScopeTest.java`, to be created).

That third item is what separates this from a README paragraph nobody
maintains. In this repo, a documentation claim that is not pinned by a
drift test is not evidence — the house pattern is
`test/jls/ExtensionPointCatalogTest.java:93` (reads `docs/extension-points.md`
and cross-checks it against code constants in both directions) and
`test/jls/FileFormatSpecTest.java:52` (reads `docs/file-format.md`).

**What the statement does not do.** GPLv3 sections 15, 16, and 17
(`LICENSE:589`, `:600`, `:612`) already disclaim all warranty, including
fitness for a particular purpose, and cap liability. The scope statement
adds **zero** warranty protection that the licence does not already
provide, and it must not be drafted as if it did. What it adds is
different and is the whole point:

| GPLv3 §15–17 says | The scope statement says |
|---|---|
| "no warranty of any kind" — a legal posture about *all* uses | "here is the use this tool was engineered for, and here is a specific named use it was not" |
| addressed to a licensee, in licence language | addressed to a procurement officer, an instructor, and a safety engineer, in their vocabulary |
| identical in every GPL program ever written, therefore information-free | names ISO 26262 / IEC 61508 / DO-330 explicitly, therefore answers the actual question |
| invisible at the command line | printed by `jls -h` |

The question this answers is one people really ask and that GPLv3 does
not: *"we're evaluating this for a lab that also does automotive/avionics
coursework — has it been tool-qualified?"* Today the honest answer exists
only in a maintainer's head. A one-line "no, and here is what we do
guarantee instead" converts a stall into a five-second decision, and it
pre-empts the worse failure mode where someone assumes silence means yes.

The statement also does **not** prohibit anything. GPLv3 §7 forbids
adding use restrictions (*a plain reading of the licence text, not a
verified legal opinion — but the drafting rule below is the safe course
either way*); a scope statement that read "you may not use
JLS for X" would be a licence-incompatible further restriction. The
drafting rule is therefore strict: **describe what the project has and
has not done, never what the user may or may not do.** "JLS has not been
qualified…" is safe; "JLS may not be used in…" is not.

#### (b) What the qualification regimes actually target

Three points that most summaries get wrong, and that determine the whole
cost analysis:

1. **The tool user classifies, not the tool supplier.** Under ISO
   26262-8:2018 clause 11, the *Tool Impact* (TI1/TI2) and *Tool error
   Detection* (TD1/TD2/TD3) determination — which yields the Tool
   Confidence Level TCL1/TCL2/TCL3 — is made by the organisation
   developing the safety-related item, in the context of their specific
   use case and their downstream detection measures. The same is true of
   IEC 61508-3:2010 §7.4.4's offline support tool classes T1/T2/T3, and
   of DO-330's tool criteria 1/2/3. **This project cannot declare a TCL
   or a tool class for itself, and any document claiming one would be
   meaningless.** What a supplier can do is supply *evidence* and
   *documented operational constraints* that make someone else's
   classification cheaper.
2. **What gets certified is a version, in an environment, under
   constraints.** A TÜV SÜD / TÜV Rheinland / exida "tool certificate"
   (landscape #236) is issued for a named tool version, running on a
   named platform, used within the constraints of a published safety
   manual / tool operational requirements document. It is not a
   certificate for "JLS" the project, and it evaporates the moment the
   version changes.
3. **TCL1 requires no qualification at all.** Under ISO 26262-8, a tool
   assessed as TCL1 needs no qualification method. Most classroom uses of
   any tool land at TI1 (the tool cannot introduce or fail to detect a
   fault in the safety-related item) simply because the output never
   enters a safety-related item. The realistic scenario in which JLS
   would ever be classified at all is narrow: a course or a company using
   JLS's `-export` Verilog/VHDL output (`src/jls/hdl/VerilogEmitter.java`,
   `VhdlEmitter.java`) as design entry for something that ships. The
   scope statement should say plainly that this is not a supported path.

The regimes named in landscape #223–#236, with the clause structure a
reader needs:

| Landscape # | Document | The mechanism, precisely |
|---|---|---|
| #223 | **ISO 26262-8:2018, clause 11** ("Confidence in the use of software tools") | TI × TD → TCL1/2/3. For TCL2/TCL3 a qualification method is required, selected per ASIL from the clause's tables: *increased confidence from use*, *evaluation of the tool development process*, *validation of the software tool*, *development in accordance with a safety standard*. Work products: a tool criteria evaluation report and a tool qualification report. |
| #225 | **IEC 61508-3:2010, §7.4.4** | Offline support tools classified T1 (no impact on the executable), T2 (verification/test tools whose errors can fail to reveal defects), T3 (tools whose output contributes to the executable). T2/T3 require a specification or manual defining the tool's behaviour and its constraints of use, plus validation evidence; "increased confidence from use" arguments are permitted with documented justification. |
| #227 | **DO-330 / ED-215 (2011)** | Tool Qualification Levels TQL-1..TQL-5, derived from the tool's criteria (1/2/3) crossed with the software level (A–D) per DO-178C §12.2. TQL-1 approaches full DO-178C rigour applied to the tool itself. |
| #227+#228 | **DO-330 alongside DO-254** | For airborne *hardware* design tools, DO-254 §11.4 governs tool assessment and qualification. *(Unverified: the exact current FAA/EASA guidance that endorses DO-330 for DO-254 tools — AC 20-152A and EASA CM-SWCEH-002 are the documents to read; I did not verify their current revisions or their precise wording, and this must be checked before anyone relies on it.)* |
| #230 | **EN 50128 / EN 50657** (rail) | T1/T2/T3 classes structurally similar to IEC 61508-3. *(Unverified: EN 50716:2023 is understood to consolidate/supersede EN 50128 and EN 50657; verify before citing either number in a shipped document.)* |
| #231 | **IEC 62304** (medical) | Tool validation happens under the manufacturer's ISO 13485 QMS rather than via a tool certificate. |
| #236 | TÜV SÜD / TÜV Rheinland / exida certificates | The commercial instrument that evidences #223/#225/#227 to a customer. |

**Scoping consequence for the drafted text:** the statement should name
these regimes but should **not** pin revision years in the shipped text.
Revisions move (ISO 26262 2011→2018, IEC 61508 Ed.1→Ed.2, the EN 50128
consolidation above); a document that says "ISO 26262-8:2018" goes stale,
one that says "ISO 26262-8 (automotive)" does not. Revision detail belongs
in `docs/standards-landscape.md`, which already carries a currency caveat.

### Implementation procedure

#### Part A — ship the scope statement (recommended)

**A1. Create `docs/intended-use.md`** as the single canonical source.
Naming follows the existing `docs/` convention (`extension-points.md`,
`file-format.md`, `component-naming.md`). Structure it with the RFC 2119
discipline the repo uses for normative docs, but note that this document
is *descriptive of the project's engineering scope*, not normative on the
user — so it should use RFC 2119 keywords only in the section that binds
the project (the maintenance rules), and plain declarative prose in the
statement itself.

The canonical text, ready to paste. The `<!-- scope:begin -->` /
`<!-- scope:end -->` markers are load-bearing: the drift test in A6
extracts exactly the text between them.

```markdown
# Intended use, and the safety-critical scope of JLS

**Status: normative on this project's scope. Not a licence, not a
warranty, and not a restriction on use.** This document states what JLS
is engineered for, what it is not engineered for, and what evidence the
project does and does not produce. Issue: (file one; cite it here).

## 1. Intended use

JLS is an educational digital-logic schematic editor and simulator. It
is built for teaching, coursework, autograding, self-study, and hobby
use: drawing circuits, simulating them interactively or in batch, and
exporting waveforms, images, and structural HDL for those purposes.

## 2. Safety-critical scope

<!-- scope:begin -->
JLS is not qualified for safety-critical use. It has never been
classified, validated, assessed, or certified as a software tool under
any functional-safety standard — including ISO 26262 (automotive tool
confidence levels), IEC 61508 (offline support tool classes), DO-330
with DO-178C or DO-254 (airborne tool qualification levels), EN 50128 /
EN 50716 (rail), IEC 62304 (medical), or IEC 61513 (nuclear
instrumentation and control) — and no such qualification is planned,
in progress, or being sought.
<!-- scope:end -->

Concretely, this project publishes none of the artifacts those standards
require of a qualified tool: there is no tool qualification plan, no tool
operational requirements document, no tool safety manual, no requirements
specification for the tool against which a validation suite is traced, no
qualification kit, no known-error list maintained under a
configuration-management plan of record, and no organisational quality
management system behind any of it. There is also no commercial support
commitment and no warranty of any kind (see LICENSE, GPLv3 sections 15
to 17).

Do not use JLS as the design-entry, simulation, or verification tool of
record for hardware whose failure could cause injury, loss of life,
environmental harm, or significant property damage, and do not use its
HDL export (`-export`) as the source of a design that will be
manufactured into such hardware. If you are building something that
must be safe, use a tool your safety process has qualified, and treat
anything JLS tells you as unverified.

## 3. Who classifies JLS, if anyone

Under every regime named above, the tool classification — ISO 26262's
Tool Impact and Tool error Detection giving a Tool Confidence Level;
IEC 61508's T1/T2/T3; DO-330's tool criteria and Tool Qualification
Level — is determined by the organisation developing the safety-related
product, in the context of their own use and their own downstream
detection measures. It is not something a tool supplier can assert on
their behalf, and this project asserts nothing about it. If your process
requires you to classify JLS, classify it as an unqualified tool and
size your detection measures accordingly.

## 4. What JLS does guarantee

The absence of safety qualification is not an absence of engineering
discipline. The following are real, documented, and test-enforced, and
are offered as evidence for anyone doing their own evaluation:

- **A specified simulation model.** `docs/simulation-semantics.md` is a
  normative specification of the time model, event ordering, value
  domain, delays, edge triggering, and tri-state resolution, written
  from the implementation with code anchors.
- **A specified, stable batch interface and file format.**
  `docs/batch-interface.md` and `docs/file-format.md` are stability
  contracts: changes require a CHANGELOG entry and either a major
  version bump or a compatibility flag.
- **Determinism.** Simulation seeding and same-time event ordering are
  canonical and pinned by tests, so the same circuit and the same
  inputs produce the same result on every machine and every run.
- **Byte-exact golden tests** over batch simulation output, VCD export,
  and HDL export, plus a full RV32I CPU run as an integration oracle.
- **Reproducible builds.** The jar and the CycloneDX SBOM rebuild
  bit-for-bit from a tagged source tree; see `docs/reproducibility.md`.
  Releases carry signed build-provenance attestations.
- **A gated build.** `mvn verify` compiles with warnings as errors,
  runs the full test suite under coverage and mutation-score floors,
  and runs SpotBugs and NullAway; CodeQL runs on every pull request.

None of that is tool qualification. All of it is the evidence a
qualification effort would have to start from, and it is why the
statement in section 2 is a scope decision rather than an admission.

## 5. Maintenance rules for this document

- The paragraph between the `scope:begin` / `scope:end` markers is the

  `SECURITY.md`, and its first sentence MUST appear in the usage text
  printed by `jls -h`. `test/jls/IntendedUseScopeTest.java` enforces this.
- Standards MUST be named without revision years here, so the text does
  not go stale as those documents are revised. Revision detail belongs
  in `docs/standards-landscape.md`.
- This document MUST NOT state restrictions on use ("you may not…"), only
  facts about what this project has and has not done. GPLv3 section 7
  forbids adding further restrictions, and a scope statement is not a
  licence term.
- Reversing section 2 requires the conditions in
  `docs/standards-landscape.md` §12.a to have changed materially, and a
  recorded decision in `ARCHITECTURE.md` — not a pull request.
```

#### Part B — what qualification would concretely require (the costed rejection)

Walked as a procedure so the size is legible, not as a survey. Assume the
narrowest useful scope: **batch simulation and HDL export only**
(`jls -b`, `-t`, `-vcd`, `-export`), headless, no GUI — because the GUI
is unqualifiable in any reasonable budget and because the headless core
is already boundary-enforced (`test/jls/HeadlessCoreRatchetTest.java`).

**B1. Tool classification, performed by the customer.** The safety
project determines TI/TD → TCL (ISO 26262-8 cl. 11), or T1/T2/T3 (IEC
61508-3 §7.4.4), or tool criteria → TQL (DO-330 §12.2 of DO-178C). JLS's
plausible worst case: a design-entry tool whose HDL export feeds
synthesis → TI2, and TD depends entirely on whether the customer
independently verifies the netlist. With good downstream verification,
TD1 → TCL1 → **no qualification needed**. Without it, TCL2 or TCL3.
*The single highest-value engineering contribution this project could
make to a safety user is therefore not qualification at all: it is
making the customer's TD argument easy* — which is what the VCD export,
the goldens, and the Verilog/VHDL round-trip validation
(`test/jls/hdl/IverilogCompileTest.java`, `GhdlCompileTest.java`)
already do.

**B2. Choose a qualification method** (ISO 26262-8 cl. 11 tables).
Four routes, and only one is open:

- *Increased confidence from use* — requires documented field data for
  an **unchanged version** used in a comparable context, with a
  systematic record of anomalies. JLS releases often and has no field
  anomaly database. **Closed today; the cheapest to open** (it needs a
  version freeze and a disciplined problem-report log, not a QMS).
- *Evaluation of the tool development process* — requires the
  development process to be assessed against a recognised standard
  (ISO 9001 / Automotive SPICE, landscape #237/#241). No QMS exists.
  **Closed.**
- *Validation of the software tool* — a validation suite demonstrating
  the tool meets its specified requirements, including behaviour under
  anomalous operating conditions. **This is the realistic route** and is
  what B3–B6 cost out.
- *Development in accordance with a safety standard* — build the tool
  itself to ISO 26262-6 / DO-178C rigour. **Closed**; this is a rewrite,
  and the project explicitly rejects rewrites.

**B3. Tool Qualification Plan.** Names the scope, the TCL/TQL claimed,
the lifecycle data to be produced, the configuration-management and
problem-reporting processes, and the verification independence. Roughly a
DO-330 TQP or an ISO 26262 qualification plan. This document does not
exist in any form in the tree and has no analogue: `CONTRIBUTING.md` is a
contribution guide, not a lifecycle plan.

**B4. A requirements specification for the tool.** This is the single
largest gap and the one most easily underestimated. JLS has excellent
*behaviour specifications* — `docs/simulation-semantics.md`,
`docs/batch-interface.md`, `docs/file-format.md` — written *from the
implementation*, with code anchors, by design. Qualification needs the
opposite direction: numbered, atomic, verifiable **tool requirements**
("TR-041: given a test-vector line …, the simulator shall drive input pin
P at time T with value V"), from which the implementation and the tests
are both derived, with a bidirectional traceability matrix. Converting
those three documents into ~400–800 numbered requirements is mechanical
but not cheap, and it changes their character: the "written from the
implementation" property that makes them trustworthy today is exactly
what a qualification auditor rejects.

**B5. A validation suite traced to those requirements.** Every
requirement needs at least one requirements-based test case, plus
robustness cases (invalid, out-of-range, and hostile inputs) and, at the
higher TQLs, structural coverage evidence at statement / decision / MC-DC
level over the tool code. What exists:

| Have | Counts as | Gap |
|---|---|---|
| `test/jls/BatchSimulationGoldenTest.java`, `SequentialGoldenTest.java`, `ElementSimulationGoldenTest.java`, `VcdExportGoldenTest.java`, `RiscvCpuGoldenTest.java` | strong behavioural evidence | behaviour-based, not requirement-traced |
| `test/jls/hdl/VerilogExportGoldenTest.java`, `VhdlExportGoldenTest.java`, plus `IverilogCompileTest.java` / `GhdlCompileTest.java` (external-tool cross-checks, skip when absent) | independent-oracle evidence — genuinely valuable | tool presence is optional, so the evidence is not guaranteed per-run |
| `test/jls/UntrustedFileHardeningTest.java`, `ContainerMutationFuzzTest.java`, `GenerativeRoundTripFuzzTest.java` | robustness / anomalous-input evidence | not traced to requirements |
| JaCoCo floors in `pom.xml` (`coverage-ratchet` execution) | structural coverage measurement exists | bundle floors, not per-requirement; no MC-DC; `jls.edit` deliberately unfloored |
| PIT floors `mutationThreshold` 80 / `testStrengthThreshold` 82 (`pom.xml:812-813`, `.github/workflows/mutation.yml`) | test-strength evidence stronger than most qualified tools publish | scoped to `jls.sim.*`, `jls.BitSetUtils`, `jls.Util`, `jls.SpatialIndex`, `jls.collab.op.*`; weekly, not per-PR |
| the `@jls.testedby` Javadoc tag — **876 occurrences** in `src/`, registered as a custom tag in `pom.xml:559` and doclint-gated | the closest thing in the tree to a traceability matrix | traces *code → test*, not *requirement → test*; an auditor needs the latter |

**B6. Tool Operational Requirements / safety manual.** The document that
tells the qualified user exactly how the tool may be used: the qualified
version, the qualified environment (which JDK build, which OS — note that
JLS's floor is "current LTS, revisited each LTS cycle" per `pom.xml:41-43`,
i.e. deliberately *moving*), the operational constraints, the inputs
outside the qualified envelope, and **a maintained list of known errors
with workarounds**. That last item is a standing obligation: every
confirmed bug must be classified for safety impact, published, and
communicated to users of the qualified version, for as long as the
certificate stands.

**B7. Configuration management and problem reporting of record.** Git
history and GitHub issues are not, by themselves, a CM plan; the auditor
wants a written plan, baselines, change control with impact analysis, and
a problem-reporting process with defined severity classification and
closure criteria. The repo has strong *mechanisms* (reproducible builds
`docs/reproducibility.md`, provenance attestations, SemVer, a detailed
`CHANGELOG.md`) and no *plan document*.

**B8. Verification independence.** DO-330 at TQL-1..3 and ISO 26262 at
higher ASILs require independence between the people who develop and the
people who verify. **A single maintainer cannot provide this at any
budget.** This is not a cost, it is a structural disqualification, and it
is the reason B2's "validation" route also eventually stalls at the
higher levels.

**B9. Assessment by a body.** Engage TÜV SÜD, TÜV Rheinland, TÜV NORD,
exida, or SGS-TÜV Saar. Typical sequence: kick-off and gap analysis →
concept/plan review → document review of the full qualification kit →
(for the process route) an on-site or remote process audit → findings and
rework cycles → certificate for a named version, with a defined validity
period and surveillance conditions. See "Certification / conformance
procedure" for what I could and could not verify about cost and time.

**B10. The forever-after obligation.** Every subsequent release requires
impact analysis against the qualification, regression of the validation
suite with traceability updated, an updated known-error list, and — for
anything but the most trivial change — re-assessment. On a project whose
whole release model is "push a `v*` tag and CI publishes"
(`.github/workflows/release.yml`), this replaces a 20-minute release with
a multi-week one, permanently.

#### For (a): how the scope statement is proven, not believed

**Golden-file strategy.** Deliberately **none**, and that is the design

**Property / fuzz opportunities.** None that are honest. The subject is a

the shipped text; dropping the README Documentation-list link. Every one
of those is a real way this decays, and each is caught at `mvn verify`
rather than by a user discovering an inconsistency.

#### For (b): what a qualification test suite would have to look like

Recorded so the difference is legible, not as work to do. The existing
suite would have to be re-presented as: a requirements register (B4)
with stable IDs; a bidirectional trace matrix requirement ↔ test ↔ result,
generated as a build artifact and archived per release; per-requirement
pass/fail evidence rather than a suite-level green; structural coverage
reported against the requirement set with justification for every
uncovered branch; robustness cases derived from the requirements rather
than from fuzzing intuition; and a review record for the tests
themselves, performed by someone other than their author. The mechanical
parts of that are within reach of this repo's infrastructure (the
`@jls.testedby` tag plus a generator could produce a trace matrix). The
non-mechanical parts — the requirements register and the independent
review — are not.

### Certification / conformance procedure

#### (a) The scope statement: self-asserted, no external body, full stop

There is **no registry, no accreditor, no regulator, and no fee**. Nobody
issues a "not safety-qualified" certificate; the assertion is the
publication. No cost, no validity period, no renewal.

What separates a credible self-assertion from boilerplate:

1. **Located where the claim is checkable.** In-tree, at a stable path,
   under version control, present at every release tag — so "as of
   v5.x.y, the project stated X" is verifiable years later.
2. **Present in the artifact, not only in the repo.** `jls -h` carries
   the sentence, so someone with only the jar can see it. This is the
   single largest credibility difference between this and a README
   paragraph.
3. **Specific.** It names the actual regimes and the actual missing
   artifacts (no qualification plan, no TOR, no known-error list). A
   generic "not for critical use" tells a safety engineer nothing.
4. **Non-contradicted.** Nothing else the project publishes may imply
   suitability. This is why A8 (updating the landscape survey) is part
   of the work and not optional housekeeping.
5. **Mechanically enforced.** The drift test means the statement cannot
   silently rot out of one of its homes.
6. **Paired with positive evidence.** §4 of the drafted document lists
   what JLS *does* guarantee. A scope statement that only says "no" reads
   as a project hedging; one that says "no, and here is the determinism,
   specification, and reproducibility evidence for your own evaluation"
   reads as a project that understands the question.

Publication steps, in full: merge the pull request; the statement is live
on GitHub immediately and ships in the next release jar and installers.
The "evidence package" is the release tag plus the existing provenance
attestation, which already binds the published bytes to a commit.

#### (b) Qualification: who assesses, and what it costs

**Who.** For ISO 26262 and IEC 61508, a functional-safety assessment body
— TÜV SÜD, TÜV Rheinland, TÜV NORD, exida, SGS-TÜV Saar are the names
that appear on EDA and compiler tool certificates. For DO-330/DO-254 the
mechanism is different: there is no "DO-330 certificate" issued by a
standards body; **tool qualification data is submitted as part of an
applicant's certification package to the FAA or EASA (or their designees)
for a specific aircraft programme.** A tool vendor can only supply a
qualification kit that an applicant then uses; the tool is qualified *for
that applicant, on that programme, at that TQL*. This distinction matters
and is routinely blurred in marketing: **a tool vendor cannot deliver a
"DO-330-certified" tool the way it can deliver a TÜV certificate.**

**Submission steps** (ISO 26262 / IEC 61508 route): request a proposal
with a defined scope (tool, version, claimed TCL/class, target ASIL/SIL)
→ gap analysis / pre-assessment → concept and plan review → staged
document review of the qualification kit (plan, requirements,
validation report, traceability, TOR/safety manual, known-error list,
CM and problem-reporting evidence) → findings and rework rounds →
final report and certificate naming the tool version, the qualified
environment, and the constraints of use.

**Cost and elapsed time — I could not verify any published figure.**
These bodies quote per engagement and do not publish fee schedules; I
found no primary source I am willing to cite a number from, and I am not
going to invent one. What can be said without inventing anything:

- The assessment fee is **not** the dominant cost in any account of these
  programmes. The dominant cost is the internal engineering effort to
  produce the kit (B3–B7) and the rework cycles against findings.
- The obligation is recurring, not one-off (B10), so the relevant figure
  is a per-release run rate, not a project total.
- **Anyone taking this seriously should get three written quotes with a
  defined scope before any planning number is used.** Treat any figure
  in this playbook, mine or anyone else's, as a placeholder.

**Validity, renewal, and what invalidates it.** A certificate names a
version. It is invalidated by: any change to the tool (including a bug
fix), any change to the qualified environment (a JDK upgrade — and JLS's
Java floor moves by policy, `pom.xml:41-43`), any change to the
operational constraints, discovery of an unreported error affecting the
qualification argument, and expiry of the certificate's validity period
or lapse of surveillance. *(Unverified: typical validity periods and
surveillance cadence vary by body and scheme; ask the body.)*

**The honest bottom line for JLS.** GPLv3 sections 15–17 disclaim all
warranty, and this project offers no support contract. A qualification
certificate whose backing is "a volunteer maintainer, no warranty, no
liability" is not something a customer's safety case can rest on even if
the paperwork were perfect. **The certificate would be theatre. The scope
statement is the truthful artifact.**

### Effort, risk, and failure modes

#### (a) Sizing: 1–3 maintainer-days

Reasoning, by piece:

| Work | Days |
|---|---|
| Draft `docs/intended-use.md` (text above is ~90 % of it; the remainder is issue numbers and cross-links) | 0.4 |
| README section + Documentation bullet, SECURITY section | 0.2 |
| `usageText()` line + `docs/batch-interface.md` trailer-line note + CHANGELOG | 0.2 |
| `test/jls/IntendedUseScopeTest.java` (7 assertions; the marker-extraction helper and whitespace normalisation are the only real work; `ExtensionPointCatalogTest` is the template) | 0.6 |
| `ARCHITECTURE.md` recorded decision | 0.2 |
| `docs/standards-landscape.md` §12.a/§13 updates | 0.2 |
| Review, wording iteration, `mvn verify` cycles | 0.5 |

Call it **1.5 days of focused work, 3 if the wording gets argued**. The
wording is the part that expands; the code is trivial.

#### (b) Sizing: not days — a programme, and a structurally blocked one

If forced to number it for the narrowest scope (batch + HDL export, IEC
61508-3 T3 or ISO 26262 TCL2 via the validation route): **150–300
maintainer-days for a first qualification, plus 10–30 per release
thereafter, indefinitely.** That estimate is soft and derived from the
work breakdown in B3–B7 (the requirements register alone — converting
three behaviour specs into several hundred numbered, atomic, traceable
requirements and then tracing every existing test to them — is the bulk
of it), not from a comparable engagement I can cite. Treat it as an
order-of-magnitude statement whose only real job is to make clear this is
100× the scope statement, not 3×.

And it does not matter, because **B8 (verification independence) and the
absence of a QMS are not purchasable with maintainer-days on a
single-maintainer project.**

#### Top 3 ways (a) goes wrong

1. **It drifts into warranty language and starts doing legal work it is
   not qualified to do.** The temptation is to write "the maintainer
   accepts no liability for…" — which adds nothing over GPLv3 §16 and
   invites the reader to treat the whole document as boilerplate to skip.
   *Mitigation:* the drafted text contains no liability language at all;
   it points at `LICENSE` once and moves on. Keep it that way.
2. **It becomes a further restriction and creates a licence problem.**
   "You may not use JLS for X" would be a GPLv3 §7 further restriction.
   *Mitigation:* the A1 maintenance rule forbids it in the document
   itself; a reviewer must check any future edit for the word "may not"
   applied to the user. (The drafted §2 says "do not use JLS as…", which
   is advice, not a licence term — if even that reads as too close to a
   restriction to a reviewer, weaken it to "JLS is not suitable as…".)
3. **It rots in one of its homes.** Four copies of a paragraph is exactly
   the shape of a documentation claim that becomes false.
   *Mitigation:* `IntendedUseScopeTest` — which is why the test is not
   optional polish but the load-bearing half of the deliverable.

A fourth, worth naming: **standards-name drift.** Naming EN 50128 when
EN 50716 has consolidated it, or citing a superseded ISO 26262 edition,
makes the project look like it is guessing about exactly the domain it is
disclaiming. *Mitigation:* assertion 5 of the test bans revision years in
the shipped text, and the drafted statement names EN 50128 **and** EN 50716
so it is right either way.

#### When the project should NOT do (a)

Honestly: there is no condition under which the scope statement itself is
a bad idea. But three conditions under which pieces of it should be cut:

- **If it cannot be test-enforced, cut the mirrors.** A statement in
  `docs/intended-use.md` alone, with no README/SECURITY copies and no
  `-h` line, is worth having. Four unenforced copies are worse than one
  enforced copy — take the single canonical document and the drift test
  and skip the rest rather than shipping copies that will diverge.
- **Do not spread it further than the four homes.** Every dialog, every
  export header, every generated Verilog file preamble — no. It stops
  being information and becomes noise, and each new home is a new drift
  surface.
- **Do not write it as a legal document reviewed by nobody.** If the
  wording debate starts reaching for indemnity, jurisdiction, or
  "warrants and represents", stop and ship the plain-English version;
  this is an engineering scope statement and its audience is engineers.

#### When (b) should be reconsidered

All three of the `ARCHITECTURE.md` revisit triggers simultaneously: a
named funded customer with a specific ASIL/SIL/DAL; a second maintainer
providing verification independence; and a support commitment this
project is willing to make. Any one alone is a reason to *decline
politely and point at `docs/intended-use.md`* — which is precisely the
function the scope statement is there to serve.
