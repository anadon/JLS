# Issue #564: FEAT-C31-2: a truth table's minimized sum-of-products expressions display and export — exact Quine–McCluskey within a stated bound, refused by name above it
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

The direction is real work with no existing implementation (`grep -rin "quine\|mccluskey" src/` and `test/` finds nothing but this issue's own text), it sits on a genuinely existing data model (`src/jls/elem/TruthTable.java`), and the exact-only kill-criterion is a legitimate, non-contradictory scope cliff. But the acceptance criteria have a real specification hole at exactly the place this feature is supposed to be careful — the complexity bound that governs refusal-vs-hang — and one AC (don't-care honoring) has no falsifiable test attached to it at all.

## Findings, most severe first

**1. HIGH — the refusal bound AC-3 depends on is never actually stated, anywhere in the issue.**
Quoted: *"above the stated input/minterm bound it refuses with the complexity named (the exponential prime-implicant growth, stated as arithmetic)"* and AC-3: *"Above the bound the tool refuses by name with the arithmetic, never hangs."* No number, formula, or derivation appears in the Outcome, AC list, or boundary notes — "the stated bound" is asserted to exist but is not present in the text that is supposed to state it. This is a materially harder problem than the sibling issue's bound: FEAT-C31-1 (#563) AC-2 at least names its arithmetic ("2^N rows" — trivial row enumeration). Quine–McCluskey's cost is dominated by prime-implicant count, which for worst-case functions grows like O(3^n/n), not by a simple row count; whether the same N as #563's table-size bound is reused, or a separate (necessarily much smaller) N is required for the minimizer to stay non-hanging, is left for the implementer to invent. The issue also conflates two different quantities — "input" bound and "minterm" bound — without saying which one is the actual refusal trigger. **Recommendation:** state the actual bound (a number or a formula in N) and which quantity it's measured over (input count, minterm count, or worst-case prime-implicant count) before this is pickup-ready; an implementer who invents their own threshold cannot be judged against an unstated one.

**2. HIGH — AC-2 ("don't-care rows are honored") has no test criterion and is satisfiable by silently ignoring don't-cares.**
AC-1 is the only criterion with a golden test, and it names a 4-input circuit with no mention of don't-cares. AC-2 asserts don't-cares are "honored" but nothing in the AC list distinguishes an implementation that actually exploits don't-cares to produce a smaller/more general minimized expression from one that treats every don't-care as a fixed 0 (still logically valid, since a don't-care by definition permits either value, but not "honoring" it in any minimization sense). Since `TruthTable.makeDontCare` (`src/jls/elem/TruthTable.java:864-896`) already ships and produces table value `2` for don't-care cells, a reviewer checking this feature has real fixtures to test against — but the issue itself pins no golden case where don't-care exploitation is required to produce a strictly smaller term count than the naive alternative. **Recommendation:** add a golden case (e.g., a 4-input table with a don't-care set chosen so that exploiting it yields fewer literals/terms than not) and assert on the term count, not just functional correctness.

**3. MEDIUM — half the Outcome's stated entry paths has zero acceptance-criteria coverage.**
Outcome: *"A truth table — extracted from a drawn circuit or entered by hand — yields minimized sum-of-products expressions."* AC-1 is the only functional-correctness criterion, and it's phrased as *"golden-tested against exhaustive simulation of the expression vs. the original circuit"* — by construction this only covers the circuit-extracted path, since a hand-entered table has no "original circuit" to golden-test against. The hand-entry path is not a hypothetical edge case either: `TruthTableDialog`/`TruthTableEditor` (`src/jls/edit/`) already ship hand-entry today, independent of any circuit extraction. An implementation could pass every stated AC while being untested (and potentially broken) on hand-entered tables — exactly the case this issue's own dependency-boundary notes flag as consumed most directly. **Recommendation:** add a golden case that starts from a hand-built `TruthTable` fixture (matching the pattern likely already used in `test/jls/elem/TruthTableModelTest.java`) with its expected minimized expression checked structurally, not via a circuit comparison.

**4. MEDIUM — the stated `ordering_after` is stricter than the actual code dependency, creating unnecessary sequencing risk.**
The only listed predecessor is *"FEAT-C31-1 truth-table extraction (its table is this feature's input)"* (#563), which itself sits behind CAP-09's (#306) combinational-subgraph extractor — an open capstone issue with substantial unbuilt scope (formal core: extractor, AIG, CNF, solver, miter). But the actual object this feature needs to consume is a populated `jls.elem.TruthTable` (input/output column names, `int[][] table` with 0/1/2 values) — which already exists and is independently constructible by hand-entry today, with no dependency on #563's circuit-extraction path or #306's cone extractor. Filing this feature as blocked on #563 (and transitively on #306) overstates the real code coupling and risks stalling PF-2's minimizer behind unrelated, much larger capstone work for no technical reason. **Recommendation:** clarify that the minimizer can be built and golden-tested against hand-built `TruthTable` fixtures now, independent of #563/#306's completion; keep the "extracted table is this feature's input" framing for the Outcome narrative but don't let it gate the actual implementation order.

**5. LOW — AC-4's export format is unspecified beyond "plain text at minimum," inviting drift.**
*"Expressions are exportable (plain text at minimum) and the whole path is headless-callable via a batch flag."* No contract for ordering (per-output blocks in what order — `outputNames` order presumably, but unstated), delimiter, or whether one file covers all outputs or one per output. The project is otherwise unusually strict about export stability (`docs/batch-interface.md`'s byte-exact VCD/output-line contracts, pinned by dedicated golden tests) — leaving this format informal is inconsistent with that discipline and means "exportable as text" can be satisfied by almost any ad hoc dump that happens to contain the right substrings. **Recommendation:** pin a minimal textual grammar (e.g., one line per output, `outputName = term + term + ...` in a fixed literal ordering) the way `docs/batch-interface.md` pins the `-t`/watched-element formats.

## What's solid

- **KC-31-1's exact-only scope cliff is correctly bounded and non-contradictory**: it matches CAP-31's own KC-31-1 verbatim, and Quine–McCluskey is a public-domain textbook algorithm — no licensing hazard from building it in-tree, unlike some of the project's HDL-toolchain integrations.
- **The don't-care foundation already exists in the data model** (`TruthTable.makeDontCare`, table values 0/1/2, `src/jls/elem/TruthTable.java:864-919`) — AC-2's premise that don't-care information is available to consume is true today, not aspirational.
- **Headless/export direction fits an established pattern**: the project already ships `-t`, `-i`, `-export`, `-vcd`, `-savetext` batch flags with a documented CLI contract (`JLSStart.FLAGS`, `docs/batch-interface.md`); adding an expression-export flag is a plausible, low-risk extension rather than a new architectural surface.
- **AC-1's golden-against-exhaustive-simulation oracle discipline matches the project's existing test lineage** (`BatchSimulationGoldenTest` and siblings) — the right verification pattern is at least named, even though its coverage is incomplete (see Finding 3).

## Verdict rationale

`needs-rework`: the feature's premise, boundary decision, and export approach are all sound and buildable, but the acceptance criteria leave the two things this issue is specifically supposed to nail down — the complexity bound that separates a correct refusal from a hang, and honest exploitation of don't-cares — unstated and untestable respectively. Both are fixable by editing the AC list before pickup; neither requires re-scoping the feature.
