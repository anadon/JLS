# Issue #850: TASK-C370-5: the spatial index reads the flat state rather than a second copy of it, and its rebuild cost is measured on the way past
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of the ask

A task child of #370 (FEAT-054, flat array runtime state): make `src/jls/SpatialIndex.java` consume the post-flattening columns (or a provably-equivalent view) instead of a second, independently-maintained copy of element position/extent, prove no divergence is possible, and record the rebuild-cost measurement #370 §6 flags as unowned. Four ACs.

## Findings, most severe first

**1. AC-1 and AC-3 contradict each other over whether a cache is allowed to survive.**
AC-1: "no separately maintained copy of element position or extent survives." AC-3: "rebuild cost on the measured fixtures is recorded **before and after**" — which presupposes a rebuildable structure still exists *after* the change, since you cannot measure the rebuild cost of a structure that AC-1 just deleted. Looking at the actual file (`src/jls/SpatialIndex.java:50-52`), the thing being rebuilt is precisely `cells` (grid→element multimap) and `indexed` (`Map<Element, Bounds>`, a snapshot of each element's bounds captured at index time) — the javadoc even calls this "deliberately forgiving about staleness" (lines 26-31) and describes `rebuild()` as the recovery mechanism. That `indexed` map *is* "a separately maintained copy of element position or extent" by the plain reading of AC-1. A spatial grid index cannot function without some cached bucket structure — eliminating it entirely turns every query back into the O(N) scan the class exists to avoid (see its own javadoc: "turns O(S x N) drag work into O(S)"), which would trip #370 invariant 3 ("editor per-edit cost … outranks the capacity gain … refused, not traded"). As written, an implementer can either (a) keep the cache and just source its initial values from the columns — technically "derives from the columns" while still being exactly the pre-existing copy-kept-in-step design AC-1 claims to forbid, or (b) take AC-1 literally, gut the cache, and regress editor responsiveness, failing #370's own veto invariant. Both readings are available; neither is obviously wrong under the text as given. **Recommendation:** AC-1 needs to say explicitly what class of "copy" is forbidden — e.g., "no cache of bounds may exist without a change-triggered invalidation path a test enforces" — and reconcile with AC-3's own premise that a rebuildable structure survives.

**2. AC-4 cites a ratchet test that does not cover the file this task modifies.**
`test/jls/HeadlessCoreRatchetTest.java` walks `CORE_FILES = {Circuit.java, FileAbstractor.java, LoadError.java, BitSetUtils.java}` plus `CORE_PACKAGE_PREFIXES = {src/jls/sim/, src/jls/elem/, src/jls/hdl/, src/jls/module/, src/jls/core/}` (lines 61-79). `SpatialIndex.java` lives at `src/jls/SpatialIndex.java` — not in `CORE_FILES`, and not under `src/jls/core/` (it's directly in `src/jls/`). `isCoreCandidate()` (lines 133-143) therefore returns `false` for it: the ratchet never inspects this file at all. #370 invariant 5 specifically names the spatial index as "a likely offender" for re-importing a graphical toolkit during exactly this kind of refactor, and #850 leans on "HeadlessCoreRatchetTest green" as its headless-safety criterion — but that test structurally cannot catch a regression in the one file this task touches. Passing AC-4 proves nothing about SpatialIndex's own headless cleanliness; it only proves the rest of the ratchet baseline didn't move. **Recommendation:** either add `SpatialIndex.java` to `CORE_FILES` (or move it under `jls.core`) as part of this task, or state a separate, explicit assertion that it stays free of `java.awt`/`javax.swing` imports.

**3. The stated prerequisite has not landed — there is nothing to migrate to.**
`ordering_after: ["TASK-C370-3 (there is no flat state to read until the migration lands)"]` names #846. Verified: #846 (TASK-C370-3) is **open**, as is #843 (TASK-C370-2, which introduces the dense index + column store #846 depends on). Confirmed directly in the tree: `src/jls/Circuit.java:48` is still `private Set<Element> elements = new HashSet<Element>();` — the pre-flattening object-graph representation, unchanged. So AC-1's "derives from the columns" has no columns to derive from yet, and the task's own acceptance criteria cannot be evaluated against real code today. That's expected and even disclosed by the issue — but note the discipline gap: unlike #370, which encodes ordering as a machine-checked `blocked_by`/`blocks` DAG walked and verified in the parent issue's own text, #850 encodes its prerequisite only as a prose string inside a YAML block with no `blocked_by` field and no enforcement. Nothing stops this task from being picked up and merged before #846 lands, other than a human reading the sentence. **Recommendation:** add a real `blocked_by: [846]` (mirrored on #846 per #370's own convention) rather than prose.

**4. The formally-verified proof bridge is not named in scope, and this task is exactly the kind of change that can break it.**
`src/jls/SpatialIndex.java`'s javadoc (lines 33-38) states that query correctness is "machine-checked: THEOREM 1 (query-parity) in `proofs/SpatialIndexCorrectness.agda`, whose modelling assumptions (interval clamping, floorDiv monotonicity, the boundsTouch formula) are pinned to this class by `jls.ProofBridgeTest`." `test/jls/ProofBridgeTest.java` pins `SpatialIndex.CELL` and `boundsTouch` by reflection (`getDeclaredField`, `getDeclaredMethod`) and loads real circuits via `SpatialIndexTest.loadWired()`. A change to how bounds are sourced (columns/view vs. the current `indexed` snapshot) is precisely the kind of internal restructuring that risks breaking those pinned assumptions or the reflective hooks — yet none of AC-1 through AC-4 mentions `ProofBridgeTest` or the Agda proof. AC-4 only names golden-corpus identity and the (non-covering, per finding 2) headless ratchet. A change that satisfies all four stated ACs could still silently invalidate the formal proof's premises. **Recommendation:** add an AC requiring `ProofBridgeTest` green and, if the modelling assumptions change, an update to `SpatialIndexCorrectness.agda` with re-verification.

**5. AC-3's "rebuild cost … recorded … committed as data" has no declared methodology, and the measurement gate it should route through is itself unbuilt.**
#370 is explicit that ungoverned measurements are the failure mode it wants to avoid ("a measurement that does not answer the question," §6), and makes FEAT-009/#335 ("every wall-clock claim in the plan divides by a measured constant") a hard prerequisite for exactly this kind of number. #335 is open (confirmed via #370's own "Related issues" list: "#335 (open) — … Hard prerequisite. Without it the band is a guess"). #850 doesn't cite #335, doesn't say what "the measured fixtures" are (the same fixtures as TASK-C370-1/#842? new ones?), and doesn't say whether the number must be taken above or below the ~165,000-element load-path wall #370 §6 describes as the threshold for a meaningful measurement. As worded, "before and after… committed as data" can be satisfied by any two numbers on any fixture the implementer picks, which is exactly the "surprise during close-out" #370 says this task exists to prevent. **Recommendation:** name the fixture(s) and cite the measurement method (or explicitly note #335 is not yet a hard dependency here and say why).

**6. Minor: AC-4's "golden corpus byte-identical" doesn't name which suite.**
ARCHITECTURE.md's test layout lists `BatchSimulationGoldenTest`, `SequentialGoldenTest`, `VcdExportGoldenTest` as "the oracles the normative docs cite." #850 says only "golden corpus byte-identical" with no test class named, unlike AC-4's other half which does name `HeadlessCoreRatchetTest` explicitly. Low cost to fix, worth doing for a checklist that's meant to be mechanically verifiable.

## What's solid

- The scope match to #370 is accurate: #370 §6 does name the spatial-index rebuild as unowned and recommends re-homing it into FEAT-005, and #850 quotes that correctly.
- AC-2's "mutate state, assert no explicit sync call needed" is a genuinely good test design for proving invariant 4 (no discipline-maintained second copy) — assuming finding 1 is resolved so it's clear what's being asserted against.
- The task correctly identifies `SpatialIndex.java` as one of the two direct-read paths #370 §1/§4 names (the other being the editor, covered by sibling task #851).

## Verdict rationale

Two of the four acceptance criteria are in unresolved tension with each other (finding 1), one cites a test that structurally can't verify what it's asked to verify (finding 2), and a formally-verified component this exact change is likely to touch is absent from scope entirely (finding 4). These are fixable without re-scoping the task, but the AC text needs another pass before an implementer can execute it without inventing the missing decisions themselves. The sequencing gap (finding 3) is disclosed and not fatal, just under-enforced.
