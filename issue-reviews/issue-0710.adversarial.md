# Issue #710: TASK-C528-3: externalGrader contract drift turns the PrairieLearn lane red, and the question-kit README runs as CI doc-test steps
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of the ask

TASK-C528-3 is the third of three tasks decomposing FEAT-C21-4 (#528, PF-4 of
capstone CAP-21 / #502): a dedicated, hermetic CI lane that (a) pins
PrairieLearn's documented `externalGrader` contract version and fails by name
on shape drift, and (b) executes the question-kit README's steps as CI
doc-tests. `ordering_after: ["TASK-C528-2"]` (#708). Confirmed against the
repo: no file mentions PrairieLearn or `externalGrader` anywhere
(`grep -rli prairielearn .` outside `issue-reviews/` is empty), and none of
the CI lane, the image, or the question kit exists yet — this is greenfield
work sitting at the bottom of an unlanded four-issue chain.

## Findings, most severe first

**1. (High) The hermeticity requirement and the "contract drift turns the lane red" framing are in direct tension, and the issue never reconciles them.** AC-3 requires "no PrairieLearn account, no network call to a PrairieLearn service." But the *only* way this lane could observe PrairieLearn actually changing its contract is a network call to the real service (or an updated fixture a human pulled from PrairieLearn's docs after noticing a change). With both forbidden, the lane can only ever fail on a JLS-side regression against a fixture the maintainer already pinned — it cannot detect drift that has not yet been noticed and hand-encoded. The issue title and outcome text ("contract drift turns the PrairieLearn lane red") read as if the lane is a live drift sensor; by construction (per its own AC-3) it is not one. This is the same gap #531's review flagged at the capstone level (finding 5, "hermeticity forecloses the only real correctness check") recurring here at the task level, but #710 states its purpose in language ("contract drift turns the lane red") that overpromises relative to what a hermetic lane can deliver. **Recommendation:** rewrite the outcome/AC-1 to say what the lane actually does — "fails when the adapter's emitted/expected shapes diverge from the last-pinned documented contract" — and separately record (as #531 finding 5 recommends for the capstone) that real vendor drift requires an out-of-band, non-hermetic revalidation step this task does not provide.

**2. (High) AC-2 depends on an artifact — a question-kit README with doc-testable steps — that no filed task in this chain commits to producing.** AC-2: *"The question-kit README's steps execute as doc-tests in that lane, end to end (CAP-21 AC-5)."* TASK-C528-2 (#708), the task this issue is `ordering_after`, has four acceptance criteria and none of them mention a README: the kit must be committed and produce native-format results, emit scores in the shared parity-vector form, work against a lab-as-data lab with no lab-specific code, and express partial credit without adapter-side invention. TASK-C528-1 (#706, the image) likewise names no README. As written, #710 is the first (and only) issue in the TASK-C528-* cluster that mentions a README at all, yet it is not the task that authors one — its boundary line explicitly says "the kit is TASK-C528-2." An implementer picking up #710 alone has no upstream deliverable to doc-test against unless they also silently expand #708's scope (or their own) to write the README first. **Recommendation:** add an explicit README-authoring acceptance criterion to #708 (TASK-C528-2), and have #710 state it consumes that artifact rather than assuming it exists.

**3. (Medium) AC-1's citation of KC-21-3 is a mismatch.** AC-1 reads: *"...fails with a named error when a shape mismatch is detected (CAP-21 risk 1 / KC-21-3)."* CAP-21 risk 1 fits ("adapters must live in dedicated CI lanes... drift surfaces as a red lane"). KC-21-3, quoted directly from #502, is a kill criterion about a different failure mode entirely: *"If keeping an adapter green requires tracking an **undocumented** platform interface, drop the adapter."* That is a decision to abandon an adapter when the only way to stay green is scraping undocumented behavior — it says nothing about how a documented-contract shape-mismatch should fail, and it is not a specification an implementer can build a "named error" mechanism against. Citing it here reads as reaching for capstone-level authority the clause doesn't actually supply. **Recommendation:** drop the KC-21-3 citation or replace it with the correct anchor (risk 1 alone, or #524 AC-5's "adapter can refuse an incompatible build with a named error," which is the actual mechanism this task would be building on).

**4. (Medium) The three-way failure classification (AC-4) names no verification mechanism and is easy to satisfy without being true.** AC-4: *"The lane's failure output distinguishes contract drift from an adapter mapping fault from a JLS-side contract change."* This asks the lane to correctly attribute root cause across three distinct failure domains — PrairieLearn's spec moving, a bug in this adapter's own JSON mapping, and #524's CLI contract itself changing underneath it — but states no test that checks the *correctness* of that attribution, only that "the failure output distinguishes" them. An implementer can satisfy the letter of this AC by printing three different string templates ("PL-DRIFT", "MAPPING-FAULT", "JLS-CONTRACT-CHANGE") selected by which of three hardcoded probes happened to fail, without ever proving the classification is accurate on a case where two failure modes could plausibly produce the same symptom (e.g., a field renamed on both sides at once). This is the identical class of gap #530's review flagged in finding 6 ("no scraping of incidental output... is a code-review-only constraint with no test named"). **Recommendation:** name a concrete verification — e.g. three seeded-fault fixtures (one per failure domain) that the lane must correctly attribute, analogous to #524 AC-2's seeded-violation transcript requirement.

**5. (Medium) `band_mw: 0.5` does not disclose that the task sits at the bottom of a four-deep unlanded chain, repeating a defect the fleet review already caught in three sibling issues.** `ordering_after: ["TASK-C528-2"]` names only the direct predecessor. The real chain is #524 (FEAT-C21-1, open, itself `ordering_after: [369, 466]`, both open and only partially scoped per the #528/#530 reviews) → #706 (TASK-C528-1, open) → #708 (TASK-C528-2, open) → #710. None of `externalGrader`, a PrairieLearn image, or a question kit exists in the tree today. At the task level the 0.5 mw figure is plausibly correct as a *marginal* cost once #708 lands, and is roughly consistent with #502's own "PF-4: 2 mw" line split across #706 (0.5-1) + #708 (0.5-1) + #710 (0.5) ≈ 1.5-2.5 mw — so this is not the same magnitude of understatement as #528's finding 1. But the issue still gives no reader-visible signal that "0.5 mw" assumes three other unstarted issues, one of them itself blocked on an unfiled task (per the #528/#530 reviews' finding 1), have already landed. **Recommendation:** one line noting the estimate is marginal-only, contingent on #706/#708/#524 landing, matching the discipline #369/#466 already apply to themselves.

**6. (Low) Possible duplicate-ownership of contract-version pinning with TASK-C528-1.** #706's AC-4 already requires "the image's entry point conforms to PrairieLearn's documented externalGrader input/output locations, with the pinned spec version recorded alongside it." #710's AC-1 separately requires "a dedicated adapter lane pins the externalGrader contract version." It is not stated whether #710 is meant to re-assert the same pin #706 already recorded (redundant) or introduce a second, independent pinning point that could drift out of sync with #706's (a consistency hazard of its own). **Recommendation:** state explicitly that #710's lane reads/enforces the version #706 recorded rather than maintaining its own copy.

**7. (Low) "named error" is undefined.** Both AC-1 here and #524's AC-5 use the phrase "named error" without a shared definition (exception class? stderr message format? exit code?). Given `ARCHITECTURE.md`'s documented CLI contract (`jls: error: ...` on stderr, exit codes 0/1/2) is the closest existing precedent and this task's failure surface is a *CI lane*, not the `jls` binary itself, it is unclear whether "named error" here means matching that existing convention or inventing a new one scoped to the adapter's own tooling. **Recommendation:** one clause pointing at the convention this should follow.

## What's solid

- The boundary line ("Guards and doc execution; image and kit are TASK-C528-1 and TASK-C528-2") is clean and matches the sibling tasks' boundary statements — no scope creep into image or kit territory.
- AC-3's hermeticity requirement itself (no account, no network call) is consistent with CAP-21 risk 1's no-toolchain-matrix / dedicated-lane discipline and with #531's fixture design at the capstone level.
- The core shape — a dedicated lane rather than an entry in the core CI matrix — correctly inherits CAP-21 risk 1 verbatim rather than reinventing it.

## Note

Findings 1 and 4 both stem from the same root cause: the issue states outcomes ("drift turns the lane red," "distinguishes failure causes") in stronger language than a hermetic, no-live-service design can actually deliver or than any named test can check. Fixing the wording to match what a pinned-fixture lane can prove, and naming concrete seeded-fault verification for the three-way classification, would resolve both without changing the task's scope.
