# Issue #704: TASK-C535-2: a canvas click adds the signal in an external viewer and the viewer's cursor moves JLS's time — one way only, and absent the viewer nothing is lost
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

TASK-C535-2 decomposes the viewer-sync half of FEAT-C23-6 (#535), itself a
planned feature of capstone CAP-23 (#504). The issue is honest about its own
precariousness — it opens by quoting #508's product review recommending the
scope be cut and gates funding on a REPLAN that has not landed. That
self-awareness is good, but it doesn't substitute for engineering grounding:
the task commits to a live network/IPC client and a CI-scriptable test
against a third-party GUI application without reconciling either against
concrete, already-in-tree constraints this repository enforces with
build-failing tests.

## Findings, most severe first

**1. (HIGH) The task's core mechanism is not reconciled with `SocketConfinementRatchetTest`, a build-failing ratchet that confines all socket/channel construction in JLS to `src/jls/collab/net/`.** `test/jls/SocketConfinementRatchetTest.java:35-83` scans every file under `src/` for `new Socket(`, `new ServerSocket(`, `SocketChannel.open`, etc., outside `src/jls/collab/net/` and fails the build if any are found — "socket construction outside jls.collab.net; the network surface must stay confined (issue #168)." `SECURITY.md:142-146` states the rationale directly: "The socket transport ... is the only code in JLS that constructs a socket, and it lives under `jls.collab.net` and nowhere else ... along with the rule that nothing under `jls.collab` ever touches Java object serialization." A client that talks to "Surfer over its remote-control protocol" almost certainly needs some live-process transport (TCP/WebSocket/Unix socket) to reach an already-running external viewer, and `jls.collab.net` is explicitly the peer-to-peer collaborative-editing session-security foundation (Ed25519 identity, SIGMA handshake, SAS verification) — not a generic place to route unrelated third-party-tool traffic. The issue names none of this: not where the client's networking code is meant to live, not whether the ratchet's allowlist is meant to grow, not whether a different transport (e.g. a local file/command-poll loop, avoiding sockets entirely) is intended instead.
**Recommendation:** state explicitly which transport the client uses and where its code lives relative to `ALLOWED_PREFIX`; if it needs a socket outside `jls.collab.net`, say so and treat widening that ratchet as an explicit, reviewed acceptance criterion rather than a silent build break waiting to happen at implementation time.

**2. (HIGH) AC-1's CI-scriptable `ViewerSyncTest` contradicts the project's own recorded finding that Surfer cannot be automated headlessly.** `docs/standards-adoption/07-waveform-formats.md:394-396`: "Surfer has no headless verification mode I am aware of, so Surfer stays a manual check — which is already the documented posture (`VcdExportGoldenTest`'s class Javadoc says 'GTKWave/Surfer validation stays manual, outside CI')." AC-1 requires "a scripted session against the pinned viewer version verif[ying] add-signal from a canvas click and JLS time-follow from a viewer cursor move" with no discussion of how that squares with the existing manual-only posture, and no fallback (protocol-level mock, a documented once-per-release manual checklist in the `docs/wayland-desktop-checklist.md` style) is proposed. This is the same gap the sibling feature #535 was already flagged for (issue-reviews/issue-0535.adversarial.md finding 3) and it survives unaddressed into this task's own concrete AC.
**Recommendation:** either verify and record that Surfer's remote-control channel is scriptable without a display (distinct from "headless verification" of rendered output, which is what the cited passage is actually about) before committing to AC-1 as a CI gate, or scope AC-1 down to a protocol-level test against a stub/mock server, with real-Surfer verification demoted to a manual release-cadence check.

**3. (MED-HIGH) The task is filed as concrete, implementation-ready decomposition for a scope its own parent chain has not confirmed will be funded.** CAP-23 (#504) Open Question 2 — the question this task's design directly answers ("Surfer via its remote-control protocol, pinned by version") — is explicitly tagged "**Blocks PF-6's filing**." #504's own filing-pass comment (2026-08-04) records: "#508's funded CAP-23 wedge covers only the chronogram slice and the cause-chain inspector — it recommends cutting the PF-6 viewer-sync scope... Filed anyway per today's directive; adopting the cut requires a REPLAN here re-deriving §2's sufficiency argument." No such REPLAN comment exists on #504, #535, or #702 as of this review. #704 nonetheless proceeds two decomposition levels past that unresolved gate, writing task-level acceptance criteria (`ViewerSyncTest`, per-name viewer refusal, once-only degradation reporting) for a scope #508 named as the first candidate to cut — the exact "planning ratchet" pattern #508 itself criticized ("no new tier:feature/tier:task until two capstones close... consumed ~one remediation cycle per planning cycle").
**Recommendation:** hold this task's implementation until #504 records the REPLAN adopting or rejecting #508's recommendation, as the task's own "Recorded before work starts" note already says — but also stop compounding sunk planning cost by decomposing further beneath the unresolved gate.

**4. (MED-HIGH) AC-4's "no path exists from viewer input into simulation state" names no enforcement mechanism, and the repository's own idiom for this exact class of claim is a static/reflective ratchet, not a prose test description.** Compare `HeadlessCoreRatchetTest`, `NotificationRatchetTest`, and `SocketConfinementRatchetTest` (all cited in `ARCHITECTURE.md` or found in `test/jls/`) — each pins a "never happens" claim by scanning source or bytecode for the forbidden pattern, not by testing one call path in isolation. AC-4 as written ("a test asserts no path exists...") could be satisfied by a narrow unit test that checks one specific class never calls one specific method, while a different integration point (a future debug hook, a second listener, a copy-paste of the sync client) reintroduces exactly the callback KC-23-4 exists to prevent, with no red build to catch it.
**Recommendation:** name the enforcement technique explicitly — e.g. a source/bytecode scan (in the `SocketConfinementRatchetTest` idiom) proving the viewer-sync package never calls into `jls.sim`'s value-setting API — not just "a test asserts."

**5. (MED) AC-2 ("refused by name") and AC-3 ("the absence is reported once") are not reconciled for the case of a viewer that is installed, reachable, but the wrong version.** AC-2 implies an active, presumably visible rejection naming the mismatched viewer; AC-3 implies a single, passive notice indistinguishable in tone from "nothing is installed." The issue does not say whether a version mismatch is routed through AC-2's refusal path, AC-3's degrade-and-report-once path, or is a third, undescribed behavior — a real ambiguity given AC-3's explicit promise that "every in-tool debug capability behaves exactly as it does without this task" in the absent case, which is a stronger guarantee than AC-2's bare "refused."
**Recommendation:** state which of the two paths a version mismatch takes, and confirm AC-3's "exactly as it does without this task" guarantee also holds on that path.

**6. (MED) "reported once, not per click" (AC-3) has no defined scope for "once."** Once per JLS process launch, once per chronogram session, once per failed connection attempt, or once per some other window are all different UX outcomes and all satisfy the sentence's letter. A trivial implementation (report on the first click after startup, then silently swallow every later click including a reconnect attempt) would pass a literal reading of AC-3 while behaving unhelpfully the first time a student later installs the viewer mid-session and it still doesn't sync.
**Recommendation:** name the reporting scope precisely (e.g. "once per editor session, reset on the next successful connection attempt").

**7. (LOW-MED) No lifecycle or connection-management contract is specified for what is, functionally, a live peer connection to another process.** Contrast the level of detail the repository's other live external-process integration carries: #63's HDL co-simulation task names a bounded timeout (~5s default), explicit spawn/kill/restart/reap lifecycle, and a crash/handshake-failure surface that stops simulation naming the component with a bounded stderr tail. `jls.collab.net`'s socket listener (SECURITY.md:142-156) is documented down to "runs under a read timeout so a stalled peer cannot pin the accepting thread" and "each handshake message is length-capped before its buffer is allocated." #704 says nothing about how JLS discovers/connects to a running Surfer instance, what happens on a mid-session disconnect (is that AC-3's "absent" path, or an error?), or whether any input from the viewer is length-capped or otherwise hostile-input-hardened before being acted on — a real question given the viewer is, from JLS's perspective, an untrusted external peer sending unsolicited cursor/selection data.
**Recommendation:** add a connection-lifecycle and hostile-input-handling contract at the level of detail #63 and the collab-net listener already establish as this repository's norm for any live external endpoint.

## What's solid (no rework needed)

- AC-4's directional constraint (cursor/add-signal only, never values into simulation) is a good, correctly-cited guardrail against reopening KC-23-4/#498 §7.2/#63.
- AC-5 (GTKWave stays the documented file-handoff path, not replaced) is a sound non-regression clause that prevents this task from quietly obsoleting existing, working documentation.
- The task's `band_mw: 1-1.5` sums with sibling TASK-C535-1's `2-2.5` to `3.5-4`, matching #504's own PF-6 estimate of "3–4 mw" — no arithmetic drift between the capstone, feature, and task levels.
- Scoping the sync surface to exactly two commands (move cursor, add signal) rather than a richer remote-control API is the right minimal-surface instinct, even though findings 1 and 7 show the mechanics of enforcing that minimality are unaddressed.
- Opening with the #508 funding risk recorded plainly, rather than burying it, is good practice and matches this repo's own REPLAN discipline elsewhere.
