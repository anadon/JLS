## Findings

### 1. [HIGH] The issue body's own machine block is stale and contradicts its comments — a live duplicate-work trap
The body's `planned_tasks` YAML and the §2 roster table list TASK-0015/16/17/18 with no issue numbers, and the roster explicitly says `not filed` for all four:
> `TASK-0015 (planned, not filed) | ... | not filed` (repeated for 16/17/18)

But the issue's own comment thread (dated 2026-08-03 and 2026-08-04) records that all four were filed days ago: *"TASK-0015 / #374 ... TASK-0016 / #378 ... TASK-0017 / #406 ... TASK-0018 / #411."* I fetched #374 and #406 directly: both declare `part_of_feature: 317` in their own machine blocks, both are `state: open`, and #406 is `blocked_by: [374]` — internally consistent with #317's plan, just absent from #317's visible body. The Completion Criteria checkbox "`planned_tasks` empty (each resolved to a filed issue or descoped)" is therefore unmet in the text an executor actually reads first.

This is not cosmetic: the whole corpus's coordination discipline depends on the machine block being authoritative ("Do not re-file any of these" appears verbatim in §1), and DAG-walking is done by reading `blocked_by`/`blocks`/`planned_tasks`, not comments. Anyone who reads only the body risks re-filing #374/#378/#406/#411, or worse, planning fresh task numbers that collide with real ones.
**Recommendation:** edit the issue body now — update `planned_tasks`/roster to `#374/#378/#406/#411`, and either check the DoD box or leave it explicitly open with a note pointing at the four child issues.

### 2. [HIGH] TASK-0017 (#406) and the sibling platform features overlap on the same file edits, acknowledged but unresolved
Comment (2026-08-04) states outright: *"#406 and the eight newly-filed per-platform slices (#661–#664, #667–#670) own the same four `ci.yml` edits — drop the job-wide `continue-on-error`, arm the toolchains fail-closed, arm the macOS display suite, remove `-Djacoco.skip=true`. Executing both paths lands them twice."* It calls this "a maintainer call, not a dedup call" and defers resolution to a comment on #406 — but #317's own body (§1 "Overlap with existing issues") only says #265/#111 are "cited rather than duplicated" and never surfaces this specific double-implementation hazard or its resolution.
**Recommendation:** before anyone picks up #406, #667–670, or #661–664 concurrently, the "cheaper reading" decision referenced in the comment needs to land as an explicit ownership statement in #317's own Decomposition table, not only in a comment on a different issue.

### 3. [MEDIUM] TASK-0018's "two GUI check names" is unspecified against a tree that has four GUI-boot lanes, two of which are orphaned
The Background section (§1) only ever discusses `gui-wayland` in depth and frames TASK-0018 as "RESIDUAL ONLY" of that one rig. But the checked-out `ci.yml` (job count matches the issue's own cited "14 jobs" in `ci.yml`) also defines `gui-x11` (already effectively hard-gated — `# HARD GATE since #101 ... this lane went 20/20 green ... now fails CI`, no `continue-on-error` in the job block), `macos-gui` (`continue-on-error: true` at `ci.yml:598`), and `windows-gui` (`continue-on-error: true` at `ci.yml:726`). None of these three is named anywhere in #317's body. I confirmed by reading #406 directly that TASK-0017 explicitly scopes itself to only the `windows`/`macos` *build* jobs, not `macos-gui`/`windows-gui` — and TASK-0018 is scoped to Wayland's two placeholders only. That leaves `macos-gui` and `windows-gui` — both first-light, advisory, un-promoted GUI-boot lanes — with no task in the roster that owns their promotion, even though Capability item 4 ("the display... suites are armed rather than best-effort" on all three platforms) reads as if it covers them.
**Recommendation:** either explicitly descope macOS/Windows GUI-boot-lane promotion to #265/#111 (where `macos-gui` Stage 9 is in fact tracked) and say so in §1's scope boundary, or name exactly which two of the four GUI check names TASK-0018 registers.

### 4. [MEDIUM] Evidence citations are unverifiable from this checkout, and the issue offers no fallback
`evidence_commit: 2d0ca9dcd9db78b36c3caf4c6c57dd8701862cc7` does not resolve (`git cat-file -t` fails) in the local clone, and the cited `docs/plan/evidence/BRIEF.md` (landed at `3a81a4a7d6a0f108ec201e632732d308cc02b3fc`, source of the required-gate's "141 s" baseline in Open Question 2) does not exist anywhere in this repository's tree or reachable history. This may simply be an artifact of a shallow clone (`git rev-parse --is-shallow-repository` → true) rather than a fabricated citation, but that is exactly the practical risk: `actions/checkout` defaults to `fetch-depth: 1`, so an executor working from an ordinary CI checkout — the norm, not an edge case — cannot verify the same evidence the issue asks them to trust, and the Completion Criteria demand "every cited evidence document and permalink resolves on the default branch at close" with no guidance for how to do that from a shallow clone.
**Recommendation:** cite a resolvable permalink (GitHub blob URL, already used elsewhere in the sibling issues) rather than only a bare local commit hash, and note in the issue that verification may require an unshallowed fetch.

### 5. [LOW-MEDIUM] I3's "at least one run measured in hours" is gameable as written
Integration criterion I3 says: *"Trigger the scheduled lane and let it complete → At least one run measured in hours completes end to end... its artifacts are retrievable."* Open Question 1 explicitly leaves the door open for that run to be "one representative run rather than the whole capstone suite." Nothing in I3 ties the representative run's content to actual capstone-acceptance work — a `longrun`-tagged test built purely to sleep for three hours and exit 0 would satisfy I3's literal text (lane exists, is not the required gate, runs for hours, completes, artifacts exist) while validating nothing. The six capstones this feature claims to serve (§ Intended Audience) would gain no real coverage from that pass.
**Recommendation:** tighten I3 to require the representative run be a real capstone acceptance test (name one), not merely a job whose duration is measured in hours.

### 6. [LOW] Cost reconciliation in §5 doesn't cover I2's budget assertion as a line item
Capability item 3 asserts the required gate "stays inside a stated budget" and I2's "Pinned by" column says "A gate-duration assertion in CI... Does not exist; this issue's close-out" — i.e., the budget number and its CI enforcement are owned by #317's own close-out, not by any of the four listed tasks. Yet the cost reconciliation (Open Question 5) sums only TASK-0015 through TASK-0018 to reach the 4.7-week figure; the work of picking B and wiring a budget-violation assertion has no line item and no owner distinct from "this issue," which is unusual for a plan this granular elsewhere.
**Recommendation:** either fold the budget assertion into TASK-0016 explicitly (it is the natural owner, since it already creates the lane split) or give it its own cost line.
