## Findings, most severe first

### 1. CRITICAL — the Outcome's founding claim is false: the simulator does not compute a producer-to-consumer relation anywhere, so there is nothing to "retain"
The Outcome states as fact: *"The simulator computes, for every scheduled event, which event and which element produced it — and throws that relation away the moment the event fires."* This is checkable against the actual data model and it does not hold:

- `SimEvent` carries exactly four fields — `time`, `seq`, `callBack` (the *consumer*), `todo` (`src/jls/sim/SimEvent.java:95-102`). There is no producer field, no parent-event pointer, nothing identifying which prior event or element caused this one to be posted.
- The dominant payload, `PinChanged`, is a **zero-field record** (`SimEvent.java:30-31`): `public record PinChanged() implements Payload {}`. Every `PinChanged` instance is equal to every other one (`SimEvent.equals`, `SimEvent.java:161-172`, delegating to `todo.equals`). It cannot carry a producer identity even in principle without a redesign of the payload itself.
- `Reacts.react(long now, Simulator sim, SimEvent.Payload todo)` (`Reacts.java:27-28`) is the only information a reacting element receives: current time, the simulator, and the payload. It gets no reference to the event that caused the call, so it has nothing to forward when it turns around and calls `sim.post(...)`.
- Every one of the 27 `sim.post(new SimEvent(...))` call sites in `src/jls/elem/*.java` (e.g. `WireNet.java:507`, `Gate.java:708`, `Register.java:768`, `TriState.java:505`, `Mux.java:547`) constructs a brand-new `SimEvent` from scratch — none passes a reference to an upstream event, wire, or pin.

So the "relation" AC-1 asks to "retain" must be **synthesized from nothing** — e.g. by adding a "currently-reacting event" context to `Simulator` that tags every `post()` call made during a `react()` with a parent pointer — which is a materially different, harder design task than "capture a value that already exists before it's discarded." This is not a new observation: the parent feature #532's own adversarial review (`issue-reviews/issue-0532.adversarial.md`, finding 1) already established this exact fact against the identical code. #688 was filed as #532's foundational task and **repeats the same false premise instead of correcting it**, this time as the literal title ("the producer-to-consumer relation... is retained") rather than a background clause.

**Consequence for downstream tasks:** #689 (TASK-C532-2) requires each hop of the rendered ancestor chain to name "the element that fired and the propDelay it consumed" by reading only this task's accessor, and #691 (TASK-C532-3) requires **distinct reconvergent paths** at a fan-in point. A two-input element receiving two `PinChanged` events at the same tick — the exact reconvergence case #691 exists to render — cannot be told apart by `todo` (both are the identical zero-field `PinChanged`) and the element's `react()` re-reads *all* current pin values rather than being told which pin changed. Attribution at the pin level, which #691 needs, is not obtainable from anything #688 as scoped can produce.
**Recommendation:** Rewrite the Outcome to state plainly that producer identity does not exist today and must be added (parent-event context on `Simulator`, and — if #691's per-path claim is to survive — per-pin identity on `PinChanged`, which today has none). Re-cost `band_mw: 1.5-2` against that actual scope, and get #689/#691 to confirm their granularity needs can be met by whatever attribution mechanism is chosen before this task is built.

### 2. HIGH — AC-5's escape hatch cites "KC-23-2" and "before further work" with no test, no gate, and no resolvable referent
AC-5: *"If the bounded window cannot hold the chain for the seeded glitch the analyzer is meant to catch, that is recorded as the KC-23-2 finding and the re-scope to trigger-window retention is raised on #532 before further work."* Two problems:
- `KC-23-2` does not resolve to anything in this corpus. A search across issue bodies for the string turns up nothing that defines it — not an issue number, not a doc anchor. An acceptance criterion that tells the implementer to "record" a finding under an identifier nobody can look up is not verifiable by anyone reviewing the PR.
- Even read charitably as "write a comment citing this label," the criterion has no test backing it — contrast AC-3, which is explicitly test-gated ("a test asserts it names no concrete queue type"). A PR can ship a ring buffer that silently drops part of the seeded glitch's chain, note "KC-23-2" in a comment, and nothing in CI or in this issue's own text would catch or block that. This is the identical non-falsifiable-kill-switch pattern already flagged in #532's own AC-4 (`issue-reviews/issue-0532.adversarial.md`, finding 5) — #688 inherited the pattern rather than fixing it when the responsibility moved down to the task that actually implements the buffer.
**Recommendation:** Fold the condition into whatever test exercises the seeded glitch (see finding 4) so it fails loudly rather than degrading silently, and either link KC-23-2 to a real issue/doc anchor or drop the label and state the re-scope condition in plain prose.

### 3. MEDIUM — no cross-thread contract for a buffer written on the Runner thread and read from the EDT
ARCHITECTURE.md's Threading model is explicit and names exactly this shape of interaction: *"Interactive simulation runs on a dedicated thread (the 'Runner' thread...). Control state shared between the EDT and the sim thread... is `volatile`... UI work initiated from the sim thread is routed through `SwingUtilities.invokeLater`... Follow this discipline for any new sim-thread → UI interaction."* The ring buffer this task builds is populated on every retired event on the Runner thread (via whatever hook #678's tap seam provides) and is read by a chronogram/inspector opened on the EDT (AC-1, AC-2). None of the five acceptance criteria mention synchronization, visibility, or the `invokeLater` routing ARCHITECTURE.md mandates for this exact pattern. "Zero cost when nothing is watching" (AC-2) is a performance statement only — it says nothing about correctness once the buffer is actually being read concurrently with being written, which is the state AC-1's "while enabled" describes.
**Recommendation:** Add an explicit criterion naming the concurrency discipline (e.g., a lock-free or `volatile`-published snapshot-on-read design, or an explicit `invokeLater`-marshaled copy), matching what ARCHITECTURE.md already requires elsewhere in this codebase for sim-thread → UI data flow.

### 4. MEDIUM — AC-4's capacity-derivation basis and AC-5's "seeded glitch" fixture are both unnamed, so the two criteria that most need a fixed test corpus have none
AC-4 requires the default capacity be "a recorded measurement (events retained per simulated tick on the shipped hazard demo)," and AC-5 requires testing against "the seeded glitch the analyzer is meant to catch." Neither the "shipped hazard demo" nor the "seeded glitch" fixture is named anywhere in this issue — no file path, no seed value, no circuit name. Grepping the tree turns up no existing fixture answering to either description (there is no `Chronogram` reference of any kind in `src/` or `test/` yet — this whole feature line is unbuilt). The sibling task #691 has the same gap for its own `CauseChainCompletenessTest` fixture, and #532's review (finding 7) already flagged the identically-shaped problem one level up. A capacity "measurement" and a glitch-retention check both need a pinned fixture to mean anything; without one, "measured, not chosen by taste" (AC-4) is unfalsifiable — any number can be presented as "the measurement" against an ad hoc, unpinned demo.
**Recommendation:** Name the hazard-demo circuit and the seeded-glitch fixture (file path or seed) here, or explicitly inherit them from wherever #532/#691 eventually pins theirs, rather than leaving both open in three related issues simultaneously.

### 5. LOW — the three TASK-C532 siblings' cost bands sum slightly over the parent's own top-line budget
#688, #689, and #691 each carry `band_mw: 1.5-2`, summing to 4.5-6. The parent #532 (FEAT-C23-3) inherits `4-6 mw` from CAP-23's (#504) per-PF costing (quoted directly in `issue-reviews/issue-0532.adversarial.md`, finding 6). The low end of the sum (4.5) already exceeds the low end of the inherited band (4) before any of the three tasks has an actual design (finding 1 above shows #688 in particular is undercosted relative to what "synthesize producer identity from nothing" actually requires). This is a minor discrepancy on its own, but stacks with finding 1's re-costing recommendation.
**Recommendation:** Re-sum the three task bands against #532's inherited 4-6 once finding 1 is resolved and the real design cost for producer-identity synthesis is known.

## What's solid

- The "retention off unless a chronogram or inspector is open" default and AC-2's baseline-matching requirement are a reasonable, testable performance contract, structurally consistent with #678's and #527's "free when closed" pattern for the same feature line.

## Verdict rationale
The issue's central claim — that a producer-to-consumer relation already exists in the simulator and merely needs to be captured before it is discarded — is demonstrably false against the current `SimEvent`/`Reacts`/`WireNet` code, a fact this same review corpus already established one level up (#532) and that #688 was supposed to have absorbed rather than restated as its own title. That single false premise understates both the actual design work (synthesizing causal identity, possibly down to the per-pin level #691 will need) and the cost band. Layered on top: an unfalsifiable escape-hatch criterion referencing an unresolvable "KC-23-2" label, a missing cross-thread contract for a GUI-adjacent buffer in a codebase that documents that discipline explicitly, and two acceptance criteria (AC-4, AC-5) that depend on fixtures nobody has named. None of this makes the eventual feature a bad idea, but the issue as filed would let an implementer build the wrong-granularity mechanism, pass every stated acceptance criterion, and still leave #691 unable to do its job — hence needs-rework rather than should-not-proceed.
