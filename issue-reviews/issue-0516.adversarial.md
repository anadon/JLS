# Issue #516: CAP-32: a prospective user runs a curated JLS example in the browser, read-only, without installing anything — the evaluation-cost gap to web tools closes without JLS becoming a web app
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of the ask

A capstone proposing a read-only, browser-hosted demo of curated JLS example
circuits, deliberately scoped narrower than the refused CAP-19 (#500, closed
`not_planned`). Its own PF-1 (filed as #572) proposes CheerpJ to run the real
Swing GUI in-browser as the primary mechanism, with two ranked fallbacks if
that fails a go/no-go spike. The three PFs are already filed (#572/#573/#574)
and a fourth, share-by-link (#886), was adjudicated in and added on
2026-08-08, the same day this review runs.

## Findings, most severe first

**1. The primary mechanism's core feasibility question is answerable now, without a spike, and the issue never asks it.** `pom.xml:43` sets `<maven.compiler.release>25</maven.compiler.release>` — JLS ships Java-25-targeted bytecode, and #510 touts "JDK 25, sealed dispatch" as a competitive strength. CheerpJ is a from-scratch JVM reimplementation whose supported class-file/language level is a hard, documented ceiling, not a tuning parameter — running unsupported bytecode isn't a "load time and interaction fidelity" measurement, it's a boot failure. Neither #516 nor #572 (its own feasibility-spike issue) mentions checking CheerpJ's supported Java version against JLS's Java-25 target before funding the 1-2 mw spike. This is a hidden assumption load-bearing for the entire capstone: if PF-1's mechanism can't even load the classes, AC-1's "≤15s load, go/no-go" framing implies a nuanced measurement outcome where the real answer may be a same-day desk-check "no." Recommend: a 30-minute compatibility check against CheerpJ's current documented JVM support level, done *before* PF-1 is scheduled, not as its first spike task.

**2. AC-2 ("read-only by construction") is not actually delivered by the chosen primary mechanism, and the issue doesn't notice.** Quoted: `AC-2: The demo is read-only by construction: no save, no upload, no user content`. But PF-1's primary candidate is "CheerpJ-wrapped jar running the Swing GUI" — i.e., the *actual, unmodified* editor: full palette, full mouse/keyboard editing state machine (`SimpleEditor`, `src/jls/edit/SimpleEditor.java`), full undo/redo. Running that GUI in a browser does not make it read-only "by construction" — a visitor can add gates, delete wires, and rewire the circuit; the only thing genuinely prevented is *persisting* the edit (no filesystem to save to). "No user content" is stated as a demo property but the interaction surface as described would let a visitor create user content transiently. Making the demo actually read-only requires either (a) a restricted/read-only mode built into `SimpleEditor` — real engineering the 1-2 mw PF-1 band doesn't budget and that reaches back into the desktop codebase, something #886's own "Open Question 2" flags as a boundary this capstone should avoid crossing — or (b) the issue quietly means "read-only" as "can't be saved out," which is a materially weaker claim than what AC-2 states and what a #38-threat-model reviewer would check for. Recommend: either name the enforcement mechanism (a locked-down mode, a CSS/JS overlay disabling toolbar buttons, etc.) and cost it, or rewrite AC-2 to the claim actually being made.

**3. The kill-criterion fallback path contains an unexamined contradiction with the capstone's own stated rationale for existing.** KC-32-1 binds PF-2 to fallback (a) — "headless-rendered interactive SVG with a JS signal player driven by pre-computed VCD" — "without re-litigating" if CheerpJ fails. But the Outcome statement promises a visitor can "toggle inputs, observe signal trace" on a *running* circuit. A VCD-driven player replays a **pre-computed** trace; toggling an input outside the recorded scenario either does nothing (breaking the "poke" promise the Outcome statement and #886's differentiation from #574 both lean on) or requires a live JS logic evaluator — which is exactly the "second execution strategy" problem CAP-19 was refused over (#500 KC-19-1, #221's sole-discrete-event-interpreter decision), minus the golden-replay conformance harness (#500 PF-4) that CAP-19 built specifically to make that risk tolerable. #516 leans on "this is narrower than CAP-19, so it avoids CAP-19's refusal reason" (correctly, for the CheerpJ path) but never notices that its own binding fallback silently reintroduces the reason it's avoiding, with none of the safety net CAP-19 designed in. Recommend: either bound fallback (a) explicitly to "canned scenario replay, not live interaction" and update the Outcome statement's "poke" language accordingly, or state plainly that a live JS evaluator is in scope for the fallback and give it the same conformance-harness treatment #500 demanded.

**4. A real but unstated licensing/operational dependency: CheerpJ's runtime is a proprietary, dual-licensed product, not "static files."** AC-3 states: `Hosting is static files only; nothing to operate, nothing that can die and take user data with it`. CheerpJ (Leaning Technologies) is closed-source; its free tier historically requires loading a many-megabyte runtime from the vendor's CDN (or a self-hosted mirror requiring its own update/maintenance burden) and carries attribution/branding terms distinct from GPLv3. If the demo pulls the CheerpJ runtime from a third-party CDN, "nothing that can die and take user data with it" is not quite true of the *mechanism* — it's true of JLS's own hosting, but the demo becomes unusable if Leaning Technologies' CDN is unavailable or changes free-tier terms, which is exactly the "permanence" pitch (#510's "anti-simulator.io" framing) this capstone claims to embody. Neither #516 nor #572 mentions checking CheerpJ's license terms for a GPLv3 educational tool's public demo, or the self-hosting option's cost. Recommend: name the licensing check and the CDN-vs-self-host decision as an explicit line item, not an implicit assumption inside "static files."

**5. AC-1's "<30 seconds" is unconditioned and gameable against the audience it's meant to serve.** Quoted: `AC-1: A stock browser on a machine with no JDK reaches a running example in <30 seconds from click.` No cache state, connection speed, or hardware baseline is specified. CheerpJ-style in-browser JVMs are known to have a large first-load payload; a warm-cache/fast-fiber test run could pass while the actual target audience named in the issue's own rationale — "K-12/GCSE and browser-student segments," school Chromebooks on shared Wi-Fi — fails it. This makes AC-1 satisfiable on paper without validating the population it exists to serve. Recommend: specify cold-cache and a stated connection-speed floor (e.g. throttled to a representative school-network profile) as part of AC-1's measurement protocol, matching the rigor #510 uses elsewhere (e.g. the benchmark-publication gate).

**6. Minor: the capstone's own cost accounting is already stale by its own comment thread.** `band_mw: "3-6"` was set 2026-08-04 and reconciled against PF-1+PF-2+PF-3 (2.5-5 mw) in the second coverage-verification comment. #886 (filed 2026-08-08, same day as this issue's last update) lists `serves_capstones: ["CAP-32 #516 ...`]` and bands itself 1-2 mw, which was never folded back into #516's `band_mw` — the total is now 3.5-7 to 4-7, mildly over the declared ceiling with no recorded band revision. Not load-bearing, but the issue's own "Re-planning Protocol" discipline (borrowed from CAP-19/#500's template) would call this a required REPLAN that hasn't happened here.

## What's solid

- The narrowing from CAP-19 (full HTML export, refused) to "read-only hosted demo of curated examples, no export, no accounts" is a genuine, well-reasoned scope cut, and the CheerpJ path (running real JVM bytecode, not a JS reimplementation) legitimately sidesteps CAP-19's specific "second execution strategy" refusal reason for the *primary* mechanism (see Finding 3 for why the fallback reintroduces it).
- The provenance note's self-aware hedge — "If the maintainer judges even this inside the CAP-19 refusal's intent, close this too and the record is coherent" — is honest framing that doesn't presuppose approval.
- KC-32-2's scope cliff ("anything that makes this an editor in the browser is out of scope") is a clear, checkable boundary, correctly anchored to the CAP-19 closure.
- The dependency on CAP-27 PF-2's curated example library (#511 → #548) for demo content is a real and correctly identified sequencing dependency, not scope creep.

## Verdict rationale

`needs-rework`: the capstone's boundary-setting and provenance discipline are sound, but the central technical bet (CheerpJ) has an unaddressed, cheaply-checkable compatibility risk (Finding 1) that should be resolved before funding the spike, and AC-2's "read-only by construction" claim (Finding 2) doesn't actually hold for the chosen primary mechanism as described. Finding 3's fallback contradiction is the most consequential: it means the capstone's binding "no re-litigating" kill criterion could lock in a mechanism that quietly violates the Outcome statement it's supposed to serve. None of these require killing the capstone — they require tightening the acceptance criteria and doing a same-day desk check before the funded spike starts.
