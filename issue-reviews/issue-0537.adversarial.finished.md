# Issue #537: FEAT-C24-2: a drawn circuit becomes CircuiTikZ code that compiles standalone, with every approximation named and a sample document built in CI
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary

This is a well-formed planning-taxonomy stub (feat_id/serves_capstones/band_mw/ordering_after machine block, tied to capstone #505 CAP-24 PF-2) rather than an implementation-ready spec. It is internally consistent with its parent capstone and sibling features, but several of its acceptance criteria reference artifacts and infrastructure that do not exist anywhere in this tree, and at least one AC is testable in a way that would pass while the stated goal (fidelity for real courseware schematics) silently fails.

## Findings, most severe first

1. **AC-1 and AC-2 depend on a fixture — "the hazard-demo circuit" — that does not exist in the repository.** `grep -ril "hazard-demo" .` across the whole tree (including `test/`, `examples/`, `resources/`) returns nothing; the only "hazard" hits are unrelated glitch-hazard comments in `MemoryModelTest.java` and `SimulationSemanticsRegressionTest.java`. Both this issue and its dependency #536 ("Exporting the hazard-demo circuit produces an SVG and a PDF...") and the parent capstone #505 (§1 step 1: "Open the hazard-demo circuit") treat it as an already-agreed shared fixture, but nobody has filed or built it. That's a hidden prerequisite this issue doesn't own or reference by number. Recommendation: either this issue (or an explicit prerequisite task) must create and check in a canonical `hazard-demo.jls` with a documented topology (the name implies a combinational hazard, i.e. reconvergent paths with mismatched delays — which itself exercises `resetPropDelay`/timing, not just static topology) before AC-1 is checkable at all.

2. **AC-1's acceptance test is gameable: "no manual edits" and "compiles standalone" say nothing about fidelity.** A minimal, technically-passing implementation could emit a CircuiTikZ document containing only trivial elements (e.g. a couple of gates) that happens to compile, while never exercising buses, multi-bit wires, wire labels, or hierarchy — because the one fixture named is a single flat "demo" circuit whose contents are undefined (see #1). Nothing in the AC requires the exported diagram to be recognizable as the source schematic (no visual/structural golden is specified, unlike #536 AC-1 which explicitly says "visual goldens checked in"). Recommendation: add a structural or rendered-visual golden comparison for the TikZ output, not just "it compiles."

3. **Subcircuits/hierarchy are unaddressed.** `ARCHITECTURE.md` describes `Circuit.load`/`finishLoad` resolving "subcircuits," and JLS supports nested circuit instances as first-class elements. Neither this issue nor #505's approximation-table framing (§3 risk 3: "memories, state machines, truth-table displays") mentions how subcircuit instances are exported — inlined, flattened, or represented as a black-box symbol. If the hazard-demo fixture (once it exists) happens to be flat, AC-1/AC-3 can pass while any real hierarchical courseware schematic — plausibly the common case for a "hardware course authoring" tool — breaks on first use. Recommendation: name subcircuit handling explicitly in the approximation table's scope, or state it's out of v1 with a boundary note (the issue has a "Boundary and reference notes" section that currently says nothing about hierarchy).

4. **AC-3's "every element type not rendered natively by CircuiTikZ" is unenumerated and therefore unverifiable as stated.** `ARCHITECTURE.md` lists roughly 30 concrete element classes in `jls.elem`. The issue names three examples (memories, state machines, truth-table displays) and calls that "with every loss named," but a reviewer has no closed list to check the delivered table against — a table covering only the three named examples while silently omitting e.g. RAM/ROM arrays, bus splitters/mergers, seven-segment displays, or probes would satisfy a literal reading of AC-3. Compare sibling issue #540 (FEAT-C24-5, print-symbol totality ratchet), which is explicitly built to enforce *registry-keyed totality* with a failing-build guarantee — this issue has no equivalent mechanical completeness check, only prose ("published in-tree"). Recommendation: either make AC-3 a mechanical sweep (iterate the element registry, assert every non-natively-renderable type has a table row) analogous to #540's ratchet, or explicitly scope AC-3 to a named element subset.

5. **AC-4's "byte-identical across the three CI platforms" claim is asserted without addressing the concrete cross-platform hazard for generated text: locale- and JDK-dependent numeric formatting.** Unlike #536 (SVG/PDF), where the issue correctly identifies font-metric platform variance as "the known-hard part" and assigns it a kill criterion (KC-24-1) and 4-6 mw budget for exactly that reason, this issue's TikZ text output has its own, unaddressed byte-identity hazard: coordinate/dimension formatting (`Double.toString`, `String.format` with a default vs. explicit `Locale`, trailing-zero/scientific-notation differences) can differ by JDK version or default locale across the three CI runner images even when the algorithm is identical. The issue inherits AC-2/AC-4's "byte-identical" bar wholesale from #505's SVG-focused risk-1 analysis without restating why it's expected to hold for a different artifact type. Recommendation: add an explicit requirement to format all emitted numbers via a fixed `Locale.ROOT` / fixed-precision formatter, and note this as the TikZ-specific instance of CAP-24 risk 1.

6. **New CI toolchain dependency (a LaTeX distribution with CircuiTikZ) is required by AC-2 but its cost is entirely unaddressed.** `grep` confirms no LaTeX/TeX Live reference exists anywhere in `.github/workflows/*.yml` today; CI currently runs on `ubuntu-latest`, `windows-latest`, `macos-latest` (`.github/workflows/ci.yml`), none of which ship LaTeX. AC-5 correctly fences this out of the *shipped jar*, which is good and consistent with the repo's stated minimalism (no Node/network deps, per #505 §8 exclusion 7 referenced in the capstone), but says nothing about the *CI-time* cost: installing a working TeX Live + circuitikz on three platforms on every run is a nontrivial, multi-minute-to-tens-of-minutes-per-platform addition, and package-manager availability/version pinning for circuitikz differs meaningfully between apt, Homebrew/MacTeX, and Windows TeX distributions (MiKTeX vs. TeX Live). Recommendation: name the concrete LaTeX distribution/action to use (e.g. `xu-cheng/latex-action` or a pinned TeX Live install script) and budget the added CI wall-clock/cache cost, or restrict the "builds clean in CI" job to a single platform with the other two only checking the generated `.tex` source is well-formed (weakening AC-2's cross-platform claim explicitly rather than leaving it implicit).

7. **"compiles standalone (documentclass + circuitikz only)" is ambiguous and could be read two incompatible ways.** LaTeX has a specific document class literally named `standalone` (commonly paired with circuitikz for cropped figure output), and the phrase could mean either "use `\documentclass{standalone}` plus the `circuitikz` package" or "the document is self-contained, using some class plus circuitikz." Given `\documentclass{standalone}` is the idiomatic choice for this exact use case, the ambiguity is a real implementation fork, not pedantry — a reviewer checking "documentclass + circuitikz only" literally could accept `\documentclass{article}` + circuitikz just as easily. Recommendation: name the document class explicitly.

8. **The issue's own ordering metadata puts real work here behind two unlanded prerequisites, and the dependency isn't restated in the body.** `ordering_after: [FEAT-C24-1]` (→ #536) is present only in the YAML block; #536 itself carries `ordering_after: [FEAT-C24-5]` (→ #540) and is blocked on an un-adjudicated Open Question (OQ-3, "PDF via SVG-to-PDF conversion or direct?" — flagged "Blocks PF-1's filing" in #505 but #536 was filed anyway with only a recommended default). So #537 sits three deep in a chain (#540 → #536 → #537) where the immediate predecessor (#536) is itself not yet resolved past "recommended default, pending REPLAN." A contributor picking up #537 in isolation (its body alone, without cross-referencing #536/#540/#505) would not know this and could start on the "theming seam" prematurely, duplicating or conflicting with #536's still-open PDF-direct-vs-conversion decision. Recommendation: restate the concrete blocking chain and its current unresolved state in "Boundary and reference notes," not just as an opaque `ordering_after` id.

9. **`band_mw: 2-3` cost estimate is asserted, not derived, and the issue doesn't address the CI-toolchain cost identified in finding 6 against that budget.** #505 states costs are "Filing-time re-derivation, not a measurement," which is an honest caveat, but nothing in #537 revisits whether standing up a three-platform LaTeX CI job is realistically inside a 2-3 "mw" band (an unexplained unit — not defined in this file, `ARCHITECTURE.md`, or the issue templates I checked) alongside the exporter code itself. This is a soft finding given the explicit disclaimer, but worth flagging since finding 6 suggests the estimate may be optimistic.

## What's solid

- Scoping the shipped-jar boundary (AC-5: LaTeX is CI/dev-time only) is correct, testable, and consistent with the project's recorded minimalism decisions (single self-contained jar, no Node/network deps) — good discipline, one line, moving on.
- The dependency on #536's "theming seam" rather than minting a second symbol vocabulary is consistent with #505's explicit risk 2 ("Two symbol vocabularies must not fork") and with `src/jls/Theme.java`'s existing registry-keyed design — sound architectural alignment, no objection.
- Framing approximations as a named, in-tree table rather than silent simplification (CAP-16 style, per the body) is the right instinct even though its completeness isn't yet mechanically enforced (see finding 4).

## Bottom line

The issue is a coherent slice of a well-organized capstone plan, correctly bounded away from the shipped jar and correctly deferring to a shared theming seam. But two of its five acceptance criteria (AC-1, AC-3) currently cannot be verified against anything concrete — one against a fixture that doesn't exist, one against an unenumerated set — and AC-2/AC-4's cross-platform byte-identity claim and its CI cost are asserted without the same rigor the sibling issue #536 applies to its own (structurally identical) determinism risk. None of this is disqualifying, but the issue needs the hazard-demo fixture named/created, AC-3 made mechanical or scoped, and the LaTeX CI cost priced before implementation should start.
