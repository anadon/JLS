## Findings

### 1. [High] The landing surface is undefined, and #805 doesn't even name its real blocker
AC5 says only "Nothing lands inside `SimpleEditor` (KC-37-1); if #316 stalls, this task waits" — it never says *where* the code does land. Parent feature #593's own boundary note names the target: "driven through #441's `MouseMachine`/`InteractionState`." But **#441 was closed as a duplicate into #84 on 2026-08-08** (confirmed via `issue_read` — `state_reason: duplicate`, migration comment on #441 pointing to #84). Both #804 and #593 have since received explicit "STALE REFERENCE — CORRECTION" comments (2026-08-08T17:44) fixing this dangling pointer and spelling out the real chain: `#440 → #84 → #804 → #593/#805/#806 → #521`. **#805 received no such correction and its body never names #84, #441, or `MouseMachine`/`InteractionState` at all.** Its `ordering_after` frontmatter lists only `[TASK-C593-1]` (#804) — #84 is not a stated prerequisite of #805 even though it is the issue that will create the collaborator class #805 must land its group-drag/align/duplicate logic in. An executor picking up #805 in isolation (as this task is designed to be picked up — it's `tier: task`) has no way to discover the concrete class to extend.

Verified in the checkout: `wc -l src/jls/edit/SimpleEditor.java` → 5852 (unchanged from every cited evidence commit); `grep -rl "MouseMachine\|InteractionState" src test` → no matches. The decomposition #805 depends on has not started.

### 2. [High] "Preserves connectivity or refuses by name" sets no functional floor — the criteria are gameable
AC1: "Group drag moves the whole selection with a stated snap rule, preserving every connection ... — or refusing by name." AC2 repeats the same disjunction for align/distribute. Nothing requires that refusal be rare, or that any nontrivial case actually succeed. An implementation that refuses every drag/align/distribute touching more than one connected element (accepting only the 0/1-element trivial case) satisfies AC1–AC2 to the letter — the test "fails at the pre-change commit" trivially, because the feature doesn't exist pre-change, and "refuses by name" is satisfied by any string. That implementation would ship a group-manipulation feature that never actually manipulates a nontrivial group, directly contradicting the parent feature's stated Outcome (#593: "behaves the way a Logisim-Evolution, Digital or CircuitVerse user expects on their first attempt"). There is no minimum success corridor (e.g. "the enumerated topologies in #592's catalog must succeed, not merely refuse") — see Finding 4, which makes this worse rather than better.

### 3. [Medium] "Documented reference rules" for align/distribute doesn't require matching any cited incumbent
AC2 only requires the rules be "documented," not that they match Logisim-Evolution/Digital/CircuitVerse conventions — despite #593's Outcome explicitly measuring success against those three editors and #592's catalog being built specifically to cite incumbent behavior row-by-row. A self-consistent but idiosyncratic align/distribute rule (e.g. always-align-to-first-selected when every incumbent aligns-to-last-selected, or vice versa) passes AC2 while failing the parity goal the whole CAP-37 program exists to serve.

### 4. [Medium] AC4 depends on a catalog that doesn't exist yet, and that dependency isn't declared
AC4: "Each behaviour ... corresponds to a scored GAP row in #592's catalog." `docs/` in this checkout has no ergonomics/parity/catalog file (confirmed by directory listing) — #592 (FEAT-C37-1, the catalog feature) is itself open and unbuilt. Sibling task #804 at least names its catalog-producing prerequisite explicitly in its own frontmatter (`ordering_after: [TASK-C592-2, 441]`, i.e. #803). **#805's `ordering_after` is only `[TASK-C593-1]`** — it never names #592, #803, or any catalog-producing task, even though AC4 requires rows to already exist and be scored specifically for group-drag/align/distribute/duplicate before this task can close. If #804 lands before #592/#803 do, AC4 is unsatisfiable through no fault of the implementer, and the task has no stated fallback (a `WAIVED:`-style escape hatch exists in the sibling task-template convention seen elsewhere in this corpus, but #805 doesn't invoke it).

### 5. [Medium] Feasibility: the entire prerequisite chain is unlanded, and #805 doesn't flag this as a risk
Verified via `issue_read`: #440 (TASK-0019, the `jls.edit` coverage floor #84 is blocked on) is open, and `pom.xml:408` still reads "jls.edit is deliberately unfloored" — unchanged. #84 (the decomposition #805's manipulation logic must land in) is open with no landed extraction. #804 (TASK-C593-1, #805's own direct prerequisite) is open. So #805 sits at the end of a four-deep unlanded chain (#440 → #84 → #804 → #805) for a task priced at `band_mw: 1-1.5` — a price that covers only #805's own slice and says nothing about the fact that, per its own AC5, the task literally cannot be started today. This is a legitimate scheduling/readiness risk that the issue itself doesn't surface.

### 6. [Low-Medium] Scope overlaps existing, already-tested machinery without saying whether to reuse or duplicate it
- **Group drag (AC1)** overlaps `SimpleEditor.moveSelectionPlan` (`src/jls/edit/SimpleEditor.java:1053`) and `jls.collab.op.MoveElements`, which — per `test/jls/edit/MoveGestureTest.java`'s own javadoc — already handles "single- and multi-element pure relocations" through the `OpSink` seam, including a rejection path ("a `MoveElements` that would push an element off the canvas is rejected and leaves the circuit byte-identical"). That is already most of AC1's "preserve or refuse" shape.
- **Duplicate (AC3)** overlaps the existing Cut/Copy/Paste clipboard path (`SimpleEditor.java` ~1172–1812, `EditOp.PASTE`), which already detects and reports duplicate-name collisions on paste (`"Paste will result in elements with duplicate names"`, ~line 4986).

#805 doesn't say whether "group drag" and "duplicate" are new features built on top of this existing infrastructure or parallel logic in the new (not-yet-created) collaborators. Left unresolved, this risks two divergent implementations of "move a set of elements" and "place a copy of a set of elements" — one via `moveSelectionPlan`/paste, one via whatever #805 builds — which is exactly the kind of duplication the #316 decomposition is supposed to prevent.

### 7. [Low] "Stated snap rule" and "stated offset" are undefined placeholders
AC1 and AC3 leave the snap increment and duplicate-placement offset entirely to the implementer, with no default and no acceptance corridor. Reasonable for a task-level issue in isolation, but combined with Finding 3 (no incumbent-conformance requirement) and Finding 4 (no live catalog to check against), there is currently no mechanism that would catch a chosen value diverging from what students coming from Logisim-Evolution/Digital/CircuitVerse expect — which is the entire point of the CAP-37 program this task serves.

## What's solid
- The core hard-constraint framing — "preserve connectivity or refuse by name, never silently disconnect" — correctly identifies the actual failure mode worth guarding against, and is a good design invariant independent of the criteria-gaming risk in Finding 2.
- The scope split against sibling tasks is clean: #804 (compound selection gestures) and #806 (wire-segment resolution) were read in full and their acceptance criteria do not overlap #805's group-drag/align/distribute/duplicate scope.
- AC5's refusal to let anything land inside `SimpleEditor` is the correct call given #316/#84's still-unlanded state (verified: 5852-line file, no decomposition artifacts), even though (per Finding 1) the issue should say so by naming #84 directly rather than leaving it to be inferred.
