# Issue #545: FEAT-C27-1: the README shows the product — a stranger scrolling for ten seconds sees circuits drawn, simulated and compared before reading a single paragraph
- Lens: visionary
- Date: 2026-08-08
- Reviewer: Claude Opus 5
- Verdict: endorse-with-reframing

## What this issue is actually for

Not "the README has no images." The end is: **an instructor or switcher can decide in ten
seconds whether JLS deserves their next ten minutes.** CAP-27 (#511) is right that this is
the cheapest capstone on the board and that it gates every adoption capstone; a shop window
costing 1–2 mw sitting in front of the ~150 maintainer-weeks of capability programs in
`docs/capability-roadmap/README.md` (P1–P6) is correctly proportioned. The goal is
endorsed without reservation. The mechanism as specified is wrong in three places, and the
project already contains the better mechanism.

## Reframing 1 — the README's problem is subtraction, not addition

`README.md` is 368 lines. Lines 12–70 are installer verification: Authenticode/SignPath
publisher strings, `SHA256SUMS-installers-<os>-<arch>`, `gh attestation verify`, the GPG
non-signing custody rationale for the rpm and AppImage. Lines 148–184 are the Wayland
toolkit matrix and the headless-sway rig. Lines 203–287 are optional dev tooling and the
devcontainer. Lines 289–323 re-tell `.jls` container archaeology that
`docs/file-format.md` already owns normatively. **The top of this file is a loading dock,
and nothing in #545's AC set touches that.** Adding two screenshots and a GIF above sixty
lines of cosign incantations produces a README that shows the product and then immediately
resumes not being about the product; a stranger's ten seconds of scroll still lands in
supply-chain prose.

The delta that most changes the outcome is re-homing, and it is *cheaper* than the GIF:
README shrinks to ~80 lines (what it is, one still, one motion artifact, the positioning
section, one install line per OS, links out), with packaging/verification moving to a new
`docs/install.md` (much of it already duplicated in `SECURITY.md`), the Wayland matrix to
`docs/desktop-platforms.md` next to the rig it describes, and the container prose deleted
in favour of the `docs/file-format.md` link that already exists. I would add this as an
AC. As written, #545 can be fully satisfied and a visitor still bounces.

## Reframing 2 — the images should be build products now, and the tree can already do it

AC-1 checks images in by hand; AC-4 fails the build when a referenced path does not exist.
That drift check pins the wrong invariant. A missing path is a typo, caught by any link
checker. The failure that actually occurs is that the file is still there and no longer
depicts the program — exactly what the FlatLaf default, the #381 dark variant, and the
empty-state panel will each do to a 2026-08 screenshot. AC-4 buys a green bar over a
stale picture, which is the failure mode `docs/capability-roadmap` and #381 §9 both name
in other contexts ("a green bar is not a user").

Two sibling issues in the same capstone family already demand the right invariant:
#519 AC-3, *"Screenshots in README/docs are build products, not hand-pasted files"*, and
#551 AC-2, *"regenerated by one scripted command in CI ... so renders cannot silently
drift."* #545 alone entrenches hand-pasted binaries and then asks CI to bless them. It
also does this while explicitly binding itself to #73 §4's invariant — *"README claims
nothing a fresh clone cannot reproduce"* — with a deliverable a fresh clone cannot
reproduce. A screenshot is a claim about what the program looks like. This tree refuses
unbacked claims everywhere else (`HelpTopicsTest`, `HotkeysHelpAccuracyTest`,
`CliFlagTableTest`, `ThemeTest`'s simulated-vision transform, the ratchet culture in
ARCHITECTURE.md). The README should not be the one surface exempted.

The reason to fix this here rather than defer to #519 PF-3 is that **the pipeline mostly
exists at HEAD**, and the issue's "hand-captured images are acceptable until CAP-35 lands"
is a concession bought for nothing:

- Circuit renders need no GUI at all. `-i out.svg` / `.png` ships today
  (`src/jls/JLSStart.java:765,810,821`, issues #71/#154), is headless, is exercised by
  `CliImageExportTest`, and is the same path #551 AC-1 builds the gallery on. A drawn
  circuit picture is one `java -jar ... -i` invocation over a checked-in `.jls`.
- App-window stills are a small delta on infrastructure that runs on **every push**.
  `scripts/wayland-rig.sh` already boots the shaded jar under headless sway, screenshots
  with `grim` into `$ARTIFACTS_DIR` (`desktop-before.png` / `desktop-after.png`), and even
  runs an ImageMagick pixel diff. What is missing is a circuit to open and a named capture
  list — not a pipeline.

Make the stills generated, and AC-4 disappears rather than being satisfied: a regenerated
file always exists, and "regenerate and compare" is a real drift check. That is the
reframing that makes the problem go away, and it hands #519 PF-3 a working pipeline
instead of a migration.

## Reframing 3 — the GIF is the wrong motion artifact

Be honest about the limit: *drawing* — palette click, drag-to-wire, dialog — is genuinely
not a build product today; the rig drives keyboard via `wtype` and has no gesture driver.
So the GIF is the one item that must be hand-captured. But it is also the item worth
questioning. An animated GIF is unreproducible, a large binary in a project whose identity
is byte-reproducibility, unreadable at README width for a four-second wiring gesture, and
stale the day the palette changes.

What the visitor wants from motion is "what does simulating feel like." JLS can generate
that: a checked-in circuit plus a `-t` vector file, run under the batch simulator, rendered
as a short strip of SVG frames (or an SVG animation) at chosen timestamps via the export
that already ships. Byte-reproducible, diffable in review, theme-aware (#551 AC-4 already
worries about light/dark), kilobytes, and regenerable by CI. That is strictly more on-brand
than a screen recording, and it is out of scope for nothing — it uses two shipped CLI paths.
Keep a hand-captured drawing GIF if the maintainer wants one, but it should be the
*optional* item, not the load-bearing one.

## Reframing 4 — the table sells JLS on the axis where it is weakest

AC-2 requires a four-way table honest per `docs/hdl-support-research.md`. That document is
an HDL-support research pass: it covers Digital (`[verified]`, §"the reference point") and
Logisim-evolution (`[verified follow-up]`). It does not mention CircuitVerse or Falstad
once — `grep -rn "Falstad\|CircuitVerse" docs/ *.md` returns nothing outside
`lf-08-clocks-and-cdc.md`. CAP-27's cited evidence path `docs/reviews/evidence/2026-08-
niche-survey/` does not exist in the tree. **Half the table's columns have no citable
source, under an AC that names a source.** Either narrow the table to the two tools whose
source this project has actually read, or land the niche-survey teardowns as a `docs/`
file first and cite that.

Deeper: a checkmark grid against rivals is the most rot-prone artifact you can put on a
README and the one a competitor's next release can falsify. And the ten seconds it buys
sells *drawing and simulating* — which CircuitVerse and Falstad also do, in a browser, with
zero install. That is JLS competing where it loses.

The differentiator visible in this tree and invisible in the issue's plan is that JLS is the
educational simulator whose **grading interface is a documented stability contract**
(`docs/batch-interface.md`), with VCD export for GTKWave/Surfer, a headless multi-arch
container for autograders, a byte-reproducible jar with provenance attestation, a normative
simulation-semantics spec, and structural Verilog export. The person who decides adoption is
the instructor. The persuasive ten seconds is: a student circuit, the one command the
autograder runs, its output, and a waveform — not a mouse drawing a wire. I would replace
the grid with a short "what JLS is for / when to use each rival instead" section, which is
cheaper to keep true, matches this project's unusually good honesty genre
(`CellValidator`'s apology paragraphs, `VhdlEmitter`'s disclaimer, the recorded decisions
with revisit triggers), and cannot be invalidated by someone else's release notes.

## Smaller findings

- **AC-3 is near-vacuous at HEAD.** The README has exactly one badge (line 3, OpenSSF
  Scorecard) and no decorative ones to remove. Ironically it is the badge that answers a
  supply-chain auditor's question, not a prospective user's. The honest action is *adding*
  informative badges (latest release, build status, Java floor) — the opposite verb from the
  one AC-3 uses. AC-3 was written against an imagined README with badge soup.
- **The seam between #73, #381 and #545 is cut along the wrong axis.** Three issues now edit
  one file: #73's "README onboarding pass" task, #381's README items, and this "delta,"
  which owns the drift test for images the other two produce. That is content-vs-content.
  The natural seam is mechanism-vs-content: **one issue owns the README's structure and the
  image pipeline; #73/#381 keep the in-app surfaces they were always about.** #545 carving
  a delta out of another issue's unfiled task is the smell.
- **`ordering_after: [381]` should be dropped, not merely breakable.** #381 bundles a dark
  theme, a 96-literal renderer sweep, a manual cross-platform scaling matrix, samples, the
  empty-state panel, and an n=5 usability trial. Attaching the cheapest capstone slice to
  the tail of the most expensive task on the board is a scheduling error even as convention.
  If the stills are generated, re-capture cost is zero and the convention loses its only
  stated rationale.

## Disposition

Endorse the outcome; reframe the mechanism. Concretely, I am disregarding AC-1's "checked
in," AC-4 as written, and AC-2's source and shape: replace them with (a) README structural
surgery to ~80 lines with packaging re-homed, (b) generated stills from `-i` export and the
existing sway rig, with regenerate-and-compare as the drift check, (c) generated SVG
simulation frames as the motion artifact and any GIF as optional, (d) a positioning section
citing only tools the tree has verified evidence for, leading with the batch/grading
contract. Every substitution is cheaper or equal in maintainer-weeks, and each one deletes
future work in #519 PF-3 rather than creating it.
