# Issue #617: TASK-C558-4: an imported Digital circuit arrives laid out and readable, not as a pile of correctly-wired elements at the origin
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of the issue

#617 is one of five tasks under FEAT-C29-2 (#558, "a Digital .dig circuit opens in JLS"), itself under CAP-29 (#513). It owns coordinate/orientation/wire-routing translation from Digital's `.dig` geometry onto JLS's grid, explicitly scoped as "coordinate translation, not auto-layout," and disclaims the heuristic layouter lineage (#62) as belonging to geometry-free netlist imports only. Zero `.dig`/Digital/XStream code exists anywhere in this repo today (`grep -rn "\.dig\b|XStream" src/` and `docs/` — the only hits are in `docs/hdl-support-research.md`'s survey prose and other planning issues); this whole family (#556, #558–562, #608–639) is pre-implementation planning stacked several layers deep.

## Findings, most severe first

### 1. AC-2/AC-3 contradict the issue's own boundary note by re-deriving a solved problem instead of reusing it
The Boundary notes say: "This is coordinate translation, not auto-layout. The heuristic layouter lineage (#62) is for netlists that arrive without geometry; `.dig` arrives with it." But AC-2 requires "where [Digital's routing] is not [expressible in JLS], the wire is re-routed" and AC-3 requires "a grid-snap that would collide two elements is resolved deterministically." Re-routing wires around obstacles and resolving element collisions on a grid *is* the auto-layout problem — it is exactly what `src/jls/hdl/layout/HeuristicLayeredLayouter.java` and `LayoutInvariants.java` already solve, with a tested contract (zero overlaps, grid-locked, orthogonal nonzero segments — see #62's IC1/IC3) and 31 unit tests. By ruling #62's seam out of scope by fiat, #617 commits its implementer to hand-rolling a second, untested collision-resolution and re-routing algorithm alongside the one that already exists and is invariant-checked. This is either scope creep (silently re-implementing #62's machinery under a different name) or an unstated dependency that should instead route obstacle cases through `SchematicLayouter`/`LayoutInvariants`. As written, an implementer who takes the boundary note literally has no design for AC-2/AC-3's harder branches at all.
**Recommendation:** either explicitly permit falling back to the #62 seam for the "not expressible" / "would collide" cases (and add that as an ordering dependency), or specify the deterministic resolution algorithm here so it isn't invented ad hoc and diverges from #62's invariants.

### 2. AC-1's determinism claim is unfalsifiable without a stated coordinate-mapping function, and the grid units genuinely differ
AC-1: "Element coordinates and orientations map to JLS grid positions deterministically; re-importing the same file twice produces identical placement." This is trivially satisfiable by *any* deterministic function, including `identity` or `round-to-nearest-grid`, regardless of whether the result resembles the source layout — the acceptance test as stated cannot distinguish "looks like what the instructor drew" (the stated Outcome) from "deterministically wrong." `Geometry.SPACING = 12` (`src/jls/core/Geometry.java:19`) is JLS's fixed grid unit; Digital's native grid unit is different and the issue never states the scaling/rounding rule (linear scale? 1:1 pixel copy? nearest-multiple snap?). A naive 1:1 copy could place adjacent Digital elements on the same or overlapping JLS grid cells (feeding AC-3's collision case constantly rather than rarely), while a scaled copy changes relative spacing in ways "identical placement on re-import" does nothing to catch. The AC needs either a worked example or a visual/structural-similarity check (e.g., relative ordering and adjacency preserved), not just idempotence.
**Recommendation:** name the mapping function (or defer it to a cited design doc) and add a criterion that checks fidelity to the source layout, not just repeatability.

### 3. Upstream contract gap: #614 (TASK-C558-2, the element-mapping task this "places") never promises to carry geometry through
#617's outcome says it "places" the elements TASK-C558-2 maps. But #614's four ACs are entirely about element-type mapping, attribute correspondence, and net-partition equivalence ("AC-4: Wiring and connectivity survive the mapping... asserted structurally rather than visually") — none of #614's ACs mention preserving or forwarding Digital's source coordinates, orientation, or wire-routing points from the parsed model. If #614 lands as specified, #617 has no guaranteed input to translate: it would need to reach back into TASK-C558-1's (#612) raw parsed model itself, bypassing #614's mapping table, or #614 needs a fifth AC nobody has written. This is a real hole between sibling tasks in the same feature, not a nitpick — #617's `ordering_after: ["TASK-C558-2 (the mapped elements this places)"]` asserts a data contract that #614's own acceptance criteria don't establish.
**Recommendation:** add an AC to #614 (or a note here) requiring the mapping table/output to retain each Digital element's original position, orientation, and each net's routing waypoints, or explicitly route #617 to consume TASK-C558-1's raw model directly.

### 4. "Expressible in JLS" (AC-2) is undefined against the actual Wire model
`src/jls/elem/Wire.java:12` documents `Wire` as "a wire segment (between two WireEnds)" — a single straight segment; multi-bend routes require chaining WireEnds. The issue never states what routing Digital emits (arbitrary polylines? diagonal segments? does Digital even allow non-orthogonal wires?) nor what "expressible" means operationally (any polyline via WireEnd chaining is "expressible" if you allow unlimited synthetic elbow points — so is the AC ever actually triggered, or is "re-routed... named in the report" dead code that never fires because everything is always expressible via enough WireEnds?). Left this vague, a submitter could satisfy AC-2 by always chaining WireEnds to replicate any routing exactly (never touching the "re-route + report" branch), which may be correct or may produce degenerate wire art with dozens of coincident-point segments — the AC doesn't say which failure modes actually count as "not expressible."
**Recommendation:** enumerate what does *not* map (e.g., diagonal segments if Digital allows them, routing through element bodies) so the re-route branch has a concrete trigger and a concrete report entry.

### 5. Gameable AC-3: "resolved deterministically rather than by iteration order" is satisfied by an arbitrary tiebreak that can defeat the Outcome
Any fixed rule — "when two elements collide, keep the one with the lexicographically smaller Digital element ID and nudge the other by one grid cell in +x" — is deterministic and passes AC-3 to the letter, while silently drifting the "instructor drew this" layout the Outcome paragraph cares about, with no report entry required (AC-3 doesn't cross-reference the report contract that AC-2 invokes). A grader running only the stated ACs cannot tell a defensible resolution (e.g., "nudge along the minority axis, log it") from one that scrambles a moderately dense circuit.
**Recommendation:** require collision resolutions to also be named/logged entries in #556's shared report contract, the same discipline AC-2 already applies to unrepresentable routing.

### 6. Feasibility/cost: `band_mw: "1"` looks underscoped against the sibling #62's actual cost
#62 (schematic auto-layout for geometry-free netlists) shipped an engine-neutral seam, a hand-rolled layered layouter, 31 unit tests, and *still* has its own rubric-verification task (#290) open — a multi-PR, multi-week effort for what is acknowledged to be a hard, NP-hard-adjacent problem (crossing minimization). #617's collision-resolution and re-routing requirements (AC-2, AC-3) are a lighter-weight but structurally similar problem, budgeted here at `band_mw: "1"` (roughly a fifth of #62's stated "4-6" band for the whole parent feature). Given finding #1 (no reuse of #62's tooling permitted) and finding #4 (undefined trigger conditions), the actual effort to build a correct, tested, deterministic collision/re-route path from scratch is likely underestimated.
**Recommendation:** re-cost after resolving findings #1 and #4, or explicitly bound scope (e.g., "collisions are rare and any deterministic nudge suffices, out-of-scope: readability of the nudge") so `band_mw: "1"` is honest about what's being skipped.

### 7. No hardening/bounds requirement on translated coordinates, despite project-wide untrusted-input discipline
The project's own standard (README's "hostile-input caps," ARCHITECTURE.md's `UntrustedFileHardeningTest`, and #558's own AC-4 XXE-hardening requirement) treats `.dig` as untrusted input everywhere else in this feature family. #617 is the one task that actually computes pixel/grid coordinates from attacker-controlled source values, yet none of its ACs mention bounding pathological coordinates (e.g., a `.dig` with element positions at `Integer.MAX_VALUE` or deeply negative, which could produce an enormous or negative-offset JLS canvas, OOM during placement, or integer overflow in the grid-snap arithmetic). This is squarely this task's responsibility (TASK-C558-1/#612 hardens the *parse*, not what #617 does with the parsed numbers).
**Recommendation:** add an AC bounding/clamping translated coordinates consistent with issue #38's hostile-input discipline, with a test fixture using extreme coordinate values.

## What's solid
- The Outcome statement is well-motivated and concrete: geometry fidelity is plausibly what separates an accepted migration from an abandoned one, and it correctly cites #558's outcome as the umbrella it serves.
- AC-4 ("nothing about the import locks geometry or marks elements read-only") is clear, testable, and consistent with #62's IC8 (import as one undoable-but-editable unit) and #558 AC-5 (import is undoable, not frozen).
- The dependency declaration (`ordering_after: TASK-C558-2`) is at least directionally correct even though its data contract is underspecified (finding #3); it correctly does not claim to be self-contained.
- Scoping wire-routing/collision handling out of TASK-C558-2 and TASK-C558-1 (parse-only) is the right decomposition in principle — the flaw is in how the excluded work relates to #62, not in the decomposition boundary itself.
