# Issue #489: Issue templates: record the tracker read-path quoting rule — `issue_read` deletes tag-shaped runs, `search_issues` is the lossless read path
- Lens: adversarial
- Date: 2026-08-08
- Reviewer: Claude Sonnet 5
- Verdict: needs-rework

## Summary of what's proposed

Insert a near-identical ~30-line HTML-comment block into the leading machine-read-only comment of `capstone.md`, `feature.md`, and `scientific_task.md`, documenting a claimed quirk of the `mcp__github__issue_read` tool (it strips tag-shaped runs, including inside code fences) versus `mcp__github__search_issues` (lossless when `body` is requested). No code, doc, or test outside `.github/ISSUE_TEMPLATE/` is touched.

## Findings

**1 (High) — the central damage claim is uncited and unfalsifiable.** The "Cost of not applying it" section asserts "three issue bodies corrupted" by rewrites driven off a stripped read, but never names which three issues. Every template this issue proposes to edit requires citations resolvable against a pinned commit or a specific artifact (`scientific_task.md` rule 3/6, `feature.md` rule A) — this issue's own most serious claim fails that bar it asks future authors to meet. A reviewer cannot check whether the "corruption" happened, was reverted, or is even distinguishable from ordinary edits. Recommendation: name the three issues (numbers + diff or before/after quote) or drop the claim to "observed but not preserved."

**2 (High) — the sole evidence is an unrecorded, session-local comparison with no artifact retained in the repo.** F1–F5 rest on "One issue, #404, read two ways in the same session on 2026-08-03" — no diff file, no test, no committed transcript. I partially reproduced the symptom independently: fetching #404 via `mcp__github__issue_read` in this review session returned `protected java.util.List savedAttributes() {` (bare `List`, no generic) and `The `` line names exactly the mechanism O1 shows.` (empty backticks around what should be a quoted token), matching the issue's F1 description. That corroborates the technical claim exists in this environment today, but the issue asks the repo to encode this as a settled, permanent fact ("Do not re-derive it") in a comment nobody enforces — if the MCP server's behavior changes (version bump, config change, different agent's tool), the block silently goes stale with no test and no recorded revisit trigger, unlike every other convention this repo records (contrast ARCHITECTURE.md's "Recorded decisions," each of which states an explicit revisit trigger). Recommendation: add a revisit trigger sentence, or point at a script/test that can re-verify the claim rather than asking humans to trust prose forever.

**3 (Medium) — acceptance criteria are gameable and test form, not substance.** The checklist's `md5sum` checks verify only that the pasted text is byte-identical to what the issue supplied; they do not verify the underlying claim is true, still true, or that the block is being read by anyone before filing. An executor can satisfy every checkbox by copy-pasting into an HTML comment that most humans skip past in the GitHub form UI, while the actual failure mode the issue worries about (a future author "fixing" non-existent damage) remains completely untested — no ratchet test, no CI check, nothing like this repo's `HeadlessCoreRatchetTest` / `NullMarkedRatchetTest` / `SealedHierarchyTest` pattern of pinning a convention with an assertion. Recommendation: at minimum add a repo-level test or script (e.g. a markdown/grep check) that fails if the block goes missing or drifts between the three files, so the convention has the same enforcement discipline as everything else CONTRIBUTING.md documents.

**4 (Medium) — DRY violation invites the exact drift the issue warns about.** The same ~30 lines are duplicated verbatim across `capstone.md` and `feature.md`, with a 3-line variant for `scientific_task.md`. Nothing in the acceptance criteria requires the three copies to stay in sync going forward; a future correction to the "nuance" paragraph (e.g. if the entity-escaping behavior changes) requires three synchronized hand-edits with no automated check that they were all made. A single canonical location (a new `docs/*.md` note, or a CONTRIBUTING.md section) referenced by one line per template would remove the drift risk entirely. Recommendation: single-source the block; templates get a one-line pointer.

**5 (Medium) — scope: this is a change to the issue-authoring pipeline, not to JLS.** Labeled `enhancement, documentation` alongside genuine product work, but it touches no `src/`, no normative doc (`docs/file-format.md`, `docs/simulation-semantics.md`, etc.), and no test — only prose aimed at whichever agent files the next issue. That may be legitimate given this repo's evidently agent-heavy, template-driven issue process, but it is worth the maintainer explicitly separating "meta-process hygiene for the tracker itself" from the product roadmap CONTRIBUTING.md points to (#33), so contributors don't mistake this for user- or codebase-facing work.

**6 (Medium) — the issue body embeds an instruction directed at the reading agent's tool choice, not just at a human executor.** "If you are reading this body through a tool and you see empty backticks... Re-read this issue with `mcp__github__search_issues`" is phrased as a directive to whatever process is currently reading the issue, inside the issue content itself, rather than as a completion-criteria bullet under Method. The issue is filed by the repo owner and the underlying technical claim checks out in this session (finding 2), so this is not itself malicious — but normalizing "issue bodies may redirect an automated reader's next tool call" as an accepted pattern in this tracker is exactly the shape a hostile version of the same trick would take if filed by a non-owner or a compromised account, and the templates don't distinguish "trusted meta-instruction from the maintainer" from "content that should never be treated as an instruction." Recommendation: state the read-path caveat as information for a human/agent to consider, not as an imperative re-read command, and keep any actual required re-read step inside the Method/Acceptance checklist where it's auditable like every other step.

**7 (Low) — acceptance criterion for the version-bump decision is underspecified.** "A decision is recorded on whether the template version headers... get bumped" doesn't say where it must be recorded or what satisfies it — unlike ARCHITECTURE.md's decisions, which are recorded in a fixed, discoverable location. As written, any PR comment saying anything at all technically closes this item.

**8 (Low, solid) — the insertion points are verified accurate.** I confirmed byte-exact anchors against the current tree: `capstone.md:77` ends `     fits.` immediately before the closing `-->` at line 78; `feature.md:81` ends `     convenience rendering, never evidence.` before `-->` at line 82; `scientific_task.md:103` ends `  next reader of the raw issue body.` before `-->` at line 104. The mechanical part of this issue (where to paste) is correct and low-risk to execute.

**9 (Low, solid) — the technical claim is at least partially independently reproducible.** As noted in finding 2, fetching #404 through `issue_read` in this review session did show bare-`List` and empty-backtick artifacts consistent with F1. This is not nothing — the issue isn't inventing a phenomenon from whole cloth.

## Verdict rationale

The mechanical instructions (where to paste, what text) are precise and verified against the actual files. But the issue fails several of the evidentiary standards it exists to codify: its single most serious claim (three corrupted issue bodies) is uncited, its acceptance criteria test paste-fidelity rather than correctness or durability, the content is tripled with no sync mechanism, and it embeds a directive-to-the-reading-agent pattern inside issue prose that the tracker's own conventions should probably guard against rather than model. These are fixable without abandoning the core idea — **needs-rework**, not should-not-proceed.
